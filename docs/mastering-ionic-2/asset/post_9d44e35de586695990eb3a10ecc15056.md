```typescript
// src/pages/rate-food/rate-food

import { Component } from '@angular/core';
import { IonicPage, NavController, NavParams } from 'ionic-angular';

import { AngularFire, FirebaseListObservable } from 'angularfire2';
import * as firebase from 'firebase';

@IonicPage()
@Component({
  selector: 'page-rate-food',
  templateUrl: 'rate-food.html',
})
export class RateFoodPage {

  rateItems: FirebaseListObservable<any[]>;
  data: {name?: string, review?: string, rating?: any} = {};
  constructor(
    public navCtrl: NavController,
    public navParams: NavParams,
    public af: AngularFire) {

    this.rateItems = af.database.list('/rateItems');
    console.log(this.navParams.data);
    this.data.name = this.navParams.data.name;
  }

  rate() {
    let data = {
      "rating": this.data.rating,
      "review": this.data.review
    }
    let url = "rateItems/" + this.navParams.data.$key +
      "/" +
      this.makeid();
    firebase.database().ref().child(url).set(data);
    this.navCtrl.pop();
  }

  makeid() {
    var text = "";
    var possible =
      "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789";

    for( var i=0; i < 8; i++ )
      text += possible.charAt(Math.floor(Math.random() *
        possible.length));

    return text;
  }
}
```

We have used the `makeid()` function to generate random `$keys` for reviews/rating of the same `foodItems` by multiple users. Here you can see we haven't used the `AngularFire` method and rather used directly Firebase method because we will not be able to insert data in this way using `AngularFire` standard functions.

## Structuring and securing data

While storing and structuring data inside Firebase we have to think twice about how we will be fetching the data for the application. This problem is the same as when we use any other NoSQL database such as MongoDB. We should prefer flattening data rather than nesting everything and while fetching the data we have to join the flattened data.

Let's take the example of a blogging website where users create blog posts and all blog posts have comments. So, rather than nesting data in Firebase we prefer to divide it:

```json
{
  "users": {
    "user1": {
      "name": "John Smith",
      "type": "editor",
      "blogs": {
        "post1": {
          "id": 123456,
          "title": "Welcome to Ionic",
          "post": "Ionic is an open source SDK for hybrid apps"
        },
        "post2": {
          "id": 123457,
          "title": "Welcome to Ionic",
          "post": "Ionic is an open source SDK for hybrid apps"
        }
      }
    },
    "user2": {
      "name": "Adam",
      "type": "admin",
      "blogs": {
        "post1": {
          "id": 234567,
          "title": "Welcome to Ionic",
          "post": "Ionic is an open source SDK for hybrid apps"
        }
      }
    }
  }
}
```

This way of storing the data is initially easy to handle but later on, as the data increases, querying the dataset will be slow and performance will be harmed. So, the best way to store data is:

```json
{
  "users": {
    "user1": {
      "name": "John Smith",
      "type": "editor",
      "blogs": {
        "123456": true,
        "123457": true
      }
    },
    "user2": {
      "name": "Adam",
      "type": "editor",
      "blogs": {
        "234567": true
      }
    }
  },
  "blogs": {
    "123456": {
      "title": "Welcome to Ionic",
      "post": "Ionic is an open source SDK for hybrid apps"
    },
    "123457": {
      "title": "Welcome to Ionic 2",
      "post": "Ionic is an open source SDK for hybrid apps"
    }
  }
}
```

Now we have stored the data inside Firebase and the next step is to fetch the data and join it back. Joining flattened data is a bit difficult but this approach comes with a lot of performance and modularity. Let's see how we can fetch the above data and join it.

As Firebase uses web sockets, performance will be high while fetching the data this way and Firebase internally does optimizations on incoming and outgoing requests.

Firebase also provides a set of security rules for securing our data and helps determine who has read and write permission for the data set. All the security rules are in the dashboard inside the **Security & Rules** tab. Inside our application, the application data is user-defined and associated with the user, so we have set the rules accordingly:

![](img/c54e3488d7687ea0d26e8c2ce3cdfae3_317_0.png)

There are three types of rules:

- `.read` - when data is allowed to be read by users
- `.write` - when data is allowed to be written
- `.validate` - defines correctly formatted data and validates before pushing to the database

Security rules are in the JSON structure as you see in the previous screenshot and this makes it easier to understand and set rules. You will be associated with the user, so we have set the rules accordingly. In our application we first need to store the user-related data during the signup process such as the name, e-mail, and other details:

```json
{
  "rules": {
    "users": {
      "$user_id": {
        ".read": "$user_id === auth.uid",
        ".write": "$user_id === auth.uid"
      }
    }
  }
}
```

We have created a users model to store these details. We have nested the data inside a `$user_id` key so that we can create an access control and only the user who created this data set can edit and access it. Similarly for `feeds`, users can only read the feeds and can't write a feed to it:

```json
{
  "feeds": {
    ".read": true,
    ".write": false
  }
}
```

There are ways inside Firebase that help increase performance while querying data. For example if we have scores of students inside a model and we need to query that data by score then we can use `.indexOn` inside the rule so that performance while fetching records increases. You can study more about securing data inside Firebase here: https://firebase.google.com/docs/database/security/.
