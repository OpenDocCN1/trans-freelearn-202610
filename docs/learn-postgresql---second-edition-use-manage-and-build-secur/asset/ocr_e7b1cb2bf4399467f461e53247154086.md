For instance, in the preceding example, you can see that `rolcreatedb` is false, which means that the role has been created (or altered) with the NOCREATEDB option.

The role password (`rolpassword` field) is expressed as a hash, with the identifier of the algorithm used (in the above, SCRAM-SHA-256).

Why do we need two similar views of the same data? Only cluster superusers can query pg_authid, while every user can query pg_roles, since there is no risk of the role password being revealed (as you can see the password field has been masked out).

What about group membership? You can query the special `pg_auth_members` catalog to get information about what roles are members of what other roles. As an example, the following query provides a list of groups:

```
```sql
forumdb=> SELECT r.rolname, g.rolname AS group,
                 m.admin_option AS is_admin
             FROM pg_auth_members m
             JOIN pg_roles r ON r.oid = m.member
             JOIN pg_roles g ON g.oid = m.roleid
             ORDER BY r.rolname;
```
