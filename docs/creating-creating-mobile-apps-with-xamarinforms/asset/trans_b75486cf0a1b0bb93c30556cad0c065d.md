## 简介

这是一本关于使用 Xamarin.Forms 编写应用程序的书的预览版。Xamarin.Forms 是 Xamarin 于 2014 年 5 月推出的面向 iOS、Android 和 Windows Phone 的激动人心的移动开发新平台。Xamarin.Forms 让你可以使用 C# 和 XAML（可扩展应用程序标记语言）编写共享用户界面代码，这些代码会映射到这三个平台上的原生控件。

这本书是预览版，因为它并不完整。它只有六章。我们预计最终版本将至少增加六章，并且这个预览版中的章节可能会得到充实、增强或完全重新构思。该书的最终版本可能会在 2015 年春季出版。

## 本书读者对象

本书面向那些希望使用单一代码库为三个最流行的移动平台（iOS、Android 和 Windows Phone）编写应用程序的 C# 程序员。Xamarin.Forms 也适用于那些最终希望使用 C# 和 Xamarin.iOS 及 Xamarin.Android 库来针对这些平台原生应用程序编程接口（API）的程序员。Xamarin.Forms 可以极大地帮助你入门这些平台，或者构建原型或概念验证应用程序。

### 前提假设

本书假设你了解 C#，并且对 .NET Framework 的使用有一定程度的熟悉。然而，当我讨论一些对近期开始学习 C# 的程序员来说可能有些陌生的 C# 和 .NET 特性时，我会放慢速度。特别是，第 3 章中引入 `async` 关键字和 `await` 运算符，是在一段展示如何使用传统回调方法进行异步编程的讨论之后。

## 更新代码示例

构成 Xamarin.Forms 的库通过 NuGet 包管理器分发。Xamarin.Forms 包由五个动态链接库组成：Xamarin.Forms.Core.dll、Xamarin.Forms.Xaml.dll、Xamarin.Forms.Platform.iOS.dll、Xamarin.Forms.Platform.Android.dll 和 Xamarin.Forms.Platform.WP8.dll。Xamarin.Forms 包还需要 Xamarin Support Library v4（Xamarin.Android.Support.v4.dll）和 Windows Phone Toolkit（Microsoft.Phone.Controls.Toolkit.dll），它们应会自动包含。

当你使用 Visual Studio 或 Xamarin Studio 创建新的 Xamarin.Forms 解决方案时，某个版本的 Xamarin.Forms 包会成为该解决方案的一部分。但是，这可能不是 NuGet 提供的最新 Xamarin.Forms 包。以下是更新该包的方法：

在 Visual Studio 中，右键单击解决方案资源管理器中的解决方案名称，然后选择**管理解决方案的 NuGet 包**。在对话框左侧选择“已安装的包”以查看当前安装的内容，并在左侧选择**更新**和**nuget.org**以更新包。如果有可用更新，单击**全部更新**按钮是最容易将其放入解决方案的方法。

在 Xamarin Studio 中，在“解决方案”列表中各个项目的“包”下，选择 Xamarin.Forms 包，然后从工具下拉菜单中选择“更新”。

存储在 GitHub 上的本书源代码不包含实际的 NuGet 包。Xamarin Studio 会在你加载解决方案时自动下载它们，但 Visual Studio 不会。首次将解决方案加载到 Visual Studio 后，右键单击解决方案资源管理器中的解决方案名称，然后选择**管理解决方案的 NuGet 包**。你应该会在对话框顶部看到一个**还原**按钮，可以利用它还原包。然后，你可以通过选择左侧的**更新**和**nuget.org**并（如果有更新）按下**全部更新**按钮来更新包。

## 第 1 章

## Xamarin.Forms 如何融入其中？

编程中有很多乐趣。分析问题、将问题分解成小块、制定解决方案、规划策略、从不同角度探讨问题以及编写代码，都有乐趣。看到程序第一次运行会带来许多乐趣，而随后急切地投入代码，让它更好、更快，则带来更多乐趣。

追查 bug、确保程序运行平稳且可预测，也常常充满乐趣。很少有事情能像最终识别出一个特别顽固的 bug 并彻底根除它那样令人愉快。

甚至当你意识到最初采取的方法并非最佳时，也有乐趣。许多开发人员发现，他们在编写程序时学到了很多，包括有更好的方式来组织代码。有时，部分甚至完全重写可以产生好得多的应用程序。这个过程就像站在自己的肩膀上，获得这种视角和知识带来了很多乐趣。

然而，编程并非所有方面都那么愉快。最糟糕的编程工作之一，是把一个现有的正常运行的程序用完全不同的编程语言重写，或者将其移植到另一个具有完全不同的应用程序编程接口（API）的操作系统上。

这样的工作可能非常辛苦。然而，这样的重写很可能很有必要：在 iPhone 上极受欢迎的应用程序在 Android 设备上可能会更受欢迎，而且只有一种方法可以找出答案。

但问题在这里：在你浏览原始源代码并将其转移到新平台时，你是一路上都保持相同的程序结构以便两个版本并行存在？还是尝试进行改进和增强？

当然，诱惑是彻底重新思考应用程序，让新版本变得更好。但两个版本之间偏离得越远，将来就越难维护。

因此，将一个应用程序分叉为两个时，一种与生俱来的恐惧感弥漫其中。每写一行代码，你都会意识到所有未来的维护工作、所有未来的修订和增强，都将变成两份工作，而不是一份。

这不是一个新问题。半个多世纪以来，开发人员一直渴望能够编写一个在多种机器上运行的程序。这正是高级语言最初被发明的原因之一，也是“跨平台开发”这一概念能够继续对程序员产生强大吸引力的原因。
