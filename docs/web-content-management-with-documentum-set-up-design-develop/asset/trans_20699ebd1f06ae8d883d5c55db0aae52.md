## 10 设计 Documentum 应用

慢工出细活——这是一句老话，但极其贴切。你们中的许多人一定会同意，成功的项目实施关键在于良好的设计。设计越健壮、灵活且可扩展，其开发过程就越顺畅，后续的维护也越容易。无论选择何种技术，一个经过深思熟虑的良好设计都能避免软件开发生命周期后期出现问题。

Documentum 仍然不是一种被广泛理解的技术，因此有必要建立在良好的设计之上。本章包含一些需要遵循的基本指导方针和良好的设计实践，以确保 Documentum 解决方案达到可接受的标准，并在开发、部署以及维护/未来发布等各个阶段不会出现已知问题。

Documentum 是一项令人兴奋的技术，但需要被很好地理解和设计。在开始设计和开发之前，请注意以下几点：

- 分析网站结构和导航流程。
- 确定网站上内容的性质，并将其分类为纯静态、频繁更新、纯动态等。
- 对内容类型进行分类，例如图像、文本文档、横幅、表格和富媒体（列表可根据网站性质而变化）。
- 浏览网站上的每一个页面，并确定业务用户可以创建/贡献的页面，以及那些必然需要应用开发团队（IT 人员）参与的页面。

### 10.1 案例研究——简单的新闻网站

学习任何东西最好的方式是通过示例。让我们以一个虚构的新闻网站为例进行简单案例研究，该网站选择通过 Documentum Web 内容管理系统发布其在线版本。图 10.1 显示了该网站的首页，展示了其页眉部分、页脚部分、主体（中心窗格）和侧边导航链接。

大多数网站都有类似的基本布局，主要区别在于页面的结构和外观。如果你仔细研究首页，你会发现它可以分为以下几个部分：

- 页眉，显示新闻网站名称、日期和出版公司
- 页脚，显示版权信息和其他链接，如隐私政策、联系我们等。
- 网站各页面的侧边导航链接
- 中心窗格显示所选新闻文章

![](img/b18244e6621ecc39cef03ff6c0e55e7c_135_0.png)

图 10.1：虚构新闻网站的首页

使用 Documentum WCM 管理此网站的想法是，无论网站页面如何，页眉和页脚始终保持不变，网站结构也保持恒定，显示侧边导航链接和中心页面内容。

每天，页面的外观和感觉都保持不变——发生变化的是实际的新闻内容以及新闻文章或链接的名称。

想象一下，新闻内容贡献人员每天依赖 IT 人员根据当天的相关新闻创建和更新页眉日期、侧边导航链接和文章。

进入 Documentum WCM 的世界。我们现在将通过这个简单示例讨论如何使用 Documentum 提供的丰富功能来定义网站组件的模板和结构。

一旦 Documentum WCM 设计就绪，报纸业务团队只需使用 Documentum 系统每天创建、更新和发布文章，以保持报纸网站最新并运行，而无需涉及技术 IT 人员！

### 10.2 开始 Documentum 设计

为了对网站上的内容进行模板化，让我们仅以中心窗格新闻文章设计为例，看看如何从 Documentum 中创建和发布它。

如果你仔细分析中心窗格文章，你会发现它可以细分为以下几个部分：

- 横幅“头条”图像
- 新闻文章日期
- 正文（主要新闻内容）
- 完整文章链接（相关详情）

其思路是在 Documentum 中设计并创建一个表单，业务用户只需填写相关详细信息（实际内容），系统随后负责外观和感觉（网页布局）以及向网站主机的发布。

在 Documentum Web Publisher 的术语中，这样的表单称为模板。模板不过是一个 XML 文件，其中为用户需要填写的每个模板字段都有 XML 元素。每个模板字段的行为和验证通过一个 Rules 文件控制，该文件是另一个 XML 文件。最后，基于模板的页面布局通过一个 Presentation 文件实现，该文件不过是一个 XSL 文件，它对从模板 XML 文件创建的内容 XML 文件进行样式设置并生成必要的 HTML 输出（或其他格式，如 WML、xHTML 等）。

图 10.2 说明了这些概念。

![](img/b18244e6621ecc39cef03ff6c0e55e7c_137_0.png)

图 10.2：Web Publisher 模板及支持文件

当你创建 Web Publisher 模板时，它必须附加到 Docbase 中的一个对象类型，以便每当从该模板创建实例或内容时，内容都会作为相应对象类型的实例创建。

例如，模板 temp.xml 与对象类型 my_object 相关联。每当使用 temp.xml 创建内容时，它实际上是对象类型 my_object 的一个实例。

让我们首先使用 Documentum Application Builder 创建一个自定义对象类型，然后在 Web Publisher 中创建模板并将其与自定义对象类型关联。

### 10.3 使用 Documentum Application Builder (DAB)

启动 Documentum Application Builder 并选择我们之前创建的 Docbase。提供安装用户名和密码（如果是 Windows NT 服务器，可选提供域名）以登录。

![](img/b18244e6621ecc39cef03ff6c0e55e7c_137_1.png)

图 10.3：DAB 登录对话框

我们现在将创建自定义 DocApp 来存储和打包应用程序的自定义对象。登录后选择创建新 DocApp 并为自定义 DocApp 提供名称。

为 DocApp 提供一个友好的名称，例如：TestDocApp。此 DocApp 将容纳我们为业务应用程序创建的自定义对象。

DocApp 创建后，它存储在 Docbase 中 System 柜子的 Applications 文件夹内，与 DocApp 名称相同的文件夹中。

因此，在我们的例子中，TestDocApp 存储在 dev_doc Docbase 的以下位置：cabinets/System/Applications/TestDocApp。

请注意，初始创建 DocApp 时它处于签出状态。你需要使用 DAB 菜单选项显式签入 DocApp，或右键单击并选择签入 DocApp。

### 10.4 在 DocApp 中创建自定义对象

我们现在可以在自定义 DocApp 中创建所需的对象。使用 DAB 我们可以创建各种类型的 Documentum 对象，如生命周期、工作流、权限集、对象类型、方法、作业等。我们可以执行以下任一操作：

- 从 Docbase 中选择现有对象并将其包含在自定义 DocApp 中。为此，选择插入 | 从 Docbase 插入对象。
- 从头创建新对象并将其包含在 DocApp 中。为此，选择菜单选项插入。

如果你对对象进行了一些更改且尚未准备好将 DocApp 签入 Docbase，最好选择文件 | 另存为，并将更改保存到本地文件系统上的文件。你之后可以通过选择文件 | 打开来加载这些已保存的更改。

一旦你保存更改（以 *.dpa 文件形式），Documentum 内部会同时创建 *.ser 文件。

为了从 DocApp 中删除对象，大多数开发人员常犯的一个错误是选择对象并选择编辑 | 从 Docbase 删除对象(s)。不应这样做，因为这会从 Docbase 本身中销毁对象。当你只需从自定义 DocApp 中删除对象时，选择该对象并按 Delete 键。

Documentum 应用设计不仅仅局限于理解 Application Builder 和对象。它还有更多内容，随着你在本书中的深入，你会发现许多其他领域，可以在其中投入细致的思考，以实现针对特定业务需求的内容管理系统。

### 10.5 摘要

本章我们简要讨论了在构建应用程序之前良好设计的重要性。我们随后以一个虚拟新闻网站的示例案例研究为例，讨论了如何使用模板通过 Documentum 进行管理。

我们随后涉及了 Web Publisher 模板、Rules 文件和 presentation 文件架构。

Web Publisher 模板文件可以被视为一个简单的 XML 文件，具有预定义字段，内容作者可以填写这些字段以创建内容。

Rules 文件又是控制每个模板字段 XML 元素行为的 XML 文件。

最后，presentation 文件不过是一个 XSL 样式表，控制从模板文件创建的页面的格式（布局）。

在本章末尾，我们讨论了如何创建自定义 DocApp 以存储和管理自定义应用程序所需的 Docbase 对象。
