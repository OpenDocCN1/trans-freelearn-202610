# Jupyter 的未来

尽管 Fernando Perez 是*终身仁慈独裁者*，并且 Jupyter 设有一个由 10 名成员组成的指导委员会，但 Jupyter 是一个采用修订版 BSD 许可证的开源项目。因此，并不存在权威的待办事项清单，取而代之的是不同程度的“官方”规划。

## 官方路线图

第一层是 Jupyter GitHub 站点上的主要子项目：`https://github.com/jupyter`。高层次路线图位于 `https://github.com/jupyter/roadmap`。下表列出了一些重点：

| 功能 | 描述 | 详情 |
|---|---|---|
| **JupyterLab** | 最初是在现有 Notebook Web 应用中新增的一个页面，允许在同一个浏览器标签页中使用多个插件 | 有望取代当前的 Notebook 界面。这是一个大型项目。 |
| **ipywidgets** | 交互式组件，可将内核中的代码与浏览器中的 JavaScript/CSS/HTML 联系起来 | 改进样式。全面重构。将 JavaScript 模块化。 |
| **JupyterHub** | 管理并代理多个单用户 Jupyter Notebook 服务器实例 | 改进配置。支持共享与协作。 |
| **IPython** |  | 相对成熟，因此计划中的重大变更很少。 |

更具体的事项则包括 **Issues** 标签下列出的错误，以及 **Pulls** 标签下的新功能。

接下来似乎是 **Jupyter 增强提案（JEP）**（`https://github.com/jupyter/enhancement-proposals`）。根据文档（`http://jupyter.readthedocs.org/en/latest/contrib_guide_bugs_enh.html`），这类提案与错误请求类似：提交者希望由其他人来完成相关工作。目前，该站点上只有四项增强提案，也有四个拉取请求，但它们似乎都不是路线图中的重点内容。

难点在于，这些工具各自为政。知道何时该用哪种工具，以及如何使用，更像是一门艺术，而非一门科学。这种情况类似于汇编语言时代的末期：有些开发者能用这些工具做出令人惊叹的成果，但这样的人并不多；而且，显而易见，仅靠持续的临时性进展已不足以应对挑战。

# 更好的工具

另一种方法是为程序员提供更好的工具，增强他们的能力。这种方法与务实的演进方法相辅相成：新技术往往需要新工具才能更容易地使用，而新工具也能推动新技术的发展。《重大挑战》论文中有多个章节专门讨论工具。论文特别提到了几种工具，包括编译器、调试器和开发环境。

IPython 在这一方法上可谓一只脚稳稳地踏入其中。使用 IPython（配合 Python），就意味着牺牲一定的性能，以换取其他优势：高层次抽象、多语言支持、友好的 IDE，以及本书详述的其他所有功能。从某种意义上说，这是一场押注——运行 IPython 所耗费的计算周期，所换来的收益将超过使用效率较低的最终产品所损失的部分。考虑到工具的强大与否，往往决定了能否做出可用的产品，这看起来是一场稳妥的押注。

如果把 IPython 看作交互式并行计算工具，那么它的未来似乎有保障，尽管具体前景尚不明朗。说它有保障，是因为随着新技术不断涌现，IPython（以及整个 Jupyter 组织）完全有条件将这些技术整合进自身。说它不明朗，则是因为没人知道未来会出现哪些新技术。

由于并行计算仍在持续发展，学习 IPython 并不是背下一些语法、做几道编程练习就能完成的事。未来几十年里，IPython 将不断发展演进，开发者不仅需要采用新版本的工具，还需要定期更新自己对这一领域的认知。

# 下一个重大创意

通过不断演进新技术并改进工具，社区或许能够找到一个令人满意的并行系统开发框架。然而，如果历史经验可以作为参考，我们仍然需要一种全新的范式（类似于从手写汇编代码转向编译高级语言），才能实现突破。

以巴黎圣母院为例。概括而言，它听起来很像一个软件项目：

![](img/8628b86fcc4f22d859c0104c2ec1d15f_366_0.png)

图片来源：https://commons.wikimedia.org/wiki/File:Notre_Dame_dalla_Senna.jpg

巴黎圣母院历时约 182 年建成（公元 1163 年至约 1345 年），期间至少更换过四位建筑师。尽管工程一直在进行，它从建成初期起便持续投入使用。虽然最初有整体规划，但随着施工困难暴露出新的需求，一些重要特征（包括著名的飞扶壁）也在后续逐步增建。这是一项非凡的工程成就。

更令人惊叹的是，从某种非常现实的意义上说，参与其中的人其实都不真正明白自己在做什么。直到近 350 年后的牛顿时代，人们才理解那些能够证明建筑设计决策合理性的基本物理定律。在牛顿之前，所有建筑知识都来自反复试验：墙体厚度、建筑高度、承重能力、拱门的高度和宽度，以及其他所有结构参数，都是依据以往实验的累积结果和建筑师自身的判断来决定的。

这并不意味着他们的决策是错误的——显然，他们能够建造出规模相当大、结构稳固且美观的建筑。但这意味着他们能做到的事情有严格的限度。建筑规模越大，可供借鉴的先例就越少，失败的代价也越高。

面向大规模并行计算机的软件开发也面临同样的问题。我们在构建规模较小的并行系统方面积累了丰富经验，在并行度更高的系统方面也有一些经验，但问题和失败代价都在不断增大。这个领域需要类似《自然哲学的数学原理》（Principia）的成果——一套统一的并行编程理论。我们需要下一个重大创意。

在下一个重大创意出现之前，科学软件开发社区可以借鉴软件工程领域的一些实践来推动发展。

# 提升专业化水平

> “科学家建造，是为了学习；工程师学习，是为了建造。”
>
> — Fred Brooks

科学家和工程师的工作各不相同。科学家致力于扩展知识，工程师则致力于应用知识。科学家建造某样东西，是为了获得所需的知识；一旦获得这些知识，这个东西的使命便告结束。工程师建造某样东西，则是为了应用知识，而让它长期发挥作用正是其目的。

许多科学软件都是由科学家为科学研究而编写的。因此，一旦从软件中提取出预期的知识，它往往就会被视为可以弃用，这并不令人意外。虽然这种做法能够立即取得成果，但该领域中其他同样希望使用这些软件的研究人员，往往会发现它们难以使用、维护和扩展。
