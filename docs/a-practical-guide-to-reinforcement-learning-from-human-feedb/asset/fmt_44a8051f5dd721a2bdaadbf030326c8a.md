
### Entropy Regularization

For PPO implementation above we used entropy regularization to help with exploration. The idea is to maximize the entropy of the policy distribution, which means encouraging the agent to maintain a diverse set of actions rather than converging to a deterministic policy too quickly. This approach promotes exploration dynamically throughout training, adapting based on the current policy distribution. Entropy regularization can stabilize learning by preventing premature convergence to suboptimal policies, allowing the agent to explore more diverse actions. The weight of the entropy term needs to be carefully tuned. Too much regularization can lead to excessive exploration, while too little may cause the agent to exploit suboptimal actions. Unlike epsilon-greedy, where there’s a guaranteed exploration rate, entropy regularization might lead to periods of suboptimal exploration if the policy converges too quickly. Comparison with epsilon-greedy shows pros and cons of the two approaches can be seen in Table 4.1.

| Criterion | Epsilon-Greedy | Entropy Regularization |
| --- | --- | --- |
| Exploration mechanism | Random action selection with ϵ | Encourages diverse action distributions |
| Simplicity | Simple to implement | More complex due to tuning |
| Exploration Guarantees | Fixed probability of exploration | Adaptive exploration based on policy |
| Efficiency | Can lead to inefficient exploration | Can lead to more informed exploration |
| Tuning | Epsilon decay schedule | Weight of entropy term |

Table 4.1 Comparing epsilon-greedy and entropy regularization exploration strategies.

While the exploration strategies can help to some extent, sometimes reward sparsity is severe, and a more direct approach such as providing human guidance, or initializing with good or diverse set of policies can improve exploration. In the next section, we will discuss how human guidance can be incorporated in the form of behavioral cloning, along with PPO, and used for model initialization.

### Using Human Guidance

In the last section, we explored various policy training techniques and implemented the PPO algorithm on the continuous action Mountain Car problem. The training takes a significantly large number of episodes to achieve high returns. One of the main reasons is that the reward structure presents significant challenges: while the goal is to climb and reach the flag for a reward of +100, this conflicts with the necessity to limit action magnitudes (`-0.1 * action^2`). The momentum created by larger actions aids in reaching the flag, yet we need to maintain smaller action magnitudes. Additionally, generating momentum requires consistent climbing, which demands extensive experience through many episodes. As humans, we inherently understand how we want a car to behave, yet defining an accurate reward function can be challenging. Much like human decision-making, which often requires evaluating the entire episode, an agent also benefits from comprehending the desired behavior in specific scenarios, such as climbing a mountain. For effective reward modeling, we typically gather preferences from multiple human evaluators to inform the reward function. However, individual actions and states at a single-step level are often insufficiently informative. Therefore, it may be necessary to adjust the training setup to consider sequences of actions at the episode level. An alternative approach is to initialize the agent's policy with a pretrained behavioral clone based on human expert trajectories. In this case, we will collect a set of human demonstrations and synthesize this data to enhance our training set. We will then employ behavioral cloning using the same agent architecture as in Proximal Policy Optimization (PPO) to replicate the demonstrated behavior. This process will initialize the agent for PPO training, enabling it to fine-tune its performance and generalize across scenarios not encountered during the initial demonstrations. We will discuss each step in policy initialization for PPO using behavioral cloning in the Behavioral Cloning section. #### Data Collection Process

We will utilize the Gym environment for the Mountain Car problem, employing the Pygame library to facilitate interaction via keyboard input. This allows human actions to directly influence the magnitude and direction of the car's movement. By collecting these human-demonstrated trajectories, we aim to enhance the reward structure for PPO training. The data collection process must be strategic; each action incurs a small negative reward, while only a sequence of actions leads to the eventual reward of +100. Random actions are inefficient for this task. Given that the equilibrium state of the Mountain Car environment lies at the valley bottom, many actions lead to the car descending rather than ascending. Instead of developing heuristics to help the car climb, we can redesign the environment to enable direct human interaction, allowing users to generate effective actions and policies. In this section, we will implement an interactive environment using Pygame and Gym to collect human demonstration data for training a reward model, focusing on essential code snippets to facilitate this process. The `human_feedback_keyboard.py` script to collect human demonstration is available in the github repository:

1. After importing relevant libraries, we initialize pygame, create the gym environment and reset it to the initial state:

```
pygame.init()
env = gym.make('MountainCarContinuous-v0', render_mode="human")
state, _ = env.reset()
```

2. We write a docstring and print the instructions on how the user can interact with the game environment as follows:

```
instructions = """
Press 'a' to accelerate left,
'd' to accelerate right,
's' to stop,
'q' to quit.
"""
```

3. Then, we set the main loop to keep the Pygame window responsive and check for a quit event.

```
running = True
while running:
    for event in pygame.event.get():
        if event.type == pygame.QUIT:
            running = False
```

4. Then, we handle key presses using below event conditions:

```
keys = pygame.key.get_pressed()
if keys[pygame.K_a]:
    action = action_space.low[0] * np.random.uniform(0.2, 0.5)  # Accelerate left
elif keys[pygame.K_d]:
    action = action_space.high[0] * np.random.uniform(0.2, 0.5)  # Accelerate right
elif keys[pygame.K_s]:
    action = 0.0  # No acceleration (stop)
elif keys[pygame.K_q]:
    print("Quitting...")
    running = False  # Exit loop
```

Note that acceleration is set to action values randomized in a small low magnitude range so that less energy is used. This is in alliance with the reward goal of `-0.1 * action^2`.

5. With these human selected actions, we step through the environment loop, and continue until `done=True`. For each step, we record the `state`, `action`, `next_state`, `reward`, and `done`.
