
# GAE Implementation and PPO Update

## GAE Computation

Here is how GAE is implemented to compute advantages and returns. After making appropriate device selection and advantages, a variable is initialized as a tensor filled with zeros that has the same shape as the `rewards` tensor. This tensor will store the computed advantage values for each timestep. This is followed by initialization of the last GAE lambda. This variable is used to keep track of the advantage calculated at the next timestep (moving backward through the trajectory). It starts at 0 for the last step.

```
device = torch.device("cuda" if torch.cuda.is_available() and args['cuda'] else "cpu")
advantages = torch.zeros_like(rewards).to(device)
lastgaelam = 0
```

Then a loop iterates backward over the time steps, from `args['num_steps'] - 1` (the last step) down to 0. This reverse traversal is necessary for GAE, which propagates information from future rewards backward. In this loop we are passing all of the environment variables and computing advantages and returns. As discussed previously, in vectorized environments, some episodes might have terminated earlier, and it is important to handle them properly. The key to handling terminated episodes lies in the use of the `dones` tensor, which indicates whether an episode has ended at a particular time step. In terminated episodes, the environment provides a done signal. This affects how future rewards are propagated, particularly by ensuring that after termination, the value of future rewards is cut off, which prevents future rewards from being propagated across episode boundaries.

We create a new variable named `nextnonterminal`, which takes the value `1.0` when the episode has not terminated and `0.0` when the episode has terminated. If `dones[t+1]` (or `next_done` for the last step) is `True` (meaning the episode has terminated), `nextnonterminal` becomes `0.0`, cutting off any future rewards and preventing further value propagation. This mechanism ensures that once an episode terminates, future rewards and values are not incorrectly added to the current step's advantages. Hence, we check for the condition whether the step is the last step of the episode, and assign `nextnonterminal` accordingly.

```
for t in reversed(range(args['num_steps'])):
    if t == args['num_steps'] - 1:
        nextnonterminal = 1.0 - next_done
        nextvalues = next_value
    else:
        nextnonterminal = 1.0 - dones[t + 1]
        nextvalues = values[t + 1]
```

`nextvalues` in the above code snippet is set to `next_value` when `t` is the same as the last step of the episode or trajectory. The `next_value` is the value estimate for the next state, which is input to the function `compute_advantages_and_returns`. For all other steps it is set to the value estimate at the next timestep (`t+1`).

In the loop, we then calculate the TD (Temporal Difference) residual, `delta`, using:

- `rewards[t]`: the immediate reward at the current step,
- `args['gamma'] * nextvalues * nextnonterminal`: the discounted value of the next step, considering whether the episode continues (`nextnonterminal`),
- `values[t]`: the value estimate at the current step.

The difference between the sum of the immediate reward and the discounted future value and the current value estimate gives the TD error (`delta`).

```
delta = rewards[t] + args['gamma'] * nextvalues * nextnonterminal - values[t]
```

When `nextnonterminal` is `0.0` due to termination, the term `args['gamma'] * nextvalues * nextnonterminal` becomes `0.0`. This means that the reward at time step `t` only considers the immediate reward `rewards[t]` and not the future value `nextvalues` from the next timestep.

The advantage at step `t` is updated using GAE, which incorporates both the TD error (`delta`) and the advantage from the next timestep (`lastgaelam`), with discounting by `gamma` and weighting by `gae_lambda`. At the same time, `lastgaelam` is recursively updated with this new advantage value, to be used in the next iteration of the loop (moving backward).

```
advantages[t] = lastgaelam = delta + args['gamma'] * args['gae_lambda'] * nextnonterminal * lastgaelam
returns = advantages + values
return advantages, returns
```

When an episode terminates, `nextnonterminal` is `0.0`, meaning that `lastgaelam` (which carries over advantages from future timesteps) no longer contributes. The advantage at time step `t` depends only on the immediate TD residual (`delta`) rather than any future advantages. This ensures that GAE does not propagate advantages across episode boundaries, thus maintaining the integrity of the trajectory.

The returns are then calculated by adding the estimated values to the computed advantages. This gives the total expected return (reward + future value) for each timestep. The function returns both advantages and returns, which can be used in the loss calculations.

## Minibatch Sampling and PPO Update

In PPO, training is often repeated for several epochs. To achieve this, the collected batch is shuffled and split into minibatches for each epoch.

```
for epoch in range(args['update_epochs']):
    np.random.shuffle(b_inds)
    for start in range(0, batch_size, minibatch_size):
        mb_inds = b_inds[start:end]
        _, newlogprob, entropy, newvalue = agent.get_action_and_value(b_obs[mb_inds], b_actions[mb_inds])
        ratio = (newlogprob - b_logprobs[mb_inds]).exp()
        pg_loss1 = -mb_advantages * ratio
```

### Policy Gradient Loss

Policy Gradient Loss is the core PPO update and plays a central role in updating the agent's policy. It is formulated in a way that modifies the policy to increase the probability of taking actions that yield higher rewards, based on collected experiences. It uses a clipped objective to prevent large policy updates and maintain stability.

`ratio` measures the change between the old policy (`logprob`) and the new policy (`newlogprob`) for a specific action, where old `logprob` is the log-probability of the action under the policy before the update (from the previous iteration), and new `logprob` (`newlogprob`) is the log-probability of the action under the current policy (after the update). The `ratio` allows us to measure how different the new policy is from the old one for the same action, and by using this ratio, PPO controls how much the policy can change at each step.

PPO introduces clipping to prevent excessively large updates to the policy, which could destabilize training:

```
pg_loss2 = -mb_advantages * torch.clamp(ratio, 1 - args['clip_coef'], 1 + args['clip_coef'])
pg_loss = torch.max(pg_loss1, pg_loss2).mean()
```

Clipping ensures that the ratio stays within a reasonable range: `[1 - clip_coef, 1 + clip_coef]`, where `clip_coef` is a small value, typically between 0.1 and 0.3. This prevents the policy from updating too aggressively (too far from the old policy).

Two Loss Terms:
- `pg_loss1` is the standard policy gradient, unmodified by any constraints.
- `pg_loss2` applies the clipping. If the ratio exceeds the bounds, the advantage is capped, preventing excessive updates.

By taking the maximum of `pg_loss1` and `pg_loss2`, PPO ensures that if the policy update is too large, it is restricted, thus maintaining stability.

## Value Function and Entropy Loss

PPO is a policy-based method, but it also uses a value function to estimate the expected return from a given state. These two components work together, with the policy deciding actions and the value function predicting how good a state (or state-action pair) is.

```
v_loss = 0.5 * ((newvalue - b_returns[mb_inds]) ** 2).mean()
```
