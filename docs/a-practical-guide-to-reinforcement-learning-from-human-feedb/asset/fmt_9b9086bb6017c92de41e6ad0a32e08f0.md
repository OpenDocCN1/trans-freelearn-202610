## Evaluation Metrics

Evaluation output shows key metrics that are typically reported after evaluating a model's performance during or after training. Evaluation outputs can be reported as follows:

```

```

The loss calculated during evaluation process is `eval_loss`, a measure of how well or poorly the model's predictions match the true values (ground truth). Similarly, `eval_accuracy` is the accuracy of the model on the evaluation dataset. Accuracy is the proportion of correctly predicted instances out of the total number of instances. `eval_runtime` is the total time taken to run the evaluation phase, measured in seconds. This can be useful for understanding the efficiency and speed of the evaluation process, especially when dealing with large datasets or when using complex models. Other evaluation metrics are `eval_samples_per_second` is a measure of model throughput showing us the number of evaluation samples processed per second during the evaluation. Similarly, `eval_steps_per_second` gives insights into the efficiency of model evaluation in terms of how quickly batches are processed, and it is influenced by factors like batch size, model complexity, and hardware. The `epoch` is specified during training, and is also presented with valuation, as it is a measure of how many times the model has seen the entire training dataset and can be useful for experimentation.

## Adding Margin to Loss

There is a margin, which is the difference between these predicted scores for the "chosen" and "rejected" responses. It indicates how confident the model is in selecting one response over another. It is calculated using predicted scores above, and helps with decision-making. Assuming `output.predictions` contains the predicted scores for chosen and rejected responses, the margin can be calculated as their difference.

```
score_chosen = predictions[:, 0]
score_rejected = predictions[:, 1]
margin = score_chosen - score_rejected
```

You should compute the **margin based on predicted scores** because the margin represents the model's confidence in its choices and directly informs the training process by providing a signal for how well the model distinguishes between different responses. The evaluated scores are useful for tracking the model's performance but aren't used for calculating margins during training. According to HuggingFace TRL documentation, you can add margin to the loss by adding a margin column directly to the dataset. The reward collator will account for it by default, if the margin column exists. An example snippet showing how margin can be added to the dataset used in the above example is as follows:

```
def add_margin(row):
    return {'margin': row['score_chosen'] - row['score_rejected']}
dataset = dataset.map(add_margin)
```

`dataset.map(add_margin)` applies the `add_margin` function to every row in the dataset, resulting in a dataset with an added column (margin) containing the computed margin for each row.

## Data Quality, Balance and Diversity

Data collection process involves several important considerations beyond user experience and scaling for user interaction and telemetry. The data quality is impacted by how the workers input the data, since human inputs involve subjectivity. The consistency in data quality can be improved by providing clear annotation guidelines, and checking for consistency. Similarly, the type of prompts provided to workers should have balanced coverage by including different types of responses by covering variety of topics and difficulty levels. If the model is given easy or happy-path type of questions, answers might lead to obvious correct answers, and workers rating them higher, giving an unbalanced score. Adding nuanced prompts and questions, or a variety, will help with more robust outcomes. Like coverage, diversity of annotators can help reduce systematic bias usually observed in a unipolar group.

Before using the human annotated data for training a RM, it is important to assess the annotation quality. Measuring inter-annotator agreement and reliability helps with higher signal quality. Better agreement among annotators means higher confidence that annotated data correctly represents the correct signal. If human annotators differ widely on their preferences and judge outputs by a wide margin, it is indicative of requiring more data, as using such data can lead to suboptimal policies.

There are several metrics to help with determining the quality of human annotators. One common metric that is widely used in computational linguistics, and is considered in reward modeling research is **Cohen's Kappa**. It uses inter-annotator agreement and accounts for chance agreement. It usually has ranges from -1 to 1, where 1 denotes perfect agreement, 0 denotes agreement equivalent to chance, and -1 indicates systematic disagreement. If you have only two annotators and the labeling is strictly categorical (e.g., chosen vs. rejected), as in the case of pairwise preferences or likert-5 scale, Cohen's kappa can be applicable and it gives a clear metric of how reliably the annotators agree.
