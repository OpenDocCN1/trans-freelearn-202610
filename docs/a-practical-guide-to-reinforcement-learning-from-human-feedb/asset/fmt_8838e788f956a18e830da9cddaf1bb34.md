
# Data Collection, Preprocessing, and Tokenization for Reward Modeling

Raw data can be collected in a `json` format or any other form convenient for preprocessing. The data collection process typically involves presenting a large number of prompts and paired model responses to human annotators via a user interface instrumented with telemetry. Annotators are asked to express a preference—either by selecting the better of two responses or by rejecting both. This preference is then encoded using binary labels, such as `1` indicating that `response_1` is preferred, and `0` indicating that `response_2` is preferred. An example raw data is given below.

```
raw_data = [
    {
        "prompt": "Tell me a joke.",
        "response_1": "Why did the chicken cross the road?",
        "response_2": "Knock, knock!",
        "label": 1,  # 1 means response_1 is preferred
    },
    {
        "prompt": "What is AI?",
        "response_1": "Artificial Intelligence.",
        "response_2": "A type of plant.",
        "label": 0,  # 0 means response_2 is preferred
    },
]
```

The collected raw data can be large, and is usually stored in a database. Before `RM` training, this data is accessed and preprocessed. In practice, it is best to start with a `json/csv` on `git`, for starting out. This is especially suitable if update to the data is not frequent, e.g. daily. As the data size grows, or is estimated to grow, and there are scenarios of frequently changing datasets, and need for advanced querying, a `SQL` or `NoSQL` database is more appropriate. Regardless of storage format, curating high-quality data is essential for stable and accurate reward modeling. Some best practices to help ensure that preference datasets remain reliable are as follows:

**Annotator training**: Providing clear labeling guidelines and example tasks to promote consistency can help improve the quality of raw data.

**Prompt diversity**: Including a variety of task types can help avoid overfitting the reward model to a narrow domain.

**Response quality filtering**: If both the responses in the pair are uninformative or too similar, it will not be helpful during training, and should be filtered out.

**Monitor agreement**: Tracking inter-annotator agreement and refining prompt instructions based on review of disagreements can help with signal consistency.

**Bias auditing**: Human data collection can lead to systematic preferences or cultural bias, and periodically reviewing the data to check bias, can help remove bias and save cost on de-biasing the data.

**Uncertainty signals**: Human annotator may have varied confidence level while adding preference labels, and including a confidence level field can inform how those labels are weighted during training.

**Deduplication and variation**: Duplicate examples should be avoided and stylistic diversity in model outputs should be encouraged, so that outputs reflect a range of tones, phrasings, and expressive styles. This is particularly useful when training reward models, since human preference is often sensitive not only to correctness or helpfulness, but also to *how* something is said.

These steps help produce a dataset that not only captures human preferences faithfully but also supports robust and generalizable reward modeling.

## Preprocess Data

Once the raw data has been retrieved—whether from a database or a `JSON` file—we have to first preprocess it to use it into a format suitable for training. Typically, we begin by loading the raw list of prompt-response-label dictionaries into a pandas `DataFrame`. The goal of preprocessing is to map the human preference labels into a structured format that separates `accepted` and `rejected` responses into their own columns. This format is not only convenient but essential for many preference learning setups. In some preference models, “`chosen`” or “`accepted`” and “`rejected`” are distinct labels to model responses and clearly indicate what the human annotators chose.

```
df = pd.DataFrame(raw_data)
def map_responses(row):
    if row["label"] == 1:
        return {"prompt": row["prompt"], "accepted": row["response_1"], "rejected": row["response_2"]}
    else:
        return {"prompt": row["prompt"], "accepted": row["response_2"], "rejected": row["response_1"]}
processed_data = df.apply(map_responses, axis=1).to_list()
dataset = Dataset.from_list(processed_data)
```

Structuring the data with `accepted` and `rejected` columns serves an important purpose. In many reward modeling pipelines, the learning objective is based on pairwise comparisons, where the model is trained to assign a higher reward to the preferred response than to the rejected one. This data format aligns directly with such objectives. It is particularly helpful not just for neural reward models, but also for scoring models based on logistic preference modeling or Bradley-Terry-style ranking models, which rely explicitly on clear preferred vs. rejected pairs. By preprocessing the data in this way, we ensure compatibility across a range of reward modeling techniques while making the supervision signal explicit and interpretable.

## Data Tokenization

After preprocessing the dataset to clearly separate the `accepted` and `rejected` responses for each prompt, the next step is to tokenize the text so it can be used for model training. Tokenization involves converting each text input into a sequence of token IDs, along with attention masks to indicate which tokens should be attended to by the model. We begin by selecting a base pretrained language model whose tokenizer we will use. For instance, we can use a `BERT` tokenizer model, such as `bert-base-uncased`, using the `AutoTokenizer` method in `HuggingFace`. This ties the tokenization process to the model architecture so that it can be used during model training. It can be declared as follows:

```
model_name = "bert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(model_name)
```

For preference data, we tokenize both the `accepted` and `rejected` responses alongside the prompt. This allows the reward model to later distinguish between high- and low-quality outputs for the same prompt. We define a `tokenize_function` that applies the tokenizer to each batch, encoding prompt-response pairs separately for `accepted` and `rejected` responses.

```
def tokenize_function(batch):
    tokenized_accepted = tokenizer(
        batch["prompt"], batch["accepted"], truncation=True, padding="max_length", max_length=128
    )
    tokenized_rejected = tokenizer(
        batch["prompt"], batch["rejected"], truncation=True, padding="max_length", max_length=128
    )
    return {
        "input_ids_accepted": tokenized_accepted["input_ids"],
        "attention_mask_accepted": tokenized_accepted["attention_mask"],
        "input_ids_rejected": tokenized_rejected["input_ids"],
        "attention_mask_rejected": tokenized_rejected["attention_mask"],
    }
tokenized_dataset = dataset.map(tokenize_function, batched=True)
```
