
The episode length is the number of tokens generated per sample during rollouts. Monitoring the length of generated responses (measured in tokens) can help detect unintended changes in model behavior. For example, if the fine-tuned model starts producing much shorter or longer outputs than expected, this may reflect instability in sampling behavior or flawed reward conditioning. It may also indicate shifts in how the model interprets stopping conditions or special tokens, particularly if special stop tokens are involved in training.

## Loss Values

The loss values includes `policy loss`, `value loss`, and `total PPO loss`, which together indicate learning dynamics. While RLHF focuses on human-aligned objectives, the underlying PPO optimization is still gradient-driven. Monitoring loss values helps assess whether the training process is stable. The `policy loss` reflects how much the model is being updated in response to the advantage estimates. The `value loss` indicates how well the critic (value function) is predicting future rewards. Sudden spikes or collapses in these values may require adjusting learning rates, clipping coefficients, or reward normalization strategies.

In the TRL framework, after each training step using `ppo_trainer.step()`, a dictionary of metrics called `stats` is returned. This `stats` dictionary contains important indicators such as KL divergence (e.g., under keys like `'ppo/policy/approxkl'` `or 'ppo/policy/policykl'`), `policy loss`, `value loss, entropy`, and the `average reward`. These metrics can be logged, printed, or stored for analysis, making it easier to monitor training dynamics and intervene if necessary. By examining the `stats` output at each iteration, you gain visibility into how well PPO training is progressing and whether any hyperparameters (such as the KL coefficient or learning rate) may need adjustment. Together, these metrics serve as diagnostic tools to ensure PPO training proceeds smoothly. By observing reward trends, KL divergence, policy loss, and entropy, you can make informed adjustments during training, avoid instability, and better interpret the outcome of fine-tuning.

## Evaluating the Fine-Tuned Model

After RLHF fine-tuning, the trained model can be saved and evaluated on real-world prompts. To evaluate improvements, we compare responses from the original (pre-trained) model with those of the fine-tuned model. The quality of responses is measured using a reward model, which assigns higher scores to responses aligned with human preferences. This process allows us to assess whether RLHF successfully improved the model’s behavior.

After fine-tuning, the model can be evaluated by switching it to evaluation mode using the `eval()` method. Test using some `input_text`, tokenize it using the tokenizer function. Note that you may get a warning if the attention mask and the pad token ID are not explicitly provided. You need to explicitly provide `attention_mask` along with the input IDs during inference. Additionally, you should set `pad_token_id` explicitly for text generation. The `generate()` method is used for both the fine-tuned model and the reference model. A sample snippet of how you can generate model response is shown as follows:

```
with torch.no_grad():
    model.eval()
    ft_output = model.generate(
        input_ids,
        max_new_tokens=MAX_NEW_TOKENS,
        do_sample=True,
        top_p=0.9
    )
```

Once the output response for model and reference model is generated, we can reuse the `compute_reward()` function to evaluate the improvement in reward for generated output from fine-tuned model relative to the reference model that was unchanged.

```
# Calculate scores
original_score = compute_reward([prompt + " " + ref_response])[0].item()
finetuned_score = compute_reward([prompt + " " + ft_response])[0].item()
print(f"Original reward: {original_score:.4f}")
print(f"Fine-tuned reward: {finetuned_score:.4f}")
```

Note that the fine-tuning using reward models is typical part of the RLHF process, and several experimental training aspects such as `generation_kwargs`, model configuration parameters, and training parameters must be updated depending upon size of model, dataset training size, token size and reward model. Here we used a pretrained reward model, which was sufficient for demonstration purposes. In practice, a pretrained reward model can be fine-tuned, before using it for RLHF based alignment. In this chapter, we present a starting point for fine-tuning models for alignment. For production cases, more training iterations might be necessary, and some experimentation with training parameters might become essential. Sometimes during training, KL Divergence might become negative, and this should be avoided, as this value should usually range between 0 and 10. There are some training debugging practices and advice discussed on the TRL documentation, [https://huggingface.co/docs/trl/en/how_to_train](https://huggingface.co/docs/trl/en/how_to_train), which can be beneficial. If you are interested in developing production level RLHF policy optimization and model alignment, you can scale the approach to larger base models e.g. `gpt3.5` instead of `gpt2`, or use smaller models but train through more iterations and monitor reward improvements.
