
The choice of tokenization settings can significantly impact model accuracy and training dynamics. For example, `Truncation` ensures that long inputs do not exceed the model's maximum input length. However, truncating too aggressively may remove important context, especially in longer prompts or responses, leading to degraded reward predictions. `Padding` with `max_length` allows for consistent input sizes across batches, which is more efficient for training but may result in wasted computation for shorter sequences. `Max length` should be chosen carefully to balance efficiency and completeness. A limit that is too short may cut off essential information, while one that is too long can increase memory usage without clear performance gains. It's good practice to analyze the distribution of prompt and response lengths in your dataset to choose an appropriate `max_length` value. In some setups, dynamic padding (i.e., padding only up to the maximum length in a batch) may offer better performance. Once tokenized, the dataset is ready to be used as input for reward model training. Each example now contains two tokenized versions of the same prompt—one paired with a preferred (accepted) response and the other with a less preferred (rejected) response. These are used to train models that can assign higher scores to preferred completions. Whether training a neural reward model or implementing a simpler preference-ranking function, this tokenized structure provides a standardized, parallel format for computing relative quality signals, which are central to preference-based learning. In the next section we will explore techniques of reward modeling and bring in important concepts to consider during modeling.

## Exploring Techniques for Reward Modeling

Reward modeling for language modeling has mainly used supervised learning models trained on human preferences as data. Preference labels can be assigned to full behavioral trajectories—akin to inverse RL—or to individual input-output response pairs. Since crowd workers are humans providing a preference between a pair of output responses, the *Bradley-Terry model* of preference is suitable for measuring the probability of outcome where one response is preferred over another. The Bradley-Terry model is a probabilistic model that estimates the likelihood of one response being preferred over another. This formulation underlies the pairwise loss function used to train many reward models in RLHF. An alternative to pairwise comparisons is a regression-based approach, where the model is trained to predict scalar ratings (e.g., Likert-scale scores, a scale of five points ranging from strongly disagree to strongly agree). They also require crowd workers to use an ordinal scale for input. The HELPSTEER2-Preference paper: [https://openreview.net/pdf?id=MnfHxPP5gs](https://openreview.net/pdf?id=MnfHxPP5gs) compares these two approaches and shows how complementing the two approaches can be beneficial. In practice, most reward models used in language fine-tuning rely on the pairwise preference format. Libraries like TRL support this approach directly through tools such as `RewardTrainer`.

### Reward Modeling using TRL's RewardTrainer and RewardConfig

The TRL library's `RewardTrainer` module implements this **pairwise preference–style** reward modeling by optimizing the reward model to assign higher scores to preferred completions over rejected ones. It trains a RM from pairs of "chosen vs. rejected" samples, encouraging the model's reward output to rank the chosen completion higher than the rejected one. RM can first initialize using similar method as for fine-tuning, using methods such as `AutoModelForSequenceClassification.from_pretrained()` from transformer library's AutoModel methods. The `RewardConfig()` method from trl library allows specifying training configuration for training the RM.

```
reward_model = AutoModelForSequenceClassification.from_pretrained(model_name, num_labels=1)
reward_config = RewardConfig(
    output_dir="./reward_model_output",  # Directory to save model
    max_length=128,  # Maximum sequence length
    per_device_train_batch_size=8,  # Training batch size
    per_device_eval_batch_size=8,  # Evaluation batch size
    learning_rate=5e-5,  # Learning rate
    num_train_epochs=3,  # Number of training epochs
    evaluation_strategy="steps",  # Evaluate periodically
    logging_strategy="steps",  # Logging configuration
    logging_steps=10,  # Log progress every 10 steps
    save_steps=500,  # Save model every 500 steps
    remove_unused_columns=False,  # Required for pretokenized datasets
    report_to="none",
)
```

In addition to specifying training configuration, similar to training configuration in case of fine-tuning, the RM training data is first processed into batches. This is facilitated by using Data Collator methods from transformer library. There are specific data collator methods such as `DataCollatorWithPadding()` that create minibatches and pad data (or concatenate) where required, by using the tokenizer that needs to be passed. The data collators can then be passed to the model trainer `RewardTrainer()` along with the training configurations `RewardConfigs`.

```
data_collator = DataCollatorWithPadding(tokenizer=tokenizer)
trainer = RewardTrainer(
    model=reward_model,
    args=reward_config,
    train_dataset=tokenized_dataset,
    eval_dataset=tokenized_dataset,
    data_collator=data_collator,  # Use DataCollatorWithPadding
    tokenizer=tokenizer,  # Pass tokenizer for preprocessing
)
```

Here, we are using the tokenized dataset for demonstration purposes. In practice, the training dataset and eval dataset can be split, or carefully curated. Upon passing the reward configuration and data collator to trainer, the training and evaluation can be run similar to fine-tuning case we saw in *chapter 6*.

```
trainer.train()
results = trainer.evaluate()
print("Evaluation Results:", results)
```

The training output shows a table of `chosen_text`, `rejected_text` and `logits`. The logits are raw model predictions that are used to determine reward score. Logits can help calculate probabilities or make decisions about which output to accept or reject based on the RM's criteria. The RM would evaluate candidate text by comparing its logits to those of the "ideal" text (the human-preferred output or a highly rated candidate).
