
# RLHF Training Loop

After the models are initialized, we load the tokenizer and dataset. The dataset is processed through the `RLHFDataset` class, which structures the data for use in training. This staged initialization ensures memory is allocated incrementally, improving stability and scalability.

```
tokenizer = AutoTokenizer.from_pretrained(MODEL_NAME)
tokenizer.pad_token = tokenizer.eos_token  # Ensure compatibility with padding
rlhf_dataset = RLHFDataset(prepared_data, tokenizer)
```

While GPT-2 is not extremely large compared to recent models, it still occupies significant GPU memory. Loading it before the dataset ensures that the most memory-intensive component is allocated first, avoiding out-of-memory errors. Additionally, tokenizers are typically tied to the model architecture and must be initialized using the same model name. Creating the dataset afterward ensures that memory is used incrementally and predictably during setup, which is essential for stable RLHF training on limited hardware.

Now that we have the model initialized and dataset prepared and loaded, we can start discussing the RLHF training loop.

## Structuring Data and PPOTrainer Instantiation

Before model training begins, the dataset must be structured efficiently to align with the needs of PPO-based optimization. This is where the **data collator** plays a central role. A **data collator** is responsible for gathering multiple samples into a batch while ensuring that all inputs are properly formatted. Unlike supervised learning, where batches consist of fixed-length token sequences, RLHF requires flexible data structures, including:

*   **Raw prompts** from the dataset.
*   **Chosen and rejected responses**, used to compute rewards and policy updates.
*   **Tokenized sequences**, which must be padded and formatted consistently.

The data collator collects all relevant fields into a structured batch, ensuring that **each training step processes multiple examples efficiently** without unnecessary memory overhead. The following snippet is a sample example of how it can be implemented.

```
def collator(data):
    return {key: [d[key] for d in data] for key in data[0].keys()}
```

Before instantiating the `PPOTrainer`, we must define a `PPOConfig`—a configuration object that governs the key hyperparameters for the training process. This includes settings like learning rate, batch size, KL-divergence penalty type, and memory optimization flags. Defining this configuration object is essential because the `PPOTrainer` uses it internally to schedule learning updates, control divergence from the reference model, and optimize memory usage during training.

Here is an example PPO configuration designed for training under resource constraints:

```
# PPO Configuration with memory-optimized settings
config = PPOConfig(
    model_name=MODEL_NAME,
    learning_rate=LR,
    batch_size=BATCH_SIZE,
    mini_batch_size=2,
    reward_model="OpenAssistant/reward-model-deberta-v3-base",
    query_dataset="Anthropic/hh-rlhf",
    kl_penalty="kl",
    optimize_cuda_cache=True,
    log_with=None
)
```

Once the configuration is defined, we can instantiate the `PPOTrainer`. The `PPOTrainer`, implemented in the `trl` library, orchestrates the fine-tuning process. It takes in several components:

*   A **policy model** (the model being fine-tuned), `model`.
*   A **reference model** (a frozen copy of the original model, used to prevent over-optimization), `ref_model`.
*   A **reward model** (which scores generated responses based on human feedback), `reward_model`.
*   A **dataset** (containing prompts, preferred responses, and rejected responses), `dataset`.
*   The tokenizer and data collator, `collator`.

An example `PPOTrainer` instantiation is given here:

```
ppo_trainer = PPOTrainer(
    config=config,
    model=model,
    ref_model=ref_model,
    tokenizer=tokenizer,
    dataset=rlhf_dataset,
    data_collator=collator
)
```

This order of construction—starting with configuration and followed by trainer instantiation—is essential to maintain modularity, reproducibility, and code clarity. It also ensures that training-specific optimizations like memory handling and batch scheduling are consistently applied during PPO updates.

> **Tip: Understanding Advanced PPOConfig Parameters**
>
> `PPOConfig` offers several tunable fields to control training dynamics, including:
>
> *   `init_kl_coef`, `target_kl`, and `adap_kl_ctrl` for adaptive KL regularization.
> *   `cliprange` and `cliprange_value` to prevent unstable updates.
> *   `optimize_cuda_cache` to reduce memory fragmentation on GPU.
> *   `log_with` for flexible integration with tracking tools like wandb or tensorboard.
>
> These allow you to balance reward maximization, stability, and memory efficiency—critical for RLHF fine-tuning on resource-limited hardware.

The `PPOTrainer` method sets the PPO training; as per the intended goal of the PPO algorithm, it **balances reward maximization and stability** by constraining updates to prevent drastic changes, ensuring steady improvements in model behavior.

During RLHF fine-tuning, **generation parameters** govern how the language model produces outputs and must be specified before entering the training loop. Proper tuning of these parameters ensures that the model remains fluent and coherent while balancing creativity and adherence to learned behavior. These are passed as `generation_kwargs` during the training loop. Key parameters include:

*   **`top_p` (Nucleus Sampling)**: Restricts the sampling pool to the most probable tokens, controlling diversity. Higher values (e.g., 0.9) allow for more varied outputs. Lower values (e.g., 0.3) make responses more deterministic.
*   **`do_sample` (Sampling Activation)**: Enables randomness in token selection instead of always picking the most probable token.
*   **`max_new_tokens` (Response Length Control)**: Limits the number of tokens generated to prevent overly long or short responses.

A sample snippet is as follows:

```
generation_kwargs = {
    "top_p": 0.9,
    "do_sample": True,
    "max_new_tokens": 32
}
```

These settings directly influence response diversity, coherence, and quality and will be passed to the `ppo_trainer` during the training loop for generation of response.
