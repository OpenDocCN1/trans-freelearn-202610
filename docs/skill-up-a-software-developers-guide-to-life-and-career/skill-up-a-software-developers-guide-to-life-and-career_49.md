## Chapter 53. Is Writing Bad Code Immoral for Developers?

在本章中，我将讨论一个有点奇怪的问题：为开发者编写坏代码是否不道德？这引出了编写良好代码的重要性这一概念。

这个问题乍一看似乎很奇怪，因为大多数开发者的思维方式是代码项目既不道德也不不道德，它们只是执行各种功能的编程文件。我希望大多数开发者为自己的工作感到自豪，因此希望编写符合最佳实践的代码。然而，由于进度和预算限制，许多项目会退化，首要目标变成仅仅能工作并尽快完成。

然而，这种思维方式可能导致诸如：功能缺少边界情况以及难以维护的组织不良的代码库等问题。关于编写坏代码是否不道德的问题，我听了我的德克萨斯理工大学计算机科学教授之一 Dr. Michael Gelfond 的一个精彩故事，这也是我写这一章的想法。

在我们的一次讲座中，Dr. Gelfond 提出了这个问题，然后讲了一个故事。几十年前，当他作为软件组织的程序员工作时，他遇到了一个糟糕的代码错误。他花了好几天才弄明白，之前的开发者构建了一个结构不良的函数，导致他正在工作的模块崩溃。

Dr. Gelfond 告诉我们这个故事后，他再次问我们编写坏代码是否不道德；大多数同学回答说不是。但随后他问，如果我们在一人死前几天杀死他，“这不道德吗？”对此，每个人都一致回答“是”。他结束讲座时说：“那么上一个开发者的代码偷走了我生命中的两天，这难道不不道德吗？”

这个故事和问题在我脑海中留下了深刻印象，现在我对“编写坏代码是否不道德？”这个问题给出的答案是响亮的“是”！作为开发者，我们应该为自己生产的工作感到自豪，不仅仅是为了客户或雇主的利益，而是仅仅因为我们的目标应该是成为我们所做的一切的真正工匠。

编码是我们这个世界最接近魔法的东西，我感到很荣幸能够每天与之工作，并能够教导他人如何做同样的事情。并且有了这个想法，它应该激励我们有一个明确的目标，即在我们的手艺上做到卓越。

我一生中最喜欢的棒球运动员之一是 Joe DiMaggio，他有一句很棒的引言，我认为非常适用于开发者。他说：

> *There is always some kid who may be seeing me for the first time. I owe him my best.*

我尝试将其应用于我所做的所有代码项目，很容易陷入懒惰的习惯。然而，我提醒自己，有人可能会查看这个项目，这可能是他们对我作为开发者的第一印象，如果我走了捷径，即使应用程序能工作，也可能对我的工作产生负面影响。

这并不意味着你不能犯错误，恰恰相反。 我不断努力成为更好的开发者，正因为如此，我总是尝试构建我以前从未创建过的功能和项目，这自然会在学习过程中导致错误。然而，尝试构建雄心勃勃的功能时犯下的错误，与由于懒惰和编写不良代码而出现的项目错误之间存在明显区别。

### How to write better code

那么，如果编写坏代码是不道德的，可以做些什么来对抗它呢？值得庆幸的是，我们有一套不错的工具和工作流程可以实施。以下是其中我发现最有用的



有效做法：

- **TDD/BDD（测试驱动开发/行为驱动开发）**：无论你对测试驱动或行为驱动开发持何种看法，不可否认的是，只要实施得当，它们就能打造出结构良好的代码库。TDD 自然会引导你遵循低耦合、小方法等最佳实践，并且借助其重构步骤，我非常喜欢用它来确保应用程序以正确的方式构建。
- **持续集成**：假设你拥有全面的自动化测试套件，那么 Codeship 或 Travis 等持续集成工具将确保代码在通过全部测试套件之前不会被推送到生产环境。我有多次 Codeship 阻止了可能导致网站宕机的错误部署经历。此外，它还会在尝试错误部署时向开发团队提供需要修复内容的报告。
- **结对编程**：这是开发者可以使用的最强大的工具之一。如果你不熟悉它，结对编程是指你与另一位开发者在同一时间轮流在同一项目上工作，最好是在同一房间、使用同一台电脑。当其中一人编码时，另一人负责观察并提出建议或警告。每当我在构建复杂功能时，总会使用结对编程，因为这就像用两个大脑来处理同一功能。
- **持续学习**：无论你成为开发者多久，永远不会有学习终结的阶段。我每天都尝试学习新东西，无论是通过教程、书籍还是其他程序员写的博客文章。

### 总结

希望这一章能引发你的思考，并帮助你在成为代码工匠的道路上不断前行。
