

# 第56章. 项目开发实践指南

作为一名教师，我最喜欢的部分就是与学生互动。而本章将重点回答一位观众关于**项目开发方法**策略的问题。

## 学生提问

以下是德国开发者 Christian 写给我的信件：

> *一年前开始学习网页开发，我目前正在使用 Rails 构建我的第一个商业产品（一个分类广告网站）。我真的很想听听你关于如何在应用上构建功能的建议，因为我有以下问题：*
> 
> *我无法从头到尾规划一个功能，因为我总觉得自己遗漏了什么重要内容*
> 
> *拖延和害怕犯下未来纠正成本高昂的错误*
> 
> *当你不确定范围时，你如何构建功能？*
> 
> *你的流程是什么，你如何摆脱困境？*
> 
> *此致，*
> 
> *Christian*

## 项目开发方法策略

在这封信中，每个问题都围绕着项目开发方法策略展开。而在本章中，我将逐一为每个问题提供解答。

## 从头到尾规划功能

我们开发者 Christian 的第一个问题是：

> “当你不确定范围时，你如何构建功能？”

这是一个很好的问题。虽然从项目开始就拥有明确定义的范围会很有帮助，但这种情况很少发生。即使你被提供了一个完美制定的项目范围，它在开发的某个阶段也最有可能发生变化。这本质上会让范围变得毫无意义。我们的开发者 Christian 在邮件中说他正在构建一个分类广告网站，所以我们将在本章中以此作为案例研究。

## 从需求到用户故事

其中一个说法是，你不习惯从头到尾规划功能，因为你觉得自己遗漏了某些东西。当你基于一组需求构建应用程序时，这是一个常见问题。你可能尝试列出需求清单，例如：

- 用户应该能够注册
- 记录只能由创建该帖子的用户编辑

如果你采用这种方法，感觉自己遗漏了功能是很自然的，尤其是如果你是开发新手。与其使用需求，我建议创建用户故事。我给你一个我去年构建的分类广告应用中的一个例子：

*用户登录到应用程序。从那里，她会看到创建新帖子或编辑之前创建的帖子的按钮。她只能看到自己创建的帖子，并且在未登录应用的情况下无法访问此页面。除了查看她的帖子外，她还可以点击一个帖子来查看用户对该帖子的所有回复。*

注意到这比简单列出需求实用得多吗？你的应用应该有数十个用户故事，包含你想要构建的所有初始功能。

## 从基础案例开始

现在你的应用已经有一组不错的用户故事了，它们应该详细到什么程度？老实说，我建议你尽可能保持功能基础。当我构建应用程序时，我甚至不包含我知道以后会需要的全部参数。

在项目开发方法上，我采用基础案例策略。这意味着我将功能钻研到最基本的组件。回到你的分类广告应用，假设它有一个这样的故事：

*当用户在创建新列表的页面上时，她可以添加标题、描述和最多5张图片。从那里她可以点击保存来创建帖子，这会将她重定向到帖子展示页面。*

如果你尝试构建整个功能会非常令人望而生畏。所以，我的方法是首先简单创建一个表单页面。从那里我只会添加使用标题创建帖子的能力。描述可以在未来轻松添加。

因此，我认为在开始时浪费时间毫无意义。我会在开始时完全忽略图片上传功能，因为这需要使用诸如嵌套属性之类的工具。所以，在用户可以用标题创建帖子之后，我可以回头一次一个地添加其他组件。这种方法使整个过程不那么令人望而生畏。

## 未知恐惧

在邮件中，他提到害怕遗漏重要内容。这种对未知的恐惧完全自然，让我说：你会遗漏重要内容。创建用户故事应该有助于捕捉关键项目。然而，我保证总会有组件最初会从缝隙中溜走。然而，不要让这吓到你，你可以在以后添加新功能。

从我个人经验来看，我记得有一次我在构建企业应用时，完全忘记给经理查看他们应该批准的帖子的能力！然而，在我意识到遗漏了关键功能后，我可以添加它，客户也很满意。

所以，不要让害怕遗漏关键功能阻止你构建。记住最初的 Facebook 开发者策略。

## 快速行动，打破常规

在成为上市公司后，Facebook 在项目开发方法上已略微偏离了这种方式。然而，就构建应用程序而言，这仍然是我所拥抱的策略。而且我发现它能带来更多成果。此外，快速行动、打破常规也将有助于解决你的第二个问题。

## 应对拖延

我非常感谢 Christian 的坦率（这也是我决定给他写 1,500 字的回复而不是指向其他资源的主要原因）。在邮件中，他承认自己在拖延方面挣扎。而我很高兴他这么做了，因为拖延是我认识的每位开发者，包括我自己，都必须对抗的问题。

我用来对抗拖延的顶级工具之一是思考要小。我们作为开发者，自然倾向于将具有挑战性的功能推迟。相反，我们喜欢专注于我们已经熟悉的组件。这对每个人来说都是自然的，然而这并不好。我必须每天提醒自己这一点。

在他的书 *Deep Work* 中，Cal Newport 讨论了深度工作（将某人从优秀带到卓越的那种工作）并不有趣。事实上，在研究顶尖表现者时，Newport 发现 100% 的个人都不喜欢从事具有挑战性的任务。所以，就项目开发方法而言，请理解最可怕的功能可能是你作为程序员进步的最大催化剂。

## 小而实用的步骤

所以，我的个人建议是，你要拥抱困难的功能，但采取增量方法。例如，想象你对在分类应用中构建让用户为每个列表上传多张图片的能力感到畏惧。这个功能甚至会让经验丰富的开发者感到畏惧。你需要使用嵌套属性并结合许多 JavaScript 元素以允许动态行为。

这就是可能导致你拖延的功能，因为它有点可怕。然而，我建议你立即着手处理该功能。你可以写下你将如何构建组件的策略，例如：

1. 为帖子集成嵌套属性。
2. 构建一个可以动态创建新文件上传元素的 JavaScript 脚本。
3. 在数据库中的示例记录中硬编码一些图片 URL。
4. 最后将系统连接到存储引擎。

然后猜猜怎么着，你完成了！注意到当你将其分解为更小的步骤时，功能似乎不那么令人望而生畏了吗？这就是对抗拖延的关键。
