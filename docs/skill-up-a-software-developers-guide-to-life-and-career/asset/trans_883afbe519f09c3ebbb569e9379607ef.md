
可以更清楚地了解客户的愿景。如果你只是将应用程序的链接发送给客户测试，他们回馈的许多内容都将与不理解系统功能有关。然而，如果你能清楚地展示应用的工作方式，就能缩短这一过程，并让你更快地了解实际需要修复的问题。

## 远程演示工作服务回顾

有许多方法可以让你远程向客户演示工作。我将回顾过去几年中我使用过的流程，并讨论每种选项在什么时候最理想。

### 录屏

我将回顾的第一个选项是创建录屏。如果有多个客户需要查看该功能，这是一个很好的选择：

![](img/de22e3e00f8df753e0d57f7da4d1c581_175_0.png)

从核心上讲，录屏就是你自己录制自己演示应用程序的过程。如果是基于 Web 的应用程序，你可以让视频展示应用程序的每个功能。在我自己的工作中，我会使用以下工具：

- 放大特定屏幕区域
- 我会高亮我想要关注的屏幕部分

这个过程只需花费很短的时间。然而，它非常值得，因为它能让客户对系统有一个切实的演示体验。

你可以使用多种工具来录制屏幕。我个人最喜欢的是 Camtasia；不过它有点贵。所以，如果你预算有限，还有无数免费选项，例如 Screencast-O-Matic。

录制完屏幕演示后，你可以将其上传到 YouTube、Vimeo 或视频托管网站。然后，你可以让客户在方便的时候查看链接。

### 远程桌面

在远程演示工作工具列表中，接下来是远程桌面会话。每个客户都略有不同。许多客户对电子邮件和视频演示感到满意。然而，其他客户希望有更多个性化互动：

![](img/de22e3e00f8df753e0d57f7da4d1c581_177_0.png)

如果客户希望在演示过程中与你进行充分互动，远程桌面工具可能是展示你工作的最佳选择。我还发现，当我为其他开发者工作时，这个选项也很理想。这主要是因为远程桌面演示支持结对编程。在远程桌面工具方面，有几种不同的选择：

- **GoToMeeting**：如果你的客户想要传统的实时演示，GoToMeeting 或 Join.me 等服务就很不错。它们可以让客户查看你的屏幕，而且如果你与多个利益相关者合作，它们还附带专门的电话会议线路。
- **屏幕共享**：有时你需要能够与客户同时进行演示。这适用于我刚才提到的场景，即你为开发者工作，他希望与你同时浏览应用程序。我最喜欢用于此类演示的服务是 Screenhero。它提供了一种让多个用户同时控制屏幕的简单方法，而且价格相当实惠。
- **免费选项**：如果你预算有限，有许多免费的屏幕共享和远程桌面选项。其中值得一提的是 Google Hangouts、TeamViewer 和 Skype。

### PowerPoint

在远程演示工作工具列表中，最后一种是 PowerPoint 类型的演示文稿。我说类型是因为你不一定非要使用 PowerPoint 不可。我曾使用 PowerPoint、Google Slides 和 Keynote 进行产品演示。在项目开发初期，我喜欢使用基于幻灯片的演示。

![](img/de22e3e00f8df753e0d57f7da4d1c581_178_0.png)

很多时候，我构建了后端功能后，想确认其配置是否正确。然而，我意识到如果客户看到一个丑陋的用户界面，他们无法欣赏已完成的工作。于是，我借鉴了 Google Ventures 的做法，创建了一个 Keynote 幻灯片组。我设计这套幻灯片来模拟我计划最终添加的用户界面。

然后，我简单地将我实际在应用程序中构建的行为加载到幻灯片中。这种方法效果很好，客户也很满意。更重要的是，这个选项让客户专注于我所构建的内容，而不是那些仍在待办清单上的需求。

这个选项也非常适合移动应用演示。移动应用对客户来说，在手机上演示是相当复杂的。因此，基于幻灯片的方法可以更高效地展示应用的设计和行为。

### 总结

我希望这是一份有用的自由职业者指南，能帮助你远程向客户演示工作。

## 当范围蔓延失控时

应用完成后，客户对系统没有动态可点击的推送通知感到不满。我本可以指出他们从未要求过这个功能。但在我看来，这个行为是一个常识性功能，所以我不收取额外费用就为客户添加了。

范围蔓延很少有这么简单。你会发现，通常客户会提出新想法，然后试图让你免费实现它们。如果你没有为项目成功建立明确的定义，你最终会面对一个愤怒的客户，认为你想多收他的钱。请记住，在客户看来，他们可能没有意识到他们要求的功能超出了原始需求集合。定义项目成功有两种方式。我们将逐一讨论。

### 基于需求

首先也是最重要的是传统方法，即基于一组需求。这种方法还可以；然而，它在现实世界中很少奏效。该过程遵循以下工作流程：

1. 写出一整套全面的项目需求。
2. 需求听起来像是：用户应能够登录。
3. 每个功能都有自己的需求。
4. 一旦所有需求都实现，项目即视为完成。

理论上，这似乎是一个很好的计划。然而，在真实项目中，它很少奏效。问题主要在于，即使是最有经验的开发人员或项目经理也无法列出每一个……单独……细小的功能。实际情况是，功能会被遗漏，而你或客户将不得不妥协才能完成项目。

### 基于故事

那么，如果基于需求来定义项目成功并不切实际，更好的方法是什么呢？就我个人而言，我通过构建易于理解的应用程序故事取得了最大的成功。什么是应用程序故事？让我看看我最近为一个项目编写的故事：

*当管理员用户登录应用程序时，她会看到一个自定义仪表盘，其中呈现她管理的所有项目。从那里，她可以编辑项目详情。她还可以导航到资源部分、用户管理仪表盘和用户审计日志。*

注意到故事与一组需求有什么不同了吗？当向客户展示故事时，他们更容易想象最终产品。这让他们在项目开始时而不是在项目结束时，向你提供完整的需求行为。最后，构建良好的用户故事为你提供了清晰的项目成功定义。这些故事能否正常运作？如果可以，那么项目就完成了，就是这么简单。

### 正式签署

在客户批准完整的应用程序故事集后，务必让客户正式签署确认。通常，这意味着让他们签署一份包含所有故事的文件。这提供了一份实用的协议，当所有功能都实现后，你可以以此作为依据。

### 总结

我希望这是一份有用的指南，帮助你作为自由职业者定义项目成功，并且你可以在下一个项目中使用这种方法。
