## 关闭 MongoClient 以防止资源泄漏

如果你使用的驱动程序支持，则应在应用程序关闭例程中始终调用 MongoClient.close() 方法，以正确释放所有连接及相关资源。这可以防止资源泄漏并确保应用程序干净终止。有关适当的连接清理策略的更多详细信息，请参阅本章后面“优化连接管理”部分。

理解 MongoDB 连接生命周期对于构建性能优异且健壮的应用程序非常重要。连接建立会带来一定的开销，因此对于高吞吐量系统而言，高效的池化和复用非常重要。正确处理连接终止可以防止随着时间的推移可能导致应用程序性能下降的资源泄漏。

## MongoDB 连接架构

理解 MongoDB 如何从驱动程序到服务器管理连接对于设计健壮的应用程序非常重要。本节介绍基本连接机制以及它们如何在应用程序栈中交互，包括 TCP/IP 和 MongoDB Wire 协议、驱动程序连接池以及服务器连接处理。

## TCP/IP 和 MongoDB Wire 协议

MongoDB 的客户端-服务器通信基于 TCP/IP，但包含多个 MongoDB 特定的增强和优化。理解这些技术细节有助于开发人员诊断连接问题并优化网络性能。

MongoDB Wire 协议是一种基于套接字的请求-响应式协议，定义了客户端和服务器如何通过标准 TCP/IP 套接字进行通信。它具有以下几个定义特征：

- **二进制 JSON（BSON）格式：** 与基于文本的协议（如 HTTP）不同，MongoDB 使用 BSON 实现高效的序列化和反序列化，且 CPU 开销最小。
- **现代消息格式：** 自 MongoDB 5.1 起，OP_MSG 已成为客户端请求和数据库回复的主要操作码，取代了旧的操作码，如 OP_QUERY 和 OP_REPLY。
- **压缩支持：** OP_COMPRESSED 使用 snappy、zlib 或 zstd 等压缩算法包装其他操作码，以减少网络带宽。
- **消息校验和：** 可选的 CRC-32C 校验和确保数据完整性，尤其对非 TLS 连接很重要。

当客户端连接到 MongoDB 时，会按顺序发生多个操作，每个阶段都可能带来性能影响：

1. **DNS 解析阶段：** 连接过程始于解析 MongoDB 服务器地址。DNS 解析将主机名转换为 IP 地址，SRV 记录可为副本集和分片集群启用智能服务发现。DNS 记录上的 TTL 设置会影响拓扑更改向客户端传播的速度。解析失败可能会在驱动程序中触发指数退避重试算法，可能导致连接延迟。一旦地址解析完成，连接将进入 TCP 建立阶段。
2. **TCP 连接阶段：** DNS 解析后，客户端建立网络基础。Keep-alive 数据包有助于维护长连接并检测死连接以释放资源。TCP 窗口缩放通过允许在需要确认之前传输更多数据，从而在高延迟连接上实现更高吞吐量。TCP 连接建立后，将应用安全层。
3. **TLS/SSL 安全阶段：** TCP 连接建立后，随后建立安全加密。证书验证会在验证服务器真实性时引入少量延迟。TLS 会话恢复可以通过重用先前会话的参数来减少重连时的握手开销。在 TLS 1.3（在较新 MongoDB 版本中受支持）下，握手往返次数从两次减少到一次，从而提高连接速度。所选密码套件会影响安全态势和 CPU 开销。一旦加密通道建立，MongoDB 特定协议协商开始。
4. **MongoDB 特定握手阶段：** 连接现在交换 MongoDB 协议信息。客户端发送 `hello`（或 `isMaster`）命令以交换功能文档（`isMaster` 保留用于向后兼容）。在此阶段，驱动程序检测服务器版本并相应调整功能兼容性。拓扑发现识别集群中的主节点、从节点和仲裁节点。诸如 `maxWireVersion` 之类的服务器参数决定可用功能和 Wire 协议兼容性。建立协议兼容性后，连接进入身份验证阶段。
5. **身份验证阶段：** 最终阶段在允许数据库操作之前验证客户端身份。SCRAM-SHA-256（默认）提供强大的安全性，但需要多次往返。X.509 证书身份验证将身份绑定到 TLS 证书以增强安全性。LDAP 和 Kerberos 代理身份验证会增加额外的网络跳数和延迟。一旦身份验证完成，连接即完全建立并可使用。

这些步骤中的每一个都会导致总连接延迟的增加，该延迟在本地部署中可能为几毫秒，而在跨地理区域或使用复杂身份验证方案时可能达到数百毫秒。这种连接开销凸显了连接池对于高性能应用程序至关重要的原因。

## 驱动程序连接池

MongoDB 驱动程序是特定于语言的库，处理与 MongoDB 服务器通信的复杂性。它们最重要的功能之一是连接池。当你的应用程序初始化 MongoDB 客户端时，驱动程序会创建一个连接池（或根据拓扑创建多个池）。当你的代码执行 MongoDB 操作时，驱动程序会从池中借用一个可用连接。它通过连接发送命令并等待响应。操作完成后，连接会被归还到池中以供重用。驱动程序还通过监控连接健康状况来维护连接池，并可能定期测试或替换它们。

连接池具有以下可调整参数：

- **maxPoolSize：** 池可维护的最大连接数（大多数驱动程序中默认为 100）。
- **minPoolSize：** 池即使在空闲时也能维护的最小连接数（大多数驱动程序中默认为 0）。
- **maxConnecting：** 限制并发建立中的连接数（大多数驱动程序中默认为 2）。此参数在 Rust 驱动程序中不可用。
- **maxIdleTimeMS：** 空闲连接在池中保留的时间，然后被关闭。

![](img/11c6cf3488b31bf4339aa4bd8ea9b45b_266_0.png)

> **为异步应用程序优化 maxPoolSize**
>
> 对于异步应用程序，将 maxPoolSize 设置为与预期并发量匹配而不是线程池大小，通常会带来更好的性能。

有关上述连接池参数的更多信息，请务必查看 MongoDB 文档 https://www.mongodb.com/docs/manual/tutorial/connection-pool-performance-tuning/。

连接池行为因驱动程序是同步还是异步而有显著差异。对于同步驱动程序，当没有可用连接时，调用线程会阻塞操作，直到有连接可用或等待队列超时到期。另一方面，异步驱动程序会返回一个 future 或 promise，在连接可用时解析，而不是阻塞。

## MongoDB 服务器连接处理

高效的连接处理支持可扩展、高性能的 MongoDB 部署。在服务器端，MongoDB 使用可配置参数和操作系统级资源的组合来管理传入的客户端连接：

- **net.maxIncomingConnections：** 控制同时客户端连接的最大数量（Windows 上默认为 100 万；在 Linux 上，默认为最大文件描述符限制的 80%）。由于每个连接都需要一个文件描述符，此限制有助于防止服务器资源耗尽。
- **操作系统限制：** 文件描述符限制（Linux/Unix 系统上的 `ulimit -n`）也可能限制连接数。

连接管理的具体细节还取决于部署拓扑（是单机实例、副本集还是分片集群）：

- **Standalone：** 应用程序直接连接到单个 MongoDB 服务器，使用单个连接池
- **Replica set：** 驱动程序发现所有成员并为每个成员维护单独的连接池，根据读取偏好路由操作
- **Sharded cluster：** 应用程序连接到 mongos 路由器，后者维护其与分片的连接，形成多层连接架构
