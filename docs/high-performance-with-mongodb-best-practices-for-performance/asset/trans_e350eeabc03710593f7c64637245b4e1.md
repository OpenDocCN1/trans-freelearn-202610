
## 连接超时配置

构建能够优雅处理网络中断和服务降级的弹性、高性能应用程序，需要配置适当的超时设置。配置不当的超时可能导致级联故障、资源耗尽或用户体验下降。MongoDB 提供了多个可配置的超时参数，用于控制连接行为的不同方面：

- **connectTimeoutMS**: 驱动程序在建立新连接时等待的时间。将此值设置为大于您部署中任何成员的最大网络延迟。
- **socketTimeoutMS**: 驱动程序等待特定操作响应的时间。将此值设置为驱动程序运行的最慢操作长度的两到三倍。
- **maxIdleTimeMS**: 空闲连接在池中保留的时间（在连接频繁创建与资源利用之间取得平衡）。

正确调整这些超时参数需要了解应用程序行为和 MongoDB 部署拓扑。

![](img/11c6cf3488b31bf4339aa4bd8ea9b45b_272_0.png)

> **重要**
> 
> 不要使用 socketTimeoutMS 来防止长时间运行的服务器操作。相反，对于支持客户端操作符超时的驱动程序，请使用 maxTimeMS() 或 timeoutMS() 与您的查询一起使用，以便服务器可以取消长时间运行的操作。例如，如果操作在驱动程序级别优雅地超时，应用程序可以尝试有意义的重试，而不会压垮服务器。如果没有适当的超时，重试可能会淹没连接池，加剧资源耗尽，并导致系统范围的停机。

## 服务器端优化

在自托管部署中，您需要配置 MongoDB 的连接参数和底层操作系统的限制，以确保最佳性能。这些设置共同决定有多少并发客户端可以连接到数据库。

```yaml
net:
  maxIncomingConnections: 65536
```

maxIncomingConnections 设置控制 MongoDB 将接受的同时客户端连接的最大数量。增加此限制允许更多并发客户端应用程序连接到 MongoDB 服务器，这对于高流量应用程序或具有许多微服务的环境至关重要。然而，仅仅增加此参数是不够的；您还必须调整操作系统的限制。

## 操作系统配置

在基于 Unix 的系统中，MongoDB 为每个客户端连接使用一个文件描述符。当 MongoDB 达到 maxIncomingConnections 限制或操作系统的文件描述符限制（以较低者为准）时，它将拒绝额外的客户端连接。这会在高需求期间造成瓶颈，严重影响应用程序可用性。

对于使用 systemd 的 Linux 系统，您应该在 MongoDB 服务文件中配置文件描述符限制：

```
[Service]
# In the MongoDB systemd service file
LimitNOFILE=64000
```

对于非 systemd 环境，请在 /etc/security/limits.conf 文件中为 MongoDB 服务用户设置限制：

```
mongodb soft nofile 64000
mongodb hard nofile 64000
```

更改这些限制后，必须重启 MongoDB 才能使更改生效。为了确认配置更改对部署有益，您可以使用以下验证方法：

- 1. 使用以下方法检查当前操作系统的限制：
```
ulimit -n      # For the current shell session
cat /proc/$(pidof mongod)/limits  # For the running MongoDB process
```
- 2. 通过 serverStatus 命令监控 MongoDB 连接利用率：
```
db.adminCommand({ serverStatus: 1 }).connections
```

输出将显示：

```
{
  "connections": {
    "current": 123,      // Current active connections
    "available": 63877,  // Remaining available connections
    "totalCreated": 1578  // Total connections created since startup
  }
}
```

- 3. 在 MongoDB 日志中查找连接拒绝错误，这表明您已达到连接限制：
```
[conn12345] Too many open connections
```

正确配置 MongoDB 的 maxIncomingConnections 限制和操作系统的文件描述符限制后，您应该在负载下看到改进的稳定性和性能。即使在流量激增期间，应用程序也能可靠地建立连接，并且您将避免在达到连接限制时发生的级联故障。MongoDB Atlas 根据集群层自动管理这些设置，根据工作负载需求扩展数据库配置和底层基础设施资源。

## 利用网络压缩进行性能优化

网络压缩是 MongoDB 中的一项重要优化技术，可减少客户端和服务器之间传输的数据量。通过在传输前压缩数据并在接收时解压缩，MongoDB 可以显著降低网络带宽需求，同时可能提高整体性能。此功能在高延迟连接或带宽受限环境中运行尤其有价值。

### 网络压缩的优势与权衡

在 MongoDB 部署中实施网络压缩时，了解优势和潜在缺点对于做出明智的决策非常重要。

启用压缩的主要好处之一是显著减少网络带宽消耗。通过在传输前压缩数据，MongoDB 可以显著减少网络上传输的总数据量。

这对于文本密集型文档尤其有效，例如具有冗长字段名称或字符串值的 JSON 数据，通常压缩效果很好。另一个显著优势是在某些环境中降低延迟并加快响应时间。由于需要跨网络传输的数据更少，操作可以更快完成，从而为用户提供更具响应性的应用程序体验。

然而，在生产环境中启用压缩之前必须考虑一些重要因素。CPU 资源利用率是一个重要因素。压缩和解压缩操作需要在客户端和服务器端消耗计算资源。在 CPU 资源已受约束的环境中，额外的处理需求可能会抵消网络优势。

还必须认识到，压缩并不总是能带来有意义的性能改进，在某些情况下甚至可能引入低效率。对于小型操作或处理已压缩的二进制数据（例如图像或视频）时，压缩和解压缩的开销可能超过减少网络流量的好处。在这些情况下，启用压缩可能会降低整体性能。

### 可用的压缩算法

MongoDB 提供了几种压缩算法选项，每种都有不同的特性，使其适用于各种用例：

- **snappy** 在压缩速度和比率之间提供了出色的平衡。它通常将数据压缩到原始大小的约 30-50%，同时使用最少的 CPU 资源。这使其成为大多数 MongoDB 部署的理想默认选择，提供有意义的带宽节省而不会产生显著的处理开销。
- **zlib** 比 Snappy 提供更高的压缩比，可能将数据大小减少到原始大小的 20-40%。然而，这以增加压缩和解压缩的 CPU 使用为代价。当带宽极其有限且 CPU 资源充足时，zlib 可能适用。
- **zstd**（在较新的 MongoDB 版本中可用）提供出色的压缩比，同时保持合理的 CPU 效率。它通常比 zlib 实现更好的压缩，同时计算成本更低，使其成为支持该环境的越来越受欢迎的选择。

选择压缩算法取决于系统在 CPU 使用和网络带宽之间可以承受的具体权衡，并且理想情况下应通过在工作负载上下文中进行基准测试来指导。
