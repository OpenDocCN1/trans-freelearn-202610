# 9 事务

在本章中，我们将深入探讨 MongoDB 的多文档 ACID 事务，这是一项在引入时极大地扩展了 MongoDB 能力的特性。事务是你数据库工具箱中的重要工具，但正如你不会用螺丝刀钉钉子一样，务必仅在它们是合适工具时才使用。尽管功能强大，但事务在被错误使用时可能会造成性能瓶颈。

你可能会惊讶地听到，MongoDB 中的事务并不总是你需要的解决方案。事实上，有时它们恰恰是你应该避免使用的！在本章中，你将获得超出基本实现的 MongoDB 事务能力的全面理解。你将学习如何在数据一致性需求与性能要求之间取得平衡，就何时真正需要事务做出明智决策。我们将探讨展示 Core 和 Callback API 的实际示例，分析不同事务模式的性能影响，并为你提供优化事务工作负载的策略。到本章结束时，你将具备实施在保持数据完整性的同时不牺牲使 MongoDB 成为强大数据库平台的性能优势的事务的能力。

本章将涵盖以下主题：

- 学习 MongoDB 如何支持多文档 ACID 事务
- 使用事务 API 并有效管理会话
- 通过最佳实践优化事务性能
- 识别并避免常见的事务反模式

### 了解多文档 ACID 事务

让我们深入探讨 MongoDB 的多文档 ACID 事务，这项能力标志着 MongoDB 从一个基础的文档型数据库向能够处理复杂、关键任务工作负载的平台演进的重要里程碑。虽然 MongoDB 一直提供强大的文档级原子性，但多文档事务将这些保证扩展到多个文档、集合和数据库。

即使许多应用程序可以利用丰富的文档结构来确保相关的写入一起发生，仍然存在需要协调多个不同文档之间写入的使用场景，这些文档可能位于同一集合或不同集合中。因此，了解 MongoDB ACID 多文档事务的保证以及如何最好地使用它们非常重要。

在本节中，我们将首先探讨 MongoDB 中事务支持的历史和演进，从单文档原子性到分片集群中的分布式事务。然后，我们将分解核心 ACID 属性，即 **atomicity**、**consistency**、**isolation** 和 **durability**，以及它们如何在 MongoDB 的事务模型中应用。最后，我们将比较文档级原子性与多文档事务，帮助你了解何时采用每种方法合适以及如何在数据完整性和性能之间取得平衡。

### MongoDB 中事务的历史与演进

MongoDB 在事务支持方面的历程讲述了一个有趣的故事，说明数据库如何演进以满足日益复杂的应用程序需求：

- **单文档时代（MongoDB 4.0 之前）**：自诞生以来，MongoDB 在单文档级别提供原子性。这对于许多用例来说已经足够，特别是利用 MongoDB 灵活的文档模型将相关数据嵌入到单个文档中时。开发人员通常会专门设计模式以利用这种单文档原子性。
- **副本集里程碑（MongoDB 4.0，2018）**：此版本为副本集引入了多文档 ACID 事务，这是一个改变游戏规则的功能，使 MongoDB 在需要跨多个文档强一致性的应用程序方面与关系数据库达到同等水平。此初始实现支持单个副本集内的事务。
- **分布式事务突破（MongoDB 4.2，2019）**：在前一版本的基础上，MongoDB 4.2 将多文档事务支持扩展到分片集群。这一重大进步实现了跨分片的分布式事务，为复杂的大规模应用程序提供了全面的解决方案。
- **持续改进（MongoDB 4.4 及以后）**：最近的版本专注于性能改进、操作可管理性和事务的更广泛 API 支持。

这一演进反映了 MongoDB 满足多样化应用程序需求的同时保持其在灵活性、可扩展性和性能方面的核心优势的承诺。

### MongoDB 中 ACID 属性简介

ACID 代表确保数据库事务即使在出现错误、崩溃或断电的情况下也能可靠处理的根本属性。让我们分解这些属性在 MongoDB 上下文中的含义：

- **Atomicity：** 这保证事务是全有或全无；即事务中的每个操作都成功或都不成功。如果事务的任何部分失败，整个事务将被回滚，使数据库恢复到原始状态。虽然 MongoDB 一直在单文档级别提供原子性，即如果对文档的任何更改失败，则该文档的所有更改都会失败，多文档事务将此保证扩展到多个文档。
- **Consistency：** 此属性确保事务将数据库从一个有效状态带到另一个有效状态，保持所有定义规则和约束。在 MongoDB 中，一致性验证主要通过文档和模式验证功能在每个文档的基础上存在。单文档操作和多文档事务都保证一致性。其他一致性验证，例如唯一索引约束，在事务内外也以相同方式得到保证。
- **Isolation：** 将隔离视为每个事务在其自己的小气泡中运行。它确保并发执行的事务不会相互干扰其结果，就好像它们是顺序执行一样。MongoDB 为事务提供快照隔离，这意味着每个事务都会看到数据在事务开始时存在的一致快照，而不管在执行期间由其他事务提交的更改如何。如果两个事务尝试进行冲突的修改，其中一个将失败并重试整个事务。
- **Durability：** 一旦事务提交，其更改就是永久的，并且将存活于随后的系统故障，例如断电或崩溃。在 MongoDB 中，持久性通过多节点上的日志记录和写入关注机制实现。当事务使用适当的写入关注提交时（例如默认的 `{w: "majority"}`），更改保证在副本集的大多数成员中持久存在。这比单个节点将写入提交到磁盘的保证更强。

总之，ACID 属性为 MongoDB 事务中的可预测和可靠行为提供了基础。它们确保多步骤操作要么完全完成，要么没有任何效果，有助于在并发工作负载、应用程序错误或系统故障存在的情况下保持数据完整性。这对于协调跨多个集合的更改的应用程序尤其重要，例如处理订单、更新库存或管理用户账户。

### 文档级原子性与多文档事务

理解 MongoDB 默认的文档级原子性与多文档事务之间的差异对于有效的数据建模和优化性能至关重要。

### 文档级原子性

MongoDB 一直保证对单个文档的操作是原子的。当你更新文档中的多个字段时，要么所有更改都应用，要么都不应用；没有中间状态只有部分字段更新。这些更改也只会一起或根本不向其他线程可见。这种内置的原子性，结合 MongoDB 允许嵌入相关数据的丰富文档模型，意味着许多用例实际上根本不需要多文档事务。

例如，如果你正在跟踪订单及其明细，将明细嵌入到订单文档中可确保对订单状态及其项目的更新以原子方式发生：

```json
{
  "_id": "order123",
  "customer": "jane_doe",
  "status": "shipped",
  "items": [
    { "product": "widget", "quantity": 5, "price": 10 },
    { "product": "gadget", "quantity": 1, "price": 20 }
  ]
}
```

这种方法使数据紧密耦合，并在不协调跨多个文档更改的开销的情况下确保一致性。



## 多文档事务原子性

多文档事务将原子性保证扩展到涉及多个文档的操作中，这些操作可以跨不同的集合、数据库或分片。多文档事务是必不可少的，当相关数据无法合理地嵌入到单个文档中时。例如，处理电子商务订单可能涉及同时更新库存水平、客户历史记录和订单记录以维护数据完整性：

```
// Start a session and transaction
const session = client.startSession();
session.startTransaction();

try {
  // 1. Create and insert the order document
  const order = {
    customerId: "customer123",
    items: [
      { productId: "product456", quantity: 2, price: 25.99 },
      { productId: "product789", quantity: 1, price: 49.99 }
    ],
    totalAmount: 101.97,
    status: "processing",
    createdAt: new Date()
  };

  const orderResult = await db.orders.insertOne(order, { session });
  const orderId = orderResult.insertedId;

  // 2. Update inventory for multiple products
  await db.inventory.updateOne(
    { _id: "product456" },
    { $inc: { stockCount: -2 } },
    { session }
  );

  await db.inventory.updateOne(
    { _id: "product789" },
    { $inc: { stockCount: -1 } },
    { session }
  );
```

```
// 3. Update customer purchase history
await db.customers.updateOne(
  { _id: "customer123" },
  {
    $inc: { totalSpent: 101.97, orderCount: 1 }
  },
  { session }
);

// If all operations succeed, try to commit the transaction
await session.commitTransaction();
} catch (error) {
// If an error occurred, abort the transaction
await session.abortTransaction();
console.error("Transaction aborted due to error:", error);
throw error;
} finally {
// End the session
session.endSession();
}
```

需要理解的关键权衡是，虽然多文档事务提供了更强的 consistency 保证，但与单文档操作相比，它们通常会带来更高的性能开销。作为一般规则，在可能的情况下利用单文档原子性，并在真正必要时谨慎使用多文档事务。

## 何时在 MongoDB 中使用多文档事务

虽然 MongoDB 支持多文档事务，但这并不意味着你应该默认使用它们。事务会带来性能权衡，在许多情况下，MongoDB 的原生设计提供了更好、更高效的替代方案。那么，什么时候使用多文档事务是明智的？什么时候最好不用它们？

让我们看看一些多文档事务不仅有帮助而且必要的场景：

- **财务操作**通常需要严格的一致性以避免可能导致严重错误的差异。例如，在记录付款时，至关重要的是同时更新 payments 集合和相应的客户文档以扣除所欠资金。如果一个更新成功而另一个失败，系统可能会显示不正确的余额或不完整的记录，而多文档事务正是为了防止这种情况而设计的。
- **库存和订单管理**通常涉及在创建订单的同时同时更新多个产品的库存水平。必须确保所有这些更新作为一个整体成功或失败，以防止超卖或库存不一致。例如，如果订单已记录但库存更新失败，系统可能会显示不正确的库存可用性，导致客户不满和物流问题。多文档事务确保订单创建和所有相关的库存调整以原子方式应用，在整个过程中维护数据完整性。
- 在管理**版本更新**时，重要的是明确指定当前活动的实体版本，同时将上一个版本标记为非活动。这确保了应用程序或用户应使用哪个版本永远不会产生歧义。如果这些更改分别应用且其中一个更新失败，可能导致冲突数据，例如多个活动版本或根本没有版本，从而导致错误或不一致的行为。多文档事务允许以原子方式进行两次更新，保持清晰可靠的版本状态。

然而，并非每个多步骤过程都需要事务。MongoDB 的文档模型从一开始就是以性能为设计目标的，这一点在比较单文档操作与多文档事务时最为明显。两者之间的性能差距存在是因为事务需要额外的锁定以确保隔离，保持数据的快照、在多个服务器之间协调（在分片集群中）以及两阶段提交协议（在分片集群中）。

**当性能很重要时，请遵循此规则：**如果你能设计数据模型将相关数据保留在单个文档中，你几乎总是会比使用多文档事务获得更好的性能。因此，请考虑在以下情况下避免使用多文档事务：

- **相关数据可以在单个文档中建模：**如果所有需要原子更新的信息都适合放在单个文档中，利用 MongoDB 内置的单文档原子性会更高效。这种方法减少了与多文档事务相关的复杂性和开销，从而获得更好的性能和更简单的错误处理。使用单文档原子性还可以避免跨多个文档或集合的事务带来的额外锁定和协调成本。
- **较弱的一致性是可以接受的：**并非每个应用程序都需要严格的一致性保证。在某些情况下，允许宽松的一致性可以通过减少锁定和协调开销来提高性能和可扩展性。例如，分析仪表板或社交媒体信息流可以容忍数据中的轻微延迟或临时差异，而不会影响用户体验。在适当的情况下选择较弱的一致性可以帮助优化资源使用和系统响应能力，避免在不需要多文档事务时产生额外成本。
- **大规模写操作：**事务在可以修改的文档数量上存在实际限制。例如，不要使用事务加载数千个文档来生成报告或分析仪表板。这会产生不必要的开销并可能导致超时错误。相反，使用带有 `{readConcern: "snapshot"}` 选项的快照读取以实现时间点一致性，或创建 MongoDB 视图，在没有事务开销的情况下呈现数据的统一视角。

请记住，有效的模式设计通常可以完全消除对事务的需求。在使用事务之前，请自问：*“这里绝对需要事务一致性吗？”* 和 *“我能否以不同的方式建模此数据以利用单文档原子性？”*

## 事务 API 和会话管理

MongoDB 提供了两种处理事务的方法：Core API 和 Callback API。每种方法各有其适用场景，取决于你的需求和编码风格。

### Core API

Core API 让你可以显式控制事务生命周期的每个步骤。你负责启动会话、开始事务、提交或中止事务以及结束会话。下面是一个典型的模式，它启动会话、启动事务、执行若干操作并尝试提交事务。它必须处理提交的成功或失败，如果要进行另一次尝试，则必须在代码中显式编写，如下所示：

```
// Start a session
const session = client.startSession();

// Start a transaction
session.startTransaction();
```

```
try {
  // Perform operations within the transaction
  await collection1.updateOne({ _id: 1 }, { $set: { status: "active" } }, { session });
  await collection2.insertOne({ refId: 1, details: "..." }, { session });

  // Commit the transaction
  await session.commitTransaction();
} catch (error) {
  // If an error occurred, abort the transaction
  await session.abortTransaction();
  throw error;
} finally {
  // End the session
  session.endSession();
}
```

让我们逐一回顾每个部分以了解正在发生的事情：

1. **会话创建：**首先，我们使用 `client.startSession()` 创建一个新会话。MongoDB 中的所有事务都需要会话。
2. **事务初始化：**我们使用 `session.startTransaction()` 在会话中启动新事务。
3. **数据库操作：**在 try 块内部，我们执行多个操作（更新一个集合并向另一个集合插入）。每个操作都包含会话对象以将其与我们的事务关联。
4. **事务提交：**如果所有操作都成功，我们使用 `session.commitTransaction()` 提交事务，这将使所有更改可见。
5. **错误处理：**如果在操作或提交期间发生任何错误，我们捕获它，使用 `session.abortTransaction()` 中止事务，并重新抛出错误。
6. **清理：**finally 块确保无论成功还是失败，我们始终使用 `session.endSession()` 结束会话以释放资源。

使用 Core API 给予你完全的控制，但这也意味着你负责管理事务生命周期的每个细节。虽然功能强大，但这种方法需要仔细的错误处理和清理以确保可靠性和一致性。



## 回调 API

回调 API（也称为便捷 API）通过处理大部分样板代码来简化事务管理。无需显式写出所有步骤，每个驱动程序都提供了一种更简洁的方式来实现相同的功能，并且能够自动处理某些错误上的重试。为了更好地了解，让我们看一个示例：

// Using the Callback API
await client.withSession(async (session) => {
  return await session.withTransaction(async () => {
    // Perform operations within the transaction
    await collection1.updateOne({ _id: 1 }, { $set: { status: "active" } }, { session });
    await collection2.insertOne({ refId: 1, details: "..." }, { session })
  });
});

这个示例演示了使用回调 API 的 MongoDB 事务，它相比核心 API 具有以下几个优势：

- **简化会话管理：** client.withSession() 方法会自动创建会话，并在操作完成时确保其正确关闭，无论成功还是失败。
- **自动化事务处理：** session.withTransaction() 方法管理整个事务生命周期。它启动事务，在回调完成后尝试提交，并在发生错误时自动中止。
- **内置重试逻辑：** 与核心 API 示例不同，回调 API 包含针对瞬态错误的自动重试逻辑，遵循 MongoDB 推荐的重试模式。
- **更简洁的代码：** 嵌套的回调结构消除了显式 try/catch/finally 块的需求，使代码更简洁，并更专注于业务逻辑而非事务管理。

对于大多数应用程序，**推荐使用回调 API**，因为它简单且内置了重试和错误处理。然而，在需要对事务行为进行非常具体的控制或需要在复杂情况下交错事务和非事务操作时，核心 API 可能更可取。

## 读写关注点与事务行为

读写关注点控制着操作的持久性和一致性保证，包括读取数据的陈旧性和持久性。然而，在事务中，读写关注点具有一些特殊行为。

MongoDB 中的事务采用推测性多数读行为以确保读写自一致语义，这意味着所有或大多数读关注点行为相同：它们读取快照中可用的最新数据，并且事务成功提交的能力意味着数据将在事务成功完成时被多数提交。

写关注点决定了 MongoDB 对写操作请求的确认级别。我们在第 5 章《复制》中讨论了各种选项，但对于事务而言，重要的是要知道默认写关注点 majority 是唯一有意义使用的关注点，并且它适用于整个事务，而非事务内部的单个写操作。

> **事务级读写关注点**
> 
> 读写关注点是在事务级别设置的，而不是在事务内的单个操作上，因此你不能为事务中的单个操作指定不同的读写关注点。

要在事务上设置读写关注点，请将值传递给 startTransaction 方法：

// Example showing proper transaction read/write concern configuration
session.startTransaction({
  readConcern: { level: "snapshot" },  // Default
  writeConcern: { w: "majority" }      // Default
});

作为一般规则，如果你关心事务的正确性和持久性，最好保留读写关注点的默认值。

## 事务的性能考虑

对于 MongoDB 事务而言，性能是一个重要的考虑因素，可能决定应用程序的成败。虽然事务提供了强大的一致性保证，但它们也会引入开销，可能影响系统的速度、可扩展性和资源利用率。在本节中，我们将探讨 MongoDB 事务的关键性能考虑因素，并提供优化事务工作负载的实用建议。

### 副本集与分片集群事务

事务的行为和性能影响取决于你是在副本集还是分片集群上运行。在副本集中，事务性能相对简单。事务中的所有操作都由主节点协调。影响性能的主要因素是受影响文档的数量、文档的大小以及客户端与主节点之间的网络延迟。这些元素直接影响事务执行的速度和提交速度。

在分片集群中，情况变得更加复杂。跨分片事务，即触及多个分片数据的事务，需要分布式事务协调器和两阶段提交协议。这增加了开销，并可能在以下几个方面影响性能：

- **延迟增加：** 每个跨分片操作都会在协调器和分片之间增加网络往返
- **资源利用率更高：** 事务协调需要额外的内存和 CPU
- **级联性能问题的潜在风险：** 如果一个分片变慢，可能会影响整个集群的事务性能

然而，并非所有分片事务都相同。仅与一个分片上的文档交互的事务在性能上与副本集事务相同。读取多个分片但只写入一个分片的分片事务会产生轻微的性能损失。最昂贵的事务是写入多个分片的事务。涉及的分片越多，延迟越高。

在分片环境中，通过设计分片局部性可以显著提高性能。这意味着结构化数据和分片键，使事务中经常一起更新的相关文档驻留在同一分片上。这最大限度地减少了跨分片事务的需求。

此外，如果你的应用程序是全球分布式的，重要的是要考虑跨区域事务延迟。为缓解此问题，请考虑以写入限制在单个区域的方式分发集合，或探索其他技术以平衡一致性和性能。

### WiredTiger 缓存考虑

MongoDB 的 WiredTiger 存储引擎使用内存缓存来提高性能，但事务与此缓存的交互方式有时会导致性能问题。

事务通过创建读取或修改的文档快照来依赖缓存。这些快照必须保留在缓存中，直到事务完成。长时间运行的事务会阻止缓存驱逐，导致内存压力。

最严重的问题是当这导致 TransactionTooLargeForCache 错误时，该错误发生在事务的操作和快照超过可用缓存大小时。这通常发生在以下情况：

- 事务触及的文档太多
- 事务包含非常大的文档
- 事务运行时间过长，阻止缓存驱逐
- WiredTiger 缓存配置对于工作负载来说太小

为防止这些情况，具体取决于情况，有几种策略：

- **限制事务大小：** 将每个事务的文档数量保持在 1,000 以下
- **限制事务持续时间：** 在 60 秒内提交或中止事务（默认限制）
- **配置适当的缓存大小：** 确保 WiredTiger 缓存设置为事务繁重工作负载的 RAM 至少 50%
- **监控缓存压力：** 关注 `wiredTigerCacheSizeBytes` 和 `wiredTigerCacheMaxBytes` 等指标的增加

确保良好的事务性能需要使用最佳实践、勤勉的监控，并在不必要时最大限度地减少事务使用。



## 管理事务运行时限制和错误

MongoDB 强制执行默认的 60 秒事务运行时限制，以防止长时间运行的事务影响集群健康。该限制存在有几个重要原因：长时间的事务会长时间锁定文档，阻止其他操作访问所需数据并在应用程序中造成瓶颈；它们会增加服务器的内存压力，可能影响整体数据库性能；它们会阻止 WiredTiger 缓存从缓存中驱逐数据，这可能导致内存耗尽和性能下降；并且它们会显著增加操作冲突和中止的可能性，迫使应用程序处理更多错误情况。

鉴于这些限制，有效管理事务持续时间对应用程序的可靠性至关重要。你可以通过跟踪事务通常运行的时间长短并为接近限制的事务设置警报来监控事务持续时间，从而在故障发生前获得优化的时间。虽然可以通过调整 transactionLifetimeLimitSeconds 服务器参数来配置限制，但增加它应被视为最后的手段，因为它并不能解决根本的性能问题，而且可能恶化整体系统健康状况。

更可持续的方法是优化事务以更快完成。这可以通过将大型事务拆分为更小、更易管理的事务来实现，每次处理更少的文档；确保所有查询谓词都已建立索引以加快文档选择；优化事务中使用的任何查询和聚合管道以减少处理时间；避免事务范围内的不必要操作；并且在可能的情况下，将只读操作在事务之外执行，当它们不需要事务提供的 ACID 保证时。

除了时间限制的挑战之外，像 MongoDB 这样的分布式系统不可避免地会遇到需要正确处理的瞬态错误，以实现健壮的应用程序。MongoDB 通过特定的错误标签帮助开发人员识别这些情况，这些标签建议适当的恢复策略。当你遇到 TransientTransactionError 时，它表示存在临时问题，例如网络故障、主节点选举或短暂的资源限制，如果重试则可能成功。对于这些情况，实现带有指数退避的完整事务重试可以让你的应用程序优雅地恢复，同时在不稳定期间防止系统过载。

同样，UnknownTransactionCommitResult 错误表示对提交是否成功存在不确定性，通常由提交确认期间的网络问题引起。此处的正确响应略有不同：你应该只重试提交操作而不是整个事务，因为事务工作本身已经执行完毕，只有最终确认存在疑问。

重要的是，监控重试率可以为你的系统健康提供宝贵的见解。重试次数突然增加通常表明存在潜在的性能问题，例如网络不稳定、资源限制或配置问题，需要进行调查。通过将重试监控与整体性能指标连接起来，你可以在问题对应用程序的可靠性产生重大影响之前识别并解决它们。

## 锁获取与竞争管理

MongoDB 对事务使用多粒度锁定系统。理解锁行为对于优化事务性能至关重要。MongoDB 的锁定机制在多个粒度级别上运行，从数据库级到单个文档锁，创建了一个在数据一致性和操作吞吐量之间取得平衡的层次系统。

锁竞争通常在多个事务竞争修改同一文档时、在索引或集合创建等管理操作期间，或在集中在少量文档上的高写入负载下出现。有效的缓解需要多方面的方法，重点是减少锁冲突的可能性和持续时间。

保持事务小而专注是最小化锁持续时间的基础，使其他操作能够更快进行。不是将写入集中在特定文档上，分散这种活动有助于防止形成成为瓶颈的热点。管理任务应在活动较低的时段安排，以避免与常规应用程序工作负载竞争。

适当的索引通过减少操作的执行时间从而最小化它们持有锁的时间，在操作效率中发挥着至关重要的作用。通过 db.serverStatus().locks 进行定期监控可提供有关锁等待时间的宝贵见解，使能够在问题影响应用程序性能之前主动识别新兴问题。

锁竞争问题的识别通常通过几个关键指标表现出来：事务中止率和重试次数开始攀升，因为操作第一次未能成功完成，操作队列随着请求等待资源可用而变得更长，锁等待时间明显增加，并且客户端在操作超过可接受的响应阈值时遇到超时。通过理解这些模式并实施适当的预防措施，数据库管理员即使在要求苛刻的工作负载下也能保持最佳性能。

## 优化事务大小和持续时间

确保良好事务性能最有效的方法是保持事务小而短暂。在本节中，我们将重点介绍如何通过限制事务大小和最小化事务持续时间来优化你的事务占用。

首先，尝试限制事务的大小。在可能的情况下，将其限制在每个事务少于 1,000 个修改的文档。接下来，有一些重要的策略可用于最小化事务持续时间：

- **在事务前准备数据：** 在事务之外执行昂贵的计算
- **使用高效查询：** 确保事务内的所有操作都使用索引
- **批量相关更改：** 在可能的情况下将多个写入分组到单个批量操作中
- **拆分大型操作：** 将非常大的操作分解为更小、更易管理的事务

通过应用这些优化策略，你可以显著提高 MongoDB 中事务工作负载的性能。

## 常见事务反模式及其性能成本

即使怀着最好的意图，在 MongoDB 中使用事务时也很容易陷入常见陷阱。理解如何不使用事务与了解何时使用事务一样重要。在本节中，我们将探讨最频繁的反模式，解释它们为何会损害性能，并提供实用的指导以避免它们，这样你就可以让数据库保持高效运行，让运维团队满意。

### 长时间运行的事务及其对系统性能的影响

在为 MongoDB 设计事务时，性能应是主要考虑因素。高效的事务确保你的数据库保持响应、保持高吞吐量，并为用户提供良好的体验。糟糕的事务设计，特别是当操作运行时间过长时，会对系统资源造成过度压力，增加冲突风险，并最终导致故障。

长时间运行的事务就像那个 overstays their welcome 的访客；它们占用资源、阻塞其他操作，并可能导致严重的性能问题。过长事务的一些示例如下：

- 一个事务尝试在单个操作中插入或更新数千或数百万个文档
- 包含外部 API 调用、复杂计算或终端用户交互的操作，导致事务保持打开状态数秒或数分钟
- 批处理作业将整整一天的数据导入包装在单个事务中

长时间运行的事务带来了一些性能成本。包括以下内容：

- **增加锁竞争：** 锁在事务持续时间内被持有，阻止其他操作访问被锁定的文档，并显著降低并发性和吞吐量。
- **WiredTiger 缓存压力：** 存储引擎必须在事务完成之前将所有修改数据的预映像和后映像保留在缓存中。大型事务可能消耗大量缓存，迫使频繁驱逐其他有用数据。
- **TransactionTooLargeForCache 错误的风险：** 如果修改超过 WiredTiger 缓存的某个阈值，事务将完全失败。
- **超过 transactionLifetimeLimitSeconds：** MongoDB 默认的 60 秒事务限制是有充分理由的。长时间运行的事务有被自动中止的风险，导致工作浪费和重试风暴。
- **复制滞后：** 大型事务在提交时可能产生 oplog 条目的突发，可能导致从节点落后。

关键要点是： 将大型操作分解为更小、更易管理的事务。保持事务简短而高效，最好在毫秒而不是秒内完成。这种方法有助于保持系统性能，减少资源竞争，并降低事务失败的可能性。

### 在单文档原子性已足够的情况下不必要的事务使用

新接触 MongoDB 的开发人员可能会陷入过度使用事务的陷阱，将关系数据库中并不总是必要的习惯带入文档模型。让我们检查一些事务被误用的常见场景：

- **对单个文档更新使用事务：** 将单个文档更新包装在事务中是不必要的，因为 MongoDB 中单文档操作本身就是原子的。这种冗余方法会增加处理开销，却不会提供任何额外的数据完整性保障。
- **使用事务代替更好的模式设计：** 另一个常见错误是在数据可以建模为单文档时仍使用事务。花时间妥善设计模式可以消除许多事务需求，并显著提升性能。
- **将逻辑相关的数据拆分到多个集合中：** 开发者还经常为逻辑上应归属在一起的数据创建单独的文档，然后使用事务来原子化地更新它们。这种方法不仅使代码复杂化，还会引入潜在的性能瓶颈，并增加事务冲突的可能性。
- **忽略单文档原子性：** MongoDB 的单文档原子性是一个强大的特性；不要忽视它！对于可以用单文档更新处理的运算，使用多文档事务会增加不必要的开销和复杂性。

### Tip

在适当的情况下，将相关数据嵌入到单个文档中，以减少对多文档事务的需求。

下面是一个示例，展示了事务繁重的关系型方法与文档优化的 MongoDB 模型之间的差异：

// Instead of separate collections requiring transactions:
// users collection: { _id: userId, name: "Jane", ... }
// profiles collection: { userId: userId, preferences: {...}, ... }
// settings collection: { userId: userId, notifications: {...}, ... }

// Consider a consolidated model:
// users collection
{
  _id: userId,
  name: "Jane",
  profile: {
preferences: {"..."}
},
settings: {
  notifications: {"..."}
}
}

在第一种方法中，用户信息被拆分到三个独立的集合：users、profiles 和 settings。每次需要在这些集合间更新相关数据时，都需要使用多文档事务来确保一致性。这种方法会造成不必要的复杂性和性能开销。

第二种方法展示了一种合并模型，其中所有用户相关信息都嵌入在 users 集合中的单个文档内。采用这种设计，你可以在一次原子操作中更新用户的个人资料偏好和通知设置，而无需事务。这种方法简化了代码、提升了性能，并利用了 MongoDB 文档模型的设计初衷。

## 单文档事务

对单个文档进行多次不同的更新，通常都可以用一次原子更新来替代。除非在两次写入之间涉及第三方交互，而这本身就存在问题，因为可能导致延迟大幅增加并有超出事务超时限制的风险，否则正确的做法是组合一次更新（必要时使用富有表现力的聚合语法），在一次操作中完成所有修改。

如果必须确保在某个线程更新文档时没有其他线程读取该文档，可以在不使用事务的情况下通过在文档中放置一个逻辑锁字段来实现：先用一次更新设置该字段，后续在更新其他字段时取消该字段。请注意，确保其余操作在与文档交互时检查锁是否存在。

## 仅用于只读操作的事务

仅为读操作使用多文档事务是不必要的开销，会对性能产生负面影响。为了确保对多个文档的一系列读取具有一致的快照，请使用 read concern snapshot 而不是启动事务。如果需要确保读取反映之前的写入，请使用因果一致的会话或使用线性化读关注。

## 对事务范围和原子性的误解

一种常见的反模式是事务中包含过少或过多的内容，或误解了哪些操作真正是原子的。另一个常见误解是认为单个写入命令即使影响多个文档也是原子的。带有 `multi:true` 选项的更新操作或 `updateMany` 方法整体上不是原子的；只有其中的每个单独写入是原子的。要使此类多更新成为原子操作，就需要将其包装在事务中。

仅将必须一起保持原子的操作包含在事务中。非关键操作应放在事务之外执行，以减少范围并提升性能。

## 对热点文档/集合的频繁小事务

小事务通常是好事，但对同一文档过于频繁地运行可能会导致性能问题。这通常发生在不同服务独立更新相关文档时，例如多个微服务同时修改同一产品的订单状态和库存。当许多事务尝试更新单个热门文档时也可能出现问题，例如大型游戏活动期间的排行榜条目。在某些工作流程中，例如用户认证流程会频繁更新会话数据、日志和审计记录，相同的集合会被反复触及，问题会累积。

这些情况会造成实际的减速。即使是快速的事务也可能需要排队等待文档锁，这意味着操作是串行处理而不是并行处理。竞争越激烈，写入冲突发生的可能性越大，从而迫使事务重试。

在这些情况下，其他方法通常更有效。不要触发大量小事务，可以在应用程序中批量更新并作为一次操作发送。对于需要高吞吐量的场景，基于队列的系统可以收集操作并批量处理。

如果无法避免竞争并且需要在事务中更新多个文档，请尝试先更新竞争最激烈的文档。这样，如果事务需要重试，就不必重复太多工作。

## 不当的错误处理和重试逻辑

事务可能因多种原因而失败：瞬时网络问题、临时锁竞争或服务器端条件。如果你直接使用 Core API（而不是会自动处理重试的 Callback API），则在应用程序代码中实现适当的错误处理和重试逻辑至关重要。

一个常见错误是在遇到 TransientTransactionError 后未能重试事务，而该错误通常可以通过简单重试恢复。另一方面，过于激进地重试，而不进行任何延迟或退避，会使情况恶化，增加竞争。另一个问题是无限重试而不设置最大尝试次数，这可能导致资源浪费和进程卡住。开发者有时也会错误处理 UnknownTransactionCommitResult，重试整个事务而不是仅重试 commitTransaction 命令。

这类错误可能产生严重后果。管理不善的重试在高流量期间可能使服务器过载。此外，如果重试逻辑不是幂等的或范围不正确，相同的操作可能会被应用多次。

为了避免这些陷阱，最佳做法是使用 Callback API，它会在内部安全地自动重试事务。如果你使用 Core API，请确保实现带有指数退避和抖动的重试逻辑，以避免压垮系统，同时仍允许可恢复的失败在后续尝试中成功。

## 事务指标监控不足

正如俗话所说，“如果不测量，就无法改进！” 未能监控事务性能会让看不见的问题演变成生产事故。

为了掌握事务健康状况，重要的是跟踪关键指标，例如活动事务数以及启动、提交和中止的总事务数。监控事务延迟，即事务完成所需的时间，有助于识别减速。此外，关注 WiredTiger 缓存压力和驱逐率可提供缓存利用率的洞察。诸如等待时间和获取次数等与锁相关的指标可揭示事务是否因竞争而延迟。最后，跟踪错误率，特别是事务中止或需要重试的频率与总事务数的比例，有助于定位不稳定性。

为了有效监控，请在 MongoDB Atlas 或你偏好的系统中设置仪表板以可视化这些指标。为异常趋势创建警报，例如中止率飙升或事务持续时间增加。将事务执行详情与数据库指标一起记录可以帮助关联问题。定期审查这些事务模式可实现持续优化并及早发现潜在问题。



## 摘要

MongoDB 中的事务提供了强大的一致性保证，但它们也伴随着需要仔细考虑的权衡。通过遵循本章概述的最佳实践，只要记住几个关键原则，你就可以在对性能影响最小的情况下有效使用事务。在数据模型允许时，优先使用单文档原子性而非事务。保持事务小巧、专注且生命周期短。随着应用程序的演进，持续监控和优化。当然，在生产部署之前，务必在真实负载条件下测试事务行为。

最成功的 MongoDB 应用程序审慎使用事务：作为一种更广泛的数据一致性策略中的工具，该策略满足应用程序的要求，同时保持用户期望的性能和可扩展性。
