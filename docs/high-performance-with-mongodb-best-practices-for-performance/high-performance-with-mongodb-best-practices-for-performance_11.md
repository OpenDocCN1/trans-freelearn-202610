# 11 管理连接和网络性能

## 管理连接和网络性能

适当的连接管理策略可以决定解决方案是极速、具有弹性，还是在负载下崩溃。在本章中，我们将探讨连接管理在实现最佳性能和可靠性方面的作用。

首先，我们将检查连接基础以及影响数据库性能的网络因素，包括延迟、连接频繁创建与销毁以及网络饱和。然后，我们将探讨 MongoDB 连接架构，从 TCP/IP 层到驱动程序连接池，并深入研究连接生命周期，以了解连接是如何建立、使用和终止的。最后，我们将介绍监控、故障排除和优化连接管理的必要策略，以防止故障级联并确保您的 MongoDB 应用程序在真实条件下保持峰值性能。

本章涵盖的主题包括以下内容：

-   MongoDB 中连接工作原理背后的关键概念
-   典型的连接生命周期是什么样的
-   某些连接故障如何导致更广泛的系统问题
-   MongoDB 如何在内部处理连接的概述
-   高效管理连接的技巧

## 了解连接基础

网络性能通常成为数据库驱动应用程序中的隐藏瓶颈。即使硬件强大且查询已优化，糟糕的网络连接也会对应用程序的响应能力和用户体验产生负面影响。有几个因素促成了这种影响，包括以下内容：

-   **往返延迟：** 每个数据库操作至少需要一次网络往返，导致在用户期望亚秒级响应的交互式应用程序中出现明显延迟。这在微服务架构中尤其成问题，因为单个用户请求可能会触发多个级联数据库操作。
-   **连接建立开销：** 创建新连接需要 TCP 握手、TLS 协商和 MongoDB 身份验证。这些步骤可能使会话中的首次查询增加数百毫秒的延迟。这种开销的影响在无服务器环境或高并发应用程序中更为明显，在这些环境中连接经常建立和终止。
-   **带宽限制：** 大查询结果或批量操作可能会饱和可用网络容量，导致共享同一网络路径的所有数据库操作延迟。处理媒体文件、生成包含大量数据集的报告或执行数据迁移或 ETL 任务的应用程序尤其容易受到带宽限制的影响。
-   **网络稳定性：** 数据包丢失或间歇性连接问题可能导致重试和超时，从而导致响应时间不可预测和用户体验下降。这些问题在移动应用程序、边缘计算场景或在基础设施可靠性较差的地区运营时尤其具有破坏性。
-   **分布式系统复杂性：** 在现代分布式架构中，应用程序可能与分布在不同区域或云提供商中的多个数据库实例通信，从而增加连接开销并引入协调挑战。这种复杂性在全球部署期间最为明显，此时跨区域延迟会显著影响性能，或在部分中断期间触发故障转移机制时。

虽然开发人员经常专注于优化查询和索引，但网络层通常决定了实际的性能上限。单个管理不善的连接可能会使操作时间增加数百毫秒，对用户造成明显影响。

## 生产负载下的连接管理

连接管理问题通常只在生产负载下才会出现。一个在开发期间表现良好的系统在暴露于真实流量模式时仍可能经历严重的连接问题。

了解网络因素和连接过程如何影响您的应用程序有助于识别和解决 MongoDB 部署中的潜在性能瓶颈。有三个关键网络因素直接影响应用程序的吞吐量和响应能力：延迟、连接频繁创建与销毁以及网络饱和。让我们逐一检查这些因素。

## 延迟

延迟是发送请求和接收响应之间的延迟。这种延迟会影响每个操作，无论大小如何。MongoDB 操作中的延迟受多种因素影响，包括地理距离、网络条件以及操作的结构，使得全球分布式应用程序采用数据本地性或边缘缓存等策略以保持响应能力至关重要。请考虑以下因素：

-   应用程序服务器与 MongoDB 实例之间的地理距离增加了不可避免的基础延迟。将 MongoDB 实例部署在与应用程序服务器相同的区域，并为全球应用程序使用具有适当读偏好的多区域集群。
-   网络质量问题，例如拥塞或路由问题，会增加延迟变化。实施网络监控，使用 MongoDB Atlas 指标或自定义探针等工具，在网络退化影响用户之前识别和解决网络退化。
-   与批量操作相比，单独发送的单个操作会产生累积的延迟惩罚。在适当时使用批量操作。
-   具有全球分布用户的应用程序可能需要数据本地性或边缘缓存等策略来减轻高延迟影响。

总之，延迟是影响 MongoDB 性能和用户体验的重要但经常被忽视的因素。即使是微小的延迟改进的累积影响也能显著增强应用程序的响应能力，尤其是在规模化时。通过战略性地解决地理位置、网络质量、操作批处理和数据本地性，开发人员可以最小化延迟瓶颈，并在全球分布式应用程序中提供用户期望的响应体验。请记住，延迟优化不是一次性任务，而是一个需要随着应用程序和用户群的演变而定期测量、分析和改进的持续过程。



## 连接抖动

频繁创建和销毁连接会产生显著的开销，这会严重影响应用程序性能和资源利用率。连接抖动是指数据库连接的快速建立和终止，每次都会引入多个昂贵的操作。以下是一些示例：

- 新连接需要 TCP 握手，通常还伴随 TLS 协商。每个 TCP 握手至少需要在客户端和服务器之间进行一次往返，而 TLS 协商则会增加多次额外的往返以及复杂的加密操作，尤其是在跨地理区域的情况下，完成可能需要数百毫秒。
- MongoDB 的 SCRAM 认证需要多次往返。这种安全认证机制执行挑战-响应序列，通常需要在连接经过认证并准备好使用之前进行 2-3 次网络往返，从而为每次新连接增加延迟。
- 客户端和服务器都必须为每个连接分配内存和资源。在服务器端，MongoDB 为每个连接分配内存缓冲区、创建线程资源并维护状态。在客户端，类似的资源也会被分配，包括套接字缓冲区和管理结构，当连接数达到数百或数千时，这些资源会变得十分可观。
- 现代 TLS 握手涉及复杂的加密操作，包括密钥交换、证书验证和密码套件协商。这些操作会消耗 CPU 周期，在高连接速率下会加剧 CPU 饱和。

连接抖动在无服务器环境或微服务架构中尤其成问题，在这些环境中服务频繁启动和停止。在无服务器环境中，如果未妥善管理，每个函数调用都可能建立一个新的数据库连接。在规模化情况下，这在流量高峰期间可能导致每秒数千次的连接尝试，压垮数据库服务器和应用程序基础设施。

在后面的章节中，我们将探讨如何通过使用连接池来解决连接抖动问题。我们还将简要讨论在使用无服务器环境时如何最大限度地减少连接抖动。

## 网络饱和

当连接数或带宽达到上限时，性能会迅速下降，这可能导致一系列潜在问题出现：

- MongoDB 服务器对并发连接数有配置限制
- 过多的活动连接会消耗可用的服务器线程
- 当连接饱和时，操作必须在队列中等待
- 过多的操作会压垮可用的网络带宽

监控连接使用情况，以确保您不会接近饱和阈值。主动预防有助于避免在负载下突然出现的级联故障。

现在我们已经确定了管理这些网络因素的重要性，让我们深入了解 MongoDB 连接在整个生命周期中是如何实际建立、维护和终止的。了解这些机制将为优化应用程序的数据库交互提供实用的见解。

## 了解连接生命周期

MongoDB 连接具有明确定义的生命周期。了解此生命周期可以帮助您构建高效、可扩展的应用程序。连接生命周期分为三个阶段，我们将在以下各节中进行探讨。

### 连接建立

建立 MongoDB 连接涉及一系列低级和应用级握手，为客户端和服务器安全高效地通信做好准备。此过程中的每个步骤都会引入一定的开销，但它们共同构成了可靠且经过身份验证的会话的基础：

- 1. TCP 三次握手创建网络连接：此初始步骤使用标准的 SYN、SYN-ACK、ACK 数据包交换在您的应用程序和 MongoDB 服务器之间建立通信。
- 2. TLS/SSL 握手（如果启用）协商安全通信：当启用传输中网络加密时，此额外的握手会交换证书、验证身份并协商加密协议。现代 MongoDB 部署通常使用 TLS 1.2 或 1.3 以获得最佳安全性。
- 3. MongoDB 握手交换版本和身份验证信息：一旦网络连接建立，驱动程序和服务器就会交换协议信息，包括支持的功能、服务器功能和 MongoDB 版本兼容性。这确保驱动程序和服务器能够使用兼容的功能进行正确通信。
- 4. **认证过程验证凭据：** 根据您的安全配置，MongoDB 使用您配置的认证机制验证用户凭据。失败的认证尝试会被记录，并且根据配置可能会触发安全警报。
- 5. **服务器为新连接分配资源：** 每个连接都会消耗服务器资源，包括缓冲区内存、线程调度容量和文件描述符。这些资源在任何服务器上都是有限的，这就是为什么存在连接限制以防止资源耗尽，从而可能影响数据库性能或稳定性。

综合起来，这些步骤确保每个新连接都是安全的、经过身份验证的，并且完全准备好进行客户端-服务器交互。

### 连接使用与连接池

MongoDB 驱动程序使用连接池来优化性能、降低延迟并更高效地管理资源。以下是连接池在幕后如何工作：

- **连接池维护已建立的连接：** MongoDB 驱动程序实现连接池，预先建立并维护一组连接。这消除了后续操作的建立开销，并提供对数据库资源的即时访问。
- **操作在需要时从池中获取连接：** 当您的应用程序执行查询、更新或命令时，驱动程序会自动从池中获取一个可用连接。如果没有可用连接，操作要么等待（可配置超时），要么在低于最大容量时池会创建新连接。
- **操作完成后将连接释放回池中：** 操作完成后，连接会返回到池中而不是关闭，使其可立即供下一个操作使用。这种循环利用方法通过避免每次操作的建立成本来提高吞吐量。
- **合理复用消除了重复建立的成本：** 通过重用连接，应用程序避免了重复握手和身份验证的累积开销。对于高负载应用程序，这可以降低延迟并显著提高整体吞吐量。
- **健康监控确保连接保持有效：** 驱动程序会定期使用轻量级心跳命令检查池中连接的有效性。这可防止应用程序使用可能已被防火墙、代理或网络问题关闭的陈旧连接，确保操作不会因使用无效连接而失败。

连接池使 MongoDB 使用更高效，了解其作用可以帮助您更好地管理应用程序性能，尤其是在负载下。

### 连接终止

无论是有意设计还是由于意外事件，MongoDB 连接都可能并且会终止。了解常见原因和处理终止的最佳实践可确保您的应用程序保持稳定和响应：

- **空闲连接可能在配置的超时时间后关闭：** 为了节省资源，驱动程序和服务器都可以关闭长时间未使用的连接。此清理可防止资源泄漏，但在超时后恢复活动时需要重新建立。
- **应用程序关闭时应正确关闭连接：** 设计良好的应用程序会在优雅关闭期间显式关闭其 MongoDB 客户端。这会及时释放服务器资源并防止连接泄漏。大多数现代框架都提供用于注册这些清理操作的钩子。
- **网络错误可能导致连接被强制中断：** 诸如网络分区、防火墙中断或硬件故障等意外问题可能会突然终止连接。健壮的应用程序会实现重试逻辑并采用指数退避来优雅地处理这些情况，而不会影响用户。
- **服务器重启或维护需要重新建立连接：** 在 MongoDB 维护操作或副本集选举期间，现有连接可能会被终止。驱动程序会自动检测这些事件并建立新连接，但应用程序应为这些转换期间的操作实现适当的错误处理。
- **适当的清理确保资源及时释放：** 每个连接都会在客户端和服务器上消耗内存、文件描述符和处理能力。适当的终止会释放这些资源，防止内存泄漏和系统限制（如最大文件描述符）的耗尽。

通过主动管理空闲超时、应用程序关闭和意外断开连接，您有助于确保资源得到干净释放，并且应用程序能够优雅地恢复。

## 关闭 MongoClient 以防止资源泄漏

如果你使用的驱动程序支持，则应在应用程序关闭例程中始终调用 MongoClient.close() 方法，以正确释放所有连接及相关资源。这可以防止资源泄漏并确保应用程序干净终止。有关适当的连接清理策略的更多详细信息，请参阅本章后面“优化连接管理”部分。

理解 MongoDB 连接生命周期对于构建性能优异且健壮的应用程序非常重要。连接建立会带来一定的开销，因此对于高吞吐量系统而言，高效的池化和复用非常重要。正确处理连接终止可以防止随着时间的推移可能导致应用程序性能下降的资源泄漏。

## MongoDB 连接架构

理解 MongoDB 如何从驱动程序到服务器管理连接对于设计健壮的应用程序非常重要。本节介绍基本连接机制以及它们如何在应用程序栈中交互，包括 TCP/IP 和 MongoDB Wire 协议、驱动程序连接池以及服务器连接处理。

## TCP/IP 和 MongoDB Wire 协议

MongoDB 的客户端-服务器通信基于 TCP/IP，但包含多个 MongoDB 特定的增强和优化。理解这些技术细节有助于开发人员诊断连接问题并优化网络性能。

MongoDB Wire 协议是一种基于套接字的请求-响应式协议，定义了客户端和服务器如何通过标准 TCP/IP 套接字进行通信。它具有以下几个定义特征：

- **二进制 JSON（BSON）格式：** 与基于文本的协议（如 HTTP）不同，MongoDB 使用 BSON 实现高效的序列化和反序列化，且 CPU 开销最小。
- **现代消息格式：** 自 MongoDB 5.1 起，OP_MSG 已成为客户端请求和数据库回复的主要操作码，取代了旧的操作码，如 OP_QUERY 和 OP_REPLY。
- **压缩支持：** OP_COMPRESSED 使用 snappy、zlib 或 zstd 等压缩算法包装其他操作码，以减少网络带宽。
- **消息校验和：** 可选的 CRC-32C 校验和确保数据完整性，尤其对非 TLS 连接很重要。

当客户端连接到 MongoDB 时，会按顺序发生多个操作，每个阶段都可能带来性能影响：

1. **DNS 解析阶段：** 连接过程始于解析 MongoDB 服务器地址。DNS 解析将主机名转换为 IP 地址，SRV 记录可为副本集和分片集群启用智能服务发现。DNS 记录上的 TTL 设置会影响拓扑更改向客户端传播的速度。解析失败可能会在驱动程序中触发指数退避重试算法，可能导致连接延迟。一旦地址解析完成，连接将进入 TCP 建立阶段。
2. **TCP 连接阶段：** DNS 解析后，客户端建立网络基础。Keep-alive 数据包有助于维护长连接并检测死连接以释放资源。TCP 窗口缩放通过允许在需要确认之前传输更多数据，从而在高延迟连接上实现更高吞吐量。TCP 连接建立后，将应用安全层。
3. **TLS/SSL 安全阶段：** TCP 连接建立后，随后建立安全加密。证书验证会在验证服务器真实性时引入少量延迟。TLS 会话恢复可以通过重用先前会话的参数来减少重连时的握手开销。在 TLS 1.3（在较新 MongoDB 版本中受支持）下，握手往返次数从两次减少到一次，从而提高连接速度。所选密码套件会影响安全态势和 CPU 开销。一旦加密通道建立，MongoDB 特定协议协商开始。
4. **MongoDB 特定握手阶段：** 连接现在交换 MongoDB 协议信息。客户端发送 `hello`（或 `isMaster`）命令以交换功能文档（`isMaster` 保留用于向后兼容）。在此阶段，驱动程序检测服务器版本并相应调整功能兼容性。拓扑发现识别集群中的主节点、从节点和仲裁节点。诸如 `maxWireVersion` 之类的服务器参数决定可用功能和 Wire 协议兼容性。建立协议兼容性后，连接进入身份验证阶段。
5. **身份验证阶段：** 最终阶段在允许数据库操作之前验证客户端身份。SCRAM-SHA-256（默认）提供强大的安全性，但需要多次往返。X.509 证书身份验证将身份绑定到 TLS 证书以增强安全性。LDAP 和 Kerberos 代理身份验证会增加额外的网络跳数和延迟。一旦身份验证完成，连接即完全建立并可使用。

这些步骤中的每一个都会导致总连接延迟的增加，该延迟在本地部署中可能为几毫秒，而在跨地理区域或使用复杂身份验证方案时可能达到数百毫秒。这种连接开销凸显了连接池对于高性能应用程序至关重要的原因。

## 驱动程序连接池

MongoDB 驱动程序是特定于语言的库，处理与 MongoDB 服务器通信的复杂性。它们最重要的功能之一是连接池。当你的应用程序初始化 MongoDB 客户端时，驱动程序会创建一个连接池（或根据拓扑创建多个池）。当你的代码执行 MongoDB 操作时，驱动程序会从池中借用一个可用连接。它通过连接发送命令并等待响应。操作完成后，连接会被归还到池中以供重用。驱动程序还通过监控连接健康状况来维护连接池，并可能定期测试或替换它们。

连接池具有以下可调整参数：

- **maxPoolSize：** 池可维护的最大连接数（大多数驱动程序中默认为 100）。
- **minPoolSize：** 池即使在空闲时也能维护的最小连接数（大多数驱动程序中默认为 0）。
- **maxConnecting：** 限制并发建立中的连接数（大多数驱动程序中默认为 2）。此参数在 Rust 驱动程序中不可用。
- **maxIdleTimeMS：** 空闲连接在池中保留的时间，然后被关闭。

![](img/11c6cf3488b31bf4339aa4bd8ea9b45b_266_0.png)

> **为异步应用程序优化 maxPoolSize**
>
> 对于异步应用程序，将 maxPoolSize 设置为与预期并发量匹配而不是线程池大小，通常会带来更好的性能。

有关上述连接池参数的更多信息，请务必查看 MongoDB 文档 https://www.mongodb.com/docs/manual/tutorial/connection-pool-performance-tuning/。

连接池行为因驱动程序是同步还是异步而有显著差异。对于同步驱动程序，当没有可用连接时，调用线程会阻塞操作，直到有连接可用或等待队列超时到期。另一方面，异步驱动程序会返回一个 future 或 promise，在连接可用时解析，而不是阻塞。

## MongoDB 服务器连接处理

高效的连接处理支持可扩展、高性能的 MongoDB 部署。在服务器端，MongoDB 使用可配置参数和操作系统级资源的组合来管理传入的客户端连接：

- **net.maxIncomingConnections：** 控制同时客户端连接的最大数量（Windows 上默认为 100 万；在 Linux 上，默认为最大文件描述符限制的 80%）。由于每个连接都需要一个文件描述符，此限制有助于防止服务器资源耗尽。
- **操作系统限制：** 文件描述符限制（Linux/Unix 系统上的 `ulimit -n`）也可能限制连接数。

连接管理的具体细节还取决于部署拓扑（是单机实例、副本集还是分片集群）：

- **Standalone：** 应用程序直接连接到单个 MongoDB 服务器，使用单个连接池
- **Replica set：** 驱动程序发现所有成员并为每个成员维护单独的连接池，根据读取偏好路由操作
- **Sharded cluster：** 应用程序连接到 mongos 路由器，后者维护其与分片的连接，形成多层连接架构

现在你已熟悉 MongoDB 的连接架构，让我们讨论它如何促进连接的监控和故障排除。



## 监控和故障排除连接

有效的连接管理需要持续监控以及在问题发生时快速诊断问题的能力。通过实施主动监控实践并准备好清晰的故障排除方法，您可以在潜在问题影响应用程序的性能和可靠性之前识别它们。

MongoDB 驱动程序公开有关其连接池的详细指标，让您了解应用程序如何利用数据库连接。

大多数 MongoDB 驱动程序都实现了连接监控和池化（CMAP）规范，尽管每种语言驱动程序提供访问这些指标的不同方法。例如，在 Node.js 中，您可以使用事件监听器来监控连接池活动：

// Node.js example using event listeners for CMAP events
const uri = "mongodb+srv://user:pass@abcdef.mongodb.net/";
const client = new MongoClient(uri);
client.on('connectionPoolCreated', event => console.log(event));
client.on('connectionCheckedOut', event => console.log(event));
client.on('connectionCheckedIn', event => console.log(event));
```

请参阅 https://www.mongodb.com/docs/drivers/node/current/monitoring-and-logging/monitoring/#connection-pool-events 以了解有关使用 Node.js 驱动程序跟踪这些连接指标的更多信息。

虽然驱动程序指标捕获应用程序与其数据库交互的视图，但 MongoDB 服务器从其角度提供有关传入连接的补充指标。这些指标可以帮助您了解部署在所有客户端应用程序中的整体连接利用情况：

- **connections.current**：服务器上活动客户端连接数。接近最大值表示可能出现连接饱和。
- **connections.available**：服务器在达到配置限制之前还可以接受多少个连接。
- **connections.totalCreated**：服务器启动以来创建的连接总数。快速增加可能表示连接频繁创建和销毁。

您可以通过 MongoDB Shell 中的 serverStatus 命令或您首选的 MongoDB 驱动程序检索这些指标：

```
db.adminCommand({ serverStatus: 1 })
```

通过关联客户端和服务器端指标，您可以构建整个应用程序堆栈中连接健康的全面视图。请参阅 https://www.mongodb.com/docs/manual/reference/command/serverStatus/#connections 上的 MongoDB serverStatus 命令文档以了解更多信息。

当连接问题发生时，它们通常表现为特定类型的错误。学习如何识别这些症状对于有效故障排除至关重要：

- **socketTimeout**：操作花费的时间超过了配置的 socketTimeoutMS。通常表示网络拥塞或服务器过载。
- **EOF (End of File)**：服务器意外关闭了连接。这可能是由于服务器重启、网络中断或空闲超时策略造成的。
- **Broken pipe**：连接在客户端仍在使用时被切断。通常表示网络故障或代理中断。
- **Authentication failures**：凭据或身份验证配置不正确。可能在凭据轮换或配置更改后发生。

连接池耗尽是一个特别严重的情况，可能迅速降低应用程序性能。请注意以下警告信号：

- 驱动程序指标中等待队列长度增加
- 应用程序日志中出现 MongoWaitQueueTimeoutException 或类似错误
- 操作延迟突然增加
- 流量高峰期间请求失败

请记住，连接池耗尽会迅速级联成系统范围的故障，因为超时会触发重试，从而创建更多连接请求，加速耗尽。

对于使用 TLS 或基于 DNS 的服务发现的部署，可能会因安全或网络配置问题而出现额外的连接问题。这些问题可能特别具有挑战性，因为它们可能间歇性出现或仅在特定条件下出现。安全连接依赖于正确的 TLS 配置和证书管理。当遇到与 TLS 相关的连接故障时，请验证以下内容：

- 证书链有效且受所有客户端信任
- 证书主机名与服务器配置的主机名匹配
- TLS 协议版本和密码套件在客户端和服务器之间兼容
- 证书到期日期有效且未接近到期
- 中间证书已正确安装在所有系统上

当客户端和服务器的 TLS 配置不匹配时，常见问题就会出现。例如，如果您的应用程序需要 TLS 1.3，但 MongoDB 服务器仅支持到 TLS 1.2，即使两个系统都有有效证书，连接也会失败。

MongoDB Atlas 和副本集通常依赖 DNS SRV 记录进行服务发现。当这些环境中出现连接问题时，DNS 配置是常见原因。对于 DNS SRV 解析问题，您可以使用标准 DNS 诊断工具来验证配置是否正确：

```
dig srv _mongodb._tcp.your-cluster-hostname.mongodb.net
dig txt your-cluster-hostname.mongodb.net
```

这些命令有助于验证您的 DNS 是否正确配置以支持 MongoDB 的服务发现机制，这在副本集和分片集群部署中尤为重要。使用 MongoDB Atlas 时，请记住 DNS 传播延迟有时会在集群配置更改后导致临时连接问题。如果您最近修改了 Atlas 集群，请留出足够的时间让 DNS 更新在网络中传播。

## 连接监控最佳实践

在了解如何诊断特定连接问题后，实施全面的监控策略对于随着时间的推移维护系统健康至关重要。为了有效进行连接监控，您应执行以下操作：

- 1. **建立基线**：了解应用程序的正常连接模式
- 2. **设置有意义的阈值**：根据连接使用情况相对于限制来配置警报
- 3. **关联指标**：连接驱动程序端和服务器端指标以获得完整视图
- 4. **监控趋势**：注意可能表明问题发展的渐变
- 5. **自动化警报**：为高等待队列时间或接近限制的连接数设置主动通知

通过将这些监控实践与前面概述的故障排除方法相结合，您可以构建强大的连接管理策略，帮助在问题影响用户之前防止问题。

## 优化连接管理

现在您已经了解了如何通过连接管理实现和维护弹性系统，以及如何监控和故障排除连接问题，让我们更进一步，谈谈如何优化连接管理。实现最佳的 MongoDB 性能和弹性需要深思熟虑地调整连接管理策略。本节涵盖了优化连接池和为不同工作负载模式实施策略的关键方法。

## 连接池优化

优化连接池首先要确保池的大小适合您的应用程序。理想的连接池大小取决于应用程序的工作负载特征：

- **OLTP 工作负载：** 对于许多短操作，从中等池大小（50-100 个连接）开始
- **OLAP 工作负载：** 使用较小的池，其大小与预期的并发分析操作相匹配
- **批处理：** 根据批处理操作的并行度调整池大小

最佳实践是根据应用程序性能指标和观察到的行为调整连接池大小，而不是依赖固定的利用率百分比。监控等待队列大小、操作延迟和服务器端连接指标等关键指标，以确定连接池大小是否需要调整。

调整连接池时请考虑以下指南：

- 如果您的应用程序花费过多时间创建新连接，请增加 `minPoolSize` 以确保启动时有足够的连接可用
- 如果数据库 CPU 使用率高于预期且连接尝试次数较多，请考虑减少 `maxPoolSize` 以降低负载
- 如果负载较低但应用程序吞吐量低于预期，您可能需要增加 `maxPoolSize` 或调整应用程序线程

请记住，每个 MongoDB 驱动程序为拓扑中的每个服务器创建一个单独的连接池，因此应用程序的总连接数将为 `maxPoolSize` 乘以 MongoDB 服务器的数量。



## 连接超时配置

构建能够优雅处理网络中断和服务降级的弹性、高性能应用程序，需要配置适当的超时设置。配置不当的超时可能导致级联故障、资源耗尽或用户体验下降。MongoDB 提供了多个可配置的超时参数，用于控制连接行为的不同方面：

- **connectTimeoutMS**: 驱动程序在建立新连接时等待的时间。将此值设置为大于您部署中任何成员的最大网络延迟。
- **socketTimeoutMS**: 驱动程序等待特定操作响应的时间。将此值设置为驱动程序运行的最慢操作长度的两到三倍。
- **maxIdleTimeMS**: 空闲连接在池中保留的时间（在连接频繁创建与资源利用之间取得平衡）。

正确调整这些超时参数需要了解应用程序行为和 MongoDB 部署拓扑。

![](img/11c6cf3488b31bf4339aa4bd8ea9b45b_272_0.png)

> **重要**
> 
> 不要使用 socketTimeoutMS 来防止长时间运行的服务器操作。相反，对于支持客户端操作符超时的驱动程序，请使用 maxTimeMS() 或 timeoutMS() 与您的查询一起使用，以便服务器可以取消长时间运行的操作。例如，如果操作在驱动程序级别优雅地超时，应用程序可以尝试有意义的重试，而不会压垮服务器。如果没有适当的超时，重试可能会淹没连接池，加剧资源耗尽，并导致系统范围的停机。

## 服务器端优化

在自托管部署中，您需要配置 MongoDB 的连接参数和底层操作系统的限制，以确保最佳性能。这些设置共同决定有多少并发客户端可以连接到数据库。

```yaml
net:
  maxIncomingConnections: 65536
```

maxIncomingConnections 设置控制 MongoDB 将接受的同时客户端连接的最大数量。增加此限制允许更多并发客户端应用程序连接到 MongoDB 服务器，这对于高流量应用程序或具有许多微服务的环境至关重要。然而，仅仅增加此参数是不够的；您还必须调整操作系统的限制。

## 操作系统配置

在基于 Unix 的系统中，MongoDB 为每个客户端连接使用一个文件描述符。当 MongoDB 达到 maxIncomingConnections 限制或操作系统的文件描述符限制（以较低者为准）时，它将拒绝额外的客户端连接。这会在高需求期间造成瓶颈，严重影响应用程序可用性。

对于使用 systemd 的 Linux 系统，您应该在 MongoDB 服务文件中配置文件描述符限制：

```
[Service]
### In the MongoDB systemd service file
LimitNOFILE=64000
```

对于非 systemd 环境，请在 /etc/security/limits.conf 文件中为 MongoDB 服务用户设置限制：

```
mongodb soft nofile 64000
mongodb hard nofile 64000
```

更改这些限制后，必须重启 MongoDB 才能使更改生效。为了确认配置更改对部署有益，您可以使用以下验证方法：

- 1. 使用以下方法检查当前操作系统的限制：
```
ulimit -n      # For the current shell session
cat /proc/$(pidof mongod)/limits  # For the running MongoDB process
```
- 2. 通过 serverStatus 命令监控 MongoDB 连接利用率：
```
db.adminCommand({ serverStatus: 1 }).connections
```

输出将显示：

```
{
  "connections": {
    "current": 123,      // Current active connections
    "available": 63877,  // Remaining available connections
    "totalCreated": 1578  // Total connections created since startup
  }
}
```

- 3. 在 MongoDB 日志中查找连接拒绝错误，这表明您已达到连接限制：
```
[conn12345] Too many open connections
```

正确配置 MongoDB 的 maxIncomingConnections 限制和操作系统的文件描述符限制后，您应该在负载下看到改进的稳定性和性能。即使在流量激增期间，应用程序也能可靠地建立连接，并且您将避免在达到连接限制时发生的级联故障。MongoDB Atlas 根据集群层自动管理这些设置，根据工作负载需求扩展数据库配置和底层基础设施资源。

## 利用网络压缩进行性能优化

网络压缩是 MongoDB 中的一项重要优化技术，可减少客户端和服务器之间传输的数据量。通过在传输前压缩数据并在接收时解压缩，MongoDB 可以显著降低网络带宽需求，同时可能提高整体性能。此功能在高延迟连接或带宽受限环境中运行尤其有价值。

### 网络压缩的优势与权衡

在 MongoDB 部署中实施网络压缩时，了解优势和潜在缺点对于做出明智的决策非常重要。

启用压缩的主要好处之一是显著减少网络带宽消耗。通过在传输前压缩数据，MongoDB 可以显著减少网络上传输的总数据量。

这对于文本密集型文档尤其有效，例如具有冗长字段名称或字符串值的 JSON 数据，通常压缩效果很好。另一个显著优势是在某些环境中降低延迟并加快响应时间。由于需要跨网络传输的数据更少，操作可以更快完成，从而为用户提供更具响应性的应用程序体验。

然而，在生产环境中启用压缩之前必须考虑一些重要因素。CPU 资源利用率是一个重要因素。压缩和解压缩操作需要在客户端和服务器端消耗计算资源。在 CPU 资源已受约束的环境中，额外的处理需求可能会抵消网络优势。

还必须认识到，压缩并不总是能带来有意义的性能改进，在某些情况下甚至可能引入低效率。对于小型操作或处理已压缩的二进制数据（例如图像或视频）时，压缩和解压缩的开销可能超过减少网络流量的好处。在这些情况下，启用压缩可能会降低整体性能。

### 可用的压缩算法

MongoDB 提供了几种压缩算法选项，每种都有不同的特性，使其适用于各种用例：

- **snappy** 在压缩速度和比率之间提供了出色的平衡。它通常将数据压缩到原始大小的约 30-50%，同时使用最少的 CPU 资源。这使其成为大多数 MongoDB 部署的理想默认选择，提供有意义的带宽节省而不会产生显著的处理开销。
- **zlib** 比 Snappy 提供更高的压缩比，可能将数据大小减少到原始大小的 20-40%。然而，这以增加压缩和解压缩的 CPU 使用为代价。当带宽极其有限且 CPU 资源充足时，zlib 可能适用。
- **zstd**（在较新的 MongoDB 版本中可用）提供出色的压缩比，同时保持合理的 CPU 效率。它通常比 zlib 实现更好的压缩，同时计算成本更低，使其成为支持该环境的越来越受欢迎的选择。

选择压缩算法取决于系统在 CPU 使用和网络带宽之间可以承受的具体权衡，并且理想情况下应通过在工作负载上下文中进行基准测试来指导。



## 实现网络压缩

在 MongoDB 中启用压缩非常简单，且只需最少的配置更改。您可以在建立与数据库的连接时，通过连接字符串指定首选的压缩算法：

```
mongodb://hostname/?compressors=snappy,zlib
```

建立连接时，客户端和服务器会协商从提供的列表中选择最佳的相互支持的压缩算法。如果指定了多个算法（如前例所示），它们将按从左到右的偏好顺序进行评估。

默认情况下，MongoDB 部署已配置为启用压缩；然而，除非客户端指定 compressors 配置，否则客户端与集群之间的消息不会被压缩。使用适合您特定需求的算法启用网络压缩，可以在保持出色性能的同时降低 MongoDB 部署的网络利用率。

## 无服务器环境的连接策略

由于其临时性和独特的执行模型，在无服务器环境中管理连接会带来独特的挑战。本节探讨了针对无服务器函数（AWS Lambda、Azure Functions、Google Cloud Functions）的全面 MongoDB 连接策略，涵盖临时执行上下文、冷启动、扩容期间的连接突发以及资源限制等基本挑战，然后介绍实用的实现模式，包括连接池优化、函数处理程序外部的初始化技术以及在调用之间保持连接持久性的方法——所有这些都旨在帮助您构建具有可靠 MongoDB 连接性的弹性、高效的无服务器应用程序，同时最大限度地降低成本并提高性能。

无服务器函数按设计是临时的，带来了独特的连接管理挑战：

- **临时执行：** 函数启动、处理请求，并可能在任何时候被终止
- **冷启动：** 新的函数实例必须建立新的连接
- **连接突发：** 许多并发函数调用可能导致连接峰值
- **资源限制：** 函数实例具有内存和 CPU 限制

对于无服务器环境而言，最关键的模式是在函数处理程序外部初始化 MongoDB 客户端和连接池。让我们看一下以下示例，以便更好地理解：

```
const { MongoClient } = require('mongodb');
// MongoClient now auto-connects so no need to store the connect()
// promise anywhere and reference it.
const client = new MongoClient(process.env.MONGODB_URI);

export const handler = async() => {
  const databases = await client.db('admin').command({ listDatabases: 1 });
  return {
    statusCode: 200,
    databases: databases
  };
};
```

此代码演示了针对 AWS Lambda 专门优化的 MongoDB 连接模式的实现，但也可以改编用于其他无服务器环境。

MongoClient 实例在函数处理程序的范围之外创建，这将允许其被重用。故意在处理程序末尾排除 client.close() 应可使连接池在后续调用中保持活跃，从而降低“热”函数调用的延迟。

无服务器环境的连接池通常需要与传统应用程序不同的配置：

- **较小的池大小：** 从较小的 maxPoolSize（3-5 个连接）开始，因为每个函数实例都有自己的池
- **更低的空闲超时：** 设置更短的 maxIdleTimeMS 限制，以便更快地释放未使用的连接
- **避免过多的最小池：** 使用 minPoolSize: 0 以防止维护可能未使用的连接
- **设置适当的等待队列超时：** 与函数执行时间限制相匹配

在无服务器环境中采用适当的连接策略可以帮助缓解这些临时函数典型的一些挑战。通过使用优化的参数在函数处理程序外部策略性地初始化连接池，开发人员可以缓解冷启动和连接突发，确保持久、低延迟的数据库交互。

## 摘要

有效的 MongoDB 连接管理对于构建高性能、弹性应用程序至关重要。在本章中，我们探讨了网络堆栈如何成为数据库架构的关键基础，从延迟、连接频繁变化和饱和等基本网络因素到 MongoDB 的线协议和连接生命周期的技术细节。

连接池是最具影响力的优化技术，通过重用 TCP 连接并在多个操作之间分摊身份验证成本，显著提高应用程序性能。正确实现需要了解客户端池配置参数和相应的服务器端限制。MongoDB 的 maxIncomingConnections 参数与操作系统文件描述符限制之间的关键关系值得特别关注，因为这些设置共同决定了高峰流量期间的连接容量。

不同的计算环境需要特定的连接管理方法。对于无服务器部署，请在函数处理程序外部初始化连接池，并使用具有适当超时值的较小池。在分布式架构中，根据网络特征调整超时设置，并在可能的情况下利用感知本地性的路由。

对客户端指标（如池利用率和等待队列时间）进行定期监控，结合来自 serverStatus 的服务器端指标，可以全面了解连接健康状况。这种可观测性使您能够通过早期检测和适当的规模调整来防止级联故障。

通过在整个技术堆栈中实施这些技术原则，您将开发出即使在具有挑战性的网络条件下也能保持一致性能的 MongoDB 应用程序，确保随着数据量和用户群的扩大，可靠性和高效的资源利用。
