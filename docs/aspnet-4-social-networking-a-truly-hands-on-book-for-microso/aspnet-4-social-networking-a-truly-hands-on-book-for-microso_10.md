## 比较 ASP.NET MVP 与 ASP.NET MVC

微软平台上的 Web 应用程序开发已经从基于 CGI 的开发演进到经典 ASP 页面，再到 ASP.NET Web Form 开发，直至最新的 ASP.NET MVC。ASP.NET 于 2000 年初推出，它给 Web 应用程序的构建方式带来了重大变化，并且凭借其丰富的服务器控件（每次新版本都会新增控件），为应用程序开发带来了极大的生产力提升。

ASP.NET Web Form 开发模型旨在为 Web 开发者提供类似 Windows Form 的应用程序开发环境。而 Windows Form 开发本身又深受 VB 6.0（及更早版本）所提供的快速应用程序开发环境的影响。

### ASP.NET Web Forms

ASP.NET Web Forms 解决了早期经典 ASP 构建 Web 应用程序方式中的大量问题。其中一些如下：

- 减少了面条式代码，ASPX 和代码后置文件中的 HTML 与代码实现了更清晰的分离
- 能够使用 .NET 的一等公民语言，如 C# 和 VB.NET
- 编译后的代码带来了性能提升
- 服务器控件的可用性极大地提升了生产力，并帮助快速构建复杂应用程序
- 事件模型使得处理页面上的用户操作变得容易
- ViewState 和 ASP.NET 引擎帮助在回发之间保留数据（这也带来了一些副作用）
- 编程模型简单，任何人都能快速上手

其他好处，如更好的线程模型、垃圾回收等，都随 .NET 核心框架一起到来，很快便有大量开发者涌入这项技术。

虽然这一模型解决了很多问题，但它也引入了一些自身的问题。其中一些如下：

- 对 Web 编程标准（如 MVC 模式）的遵循度不够
- 测试 ASP.NET 应用程序并不容易
- 虽然业务逻辑仍然可以测试，但测试 UI 代码非常麻烦
- 代码本身没有促进关注点分离，虽然在 ASPX 页面中避免了面条式代码，但在后端却出现了数据访问逻辑与 UI 代码混在一起的情况
- 由于对生成的 HTML 控制有限，构建跨浏览器和可访问的应用程序并不总是那么容易

然而，情况并非毫无希望，确实也出现了一些模式来解决其中的部分缺陷。

### Web 表示模式

微软 **Patterns and Practices (PnP)** 团队提出了多种归类为 Web 表示模式（Web Presentation patterns）的模式。下面将对这些模式进行简要讨论。要了解更多细节，请查看：**http://msdn.microsoft.com/en-us/library/ff650511.aspx**。

### 页面缓存

很多时候，用户访问某个网页时看到的页面信息是相似的。页面本身是动态构建的，但由于查询性质的原因，最终呈现的视图却可能是相似的。因此，与数据缓存类似，我们可以通过利用过期策略来启用 ASPX 页面本身的缓存。这种特性正是页面缓存（Page Cache）模式所支持的。

### 拦截过滤器

拦截过滤器（Intercepting filter）模式扩展了前端控制器（Front Controller）的概念，它通过使用 HTTP 模块，在 ASP.NET 运行时引擎处理请求之前和之后都可以拦截这些请求。

### ASP.NET MVC

我们探讨了各种模式，也简要讨论了当前开发者在使用 ASP.NET Web Forms 技术构建 Web 应用程序时面临的关键问题。将近十年过去了，某种程度上我们确实需要有某种新模型尽快出现。不过，我们要明确一点：ASP.NET MVC 并不是对 ASP.NET Web Form 编程风格的替代。它的确解决了某些关键问题，并且应当被视为 ASP.NET 世界中的一种新编程范式。简而言之，这意味着当你开始构建一个新的 Web 应用程序时，你必须在 ASP.NET Web Form 和 ASP.NET MVC 之间做出选择。

但在我们进入选择之前，先快速强调一下 ASP.NET MVC 的关键方面。**模型-视图-控制器（Model-View-Controller，MVC）** 是一种架构模式，已经存在很多年了。这个模式本身相当容易理解。**模型**代表了应用程序领域中按需组织的数据。很多时候它还会支持捕获数据的更新并将其存储回适当的存储介质。**视图**是将这些数据在用户界面上的可视化表现。**控制器**负责处理对资源/数据的请求，找到合适的模型，然后以合适的格式将其传递给视图，最终呈现给用户。你可以在这里阅读更多关于 MVC 模式的内容：**http://en.wikipedia.org/wiki/Model-view-controller**。

微软修改了传入请求的处理方式以及传递给 ASP.NET 引擎的方式。请求不再采用 .aspx 页面的形式，而是更具 RESTful 风格并且面向操作。一个处理器会拦截这些请求，并将它们传递给控制器中正确的操作/方法。

ASP.NET MVC 强制将 SoC（关注点分离）原则贯彻到底。由于控制器是纯逻辑，很容易在测试框架中实例化它并测试功能，而无需加载整个 ASP.NET 运行时引擎。虽然你仍然无法测试最终数据的渲染效果，但你完全可以测试需要渲染的数据。再加上一些手动 UI 验证，就可以帮助完成整个应用程序的测试。与 ASP.NET MVP 不同，这种模式不依赖完整的运行时引擎；ASP.NET MVC 在设计时就考虑到了可测试性。它为 HttpContext、HttpRequest 和 HttpResponse 等内在对象提供了抽象类，从而让测试更加容易。

ASP.NET MVC 中的视图是使用标准 HTML（通过 HTML 辅助方法完成）构建的。这里没有 ASP.NET 服务器控件可用，因此开发者最终需要自己编写大部分 HTML，但反过来这也让他们对 HTML 有了完全的控制权，从而能更好地处理可访问性需求。虽然此时 Visual Studio 对 ASP.NET MVC 的 HTML 控件支持有限，但你也不必完全自己动手，因为你可以选择使用不同的视图引擎。目前已有第三方控件可以与 ASP.NET 一起使用。你可以从 NVelocity、Brail、NHaml、Spark 等视图引擎中挑选来构建你的视图。

> 关于 ASP.NET MVC 的更多细节，可以参考 MSDN 库：http://msdn.microsoft.com/en-us/library/dd381412.aspx。

现在，我们来回答最后一个问题：如何在 MVP（本质上使用 ASP.NET Web Forms 方法）和 MVC 之间进行选择。

### 在 MVP 和 MVC 之间选择

MVP 和 MVC 模式都能够生成企业级应用程序。虽然 MVC 无疑是更好的模式，但同样真实的是，就目前而言，使用 MVP 方法所获得的生产力优势要远远胜出。MVC 模式对当前的 Web 开发者，甚至刚入门的新手来说，都意味着一条相当陡峭的学习曲线。

考虑到社交网站对丰富用户界面的期望，使用 MVC 还意味着，几乎每一个显示需求都需要额外做大量工作来创建自定义控件。MVP 则允许我们使用大量 ASP.NET 服务器控件。

在开始构建一个新应用程序时，你可以更有说服力地支持 MVC。然而，就我们的情况而言，由于这是本书的更新版，且相关源代码是在上一版基础上构建的，使用 MVC 将意味着一个非常长的周期。

目前还没有迁移向导可以帮助轻松地将某些基于 MVP 的代码转换为 MVC。如果我们选择了 MVC，那将意味着对表示层的重写，并且会影响本书的发布时间表。




## 摘要

我们已经讨论了在 ASP.NET Web Forms 应用程序开发中可用的各种 Web 呈现模式。我们还了解了 ASP.NET MVC 所提供的功能，并将我们在本书上一版中使用的 MVP 模式与 MVC 进行了比较。经过多次讨论，我们最终得出结论：在表示层保留 MVP 模式是最好的选择。将来如果时间允许，我们一定会为我们的 Fisharoo 网站探索基于 MVC 的前端。
