
## CloudFormation Stack Roles

When deploying a CloudFormation stack, the service uses the identity of the IAM principal logged into the AWS account to perform necessary stack operations such as creating, updating, or deleting. The IAM principal must, therefore, have the required permissions either through a policy attached to it (or a group that the user is a member of) or by assuming a role.

Often, in large organizations, you may need to assign the capability of creating and updating stacks to team members who should not otherwise have full access to create and manage the individual resources that make up the stack. For example, you may have a helpdesk team that can be granted the ability to provision CloudFormation stacks, but they must not be able to individually deploy the resources of the stack outside of CloudFormation. In this scenario, you can configure service roles for CloudFormation. Using service roles, you can ensure that you follow the principle of least privilege. The procedure is as follows:

- An admin creates an IAM role that grants the necessary permissions to create the resources required by the CloudFormation stacks. The admin must create a trust policy where the trusted entity is the CloudFormation service, as shown in the following policy code:

  ```
  {
    "Version": "2012-10-17",
    "Statement": {
      "Effect": "Allow",
      "Principal": {"Service": "cloudformation.amazonaws.com"},
      "Action": "sts:AssumeRole"
    }
  }
  ```

- The helpdesk staff must then be granted the permissions to use CloudFormation to create, update, or delete stacks and to ensure that CloudFormation has the permissions to provision the resources. The helpdesk team should be assigned the permissions to pass the IAM role to CloudFormation using the iam:PassRole action, as per the following code snippet:

  ```
  {
    "Sid": "AllowPassingAppRoles",
    "Effect": "Allow",
    "Action": "iam:PassRole",
    "Resource": "arn:aws:iam::<account ID>:role/cfnroles/*"
  }
  ```

Using CloudFormation stack roles, you can add a layer of security to ensure that only authorized personnel can work directly with resources. Other users who may need to deploy infrastructure components can only do so via AWS CloudFormation.

## AWS CDK Overview

The AWS Cloud Development Kit (CDK) is a software development framework for defining cloud infrastructure in code and provisioning it through AWS CloudFormation. With the CDK, developers can define their infrastructure using familiar programming languages, including TypeScript, Python, Java, and C#. The CDK uses familiar programming constructs, such as classes and objects, to define cloud resources, making it easier for developers to use and understand.

The CDK provides a high-level, object-oriented interface to AWS services, allowing developers to define their infrastructure in a more abstract and less verbose way than is possible with traditional CloudFormation templates. For example, instead of specifying the properties of an EC2 instance in a JSON or YAML file, developers can define the instance using a class and object in their preferred programming language.

The CDK also provides a set of constructs, which are pre-written, reusable building blocks for defining infrastructure. Constructs include everything from basic components such as EC2 instances and RDS databases to more complex components such as Auto Scaling groups and load balancers. The use of constructs makes it easier and faster to define infrastructure and reduces the amount of code that needs to be written.

Another benefit of the CDK is its integration with the AWS CLI and other AWS tools, including AWS CloudFormation, AWS CloudWatch, and AWS CodeDeploy. This integration allows developers to use their preferred tools and workflows to manage their infrastructure and helps ensure consistency and stability across their development and production environments.

The main components of the AWS CDK are as follows:

- **Constructs**: Constructs are components of your application that represent one or more resources created by CloudFormation. For example, constructs could represent your EC2 instance or RDS database instance. You define constructs as classes that you import into your CDK application. You can access predefined constructs from the AWS Constructs library, create your constructs, or use third-party-built constructs.
- **Stacks**: Stacks are a collection of AWS resources created and managed as a single unit in the CDK. They can contain one or more constructs and are used to define and manage a specific set of resources in the cloud.

The key components of your CloudFormation stack are as follows:

- The VPC is configured using a CIDR range of 10.10.0.0/16. Recall that the CIDR range you used for the VPC in the Development account was 10.0.0.0/16. It is recommended that your VPCs do not have overlapping IP addresses to ensure you can establish a VPC peering connection between them if required.
- The CloudFormation template defines an internet gateway that is then attached to the VPC.
- The configuration comprises six subnets – two public subnets across two Availability Zones and four private subnets (two for your compute resources, such as EC2, ECS, and so on, and two for your database resources).
- A NAT gateway is declared in the template to enable secure access to the internet for compute resources in the private subnet. Note that in this lab project, you will only be deploying a single NAT gateway to minimize any costs as these are a chargeable service. AWS recommends you have one NAT gateway per AZ.
- Route tables are defined to ensure that traffic is routed to the correct endpoints in the VPC and associated with their relevant subnets. While not absolutely necessary, the template defines a route table per subnet.
- Security groups are then declared in the template to ensure that traffic to internal resources is restricted by port/protocol and source.
