Lambda functions can be invoked synchronously (wait for the result) or asynchronously (queue the invocation). Lambda queues the event before processing for asynchronous invocation; if it fails, it retries automatically. Event source mapping is a way to connect a Lambda function to an event source, such as Amazon SQS or Kinesis, with built-in retries and failure handling. ## Performance Monitoring and Fine-Tuning

Amazon provides tools such as Amazon CloudWatch and AWS X-Ray to monitor the performance of your Lambda functions. These tools help identify bottlenecks, understand invocation patterns, and optimize resource allocation for better performance.

## VPC Integration

Lambda can be configured to access resources within a Virtual Private Cloud (VPC). This integration requires setting up network configurations, such as subnets and security groups, and can introduce latency due to Elastic Network Interface (ENI) provisioning. Understanding VPC integration is vital for architectures needing to access private resources securely.

It is important to note that connectivity must be provided for your Lambda function to access services and resources outside of the VPC. One option is to ensure that your Lambda function can access services outside of the VPC through a Network Address Translation (NAT) gateway, which ultimately results in the request being sent via the internet. A more secure alternative is configuring necessary VPC endpoints to the appropriate service.

## Custom Runtime and Lambda Extensions

AWS Lambda supports custom runtimes, allowing you to use languages or specific language versions not natively supported by AWS. Extensions enable you to augment your Lambda functions with additional monitoring, security, and governance capabilities by integrating with external tools.

## Error Handling and Dead-Letter Queues (DLQs)

Proper error handling is crucial for the resilience of serverless applications. Lambda supports DLQs in managing events that fail to process multiple times. This allows the decoupling of error-handling logic from the core function logic, providing a robust mechanism for managing exceptions and operational issues.

## Managing Access to Backend Services with API Gateway

API Gateway is the critical intermediary between the client applications and the backend AWS services. The front-line interface handles incoming HTTP requests from web applications, mobile clients, or other external services. The responsibilities and capabilities of API Gateway in this context are multi-faceted and essential for the overall performance and security of the application. Managing access to backend services with API Gateway involves several layered components that provide a robust interface between a user’s requests and an application’s backend services.

### API Types and Endpoints

At its core, API Gateway offers RESTful and WebSocket API interfaces. RESTful APIs are designed for stateless operations and follow the request/response cycle. RESTful APIs are available either as REST APIs or HTTP APIs. The following are their key attributes:

- **REST APIs** are a collection of resources and methods. A resource represents a logical entry point for an app via a resource path. A method refers to the REST API request that a user makes of the API and receives a response to that request, such as the GET or PUT method. REST APIs enable integration with backend services on AWS, and features such as management capabilities using API keys and per-client rate limiting are also only available with REST APIs.
- **HTTP APIs** offer a similar functionality as REST APIs, albeit designed with fewer features and thus offered at a lower price point. HTTP APIs only support regional endpoints, whereas REST APIs can also support edge-optimized and private endpoints.

Another type of API is the **WebSocket API**. It also integrates with backend services such as Lambda functions, HTTP endpoints, and other AWS services. WebSocket APIs offer bidirectional communication, which means that while clients can send messages to a service, those services can also independently send messages to clients. This type of API is ideal for building real-time applications such as chat, gaming, or financial trading.

In addition to API types, there are three endpoint types for your APIs. These are as follows:

- **Edge-optimized API Endpoints:** These route requests to the nearest CloudFront edge location, enabling you to build solutions for a geographically dispersed user base.
- **Regional API Endpoints:** These are intended for clients in the same region as the API. You can incorporate your own CloudFront distribution with your regional APIs, which gives you flexibility in the caching strategies for the distribution.
