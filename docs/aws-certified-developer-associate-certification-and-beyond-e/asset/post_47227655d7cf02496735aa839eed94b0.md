
## Cloning an Existing Elastic Beanstalk Environment

Another useful feature of Elastic Beanstalk is the ability to clone environments. This is particularly useful when you want to deploy a test version of your application to use a different platform branch and evaluate how the application performs. Cloning enables you to quickly create a new environment using the same settings as the original one. This way, you avoid having to manually configure option settings, environmental variables, and other configurations.

When you perform an environment clone, note that Elastic Beanstalk will make a copy of any AWS resources such as load balancers, security groups, and RDS databases for the cloned environment. There are some limitations to cloning, as you can see in the following list:

- While you can clone the RDS environment, the RDS data isn’t copied from the original environment.
- While you can clone an environment to use a different platform version, you cannot change the platform branch because Elastic Beanstalk cannot guarantee compatibility.
- If your Elastic Beanstalk environment was previously configured with a classic load balancer, your new cloned environment will also be configured with a classic load balancer. If you need to change your load balancer type, you will need to create a new environment and deploy your application to the new environment. Later, you can use a URL swap to direct traffic to the new environment.

## Elastic Beanstalk and Docker

In addition to deploying standard applications across the aforementioned platforms, you can also deploy applications as Docker containers. This further enables you to deploy a wide range of applications, because you are not limited to only those supported platforms. Docker containers are self-contained environments that comprise the platform, programming language, runtime, libraries, and much more. A form of OS layer virtualization, Docker containers offer much more flexibility than standard virtual machines, allowing you to deploy these multiple containers on a single host machine. You’ll explore Docker in more detail in *Chapter 11, Deploying a Multi-Tier Application Stack with Amazon ECS, Fargate, and EKS.*

Suffice it to say that, for now, you can also use Elastic Beanstalk to deploy your Docker containers and are offered the following two options:

- **Single Docker:** This option refers to deploying single or multiple containers on EC2 instances. The Docker image can be built by supplying a Dockerfile or retrieving a Docker image. Furthermore, you can use Docker Compose to specify an image to use along with additional components and options that need to be provided in a `docker-compose.yml` file.
- **ECS:** This option uses Amazon ECS, a container orchestration and management solution offered by AWS. We will discuss Amazon ECS in detail in Chapter 11, *Deploying a Multi-Tier Application Stack with Amazon ECS, Fargate, and EKS*. With this option, Amazon ECS will perform container deployments and will manage the Docker environments. Elastic Beanstalk performs all Amazon ECS activities, such as creating clusters, task definitions, and task execution. For this option, you must use the `Dockerrun.aws.json` version 2 file. This file describes how to deploy your Docker containers as an Elastic Beanstalk application and provides support for multiple containers.

An important point about the ECS option is that your Docker images must be prebuilt and stored in a repository, which can be either public or private. Elastic Beanstalk does not provide support for using a Dockerfile for the ECS-managed Docker platform, so you cannot build custom images during deployment with a Dockerfile.

So far in this section, you have learned about some of the advanced features of Elastic Beanstalk. Using these features, you can ultimately provision end-to-end infrastructure environments capable of supporting the most complex of applications on AWS. Furthermore, we also discussed the importance of managing your backend databases with Elastic Beanstalk deployment, specifically around the concept of decoupling your Amazon RDS databases from your Elastic Beanstalk configuration to ensure database retention post-project or at the end of the application’s life cycle.

An important application security concept either using traditional multi-tier architecture designs or utilizing a PaaS solution such as Elastic Beanstalk is how that application connects to a backend database solution. While utilizing IAM roles is one method of granting applications temporary credentials to connect to the database, you may also need to use standard database usernames and passwords simply because that is how the application has been built.

In *Chapter 6, Managing Multiple Databases with AWS Relational and Non-Relational (NoSQL) Databases*, you discovered the AWS Secrets Manager service, which is designed to store configuration data and secret information such as credentials often required by applications that need to connect to backend databases securely. This credentials data can then be dynamically retrieved and stored as environmental variables that the application can reference. This approach is much better than hardcoding credential data in the application source code. In addition, AWS Secrets Manager enables you to automate the rotation of database credentials at scheduled intervals, enhancing your application stack’s security.

As part of the architecture, you will be provisioning the following services and resources:

- **VPC**: You will create a new VPC in the London region comprising six subnets – two public subnets, two application layer private subnets, and two database layer private subnets. The architecture is designed to offer high availability by spreading your subnets across two AZs. In addition, you will also deploy a NAT gateway to ensure that the instances deployed by the Elastic Beanstalk service can access the internet.
- **Security group configuration**: Amazon Elastic Beanstalk will provide a set of security groups to allow traffic from the internet to the Application Load Balancer, which in turn will distribute that inbound web traffic to the EC2 instances. However, per the recommended best practices highlighted in this chapter, you will configure the backend database outside the Elastic Beanstalk configuration. This means you must also configure a set of security groups to enable traffic from the EC2 instances to the backend databases – this is depicted as the **App-Security-Group** and **Data-Security-Group** in the architectural diagram. Furthermore, this external database can help facilitate blue/green deployments as it is not tied to a specific Elastic Beanstalk environment.
- **Database subnet group and RDS database**: As discussed earlier in this chapter, it is highly recommended that you deploy an RDS database external to the Elastic Beanstalk configuration to ensure that the database is retained when shutting down and terminating your Elastic Beanstalk environment. Thus, you will be configuring a database subnet group in the VPC and deploying a MySQL RDS database in the data subnets. For this lab, you will deploy just a single RDS instance. Consider configuring your RDS deployments with Multi-AZ and read replicas in real-world scenarios.
