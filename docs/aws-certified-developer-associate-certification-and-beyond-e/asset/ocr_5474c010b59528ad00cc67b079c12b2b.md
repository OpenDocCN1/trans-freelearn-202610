# # Dead-Letter Queues

Occasionally, a consumer might not be able to process a particular message. This can be due to several factors, such as malformed messages or issues related to the consumer not having sufficient time to process the message. As part of your application design, you may also retry processing a given message just in case the failure to process it was a one-off.

However, if your consumers continue to fail to process a given message, you must isolate that message for further analysis and debugging. This is achieved using a **dead-letter queue**. You can configure your SQS queue by setting a *redrive policy* to set the `maxReceiveCount` threshold value. This value defines the number of times a message can fail to be processed before it is sent to the dead-letter queue, as illustrated in *Figure 15.9*. To ensure resilience and prevent false positives, set `maxReceiveCount` to a higher value to allow sufficient retries before sending the message to the dead-letter queue.

By isolating unconsumed messages in a separate dead-letter queue, you can analyze log files for exceptions related to the message, identify issues related to message content, or determine whether the consumer needs more time to process the message, potentially increasing the visibility timeout period.
