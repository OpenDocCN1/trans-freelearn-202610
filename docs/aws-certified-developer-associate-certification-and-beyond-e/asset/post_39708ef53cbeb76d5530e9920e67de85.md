
## Instance Endpoints

- Each DB instance has its own endpoint address, so the writer DB instance has an endpoint and the two reader instances also have their own endpoint addresses. Use of the instance endpoint should only be permitted if you have client applications that require access to specific instances.

You can view the cluster details for Amazon Aurora databases using the `aws rds describe-db-cluster-endpoints` command when using the **command-line interface (CLI)**.

Multi-AZ configuration is primarily designed to provide high availability and failover options in the case of disasters, planned maintenance tasks, or Availability Zone outages. In addition, when configured as a Multi-AZ DB cluster, you get the additional benefit of using the reader instances to direct read traffic to, and thus reduce the load on, the writer instance. Note that this configuration is only available for PostgreSQL and MySQL currently.

However, if you are looking to design your database solution with multiple reader instances, then Amazon RDS offers another configuration known as Read Replicas which you will explore next.

## What about Read Replicas?

While Multi-AZ offers disaster recovery, another feature offered by AWS is **read replicas**, which are designed to help improve read performance and scalability. Out of the box, Amazon RDS only offers one master database instance that caters to both read and write capabilities. Often, this can create a bottleneck, especially when you may have additional applications that only require read access to the data such as those associated with business intelligence or analytics.

To cater to those read-only applications, you can create additional read replicas of your database, which reduces the overall load on your primary master instance. This enables you to serve read traffic to your application should the primary DB instance become unavailable.

Another benefit of using read replicas is that you can use them as part of disaster recovery. So, in the event of major failures on the primary instances, you can promote a read replica to become a new standalone instance.

This ensures that you have read copies of your databases in distant regions where there may be local requirements to access that data, resulting in lower latency. In addition, with read replicas, you can address the ultimate regional disaster by having read replicas in other regions should there be a major regional failure.

In terms of configuration, it is important to note that the read replica feature is only available if you configure automatic backups on the source DB instances and set a retention value to a number other than 0. You will learn more about automatic backups in the next section.

Depending on the database engine type you use, there are certain restrictions and specifications to be aware of. They include the following:

- You can create read replicas of existing read replicas for MariaDB, MySQL, and certain versions of PostgreSQL. You cannot do this for Oracle or Microsoft SQL.
- Circular replication is not supported. This means that you cannot have a replication from an existing read replica back to its source. Replication is only one way, so for example, if you have a source database called `MyDBInstance` that replicates to `ReadReplica1`, it is not recommended or typically possible to configure `ReadReplica1` to replicate data back to `MyDBInstance`.

While Multi-AZ and read replicas can help address concerns related to the source database failing, you must remember that they cannot necessarily protect against data corruption. If data gets corrupted on the source database instance, then due to the nature of replication, this corrupted data will be replicated to the Multi-AZ standby as well as any read replicas. In this scenario, you should revert to backups that were hopefully created before the corruption occurred. You can configure Amazon RDS for both automatic and manual backups and you will learn more about this next.

## Automatic and Manual Backups

Amazon RDS offers two backup options for your database instances. These are manual snapshots and automatic backups. As a managed service, you only need to enable automatic backups or start a manual snapshot and AWS will take care of the rest in terms of taking the snapshots and storing them. All backed-up data is stored in Amazon S3 within AWS-managed folders, so you do not have direct access to the S3 buckets that contain your data.

Let’s look at each backup option and how they work within the Amazon RDS platform.

## Manual Snapshots

You can take manual snapshots of your database instance at any point in time. When you take a backup, you are taking a snapshot of the entire database instance and so this will include all databases created on that instance.

You can take manual snapshots as frequently as you like, which means the more often you take a backup, the lower your **recovery point objective (RPO)**. An RPO refers to the amount of acceptable data loss measured in time. So, for example, if you take a backup once every 24 hours then your RPO is 1 day and you are willing to accept a worst-case scenario of losing a day’s worth of data.

Another factor to consider is that if you take a backup of a single DB instance, there will be a brief I/O suspension that could last between a few seconds and a few minutes depending on the size of the database. This is normal behavior and ideally, you should take your snapshot outside of normal business hours. If you wish to take more frequent backups during business hours, consider configuring your database with Multi-AZ. In this configuration, the backups are taken from the standby copy of the database and so any I/O suspension is not noticed by the end user of the database.

> **Note**
>
> This capability of avoiding brief I/O suspensions by using a Multi-AZ configuration where backups are taken from the standby instance is not available for Microsoft SQL Server. Customers will experience a brief I/O suspension during backups even with Multi-AZ configurations on this engine type.

Manual backups are chargeable based on the storage space consumed and continue to exist even if you delete the database. These will need to be manually deleted if you no longer require them. There is no default expiry set on manual snapshots.

You can copy your manual snapshots to other regions meaning that if required, you can perform restore operations in other regions. Snapshots can also be shared across other AWS accounts. This allows authorized accounts to copy the snapshots. Note that if the snapshot you share is encrypted, then the authorized AWS accounts need to first copy the snapshot and then perform a restore from the copy.

Another important concept to understand is that when you restore from your snapshots, Amazon creates a new database instance. You do not actually restore to an existing DB instance. To perform a restore, you need to provide the snapshot name and the new DB instance name you wish to create from that snapshot. You can then use the restored DB instance as soon as its status becomes available. Note that even if the status is Available, the data restoration may still be in progress in the background; a feature known as lazy loading.

With lazy loading, if you try to access data that hasn’t been restored fully yet, the DB instance will download the data from Amazon S3. Also note that by using the `Select *` statement, you can reduce the effects of lazy loading since you are performing full table scans.

Next, you will explore automatic backups.

## Automatic Backups

The second backup option is automatic backups. Automatic backups start with a full backup, which is a complete point-in-time backup of all the data held on disk. Subsequent backup operations are performed incrementally backing up only the data that has changed or added to the databases.

Here, again, it is important to ensure that your database is configured with Multi-AZ so that backup operations take place on the standby copy of the database and not the master. This allows customers to avoid experiencing the brief I/O suspension when the backup process initializes.

With automatic backups, you can configure a maximum retention period of up to 35 days after which the backups are deleted. When setting up automatic backups you can set the retention period anywhere between 0 and 35 days (where 0 means that you have disabled automatic backups). Furthermore, you can specify a particular time of day to perform the daily backup. When you delete the database, you can choose to retain your automatic backups. Note, though, that automatic backups are still deleted after the configured retention period. If you need to retain a copy of the database, choose to create a final snapshot when you delete the database. This final snapshot is like any other manual snapshot and is under your full control.
