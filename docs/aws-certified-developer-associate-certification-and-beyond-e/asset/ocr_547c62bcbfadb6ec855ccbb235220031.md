AWS CloudFormation offers a sophisticated rollback feature that gives you options to determine what to do when a stack fails to deploy, as illustrated in the following screenshot.

Figure 13.7: Stack failure options

As per Figure 13.21, you can have your stack roll back to the last known stable state, which would result in any newly created resources. Alternatively, you can preserve any successfully provisioned resources while rolling back failed resources to their previous states.

Sometimes, when performing an update, a stack may go into the UPDATE_ROLLBACK-FAILED state because CloudFormation was not able to roll back all the changes while performing an update that failed to complete. An example is when you are rolling back to an old database instance, but that instance was previously deleted manually outside of the CloudFormation management process. Since CloudFormation cannot roll back to a previous database instance, which it was expecting, this can result in a failed rollback attempt. In most cases, you would need to fix the error that caused the update rollback to fail before continuing your rollback operation.

Normally, when you delete a CloudFormation stack, the process deletes all resources created. Sometimes, you may need to preserve certain resources even after the end of a project, for example, backend databases. In such cases, you can configure a deletion policy, which is discussed in the next section.

# CloudFormation Deletion Policy Attribute

When deleting a CloudFormation stack, the default behavior is to delete all its resources. Since this behavior is the default, it is not necessary to define this deletion policy.
