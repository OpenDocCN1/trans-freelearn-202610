## Figure 13.1: CloudFormation stack

The example template in Figure 13.1 defines the configuration items associated with a typical VPC. Within the template, you would define the subnets, route tables, security groups, and components such as NAT gateways. The CloudFormation service will then use the information in the template to build a stack, a collection of resources managed as a single unit. Stacks defined by CloudFormation templates can be created, updated, and deleted using the AWS Management Console, the AWS CLI, or the CloudFormation API.

When you upload your template to CloudFormation, the service creates and stores the template in an AWS-managed S3 bucket. You can use your own S3 buckets if you wish. This AWS CloudFormation template can range from simple configuration definitions deploying a few resources to more complex architectures. In the next section, you will learn more about the anatomy of a CloudFormation template.

## Anatomy of a CloudFormation Template

The AWS CloudFormation template is made of several components. An example snippet is shown as follows:

```
Resources:
  VPC:
    Type: AWS::EC2::VPC
    Properties:
      CidrBlock: !Ref VpcCIDR
      EnableDnsSupport: true
```

```
EnableDnsHostnames: true
Tags:
- Key: Name
  Value: !Ref EnvironmentName
InternetGateway:
Type: AWS::EC2::InternetGateway
Properties:
Tags:
- Key: Name
  Value: !Ref EnvironmentName
InternetGatewayAttachment:
Type: AWS::EC2::VPCGatewayAttachment
Properties:
InternetGatewayId: !Ref InternetGateway
VpcId: !Ref VPC
```

The components of the CloudFormation template is as explained below:

### Format version

This section of your template is optional and identifies the template's capabilities. AWS CloudFormation expects you to use the current template version, 2010-09-09. This is specified in the template as per the following code snippet:

```
AWSTemplateFormatVersion: "2010-09-09"
```

### Description

This section is optional. It enables you to provide some information about your template, which can be helpful for anyone who needs to review and use it:

```
Description: This template deploys a VPC for Todo Plus Limited, with a pair of public and four private subnets spread across two Availability Zones. It deploys an internet gateway, with a default route on the public subnets. It deploys a pair of NAT gateways (one in each AZ), and default routes for them in the private subnets.
```

### Parameters

AWS CloudFormation allows you to define parameters in your templates. Although an optional section, parameters are extremely valuable as they will enable you to provide additional configuration information when deploying your CloudFormation stack, especially if you cannot offer these configuration details ahead of deployment.

Since one stack may vary in configuration from another, parameters enable you to reuse your templates across different stacks, giving you flexibility and the ability to extend the life cycle of your templates.

An example of a parameter is depicted in the following snippet:

```
Parameters:
  InstanceType:
    Description: Webserver EC2 instance type
    Type: String
    AllowedValues:
      - t2.nano
      - t2.micro
      - t2.small
    Default: t2.micro
    ConstraintDescription: must be a valid EC2 instance type
```

As depicted in the above code, when this template is deployed using CloudFormation, the user is prompted to either accept the *default* instance type (in this example, `t2.micro`) for launching an EC2 instance or select another instance type from an *array* of allowed values. In this example, the allowed values are `t2.nano`, `t2.micro`, and `t2.small`.

Each parameter will have a logical name (logical ID) that must be unique among all other logical names in the template. In this example, the parameter's logical name is `InstanceType`.

The chosen value is then stored in the parameter as a variable, which you can reference using the `Fn::Ref` intrinsics function from within the **Resources** and **Outputs** sections of the template. When creating a YAML-formatted template, you can use the **!Ref** function, as depicted in the following snippet:

```
Parameters:
  **InstanceType:**
    Description: Webserver EC2 instance type
    Type: String
    AllowedValues:
      - t2.nano
      - t2.micro
      - t2.small
    Default: t2.micro
    ConstraintDescription: must be a valid EC2 instance type
Resources:
  EC2Instance:
    Type: AWS::EC2::Instance
    Properties:
      InstanceType: **!Ref InstanceType**
```

As seen in the preceding code block, the details on the instance type are required when launching an EC2 instance, which is not hardcoded in the template. Instead, it is obtained by the value stored in the parameter, using the !Ref intrinsic function. This allows additional flexibility when deploying your CloudFormation stack. You can reference parameters and resources using the !Ref intrinsic function anywhere in your template.

When defining your parameters, you must specify the data type, as per line 4 of the previous code block. Data types can be of any of the following types:

- **String**: Alphanumeric characters – for example, MyVPCName.
- **Number**: This can be an integer or a float. Note that although CloudFormation will validate the parameter value as a number, when referenced in the template using the `!Ref` intrinsic function, the value will be passed as a string.
- **List\<Number\>**: This can be an array of integers or floats.
- **CommaDelimitedLists**: This is a list of strings separated by commas – for example, `test,dev,prod`.
- **AWS-specific parameter types**: AWS defines these and helps to catch invalid values that the user might enter. AWS will validate users’ inputs against existing values in the AWS account. For example, the `AWS::EC2::VPC::Id` parameter type must match an existing VPC ID in the AWS account.
- **SSM parameter**: This enables you to get a parameter value from the SSM parameter store. If the SSM parameter is shared from an external account, you must provide the full ARN of the parameter.

Several additional properties can be defined using the `Parameters` section. Some of these properties are as follows:

- **AllowedPattern**: This enables you to define regular expressions (regex) in text to ensure they conform to a specific pattern. This allows you to validate entries and avoid errors quickly.
- **AllowedValues**: This is an array of allowed values that can be used to define the parameter value.
- **MaxLength**: This is an integer value defining the largest number of characters for `string` types. `MinLength` is the opposite, defining the smallest number of characters.
- **MaxValue**: This is a numeric value defining the largest numeric value of the `number` types. `MinValue` is the opposite, defining the smallest numeric value allowed.
- **NoEcho**: This is used when you need to prevent the value from being displayed in the console, such as a password for a database.

In addition, you can also use several pseudo parameters that AWS CloudFormation defines. These parameters are predefined; you do not need to declare them in your template. These pseudo parameters include the following:

- **AWS::AccountId**: Returns the AWS account ID within which the CloudFormation stack is being created.
- **AWS::Region**: Returns the Region in which the resource is being created – for example, `us-east-1`.
- **AWS::StackId**: Returns the CloudFormation stack ID.
- **AWS::NoValue**: Used when you want to remove a corresponding resource property when using the `Fn::If` intrinsic function if the condition evaluates to false.

### Resources

The Resources section is the only **mandatory section** of any CloudFormation template. This makes sense since a CloudFormation template defines resources that must be deployed. Examples of resources that form a stack include VPCs, EC2 instances, and S3 buckets.

The format of the Resources section is depicted in the following snippet:

```
Resources:
  LogicalID:
    Type: Resource type
    Properties:
      Set of Properties
```

The resources section comprises several components, as follows:

- **Logical ID**: This is the logical name of the resources that you assign in the CloudFormation template. Logical names (IDs) must be unique throughout the template so that you can reference them where necessary. For example, for the Todo List application, the logical ID for an EC2 instance that will host the backend application might be **TodoAppEC2Instance**. Certain resources will also be assigned a physical ID. For example, the EC2 instance that CloudFormation deploys for the backend application will also have a physical ID, such as `i-29f8bg54`. This physical ID is defined once the EC2 instance has been created and allows you to reference the resource outside of CloudFormation templates.
- **Resource type**: This defines the type of resource that you want CloudFormation to create. For example, for the Todo List application, the resource type of **TodoAppEC2Instance** would be of type **AWS::EC2::Instance.**
