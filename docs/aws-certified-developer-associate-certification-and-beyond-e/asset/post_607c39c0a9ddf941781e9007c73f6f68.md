
- **Resource properties**: These are additional options that you specify for the resource. For the **TodoListAppInstance** resource, you must specify the **Amazon Machine Image (AMI) ID** as depicted in the following snippet:

```yaml
Resources:
  TodoListAppInstance:
    Type: "AWS::EC2::Instance"
    Properties:
      ImageId: "ami-0ff8a91507f77f867"
```

- Note that this has a logical name, followed by a resource type that specifies it as an EC2 instance. Additionally, one or more properties may be required to provision the resource. In this example, the AMI ID is a mandatory property required by CloudFormation to launch the instance.
- Property values can be literal strings, Booleans, parameters, pseudo references, and even values returned by functions.

## Mappings

Often, you may need to define the properties of your resources depending on how and where they are being deployed. This is where mappings come in handy. For example, when launching an EC2 instance, you must specify the AMI ID of the image you wish to deploy. AMIs are Region-specific, which means that you must select the correct AMI ID based on the Region where you are deploying your instance.

The **Mappings** section enables you to match a key to a corresponding set of name-value pairs. For example, suppose you wish to choose an AMI ID based on the Region where the instance is being deployed and specifically on the compute architecture used for the EC2 instance. In that case, you can create a mapping that defines a set of values (in this case, AMI IDs) using a Region name as the key containing the name-value pair combinations.

In the following snippet, note the list of AMI IDs based on Region keys identifying Region names:

```yaml
Mappings:
  RegionMap:
    us-east-1:
      HVM64: ami-0ff8a91507f77f867
      HVMG2: ami-0a584ac55a7631c0c
    us-west-1:
      HVM64: ami-0bdb828fd58c52235
      HVMG2: ami-066ee5fd4a9ef77f1
    eu-west-1:
      HVM64: ami-047bb4163c506cd98
      HVMG2: ami-0a7c483d527806435
    ap-northeast-1:
      HVM64: ami-06cd52961ce9f0d85
      HVMG2: ami-053cdd503598e4a9d
    ap-southeast-1:
      HVM64: ami-08569b978cc4dfa10
      HVMG2: ami-0be9df32ae9f92309
```

You can have several mappings, where each map will need its own logical name as in this example, where the mapping name is **RegionMap**.

You can have name-value pairs containing multiple string values within your mapping keys (us-east-1, us-west-1 . . . , etc). For example, in the preceding code snippet, you have keys mapped to two sets of name-value pairs: one named HVM64 and the other named HVMG2.

Once you have defined your mappings, you can call a value based on a specific key using the `Fn::FindInMap` intrinsic function. You can also reference **pseudo parameters** to identify details such as which Region you are in or the ID of the AWS account within which you are deploying a CloudFormation stack. This can dynamically identify information and customize your deployment based on the name-value pairs defined in your **Mappings** section.

In the following code snippet, note that the selection of the AMI is based on the Region in which the CloudFormation template is used to deploy a stack:

```yaml
AWSTemplateFormatVersion: "2010-09-09"
Mappings:
  RegionMap:
    us-east-1:
      HVM64: ami-0ff8a91507f77f867
      HVMG2: ami-0a584ac55a7631c0c
    us-west-1:
      HVM64: ami-0bdb828fd58c52235
      HVMG2: ami-066ee5fd4a9ef77f1
    eu-west-1:
      HVM64: ami-047bb4163c506cd98
      HVMG2: ami-0a7c483d527806435
Resources:
  myEC2Instance:
    Type: "AWS::EC2::Instance"
    Properties:
      ImageId: !FindInMap [RegionMap, !Ref "AWS::Region", HVM64]
      InstanceType: m1.small
```

You can use the `!FindInMap` (YAML-formatted) function to identify a mapping called `RegionMap` and pull a corresponding value for an AMI ID that refers to the Region in which the stack is being deployed. This is because you are using the `!Ref AWS::Region` intrinsic function to obtain the Region information and then selecting the AMI that corresponds to the HVM64 architecture in that Region.

## Conditions

Conditions allow you further flexibility in the deployment of stacks. You can define variations in your deployments based on whether a condition is validated as true or false. You might want a stack configured in a particular manner if your deployment is within a development versus a production environment.

For example, you can define an **EnvType** input parameter, which will have a default value but also allow you to input from a choice of dev, test, or prod. You can also use pseudo parameters to define your predefined conditions.

Next, you can define a Conditions section in your template that uses intrinsic condition functions to determine whether the associated resource is created. Finally, you can associate a condition with the resources or output that you want to create based on the condition being true. If the condition validates to false, then the resources or output will not be created.

When defining your conditions, you must use one of the following conditions’ intrinsic functions to validate it:

- `Fn::And`
- `Fn::Equals`
- `Fn::ForEach`
- `Fn::If`
- `Fn::Not`
- `Fn::Or`

> **Note**
> When using the YAML-formatted template, the syntax of the intrinsic functions is slightly different. For example, Fn::Equals in JSON is written as !Equals in YAML.

In the following code snippet, note that a condition has been set such that if an EC2 instance is deployed in a prod environment, it will be configured with an EBS volume:

```yaml
AWSTemplateFormatVersion: "2010-09-09"
Parameters:
  EnvType:
    Description: Environment type.
    Default: test
    Type: String
    AllowedValues: [prod, dev, test]
    ConstraintDescription: must specify prod, dev, or test.
Conditions:
  CreateProdResources: !Equals [!Ref EnvType, "prod"]
  CreateDevResources: !Equals [!Ref EnvType, "dev"]
Resources:
  EC2Instance:
    Type: "AWS::EC2::Instance"
    Properties:
      ImageId: !FindInMap [RegionMap, !Ref "AWS::Region", AMI]
      InstanceType: !If [CreateProdResources, c1.xlarge, !If [CreateDevResources, m1.large, m1.small]]
  MountPoint:
    Type: "AWS::EC2::VolumeAttachment"
    Condition: CreateProdResources
    Properties:
      InstanceId: !Ref EC2Instance
      VolumeId: !Ref NewVolume
      Device: /dev/sdh
  NewVolume:
    Type: "AWS::EC2::Volume"
    Condition: CreateProdResources
    Properties:
      Size: 100
      AvailabilityZone: !GetAtt EC2Instance.AvailabilityZone
```

In the preceding code snippet, note that an input parameter called EnvType has been defined. This parameter allows the user to indicate whether this stack will be deployed in a development, testing, or production environment.

Next, for the EC2 instance resources, the instance type that will be deployed is `c1.xlarge` if the `CreateProdResources` condition is set to true using the `!Equals` intrinsic function. Alternatively, if the `CreateDevResources` condition is true, then the only options available are the `m1.large` or the `m1.small` instance types.

The *MountPoint* and *NewVolume* resources are associated with the `CreateProdResources` conditional statement and are only created if the `EnvType` parameter is set to `prod`.

## Transforms

The `Transform` section is another optional section that specifies one or more macros that CloudFormation can use to process your template. Macros are executed in the order in which they are defined.

These macros can perform simple tasks or more extensive transformations of your templates. You can also reference code stored elsewhere, such as in an Amazon S3 bucket or a Lambda function.

You can use macros provided and hosted by AWS, such as the following:

- `AWS::Serverless`: This transform takes a template built using the **AWS Serverless Application Model (AWS SAM)** syntax and transforms it into a compatible CloudFormation template.
- `AWS::Include`: This transform works with template snippets that are stored separately from the main CloudFormation template.

## Outputs

The Outputs section is also another optional section. This section lets you declare output values upon creating and configuring resources that CloudFormation builds following your template. This is often useful when you need to identify the resources you have created.

In the following example code snippet, the output named LoadBalancerDNSName returns the DNS name for the resource with the logical ID:

```yaml
Outputs:
  LoadBalancerDNSName:
    Description: The DNS Name of the backup load balancer
    Value: !GetAtt LoadBalancer.DNSName
```

Notice that another intrinsic function, `Fn::GetAtt` (`!GetAtt` in YAML) is used. This intrinsic function returns the value of an attribute from a resource in the template. The function has two components, as follows:

`!GetAtt logicalNameOfResource.attributeName`

- `logicalNameOfResource`: This is the logical ID of the resource that contains the attribute you need to reference.
- `attributeName`: This is the resource-specific attribute whose value you want.

The resulting output values can also be used as input values for other stacks (if you export them first). This also allows you to create **cross-stack** references. Cross-stack references come with several benefits, enabling you to define **shared resources** easily referenced by other stacks. This allows you to build stack components following a service-oriented approach and create resources that are easily reusable.

When scripting your Outputs section, you will need to export the resource value, which can then be imported by other stacks, as per the following code snippet:

```yaml
Outputs:
  LogicalID:
    Description: Information about the Value
    Value: Value to return
    Export:
      Name: Name of resource to Export
```
