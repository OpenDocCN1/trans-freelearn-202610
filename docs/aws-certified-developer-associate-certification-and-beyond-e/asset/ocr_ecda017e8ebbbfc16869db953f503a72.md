As part of the architecture, you will be provisioning the following services and resources:

+   1. **VPC**: You will create a new VPC in the London region comprising six subnets – two public subnets, two application layer private subnets, and two database layer private subnets. The architecture is designed to offer high availability by spreading your subnets across two AZs. In addition, you will also deploy a NAT gateway to ensure that the instances deployed by the Elastic Beanstalk service can access the internet.
+   2. **Security group configuration**: Amazon Elastic Beanstalk will provide a set of security groups to allow traffic from the internet to the Application Load Balancer, which in turn will distribute that inbound web traffic to the EC2 instances. However, per the recommended best practices highlighted in this chapter, you will configure the backend database outside the Elastic Beanstalk configuration. This means you must also configure a set of security groups to enable traffic from the EC2 instances to the backend databases – this is depicted as the **App-Security-Group** and **Data-Security-Group** in the architectural diagram. Furthermore, this external database can help facilitate blue/green deployments as it is not tied to a specific Elastic Beanstalk environment.
+   3. **Database subnet group and RDS database**: As discussed earlier in this chapter, it is highly recommended that you deploy an RDS database external to the Elastic Beanstalk configuration to ensure that the database is retained when shutting down and terminating your Elastic Beanstalk environment. Thus, you will be configuring a database subnet group in the VPC and deploying a MySQL RDS database in the data subnets. For this lab, you will deploy just a single RDS instance. Consider configuring your RDS deployments with Multi-AZ and read replicas in real-world scenarios.
