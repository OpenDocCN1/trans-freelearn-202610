## Amazon Elastic Beanstalk Components

Amazon Elastic Beanstalk provisions all the resources required for your application. These are application environments within which your application will run. Several components define your Elastic Beanstalk application architecture, which are discussed next.

### Application

An Amazon Elastic Beanstalk application is a collection of components such as environments, versions, and configuration items that can be thought of as a container for your application stack.

### Application Version

This refers to a specific iteration of your application code. Amazon Elastic Beanstalk will store all versions of your application in a managed S3 bucket as deployable code, such as a Java WAR file. A version can be applied to any environment as and when required, and each application version is unique. Application versions can be used for different environments where the latest iteration, for example, may be tested in a development or test environment. Still, your production would host a previous stable version of your application.

### Environment

This is a collection of AWS resources (such as EC2 instances, load balancers, Auto Scaling groups, and Relational Database Service (RDS) databases) architected to host a specific application version. Each environment can run one application version at a time. For example, you may have three different application versions – a stable production version, a test version, and one being further developed with additional features or bug fixes.

In addition to this, you can have two different environmental tiers:

- Web server tier: This is designed to host frontend web applications serving HTTP/HTTPS requests over port 80/443.
- Worker tier: This is designed to pull tasks from Amazon Simple Queue Service (Amazon SQS) to process requests accepted by the web server tier.

### Environment Configuration

This collection of settings controls how the environment and its associated resources interact. Where necessary, the configuration can be updated, which results in Elastic Beanstalk applying changes to existing resources or, if necessary, deleting and deploying new resources.

### Save Configuration

You can store the configuration as a template that can be used as a starting point for creating unique environments. It is particularly useful when standard configurations are used for environments that reflect different stages, such as development, testing, and production.

### Platform

This combines **operating systems (OSs)** such as Linux or Windows, runtime, web server, application server, and other necessary components, libraries, and more. ## Understanding Various Deployment Strategies

When deploying applications on Elastic Beanstalk, you often need to update with new releases to accommodate feature enhancements or bug fixes. Regularly releasing new versions of your application is also recommended rather than trying to release major upgrades after considerable time gaps, which may result in more technical and user experience issues.

Amazon Elastic Beanstalk offers several strategic options to help customers roll out new versions of their applications. Each option offers varying degrees of effort, costs, and minimizing downtime. In the next section, you'll explore the various deployment options available in Amazon Elastic Beanstalk.

### All-at-Once Deployment

This is by far the quickest option for rolling out updates. The strategy involves pushing updates to all application nodes in one shot and performing necessary upgrade operations. However, this does result in some downtime until the newer version of the application is installed and configured. There are no additional costs for resources with this deployment approach.

This option is ideal if you regularly roll out updates and don’t mind the outage period, especially if it is short. You can plan such rollouts to occur outside of work hours or when you anticipate very little traffic, such as midnight on a Sunday. To ensure customers are not alarmed, you may wish to send out necessary communications for such planned outages.

### Rolling Deployment

In this deployment type, you roll out updates to a portion of the compute nodes at a time until all nodes have been updated with the latest version of the application. This results in only a subset of nodes being taken out of the fleet at a time, enabling you to avoid a complete outage of service to your end users.

Depending on the number of nodes that need to be updated and the acceptable percentage of nodes that can be taken out of service (while the update rolls out), this process takes some time before all nodes are configured with the latest version of the application.

![](img/34ff9b5b5a734dae3450ab701e223c73_401_0.png)

Figure 10.4: Rolling deployment strategy

The preceding diagram illustrates how a rolling update will be completed. Assuming you have four nodes to update, you could start with two nodes and perform the updates on those nodes (resulting in them being taken out of service) as per Step 2. Once those nodes have been updated, the remaining two can be updated as per Step 4. In Step 5, all four nodes have been updated with the latest application version.

An important point to note here is that, during the update life cycle, some users may connect to the nodes that serve the newer version, whereas others will continue to experience the older version until those relevant nodes are updated. If this sort of inconsistency does not pose any issues, rolling deployments are a viable option for performing application deployments. Finally, there are no additional costs incurred in this strategy.

### Rolling with Additional Batch

With this deployment strategy, you avoid reduced availability (while waiting for some nodes to go through the application update process). This is achieved by deploying additional nodes to cover the ones that go through the application upgrade process, which results in you maintaining the same bandwidth throughput for your end users.
