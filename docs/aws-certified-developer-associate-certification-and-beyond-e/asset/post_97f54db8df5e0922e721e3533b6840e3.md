
## CloudWatch Built-In Metrics

Built-in metrics are predefined metrics generated by AWS and sent to CloudWatch. For example, built-in metrics include monitoring CPU utilization and network traffic. Disk activity, such as disk read and write, is also included.

CloudWatch needs to ingest metric information from many AWS services, which means it needs to manage metric information efficiently. To achieve this, metrics are grouped into three different levels, as follows:

- **Namespace:** At the top level, you have the namespace, a container for CloudWatch metrics. Each AWS service has a namespace to enable CloudWatch to distinguish that service and its metrics collection, as per the following diagram:

  ![](img/34ff9b5b5a734dae3450ab701e223c73_664_0.png)

  For example, the metrics related to Amazon EC2 are grouped into a namespace defined as `AWS/EC2`, whereas the `AWS/RDS` namespace includes DB instance-level metrics. Names are unique within a namespace; for example, for `AWS/EC2`, `CPUUtilization` is distinct from `DiskReadOps`. You can use namespaces to define any other external services for your applications. Note that the `AWS/` namespace is reserved for AWS services only.

- **Dimensions:** Within your namespace, metrics are further organized based on dimensions. Dimensions help identify the individual resources of your service and the metric values for each resource. For example, if you have a collection of six EC2 instances, you want to identify the `CPUUtilization` metric for each instance. Dimensions are name-value pairs, allowing CloudWatch to separate metrics by resources or some other perspective to provide more contextual information. You can add up to 30 dimensions to a metric. When sending data points for the `CPUUtilization` metric for your `AWS/EC2` service, AWS also provides information such as the instance ID and the instance type as dimensions. Thus, you can now view the `CPUUtilization` metric for each EC2 instance launched in your account, as per the screenshot in Figure 16.3.

## CloudWatch Custom Metrics

AWS also enables you to define custom metrics. This is particularly useful when you want to send system-level metrics for your EC2 instances, such as memory and disk utilization, which are not available from the built-in metrics offered by CloudWatch. Another reason for using custom metrics is when you wish to capture data points for application-level metrics, such as the number of current viewers or transactions completed.

To capture system-level metrics such as **memory and disk usage** data points at the system level, you must install the **unified CloudWatch agent**. This agent can be installed on both EC2 instances and on-premises servers. The agent also lets you collect log files that can be ingested into CloudWatch. It’s important to note that besides installing your CloudWatch Agent on your EC2 instance or on-premises servers, you must ensure that the agent is configured with IAM permissions for CloudWatch.

In addition, if you wish to capture custom metrics at the application level, you can send them to CloudWatch using either the CLI or the SDKs for the application, for example, using the `PutMetricData` API call. Custom metrics come in two different resolutions, as follows:

- **Standard resolution:** Data is ingested with one-minute granularity
- **High resolution:** Data is ingested with a granularity of one second

High-resolution metrics offer prompt insights into sub-minute activities that can trigger alarms rapidly, based on 10-second or 30-second intervals. You will learn about the alarms in the next section.

## Overview of CloudWatch Alarms

As you capture metrics, you can use these to trigger alarms when a particular metric crosses a threshold value you define for a specified period. This idea that alarms are triggered when breaching a threshold value for a defined period is important. You do not want to trigger alarms simply because of an odd spike.

There are two types of alarms, as follows:

- **Metric alarm:** Associated with a single CloudWatch metric or the result of a math expression based on CloudWatch metrics.
- **Composite alarm:** Uses a rule expression and comprises multiple alarms. Using composite alarms helps to reduce overall noise. This is because you can configure a composite alarm to go into the **ALARM** state only if all of the underlying metric alarms are also in an **ALARM** state.

An alarm can be in any of the following three states:

- **OK:** This is when the metric is within the threshold values
- **ALARM:** This is when the metric is outside of threshold values
- **INSUFFICIENT_DATA:** This is when there is not enough data, usually when you just configured an alarm and need to wait for metric data points to be collected

Once an alarm has entered the **ALARM** state, you can automate various actions in response to that alarm. You can send an alert to an Amazon SNS topic, which can then send email alerts to a developer. You can also trigger an auto-scaling group, which may launch or terminate instances based on the triggered alarm, enabling you to scale out or scale in automatically.

Furthermore, you can also trigger a Lambda action, allowing you to call a Lambda function from either the same account as the resource and CloudWatch metric or from another account, as depicted in the screenshot in Figure 16.5. You must supply the Lambda ARN and ensure you have sufficient permissions.

In addition to the preceding, specifically for EC2 instances, CloudWatch alarms offer a set of EC2 actions you can perform, as follows:

- **Stop this instance:** When an alarm is triggered against a particular EC2 instance, you can instruct CloudWatch to stop the instance. The instance must be backed by an EBS volume, as instance store volumes terminate when you shut down the instance they are attached to.
- **Terminate this instance:** This allows you to terminate the instance provided that termination protection is not enabled on the instance.
- **Reboot this instance:** This is the same as an operating system reboot.
- **Recover this instance:** This attempts to recover the instance by launching it on another host machine. This action is triggered when AWS detects an underlying hardware failure following a `StatusCheckFailed_System` failure error.
- You also have *simplified automatic recovery*, a feature enabled by default for supported instances. AWS will attempt to remediate the instance to a healthy state if a system’s status check error is detected. Certain limitations exist, such as the fact that it does not support instances using instance store volumes or is a member of an auto-scaling group.
