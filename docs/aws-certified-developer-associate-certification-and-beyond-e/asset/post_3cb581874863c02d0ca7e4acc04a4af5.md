
Another important concept to appreciate is defining the permissions necessary to access the queue when you design a decoupled architecture. You can use both IAM policies and SQS queue access policies. This is discussed in the next section.

## SQS Queue Access Policies

As part of your design architecture, you will have resources that need access to the queue either as producers or consumers. To ensure permissions are correctly defined, you can use IAM policies or SQS queue access policies (a resource-based policy).

A typical use case where you might wish to access an SQS queue is in another account. This is known as cross-account access. The scenario is depicted in Figure 15.6.

![](img/34ff9b5b5a734dae3450ab701e223c73_631_0.png)

Figure 15.6 – Cross-account access for SQS queues

In this scenario, a Lambda function must poll an SQS queue in another AWS account. This requires an SQS access policy that enables the Lambda function in account 111222333444 to poll for and receive messages from the SQS queue in account 888999777666. The following code shows a snippet of a typical policy:

```
{
  "Version":"2012-10-17",
  "Statement":[{
    "Effect":"Allow",
    "Principal":{"AWS": ["111222333444"]},
    "Action":["sqs:ReceiveMessage"],
    "Resource":"arn:aws:sqs:us-east-1:888999777666"
  }]
}
```

*Principal* represents the trusted account in the preceding code snippet, and *Resource* defines the SQS queue.

In another example, if you configure Amazon S3 event notifications for an S3 bucket such that events trigger a notification that needs to be sent to an SQS queue, you will need to create an access policy that allows Amazon SQS to allow the S3 bucket to send the notification to the queue. The following snippet of code and *Figure 15.7* illustrate the architecture:

```
{
    "Version": "2012-10-17",
    "Id": "example-ID",
    "Statement": [
        {
            "Sid": "example-statement-ID",
            "Effect": "Allow",
            "Principal": {
                "Service": "s3.amazonaws.com"
            },
            "Action": [
                "SQS:SendMessage"
            ],
            "Resource": "arn:aws:sqs:Region:account-id:queue-name",
            "Condition": {
                "ArnLike": {
                    "aws:SourceArn":
                        "arn:aws:s3:::*:awsexamplebucket1"
                },
                "StringEquals": {
                    "aws:SourceAccount": "bucket-owner-account-id"
                }
            }
        }
    ]
}
```

Figure 15.7 – Amazon S3 event notification using an SQS queue

As part of the SQS access policy, Principal has been set to the Amazon S3 service, and a conditional statement is defined that ensures that only the specific S3 bucket can send notification messages to the queue.

## Message Visibility Timeout

Consumers of your SQS queue must poll the queue for new messages and then receive the message to process it. Along with the message, you receive a receipt handle related to the action of receiving the message. Once the processing is complete, the consumer must delete it from the queue by calling the DeleteMessage action and providing this receipt handle (instead of the message ID).

If you receive the message more than once and it is duplicated, each message will have a different receipt handle. When deleting the message after processing, you must provide the most recent receipt handle.

To ensure that the message is not processed by other consumers, Amazon SQS sets a visibility timeout period. The default timeout period is 30 seconds; other consumers cannot access that specific message. This allows the consumer who did receive the message to process it and then delete it from the queue.

## Dead-Letter Queues

Occasionally, a consumer might not be able to process a particular message. This can be due to several factors, such as malformed messages or issues related to the consumer not having sufficient time to process the message. As part of your application design, you may also retry processing a given message just in case the failure to process it was a one-off.

However, if your consumers continue to fail to process a given message, you must isolate that message for further analysis and debugging. This is achieved using a **dead-letter queue**. You can configure your SQS queue by setting a *redrive policy* to set the `maxReceiveCount` threshold value. This value defines the number of times a message can fail to be processed before it is sent to the dead-letter queue, as illustrated in *Figure 15.9*. To ensure resilience and prevent false positives, set `maxReceiveCount` to a higher value to allow sufficient retries before sending the message to the dead-letter queue.

![](img/34ff9b5b5a734dae3450ab701e223c73_635_0.png)

In the preceding example, if the message fails to get processed on the third attempt, it redrives it to the dead-letter queue. By isolating unconsumed messages in a separate dead-letter queue, you can analyze log files for exceptions related to the message, identify issues related to message content, or determine whether the consumer needs more time to process the message, potentially increasing the visibility timeout period.

Additional important points to note are as follows:

- A dead-letter queue of a FIFO queue must also be a FIFO queue
- A dead-letter queue of a standard queue must also be a standard queue

Furthermore, retention periods depend on which queue you are working with. With a standard queue, the expiration of a message is based on its enqueue timestamp, which remains unchanged even if the message is moved into the dead-letter queue. This means that the ApproximateAgeofOldestMessage metric indicates when the message moved into the dead-letter queue. Suppose a message arrives in a standard queue and resides there for 1 day before moving into the dead-letter queue because it could not be processed. If the retention period for the dead-letter queue is set to 3 days, then the message will be deleted after 2 days and ApproximateAgeofOldestMessage is 2 days. It is highly recommended that the retention period of the dead-letter queue be longer than the retention period of the original queue.

For FIFO queues, the enqueue time is reset if the message is sent to a dead-letter queue. This means that if you have a retention period for a FIFO dead-letter queue set to 3 days, ApproximateAgeOfOldestMessage is also set to 3 days.

## SQS Delay Queues

By default, messages are immediately visible when they enter the queue. However, if you need to delay the processing of a message, you can set a delay queue. Here, messages remain invisible to consumers for a maximum of 15 minutes (the default is set to 0 seconds). This can be useful if your consumers need more time to process incoming new messages. You can either set a delay at the queue level or override the default value when you send a message to the queue using the DelaySeconds parameter.
