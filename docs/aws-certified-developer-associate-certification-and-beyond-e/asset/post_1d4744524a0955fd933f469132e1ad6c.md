## Amazon CloudWatch Logs

With CloudWatch Logs, you can capture, store, and monitor logging data. You can capture logs from other AWS services, such as VPC Flow Logs, CloudTrail, Elastic Beanstalk, Lambda, IoT devices, and on-premises servers. You can also store Route 53 DNS log requests.

CloudWatch Logs also allows you to capture system and application logging data from your operating systems and applications and ingest it into CloudWatch. For this type of logging data, you must install the CloudWatch agent or use the AWS SDKs, API, or CLI.

You can define expiration policies for your log files and encrypt your logs. You can review log data in CloudWatch Logs and send it to Amazon S3, Kinesis Data Streams, and Firehose.

The diagram in *Figure 16.6* illustrates how CloudWatch logging works.

![](img/34ff9b5b5a734dae3450ab701e223c73_669_0.png)

Figure 16.6 – CloudWatch Logs architecture

The preceding diagram notes the various components of the CloudWatch Logs service. In this example, logging information is captured from three EC2 instances related to the Apache access logs data and ingested into a CloudWatch Logs group.

The core components of the CloudWatch Logs service comprise the following:

- **Log events:** Log events consist of a timestamp and a raw message. The event message must be UTF-8-encoded. Each entry in the log file is called a log event.
- **Log stream:** A sequence of log events that share the same source. So, in the case of our example in Figure 16.6, you will note three log streams, one for each EC2 instance where the Apache log access file data is being captured.
- **Log groups:** For a given resource, you will have one log group, within which you have one or more log streams. Within each log group, log streams will share the same retention period, monitoring, and any access permissions through IAM roles and policies.

An important benefit of using CloudWatch Logs is the ability to create **metric filters**. These allow you to identify patterns in your CloudWatch Logs events within log streams and then create a metric from that filter that you can start to monitor. For example, you can use metric filters to extract and monitor failed logins or errors, which you can then use to trigger alarms once a specified threshold value is crossed.

CloudWatch Logs comes with additional features, which will be discussed further in the next sections.

### Exporting and Streaming CloudWatch Logs Data

You can also export logging data from CloudWatch by sending it to Amazon S3. The logging data can then be kept for long-term retention or used by other applications and systems for analysis and processing. Here, logging data is exported using the `CreateExportTask` action. Please note that the log data can take up to 12 hours to become available for export.

In addition to exporting the log data into Amazon S3, you can configure CloudWatch log data for real-time and near-real-time processing to other destinations using subscriptions. These include Kinesis Data Streams, Firehose, or AWS Lambda, which can be used for custom processing or loading onto other AWS services. You can define subscription filters to filter out which log events are delivered to your destination resources.

## CloudWatch Events (Amazon EventBridge)

CloudWatch Events has now evolved into a full-fledged product offering and has been renamed **Amazon EventBridge**. This fully managed service makes it possible to build event-driven applications, allowing you to design your loosely coupled architecture further to be truly distributed and avoid single points of failure.

At a high level, EventBridge can monitor when events occur in your AWS account and then respond to them. EventBridge uses the concept of an event bus, which is essentially a stream of events that occur from any AWS service and resources in your account. This event bus monitors state change, and if a change occurs, it can trigger an event that calls a target. A target can be another supported AWS service, such as a Lambda function or a notification to an SNS topic.

For example, EventBridge can trigger a notification to an SNS topic when one of your users stops a particular EC2 instance, as illustrated in Figure 16.8. You may need to be notified of such events, such as for auditing purposes.

![](img/34ff9b5b5a734dae3450ab701e223c73_672_0.png)

Figure 16.8 – EventBridge with SNS topic as a target

Using the Cron Job tool, you can also configure EventBridge to schedule events to be triggered at a specific time. For example, you may wish to trigger an event that calls a Lambda function to automatically stop your testing servers at 6 PM at the end of a working day. You may also want to restart those instances again at 9 AM every day and repeat this operation automatically every weekday. In addition, you could also configure events to occur following a rate expression, for example, to trigger an action every 10 minutes.

Amazon CloudWatch can provide valuable insights into the operational health of your AWS account and its resources. It offers extensive capabilities for logging, monitoring, and remediation action as necessary.

## Introduction to AWS CloudTrail

AWS CloudTrail records events in your AWS account, providing a detailed record of user actions, roles, or AWS services. Each event captured by CloudTrail provides comprehensive information that can be used for security analysis, compliance auditing, and operational troubleshooting.

Every API call you make to your AWS account, whether via the Management Console, CLI, or using the SDKs, is recorded in AWS CloudTrail. This enables you to identify what action has taken place in your account, by whom, and when, facilitating an extensive audit trail. By default, management events are logged and retained for 90 days. However, you can create a CloudTrail trail to log events to an Amazon S3 bucket for an indefinite retention period. You can also send the events captured to CloudWatch Logs and Amazon EventBridge.

A CloudTrail trail can be created for a single region or as a multi-region trail. Multi-region trails capture events across all regions and are a recommended best practice. If AWS builds a new region, it is added to your multi-region trail, enabling you to capture all activities related to your resources across the global infrastructure. When creating a trail using the AWS Management Console, it creates a multi-region trail. If you need to create a single-region trail, you must use the AWS CLI.

Three types of events can be captured with CloudTrail, as follows:

- **Management events** provide information about operations performed against resources in your AWS account, such as launching a new EC2 instance, creating a new IAM role, attaching an IAM policy, or terminating an RDS database instance. By default, trails are configured to log all management events.
- **Data events** provide detailed information about resource operations performed on or in a resource. For example, when users try downloading an object, a GetObject action is performed on objects in an S3 bucket. You can also capture Lambda function execution activities, such as the Invoke API, whenever a Lambda function is executed.
- **Insights events** enable you to identify and respond to unusual activity caused by write API calls or API error rates for both read and write APIs. CloudTrail Insights establishes a baseline by analyzing normal API calls and API error rates and generates events when these call volumes or error rates go beyond normal patterns.

Managing the security of your CloudTrail events is critical, and using encryption and IAM permissions can ensure that only authorized users can encrypt and decrypt the CloudTrail log files. CloudTrail delivers log files to your bucket using server-side encryption with a KMS key (SSE-KMS) by default, unless you do not enable KMS encryption. In this case, CloudTrail will encrypt the log files using SSE-S3.

Note that to use an existing S3 bucket with an S3 bucket key, you need to grant CloudTrail permission in the key policy to perform the GenerateDataKey and DescribeKey AWS KMS actions. Without these permissions, you will be unable to create or update a trail.

The benefits of using KMS for encryption are that you manage the keys yourself and can use the same key to encrypt and decrypt log files across all accounts in all regions. To access the log files from an S3 bucket, the user must have read permissions on the bucket as well as have a policy or role applied that allows the decrypt permissions by the KMS key policy. This further enhances your security.
