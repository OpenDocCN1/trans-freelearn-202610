## Easy Invalidations

Content hosted at edge locations or regional edge cache has a defined **time to live (TTL)**. If the content is not accessed within the TTL, it is purged to prevent collecting stale content. CloudFront allows the easy invalidation of cached objects if content needs to be refreshed before the cache expires. For example, suppose you have updated content that needs to be made available immediately, or you discover that the content is incorrect. In that case, you must ensure that users get access to accurate information. As an alternative to using invalidations, which comes at a cost, you can use file versioning to serve different versions of the file.

## What is a Cache Key?

**Cache keys** are identifiers used by CloudFront to cache objects. When CloudFront receives a request, it looks for an object in its cache that matches the request’s cache key. If it finds one, it returns the object; otherwise, it forwards the request to the origin. Cache keys typically include the URL of the requested object and can also include query strings, headers, and cookies, depending on the cache policy.

## Cache Misses and Cache Hits

A cache hit occurs when CloudFront finds the requested object in its cache, meaning it doesn’t need to return to the origin server. On the other hand, a cache miss happens when the object is not found in the cache, prompting CloudFront to fetch it from the origin server. If the content is found, it’s served directly from the cache (cache hit). If not, CloudFront fetches it from the origin and stores it in the cache for future requests (cache miss). ## Forwarding Headers to Origin

This process is crucial for applications that require specific headers for every request:

- **Always forwarded:** If your application requires specific headers for every request, you can configure CloudFront always to forward them to the origin. However, this reduces the effectiveness of the cache because CloudFront must go to the origin more often.
- **Best practice:** Forward only the headers that are necessary for the origin to process the request.

You can ensure efficient content delivery with optimal performance and cost savings by correctly understanding and configuring cache policies.

## Cache Policy versus Origin Request Policy

These two policies play crucial roles in how CloudFront handles caching and requests. Understanding the distinction between them is key to effectively managing your content delivery:

- **Cache policy:** This defines how CloudFront caches content and includes settings for cache TTL, headers, cookies, and query strings. It’s essentially a set of rules that determine what can be cached by CloudFront and for how long.
- **Origin request policy:** This policy controls which request headers, cookies, and query strings are sent to the origin, regardless of the method request (GET, POST, etc.). Origin request policies ensure that the origin receives the necessary information to generate and return the requested content.

## Cache Behaviors

Cache behaviors in CloudFront control how requests are handled for different content or path patterns. You can define a cache behavior for a specific URL path pattern and customize how content is cached and served.

When a user requests content from your CloudFront distribution, CloudFront checks whether the requested path matches any of the specified path patterns in your cache behaviors. If it does, CloudFront applies the corresponding cache behavior’s rules to handle the request. If there is no match, CloudFront uses the default cache behavior.

Cache behaviors can be configured with various options:

- **Path patterns**: Define which requests the cache behavior applies to, such as `/images/*` for all files in an image's directory or `/videos/high-def.mp4` for a specific video file
- **Viewer requests**: Based on factors such as request headers, cookies, query strings, and HTTP methods, determine whether to forward, redirect, or block user requests
- **Caching methods**: Set rules for how long content stays in the cache (TTL settings) and whether to cache based on headers, cookies, or query strings
- **Content handling**: Decide how CloudFront should handle content when it's not cached (e.g., fetch from the origin, serve a custom error page)

The benefits of using a cache include increased performance through optimized load times based on content type, fine-grained control over what content gets cached, cost-effectiveness by reducing the origin fetches, and enhanced security.
