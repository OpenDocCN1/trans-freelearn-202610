
To ensure no reduced availability, in *Step 2*, an additional batch of two nodes is introduced, bringing the total number of nodes to six. In *Step 3*, the first two nodes are upgraded, taking them offline. However, the number of nodes serving end users remains at four.

In *Step 5*, the next set of two nodes are upgraded. While these two nodes are taken offline for the upgrade, the same number of available nodes exists in the fleet and this avoids reduced availability. Once the upgrade is complete, you will have six nodes (including the two additional ones added for the deployment strategy).

Finally, the additional batch of nodes is deleted once all existing nodes have been upgraded to the latest application version.

In this example, you will incur additional costs for deploying the additional batch to facilitate this deployment strategy. In addition, the upgrade process is longer than the previous batch. However, you benefit from the fact that end users do not experience performance issues or reduced availability of services.

## Immutable Deployment

As an alternative to rolling deployment, this strategy focuses on provisioning new resources in a separate autoscaling group to test the new application and, if necessary, roll back by simply deleting the autoscaling group. This will ensure that your existing fleet is not affected, and the existing instances are not reduced in availability.

With this deployment strategy, Amazon Elastic Beanstalk will create a second autoscaling group and provision a single instance to test the new configuration and application code. Once the launch has been successful, Amazon Elastic Beanstalk will provision additional instances to match the original autoscaling group. When all instances have passed the necessary health checks, Elastic Beanstalk will move the instances into the original autoscaling group and terminate the temporary autoscaling group and the old instances.

The following points should be noted about this deployment strategy:

- During the update process, the total capacity of your environment doubles for a short period. This is when the new autoscaling group serves requests before the original autoscaling group’s instances are terminated, resulting in additional costs. Note that this can also affect your quotas and limits so you will need to ensure you do not cross any such limits during the update process.
- An immutable update results in provisioning new instances for every new version that you deploy. You may need to ensure that you use the correct version of the **Amazon Machine Image (AMI)** used to launch your instances with any necessary modifications to your AMI image as a precursor to the rollout.

## Advanced Elastic Beanstalk Features

This section looks at various advanced features of Elastic Beanstalk that can help you architect your deployment more efficiently and better manage your environments and applications.

### Elastic Beanstalk Life Cycle Policy

In the previous section, you discovered how to upload newer versions of your application to Elastic Beanstalk and examined the various deployment options available. It is important to remember that each time you upload a new version of your application, Elastic Beanstalk creates a new **application version**. By default, Amazon supports 1,000 application versions per region per AWS account.

If you reach this limit, you cannot deploy any further application versions. To help you manage your versions, Elastic Beanstalk enables you to configure the **application version life cycle policy**. A life cycle policy will enable you to define when Elastic Beanstalk deletes your application versions – you can tell Elastic Beanstalk to delete older versions of your application or specify the total number of versions to maintain, beyond which older versions are deleted.

Some additional points to note are as follows:

- Older versions of your applications are deleted after newer versions are created. The creation of newer versions does not increase the count towards the maximum number defined by your policy. Application versions currently in use are not deleted
- The application version quota applies to a given region and all applications – so, if you have 10 applications and your maximum application version quota is 1,000, then that quota is split among all 10 applications

### Elastic Beanstalk Extensions

Amazon Elastic Beanstalk uses another AWS service, AWS CloudFormation, to provision the resources required by your application. AWS CloudFormation is an IaC tool that helps you define what resources to deploy and how to configure them using JSON or YAML scripted code. These scripts can then be used as templates to facilitate repeatable deployments and the creation of environments and resources programmatically. You will learn more about AWS CloudFormation in the upcoming chapters.

Because Elastic Beanstalk uses CloudFormation to provision required environments and resources, it is possible to customize your resources or add new resources to your deployments using Elastic Beanstalk configuration files, known as `.ebextensions`.

### Configuring Elastic Beanstalk to Use HTTPS

Modern web applications accessible over the internet should be architected using higher levels of security and prevent malicious attacks. One such common configuration option is to ensure traffic between your end users and the application is encrypted. This is known as encryption in transit and is facilitated by deploying a **Secure Sockets Layer** (SSL) certificate that is used to encrypt data as it is transmitted across the internet.

By default, when setting up Elastic Beanstalk, traffic occurs over standard HTTP, which is not encrypted. You can use HTTPS to ensure that traffic is encrypted, and the process involves assigning an SSL certificate to the environment's Elastic Load Balancer. This can be done in the console as well as via the `.ebextensions/securelistener-[alb|nlb].config` file.

An example configuration of such a file is as follows:

```yaml
option_settings:
  aws.elbv2.listener:443:
    ListenerEnabled: 'true'
    Protocol: HTTPS
    SSLCertificateArns: arn:aws:acm:us-east-1:xxxxxxxxxx:certificate/##########################
```

The process will also require you to update the relevant security groups to ensure that inbound connections on HTTPS (port 443) are also permitted.

Furthermore, you can also then use a custom domain name for your end users to connect to, as well as to set up and manage your certificates using the **AWS Certificate Manager** (ACM).
