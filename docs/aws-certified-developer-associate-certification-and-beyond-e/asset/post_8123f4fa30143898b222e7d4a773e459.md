- `CodeDeployDefault.HalfAtATime`: AWS CodeDeploy will deploy the application revision to half of the instances at a time. If you have an odd number of instances, then the deployment is rolled out to half of the instances, with fractions rounded down. So, for example, if you have nine instances, it will deploy to four instances first. The deployment is considered successful if the application revision has been deployed to at least half of the instances with fractions rounded up. This means that for the deployment to be successful when you have nine instances in the fleet, at least five instances must have a successful deployment.

- `CodeDeployDefault.OneAtATime`: AWS CodeDeploy will deploy the application revision to only one instance at a time. Here, the deployment is considered successful only if the application is successfully deployed to all instances. However, one exception is that if you are deploying your application to a group of instances, then the deployment is still considered a success if all but the last instance has a successful deployment. The overall deployment fails if any of the instances (except for the last instance) has a failed deployment. In the case of a deployment group with nine instances, if the first eight have a successful deployment but the last instance has a failed deployment, this overall deployment is still considered a success.

Note that CodeDeploy uses `CodeDeployDefault.OneAtATime` if you do not specify a deployment configuration option. The disadvantage with in-place deployments is that at least one of your fleet instances will be taken offline (as in the case of the `OneAtATime` configuration).

## Blue/Green Deployments

Blue/green deployments offer the advantage of maintaining your environment as is until it is ready and then transferring traffic to the new environment. You can use the blue/green deployment type to deploy your applications to EC2 instances as Lambda functions or ECS containers.

With the **EC2 compute platform** deployments, instances are provisioned in a replacement environment, and the application revision is installed. If required, you can set an optional wait time to enable time for testing and verification. The instances in the replacement environment are then registered with load balancers, which shift the traffic from the old environment to the new one. The deployment option follows the `CodeDeployDefault.OneAtATime` approach. Traffic is also routed to one replacement instance at a time. The deployment is considered successful if traffic is routed to all the replacement instances. It is regarded as a failed deployment as soon as the first rerouting fails. However, again, if the last instance fails in the deployment, it is still considered a success.

With the **ECS compute platform** deployments, AWS CodeDeploy creates a new task set and shifts traffic from the current task set to the updated replacement task set in the same ECS service. With **AWS Lambda**, AWS CodeDeploy will deploy a new version of the Lambda function and then shift traffic from the old version to the new version.

When using blue/green deployments for either AWS Lambda or Amazon ECS deployments, you must specify how the traffic is shifted from the old version of your application to the new version. The following deployment configurations are available for defining how traffic is shifted:

- **Canary:** With canary deployments, you shift traffic in two increments. You can select a predefined canary option that provides a specific percentage of traffic to be shifted in the first increment. Then, after a specified interval period, you shift the remaining traffic.
- **Linear:** With this option, traffic is shifted in equal increments, and between each increment, an equal amount of time in minutes is defined as the interval. This ensures a gradual traffic transfer from the old resource to the new version.
- **All-at-once:** All traffic is shifted from the Lambda function’s or ECS task’s old version to the new version in one transfer shift.

In addition to choosing your deployment options and defining the deployment configuration you require; you must also provide AWS CodeDeploy with details of how to manage the actual deployment process. This is done through a configuration file known as the **Application-Specific (appspec) file**.

## The Application-Specific File

The appspec file is a YAML or JSON file (EC2/on-premises instances only use the YAML formatted version) that provides configuration information on performing the deployment through a series of **lifecycle event hooks**. Each hook represents an event in the deployment process.

Depending on the compute platform you are deploying to, the appspec file structure changes. For EC2/on-premises deployments you have a high-level structure, as depicted in Figure 12.9:

```yaml
1  version: 0.0
2  os: operating-system-name
3  files:
4    source-destination-files-mappings
5  permissions:
6    permissions-specifications
7  hooks:
8    deployment-lifecycle-event-mappings
```

Figure 12.9 – The appspec file format for EC2/on-premises compute platforms

For EC2/on-premises compute platforms, you have a files section that specifies the names of files that should be copied and installed on the instance during installation. You also have a permissions section that details the specific permissions that should be applied to the files and folders that get copied.

For ECS and Lambda deployments, you have a slightly different structure, as follows:

- For Lambda, you have a resources section that defines the name of the Lambda function to deploy, the alias, the current version, and the target version of the Lambda function to shift traffic to, as depicted in Figure 12.10:

```yaml
1 resources:
2   - name-of-function-to-deploy:
3     type: "AWS::Lambda::Function"
4     properties:
5       name: name-of-lambda-function-to-deploy
6       alias: alias-of-lambda-function-to-deploy
7       currentversion: version-of-the-lambda-function-currently-points-to
8       targetversion: version-of-the-lambda-function-to-shift-traffic-to
```

Figure 12.10 – Lambda appspec file example

- For **ECS deployments**, the `resources` section contains details of the task definition, container, and port, as per Figure 12.11:

```yaml
1  Resources:
2    - TargetService:
3      Type: AWS::ECS::Service
4      Properties:
5        TaskDefinition: "task-definition-arn"
6        LoadBalancerInfo:
7          ContainerName: "ecs-container-name"
8          ContainerPort: "ecs-application-port"
```

Figure 12.11 – ECS appspec file example
