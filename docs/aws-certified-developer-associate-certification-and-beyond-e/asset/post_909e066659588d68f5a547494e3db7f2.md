
## Amazon RDS’ Features

Amazon RDS is AWS’s relational database solution. As it is fully managed, you need not worry about installing, patching, or updating the database application, as AWS takes care of this. The alternative would be to install some database software on an EC2 instance, which is still an option if you need an engine that perhaps is not part of the current Amazon RDS offering. However, as with any other software, if you choose to install a database on an EC2 instance, you must manage that instance and ensure it is patched, updated, and secure. Amazon RDS takes away all this administrative burden from the customer. In addition, Amazon RDS offers options for redundancy and high availability along with strategies and tools to perform automatic and manual backups of your data.

Although Amazon RDS is a fully managed service from AWS, it is not strictly classified as a serverless database solution, otherwise known as a **Database as a Service (DBaaS)**. You still need to define what instance type and size you wish to procure to host your database engine. If necessary, you can choose to vertically scale the instance by increasing its compute capacity or adding more storage. This administrative effort is still your responsibility, although you do not need to patch those servers or update the instance yourself. When setting up a new Amazon RDS database, you are provisioning a database engine on a managed service platform. You can then set up one or more database tables on your instance.

For storage, you can choose an EBS volume type (General Purpose SSDs such as gp2 or gp3, Provisioned IOPS such as io1, or Magnetic) and you need to define the size of your storage volume. In terms of which to choose, the Provisioned IOPS options are ideal for highly intensive workloads and applications that require low latency and consistent throughput, whereas General Purpose is best suited to development and testing environments. Amazon RDS offers the ability to automatically scale your storage, so as you approach the storage allocation limits, you can automatically increase the storage size to handle the addition of more data.

When you choose to provision an Amazon RDS database, you need to select an Amazon VPC to deploy it in, similarly to how you would deploy EC2 instances discussed in the previous chapter. Let’s take a brief look at how you can create the necessary VPC architecture to deploy your RDS instance.

## Deploying an Amazon RDS Instance

To deploy an Amazon RDS instance, you need to first create or choose an existing VPC. Amazon RDS requires you to define a subnet group within your VPC within which to deploy your database instance. Recall from Chapter 4, *Building Private Networks in the Cloud with Amazon VPC*, that subnets are isolated network portions of your VPC bound to specific Availability Zones within which you can deploy resources such as EC2 instances. To deploy an RDS database, you need to set up a database subnet group that must comprise a minimum of two subnets across two separate Availability Zones. This tells Amazon RDS which subnets the database instance can be deployed into. In the following diagram, you can see that we have configured a database subnet group.

When setting up a database instance on AWS, you can architect your solution to offer higher levels of redundancy by configuring a feature called **Multi-AZ**. You will explore this next.

## High Availability with Multi-AZ

Your data is going to be of critical importance to your business and you want to ensure you can access that data whenever you need it. Amazon RDS Multi-AZ deployments offer high availability and redundancy features for your relational databases. There are two key options available to implement Multi-AZ deployments as follows.

### *Multi-AZ Instance Deployment*

With Multi-AZ instance deployments, you have one master copy of the database that is deployed in one Availability Zone and a secondary standby copy of the database deployed in an alternative Availability Zone. The master copy of the database offers both read and write capabilities. Note that the standby copy is designed only for disaster recovery and failover purposes and does not offer any read capability while in the standby state.

Data is synchronously replicated from the master to the standby as it is written to disk and this ensures that in the event of a failure of the master copy, you have an exact replica available on the standby to failover to. For MariaDB, MySQL, Oracle, and PostgreSQL DB instances, AWS uses its standard failover methods. For Microsoft SQL Server, **Database Mirroring (DBM)** or Always On **Availability Groups (AGs)** are used.

As depicted in the following diagram, Amazon RDS provides you with an endpoint URL to connect to the master copy of the database. During a failover (for example, if there is a planned system maintenance, database failure, or Availability Zone outage) the master copy of the database is terminated and the standby copy of the database is promoted to become the new master. Amazon makes the necessary modifications to the DNS configuration so that the same URL endpoint now points to the newly promoted master.

Additional benefits of using Multi-AZ DB cluster deployment include the fact that you can have twice the number of transaction commits when compared to a single standby configuration. In addition, you can deploy your instances onto AWS Graviton2 for high computing performance.

In order to facilitate these various options, multi-AZ DB cluster deployments offer multiple endpoints as follows:

- **Cluster endpoint:** Also known as the writer endpoint, it connects to the primary DB instance for the DB cluster, which can be used for all write operations such as DDL and DML statements. If the writer DB instance fails, Amazon automatically performs a failover to one of the reader DB instances, based on which instance has the latest change record.
- **Reader endpoints:** Designed to provide access for read-only connections to the DB cluster as well as being available as standby instances against which failover can be performed.
