
For example, you can create a stack that builds a shared VPC and creates resources such as a public subnet and a security group. The subnet ID and the security group ID can then be exported as outputs of that stack. Next, you can build another stack for deploying EC2 instances in the same VPC that will be used to host your application. In the second stack, you would import the VPC ID, subnet ID, and the security group ID required to ensure that the EC2 instance is deployed in the correct subnet and attached to the relevant security group. When using cross-stack templates, you would use `Fn::ImportValue` to import the required values into the second stack being built.

In the next section, you will learn more about a security feature known as CloudFormation capabilities. This comes into play when creating specific resources using CloudFormation, where you must acknowledge that certain types of resources will be created as a security measure.

## CloudFormation Capabilities

Often, you may need to create specific resources, but even if you have permission to do so, you must still *acknowledge* to CloudFormation that you are creating such resources. This is more for security and assurance that you are aware of the types of resources being created by the template.

The following screenshot demonstrates AWS requesting such an acknowledgment.

![](img/34ff9b5b5a734dae3450ab701e223c73_568_0.png)

Figure 13.3: AWS CloudFormation capabilities

Here, you will note the resources require the `AWS::IAM::ManagedPolicy` capability and the user is being prompted to acknowledge this.

When deploying CloudFormation templates using the CLI, you can use the `--capabilities` option to acknowledge the fact that the stack will be creating resources that affect permissions in your AWS account such as the creation of **AWS Identity and Access Management (IAM)** users or roles.

There are three capabilities options that you can specify:

- `CAPABILITY_IAM`: Required if your stack will affect IAM resources, such as the creation of an IAM user.
- `CAPABILITY_NAMED_IAM`: Required if you provide custom names for the IAM resources being created.
- `CAPABILITY_AUTO_EXPAND`: Required if you use template macros such as the `AWS::Serverless` transform macro, which converts **Serverless Application Model (SAM)** templates into CloudFormation templates.

In the next section, you will learn about a CloudFormation feature called change sets. Often, you may need to update or change the resources in an existing stack. This feature enables you to visualize your changes before implementing them and can be used as part of your overall change management process.

## CloudFormation Change Sets

Often, you may need to update and change the infrastructure you previously deployed using a CloudFormation template. You can create **change sets** and request that CloudFormation updates the stack. You can provide a modified template or input parameter values to submit changes to your stack.

Before any updates are performed, CloudFormation will notify you of the changes proposed in your updated template. Some changes will terminate and replace existing resources, for example, if you change the Availability Zone of an EC2 instance. Other changes might only require modifying an existing resource. Some modifications can be carried out without interrupting the resource, whereas others may result in an interruption. Using change sets, you can see how the changes will affect your resources and confirm whether you still want to proceed with the changes or make further modifications to the template before rolling out the updates.

The CloudFormation template in the following code block enables you to deploy a single EC2 instance. Since we are not specifying any other parameter values, the EC2 instance will be deployed in the default VPC, in the default subnet, in the us-east-1a Availability Zone:

```
Resources:
  MyInstances:
    Type: AWS::EC2::Instance
    Properties:
      AvailabilityZone: us-east-1a
      ImageId: ami-07caf09b362be10b8
      InstanceType: t2.micro
```

Note that the resource being created is an EC2 instance. The Properties section details the Availability Zone in which the instance will be deployed, the AMI ID that will be used, and the instance type.

Deploying this template and creating a CloudFormation stack will result in the events shown in the following screenshot.

![](img/34ff9b5b5a734dae3450ab701e223c73_569_0.png)

Figure 13.4: CloudFormation stack creation events

Let us say that you now realize you should have deployed this instance in the us-east-1b Availability Zone. You can create a change set with a modified template. Depending on the changes you request, CloudFormation will either add new resources or modify existing resources, which may require deleting and replacing existing resources.

In the following CloudFormation template snippet, note the change of the Availability Zone from us-east-1a to us-east-1b:

```
Resources:
  MyInstances:
    Type: AWS::EC2::Instance
    Properties:
      AvailabilityZone: us-east-1b
      ImageId: ami-07caf09b362be10b8
      InstanceType: t2.micro
```

Uploading this modified template and requesting a change set will allow you to see how the changes will affect the resources, as illustrated in the following screenshot.

![](img/34ff9b5b5a734dae3450ab701e223c73_570_0.png)

Figure 13.5 – CloudFormation Changes tab detailing the resulting action of executing the change

Upon accepting and executing the change set, AWS CloudFormation will deploy a new instance in us-east-1b and terminate the existing EC2 instance in us-east-1a. The following screenshot illustrates the events that took place as a result of executing this change set:

![](img/34ff9b5b5a734dae3450ab701e223c73_571_0.png)

Figure 13.6 – CloudFormation events resulting from the execution of the change set

Note that the CloudFormation template creates a new instance as part of the update process and then deletes the existing instance in us-east-1a as part of the clean-up process.

## CloudFormation Rollbacks

Your CloudFormation deployment may fail due to errors in the template, missing or incorrect configuration details, or simply because of references to resources such as incorrect AMI IDs. In these situations, you need a mechanism to roll back your deployment so that you can return to a clean state.

AWS CloudFormation offers a sophisticated rollback feature that gives you options to determine what to do when a stack fails to deploy, as illustrated in the following screenshot.

Stack failure options

Behaviour on provisioning failure
Specify the roll-back behaviour for a stack failure. Learn more

- [x] Roll back all stack resources
  Roll back the stack to the last known stable state.
- [ ] Preserve successfully provisioned resources
  Preserves the state of successfully provisioned resources, while rolling back failed resources to the last known stable state. Resources without a last known stable state will be deleted upon the next stack operation.

Delete newly created resources during a rollback
Specify whether resources that were created during a failed operation should be deleted regardless of their deletion policy. Learn more

- [x] Use deletion policy
  Retains or deletes created resources according to their attached deletion policy.
- [ ] Delete all newly created resources
  Deletes created resources during a rollback regardless of their attached deletion policy.

Figure 13.7: Stack failure options

As per Figure 13.7, you can have your stack roll back to the last known stable state, which would result in the deletion of any newly created resources. Alternatively, you can preserve any successfully provisioned resources while rolling back failed resources to their previous states.

Sometimes, when performing an update, a stack may go into the UPDATE_ROLLBACK_FAILED state because CloudFormation was not able to roll back all the changes while performing an update that failed to complete. An example is when you are rolling back to an old database instance, but that instance was previously deleted manually outside of the CloudFormation management process. Since CloudFormation cannot roll back to a previous database instance, which it was expecting, this can result in a failed rollback attempt. In most cases, you would need to fix the error that caused the update rollback to fail before continuing your rollback operation.

Normally, when you delete a CloudFormation stack, the process deletes all resources created. Sometimes, you may need to preserve certain resources even after the end of a project, for example, backend databases. In such cases, you can configure a deletion policy, which is discussed in the next section.

## CloudFormation Deletion Policy Attribute

When deleting a CloudFormation stack, the default behavior is to delete all its resources. Since this behavior is the default, it is not necessary to define this deletion policy.
