## Monolith versus Microservices Design Overview

A monolithic architecture encapsulates an application’s components within a single program in an interconnected and interdependent way. In such a setup, each component and its associated components must be present for the application to be executed or compiled. This traditional unified model simplifies the initial development, testing, deployment, and scaling processes because everything is managed as one block. However, it does mean that any change affects the entire system, making updates risky and deployments cumbersome. As applications scale and complexity increase, this model can hinder rapid development and flexibility. Instead, it is highly recommended that the architecture be re-engineered to a microservices architecture. Figure 15.1 illustrates this concept, where the different components are working in isolation yet are integrated to deliver the final application stack:

![](img/34ff9b5b5a734dae3450ab701e223c73_624_0.png)

Figure 15.1 – Monolithic vs. microservices architectures

Microservices can communicate using various approaches, such as synchronous communication using REST-based methods such as HTTP/S and asynchronous communication through messaging queue systems such as RabbitMQ or Amazon SQS. Using a message queuing approach, you can publish messages to a queue, and other services can consume these messages, enabling you to decouple your application components but also ensure those components can handle requests when they have the capacity.

## Transition to Microservices Architecture

Microservices architecture breaks down an application into a collection of small, interconnected services, unlike a monolithic architecture, where everything is tightly coupled. Each service in a microservices architecture runs its unique process and needs to manage its own dependencies, such as SDKs and libraries, and communicates with other services through a well-defined interface using lightweight APIs. This design provides robust fault isolation: if one microservice fails, it doesn’t bring down the whole system. Moreover, microservices allow us to use different technology stacks on a per-service basis, promoting innovation and reducing the risk of technology or vendor lock-in.

## Comparing Monoliths and Microservices

In this section, you’ll compare monoliths and microservices, looking at their scalability, development complexity, and operational overhead. You’ll also learn about the factors that influence the choice between these two architectural styles and the benefits of transitioning from a monolithic to a microservices architecture:

-   - **Scalability**
-   - Monolithic applications can be scaled by replicating the server on multiple machines, but this might lead to resource underutilization
-   - Microservices can be individually scaled depending on the demand for features, making them a more efficient model as they grow
-   - **Development Complexity**
-   - Initially simple to develop, monolithic applications can become unwieldy and difficult to manage as they grow
-   - Microservices add complexity in managing multiple services but allow independent development and deployment, significantly speeding up the development process in large teams
-   - **Operational Overhead**
-   - The operational complexity is lower in monolithic architectures as there is only one system to manage
