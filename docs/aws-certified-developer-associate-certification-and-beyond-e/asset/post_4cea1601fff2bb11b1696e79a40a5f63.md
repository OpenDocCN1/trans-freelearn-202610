
An important aspect of automatic backups is that you can only run the backup once a day. However, the service also uploads transaction logs for the DB instance every 5 minutes to Amazon S3, comprising the changes that have happened on the database. This means that when you come to restore your database, you restore from the previous day/night’s backup and then replay those transaction logs. This allows you to restore your database to any point in time within the last 35 days (assuming you have a 35-day retention period defined) up to `LatestRestorableTime`, which typically is within the last 5 minutes. The latest restorable time can be determined by making the `DescribeDBInstances` API call.

Similar to manual snapshots, you can replicate your backups and transaction logs to another region. This is not enabled by default, and you need to explicitly configure it.

You need to remember that while read replicas can substantially reduce your RPO, they are not designed to handle data corruption. As such, you want to incorporate both automatic backups and manual snapshots in your overall Amazon RDS design architecture.

## Amazon RDS Security

Amazon RDS offers several security features around data security, authentication, authorization, and network access. In this section, you will examine some of the core security offerings. Starting with encryption services for your database.

### Amazon RDS Encryption

Data security is always of major concern for any customer and on Amazon RDS, you have several different encryption options available depending on the RDS engine you wish to consume. In general, there are two encryption types: encryption in transit and encryption at rest.

The first type of encryption is **encryption in transit**. This is where the connection between a client and the database is encrypted using **Secure Sockets Layer (SSL)** and **Transport Layer Security (TLS)**. Amazon RDS will be configured with an SSL/TLS encryption using the server certificate that is automatically installed on all DB instances that you provision. You can then enforce that all communication between the client and server be encrypted.

The second type of encryption is **encryption at rest**. With encryption at rest, all data stored on the underlying storage (EBS volumes), along with read replicas, automatic backups, and snapshots are encrypted using the AES-256 encryption algorithm on the server that hosts your DB instance.

Amazon RDS manages the access and decryption of your data transparently without you having to modify the client application. The database remains unaware of the encryption and decryption operations as this is handled by the host, as depicted in the following diagram:

![](img/34ff9b5b5a734dae3450ab701e223c73_219_0.png)

Depending on the engine, you have options for encryption at rest. So for example, with MySQL and PostgreSQL, you would use AWS Key Management Service (KMS) and EBS encryption, which is handled by the RDS host and the underlying EBS-based storage. With KMS, you either use AWS- or customer-managed Customer Master Keys (CMKs) to generate the necessary data keys. These data keys are used to perform the actual encryption and decryption of your data.

For engines like Oracle and Microsoft SQL Server, encryption at rest is configured using Transparent Data Encryption (TDE). The difference here is that the actual encryption and decryption are handled by the database itself rather than the host.

For Oracle, AWS also offers CloudHSM to create and manage encryption keys, giving the customer full control over those keys and isolation from other customers as depicted in Figure 6.10.

![](img/34ff9b5b5a734dae3450ab701e223c73_220_0.png)

Figure 6.10 – Amazon RDS encryption using CloudHSM

AWS CloudHSM comprises dedicated hardware security modules (HSMs) allocated to your AWS account. CloudHSM takes care of cryptographic operations and securely stores your cryptographic keys. It is FIPS 140-2 level-3 validated and is ideal where you may have strict rules that restrict you from using shared hardware security modules for compliance and regulatory reasons.

## Amazon RDS Authentication and Authorization

There are different authentication options available for Amazon RDS. These are as follows:

- **Password authentication:** Amazon RDS engines can be configured with database users and associated passwords. These credentials are managed within the database itself and ideally, you want to ensure you use complex passwords for the users you create. You must remember that with password authentication, the database engine generates these in plain text and thus it is advisable to use a tool to store and manage your passwords such as Amazon Secrets Manager.
- **IAM authentication:** You can configure your database to use IAM user authentication. This works across MySQL and PostgreSQL database engines and you do not need to create a password. Instead, you make use of an IAM authentication token. IAM users and roles (with the necessary policies attached) that map the IAM user/role to the local database user. Using the mapping, the identities can run `generate-db-auth-token`, which creates an authentication token valid for 15 minutes.
  - You can also create EC2 instance profiles with the necessary roles and permissions to allow applications on the instances access the database.
- **Kerberos authentication:** You can also use third-party identity and access management services such as Microsoft Active Directory to authenticate into your database using Kerberos authentication processes. Kerberos enables you to use tickets and symmetric-key cryptography with which you can authenticate without transmitting passwords over the network. This is considered a highly secure method for granting access to databases.
