
Step Functions offers two types of error-handling options: Retry, which retries a failed state, and Catch, which transitions the error into a failure path that you define.

You can define a Retry field for the Task, Parallel, and Map states. You must define an array of objects, known as retriers, where an individual retrier has several retries defined and an increasing interval period known as BackoffRate. When an error is encountered and the state has a Retry field, Step Functions will scan through the error names and make retry attempts in line with the field values.

In the following example in Figure 15.17, a Retry field has been configured for an error caused by a timeout. This is defined in the ErrorEquals field.

```
"Retry": [ {
  "ErrorEquals": [ "States.Timeout" ],
  "IntervalSeconds": 3,
  "MaxAttempts": 2,
  "BackoffRate": 1
} ]
```

Figure 15.17 – Step Functions error handling

In this JSON block, Retry makes a maximum of two retry attempts, as defined by the MaxAttempts field. Furthermore, the first retry takes place after a wait period of three seconds, as defined by the IntervalSeconds field. BackoffRate increases the time interval by one second between the first and second retries.

You can also define multiple retry states, such as having States.Timeout followed by States.All, which is a wildcard that matches any error name. Note that this state must appear alone and must appear as the last retrier in the Retry array, as depicted in Figure 15.18:

```
"Retry": [
  {
    "ErrorEquals": [ "States.Timeout" ],
    "IntervalSeconds": 3,
    "MaxAttempts": 2,
    "BackoffRate": 1
  },
  {
    "ErrorEquals": [ "States.All" ],
    "IntervalSeconds": 5,
    "MaxAttempts": 5,
    "BackoffRate": 2
  }
]
```

Figure 15.18 – Multiple retriers

If the maximum number of retries have been attempted and the error still persists, then Step Functions initiates a Catch error-handling option. This is also known as a fallback state and is applicable to the Task, Map, and Parallel states. For the Catch field, you must define an array of objects, known as catchers.

Catch has two key fields, ErrorEquals and Next, as depicted in Figure 15.19:

```
"HelloWorld": {
  "Type": "Task",
  "Resource": "arn:aws:lambda:REGION:ACCOUNT_ID:function:FUNCTION_NAME",
  "Catch": [
    {
      "ErrorEquals": ["States.Timeout"],
      "Next": "fallback"
    }
  ],
  "End": true
},
"fallback": {
  "Type": "Pass",
  "Result": "This is the fallback from the catch",
  "End": true
},
```

Figure 15.19 – Step Functions error handling – Catch

In this example, if the timeout error is encountered and either the retry option is not available or the maximum number of retries have been attempted, then the next step is to perform the activity indicated in the Next field, which is to go to the fallback state.

Additionally, when you use a state machine to catch an error, you can preserve the original input with the error, which can be passed into the state specified in the Next field. So, in Figure 15.20, ResultPath in Catch will include the error with the original input.

```
"HelloWorld": {
  "Type": "Task",
  "Resource": "arn:aws:lambda:REGION:ACCOUNT_ID:function:FUNCTION_NAME",
  "Catch": [
    {
      "ErrorEquals": ["States.Timeout"],
      "Next": "fallback",
      "ResultPath": "$.error"
    }
  ],
  "End": true
},
"fallback": {
  "Type": "Pass",
  "Result": "This is the fallback from the catch",
  "End": true
},
```

Figure 15.20 – ResultPath in the Catch statement

So, for example, if you have an input of `{ "lorem": "ipsum" }`, you will get a state output when catching the error, as follows:

```json
{
    "lorem": "ipsum",
    "error": {
        "Error": "Error here"
    }
}
```

ResultPath helps you to pass errors into the next state. This means you have access to the error in the next state and you can analyze it and perform any debugging as necessary.

Using Step Functions for error handling ensures that you do not need to overload your Lambda functions, which could result in performance and timeout issues. By subscribing to the features of Step Functions, you can apply complex error-handling logic seamlessly with your application architecture.

In the next section, we provide a brief overview of another feature that will allow you to handle responses from external APIs that are part of your workflow.

## Waiting for a Task Token

Sometimes, your application workflow might be dependent on interactions with and responses from other AWS services, external APIs, or even human approval processes.

For example, during the checkout process of an e-commerce application, you might have to wait for a payment gateway to get a confirmation that a credit card payment was accepted or declined before proceeding to the next step. To facilitate this requirement, you can append `.waitForTaskToken` to the Resource field, which tells Step Functions to wait for the task token to be returned.

An example snippet of the JSON for this follows:

```json
"States": {
    "Payment Gateway Process": {
        "Type": "Task",
        "Resource": "arn:aws:states:::lambda:invoke.waitForTaskToken",
        // more fields below
    }
}
```

`.waitForTaskToken` will pause the task and wait for a response that contains a task token and either a SendTaskSuccess or SendTaskFailure API call. This enables you to rely on external systems to perform any necessary processing before progressing with the workflow.

Ultimately, AWS Step Functions manages the application workflow centrally by breaking it into multiple steps, adding business and flow logic, and tracking inputs and outputs between steps. Step Functions enables you to visualize this workflow to gain better visibility into your applications.

## Ingesting and Consuming Streaming Data with Amazon Kinesis

Amazon Kinesis makes it easy to collect, process, and analyze real-time streaming data so developers can access timely insights and react quickly to new information. The service is divided into four primary components:

- **Kinesis Data Streams**: Enables the collection of large streams of data records, which can then be consumed by applications in real time.
- **Kinesis Data Firehose**: Enables the automatic loading of streaming data into AWS data stores such as Amazon S3, Amazon Redshift, Amazon OpenSearch, Splunk, Datadog, MongoDB, HTTP endpoints, and others. The data is delivered in near-real time.
- **Kinesis Data Analytics**: Facilitates streaming data processing with standard SQL, making it easy to query streaming data and gain insights.
- **Kinesis Video Streams**: Enables you to capture, process, and store video streams.

The next section discusses the key features of Kinesis Data Streams in more detail.

### Kinesis Data Streams

Kinesis Data Streams is a streaming service designed to capture, process, and store data streams in *real time*. The service facilitates the stream of data from *producers* to *consumers*. Producers can be applications, client machines, services utilizing the Kinesis agent, and more. Consumers of that data can be applications running in your AWS account, Lambda functions, Kinesis Data Firehose, and Kinesis Data Analytics (discussed later in this chapter).

Kinesis Data Streams can store data for 24 hours by default, which is also the minimum retention period. This can be increased to a maximum of 365 days using the `IncreaseStreamRetentionPeriod` operation.

### Scaling Kinesis Data Streams

Kinesis scales by deploying one or more shards. As more data is ingested, additional shards are added. To effectively use Kinesis Data Streams, you must design your data ingestion architecture to handle the volume, velocity, and variety of your data sources. Amazon Kinesis Data Streams uses shards as the base throughput unit. Each shard provides a capacity of 1 MB/sec and 1,000 records per second for writes and 2 MB/sec for reads, as depicted in Figure 15.21. In addition, data is stored as records, a unit comprising a sequence number, partition key, and the data blob. The maximum size of this data blob is 1 MB. Data is added to the stream using the `PutRecord` and `PutRecords` operations, the **Kinesis Producer Library (KPL)**, or the Kinesis Agent.

When reading data from the Kinesis stream, consumers can choose between a shared fanout type and an enhanced fanout type. In the shared fanout type, all consumers share a shard's 2 MB/sec read throughput, whereas with the enhanced fanout type, each consumer gets its own 2 MB/sec read throughput.

Calculating the appropriate number of shards based on your data volume is crucial. This involves understanding your application’s data generation rate per second and dividing this rate by the data throughput per shard. Proper shard management ensures efficient data processing without incurring unnecessary costs.
