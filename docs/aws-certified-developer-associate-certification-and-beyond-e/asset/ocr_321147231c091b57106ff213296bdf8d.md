Another important concept to appreciate is defining the permissions necessary to access the queue when you design a decoupled architecture. You can use both IAM policies and SQS queue access policies. This is discussed in the next section.

# SQS Queue Access Policies

As part of your design architecture, you will have resources that need access to the queue either as producers or consumers. To ensure permissions are correctly defined, you can use IAM policies or SQS queue access policies (a resource-based policy).

A typical use case where you might wish to access an SQS queue is in another account. This is known as cross-account access. The scenario is depicted in Figure 15.6.

![](bbox=[0.13, 0.33, 0.85, 0.54])

Figure 15.6 – Cross-account access for SQS queues

In this scenario, a Lambda function must poll an SQS queue in another AWS account. This requires an SQS access policy that enables the Lambda function in account 111222333444 to poll for and receive messages from the SQS queue in account 888999777666. The following code shows a snippet of a typical policy:

```
{
  "Version":"2012-10-17",
  "Statement":[{
    "Effect":"Allow",
    "Principal":{"AWS": ["111222333444"]},
    "Action":["sqs:ReceiveMessage"],
    "Resource":"arn:aws:sqs:us-east-1:888999777666"
  }]
}
```
