## Figure 11.7 – Application architecture using EC2 instances for backend services

In the upcoming project tasks, you will modify the architecture by replacing the EC2 instances that host the backend functionality with containers running on the Elastic Container Service (Fargate).

TodoPlus Limited stands to benefit from this change in architecture for the various reasons discussed in this chapter. These include the removal of the administration and management overhead associated with running your own EC2 instances. With Fargate, you don’t have access to the underlying compute infrastructure and, thus, are not responsible for patching and updating the operating system or the core server components running your containers. This shift in the shared responsibility model is something companies will always strive for since it results in substantial cost savings. In addition, by using serverless architectures and managed offerings from AWS, you will align better with the Well-Architected Framework, including the Sustainability Pillar, by doing your bit for the environment.

Furthermore, the applications will be lightweight, portable across different servers, and much more efficient.

While, technically, the shift from virtual machines to containers is a no-brainer, you must consider the implications of change in any live environment. In the following project exercises, you will first deploy and configure the ECS service and transfer traffic to it before terminating the previous Auto Scaling Group configuration, which deploys the EC2 version of your architecture as documented in earlier chapters.

While this chapter doesn’t discuss deployment strategies, you must consider such strategies in real-world scenarios, some of which were examined in *Chapter 10, Designing Deployment Strategies with AWS Elastic Beanstalk*.

In the preceding diagram, you will note the changes made, which have been numbered to help identify the components incorporated into the design. The following is a breakdown of the critical services and resources that make up the architectural changes:

- **Amazon Elastic Container Registry (ECR):** The Amazon ECR service replaces the S3 bucket previously used to host the application source files in ZIP format. Recall that, previously, when the Auto-Scaling group launched EC2 instances to provide backend operations, a user-data script would run that would copy this ZIP file from the bucket to the EC2 instance and perform various configuration tasks. In this change, you will create an ECR repository that will host a Docker image, which will be used to deploy your Fargate containers.
- **Dockerfile**: A Dockerfile contains instructions to build a Docker (container) image.
- **Task and Task Execution Roles**: As part of the build, you will need a task role and a task execution role. The task role enables the containers in the task to access other AWS services, such as Secrets Manager, to retrieve the database endpoint and host details that the application needs to connect to or Amazon S3 to upload or download content. The task execution role grants your ECS container or Fargate agent permissions to perform specific actions, such as accessing the ECR registry to pull the container image or send log data to Amazon CloudWatch.
- **Task Definition**: Your task definition will contain all the parameters necessary to deploy your containers, such as which container image to use, networking mode, CPU and memory allocation, ports to map, operating system, and any environmental variables.
- **ECS Cluster**: You must deploy an ECS cluster, where, among other parameters, you will define the VPC and subnets to use for the containers.
- **ECS Service**: ECS is where you will define the task definition you created, subnets within which to deploy your containers, security groups, the load balancer and target group that will distribute traffic to those containers, and any service auto-scaling parameters.
- **AWS Fargate**: Once you have deployed your ECS service, this will trigger the launch of your containers in AWS Fargate. Access to those containers will be provided through ENIs deployed in your designated subnets within your VPC.
