
The format of accessing the stage variable in API Gateway is ${stageVariables.variableName}.

Using stage variables enables you to manage multiple release stages for your APIs. Each stage variable points to a specific Lambda alias corresponding to a specific Lambda function in this example. You would want to ensure a fixed function is delivered for production use cases. In this example, when the developer calls the prod endpoint, API Gateway returns the V1 function, which might be the stable version of the application, for example, release for production use cases.

## API Gateway Caching

API Gateway offers a caching feature that helps reduce the number of calls you make to your endpoints, improving the overall latency of requests to your APIs. You can enable caching for a stage, and responses are cached for a specified time-to-live (TTL) period. The default TTL is 300 seconds, and the maximum is 3,600 seconds. The cache size can range between 0.5 GB and 237 GB.

Ideally, you should enable caching for your production workloads but not necessarily your development workloads since this increases costs.

You may also need to invalidate your cache from time to time. This is where you flush the entire cache immediately. Clients can invalidate and reload the cache from the integration endpoint for specific requests by passing a request that contains Cache-Control: max-age=0 in the header. To ensure this action is successful, you must also configure an IAM policy attached to the IAM execution role for the user. Here is a snippet of the IAM policy to use:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "execute-api:InvalidateCache"
      ],
      "Resource": [
        "arn:aws:execute-api:region:account-id:api-id/stage-name/GET/resource-path-specifier"
      ]
    }
  ]
}
```

This policy enables the API Gateway execution service to invalidate the cache for requests on the specific resource.
