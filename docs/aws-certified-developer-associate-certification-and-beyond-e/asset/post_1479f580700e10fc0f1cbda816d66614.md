
Partition keys play a vital role in data distribution across shards. When a data record is put into the stream, a partition key associated with that record determines which shard receives the record. The partition key should be chosen such that the data is evenly distributed across shards, avoiding “hot spots” where too many data records are directed to a single shard, potentially throttling the processing capability of your application.

In the next section, you will learn more about the capacity mode options for your data stream.

## Kinesis Data Stream Capacity Modes

With Kinesis Data Streams, you can choose between two capacity modes – **on-demand** and **provisioned.**

The **provisioned** capacity mode requires you to specify the number of shards for the data stream. You must increase the number of shards within the data stream if you need more capacity. Each shard gives you 1 MB/sec or 1,000 records per second for data in and 2 MB/sec for data out throughput.

You can scale out capacity by splitting shards using the `SplitShard` API, thereby creating additional shards, and if you need to scale down, you can merge two shards using the `MergeShard` API.

The **on-demand** capacity mode provides 4 MB/sec and 4,000 records per second for writes and can scale up to 200 MB/sec and 200,000 records per second. It doubles the capacity based on observed throughput over the last 30 days. So, for example, if your write stream capacity ranges between 20 MB/sec and 40 MB/sec, then Kinesis Data Streams will ensure that you can burst to double the capacity to 80 MB/sec.

Note, however, that you may encounter the `ProvisionedThroughputExceeded` error if your traffic increases more than double the previous peak within 15 minutes. You must then throttle your stream requests, which involves reducing the frequency or the size of the requests. You can also attempt retries with exponential backoff.

## Kinesis Client Library

The KCL enables you to consume and process data from a Kinesis data stream for your custom applications. The KCL client, which is a Java-based library, needs to be configured on your instances. It handles backend processing and tasks associated with distributed computing, such as load balancing, managing consumer instance failures, pulling data from the stream, checkpoint record processing, and balancing shards to worker associates, which are called leases if the worker instance count changes or if the data stream is reshared either via a shard split or shard merge.

Each shard in your Kinesis data stream must be read by one KCL instance alone. The instance will have the KCL library installed, which can be an EC2 instance or an on-premises instance. Thus, if you have eight shards, the maximum number of KCL instances would be eight. KCL instances can share reads from multiple shards; however, remember that the number of KCL instances is limited by the number of shards.

The KCL also uses a lease table created in DynamoDB to track the shards in a stream. As records are read from the stream, checkpoints are created in the DynamoDB table. Using the checkpoints in DynamoDB, you can track other workers and share the work among workers.

As per Figure 15.22, the KCL instances can determine which shards to read from based on the checkpoints in DynamoDB. Also, if an instance fails and is replaced, the new instance can pick up operations using this information.

## Consuming Data with Kinesis Data Firehose

Kinesis Data Streams is not designed to store data persistently, nor can it deliver data natively to other AWS services. You can use the Kinesis Data Firehose service if you need to load data for processing but also want to store it for the longer term. With Kinesis Data Firehose, you can reliably load massive volumes of streaming data into AWS data stores such as OpenSearch Service, Splunk, Datadog, NewRelic, Dynatrace, Sumo Logic, LogicMonitor, MongoDB, and HTTP endpoints as destinations in *near-real time*. In addition, you can load data into HTTP endpoints such as external websites and Splunk. *Figure 15.23* provides an overview of the architecture:

While Kinesis Data Streams delivers data in real time, Firehose uses a buffering system. Data is delivered only every 60 seconds or when the data size reaches 1 MB by default. However, you can configure the S3 buffer size between 1 MB and 128 MB and buffer interval values between 60 to 900 seconds for data delivery to Amazon S3. One key consideration when setting up Kinesis Data Firehose is how data transformation is handled. This often involves integrating AWS Lambda to transform data before it reaches the destination, enabling tasks such as converting formats or applying basic data analysis in transit.

## Real-Time Data Processing with Kinesis Data Analytics

Kinesis Data Analytics extends its functionality by enabling complex real-time analytics on streams using SQL, which can significantly simplify streaming data processing.

You write standard SQL queries to process the data on the fly before it’s sent to a destination that will consume it, enabling immediate action on incoming information. This is particularly useful in scenarios such as monitoring financial transactions for fraud detection and analyzing social media streams for sentiment analysis. An essential aspect of Kinesis Data Analytics is its ability to handle “hot streams,” which are large, continuous data flows.
