
The flow in Figure 9.4 ensures that only users or applications with a valid signed cookie can access the content in the private bucket, which can only be obtained from the RESTful service with the private key. It’s a typical pattern for securing content in cloud storage services, providing controlled access through cryptographic methods.

It is also essential to understand that a signer must create a signed URL or signed cookies. This can either be a trusted key group created in CloudFront or an AWS account containing a CloudFront key pair. AWS recommends using a trusted key group with signed URLs and signed cookies. There are several reasons for this recommendation.

With a trusted key group, there is no requirement to use the AWS account root user to manage the public keys. AWS recommends you do not utilize the root user for day-to-day operations. In addition, key groups allow more flexibility and management of keys, such as rotating keys without changing CloudFront distributions. You can also define IAM permissions to limit what different users can do; for example, allow users to upload public keys but not delete them. Also, as an added feature, a higher number of public keys can be associated with a distribution.

With a CloudFront key pair, they are tied to the AWS account root user and can be less flexible for management. You configure this in your root user security credentials environment as per Figure 9.5:

![](img/34ff9b5b5a734dae3450ab701e223c73_359_0.png)

Figure 9.5: Configuring CloudFront key pairs for the root user is not recommended

The important point is that you can only have two active CloudFront key pairs per AWS account.

Choosing between a trusted key group and a CloudFront key pair often depends on your operation’s scale and management preferences. Trusted key groups offer better control and management for larger, more dynamic environments.

When distributing content via a CloudFront distribution URL, bypassing this URL and connecting directly to the origin for certain origin types is possible. For example, if you create a static website on an Amazon S3 bucket and have full public access to the S3 bucket, then anyone with the website endpoint URL can connect to it if they know the URL address. If you want to prevent this sort of access, the next section looks at features called origin access identity (OAI) and origin access control (OAC), which help achieve this.

## CloudFront OAI and OAC

Amazon CloudFront offers two options to ensure viewers can only access your content via the CloudFront distribution point.

CloudFront OAI is a feature that enables you to enforce access to content hosted in your origin, for example, an Amazon S3 bucket, using only the OAI identity that you create as part of your CloudFront distribution. Once you configure this feature, you must update the bucket policy to allow access to content only from the OAI user. You do this by adding the following to your bucket policy:

```json
"Principal": {
    "AWS": "arn:aws:iam::cloudfront:user/CloudFront Origin Access Identity <origin access identity ID>"
}
```

This ensures that OAI grants access to the content hosted in the bucket on behalf of the user. This update to the bucket policy can be automatically created while completing the CloudFront distribution, or you can manually create the policy. If the user tries to access the content directly using the Amazon S3 endpoint, they will be denied access.

There are some drawbacks to this feature, however, including the following:

- OAI doesn’t support all AWS Regions.
- OAI does not natively support Amazon S3 server-side encryption with AWS KMS (SSE-KMS). It only supports server-side encryption with Amazon S3-managed keys (SSE-S3).
- There is no support for dynamic requests such as PUT, POST, or DELETE.

The new OAC addresses these drawbacks, which will be discussed next.

Using the OAC is AWS’s recommended approach to grant users access to content hosted at your origin, such as an Amazon S3 bucket. Before configuring the OAC in your CloudFront distribution, you must allow the CloudFront service principal (cloudfront.amazonaws.com) access to your Amazon S3 bucket. Specifically, you can define a bucket policy where access is granted only if the request comes via the CloudFront distribution using a Condition element. An example policy is shown as follows, which enables users to both read and write content to the bucket:

```json
{
    "Version": "2012-10-17",
    "Statement": {
        "Sid": "AllowCloudFrontServiceReadWritePermission",
        "Effect": "Allow",
        "Principal": {
            "Service": "cloudfront.amazonaws.com"
        },
        "Action": [
            "s3:GetObject",
            "s3:PutObject"
        ],
        "Resource": "arn:aws:s3:::<S3 bucket name>/*",
        "Condition": {
            "StringEquals": {
                "AWS:SourceArn": "arn:aws:cloudfront::<AWS account ID>:distribution/<CloudFront distribution ID>"
            }
        }
    }
}
```

While ensuring that users access your content via a CloudFront distribution enhances security, you also want to protect the network traffic between the end user and your content. The next section discusses transit encryption to protect your content’s connectivity when using Amazon CloudFront. This involves configuring HTTPS between end users and your CloudFront distribution and also enforcing HTTPS connectivity between CloudFront and your origin, be that a custom origin or an Amazon S3 origin.

## Configuring HTTPS between Users and Amazon CloudFront

To ensure that traffic between your end users and the content they access via CloudFront is encrypted in transit, you can use HTTPS. You can use HTTPS for both the communication between the end user and the CloudFront distribution point and between CloudFront and your origin.

Figure 9.6 depicts a high-level overview of how this communication takes place:

![](img/34ff9b5b5a734dae3450ab701e223c73_361_0.png)

Figure 9.6: Establishing HTTPS connectivity to your content via a CloudFront distribution

The following are the key steps in the flow of traffic as depicted in the proceeding diagram:

1. The end user attempts an HTTPS connection to CloudFront, which results in SSL/TLS negotiations.
2. Once established, the end user submits an encrypted request.
3. If there is a cache hit, meaning if the content requested exists in a cache, it is returned to the end user, who then decrypts the content.
4. If there is a cache miss, CloudFront connects to the origin and performs SSL/TLS negotiations.
5. CloudFront then forwards the encrypted request to the origin.
6. The origin decrypts the request and processes the message. It then encrypts a response and sends it to CloudFront.
7. CloudFront decrypts the response and re-encrypts it, making sure to store a copy in its cache and forward it to the end user.
8. The end user then decrypts the response.

When configuring HTTPS connectivity, you can configure HTTPS for both the connection between the end user and the CloudFront distribution and then from the CloudFront distribution to the origin. The following section provides an overview of these two configuration components.

## Configuring HTTPS Communication between End Users and the CloudFront Distribution

This involves configuring cache behaviors to require HTTPS for communication between the end user/viewer and the distribution. You can also configure this communication to allow both HTTP and HTTPS, enabling you to offer some content over HTTP but enforce other content only via HTTPS.

Here, you have two options to configure:

- **Using default domain names:** If you use the provided distribution domain name such as `x12121212ebcdef9.cloudfront.net`, you must configure the Viewer Protocol Policy to either the **Redirect HTTP to HTTPS** or **HTTPS Only** setting. HTTP GET and HEAD requests are redirected to HTTPS requests with the former option. POST, PUT, DELETE, OPTIONS, or PATCH requests are redirected to HTTPS only if you are using HTTP 1.1 or above.
- **Using custom domain names:** If you use custom domain names, you will need to use an SSL/TLS certificate, which you can configure using the **AWS Certification Manager (ACM)** or purchase a third-party certificate and import it into ACM.

In addition to configuring HTTPS between the end user and your CloudFront distribution, you can configure HTTPS between your CloudFront distribution and your origin. This can be a custom origin or an Amazon S3 origin.
