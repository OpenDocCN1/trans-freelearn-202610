Amazon SNS is a fully managed **publisher/subscriber (pub/sub)** notification service that enables you to build your microservices architecture with ease. It uses a messaging framework that enables applications to push notifications to multiple subscribers through a single channel known as a **topic**, which can have one or more subscribers. Subscribers to the topics then receive those notifications and then take appropriate actions with the messages. Supported subscriber endpoints include Amazon SQS, AWS Lambda, HTTP endpoints, Amazon Data Firehose, email subscribers, mobile push notifications, and text messages (SMS).

This helps you quickly build your application architecture without having to design your own pub/sub service. As per *Figure 15.11*, the ordering service sends notifications of the order to an SNS topic. The other services running across a range of AWS services subscribe to that topic and receive those notifications, which are then used to complete their individual tasks.

![](img/34ff9b5b5a734dae3450ab701e223c73_638_0.png)

Figure 15.11 – Amazon SNS pub/sub model

With Amazon SNS, you can configure two types of subscribers – **Application to Application (A2A)** or **Application to Person (A2P)**:

- **A2A** – This type of subscriber is another application or a component of your primary application. For example, the Lambda function that subscribes to the Order Service SNS topic in *Figure 15.11* uses the notification to process the shipping component of the application to ensure the order is correctly dispatched to the customer.
- **A2P** – This type of subscriber is usually a human subscriber such as an administrator who needs to be alerted or, in the example illustrated in *Figure 15.11*, the customer, who gets an email confirming that the order has been placed.

Ultimately, the Amazon SNS pub/sub model is incredibly effective for broadcasting notifications across various types of consumers, including email addresses, SQS queues, and AWS Lambda functions.

An important feature of the SNS service is the SNS and SQS fanout pattern, which will be discussed in the next section.

## Amazon SNS and SQS Fanout Pattern

With Amazon SNS, you can design a solution where a single topic can be used to distribute messages to multiple SQS queues, effectively implementing a one-to-many communication model for information distribution. This pattern is not only scalable but also enhances the reliability of message delivery. For example, in Figure 15.11, we discussed an architecture pattern where an ordering service would notify multiple Lambda functions to process orders in an e-commerce application. As the orders come through, a notification is sent to a topic that the shipping and inventory services (Lambda functions) have subscribed to.

With Amazon SNS, messages are not stored in the topic; as the messages come through, subscribers receive notification immediately and must act on the message. This is because Amazon SNS is a push-based messaging service. However, it’s important to note that with Amazon SNS, you can configure a delivery policy that includes the option to retry the delivery of messages when subscribed endpoints become unavailable for any reason. The default retries policy of AWS-managed endpoints, such as Amazon Data Firehose, Lambda, or SQS, is three times without delay. There are four phases of a delivery policy, as follows:

The Immediate Retry phase (no delay) refers to retries after the initial delivery attempt.

The Pre-Backoff phase refers to attempting a set of retries before applying a backoff function to add a delay between those retries.

The Backoff phase controls the delay between retries using the retry-backoff function by setting the minimum and maximum delay and a retry-backoff function to define the delay increase from the minimum to maximum delay.

The Post-Backoff phase specifics the number of retries and the delay between retries.

If the delivery policy is exhausted, Amazon SNS stops retrying attempts and discards the message unless you configure a dead-letter queue to deliver the message.

Assume several orders are coming through and multiple notifications are being sent to the topic, which results in those messages getting pushed onto the Lambda functions. In such a scenario, it might be necessary to incorporate an SQS queue to hold the messages in a queue so that the Lambda function can retrieve them and process them when capacity is available. This process of sending a message to an SNS topic, which then distributes it across multiple SQS queues, is known as a Fanout pattern.

In Figure 15.12, once the order has been placed, a notification is sent to an SNS topic, which fans out the message to multiple SQS queues for different application components to process. Each order generates a single notification, but the Fanout process means that different queues belonging to different components of the application can be notified.

As you can see in the diagram, the Lambda functions for the shipping, inventory, and payment services can poll the queue for their respective jobs when they are available. This ensures scalability and prevents any messages from being processed during high-volume throughput.

Another feature of Amazon SNS is the ability to configure topics that preserve the ordering of the notifications and ensure that the notifications are delivered once only. The next section discusses the SNS FIFO topic feature.

### Message Ordering and Deduplication with FIFO Topics

Amazon SNS FIFO topics are specifically designed to deliver messages to SQS queues in the order in which the messages were published to that topic. Furthermore, your application’s functionality may require that duplicate messages be avoided at all costs. In this scenario, you can configure an SNS FIFO topic with an SQS FIFO queue as the subscriber.

The subscribers of an SNS FIFO topic can be both an SQS FIFO queue and an SQS standard queue. Since, in a Fanout pattern, not all consumers may require strict ordering of messages, using a combination of SQS FIFO and standard queues means you can also be more cost-effective and have greater flexibility.

In Figure 15.13, customer orders must be fulfilled in a strict order of first come, first served. This means your inventory service must update stock inventory following the order of successful transactions received. The inventory service can thus benefit from an SQS FIFO queue being subscribed to an SNS FIFO topic. The shipping service perhaps does not require strict ordering of messages because it might also need to consider the customer’s location to determine the method of dispatch and time of delivery.

![](img/34ff9b5b5a734dae3450ab701e223c73_641_0.png)

Figure 15.13 – SNS FIFO topics

The SNS FIFO topic ensures the deduplication of notifications using a deduplication ID or content-based deduplication. Furthermore, when publishing a message to an SNS FIFO topic, you set a message group ID, which defines which group the message belongs to. This group ID is passed to the SQS FIFO queues, which ultimately ensures that the messages of a particular group follow a strict order.

In the preceding diagram, you can see that an **AWS Lambda inventory update function** on the left of the workflow is designed to update the product inventory system as products are sold and replenished.

Each product has its message group ID, and the same SNS FIFO topic is used to push those updates to the SQS queues. The sequence of inventory updates is preserved per message group ID. Because the workflow uses the SQS FIFO queue, this ordering of messages is still preserved when the messages finally reach the *AWS Lambda retail subscriber function* within the context of the message group ID.
