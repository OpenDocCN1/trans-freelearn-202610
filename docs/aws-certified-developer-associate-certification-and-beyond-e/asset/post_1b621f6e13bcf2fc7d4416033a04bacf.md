## Introduction to IAM

Every organization has its unique set of tools, systems, environments, projects, and core functions. Within an organization, there exist many groups of people, departments, and business units that share the same services. However, each group will require varying levels of access to those services depending on their function and role within the organization.

For example, developers will require access to development environments that allow them to experiment and design new application features, whereas their access to production environments must be restricted. Similarly, junior system administrators should only be allowed to execute certain tasks and not have full administrative rights on critical workloads.

In this section, you will learn about AWS IAM and see how it may be used to implement crucial elements of cloud security. AWS IAM is a fully managed service that can help you define who or what can access your AWS account, what services can be accessed, and what resources can be created and configured. With AWS IAM, you configure IAM users, groups, and roles with specific permissions that can be used by entities such as human users or applications to interact with your AWS account.

### But First, Let’s Talk about the Root User

When you create your AWS account, a root user is automatically provisioned. It is the primary owner of your AWS account and has the power to close the account down. With complete unrestricted access to your AWS account, it is crucial to ensure you protect this account and keep its credentials safe.

> **Best practice**
>
> As a best practice, it is advisable not to use the root user account for your day-to-day operations. AWS recommends you create separate individual IAM users (discussed shortly) with enough permissions required to carry out all tasks required to fulfill their job function.

### What Are the IAM Components?

AWS IAM allows you to create and configure identities for your AWS account. You can apply permissions to those identities, determining the level of access granted.

Next, you will be introduced to the various components that constitute AWS IAM.

### IAM Users

An IAM user may be either a human being who logs into the AWS interface or a program that needs to make a service request to your AWS environment programmatically. An IAM user account can be assigned to anyone in the company who needs to utilize the AWS services, such as programmers, system administrators, and data scientists. User authentication can either be interactive via the web console or programmatic using the **command-line interface (CLI)**. In addition, applications can make use of **software development kits (SDKs)** for AWS to gain programmatic access and execute **application programming interface (API)** calls to interact with services and resources.

> **Best practice**
>
> When granting access to services, you must follow the POLP as recommended by AWS. This ensures that those identities are provided with only the necessary access needed to carry out approved tasks and perform their job functions.

As depicted in the following diagram, the root user has unrestricted access. However, your IAM users do not have any permissions when you first create them. Although these IAM users can log in to the AWS account, they will not be able to access any services or create resources. IAM users require permissions that are defined by policies you can attach to those users (or the group that the user belongs to). These permissions define what actions those users can perform in your account.

### IAM Groups

IAM groups enable you to collate individual IAM users who share common job functions. This allows you to assign permissions to the group as a whole, and the users who are members of the group will inherit those permissions. Assigning permissions to groups is much easier from a management perspective as it avoids creating and attaching multiple policies to every user directly. This makes managing permission assignments and auditing much more straightforward.

### IAM Roles

This type of identity is independent of any specific user with a defined set of permissions. These permissions are described in one or more policies attached to the role. The role can be assumed by users or applications to gain temporary access to other services and resources within an AWS account. Users who usually don't have certain permissions may be granted the ability to assume specific roles that provide elevated access levels when required. An example of this is a **Break Glass** concept, where a junior member of the team may be able to assume a role that grants special permissions to perform restricted tasks under certain conditions.

Roles can also be assumed by identities who use third-party IdPs, enabling identity federation. Examples include OpenID providers such as Facebook and Google or corporate directory services such as Microsoft AD, which supports the SAML 2.0 protocol. You can also use roles to allow users from other AWS accounts to access services and resources in your AWS account through cross-account access and role switching.

IAM roles use temporary credentials created and managed by the STS. The roles are not configured with long-term credentials (usernames and passwords or access keys). Instead, when an entity assumes the role and requests to access a resource, it is provided with temporary credentials to authenticate against the service or resource. These credentials expire quickly, and new credentials are created if the requests continue and if the entity continues to have the permissions required to assume the role. With IAM roles, it is the STS service that handles creating and managing these temporary credentials in the background.

IAM roles are also used by AWS services that interact with each other. So, if an EC2 instance needs to access some data on a storage platform such as Amazon Simple Storage Service (**Amazon S3**) or a database service such as DynamoDB, that EC2 instance must be able to assume a role, granting it the necessary permissions.

For example, regarding our Todo List application, if the website frontend were to be hosted on an EC2 instance and offer videos on time management skills, then these videos could be hosted on an inexpensive storage platform such as Amazon S3, designed to host assets such as videos, images, and documents. (We will discuss Amazon S3 in Chapter 3, Understanding Object Storage with Amazon S3, Hybrid Storage, and Static Website Hosting.)

To allow the application running on an EC2 instance access to these time management videos, a role must be created with the necessary permissions to access the videos in the S3 bucket. This role is then assigned to the EC2 instance. The process involves creating something called an EC2 instance profile, which is a container for the IAM role you wish to assign to the instance. Once assigned, the application running on the EC2 instance can make API calls to the S3 bucket so that the end user can access the videos. Without this IAM role, attempts to access the videos stored in the S3 bucket will generate an **Access Denied** error.
