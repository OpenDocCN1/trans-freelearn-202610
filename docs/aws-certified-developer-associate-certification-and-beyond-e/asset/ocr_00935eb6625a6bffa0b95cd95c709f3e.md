# IAM Roles

This type of identity is independent of any specific user with a defined set of permissions. These permissions are described in one or more policies attached to the role. The role can be assumed by users or applications to gain temporary access to other services and resources within an AWS account. Users who usually don't have certain permissions may be granted the ability to assume specific roles that provide elevated access levels when required. An example of this is a **Break Glass** concept, where a junior member of the team may be able to assume a role that grants special permissions to perform restricted tasks under certain conditions.

Roles can also be assumed by identities who use third-party IdPs, enabling identity federation. Examples include OpenID providers such as Facebook and Google or corporate directory services such as Microsoft AD, which supports the support SAML 2.0 protocol. You can also use roles to allow users from other AWS accounts to access services and resources in your AWS account through cross-account access and role switching.

IAM roles use temporary credentials created and managed by the STS. The roles are not configured with long-term credentials (usernames and passwords or access keys). Instead, when an entity assumes the role and requests to access a resource, it is provided with temporary credentials to authenticate against the service or resource. These credentials expire quickly, and new credentials are created if the requests continue and if the entity continues to have the permissions required to assume the role. With IAM roles, it is the STS services that handle creating and managing these temporary credentials in the background.

IAM roles are also used by AWS services that interact with each other. So, if an EC2 instance needs to access some data on a storage platform such as Amazon Simple Storage Service (**Amazon S3**) or a database service such as DynamoDB, that EC2 instance must be able to assume a role, granting it the necessary permissions.

For example, regarding our Todo List application, if the website frontend were to be hosted on an EC2 instance and offer videos on time management skills, then these videos could be hosted on an inexpensive storage platform such as Amazon S3, designed to host assets such as videos, images, and documents. (We will discuss Amazon S3 in Chapter 3, Understanding Object Storage with Amazon S3, Hybrid Storage, and Static Website Hosting).

To allow the application running on an EC2 instance access to these time management videos, a role must be created with the necessary permissions to access the videos in the S3 bucket. This role is then assigned to the EC2 instance. The process involves creating something called an EC2 instance profile, which is a container for the IAM role you wish to assign to the instance. Once assigned, the application running on the EC2 instance can make API calls to the S3 bucket so that the end user can access the videos. Without this IAM role, attempts to access the videos stored in the S3 bucket will generate an **Access Denied** error.
