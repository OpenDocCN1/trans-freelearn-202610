
## Asymmetric KMS Keys

Asymmetric KMS encryption keys are made of a key pair – a private key and a public key. This encryption option is advantageous when you need to enable external parties to perform encryption on data that later needs to be decrypted by you. Using a public/private key pair maintains security even if you freely distribute the public key outside the AWS environment because only you can decrypt any encrypted data using the private key.

The private key is stored in KMS and never leaves unencrypted. You need to call KMS to perform the decryption operation using this private key.

Deciding which encryption key option depends on your use case. If you need to perform encryption operations outside of AWS and access to KMS is not possible, you can use asymmetric keys. If you need to store and manage all encryption and decryption operations using an AWS service such as Amazon S3, then symmetric encryption keys are a great choice.

As previously mentioned, you may need to create data keys or even data key pairs to encrypt data larger than 4 KB. Let us examine this concept next.

## What Are Data Keys?

AWS KMS keys (AWS-managed or customer-managed) are used to encrypt and decrypt plaintext data up to a maximum size of 4 KB. Because you will mostly need to encrypt much larger datasets, you can use the KMS keys to create and encrypt data keys using the GenerateDataKey API. These data keys are symmetric and used for data encryption because they can encrypt data over 4 KB in size and can be downloaded and used outside of AWS. The operation will return both the plaintext copy of the data key and an encrypted copy.

Here are the steps of the workflow:

- 1. Use AWS KMS-generated data keys; the encrypted data key and its plaintext formats are available to download.
- 2. Use the plaintext version of the data key to encrypt your data and then discard the key from memory.
- 3. Send the encrypted data and the encrypted version of your data key to the recipient. The encrypted data key will need to be decrypted first using KMS to produce the plaintext data key.
- 4. The plaintext data key is then used to decrypt the encrypted data.

KMS will use a KMS key to create a data key and an encrypted version of the data key. KMS will be able to decrypt the encrypted data key using the KMS key.

In addition to the GenerateDataKey API mentioned earlier, you can programmatically also call other APIs to interface and work with KMS. Common API calls include the following:

- **GenerateDataKeyPair** – This operation returns an asymmetric data key pair, which you can use outside of AWS KMS. You will get the plaintext public key, and plaintext and encrypted copies of the private key.
- **GenerateDataKeyWithoutPlaintext** – This operation will return a symmetric data key for use outside of AWS KMS. With this operation, you get the encrypted data key under the encryption key you specify. This operation does not return the plaintext copy of the data key and is useful when you do not want to encrypt data immediately. When you do need to perform the encryption operation, you call the Decrypt operation on the encrypted copy of the key.
- **Encrypt** – This operation encrypts plaintext of up to 4 KB in size using a KMS key and can be used to perform both symmetric and asymmetric encryption on small amounts of data such as personal identifiers, keys, or database passwords. You do not use this operation to encrypt a data key. For data keys, you use the GenerateDataKey and GenerateDataKeyPair operations instead.

Now that you understand the fundamentals of how AWS KMS works, let us examine some services on AWS that integrate seamlessly with encryption features. We'll start by looking at the Amazon S3 service and how data is encrypted.

In situations where you want to enforce the use of a particular KMS key for server-side encryption, you must use the `s3:amz-server-side-encryption-aws-kms-key-id` header. If you don’t specify the AWS KMS key ID, then Amazon uses an AWS-managed KMS key instead.

## Dual-Layer Server-Side Encryption with AWS KMS Keys (DSSE-KMS)

This option uses two layers of object-level encryption. When you upload data to Amazon S3, it automatically encrypts it using an S3-managed key. DSSE-KMS allows you to use AWS KMS keys to encrypt the S3-managed key, creating a dual-layer encryption. This option is handy if you need multilayer encryption to fulfill regulatory requirements. With KMS, you have more control over your keys and can manage them securely. Note that the DSSE-KMS keys must be in the same region as the bucket.

## Server-Side Encryption with Customer-Provided Keys (SSE-C)

This enables you to fully manage the encryption keys, while AWS handles all encryption or decryption tasks.

## Client-Side Encryption

This refers to the process of encrypting data on the client side and uploading this data to Amazon S3. The customer must create and manage the keys and the encryption process. The key benefit of using client-side encryption is that your data is not accessible to any third party such as AWS. AWS receives the data fully encrypted and is unable to read that data. Since you encrypt the data on the client side, AWS does not perform any encryption or decryption activity on the data. It also does not identify the data as having been encrypted and only sees it as normal data.

You may choose client-side encryption if your organization needs to follow certain strict regulatory requirements.

Note that when it comes to encryption with Amazon S3, it is the object that is encrypted, not the bucket. When uploading your objects to Amazon S3, you can create policies that enforce object encryption by creating a **bucket policy** that denies any PUT requests unless the request includes the `x-amz-server-side-encryption` header. When specifying this header, you can use AES256 for S3-managed keys or `aws:kms` for KMS-managed keys.

Here is an example of a typical policy you could use, as per the diagram in *Figure 7.8:*

```json
{
  "Version": "2012-10-17",
  "Id": "PutObjPolicy",
  "Statement": [
    {
      "Sid": "DenyIncorrectEncryptionHeader",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::<bucket_name>/*",
      "Condition": {
        "StringNotEquals": {
          "s3:x-amz-server-side-encryption": "AES256"
        }
      }
    },
    {
      "Sid": "DenyUnencryptedObjectUploads",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::<bucket_name>/*",
      "Condition": {
        "Null": {
          "s3:x-amz-server-side-encryption": true
        }
      }
    }
  ]
}
```

Figure 7.8 – Enforcing encryption for object uploads

For this policy, you must specify your bucket’s correct Amazon resource name (arn).

## Amazon EBS Encryption

The **Todo List** application backend services will run on a fleet of EC2 instances distributed across multiple Availability Zones within the N. Virginia region. This will ensure that all data held on storage services will continue to reside within the US borders to fulfil the data residency requirements of the business. While the data created and managed by end customers of the Todo List application will reside in the Amazon RDS database deployed in the last chapter, it is just as imperative to consider encrypting the EBS volumes attached to the instances hosting the backend application.

Amazon EBS uses AWS KMS for all encryption services, enabling you to encrypt the root and data volumes using AES-256 data encryption. When you encrypt an EBS volume, all data that resides on the volume and any data that moves between the volume and the instance is encrypted. Encryption operations are performed on the servers that host the EC2 instances.
