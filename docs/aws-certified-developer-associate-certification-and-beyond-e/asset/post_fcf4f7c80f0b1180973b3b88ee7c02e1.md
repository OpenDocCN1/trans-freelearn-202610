
The architecture of Amazon ECS is designed to provide flexibility and control over how applications run. It comprises several components that enable you to create and manage your containers, incorporating storage and networking features and traffic distribution via load balancers. These components are depicted in Figure 11.2 and discussed next.

![](img/34ff9b5b5a734dae3450ab701e223c73_449_0.png)

Figure 11.2 – Amazon ECS components

The following are the core components of Amazon ECS:

- **Dockerfile**: This is a text file with instructions on how to build a Docker image. Usually comprising a base image like a version of Node.js or a base operating system application layer, this file will contain commands to build the image you can deploy to your containers. Commands would include what runtime environments to operate, the build instructions for your application, the working directory to use, and more.
- **Docker (Container) Image**: This image consists of all necessary components, such as libraries, runtime, ports to expose, and the application in its built state, based on the instructions of the Dockerfile.
- **Container Registry – Amazon Elastic Container Registry (ECR)**: Once you have built your Docker (container) image, you must store it in a repository. Amazon ECR is a fully managed container registry service and integrates well with other services, such as IAM and KMS, to ensure secure hosting of your container images. It offers both public and private repositories.
- **Task Definitions:** These are blueprints for your applications that define how containers should be deployed on the cluster. They include details of what Docker (container) images to use, CPU and memory allocations, networking settings, and more.
- **ECS Services:** ECS services allow you to run and maintain a specified number of instances of a task definition simultaneously in an ECS cluster. These are similar to auto-scaling services offered for your EC2 instances. You can define capacity, scaling policies to use, and triggers to configure. Failed tasks are automatically replaced by the ECS service, ensuring continuity and availability.
- **Tasks:** An instance of a task definition that runs on a container instance. Tasks can be run manually or managed by a service.
- **ECS Cluster:** A logical grouping of services or tasks. The ECS cluster is where you define the infrastructure capacity that can be used and the network environment within which to run your tasks, such as the VPC and associated subnets, monitoring options, and so on.

## ECS Launch Types: EC2 versus Fargate

Amazon ECS enables you to orchestrate and deploy your containers using two main launch types: the **EC2 launch type** and the **Fargate launch type**. You can also deploy your ECS cluster using an **External launch type**, which refers to deploying containerized applications in your on-premises environment.

Understanding the differences between these is crucial for architecting your containerized applications efficiently and cost-effectively. This section will explore both launch types and provide a detailed comparison. *Figure 11.3* illustrates the options:

## EC2 Launch Type

The EC2 launch type allows you to run your containers on a cluster of Amazon EC2 instances you manage. This launch type offers the most control over the underlying infrastructure, allowing you to optimize for specific computing, memory, and networking configurations. Key features are as follows:

- **Control**: Full control over the instance types, operating systems, and the lifecycle of your clusters. However, you manage the instances and any instance-level scalability requirements. Note that task startup times are dependent on instance startups and performance levels.
- **Customization**: Ability to optimize cluster configurations based on your application’s specific needs.
- **Cost-Effectiveness**: Potential for savings through reserved, spot, or dedicated instances.

## Fargate Launch Type

Fargate is a serverless compute engine for containers that removes the need to manage servers or clusters. With Fargate, you specify your containers’ CPU and memory requirements, and ECS handles the rest. Key features include the following:

- **Simplicity**: No need to provision, configure, or scale clusters of virtual machines to run containers. Tasks run in a shared environment managed by AWS and are accessible via elastic network interfaces injected into the VPC subnets you specify. The Fargate launch type is best for applications where simplicity and scalability are prioritized over direct control of the hosting environment.
- **Scalability**: Automatically scales compute to match the specific demands of your application.
- **Security**: Each task runs in its isolated environment, reducing the risk of security issues.

The EC2 launch type is ideal for large workloads and when price is a determining factor. When considering large workloads, often you will need to create different tasks for different components of your workloads, such as frontend and backend services. Here, the EC2 launch type can be used to determine the compute resources required for each type. Furthermore, with the EC2 launch type, you can also use Reserved Instances and benefit from the discounts offered, especially for long-term resources. The EC2 launch type is also recommended if you need more control and the advanced features it offers.

The Fargate launch type is ideal for companies just getting started with containers that perhaps do not have the expertise or the capacity to manage the underlying infrastructure. It is also ideal if you are running light or batch-type workloads. With Fargate, you cannot specify the instance type and run DaemonSets or privileged pods, making some services on your cluster unavailable.

Another crucial component of orchestrating your containers and enabling containerized applications to integrate with other AWS services is understanding how ECS works with IAM. Using policies and roles, you must grant necessary privileges to your container instances and the tasks that run within, following the principle of least privilege access. While this applies to all AWS services, understanding the critical elements of ECS where you must define appropriate roles and permissions is necessary to ensure security and grant the required level of access to function correctly. IAM roles are discussed in the next section.

## Defining IAM Roles for ECS

There are various IAM roles you can define for your ECS environment depending on what launch type you use, the requirements of the task and application, and any specific AWS service integrations you require.

Three typical IAM roles that you are likely to configure are as follows:

- Amazon ECS Container Instance Role
- Amazon ECS Task Execution Role
- Task IAM Roles

### Amazon ECS Container Instance Role

If you plan to host your containers using the EC2 launch type, you must configure an IAM role that provides the container agent installed on the instance with permission to call AWS APIs on your behalf. You can attach a managed policy provided by AWS, AmazonEC2ContainerServiceforEC2Role, to the role, granting permission to use the entire ECS feature set. This policy grants several permissions, such as registering container instances, sending log events to cloud watch, accessing the Amazon ECR repository, and more.

### Amazon ECS Task Execution Role

The task execution role grants permissions to the ECS container and Fargate agents to make API calls. Permissions include pulling container images from ECR private repositories in the same account as the containers or another account and sending CloudWatch logs using the awslogs log driver. Other permissions that can be granted include enabling the task definition to call Secrets Manager secrets or parameters from the AWS Systems Manager Parameter Store. You can use a supplied managed policy called AmazonECSTaskExecutionRolePolicy, which grants permissions necessary for everyday use cases.
