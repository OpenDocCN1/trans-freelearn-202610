## How an IGW Works

An IGW is highly scalable and fully managed by AWS. It sits at the edge of your VPC, enabling inbound and outbound connectivity between your public subnets and the internet and access to other public services offered by AWS (discussed in more detail shortly).

Once the IGW is attached to the VPC, you need to configure routing tables that provide the resources in the public subnets of your VPC (e.g., EC2 instances) a mechanism to access the gateway to send traffic to the internet.

As depicted in the preceding diagram, a public route table is configured with two routes, one for local internal traffic and the other for traffic destined for the internet. The route table is attached to the public subnets, which means that resources within those subnets can send traffic to the internet via the internet gateway. In this case, any traffic destined for 0.0.0.0 /0 (i.e., to networks outside of the 10.0.0.0/16 range) will be sent to the IGW target. The IGW then forwards the traffic to other networks depending on the destination IP address.

A key requirement to send traffic to the internet using the IGW is for the resource itself to also have a public IP address or an elastic IP address. An elastic IP address is the same as a public IP address except that elastic IP addresses are static and do not change if the resource shuts down and starts up again. Standard public IP addresses on the other hand are subject to change. Elastic IP addresses are useful when you want to use the same static IP address for a resource that does not change. In the example shown in the diagram in Figure 4.2, note that the two EC2 instances have a private IP address and a public IP address.

Note that the EC2 instance is not aware that it has a public IP address. The IGW maintains a table of public IP addresses assigned to those EC2 instances and maintains a one-to-one mapping between the resources’ public IP address and private IP address. This allows the IGW to act as a Network Address Translation (NAT) service so that replies to outbound requests can be relayed back to the resource. Furthermore, traffic generated from the internet can be sent to those servers that have a public IP address, such as when you want to connect to a server on SSH for administration remotely.

> **Note:**
> As a best practice, you want to ensure only certain types of instances should be placed in the public subnet with direct outbound internet access, such as bastion hosts that act as management servers to allow remote administration of other EC2 instances located in private subnets.

Web servers do not need to be placed in the public subnet as they still be reached from the internet if you place them behind an ALB, as previously discussed.

These private subnets will not be associated with the public route table and will not be assigned a public or elastic IP address. This is because these resources are meant to be private and accessible only from other resources within the VPC, such as load balancers or databases.

Nevertheless, resources in the private subnet need access to the internet and even other public services on AWS. To grant those resources access to the internet, while still ensuring higher levels of security, such as not having to assign a public IP address to those resources, you can configure a NAT gateway.

Security groups can often be thought of as the primary defense for a resource where, by default, all inbound traffic is denied until you create **allow** rules. NACLs can be thought of as an additional security guardrail that can help you define rules for the whole subnet. Each VPC comes with a default NACL that incidentally allows all inbound traffic. This is because ultimately, your security groups will block all inbound traffic by default until you create inbound allow rules. Furthermore, it is not possible to deploy a resource such as an EC2 instance without creating and/or attaching it to a security group (which would block all inbound traffic by default).

A key feature of NACLs is that you can also configure deny rules. This is particularly useful where you may need to allow inbound traffic, for example, on port 80 from the wider internet but then also deny traffic on the same port from specific CIDR ranges. The rules are defined in priority order, where the lowest numbered rule has a higher priority than rules further down the list. Furthermore, a deny rule at a higher priority will override an allow rule at a lower priority. Sometimes you may need to create multiple VPCs, such as for different workloads or different Regions. However, you may also need to have network connectivity between the VPCs you create. You will explore VPC interconnectivity next.

## Configuring VPC interconnectivity

Often a single VPC will not be enough, and you will find yourself creating separate VPCs for different workloads and applications as well as for different branch offices and locations. Sometimes you may need to share resources with other VPCs. In *Chapter 1, Introduction to AWS Accounts and Global Infrastructure*, you learned about the concept of hosting an AWS account to manage all shared infrastructure resources. VPCs that belong to other departments or branches of the company may wish to access resources in such shared VPCs. One way to grant access is to establish network connectivity between VPCs.

AWS offers several different options to connect your VPCs to each other, which will be explored next.

## VPC Peering

A VPC peering connection is a networking connection between two VPCs where traffic between them takes place over the AWS backbone network using private IP address space. EC2 instances in one VPC can then communicate with resources in a peered VPC. Peering connections can be configured between VPCs in your AWS accounts or even with VPCs that belong to other AWS accounts. Peering connections can also be established between VPCs within the same Region or even cross-Region.

A typical example would be where you have VPCs in different Regions that belong to branch offices of your company, and you need to establish a peering connection between them to share access to centralized resources.

Connectivity between VPCs never traverses the public internet, and this improves your security posture further by avoiding DDoS attacks and common exploits originating from the internet.

Setting up a peering connection requires sending a request from one VPC (the requester) to the other VPC (the accepter). Once the request is accepted, the peering connection is established. Note that you will still need to configure necessary routing rules in your route tables for the newly established network connections. The owner of each VPC in the VPC peering connection must create the necessary routes in the relevant route table to allow traffic to flow between the VPCs.
