
This will improve your application security posture because you can avoid hardcoding credential data within the application code, a practice that is very risky and can lead to malicious attacks. Using AWS Secrets Manager for managing the lifecycle of secrets such as credentials can help prevent such attacks.

## Enterprise Solutions with Amazon Aurora

Although offered as part of the Amazon RDS solution, Amazon Aurora should really be considered a relational database solution in its own capacity. The service is a proprietary database offering from AWS that is compatible with MySQL and PostgreSQL but comes with enterprise-grade features right out of the box. In this section, you will have a look at some of these core features.

Amazon Aurora is configured as a cluster with a single primary instance. You can have up to 15 Aurora replicas in addition to the primary DB instance, giving a total of 16 copies of your data. Aurora uses a **cluster volume** that comprises a storage volume spanning multiple Availability Zones, with each Availability Zone having a copy of the data. This is depicted in the following diagram:

![](img/34ff9b5b5a734dae3450ab701e223c73_227_0.png)

Figure 6.14 – Amazon Aurora architecture

With Amazon Aurora, you have **six copies of your data spread across three Availability Zones**. In addition, the cluster volume automatically scales as your data storage requirements increase, and depending on your DB engine version, offers a maximum volume size of 128 TB.

Unlike other engines on Amazon RDS, the storage on Aurora is elastic. This means that when you delete data, the space allocated for that data is freed. Storage is managed separately from the Aurora instances, allowing you to add instances that connect to the existing shared storage volume.

Like Amazon RDS, Amazon Aurora can only have one master instance at a time – this is the instance where writer operations to the database can be performed. In addition to the master, Amazon Aurora can have up to 15 read replicas all configured with replication of data from the master. This means that automatic failover is available in the event of the master instance failing. Another point to note is that your read replicas can provide cross-region support.

To facilitate the seamless failover of your master instance, Amazon Aurora presents endpoints that are DNS addresses to connect to for writing to and reading from the database. The following are the endpoints offered on Amazon Aurora:

- **Cluster endpoint (writer endpoint):** This is the endpoint that would be presented to any application needing both write and read access to the database. This endpoint points to the current primary instance and is capable of all write operations including **Data Definition Language (DDL)** statements.
- **Reader endpoint:** This is designed to provide load-balancing support for read-only requests to the DB cluster. This endpoint should be used by any application that only needs to perform read queries against the database. The reader endpoint only connects to the read replicas and so frees up the primary instance.
- **Custom endpoint:** This is an endpoint you define by selecting the target instances of your choice. You can choose a selection of instances based on various factors, such as by application.
- **Instance endpoint:** Each DB instance has its own endpoint address as well. This can be used to give direct control over connections to the DB cluster.

Now that you have learnt about Amazon Aurora at a high level as well as covered relational databases, it’s time to look at how you can improve application and database performance using in-memory caching engines. In addition, relational databases should be used to store data for the longer term, however, applications tend to also store and require access to temporary data such as session states or gaming leaderboards. An in-memory caching engine can be a more cost-effective way to manage this type of data than traditional relational databases.

## Caching Data with Amazon ElastiCache

Amazon ElastiCache is an in-memory caching engine designed to help improve latency and throughput for read-heavy workloads that don’t change too frequently. AWS offers two fully managed in-memory engines – Redis and Memcached.

Amazon ElastiCache can be used to provide in-memory caching services for relational databases such as Amazon RDS.

Redis is designed for more complex data types and offers advanced features such as high availability, automatic failover, backup and restore, and online re-sharding when cluster mode is enabled.

### Caching Strategies

The following are some key caching strategies offered by Amazon ElastiCache:

- **Lazy loading** – A strategy in which data is loaded only when necessary, usually resulting in a cache miss. This ensures you avoid filling up the cache for infrequently accessed data. If data is not in the cache, the application must retrieve it from the database and that data is also then written to the cache. Note that data can become stale if lazy loading is implemented without other strategies being implemented such as **Time-to-Live (TTL)**.
- **Write through** – This ensures that the cache is updated whenever a new write or update request is made to the underlying database, keeping cache data up to date and making sure that data is never stale. Note, however, that every write involves two trips: a write to the database and a write to the cache. Note that a key disadvantage is that most data is never read, and this can lead to resource wastage. Adding a TTL can help minimize this wastage by expiring and thus purging data that is no longer required.

**Amazon ElastiCache** is designed to help offload reads from a database, which is usually more expensive, especially for frequently queried data or results of expensive computation tasks and session states.

## Introduction to Modern NoSQL Databases with Amazon DynamoDB

In addition to traditional relational databases, AWS also offers NoSQL databases designed to provide better performance and seamless scalability. Amazon DynamoDB is AWS’s NoSQL database solution and is highly scalable, using distributed clusters of hardware to increase throughput without the increase in latency.

Amazon DynamoDB is designed for most modern web and mobile applications, and as a fully managed service, can support both server-based and serverless application architectures. With DynamoDB, you also do not need to make decisions on the underlying compute or storage infrastructure, as this is taken care of by AWS depending on your capacity requirements. Being fully managed in this fashion means that you can focus on designing and building solid high-performing applications.

Another key aspect of DynamoDB is that it is schema-less. Every table must have a primary key much like traditional relational databases to uniquely identify a record. However, beyond this, there are no other constraints like those found in traditional SQL databases. DynamoDB can be used to host structured and semi-structured data including JSON documents. Furthermore, DynamoDB presents itself as a complete web service and you make calls to the database using HTTP(S) requests and responses. With DynamoDB, you can use either the DynamoDB API or PartiQL, a SQL-compatible query language, to add and retrieve data from a table.

Here is an example of a PartiQL for DynamoDB query:

```sql
SELECT AlbumTitle, Year, Price
FROM Music
WHERE Song='All Night Long'
```

Like relational databases, DynamoDB uses the concept of tables, which can contain items (records) that have attributes (values). A primary key is used to uniquely identify an item and you can also have secondary indexes to offer more querying options. You will look at these core components next.

### DynamoDB Core Components

The following are the core components of a DynamoDB database:

- **Tables:** Data is stored in tables just like other relational databases. A table represents a collection of data. For example, the Employees table will contain all employee details, their salary information, pension contributions, etc.
- **Items:** Each table can then contain one or more items. This is a group of attributes that define the item and its characteristics. For example, in the Employees table, each employee would be represented as an item. Each item will need to have a primary key assigned to it that uniquely identifies that item.
- **Attributes:** Each item comprises one or more attributes. These attributes are used to store values associated with the item. For instance, examples of attributes in the Employees table are **first-name**, **last-name**, and **department**. These attributes help you define the values for each item in the table.
