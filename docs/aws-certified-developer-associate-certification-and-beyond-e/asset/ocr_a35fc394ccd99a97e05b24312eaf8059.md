# How an IGW Works

An IGW is highly scalable and fully managed by AWS. It sits at the edge of your VPC, enabling inbound and outbound connectivity between your public subnets and the internet and access to other public services offered by AWS (discussed in more detail shortly).

Once the IGW is attached to the VPC, you need to configure routing tables that provide the resources in the public subnets of your VPC (e.g., EC2 instances) a mechanism to access the gateway to send traffic to the internet.

As depicted in the preceding diagram, a public route table is configured with two routes, one for local internal traffic and the other for traffic destined for the internet. The route table is attached to the public subnets, which means that resources within those subnets can send traffic to the internet via the internet gateway. In this case, any traffic destined for 0.0.0.0 /0 (i.e., to networks outside of the 10.0.0.0/16 range) will be sent to the IGW target. The IGW then forwards the traffic to other networks depending on the destination IP address.

A key requirement to send traffic to the internet using the IGW is for the resource itself to also have a public IP address or an elastic IP address. An elastic IP address is the same as a public IP address except that elastic IP addresses are static and do not change if the resource shuts down and starts up again. Standard public IP addresses on the other hand are subject to change. Elastic IP addresses are useful when you want to use the same static IP address for a resource that does not change. In the example shown in the diagram in Figure 4.2, note that the two EC2 instances have a private IP address and a public IP address.

Note that the EC2 instance is not aware that it has a public IP address. The IGW maintains a table of public IP addresses assigned to those EC2 instances and maintains a one-to-one mapping between the resources’ public IP address and private IP address. This allows the IGW to act as a Network Address Translation (NAT) service so that replies to outbound requests can be relayed back to the resource. Furthermore, traffic generated from the internet can be sent to those servers that have a public IP address, such as when you want to connect to a server on SSH for administration remotely.

> **Note:**
> As a best practice, you want to ensure only certain types of instances should be placed in the public subnet with direct outbound internet access, such as bastion hosts that act as management servers to allow remote administration of other EC2 instances located in private subnets.

Web servers do not need to be placed in the public subnet as they still be reached from the internet if you place them behind an ALB, as previously discussed.
