While, technically, the shift from virtual machines to containers is a no-brainer, you must consider the implications of change in any live environment. In the following project exercises, you will first deploy and configure the ECS service and transfer traffic to it before terminating the previous Auto Scaling Group configuration, which deploys the EC2 version of your architecture as documented in earlier chapters.

While this chapter doesn’t discuss deployment strategies, you must consider such strategies in real-world scenarios, some of which were examined in *Chapter 10, Designing Deployment Strategies with AWS Elastic Beanstalk*.

In the preceding diagram, you will note the changes made, which have been numbered to help identify the components incorporated into the design. The following is a breakdown of the critical services and resources that make up the architectural changes:

+   - **Amazon Elastic Container Registry (ECR):** The Amazon ECR service replaces the S3 bucket previously used to host the application source files in ZIP format. Recall that, previously, when the Auto-Scaling group launched EC2 instances to provide backend operations, a user-data script would run that would copy this ZIP file from the bucket to the EC2 instance and perform various configuration tasks. In this change, you will create an ECR repository that will host a Docker image, which will be used to deploy your Fargate containers.
