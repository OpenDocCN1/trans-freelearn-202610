Ultimately, the Amazon SNS pub/sub model is incredibly effective for broadcasting notifications across various types of consumers, including email addresses, SQS queues, and AWS Lambda functions.

An important feature of the SNS service is the SNS and SQS fanout pattern, which will be discussed in the next section.

# Amazon SNS and SQS Fanout Pattern

With Amazon SNS, you can design a solution where a single topic can be used to distribute messages to multiple SQS queues, effectively implementing a one-to-many communication model for information distribution. This pattern is not only scalable but also enhances the reliability of message delivery. For example, in Figure 15.11, we discussed an architecture pattern where an ordering service would notify multiple Lambda functions to process orders in an e-commerce application. As the orders come through, a notification is sent to a topic that the shipping and inventory services (Lambda functions) have subscribed to.

With Amazon SNS, messages are not stored in the topic; as the messages come through, subscribers receive notification immediately and must act on the message. This is because Amazon SNS is a push-based messaging service. However, it’s important to note that with Amazon SNS, you can configure a delivery policy that includes the option to retry the delivery of messages when subscribed endpoints become unavailable for any reason. The default retries policy of AWS-managed endpoints, such as Amazon Data Firehose, Lambda, or SQS, is three times without delay. There are four phases of a delivery policy, as follows:

The Immediate Retry phase (no delay) refers to retries after the initial delivery attempt.

The Pre-Backoff phase refers to attempting a set of retries before applying a backoff function to add a delay between those retries.

The Backoff phase controls the delay between retries using the retry-backoff function by setting the minimum and maximum delay and a retry-backoff function to define the delay increase from the minimum to maximum delay.

The Post-Backoff phase specifics the number of retries and the delay between retries.

If the delivery policy is exhausted, Amazon SNS stops retrying attempts and discards the message unless you configure a dead-letter queue to deliver the message.

Assume several orders are coming through and multiple notifications are being sent to the topic, which results in those messages getting pushed onto the Lambda functions. In such a scenario, it might be necessary to incorporate an SQS queue to hold the messages in a queue so that the Lambda function can retrieve them and process them when capacity is available. This process of sending a message to an SNS topic, which then distributes it across multiple SQS queues, is known as a Fanout pattern.
