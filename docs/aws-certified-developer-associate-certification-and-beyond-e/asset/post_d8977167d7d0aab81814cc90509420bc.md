## Using Amazon S3 Versioning with S3 Lifecycle Management

Amazon S3 Lifecycle management allows users to define rules for a group of objects, specifying the actions that Amazon S3 should take. By combining object versioning with S3 Lifecycle, users can optimize their data preservation strategy and reduce storage costs.

Two actions can be performed with the S3 Lifecycle – transitional and expiration. Transitional actions help manage storage class transitions by transferring items to a different storage class after a specified time. For example, as per the following screenshot, the current version of objects will be moved from the S3 Standard storage class to the S3 Standard-IA storage class after 90 days and then moved to the Glacier class after a year. Non-current versions of those same objects will be moved into the Glacier class after 30 days. This strategy makes sense because the probability of wanting to access previous versions drastically reduces, and this presents an opportunity to automatically reduce overall costs.

![](img/34ff9b5b5a734dae3450ab701e223c73_118_0.png)

Figure 3.2 – An Amazon S3 Lifecycle rule example

Expiration actions allow users to specify when objects should expire, and once an object expires, Amazon S3 automatically removes it from storage.

When an object becomes eligible for a lifecycle action, the user’s bill will be updated regardless of how long it takes for Amazon S3 to act. Using object versioning with S3 Lifecycle can help control storage costs and customize data retention strategies according to business needs.

It is important to note that if Amazon S3 extends the expiration period of a scheduled item, there will not be additional charges for storage beyond the original expiration period. However, if there is a lifecycle rule in place to migrate the item to a different storage tier, the billing won't be adjusted until it is moved to that tier.

Amazon S3 Lifecycle management can be useful in various scenarios, such as transitioning recurring log files to cheaper storage classes or archiving documents that are no longer frequently accessed but need to be retained for compliance or legal purposes. Additionally, Amazon S3 can be utilized to archive certain types of data, such as digital materials, medical and financial records, unprocessed genetic sequence data, and long-term database backups.

Amazon S3 Lifecycle management is a powerful tool to control storage costs and customize data retention strategies. By combining object versioning with S3 Lifecycle, users can optimize their data preservation strategy and reduce storage costs.

## Implementing Data Protection with Resource-Based Policies

This section explores resource-based policies to enforce the principle of least privilege and restrict access to Amazon S3 buckets and objects. By default, S3 buckets are private; only the root user and the IAM account that created a bucket can access it.

In contrast to IAM policies that determine actions for IAM users or roles, resource-based policies are inline policy statements attached to the resource itself. In Amazon S3, these policies are called bucket policies, which specify the allowed access levels against that resource and its access source.

Resource-based policies can also provide additional permission levels, including the ability to grant anonymous access. This feature allows users on the public internet to access your resources. For example, you may offer a free e-book as part of your marketing strategy (without the need to have the end user register for it). Amazon S3 also allows you to host a static website (discussed later), which means the anonymous access feature is required to enable anyone to visit your website. This key feature is not available with IAM policies. The policy requires you to specify a principal, which can be a person in an AWS account or another AWS account, or a wildcard (*), which provide anonymous/public access to Amazon S3 buckets.

The following example illustrates how to grant anonymous public access using the `s3:GetObject` permission for the `packt-aws-developer` bucket. This allows anonymous users to access the contents of the bucket, as depicted in the following code:

```
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadGetObject",
      "Effect": "Allow",
      "Principal": "*",
      "Action": [
        "s3:GetObject"
      ],
      "Resource": [
        "arn:aws:s3:::Bucket-Name/*"
      ]
    }
  ]
}
```
```

In Amazon S3, the bucket owner has the authority to attach policies to their buckets. However, if objects within the bucket are owned by other AWS accounts, access control must be defined through **Access Control Lists (ACLs)**. In such a case, the bucket owner needs to transfer the ownership of those objects to gain control over them. This allows them to utilize IAM policies or resource policies to set access control for those objects.

Transferring ownership of objects is a powerful feature that enables an owner to take control over objects uploaded by other AWS accounts. This approach helps enforce the principle of least privilege and provides better control over object access. By utilizing policies, the bucket owner can define access levels and specify the source of access to the objects within the bucket.

The use of policies helps the bucket owner control access to objects owned by other accounts and ensures that only authorized users can perform specific actions on those objects. This approach provides a flexible tool to enforce security policies and implement the principle of least privilege.

> **Note**
> 
> Amazon S3 bucket policies have a 20 KB size limit to promote efficient processing. When using the S3 web console, additional permissions must be granted. These are the `s3:ListAllMyBuckets`, `s3:GetBucketLocation`, and `s3:ListBucket` permissions.

## CORS

The CORS protocol enables web applications on one domain to interact with resources on another domain. When a user agent requests a resource from a domain, protocol, or port other than those used for the current page, it sends a cross-origin HTTP request. Without CORS in place, the request is denied, thanks to security protocols defined in modern browsers.

Amazon S3 uses CORS rules to allow cross-origin requests based on specific conditions, such as matching the `AllowedOrigin` element to the `Origin` header of the request and checking the request method and headers against the defined rules. Understanding how to manage CORS on Amazon S3 is essential for effective web hosting.
