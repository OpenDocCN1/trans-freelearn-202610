
The alternative would be to hardcode the credential data of a “dummy” IAM user who has been assigned an IAM policy (discussed shortly) that grants that user access to the videos in the S3 bucket. This is clearly bad practice because if someone were to hack into the application code, they would now also have access to the credentials to access the S3 bucket. In any case, managing hardcoded credentials in application code is a huge administrative burden. IAM roles thus enable you to grant access to resources using temporary credentials that are more efficiently managed and it removes much of the risk associated with hardcoding credential data in application source codes.

Here is a quick high-level breakdown of the configuration shown in Figure 2.2:

- 1. An IAM role is created for the EC2 service. This means that EC2 is the trusted entity. A permission policy is attached to the role, which grants access to an Amazon S3 bucket containing the objects required for the web application. In this case, it would be time management videos.
- 2. The IAM role is then attached to the EC2 instance via an instance profile. Only one role can be assigned at a given time. However, a role may have one or more policy documents defining different permissions sets.
- 3. Users access the web application and attempt to watch/download the time management videos.
- 4. The EC2 instance assumes the role and is granted access to the objects in the S3 bucket. The Amazon STS service creates the necessary temporary credentials and manages access in the background.

Rather than assigning rules directly to individual users or groups in IAM, administrators must instead assign them to roles. Multiple IAM policies can be applied to a single IAM role, which can subsequently be assigned to a set of users or a group. There are several types of IAM roles based on business requirements. The different IAM roles are as follows:

- **AWS IAM role:** An identity independent of any specific user or application with one or more policies that define a set of permissions to access services and resources on AWS.
- **AWS service role:** Used by AWS services to access and manage your AWS account on your behalf. Service roles are unique to each service and can only be used to control access inside a single AWS account. We discussed attaching a role to an EC2 instance in the previous example. This kind of role is referred to as a service role. It's important to note that this role can be attached or detached at any time during the lifetime of the EC2 instance. To prevent unintended changes to the settings and ensure the instance's security right from the start, it is recommended to attach this role when launching the Amazon EC2 instance.
- **AWS service-linked role:** This type of role grants a service-specific function the necessary permissions to call other AWS services. These permissions are predetermined and defined in the role. The role may be created or deleted automatically by the service and modified or removed through a service-specific procedure or wizard. Many AWS services, such as AWS Lambda and EC2 Auto Scaling, utilize service-linked roles.
- **Role chaining:** Role chaining is a mechanism that aims to limit command-line or API requests to a maximum of a one-hour session. When assuming a role through the `AssumeRole` API method, you can set a time limit on the role session using the `DurationSeconds` argument, with a maximum duration of 43,200 seconds (12 hours). Note that when using role chaining, the operation will fail if the `DurationSeconds` argument is set to a value greater than one hour. Check out this article for further details: https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_terms-and-concepts.html.
- **Delegation:** This refers to external users or applications that require access to resources in your AWS account. The process involves establishing a secure connection between the account that contains the resources (known as the **trusting account**) and the account that requires access to those resources (known as the **trusted account**). The delegation process requires establishing a trust policy between the trusted and trusting accounts.

Figure 2.3 – Using IAM roles to configure cross-account access

As shown in Figure 2.3, we use the example of a developer in the Identities account that needs to access an S3 bucket (called TodoApp) in the development account. This is known as cross-account access, and the following are the primary steps involved in configuring this:

- I. In the development account, you must configure a role with a trust policy that identifies the trusted account (in this case, the Identities account). In this example, we named the IAM role IAM-User-S3-AccessRole. The configuration requires you to provide the ID for Account A.
- II. You will also need to configure a policy that contains the necessary permissions to perform read/write operations against the TodoApp S3 bucket in Account B.
- III. Finally, in Account A, you need to configure another policy that grants the developer the ability to assume the S3AccessRole created in Account B. You do this by specifying the Account ID of Account B and the role in the policy statement. The policy will grant the sts:AssumeRole permission as per the following JSON script:

```json
{
  "Version": "2012-10-17",
  "Statement": {
    "Effect": "Allow",
    "Action": "sts:AssumeRole",
    "Resource": "arn:aws:iam::Developer-Account-ID:role/S3AccessRole"
  }
}
```

Once the preceding configuration is in place, the developers can switch roles and access the TodoApp S3 bucket in AWS Account B.

**Note**
With the new IAM Identity Center service (previously known as AWS Single Sign-On), you may not need to use cross-account access extensively for IAM users. This is because the IAM Identity Center offers an alternative approach to granting your workforce users access to multiple out-of-the-box accounts in your AWS Organizations. These users can be from AWS IdPs as well as external providers. We discuss the IAM Identity Center later in this chapter.

- **Federation:** Applications can use identity federation to authenticate external users using external IdPs without needing a custom sign-in code. This can be achieved using Amazon, Facebook, Google, or other IdPs that are compatible with **OpenID Connect (OIDC)**, Microsoft AD, or Protocol (LDAP), which support SAML 2.0. By doing so, token-based authentication strategies can be developed between external IdPs and applications hosted on AWS, eliminating the need for separate user accounts and passwords.

## IAM Policy

A JSON document adheres to the IAM policy standard, which outlines the permissions defined by a specific IAM role. An example of such a policy is depicted here, which allows the ability to access objects stored in the TodoApp S3 bucket:

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "AccessToDoAppBucket",
            "Action": [
                "s3:GetObject",
                "s3:ListBucket"
            ],
            "Effect": "Allow",
            "Resource": [
                "arn:aws:s3:::todoapp",
                "arn:aws:s3:::todoapp/*"
            ]
        }
    ]
}
```

Now, let’s explore the types of policies that are associated with an IAM role:

- **Trust policy**: This policy defines the service that is being trusted. Each role can have only one trust policy. Services that can be trusted include EC2, EMR, an EC2 container service, **Relational Database Service (RDS)**, Lex, and Glue.
- **Permissions policy**: The authorization policies specify which resources a role has access to and what actions the role can take on those resources. Policies can be controlled by AWS or the client or added in line with the role itself. More information can be found at https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies_managed-vs-inline.html.

## Permissions Boundary

This feature allows you to set a boundary or a limit on the maximum permissions that can be assigned through an IAM policy. Permission boundaries allow you to restrict access to perform specific tasks. It is beneficial when there are many employees in an organization, and you want to allow them to create and customize their policies while ensuring that they do not exceed the permissions specified by a permission boundary.

For example, let us say that you have a group of system administrators who should have full access to IAM, S3, and RDS. You want to ensure that they do not launch any EC2 instances. You could add a policy to their account that denies them the ability to launch EC2 instances. However, if they have full access to IAM, they could either remove that restriction or create another IAM user with permission to launch EC2 instances.

A permission boundary can be applied to their account, so they can only create other IAM user accounts if this same permission boundary is attached to those additional accounts. In addition, the permission boundary will explicitly deny the ability to launch EC2 instances. Now, you have a scenario where even if one of the admins tries to create another IAM user account, that new user account will still be denied the ability to launch EC2 instances, preventing any opportunity to circumvent the policies.

In this section, we have reviewed the fundamental concepts of AWS IAM, including its key components, such as the IAM user, IAM roles, and IAM policies.

By default, accessing the web console as an IAM user requires a username and password combination. In addition, you need access keys (comprising access key ID and secret access keys) for command-line access.

Credentials comprising only usernames and passwords are a security risk, which can be mitigated with MFA. In the next section, we will examine this technology in detail.

## Improving Your Security Posture with MFA

MFA is a security feature that enhances the authentication process by requiring users to input a six-digit token in addition to their usernames and passwords. AWS strongly recommends enabling MFA for your root user account and IAM users to increase security.
