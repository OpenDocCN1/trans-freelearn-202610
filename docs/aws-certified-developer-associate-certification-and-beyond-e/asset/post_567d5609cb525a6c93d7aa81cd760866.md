
+   - Microservices require sophisticated orchestration and monitoring tools to manage multiple services and their interactions, which can increase operational overhead but provide better resilience and fault isolation

The choice between monolithic and microservices architectures often depends on the specific requirements and constraints of the project. A monolithic approach makes sense for start-ups and small applications due to its simplicity and low overhead. Larger, more complex applications, or those expecting to scale significantly, might opt for a microservices architecture to take advantage of its scalability and resilience despite the higher initial complexity and management overhead.

Understanding the strengths and weaknesses of monolithic and microservices architectures allows developers and architects to make informed decisions that best meet their application's requirements. As organizations grow and evolve, they might consider transitioning from a monolithic to a microservices architecture to better address their needs for scalability and flexibility. This decision should align with the organization's strategic goals and the specific challenges its application landscape poses.

After understanding the conceptual differences between monolithic and microservices architectures, it's essential to explore practical tools that facilitate the development of loosely coupled applications. AWS provides several services that support this architecture style, notably Amazon **Simple Queue Service** (SQS) and Amazon **Simple Notification Service** (SNS). These services are fundamental for building applications that are not only loosely coupled but also scalable and resilient to failures and is the topic of the next section.

## Building Loosely Coupled Applications with Amazon SQS and SNS

The ability to build resilient and scalable applications is crucial in the cloud infrastructure landscape. AWS provides two key services supporting loosely coupled systems architecture: Amazon SQS and Amazon SNS. These services are essential for developers implementing robust distributed systems by facilitating asynchronous communication between decoupled components, a central theme for the AWS Certified Developer Associate exam.

AWS services, such as **Application load balancers**, also enable building loosely coupled architectures using synchronous replication. The added benefit of asynchronous architectures is that messages can be held in queues temporarily, allowing downstream components to retrieve those messages when they are ready to process them.

The next subsection provides an in-depth review of the Amazon SQS service.

## Decoupling with Amazon SQS

Amazon SQS is a fully managed message queuing service that helps decouple application components. By enabling asynchronous message queues, SQS allows components of a distributed system to communicate without being connected directly, enhancing fault tolerance and scalability.

Figure 15.2 illustrates a high-level example of an application that enables end users to upload photos to a central S3 bucket. As images are uploaded, an event notification can be configured to trigger a Lambda function.

![](img/34ff9b5b5a734dae3450ab701e223c73_627_0.png)

Figure 15.2 – Event-driven synchronous architecture

The backend Lambda function processes customers’ images and uses Amazon Rekognition to detect objects within the image using its artificial intelligence and machine learning capabilities. The results from the processing could be stored in an Amazon DynamoDB table.

While the architectural design patterns work well, the synchronous design pattern does pose some risks. For example, imagine a scenario with hundreds of customers uploading images simultaneously. Images arriving at the S3 bucket simultaneously will likely trigger too many requests to the Lambda function, resulting in a backlog and possible failure to process some of those images. The lack of fault tolerance can then result in poor customer experience. To address this concern, decoupling the architecture so that frontend requests and backend processing can be handled asynchronously will yield a better design pattern, as depicted in Figure 15.3. An additional point to note is that you must ensure adequate write capacity units provisioned for your DynamoDB table (or opt for on-demand provisioning) to handle the coming write requests.

![](img/34ff9b5b5a734dae3450ab701e223c73_628_0.png)

Figure 15.3 – Using Amazon SQS to decouple application architecture

As multiple users upload images to the S3 bucket, event notifications are triggered and sent to the SQS queue, where the messages are held for a duration. The retention period can be 1 minute to 14 days, with the default period being 4 days. The Lambda function is then configured to poll the queue for new messages and retrieve them at its own pace, ensuring that no image goes unprocessed. Note that, by default, the SQS message size is limited to 256 KiB. For messages larger than this, you must use the Amazon SQS Extended Client Library for Java or Python, where the message payload is hosted on an Amazon S3 bucket, and the SQS queue is used to host a reference to that payload.

In this design architecture, the S3 bucket is the message producer, and the Lambda function is the consumer.

## Amazon SQS Queue Types

Amazon SQS provides two types of queues to facilitate different use cases: standard queues and First-in-First-out (FIFO) queues.

### Standard Queues

Standard queues are the default queue type. They provide nearly unlimited transactions per second (TPS) per API action. These API actions are SendMessage, ReceiveMessage, and DeleteMessage.

SQS queues are also regional-specific and redundantly store your messages for processing across multiple Availability Zones. This ensures that there is no single point of failure. Key features and limitations of standard queues are as follows.

### Message Ordering

Standard queues offer only best-effort ordering. This means that, sometimes, your messages might arrive in a different order from the order in which they were sent.

![](img/34ff9b5b5a734dae3450ab701e223c73_629_0.png)

Figure 15.4 – Standard queue

If your applications require the order of messages to be preserved, then AWS recommends you opt for the FIFO queue, discussed later in this chapter.

### At Least Once Delivery

Messages are stored on servers that form part of the SQS service. Occasionally, a server hosting a copy of the message might be unavailable when your consumer receives and deletes the messages from the queue. When this server returns online, the message might get delivered again when you perform a receive message action. This can result in duplicate messages getting delivered to your consumers. Because of the nature of standard queues, it is recommended that you design your applications to be idempotent, which means they do not get affected adversely when processing duplicate messages.

### FIFO Queues

FIFO queues are designed to overcome some of the limitations of standard queues, as we explain here.

### Message Ordering

The order in which your messages are sent into the queue is the order in which it is received (i.e., first in, first out).

![](img/34ff9b5b5a734dae3450ab701e223c73_630_0.png)

FIFO queues are particularly useful when your application must receive the messages in the order in which they were sent. Examples use cases include the following:

- Ensuring students can be enrolled into a course only after registration is complete
- Ensuring that commands entered are executed in the right order
- An online ticketing system must ensure that tickets are issued in the order they were created

### Exactly Once Processing

With FIFO queues, you do not get duplicate messages. Messages remain available until a consumer processes them and delete them from the queue.

When deciding whether to use standard queues or FIFO queues, it is also important to consider how many messages per second your application will be required to handle. The next section provides an overview of SQS queue throughput considerations.

### Throughput Considerations

Understanding throughput is crucial when deciding which queue type to use for your application:

- Standard queues support a nearly unlimited TPS for each action, such as sending, receiving, or deleting messages.
- FIFO queues are more limited, supporting up to 300 messages per second with batching or 3,000 messages per second without batching. This knowledge is essential for applications requiring a strict order and uniqueness in message processing.
