
Ultimately, provisioning capacity requires understanding the application’s requirements. Next, you will look at some additional concepts on how DynamoDB manages provisioned capacity.

DynamoDB is automatically enabled for **adaptive capacity**. This feature enables DynamoDB to run workloads that are unpredictable in nature and helps to minimize throttling exceptions. The feature also offers a better mechanism to handle *hot partitions*. A hot partition is one that receives higher volumes of read and write requests compared with other partitions. DynamoDB uses its adaptive capacity to handle uneven access patterns by automatically increasing throughput for partitions that receive more traffic than others. To illustrate this concept, let’s look at the following diagram:

Figure 6.17 – DynamoDB adaptive capacity

In the preceding diagram, you have a table provisioned with 400 WCUs evenly spread across four partitions. Let’s assume that partition 4 has some very popular data and becomes a hot partition. The total capacity required for partition 4 due to demand is 150 WCU/sec. With this huge increase in write capacity, eventually, you would expect traffic to be throttled as it exceeds 100 WCU/sec. However, with adaptive capacity, DynamoDB will increase partitions 4’s capacity drawing on the available capacity from the other partitions to help handle the higher workload of 150 WCU/sec without being throttled.

Another feature is known as **burst capacity**. Here, DynamoDB reserves a portion of unused capacity (a maximum of 300 seconds of unused read and write capacity) for handling any occasional usage spikes as they occur.

Note that if you exceed the maximum allowed provisioned throughput for a table, then you may get a `ProvisionedThroughputExceededException` error message. This may happen when your request rate is too high, you have a hotkey where one partition key is being read too many times, or you have very large items. Usually, AWS SDKs for DynamoDB automatically retry requests and these eventually succeed, unless the retry queue is too large to complete. To resolve this issue, you can use **exponential backoff**, which uses progressively longer waits between retries. You could also distribute your partition keys as much as possible for where the issue is caused by excessive reads, and consider implementing the **DynamoDB Accelerator (DAX)**, as it will be discussed later in this chapter.

Now that you have understood how DynamoDB provisions and manages capacity, let’s move on to discuss how we access and use DynamoDB.

## DynamoDB Access Methods

There are several ways to access DynamoDB and the tables you create within the service. The following options are available to access DynamoDB tables:

- **AWS CLI** – Like other AWS services, you can use the AWS CLI or Amazon CloudShell to access the DynamoDB service, provision and manage DynamoDB tables, and perform standard database operations including query and scan operations.
- **NoSQL Workbench** – A cross-platform, client-side GUI-based application that can be used to perform all database development and operations. NoSQL Workbench comes with an IDE tool to facilitate data modeling, visualization, and query development for your DynamoDB tables.
- **PartiQL** – A SQL-compatible query language that can be used to interact with the database by performing **create, read, update, and delete (CRUD)** operations with DynamoDB tables.

AWS DynamoDB also supports AWS SDKs for programmatic access and manipulation of data in your tables. You can then use standard programming languages such as Python, Java, and .NET. DynamoDB exposes low-level APIs as a protocol-level interface. Requests to the database using HTTP(S) requests can then be used to facilitate your application to construct low-level API requests on your behalf. DynamoDB will return an HTTP success code (200 OK), together with the results of any requested operations.

Any unsuccessful operation will result in an error code. For example, an error code such as HTTP 400 status code suggests a problem with the request such as an authentication error or a missing parameter. Error codes with HTTP 5xx suggest a problem that must be resolved by AWS, such as a transient error or an issue with the DynamoDB service, usually resulting in an HTTP 503 status code.

Next, let’s look at some common APIs as well as examine options to retrieve data from DynamoDB.

## More on DynamoDB APIs and Data Retrieval Options

As discussed earlier, DynamoDB exposes APIs to enable you to perform supported actions against your tables and the data. For a full list of API actions, refer to https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_Operations_Amazon_DynamoDB.html.

Some common APIs to be aware of include the following:

- PutItem – Allows you to create a new item or fully replace an old item. PutItem requests will consume WCUs. You can use a conditional put operation such as adding an item if a primary key doesn’t exist or updating an item only if a certain attribute value exists. This enables you to validate any updates to ensure that a new item does not replace an existing item by using a conditional expression such as the **attribute-not-exists** function. The operation will then only succeed if no matching item exists.
- UpdateItem – Allows you to edit existing or add new items if it does not already exist. You can use conditional update operations based on a certain expected attributed value. The use of this action is when you need to only update a few attributes of an existing item, unlike the PutItem action. The UpdateItem action can also be used to implement an **atomic counter**. This is a numeric attribute that is incremented each time you call the UpdateItem action regardless of whether the operation was a success or failure. This can be useful for various use cases such as tracking the number of visitors to your website if you can tolerate any overcounting or undercounting.
- GetItem – Allows you to return a set of attributes for an item when you specify a primary key or a primary and a sort key. GetItem is eventually consistent. If you require a strongly consistent read, you can set the ConsistentRead to true. Note, however, that a strongly consistent read will require additional RCUs and your application may experience some latency. You can also use ProjectExpression to retrieve only certain attributes.
- DeleteItem – Allows you to delete an item from your table. You can also use conditional delete operations. Note that if you wish to delete the table itself, then use the DeleteTable action.
- Batch Operations – Allows you to save in latency by reducing the number of API calls. Batch operations are more efficient as they are performed as parallel operations. Examples of batch operations include the following:
  - BatchWriteItem – Performs multiple puts or deletes in one or more tables. It can perform up to 25 item puts or delete operations. BatchWriteItem can transmit up to 16 MB of data and each individual item can be up to 400 KB. Note that you cannot use BatchWriteItem for updating items as any attempt to update the item will simply result in the original item being overwritten.
- `BatchGetItem` – Enables you to return attributes of one or more items from one or more tables. A single operation can retrieve up to 100 items of a total size of 16 MB of data. If the size limit is exceeded, the operation will result in partial results.

In addition to the API actions, there are two key options for retrieving data from the database – performing a scan or a query operation. You will look at the key differences between them in the next section.

## DynamoDB Scan versus Query

A scan operation will access every item in a table or secondary index before returning the item you are looking for. This means that the operation will need to review each item and its attributes on the table, making the entire process less efficient. This will result in a larger consumption of RCUs. You can reduce the number of attributes returned by using the `ProjectionExpression` parameter. For example, you can return only the make and model of a product in your scan requests, rather than all the attributes associated with the product items in a table.

Another option is to reduce the number of items returned using a `FilterExpression` where you filter the data returned based on specific values, for example, all phones that are manufactured by Apple. However, you would still have scanned every item on the table and thus consume RCUs. You can use the Limit parameter to define the maximum number of items or specify a maximum of 1 MB of data.

In addition, scan operations are performed sequentially. Parallel scan operations can be performed by providing the `Segment` and `TotalSegments` parameters. You should be aware that scan operations use eventual consistent reads when accessing data in a table by default. You can set the `ConsistentRead` parameter to `true` if you need a strongly consistent read operation.

With a **query operation**, you retrieve items on your table based on the primary key attribute and a specific value you are searching for. For example, you might wish to retrieve all data related to a specific employee by providing the employee ID (the likely primary key of an employee database). You can also use an optional sort key to refine the results. The query will return all attributes for the items but here again, you can use `ProjectionExpression` to restrict the attributes whose values are retrieved.

With query operations, because you specify the primary and optional sort keys, the operation will consume fewer RCUs compared to scan operations.
