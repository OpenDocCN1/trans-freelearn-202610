The preceding diagram illustrates how a rolling update will be completed. Assuming you have four nodes to update, you could start with two nodes and perform the updates on those nodes (resulting in them being taken out of service) as per Step 2. Once those nodes have been updated, the remaining two can be updated as per Step 4. In Step 5, all four nodes have been updated with the latest application version.

An important point to note here is that, during the update life cycle, some users may connect to the nodes that serve the newer version, whereas others will continue to experience the older version until those relevant nodes are updated. If this sort of inconsistency does not pose any issues, rolling deployments are a viable option for performing application deployments. Finally, there are no additional costs incurred in this strategy.

# Rolling with Additional Batch

With this deployment strategy, you avoid reduced availability (while waiting for some nodes to go through the application update process). This is achieved by deploying additional nodes to cover the ones that go through the application upgrade process, which results in you maintaining the same bandwidth throughput for your end users.
