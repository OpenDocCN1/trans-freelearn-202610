While the architectural design patterns work well, the synchronous design pattern does pose some risks. For example, imagine a scenario with hundreds of customers uploading images simultaneously. Images arriving at the S3 bucket simultaneously will likely trigger too many requests to the Lambda function, resulting in a backlog and possible failure to process some of those images. The lack of fault tolerance can then result in poor customer experience. To address this concern, decoupling the architecture so that frontend requests and backend processing can be handled asynchronously will yield a better design pattern, as depicted in Figure 15.3. An additional point to note is that you must ensure adequate write capacity units provisioned for your DynamoDB table (or opt for on-demand provisioning) to handle the coming write requests.

Figure 15.3 – Using Amazon SQS to decouple application architecture

As multiple users upload images to the S3 bucket, event notifications are triggered and sent to the SQS queue, where the messages are held for a duration. The retention period can be 1 minute to 14 days, with the default period being 4 days. The Lambda function is then configured to poll the queue for new messages and retrieve them at its own pace, ensuring that no image goes unprocessed. Note that, by default, the SQS message size is limited to 256 KiB. For messages larger than this, you must use the Amazon SQS Extended Client Library for Java or Python, where the message payload is hosted on an Amazon S3 bucket, and the SQS queue is used to host a reference to that payload.

In this design architecture, the S3 bucket is the message producer, and the Lambda function is the consumer.
