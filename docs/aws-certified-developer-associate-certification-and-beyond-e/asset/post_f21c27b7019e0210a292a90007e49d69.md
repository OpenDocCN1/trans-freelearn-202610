
## Continuous Integration

DevOps practice is when software code changes made by developers are merged into a release branch of a central repository. Developers must be encouraged to commit their code regularly. This ensures fewer integration issues since smaller code commits are more straightforward when resolving bugs and conflicts. Code changes must also be unit-tested before being pushed into the central repository.

Examples of repositories include AWS CodeCommit, GitHub, or Bitbucket. Once a developer commits changes to the application code and pushes them to a branch in the central repository, an automated build and test process should be initiated. This process creates one or more binaries and associated artifacts. Any necessary unit tests can also be incorporated at this stage, as per the diagram in Figure 12.2:

## Continuous Deployment

With continuous delivery, your changes are not necessarily deployed into production immediately. You may wish to integrate a decision process to ensure the output deployed is fully authorized. In essence, this stage is a business decision to roll out any changes here, which should not cause any disruptions because all tests and auditing have been carried out.

Continuous delivery ensures that software is ready to be released with manual approvals, while continuous deployment is the final phase of your CI/CD pipeline. It may include a fully automated process for software releases into production, as depicted in the diagram in Figure 12.5:

## Tools and Processes Used by DevOps Teams

Central to a DevOps team’s toolbox are CI/CD tools such as AWS CodeCommit, CodeBuild, CodeDeploy, and CodePipeline, which allow for the automation of software delivery processes. AWS CodeBuild is a service that compiles source code, runs tests, and produces ready-to-deploy software packages. CodeDeploy automates application deployments to various AWS services, such as Amazon EC2, AWS Fargate, and AWS Lambda. CodePipeline is a continuous delivery service that enables automation of the release pipelines for fast and reliable application updates.

Container services such as Amazon Elastic Container Service (ECS) and Amazon Elastic Kubernetes Service (EKS) are also pivotal, providing scalable and secure environments for application deployment with Docker and Kubernetes. They support a microservices architecture, a key tenet of the DevOps philosophy, allowing teams to build, deploy, and manage applications composed of small, independent, and loosely coupled services.

Moreover, teams often leverage IaC tools such as AWS CloudFormation, AWS Cloud Development Kit (CDK), or Terraform to define and provision AWS infrastructure using code. This practice allows for setting up and maintaining repeatable, version-controlled, and automated environments.

DevOps teams aim to create a culture and environment where building, testing, and releasing software can happen rapidly, frequently, and reliably. They leverage AWS tools to achieve efficiency, enhance security, and maintain scalability.

## AWS CodeCommit

AWS CodeCommit is a version control system that enables developers to collaborate on common application assets such as documents, source codes, and binary files. It follows the principles of Git for creating and managing source code.

> **Note**
> 
> Git is a distributed **version control system (VCS)** used to track changes in source code during software development. It is designed to handle everything from small to very large projects quickly and efficiently. Linus Torvalds created Git in 2005 for the development of the Linux kernel, and it has since become one of the most widely used VCSs in the world.

AWS CodeCommit offers several benefits aligned to Git. Users can easily create and manage repositories and branches, clone repositories to their local development environments, make changes as required, and then push them back to the CodeCommit repository.

AWS CodeCommit offers several features and benefits, including tight integration with other DevOps tools such as AWS CodeBuild and AWS CodeDeploy. This enables you to easily define and architect software release pipelines.

Key benefits of AWS CodeCommit include the following:

- Ability to collaborate with other developers: Each developer can perform pull requests, work on the other developers’ code, and then merge those changes back into the main branch when ready.
- Store your code securely: With encryption at rest using Amazon KMS and in transit.
- Scale version control projects: Can handle repositories with large numbers of files or branches, large file sizes, and extensive revision histories.
- Access control: Support for granting access using IAM roles and facilitating cross-account access capabilities.
- Use Git tools that are familiar to developers, using the same commands used by Git, such as `git clone`, `git add`, `git pull`, and `git push`, to name a few.

## AWS CodeBuild

AWS CodeBuild is a fully managed build service, making it a hassle-free process to build, test, and deploy your software. With AWS CodeBuild, you can create, test, and deploy your code in a secure, scalable, and cost-effective manner.

To get started, you must set up your AWS CodeBuild project. A build project details how to run a build, where to get the source code, which build environment to use, which build commands to run, and where to store the build output.

AWS CodeBuild can automatically detect changes to your code and start a build process. Every time you change your code, AWS CodeBuild will automatically initiate a build process to compile, test, and package it. The build process involves several steps, including compiling your code, running unit tests, and creating a deployable package.

To provide CodeBuild with a collection of build commands and settings to perform the build, you must supply some information in a file called `buildspec.yml`.

### More about buildspec.yml

This file must be written in YAML format and stored at the root of your source directory. You can, however, override the filename and its location. You can rename the file for different builds in the same repository, for example, one for staging and another for production. If you rename the file or want to store it in another location, you must instruct AWS CodeBuild when creating or updating the project, specifying the path to the file location relative to the value of the built-in environment variable, `CODEBUILD_SRC_DIR`.

Within the `buildspec.yml` file, you can define environmental variables either as standard plaintext variables or dynamically access variables from the AWS Systems Manager Parameter Store or AWS Secrets Manager.

In addition, you can define various phases of the build that comprise the following:

- `Install` - Installs the dependencies required for your build
- `Pre_build` - Commands to execute before the build
- `Build` - Commands to run to build the application
- `Post_build` - Any post-build operations, such as the creation of a `.zip` file output
