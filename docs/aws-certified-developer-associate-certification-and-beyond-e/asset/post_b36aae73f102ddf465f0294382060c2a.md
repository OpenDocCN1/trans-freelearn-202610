
When configuring filtering, you can define the scope of the filter policy with the FilterPolicyScope attribute. This lets you set the filtering scope by setting a value for either MessageAttributes, where the policy is applied to the message attributes, or MessageBody, where the policy is applied to the message body. The default is MessageAttributes, and if you do not set a policy scope for an existing filter policy, it also defaults to MessageAttributes.

By configuring subscriptions and using SNS's message filtering capabilities, subscribers selectively receive messages based on attributes defined at the topic level, which optimizes the processing and handling of incoming information.

Amazon SNS enables you to build distributed applications and achieve microservices architecture patterns. Combined with Amazon SQS, it facilitates a decoupling architecture solution that offers resilience and reliable message queuing services.

In the next section, you will learn about AWS Step Functions. This service provides a visual workflow to help you easily build distributed applications and design architectures for microservices.

## Designing Application Workflow with AWS Step Functions

Step Functions is a serverless orchestration service that makes it easy to sequence AWS Lambda functions and multiple AWS services into business-critical applications. Through workflows, you can design and run multi-step applications as a series of steps, ensuring they execute in order and as expected, handling errors, and providing consistent and reliable outcomes.

Let's use an example to understand where Step Functions can be used. When you complete a purchase on an e-commerce website, several different tasks (steps) must be performed before the product arrives at your doorstep. As illustrated in the following diagram in Figure 15.16, when the customer places an order, the inventory service must hold the product for the customer. This is then followed by the payment process run by another Lambda function. If payment is successful, the shipping steps are initiated, and yet another Lambda function may send a notification to the warehouse to package the product for dispatch to the customer. If the payment process fails, another Lambda function will be used to ensure that the product is released back into inventory so that other customers can purchase the product.

![](img/34ff9b5b5a734dae3450ab701e223c73_644_0.png)

Step Functions are useful when managing these events correctly and calling individual services, such as Lambda functions, to complete each step. The application's workflow is represented as event-driven steps using a graphical console or by using the Amazon States Language (ASL). Step Functions are based on a concept called state machines and tasks. State machines are essentially workflows for your application, represented by a series of steps with a start point and an endpoint. Each step in the workflow is then called a state. A state can accept data, modify it, and then output data.

There are two types of state machines:

- **Standard workflows** – Standard workflows execute exactly once and can run for up to 1 year. Each step in a standard workflow will execute just once. These are ideal for long-running workflows.
- **Express workflows** – These are designed for high-volume transactional workloads such as streaming data or IoT data ingestion. These workflows can run for up to 5 minutes.

State machines can be started using various services, such as API Gateway, EventBridge, Lambda functions, or even manually. In the next section, you will learn about the different states in a state machine.

### What Are States?

AWS Step Functions uses ASL to help you create a template to define your state machines, with a collection of states such as task states (to perform some work), choice states (determine which state to transition to), and fail states (if it needs to stop execution with an error). ASL is based on the **JavaScript Object Notation (JSON)** structured language.

States within your state machine can perform a variety of functions. Each state can receive an input, perform a certain action based on the input, and then pass out an output to other states. These are the available states:

- **Succeed state** – This is when a state completes an execution.
- **Fail state** – This stops the execution of a state machine and is marked as a failed state.
- **Wait state** – This is where the state will wait for a specific period or a specific date and time. It pauses the processing of the state machine for a specific time or until a specific date and time.
- **Choice state** – This is where the state machine can choose between different paths depending on an input. For example, you might want a different output depending on whether the credit card payment was accepted or declined in an e-commerce application.
- **Parallel state** – This allows you to add separate branches of execution depending on some input. A choice state can lead to a parallel state. So, for example, if the payment process is completed successfully, then you may wish to initiate multiple actions across parallel branches.
- **Map state** – This state accepts a list of things, such as a list of orders. You can run a set of steps against each item in that list.
- **Task state** – A single unit of work carried out by the state machine. It can be an activity; an invocation of a Lambda function; integration with another service such as DynamoDB, SNS, or SQS; or calling an external API. The state machine itself doesn’t do any work; it simply uses Task states, which integrate with other services to perform the actual work.

Next, we review the process of designing workflows with Step Functions.

### Designing Workflows with Step Functions

When designing an application workflow using AWS Step Functions, the process typically involves the following steps:

- 1. **Define workflow steps**: Identify and outline the tasks that must be performed. Each task is configured as a state within your Step Functions state machine.
- 2. **Create state machines**: Define the state machine using the AWS Management Console, AWS CLI, or SDKs. This involves writing a JSON-based definition that specifies the workflow steps, their order, input and output data, and branching logic based on the task outcomes.
- 3. **Handle task coordination**: Configure how data is passed between tasks and manage dependencies between tasks to ensure they are executed in the correct sequence and under the right conditions.
- 4. **Monitor and debug**: Step Functions provides tools to visualize workflows and monitor execution in real time. This can help you debug and optimize the performance of your application workflows.
- 5. **Implement error handling and retries**: Define retry policies for tasks that might fail and set up catch blocks to handle errors. This ensures that workflow execution can gracefully handle failures and exceptions. This is discussed in the next section.

### Error Handling with Step Functions

AWS Step Functions is designed to orchestrate your application workflow, through a series of steps incorporating the services of other AWS resources. An important concept to consider is how you handle errors that may occur in your workflow. Rather than having your application (for example, a Lambda function) process and handle errors, you can offload such tasks to Step Functions. This has the benefit of streamlining your application code and enabling Step Functions to maintain a history of retries and error processing.

Errors can occur for several reasons, such as issues with state machine definition rules, where a no-matching rule for a Choice state can trigger the error. Another reason for errors is exceptions in your Lambda function that result in task failures, or even network partition events known as transient issues.

Step Functions identifies errors using the Amazon States Language, which is made up of strings using the `States.` prefix. These strings form error names, some examples of which are as follows:

- `States.TaskFailed`: A Task state failed when executing
- `States.Timeout`: The Task state ran for longer than the TimeoutSeconds value or failed to send a heartbeat for a period that exceeded the HeartbeatSeconds value
- `States.Permission`: The Task state failed due to lack of permissions
- `States.ALL`: This is a wildcard to match any known error name
