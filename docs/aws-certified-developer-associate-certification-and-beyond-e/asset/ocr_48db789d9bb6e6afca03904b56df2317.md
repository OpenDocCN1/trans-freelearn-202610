Unlike other engines on Amazon RDS, the storage on Aurora is elastic. This means that when you delete data, the space allocated for that data is freed. Storage is managed separately from the Aurora instances, allowing you to add instances that connect to the existing shared storage volume.

Like Amazon RDS, Amazon Aurora can only have one master instance at a time – this is the instance where writer operations to the database can be performed. In addition to the master, Amazon Aurora can have up to 15 read replicas all configured with replication of data from the master. This means that automatic failover is available in the event of the master instance. Another point to note is that your read replicas can provide cross-region support.

To facilitate the seamless failover of your master instance, Amazon Aurora presents endpoints that are DNS addresses to connect to for writing to and reading from the database. The following are the endpoints offered on Amazon Aurora:

+   - **Cluster endpoint (writer endpoint):** This is the endpoint that would be presented to any application needing both write and read access to the database. This endpoint points to the current primary instance and is capable of all write operations including **Data Definition Language (DDL)** statements.
+   - **Reader endpoint:** This is designed to provide load-balancing support for read-only requests to the DB cluster. This endpoint should be used by any application that only needs to perform read queries against the database. The reader endpoint only connects to the read replicas and so frees up the primary instance.
+   - **Custom endpoint:** This is an endpoint you define by selecting the target instances of your choice. You can choose a selection of instances based on various factors, such as by application.
+   - **Instance endpoint:** Each DB instance has its own endpoint address as well. This can be used to give direct control over connections to the DB cluster.

Now that you have learnt about Amazon Aurora at a high level as well as covered relational databases, it’s time to look at how you can improve application and database performance using in-memory caching engines. In addition, relational databases should be used to store data for the longer term, however, applications tend to also store and require access to temporary data such as session states or gaming leaderboards. An in-memory caching engine can be a more cost-effective way to manage this type of data than traditional relational databases.

# Caching Data with Amazon ElastiCache

Amazon ElastiCache is an in-memory caching engine designed to help improve latency and throughput for read-heavy workloads that don’t change too frequently. AWS offers two fully managed in-memory engines – Redis and Memcached.

Amazon ElastiCache can be used to provide in-memory caching services for relational databases such as Amazon RDS.
