# # API Gateway Integrations

API Gateway enables you to publish and manage your APIs at scale. It is the front door to your backend services and resources. Clients connect to the API using an endpoint DNS name. It acts as an intermediary between your clients and those backend services, called integrations, enabling those services to fulfill requests made through those API calls.

API Gateway offers the flexibility to transform requests and responses as they flow through the service. This is particularly useful when your backend services require specific input formats or when you need to transform the output before sending it back to the client. By utilizing **Velocity Template Language (VTL)** templates, you can customize how the data is formatted and processed.

When your clients make a request to a backend service, such as retrieving a list of cryptocurrency recommendations as per the example illustrations discussed in *Figure 8.8*, that request needs to be authorized, validated, and, if necessary, transformed into a format that the backend service can understand. Similarly, the response is the output the backend service provides, which may need to be transformed and prepared before it can be sent back to the client.

Depending on your use case and choice of integration types, you may pass the data from the client to the backend service as is without any transformation, which is known as proxying.

There are various integration types, and choosing a specific type will depend on the integration endpoint and whether you need to transform data or pass it as it is. The following are the various integration types:

+   - **AWS**: This integration type exposes AWS service actions. You must configure both the integration request and response. You must also set up the required data mappings from the method request to the integration request and then the integration response to the method response. You can also use this integration type for the Lambda function, but once again, you must configure how the data incoming from the client is mapped to the endpoint and vice versa.
+   
+   - **AWS_PROXY** (Lambda): This type of integration enables you to invoke a Lambda function using a streamlined integration setup. You do not need to set up the integration request and response, and data is passed from the client to the integration endpoint as is. Lambda must be able to interpret what gets sent to it and then respond in a format that API Gateway expects as the response.
+   
+   - **HTTP**: This is also known as HTTP custom integration; you must configure the integration request and response. This is because the request might not be in the same format the endpoint expects, so some data conversion is required.
+   
+   - **HTTP_Proxy**: Similar to AWS_Proxy, this is a streamlined setup on a single API method. You do not need to configure the integration request and response. The data in the request is passed through from the client to the HTTP endpoint, and the response is passed from the endpoint to the client as is.
