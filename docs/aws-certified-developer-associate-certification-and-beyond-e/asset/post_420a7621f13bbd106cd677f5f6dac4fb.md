## All about Primary Keys and Sort Keys

Every item in a DynamoDB table requires a unique primary key. This key, also known as the partition key, enables you to uniquely identify an item. DynamoDB supports two types of primary keys:

- **Partition key** – This is simply the primary key that serves both as an attribute to uniquely identify an item and as an input to an **internal hash function** that is used to determine the physical storage location where the item is stored on AWS. Hence it is also called the partition key. If a table only has one partition key, no two items can have the same key.
- **Partition key and sort key** – This is also known as a composite key because it is composed of two attributes – the partition key and the sort (also known as the range key). The partition key is used to also determine the location of the item using DynamoDB’s internal function. With a composite key configuration, you can have multiple items with the same partition key if the sort key uniquely identifies one item. Thus, the sort key that is associated with a specific partition key is also stored in the same location as determined by the hash function.

As an example, consider a music database where the artist name can be the partition key and the song title the sort key. If you perform a query by simply supplying the artist’s name, you will get a list of all songs by that artist. If you also specify the song title of a track, you retrieve just that item.

In addition to DynamoDB’s standard primary and composite keys, you can also configure one or more secondary indexes. A secondary index enables you to query a table using alternative keys that offer greater flexibility, without having to scan the entire table, which would consume a large amount of read throughput. Secondary indexes contain a subset of the base table’s attributes. This is done by projecting specific attributes from the base table to the index. DynamoDB supports two types of indexes:

- **Global secondary index (GSI)**: This is an index that has a separate partition key and a sort key from those on the table. The index is classified as a global index because queries can span across all data in all partitions of the table. There are no limitations on the size of the index, and it can be configured with its own throughput settings for all read and write operations. In addition, you can create this index not only when you launch the table but also at any time later (which you cannot do with a local secondary index). You can also have up to 20 GSIs.
- **Local secondary index (LSI)**: This is an index with the same partition key as the table but a different sort key. The indexed items are limited to 10 GB per partition and the index can only be created at the time of table creation. You can return attributes from your queries that are not projected into the index. You must note that the capacity requirements for your LSI are inherited from the primary table’s configuration. Finally, you can have a maximum of five LSIs per table.

LSIs are ideal when you need strong consistency in your query results. In most cases, however, GSIs are preferred.

Using the previous example of a music database, you could use the partition and sort keys, which would consist of the artist and song title respectively. However, you may also wish to query your collection based on genre or album title. Here, a GSI would come in handy.

For the index, you could classify the genre as the alternative partition key and the album title would be the sort key.

Note that when you confirm the secondary index, DynamoDB will maintain the index automatically. As you add and delete items from the table, DynamoDB will add and delete any relevant key attributes in the index.

Now that you have understood the fundamentals of the primary (partition) keys, sort keys, and secondary indexes, you can next explore how DynamoDB provisions capacity for your application.

## DynamoDB Capacity Provisioning

When provisioning capacity for DynamoDB, you do not need to specify the instance type or size to define the amount of storage required, as you normally do with Amazon RDS. Instead, AWS fully manages and provisions the required capacity based on your application read and write throughput requirements. To that effect, you only need to define read and write capacity units, which will be discussed next.

Amazon DynamoDB offers two capacity modes that allow you to determine your capacity requirements:

- **On-demand** is a flexible billing approach that enables you to provide the required capacity as your application demands change. Amazon DynamoDB will provide the necessary capacity and no capacity planning is required. This mode is ideal when:
  - You are unsure of the workload types you plan to run
  - Traffic to your database is unpredictable
  - You want to be billed on a **pay-as-you go model**

- **Provisioned** – in this mode, you define the number of reads and writes per second required by your application. This mode is the default mode when you create a new table. You can also configure the table with auto-scaling to adjust the provisioned capacity as traffic demand changes. This mode is ideal when:
  - You know your application traffic usage patterns
  - You have consistent traffic that gradually increases
  - Capacity forecasting is possible

An additional point about provisioned capacity is that you can purchase reserved read and write capacity at a discount to reduce costs. You can switch from one mode to the other once every 24 hours.

When using the provisioned mode, you must define the **read capacity units (RCUs)** and **write capacity units (WCUs)**. Using these parameters, DynamoDB will provision the table with the required infrastructure to support your capacity requirements. The RCU and WCU values enable DynamoDB to ensure you have the right amount of infrastructure resources to meet the application’s demands. Let’s examine how DynamoDB consumes RCUs and WCUs:

- **Read requests:**
  - If you use strongly consistent reads, then each item of up to 4 KB requires **one RCU**.
  - If you use eventual consistent read, then each item of up to 4 KB in size requires **½ RCU**.
  - For transactional read requests for an item up to 4 KB in size, you will need two read request units. Transactional read and write requests are different from standard read/write requests in that they guarantee that all operations contained in a single transaction set either succeed or fail as a set.

> **More on Read Consistency**
> 
> With RCUs, you need to decide whether you want strongly consistent reads or eventual consistent reads. With eventual consistent reads, when you perform a read request, the response may not result in recently completed write operations. If you repeat the query, you are likely to retrieve updated data. You get the most up-to-date data with strongly consistent reads, reflecting updates from all previous write operations. The latter is more expensive and is not supported on GSIs.
> 
> To use strongly consistent reads, you must set the `ConsistentRead` parameter to `True` in your API calls for your `GetItem`, `BatchGetItem`, query, and scan requests.
> 
> For example, suppose your item size is 8 KB. In that case, you will require two RCUs for strongly consistent reads, one RCU for eventually consistent reads, and four RCUs for transactional read requests.

- **Write requests:**
  - A write request for an item of up to 1 KB in size requires one WCU
  - A transactional write request of up to 1 KB in size requires two WCUs

> **More on Write Capacity**
> 
> For example, if your application writes at a rate of 100 writes per second and each item is 4 KB in size, then you would require 400 WCUs (100 x (4KB / 1KB)).
