There are some important caveats to setting up VPCs as follows:

- VPC peering does not support transitive routing. In the preceding diagram, the New York VPC is peered with both the London VPC and the Mumbai VPC. However, this connection alone will not allow resources in the London VPC to send traffic to resources in the Mumbai VPC. You would need to establish an explicit peering connection between the VPCs in London and Mumbai if you needed them to access each other's resources.
- Edge-to-edge routing through a gateway is also not supported. This means that if the Mumbai VPC has access to an internet gateway, the VPC in London will not be able to use that gateway to access resources on the internet.
- VPC peering connections between VPCs that have matching or overlapping IP address ranges are not permitted.

AWS offers several services where resources need to be provisioned inside a VPC. These include EC2 instances and RDS databases. There are multiple services, however, where the resources provisioned are not within a VPC. These include SNS topics, S3 buckets, DynamoDB tables, and many more. You can call these public services, while accessing these services from resources within a VPC often requires internet access.

EC2 instances in a VPC will need to traverse the internet to get access to these public AWS services. This often means that the VPC requires an internet gateway and if the EC2 instance is in a private subnet, then it also requires a NAT gateway.

You may, however, wish to prevent such traffic from your EC2 instances traversing the public internet just to get back into the AWS ecosystem to access a resource such as a DynamoDB table. We look at VPC endpoints next, a feature that can help us achieve this configuration and address concerns related to security and compliance.

## Securing Connectivity between VPCs and Other Public AWS Services

Many services allow you to create resources that require a VPC. EC2 instances and RDS databases are examples. Other AWS services do not deploy resources within your VPC. For example, Amazon S3 buckets are in public AWS environments and not within your VPC. If your EC2 instances require access to these buckets, perhaps to upload or download objects, then you need to consider how network traffic from your instance reaches those buckets. As a default network configuration, your VPC will have an internet gateway. This means traffic from those EC2 instances must first traverse the internet gateway to access S3 buckets in public AWS space.

You can access various AWS services and resources from your EC2 instances deployed within a VPC. Often, this requires traffic to traverse from the VPC to the internet and back in again to those public AWS services. For EC2 instances located within private subnets, you must also deploy a NAT gateway to facilitate internet connectivity. While this is a perfectly viable solution, you may be concerned about traffic traversing the public internet before reaching resources created using other public AWS services. Such concerns could be related to security or costs associated with enabling internet-bound access, such as using a NAT gateway.

AWS offers an alternative known as VPC endpoints. These endpoints can enable you to connect resources in your VPC to resources in other VPCs and within the AWS public domain over the private AWS backbone network rather than traversing the public internet.

You can create two types of VPC endpoints:

- **Interface:** Interface endpoints enable you to connect to AWS services from your VPC using one or more elastic network interfaces with private IP addresses that serve as an entry point to that service. Traffic over the interface endpoint takes place over AWS PrivateLink. Examples of services that you can connect to over interface endpoints are Amazon SNS and SQS.
- **Gateway:** Gateway endpoints are used only for Amazon S3 and DynamoDB. They use specific IP routes in the Amazon VPC route tables, which are prefix lists with destinations defined for those services. Gateway endpoints do not enable AWS PrivateLink.

Next, let’s examine how you can connect your VPCs to external networks, such as your on-premises network.

## Connecting VPCs to external networks

Most companies have an on-premises network that they would like to connect to their AWS accounts and resources. There are multiple options to achieve this depending on the type of tasks that are planned to be carried out, and the amount of bandwidth required.

Options to connect your private on-premises network to the AWS cloud include the following:

- **Site-to-Site Virtual Private Network (VPN)**: This allows you to create a relatively inexpensive IPsec VPN connection between your VPC and your remote network. With this, traffic is encrypted while it traverses the public internet.
- **Direct Connect**: This is a dedicated fiber optic cabling network between your on-premises office and your local Direct Connect Partner. Traffic is then routed over private networks into the AWS platform, and it never traverses the public internet. AWS Direct Connect offers dedicated and higher bandwidths than traditional VPN connections.

AWS Direct Connect will sometimes require a lead time to be set up as the underlying cable infrastructure may first need to be provisioned between your location and the Direct Connect Partner.

Now that you have understood the key components of VPCs and examined their various security and networking components, it is also imperative that you are able to monitor the types of traffic that flow into and out of your network. AWS provides several monitoring tools to help you. One such tool you might find yourself utilizing is VPC Flow Logs, which you will explore next.

## Monitoring Traffic with VPC Flow Logs

VPC Flow Logs is a service designed to help you monitor IP traffic entering and leaving the entire VPC, a specific subnet, or a specific network interface such as the virtual network card attached to one of your EC2 instances.

This data can then be ingested into Amazon CloudWatch Logs, Amazon S3, or Amazon Kinesis Data Firehose for further analysis and storage. VPC Flow Logs can be used to do the following:

- Identify overly restrictive security group rules – for example, when certain types of traffic are not reaching your resources
- Monitor the type of traffic that reaches your instances – for example, to help you determine if that traffic is authorized or malicious
- Identify the direction of the traffic to and from the resources in your AWS account

Your flow log data is recorded as flow log records and can be pushed out to a CloudWatch Logs group created beforehand. You will also need to set up the necessary permissions in the form of an IAM role to enable your flow logs to be written to the CloudWatch Logs group.

When setting up VPC Flow Logs, you need to define the following:

- The resource you want to create the flow log for (e.g., the entire VPC, a subnet, or a network interface)
- The type of traffic you wish to capture (accepted traffic, rejected traffic, or all traffic)
- The destinations for your flow log data
