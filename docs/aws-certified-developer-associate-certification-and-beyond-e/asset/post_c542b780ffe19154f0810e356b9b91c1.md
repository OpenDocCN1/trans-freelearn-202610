
# Amazon EventBridge and AWS CloudTrail

As you record CloudTrail events, you may wish to react to certain specific event types by triggering a Lambda function or sending out a notification alert. In this case, you can integrate Amazon EventBridge with CloudTrail to react to specific API calls made by an AWS service, which is recorded by AWS CloudTrail.

For example, you may wish to trigger an email alert generated by Amazon SNS to notify an administrator whenever a user stops an EC2 instance. This design architecture can be configured as per the diagram in Figure 16.9.

Next, you must configure an SNS topic to which EventBridge will send alerts. The SNS topic will need subscribers, which, in this case, would be an administrator’s email address, and the type of notification would be an email notification.

Next, you must configure an EventBridge event rule. For this, you must configure the event source as EC2 and the event type as AWS API Call via CloudTrail. In this example, you can also capture specific operations, which, in this case, would be the StopInstances API call. As part of your configuration, you must also configure the target, which would be the SNS topic you created earlier. This will ensure that when the event of someone stopping any EC2 instances is captured, it triggers a push notification to the SNS topic, which sends the email out to subscribers.

## Distributed Tracing with AWS X-Ray

AWS X-Ray is a powerful service that helps developers analyze and debug distributed applications, such as those built using a microservices architecture. X-Ray provides end-to-end visibility into application requests as they travel through various services, offering insights into the application’s performance and operational health.

AWS X-Ray is made up of various components, as follows:

- **Segments:** AWS X-Ray receives data as segments from resources running in your application. Segments provide detailed information about the requests made in your traces, including host IP, start and end times, duration, and request methods such as POST and GET requests. Segments also allow you to identify any issue such as errors, faults and exceptions. In the following screenshot, you can see a typical segment detail for a trace:

![](img/34ff9b5b5a734dae3450ab701e223c73_677_0.png)

Figure 16.13 – Segment details

- **Annotations** are key-value pairs to add user-specific custom attributes to your trace data. They are indexed and can be used for queries using filter expressions. You can use annotations to provide more context to your searches and create groups. By adding these custom attributes as annotations, you can use filter expressions to limit the returned results based on these attributes. You can use them to group traces within the console or when you call the GetTraceSummaries API.
- **Metadata** consists of key-value pairs that are not indexed. The values can be of any type and comprise objects and lists. You can use metadata to record additional data to store in your traces but do not require it for searches.

Ultimately, AWS X-Ray is an excellent tool for monitoring your application, debugging traces, and retrieving service maps and other data by processing traces. It can also help you identify and troubleshoot the root cause of performance issues and errors within a microservices architecture and identify bottlenecks in your application stack.

## Project Task – Create a VPC Flow Log

The Todo List application is deployed in a VPC across a fleet of AWS Fargate container services. The application running on those containers makes calls to an Amazon RDS database also hosted in the same VPC in the private subnets.

The VPC has been configured by following specific best practice guidelines, incorporating security protocols and rules to ensure that only specific types of traffic are permitted into the network.

In this project exercise, you will create a VPC flow log and have the log data ingested into CloudWatch Logs. VPC Flow Logs enables you to capture IP packet information going to and from network interfaces in your VPC. The information provides insights into the source of the IP traffic, the destination IP address, the source port, the destination port, the protocol used, and whether the packet was accepted or rejected.

When you publish your flow logs into CloudWatch Logs, the log data is published to a log group. Each network interface in the VPC has a log stream used to capture flow log records in the log group. VPC Flow Logs can help you identify potentially malicious traffic or situations where you might have overly restrictive security groups, forming part of your overall troubleshooting process for your application stack.

### Project Task 16.1 – Create an IAM Role for Publishing Flow Logs to CloudWatch Logs

In this project task, you must create an IAM role that enables the VPC flow logs to be published in CloudWatch log groups:

- 1. Ensure that you have downloaded the IAM permission and trust policies from our GitHub repository, as per the *Technical Requirements* section.
- 2. In the AWS Management Console, use the search bar at the top of the web page to find and navigate to the IAM dashboard.
- 3. From the left-hand menu, select **Policies**.
- 4. In the right-hand pane, click the **Create policy** button.
