## 面向大众的大数据挖掘

在企业环境中实现一个满足特定业务需求的大数据挖掘平台并非易事。虽然构建大数据平台相对简单，但这些工具的新颖性对习惯于传统数据挖掘方法的业务用户来说，在采用上构成了挑战。这最终决定了该平台在组织内部成功的程度。

本章介绍大数据分析的一些显著特征，这些特征对分析工具的实践者和最终用户都很重要。将包括以下主题：

- 什么是大数据挖掘？
- 企业中的大数据挖掘：
  - 构建用例
  - 解决方案的利益相关者
  - 实施生命周期
- 大数据挖掘中的关键技术：
  - 选择硬件栈：
    - 单节点/多节点架构
    - 基于云的环境
  - 选择软件栈：
    - Hadoop、Spark和NoSQL
    - 基于云的环境

## 什么是大数据挖掘？

大数据挖掘是大数据分析两大类别中的第一类，另一类是预测分析，我们将在后续章节中介绍。简单来说，大数据挖掘指的是处理大规模数据集的整个生命周期，从采购到实施相应工具来分析这些数据集。

接下来的几章将阐述组织内开展的任何大数据项目的一些高层特征。

## 企业中的大数据挖掘

在中等规模到大型企业中实施大数据解决方案可能是一项艰巨的任务，因为需要考虑的因素极其多变且多样化，其中最重要的是确定该解决方案将解决哪些具体的业务目标。

## 为大数据战略构建理由

也许大数据挖掘最重要的方面是确定平台将解决的适当用例和需求。任何大数据平台的成功在很大程度上取决于在业务部门中找到相关问题，这些问题将为部门或组织带来可衡量的价值。用于收集大量传感器或流数据的解决方案的硬件和软件栈，与用于分析大量内部数据的解决方案相比，会有实质性的不同。

以下是一些建议的步骤，根据我的经验，这些步骤在构建和实施企业大数据战略方面特别有效：

- **谁需要大数据挖掘：** 确定哪些业务部门能从大数据挖掘解决方案中获益最多，是此过程的第一步。这通常涉及那些已经在处理大型数据集的部门，这些部门对业务很重要，并且直接影响收入；优化他们在数据访问或信息分析时间方面的流程，将对日常工作流程产生影响。例如，在制药组织中，这可能包括商业研究、流行病学、卫生经济学与结果研究。在金融服务组织中，这可能包括算法交易台、量化研究，甚至后台部门。

- **确定用例：** 在前一步骤中确定的部门可能已经有一个能够令人满意地满足该群体需求的平台。在多个用例和部门（或它们的集合）之间进行优先级排序，需要个人熟悉各业务部门正在进行的工作。

大多数组织遵循层级结构，同事之间的互动很可能主要沿着**等级界限**进行。确定有影响力的分析用例需要实践者和利益相关者之间的密切合作；也就是说，既需要负责监督部门的管理层，也需要进行实际分析的工作人员。业务利益相关者可以阐明其业务的哪些方面将从更高效的数据挖掘和分析环境中受益最多。实践者则提供对实际操作层面存在的挑战的洞察。将运营和管理方面结合起来以确定最佳结果的渐进式改进，必定会带来更快更好的结果。

- **利益相关者的支持：** 利益相关者的支持——换句话说，决策者和能够做出独立预算决策的人之间的共识——应该在开始处理用例之前建立。一般来说，应该争取多个支持以备冗余，这样就会有一个主要和次要来源池，可以为将任何早期胜利扩展到更广泛的目标提供适当的支持和资金。支持过程不一定是确定性的，在大多数情况下这可能无法实现。相反，就某个用例将带来的价值达成总体共识，有助于建立一个基准，在用例成功执行后可以加以利用。

- **早期成功与投入产出比：** 一旦确定了合适的用例，找到投入产出比最优的用例就至关重要。一个相对较小的用例，可以在较短的时间内以较小的预算实施，以优化特定的关键业务功能，这有助于展示早期成功，从而为所讨论的大数据解决方案增加可信度。我们无法精确量化这些无形的特性，但我们可以假设：

![](img/8ededb1e0b69e85687f6e488d1044b79_41_0.png)


在这种情况下，*努力*是实施用例所需的时间和投入。这包括诸如采购解决方案所需的硬件和/或软件需要多长时间、实施解决方案所需的资源或等价的*人时*，以及整体运营开销等方面。相对于实施可能涉及长期采购和组织风险分析的商业解决方案，开源工具可能具有更低的进入门槛。同样，一个跨部门、需要多个已经参与其他项目的资源投入时间的项目，其持续时间可能比由单个部门员工执行的项目更长。如果净努力足够低，只要不影响项目质量，还可以并行运行多个任务。

- **利用早期成功：** 在早期成功阶段，一个或多个项目的成功实施，往往为制定更宏大的大数据分析平台战略奠定基础，这一战略远不止满足单个部门的需求，而会产生更广泛的组织级影响。因此，早期成功是向受众确立大数据价值的第一步，但也是关键的一步，无论受众是否对其可行性和相关性持怀疑态度。

## 实施生命周期

如前所述，实施过程可能涉及多个步骤。这些步骤通常具有迭代性，需要试错法。这需要相当的毅力和坚持，因为大多数工作都会以不同程度的成功和失败为特征。

在实践中，大数据战略将涉及多个利益相关者，协作方法往往能产生最佳结果。业务发起人、业务支持部门以及IT与分析部门是三大类利益相关者，它们共同构建一个恰当的统一解决方案，在预算和IT能力允许的范围内满足业务需求。

## 解决方案的利益相关者

大数据解决方案利益相关者的具体性质是主观的，会因用例和问题领域而有所不同。一般来说，以下可视为高层级的表示：

- **业务发起人：** 为项目提供支持和/或资金的个人或部门。在大多数情况下，该实体也是解决方案的受益者。
- **实施小组：** 从实际操作角度实施解决方案的团队。这通常是大多数公司的IT或分析部门，负责平台的设计和部署。
- **IT采购：** 大多数组织的采购部门负责审查解决方案，从组织角度评估其竞争性定价和可行性。符合内部IT政策以及评估许可成本等其他方面，是采购部门提供的一些服务，尤其是针对商业产品。
- **法律事务：** 所有产品，除非是内部开发的，几乎肯定都会附带相关使用条款和条件。开源产品可能具有多种属性，定义了使用的许可性和限制性。Apache 2.0、MIT 和 BSD 等开源软件许可证通常比 GNU GPL（**通用目的许可证**）更为宽松。对于商业解决方案，过程更为复杂，因为需要分析供应商特定协议，并且根据许可条款和条件的性质，可能需要很长时间来评估和获得批准。

## 实施方案

解决方案的最终实施是实施小组、业务受益者和辅助部门之间协作的结晶。如“早期成功”部分所述，大多数小型项目从开始到结束所需时间通常在3到6个月不等。较大的项目可能需要数月至数年才能完成，其特点是在实施和部署阶段采用敏捷产品管理框架，逐步增加功能。

## 大数据平台的技术要素

到目前为止，我们的讨论一直聚焦于企业环境中大数据解决方案设计和部署的高层特征。现在，我们将把注意力转向这类工作的技术方面。在适当的时候，除了讨论主题的技术基础之外，我们还会加入一些高层次的说明。

在技术层面，主要有两个考量：

- 硬件栈的选择
- 软件和BI（**商业智能**）平台的选择

在最近2-3年中，企业越来越多地将其流程迁移到基于云的环境，作为内部基础设施的补充解决方案。因此，基于云的部署变得极为普遍，因而增加了关于本地部署与云部署的额外章节。请注意，术语 *On-premises*（本地部署）可以与 **In-house**（内部）、**On-site**（现场）以及其他类似术语互换使用。

![](img/8ededb1e0b69e85687f6e488d1044b79_45_0.png)

> 你经常会听到 **On-premise** 被用作 *On-premises* 的替代词。正确的术语是 **On-premises**。《钱伯斯词典》将 **premise** 定义为 *premise 名词 1（也作 premises）被假定为真实的事物，作为进一步陈述的基础*。另一方面，**premises** 是一个用来表示建筑物（以及其他事物）的术语，并且可以说更有意义。

## 硬件栈的选择

硬件的选择通常取决于所选择的解决方案类型以及硬件的部署位置。正确的选择取决于几个关键指标，例如数据类型（结构化、非结构化或半结构化）、数据规模（GB、TB 或 PB），以及在一定程度上数据更新的频率。最佳选择需要对这些变量进行正式评估，本书后面将对此进行讨论。从高层来看，我们可以总结出三种广泛的硬件架构模型：

- **多节点架构：** 这通常涉及相互连接并按照多节点或分布式计算原理工作的多个节点（或服务器）。多节点架构的典型例子是 Hadoop，其中多台服务器保持双向通信以协调作业。其他技术，如 Cassandra 这类 NoSQL 数据库和 Elasticsearch 这类搜索与分析平台，也基于多节点计算架构原理运行。它们中的大多数利用*商用服务器*，这是按企业标准相对低端机器的另一种名称，这些机器协同工作以提供大规模数据挖掘和分析能力。多节点架构适用于托管 TB 级及以上的数据。
- **单节点架构：** 单节点是指在单一服务器上完成计算。随着多节点计算工具的出现，这种方式相对不常见，但与分布式计算架构相比仍保留着巨大优势。*分布式计算的谬误*概述了一系列与分布式系统实现相关的断言或假设，例如网络的可靠性、延迟成本、带宽以及其他考虑因素。如果数据集是结构化的、主要包含文本数据，并且规模在1–5 TB 量级，那么在当今的计算环境中，完全可以像后面章节所展示的那样，使用特定技术在单节点机器上托管这些数据集。
- **云架构：** 在过去几年中，业界出现了大量基于云的解决方案。这些解决方案通过提供一个平台，使得根据当前任务需求按需配置硬件资源变得极其容易，从而大大降低了大数据分析的门槛。这实质上减少了采购、管理和维护物理硬件以及在内部数据中心设施中托管这些硬件所带来的巨大开销。

亚马逊网络服务（Amazon Web Services）、微软的 Azure 以及谷歌计算环境（Google Compute Environment）等云平台允许企业配置数十到数千个节点，成本低至每个实例每小时1美分。

随着云供应商相对于传统实体托管设施的主导地位日益增强，出现了若干用于管理客户云环境的补充服务。

例如云管理公司，如提供大数据即服务解决方案的 Altiscale，以及促进多种云解决方案选择与管理的 IBM Cloud Brokerage。

![](img/8ededb1e0b69e85687f6e488d1044b79_46_0.png)

**硬件成本的指数级下降：** 在过去几年中，硬件成本呈指数级下降。举例来说，根据 Statistic Brain 的研究，2013 年硬盘存储的成本约为每GB 4美分。相比之下，2000年时每GB为7美元，而在80年代初每GB超过10万美元。鉴于商业软件的许可成本很高，往往可能超过硬件成本，因此分配足够的预算来采购性能足够的硬件解决方案是合理的。软件需要适当的硬件才能提供最佳性能，因此，对硬件选择给予同等重视与选择合适的软件同样重要。





## 软件栈的选择

数据挖掘的软件栈选择因具体情况而异。最受欢迎的专门用于数据挖掘的选项如下所示，同时也列出了一些备选方案，虽然知名度不如前者，但在处理大规模数据集方面同样出色：

- **Hadoop 生态系统：** 大数据术语 arguably 起源于 Hadoop 在流行领域的出现。Hadoop 生态系统由 Apache 软件基金会旗下管理的多个项目组成。Hadoop 支持大数据领域中众所周知的几乎所有各种类型的数据集——例如结构化、非结构化和半结构化。其蓬勃发展的辅助工具生态系统不断增加新功能，以及公司竞相展示下一个大数据新事物的快速发展的市场意味着 Hadoop 将在可预见的未来持续存在。除了大型生态系统中存在的项目外，Hadoop 有四个主要组件，分别是：
  - **Hadoop Common：** 支持其他 Hadoop 模块的通用工具
  - **Hadoop 分布式文件系统 (HDFS™)：** 一种分布式文件系统，提供对应用程序数据的高速吞吐访问
  - **Hadoop YARN：** 用于作业调度和集群资源管理的框架
  - **Hadoop MapReduce：** 基于 YARN 的大规模数据集并行处理系统

- **Apache Spark™：** Apache Spark 最初是在加州大学伯克利分校 AMPLab 构想的一个多节点计算框架项目，作为一个平台提供无缝接口来运行并行计算并克服 Hadoop MapReduce 框架的局限性。特别是，Spark 内部利用了 **DAG—有向无环图——** 的概念，这表明其具有将一组操作优化为更少、或计算效率更高的操作集的功能。此外，Spark 提供了多个 **API—应用程序编程接口—** 给常用的语言，如 Python（PySpark）和 Scala（原生可用接口）。这消除了进入 Hadoop 空间的障碍之一，即必须掌握 Java 知识。

## 总结

在本章中，我们对大数据以及在企业中实施大数据解决方案的一些组件进行了高层次概述。大数据需要选择最佳的软件和硬件栈，这项工作并非易事，尤其因为行业中存在数百种解决方案。虽然大数据战略的主题可能被认为更适合管理层而非技术受众，但理解其细微差别至关重要。

请注意，如果没有适当的、定义良好的战略以及相应的高层支持，IT 部门在提供成功解决方案方面的能力将受到限制。此外，解决方案，包括硬件-软件栈，应该能够由现有的 IT 资源得到充分管理和支持。大多数公司会发现，为大数据实施招聘新员工是必不可少的。由于此类实施需要评估各种要素——业务需求、预算、资源和其他变量，因此根据规模和范围的不同，通常需要数月到一年甚至更长时间的提前期。

这些主题将在后续章节中深入讨论，本节作为该主题的初步介绍。
