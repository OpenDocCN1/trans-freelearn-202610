
The `./` path prefix matters. It tells Bash to look for the script in the current directory rather than searching for a system command with the same name.

At this point, you have already learned something important: scripts run in the same shell environment you have been using interactively. If your script fails, the commands inside it would probably fail if you typed them manually as well. This makes debugging much less mysterious.

## Adding logic to scripts

You can add simple logic to make scripts more useful. For example, variables let you avoid hard-coding values, like setting a `PORT` variable to `8000` and then referencing it with `$PORT` in a command:

```
#!/usr/bin/env bash
PORT=8000
echo "Starting server on port $PORT"
python manage.py runserver "$PORT"
```

On some systems, you may need to use `python3` instead of `python`.

You can also stop a script when something goes wrong. The following line tells Bash to exit immediately if any command fails:

```
set -e
```

Placed near the top of the script, this prevents later commands from running in a broken state, which is especially useful in build or deployment scripts.

For safer scripts, use the full safety preamble:

```
set -euo pipefail
```

Note the following about the preceding command:

*   `-e`: Exit immediately if any command fails
*   `-u`: Exit if you use an undefined variable (this catches typos)
*   `-o pipefail`: A pipeline fails if any command in it fails

This combination prevents entire categories of subtle bugs. Place it near the top of every script.

A simple but realistic script might combine several tasks:

```
#!/usr/bin/env bash
set -e
echo "Cleaning old files..."
rm -rf dist/
echo "Running tests..."
python manage.py test
echo "Starting server..."
python manage.py runserver
```

Nothing here is complicated, but putting these steps into a script means they always run in the same order, the same way, every time. That consistency is the real value of shell scripts.

You do not need to turn Bash into your primary programming language. Think of scripts as glue. They connect tools, enforce routines, and save mental effort.

## Always quote variables

Unquoted variables in Bash can cause bugs and security issues:

```
# If NAME contains spaces:
NAME="John Smith"
echo Hello, $NAME     # Bash sees: echo Hello, John Smith (3 args)
echo "Hello, $NAME"   # Bash sees: echo "Hello, John Smith" (1 arg)
```

In Bash, `$VAR` without quotes is subject to word splitting. If the value contains spaces, Bash splits it into multiple arguments. Good practice is to use `"$VAR"` to prevent this:

```
FILE="my document.txt"
rm "$FILE"    # Correct: deletes "my document.txt"
rm $FILE      # Bug: tries to delete "my" and "document.txt"
```

This is the single most common source of bugs in Bash scripts.

## Script arguments

So far, the scripts you have seen do exactly one thing in exactly one way. Bash scripts become much more useful when they can accept input from the command line.

Arguments passed to a script are available as numbered variables. `$1` refers to the first argument, `$2` to the second, and so on.

Create a file called `hello.sh`:

```
#!/usr/bin/env bash
NAME="$1"
echo "Hello, $NAME"
```

Make it executable and run it:

```
chmod +x hello.sh
./hello.sh Mark
```

This pattern shows up everywhere, from small utility scripts to large deployment tools. It allows one script to handle many similar tasks without modification.

## Relative and absolute paths

Paths inside a Bash script work the same way they do in the terminal. Relative paths are resolved from the current working directory, not from the location of the script itself.

This means the following script can behave differently depending on where it is run from:

```
rm data/output.txt
```

If you want predictable behavior, either use absolute paths or explicitly change the directory at the start of the script:

```
cd /Users/mark/projects/my-site
```

Understanding this early avoids a common class of bugs where scripts work for one person but fail for another.

## Comments in scripts

Bash scripts support comments using the `#` character. Anything after `#` on a line is ignored by Bash:

```
# Clean old build files
rm -rf dist/
```

Comments explain intent, which is often more important than explaining syntax. A script you understand today may be confusing in six months without comments.

## Bash as glue

Bash does not replace other languages or tools. It connects them.

A single script might call Git, Docker, Python, and a web server in sequence. Bash does not care what language a tool is written in. If it can be run from the command line, Bash can orchestrate it.

This is why Bash remains relevant even as new languages and frameworks appear. It sits at the boundary between tools and lets them work together.

## A note on safety

Bash scripts can change or delete files, stop services, and deploy code. They usually do exactly what they are told, without asking for confirmation.

Before running a script that you did not write yourself, read it. This is especially important for scripts copied from the internet or generated by AI tools. Treat shell scripts with the same caution you would give to executable files from an unknown source.

# Automating your Django development

So far, the examples have been small and focused. Now let's connect Bash directly to something you have already done: running a Django project.

In the previous chapter, you repeatedly ran a sequence of commands:

1.  Create or activate a virtual environment
2.  Install dependencies
3.  Apply database migrations
4.  Start the development server

Typing these every time is repetitive and easy to get wrong. This is exactly the kind of task Bash scripts are meant to simplify.

## The problem is repetition

A typical Django setup session might look like this:

```
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py runserver
```

There is nothing complicated here. But you run this sequence often enough that it becomes friction.

## The solution is a shell script

Create a new file in your Django project root:

```
touch run_dev.sh
```

Open it in your code editor and add the following:

```
#!/usr/bin/env bash
set -euo pipefail
echo "Setting up Django development environment..."
# Create virtual environment if it does not exist
if [ ! -d ".venv" ]; then
  echo "Creating virtual environment..."
  python -m venv .venv
fi
# Activate virtual environment
echo "Activating virtual environment..."
source .venv/bin/activate
# Install dependencies
if [ -f "requirements.txt" ]; then
  echo "Installing dependencies..."
  pip install -r requirements.txt
else
  echo "No requirements.txt found, skipping install"
fi
# Apply database migrations
echo "Running migrations..."
python manage.py migrate
# Start development server
echo "Starting Django development server..."
python manage.py runserver
```

Make the script executable:

```
chmod +x run_dev.sh
```

Now, instead of running five commands, you run one:

```
./run_dev.sh
```

This script is not doing anything new. It is just making your routine explicit and repeatable:

1.  It checks if `.venv` exists before creating it
2.  It activates the environment
