
**Good practice:** Any time you have more than one statement that must succeed or fail together, you should be using a transaction. This includes creating related rows across multiple tables, updating totals or derived values, deleting data with dependent rows, and migrations and data fixes.

Single-statement operations are often implicitly transactional, but relying on that behavior is fragile and varies by database.

# Improving performance with indexes

You can write perfectly correct SQL that is painfully slow if the database has no efficient way to find the data. Indexes exist to solve that problem, and query plans explain how the database uses them.

## What an index is

An **index** is a separate data structure that allows the database to find rows quickly without scanning an entire table. Conceptually, it is like the index in the back of a book. Instead of reading every page to find a name, you jump directly to the relevant pages.

In a database, an index stores selected column values in a structure optimized for lookup, along with references to the actual table rows. Most relational databases use variations of B-trees for indexes, which keep data sorted and allow fast searches, insertions, and range scans.

An important point is that an index is not the table itself. It is an additional structure that must be kept in sync with the table's data.

## Why indexes make reads faster

Without an index, the database has no choice but to perform a **full table scan**. That means checking every row to see whether it matches your query. This is acceptable for small tables, but it becomes slow very quickly as the table grows.

With an index, the database can jump directly to the relevant rows. For example:

* Filtering with `WHERE` on indexed columns becomes much faster
* Joining tables on indexed keys becomes cheaper
* Sorting and grouping can often reuse the index order

Indexes are especially effective for selective queries, where only a small fraction of rows match the condition.

**Prompt:** Please explain how a database chooses between a table scan and an index scan.

## Why indexes slow down writes

Every time you `INSERT`, `UPDATE`, or `DELETE` a row, the database must update not only the table, but also every index that involves the affected columns.

If a table has many indexes, each write operation has more work to do:

* New index entries must be created
* Existing entries may need to be reordered
* Deleted rows must be removed from indexes

This is why write-heavy workloads often have fewer indexes, while read-heavy workloads tend to have more. Indexes trade write speed and storage space for faster reads.

## How to choose effective indexes

A practical way to think about indexes is to start from your queries, not your tables. Ask:

* Which columns appear frequently in `WHERE` clauses?
* Which columns are used to join tables?
* Which columns are used to sort or group results?

These are prime candidates for indexes.

Also consider selectivity. Indexes are most useful when they significantly reduce the number of rows the database needs to examine. Indexing a column with only a few possible values, such as a Boolean flag, often provides little benefit on its own.

**Prompt:** Please explain index selectivity and why indexing Boolean columns is often useless.

**Composite indexes**, which cover multiple columns, can make specific queries much faster, but column order matters. An index on `(kind, release_year)` helps queries that filter by `kind`, or by `kind` and `release_year` together, but not queries that filter only by `release_year`.

## When not to index

Not every column should be indexed. Indexes cost storage and slow down writes. Tables that are small, rarely queried, or frequently updated may not benefit from additional indexes.

A common beginner mistake is adding indexes just in case. A better approach is to add them in response to real queries and real performance problems.

Indexes do not make SQL faster in general. They make specific access patterns faster. Query plans are how the database explains which access pattern it chose and why.

## How to identify performance issues

Identifying performance issues in SQL is about understanding where time is being spent and why. Slow queries are rarely caused by SQL syntax itself. They are usually the result of how data is structured, how much data is involved, and how the database chooses to access it.

### Start with symptoms, not guesses

Common signs of performance problems include:

* Queries that feel fast with small datasets but slow dramatically as data grows
* Reports or pages that hang or time out under load
* Queries that seem fine in development but struggle in production

The first mistake many developers make is trying to optimize blindly. Performance work should always start with observation.

### Measure before you change

Before changing anything, establish what *slow* actually means. Run the query on realistic data and note how long it takes, how many rows it returns, and whether the time is consistent or varies wildly.

If a query returns thousands of rows when you expect tens, the problem is often logical, not technical.

### Use EXPLAIN to see what the database is doing

Most databases provide `EXPLAIN` or `EXPLAIN ANALYZE` to show how a query will be executed. At a high level, look for:

* Full table scans on large tables
* Joins that process far more rows than expected
* Indexes not being used where you expected them to be
* Large differences between estimated row counts and actual row counts

You do not need to understand every detail of the plan. Even spotting a table scan versus an index scan is enough to explain many slow queries.

### Check filtering and joins first

Performance problems often come from:

* Missing or incorrect `WHERE` conditions
* Joins that multiply rows unexpectedly
* Filtering after joining instead of before

A useful technique is to remove joins one by one and see how the query's behavior changes. This helps isolate where row counts explode.

### Look at indexes last, not first

Indexes matter, but they are not a magic fix. Before adding an index, ask:

* Does the query filter or join on this column?
* Does the filter significantly reduce the number of rows?
* Is the data type and comparison correct?

Adding indexes to compensate for poor query logic usually leads to more complexity and slower writes without solving the real issue.

Performance issues are best approached systematically. Start by understanding what the query is doing, inspect the execution plan, verify row counts at each step, and only then consider indexing or refactoring.
