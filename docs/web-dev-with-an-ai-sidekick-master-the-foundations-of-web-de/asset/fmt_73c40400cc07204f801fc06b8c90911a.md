## Introducing Django

`Django` is a high-level Python web framework for building websites that store and retrieve data. Its core idea is that most web applications share the same fundamental problems, so the framework should solve those problems once, in a consistent way, instead of forcing every developer to reinvent them. As a result, `Django` provides routing, database access, HTML templating, authentication, forms, security protections, and an admin interface out of the box.

### MVT pattern

Architecturally, `Django` follows what it calls the `MVT pattern`: `Model`, `View`, `Template`. This is closely related to the more widely known `MVC pattern`: `Model`, `View`, `Controller`, but with slightly different naming that reflects `Django`’s specific way of dividing responsibilities:

* `Django`’s `Models` represent the data layer. They define your database schema using Python classes, and `Django` handles translating those definitions into SQL and database tables.
* `Django`’s `Templates` are responsible for presentation. They generate HTML by combining static markup with dynamic data, while keeping most application logic out of the template itself.
* `Django`’s `Views` coordinate the request. A view receives an `HTTP` request, interacts with models if needed, and returns an `HTTP` response, often by rendering a template with some context data.

If you are used to `MVC`, `Django`’s `View` roughly corresponds to a `Controller`, and `Django`’s `URL` configuration and request handling cover work that some frameworks would put in a controller layer. `URL` configuration maps incoming requests to view functions or classes, which keeps request handling explicit and easy to follow. This separation of concerns makes `Django` applications easier to understand as they grow, because models hold data rules, views handle requests, and templates render HTML.

A summary comparison of the components of `Django`’s `MVT` and `MVC` patterns is shown in *Table 9.1*:

| Concept | MVT | MVC |
| --- | --- | --- |
| Incoming request handled by: | URL configuration | Route |
| Logic executed by: | View | Controller |
| Data structure defined by: | Model | Model |
| Web page response generated by: | Template | View |

### Opinionated and convention-driven

`Django` is popular partly because it gives you working features early. It is opinionated and convention-driven: follow `Django`’s structure, and you get routing, database access, forms, authentication, and admin tools with little setup.

For example, defining a model automatically gives you database tables, a Python API for querying data, and an admin interface for managing records.

Common tasks like form validation, user authentication, and protection against common security issues are already solved, so you can spend time building features instead of infrastructure.

`Django` is especially well-suited to projects where correctness, maintainability, and development speed matter more than optimizing every performance detail from day one. Its design choices favor clarity and explicitness, which is why it is widely used for content-driven sites, internal tools, APIs, and data-heavy applications.

### Django projects versus Django apps

A useful concept to understand early is the difference between a `Django` project and a `Django` app:

* A `Django project` represents the entire website or system you are building.
* A `Django app` is a self-contained unit of functionality within that project. For example, a blog, a user accounts system, or a comments feature could each be separate apps.

A single `Django` project is made up of one or more apps, even if you only create one app to begin with. This structure encourages modular design and makes it easier to reuse or reorganize functionality as a project grows.
