
## INSERT: adding rows

The preceding code says exactly what is being inserted and where. If the table later gains a new column, this statement will still behave correctly. In SQLite, a column declared as `title_id INTEGER PRIMARY KEY` is a special case because it becomes an alias for the internal `rowid`, and SQLite will automatically generate a value if you don’t supply one.

Avoid relying on implicit column order, as shown in the following code:

```
INSERT INTO titles
VALUES ('Arrival', 'film', 2016, NULL);
```

This works only as long as the table definition never changes. That assumption rarely survives real projects.

### Inserting multiple rows

You can insert more than one row at a time, as shown in the following code:

```
INSERT INTO roles (role_name)
VALUES ('producer'),
       ('composer');
```

This is clearer and more efficient than issuing multiple separate `INSERT` statements.

### Inserting the result of a query

`INSERT` does not have to use literal values. You can insert the result of a query, as shown in the following code:

```
INSERT INTO credits (title_id, person_id, role_id, character_name)
SELECT t.title_id, p.person_id, r.role_id, 'Linguist'
FROM titles t, people p, roles r
WHERE t.name = 'Arrival'
  AND p.full_name = 'Amy Adams'
  AND r.role_name = 'actor';
```

This pattern is common when linking existing data together. It also avoids hard-coding IDs, which makes scripts safer and more portable.

## UPDATE: changing existing rows

`UPDATE` modifies one or more existing rows. The `WHERE` clause is the most important part of an `UPDATE` statement because it prevents you from accidentally updating ALL rows in the table!

### Updating a single column of a single row

For example, to ensure you only update the film named Arrival and not all the other films in the `titles` table, as shown in the following code:

```
UPDATE titles
SET universe = 'Standalone Sci-Fi'
WHERE name = 'Arrival';
```

This updates only the intended row. Without a `WHERE` clause, every row in the table is updated. This is where you will be especially glad you have database backups!

The following is valid SQL and a common source of accidental damage. A good habit is to always write the `WHERE` clause first, then add the `SET` clause:

```
UPDATE titles
SET universe = 'Standalone Sci-Fi';
```

**Good practice**: Always include a `WHERE` clause in `UPDATE` and `DELETE` statements.

### Updating multiple columns

You can update several columns at once, as shown in the following code:

```
UPDATE episodes
SET length_min = 45,
    air_date = '1991-09-30'
WHERE name = 'Darmok';
```

Each affected row is updated as a single operation.

### Updating with conditions and joins

Some databases allow `UPDATE` statements that reference other tables. Conceptually, you are still updating one table, but using related data to decide how. A subquery is a `SELECT` statement nested inside another SQL statement. The inner query runs first and its results are used by the outer query.

For example, updating all episodes for a specific series, as shown in the following code:

```
UPDATE episodes
SET length_min = 50
WHERE season_id IN (
  SELECT s.season_id
  FROM seasons s
  JOIN titles t ON t.title_id = s.title_id
  WHERE t.name = 'Star Trek: The Next Generation'
);
```

This reads as, *update episodes whose season belongs to this series*. The subquery finds all `season_id` values for a specific series, and the outer `UPDATE` uses those IDs to target the right episodes.

## DELETE: removing rows

Be extremely careful with the `DELETE` statement. There is no undo.

### Deleting just the rows you want to

`DELETE` removes rows from a table that match the `WHERE` clause, as shown in the following code:

```
DELETE FROM titles
WHERE name = 'Arrival';
```

The preceding code deletes only the matching row.

**Warning!** The following code deletes all rows in the table! The table structure remains, but the data is gone: `DELETE FROM titles;` There is no undo unless you’ve wrapped this statement in a transaction (you will learn about transactions in the next section). Always triple-check for a `WHERE` clause before running a `DELETE` statement.

### Deleting with foreign keys

Foreign key constraints matter when deleting. If other tables reference the row you are deleting, the database may block the deletion, automatically delete dependent rows, or set foreign key values to `NULL`.

The behavior depends on how the foreign key was defined. This is deliberate protection, not an inconvenience.

### Comparing deleting with dropping a table

`DELETE` removes rows but leaves the table structure intact. `DROP` removes the entire table, as shown in the following code:

```
DROP TABLE titles;
```

`DROP` is a schema change, not a data change. It is irreversible and should be treated with caution.

Now, let’s see how we can add a sort of undo capability when we are modifying data.

## Transactions

**Transactions** are how a database draws a hard line between *this change happened* and *this change did not happen*. They exist to prevent a system from ending up in a broken, half-updated state when something goes wrong.

Real database operations rarely involve a single statement. Even a simple user action can translate into multiple `inserts`, `updates`, or `deletes`. If one step succeeds and another fails, the database can be left in an inconsistent state.

Imagine adding a new order:

1. Insert the order
2. Insert the order items
3. Update inventory counts

If the order is inserted but updating inventory fails, did the operation work? From the user’s point of view, no. From the database’s point of view, half the changes were applied.

### What a transaction is

A transaction is a group of database operations treated as a single unit of work. The database guarantees that either all the operations succeed together, or none of them take effect at all.

You explicitly control this with the following commands:

* `BEGIN` (or `START TRANSACTION`)
* `COMMIT`
* `ROLLBACK`

Until a transaction is committed, its changes are provisional. If something goes wrong, a `ROLLBACK` restores the database to exactly the state it was in before the transaction started.

### Atomicity in plain language

Transactions are often described using the ACID properties. The most important one for beginners is atomicity. Atomicity means *all or nothing*.

Either the entire transaction commits, or the database behaves as if it never happened. There is no in-between state that other users can see.

### Why transactions matter even more with constraints

Constraints and transactions work together. If any statement inside a transaction violates a constraint, the database can abort the transaction. This prevents invalid data from leaking into the system.

For example, if one `INSERT` succeeds but a later `INSERT` violates a foreign key constraint, the entire transaction can be rolled back. The database does not leave behind partial results that break relationships.

Transactions are also about multiple users working at the same time. Without transactions, two users updating related data simultaneously can interfere with each other in unpredictable ways. Transactions define clear boundaries where changes begin and end, allowing the database to manage locking and isolation safely.
