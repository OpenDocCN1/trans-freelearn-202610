# 新手实用安全基线

你不需要昂贵的工具来保护小型 Django 应用。一个简单、配置良好的设置就能起到很大作用。

从 Django 的部署清单开始：

1. 设置 `DEBUG = False`
2. 定义 `ALLOWED_HOSTS`
3. 保持 `SECRET_KEY` 私密
4. 运行 `python manage.py check --deploy`

Django 明确警告：在生产环境中使用 `DEBUG = True` 会暴露堆栈跟踪、设置和敏感内部细节。

# 强制 HTTPS 和安全 Cookie

Django 建议在整个站点强制使用 HTTPS，而不仅仅是登录页面，因为会话 Cookie 在请求间共享。始终通过 HTTPS 提供服务。这能保护登录会话和用户数据。

在 Django 设置中应启用以下选项：

```python
if not DEBUG:  # 仅在生产环境启用
    SECURE_SSL_REDIRECT = True
    SESSION_COOKIE_SECURE = True
    CSRF_COOKIE_SECURE = True
    SECURE_HSTS_SECONDS = 31536000  # 1 年
    SECURE_HSTS_INCLUDE_SUBDOMAINS = True
    X_FRAME_OPTIONS = "DENY"
    SECURE_CONTENT_TYPE_NOSNIFF = True
```

关于上述设置的说明：

* `SECURE_SSL_REDIRECT = True`：强制将所有 HTTP 请求重定向到 HTTPS。如果用户访问 `http://your-site.com`，Django 会自动将他们重定向到 `https://your-site.com`。这确保所有通信都经过加密。没有此设置，用户可能通过纯 HTTP 访问你的站点，允许攻击者拦截或修改流量（中间人攻击）。
* `SESSION_COOKIE_SECURE = True`：确保会话 Cookie 仅通过 HTTPS 发送。浏览器不会在 HTTP 请求中包含会话 Cookie。会话 Cookie 标识已登录用户。如果通过 HTTP 发送，它们可能被拦截并用于劫持会话。
* `CSRF_COOKIE_SECURE = True`：确保 CSRF 保护 Cookie 仅通过 HTTPS 发送。类似于会话 Cookie，但专门用于 CSRF 令牌。CSRF 保护依赖于一个秘密令牌。如果该令牌通过 HTTP 暴露，攻击者可能绕过 CSRF 保护。
* `SECURE_HSTS_SECONDS = 31536000`（1 年，以秒为单位）：启用 **HTTP 严格传输安全 (HSTS)**，并告诉浏览器在未来一年内始终对你的站点使用 HTTPS。在通过 HTTPS 访问你的站点一次后，浏览器将在指定时长内拒绝通过 HTTP 连接。它防止降级攻击，即攻击者试图强制用户回退到 HTTP。
  
  > **警告！** 只有在你确信 HTTPS 在所有地方都正确工作后，才应启用此项。

* `SECURE_HSTS_INCLUDE_SUBDOMAINS = True`：将 HSTS 扩展到所有子域名。例如：`api.your-site.com`、`admin.your-site.com` 等。攻击者经常以较弱的子域名为目标。这确保整个域名仅限 HTTPS。
* `X_FRAME_OPTIONS = "DENY"`：防止你的站点被嵌入 `<iframe>` 中。浏览器将阻止任何尝试在另一个站点的框架中加载你的页面。防止点击劫持攻击，即恶意站点诱使用户点击你站点的隐藏元素。
* `SECURE_CONTENT_TYPE_NOSNIFF = True`：这告诉浏览器不要猜测（或“嗅探”）响应的内容类型。浏览器必须遵守服务器发送的 `Content-Type` 头。防止某些攻击，即文件伪装成一种类型（如文本）但作为另一种类型执行（如 JavaScript）。

作为一个整体，这些设置在所有地方强制 HTTPS，保护敏感 Cookie，防止常见的基于浏览器的攻击（点击劫持、MIME 嗅探），并降低流量被拦截和篡改的风险。

它们是 Django **生产环境默认安全** 方法的一部分，但只有当你的应用正确部署在 HTTPS 后面（例如，使用 Nginx 或终止 TLS 的云平台）时，它们才能正确工作。

> **警告！** 不要在开发环境中盲目启用这些设置，因为本地通常未配置 HTTPS，重定向和安全 Cookie 会破坏你的开发工作流。

# 防范 XSS 和 CSRF

Django 在这方面提供帮助，但前提是你遵循其约定：

* 使用 Django 模板，而不是手动构建 HTML 字符串
* 除非绝对必要，避免将用户输入标记为安全
* 确保所有表单都包含 CSRF 令牌，如下所示：

```html
<form method="post">
    {% csrf_token %}
    <!-- form fields -->
</form>
```

为了额外保护，考虑启用 **内容安全策略 (CSP)**，它限制脚本可以从哪里加载。Django 6 包含对 CSP 配置的内置支持，例如 `SECURE_CSP` 等设置，但早期版本如当前的 LTS 版本 5.2 不支持。

CSP 是一种浏览器强制执行的安全机制，控制网页被允许加载和执行哪些资源。它由服务器定义（通常通过 HTTP 响应头），并告诉浏览器诸如：JavaScript 可以从哪些域加载、是否允许内联脚本、图片、样式表、字体和其他资产可以来自何处等信息。

其目标是减少 **跨站脚本 (XSS)** 等攻击的影响。即使攻击者设法将恶意代码注入你的页面，配置良好的 CSP 也能阻止该代码运行，因为它不是来自批准的来源。

一个简单的示例可能如下所示：

```
Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted.cdn.com;
```

上述 HTTP 头告诉浏览器：默认仅从你自己的站点加载资源，且仅允许来自你的站点和受信任的 **内容分发网络 (CDN)** 的脚本。

CSP 作为额外防御层效果最好。它不能替代安全编码实践，但当出现问题时，它会让利用变得困难得多。
