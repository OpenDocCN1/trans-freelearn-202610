
During development, when `DEBUG=True`, Django automatically finds static files inside each installed app’s `static` directory and serves them for you. This is why you can start using CSS immediately without any extra setup.

In production, this changes. Django does not serve static files itself. Instead, static files are collected into a single directory and served by a web server such as Nginx or a `content delivery network` (`CDN`). The key takeaway for now is that Django’s static file system is designed to support that transition without changing your templates.

A CDN is a distributed network of servers that delivers static content to users from a location geographically close to them. Instead of every request for images, CSS, JavaScript, or videos going back to a single origin server, a CDN caches those files on many edge servers around the world. When a browser requests a static asset, the CDN serves it from the nearest available location, which reduces latency, lowers load on the origin server, and improves reliability.

## Common beginner mistakes with static files

A common beginner mistake is confusing static files with templates. If you put CSS inside a templates directory, Django will not find it as a static file. If you try to put template logic inside a CSS file, Django will ignore it. Templates and static files live in parallel worlds and serve different purposes.

Another common mistake is forgetting to load the `static` tag in a template. If `{% static %}` is used without `{% load static %}`, Django will raise a clear error when `DEBUG=True`.

From a mental-model perspective, static files are part of the presentation assets of your site, not part of request handling or data flow. Templates simply reference them.

# Django admin interface

One of Django’s most distinctive features is the built-in admin interface. It is a working data-management interface that is generated automatically from your models. As soon as your models exist, Django can give you a working interface for creating, editing, and deleting data.

## Registering your models for administration

By default, Django only shows models that have been explicitly registered. To make your blog models appear, open `blog/admin.py` and register them:

```
from django.contrib import admin
from .models import Author, Post, Tag, Comment
admin.site.register(Author)
admin.site.register(Post)
admin.site.register(Tag)
admin.site.register(Comment)
```

Django’s admin becomes even more useful when you customize it. Customization is done by defining `ModelAdmin` classes. Here is a more realistic configuration for the `Post` model:

```
@admin.register(Post)
class PostAdmin(admin.ModelAdmin):
    list_display = ("title", "author", "status", "created_at")
    list_filter = ("status", "created_at", "author")
    search_fields = ("title", "body")
    prepopulated_fields = {"slug": ("title",)}
    ordering = ("-created_at",)
```

Note the following about the preceding code:

* `list_display` controls which columns appear in the list view
* `list_filter` adds a filter sidebar for common fields
* `search_fields` enables full-text search over selected fields
* `prepopulated_fields` automatically generates slugs from titles
* `ordering` defines the default sort order

### Prompt

What’s the difference between using `admin.site.register(Post)` and using `@admin.register(Post)` with a `class PostAdmin(admin.ModelAdmin)` and attributes like `list_display` to register a Django model?

You can also edit related objects inline. For example, comments are usually managed alongside posts rather than separately:

```
class CommentInline(admin.TabularInline):
    model = Comment
    extra = 0
@admin.register(Post)
class PostAdmin(admin.ModelAdmin):
    list_display = ("title", "author", "status", "created_at")
    inlines = [CommentInline]
```

This allows an editor to manage comments directly on the post edit page, which matches how many editorial teams work.

The admin respects all the rules defined in your models. Field validation, required fields, choices, relationships, and permissions are enforced automatically. If you mark a field as read-only or restrict who can edit a model, the admin reflects that immediately. This tight integration is one of Django’s strengths.

## Logging into the admin site as a superuser

The admin site is enabled by default when you create a Django project. To use it, you first need a superuser, also known as an administrator account. Create one from the command line:

```
python manage.py createsuperuser
```

Follow the prompts to set a username, email address, and password.

Then start the development server and visit the following link:

[http://127.0.0.1:8000/admin/](http://127.0.0.1:8000/admin/%20)
