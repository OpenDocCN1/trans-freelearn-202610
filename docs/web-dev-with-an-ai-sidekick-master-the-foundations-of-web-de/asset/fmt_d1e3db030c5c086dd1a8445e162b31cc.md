
If your chatbot supports `custom instructions` or `memory`, put the same content there so you don’t have to repeat it. If it doesn’t, keep it in a note and paste it into each new chat.

## Pick a track so the bot teaches coherently

Free chatbots can be amazing, but they’ll happily jump around unless you set a structure. Pick one learning track and stick with it for a few sessions:

- HTML semantics and structure
- CSS layout and styling
- JavaScript fundamentals
- SQL basics using SQLite
- Django basics
- Deployment concepts and scripting with Bash

Tell the chatbot:

```
Use this track. If I ask something beyond the scope of my current track, briefly answer but then guide me back to the track.
```

## Make the bot work inside your actual project

You’ll get dramatically better help if you feed it the right context. This will become easier once we use an AI tool integrated into your code editor or IDE, but you can also manually provide context even when using a separate AI chatbot.

Try to provide:

- Your goal (“I want a page that lists blog posts”)
- Your current code (the smallest relevant piece)
- The error message/traceback
- Your file names and where the code lives (`views.py`, `urls.py`, template path)

This prevents the chatbot from guessing your setup.

## Put guardrails on code generation

Many readers skip this step, but it makes a real difference.

Add these rules to your chat:

```
You must follow these rules when your response includes code:
- Do not generate more than about 40 lines of code at once unless I ask.
- Prefer incremental changes with diffs.
- If you propose a change, show it as: what to delete, what to add.
- Tell me the one most likely issue first.
```

This keeps the experience interactive and reduces the chance that you end up with a Frankenstein project.

## Use AI as a tutor, not a compiler

AI should not be used as a tool that replaces your own implementation work. A solid routine that should become a habit for you is to use the four-step learning loop, as shown in `Figure 1.6`:

1. Ask for explanation + tiny example
2. Implement it yourself (even if it’s slow)
3. Paste your attempt and ask for feedback
4. Do a small variation (“Now add validation,” “Now add search,” and so on)

## Verification habits

Chatbots (especially free ones) will be wrong sometimes so you can encourage the AI to check themselves with the following prompts:

- `List the assumptions you made about my project structure.`
- `What are 3 ways this could fail and how would I detect each?`
- `What's the simplest alternative approach?`

If you want extra safety, cross-check tricky answers by asking a second chatbot the same question. When they disagree, that’s your cue to test carefully.

# Coding with an AI assistant as your coworker

Although chatbots are great for learning, when building a complete web development project, you need a more specialized tool that works inside your code editor or IDE and can help with multi-step coding tasks (aka agentically, a horrible marketing word that I hope dates fast). The goal of this section is to understand the pros and cons of various AI tools that integrate with your coding tools.

**Good practice**: If you follow only one setup for a code editor or IDE with an integrated coding assistant in this book, use `VS Code` with `GitHub Copilot`. This combination is widely used, integrates cleanly with the workflows we will build, and provides the least friction for beginners.

Before we look at specific tools, there is an important factor to consider about their relationship to AI models.

## Understanding the tool–model relationship

When you start using AI coding assistants, it is easy to think of each tool as a single, fixed system. For example, you might assume that `GitHub Copilot` is one AI, in the same way that `ChatGPT` or `Claude` feels like a single product.

In reality, tools like `Copilot` are better understood as interfaces to multiple underlying models.

This means that when you use a tool like `GitHub Copilot` in a code editor or IDE like `VS Code`, you are not always talking to one specific AI system. Instead, the tool can route your request to different models depending on the task, the feature you are using, or your subscription level.

AI tools are built in layers:

- The editor or interface (for example, `VS Code` with `Copilot`)
- The integration layer that connects your editor to AI services
- One or more underlying models that actually generate responses

In some cases, this includes models from different providers.

For example, inside `Copilot` you might:

- Get inline code completions from one model
- Use chat features powered by another model
- Select or be routed to models such as `OpenAI`’s `GPT-5.5` or `Anthropic`’s `Claude Sonnet`

So even though you are using `Copilot`, the actual intelligence behind a response might come from a completely different system.

This affects how you choose tools:

1. First, tool choice and model choice are not the same thing. You might prefer working in `Copilot` because it integrates with your editor, but still want to use a specific model like `Claude Opus` for certain tasks.
2. Second, results can vary even within the same tool. If `Copilot` switches models or you change settings, you may see different styles of responses, levels of detail, or coding approaches.
3. Third, you can combine strengths. For example:
   - Use `Copilot` for fast inline suggestions while coding
   - Use a `Claude`-powered chat for deeper explanations
   - Use a stronger model for complex debugging or design decisions

Do not think in terms of which single AI should I use. Instead, think about:

- Which tool fits your workflow (for example, `VS Code` with `Copilot`)?
