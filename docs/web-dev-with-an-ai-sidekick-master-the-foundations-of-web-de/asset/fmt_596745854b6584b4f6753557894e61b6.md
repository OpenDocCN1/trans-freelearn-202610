4. Navigate to your local site (for example, `http://127.0.0.1:8000`)

5. Use the browser tools to inspect and annotate the UI

The browser panel includes features such as:

* Taking screenshots of the current page
* Adding annotations to specific UI elements
* Sending those annotated screenshots directly into the chat

When you click on a button, form, or layout element and attach a comment, the model receives both the visual context (screenshot) and your instruction tied to a specific part of the UI.

For example:

```
This button is too small and blends into the background. Make it more prominent and consistent with the primary action style.
```

This is far more precise than describing the problem in text alone.

In earlier sections, you saw how important it is to define behavior and structure before generating code. UI refinement has a similar challenge: describing visual issues in words is often imprecise.

The browser interaction feature improves this in three ways:

1. **Shared context**: The AI sees exactly what you see, instead of inferring layout from templates and CSS.
2. **Targeted changes**: Feedback is attached to a specific element, not a vague description of a page.
3. **Faster iteration**: You can quickly try changes, review them, and refine again without rewriting long prompts.

This saves you from describing layout problems from memory.

## Limitations and Good Habits

This feature is useful, but it should still be used with the same discipline as the rest of your workflow.

Keep these points in mind:

* Do not accept UI changes blindly. Always review generated CSS and templates.
* Keep your `design.md` in sync with changes, so you do not drift into inconsistent styles.
* Avoid making many small, uncoordinated tweaks. Prefer grouped, intentional changes.
* Use this for refinement, not initial architecture.

Also note that interaction is currently element-by-element. If you want to change multiple components consistently, you should describe the pattern, not just individual elements.

Use the Codex browser interaction when:

* The application is already running
* You are refining layout, styling, or usability
* You can point to specific issues on the screen

Do not rely on it for:

* Initial project design
* Data modeling decisions
* Security or permission logic

Those still belong in your project brief and design thinking earlier in the chapter.
