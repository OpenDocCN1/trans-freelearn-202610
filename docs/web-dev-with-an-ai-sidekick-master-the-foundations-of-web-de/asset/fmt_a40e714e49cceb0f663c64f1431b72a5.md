
# Constraints

## CHECK and FOREIGN KEY Constraints

### Table 7.1: Common Constraints

| Constraint | Description |
|------------|-------------|
| `CHECK` | Restricts the range or format of values that can be stored in a column. It encodes simple business rules directly into the database. Examples include a release year must be greater than or equal to 1888, a rating must be between 1 and 5, and a status must be one of a fixed set of values. They are not meant to replace complex validation logic, but they are very effective for guarding basic invariants. |
| `FOREIGN KEY` | Enforces relationships between tables. It ensures that a value in one table refers to a valid row in another table. For example, an episode cannot reference a season that does not exist, and a credit cannot reference a person that is not in the person table. Foreign keys can also define what happens when related data changes. Common behaviors include preventing deletion, cascading deletes, or setting the reference to `NULL`. |

Each constraint type solves a different class of problem, but they work best together. `NOT NULL` ensures required data exists. `UNIQUE` ensures it is not duplicated. `CHECK` ensures it makes sense. `FOREIGN KEY` ensures it relates correctly to other data.

Without constraints, a database is just a passive storage system that accepts whatever it is given. With constraints, the database actively defends the assumptions your application is built on. This reduces bugs, simplifies queries, and makes long-term maintenance significantly easier. Constraints are about preventing bad data.

## SQL Naming Conventions for Database Objects

Sticking to a consistent naming convention for your database objects will make it easier to maintain. Since most SQL dialects are case-insensitive but preserve case in display, a few conventions have become common to ensure your code remains readable and portable across different systems.

The most widely recommended convention, especially for PostgreSQL, MySQL, and SQLite, is `lower_snake_case`. For example:

- Table names: `user_accounts`, `order_items`, `product_categories`
- Column names: `first_name`, `created_at`, `email`

Why? Many SQL engines convert everything to lowercase internally. Using `lower_snake_case` ensures that your code looks the same in your editor as it does in the database logs.

### Table Naming Guidelines

- Tables represent collections of things so use collective or plural names. For example, use a `users` table instead of a `user` table. A table is a container for many records.
- Avoid prefixes. Don't name tables `tbl_users`. Database tools already know it's a table.
- Be descriptive. If a table stores a relationship between users and groups, name it `user_groups` rather than `mapping_table_1`.
- Avoid SQL keywords. A table named `order` would conflict with `ORDER BY`, a table named `group` would conflict with `GROUP BY`, and `USER` is a keyword in PostgreSQL.

**Good practice**: Check your database's reserved words list when choosing table names. When in doubt, use more descriptive names like `user_accounts` or `customer_orders`.

### Column Naming Guidelines

- For the column designated as the primary key (row unique identifier), there are two competing schools of thought. You can use the simple `id`, so every table has a column simply named `id`. But when joining users and orders, you end up with two columns named `id`, which can be confusing. Or you can use a prefix like `user_id` so the primary key column name includes the table name.
- Prefix Boolean column names with `is_`, `has_`, or `can_` to clarify that the value is `true` or `false`. For example, `is_active`, `has_discount`, and `can_post`.
- For dates and times, include a suffix to indicate if it is a date or a full timestamp. For example, `created_at` (timestamp), `birth_date` (date only).

### Names to Avoid

- Never name a table `User`, `Order`, or `Group`. These are reserved keywords in some dialects of SQL and will require you to use annoying quotes like `"User"` or square brackets like `[User]` every time you write a query.
- Never use spaces in table or column names like `Order Date` because it will require you to use extra quotes like `"Order Date"` or square brackets like `[Order Date]` every time you write a query. Use underscores like `order_date`.
- Avoid abbreviations like `cust_addr_id`. Use `customer_address_id`. Space is cheap. Time spent decoding abbreviations is not.

**Good practice**: Using `UPPERCASE` for SQL keywords is the most widely accepted convention in the industry. While SQL is case-insensitive (meaning `select` works the same as `SELECT`), writing keywords in uppercase improves visual parsing.

# Setting Up SQLite and a Sample Database

SQLite is a small, fast, cross-platform, self-contained **Relational Database Management System (RDBMS)** that is available in the public domain. It's the most common RDBMS for mobile platforms such as iOS (iPhone and iPad) and Android. SQLite is the most used database engine in the world, and there are more than one trillion SQLite databases in active use. You can read more about this at [https://www.sqlite.org/mostdeployed.html](https://www.sqlite.org/mostdeployed.html).

I am using SQLite here because it is cross-platform, easy to install, and more than enough for learning core SQL and database design.

Now let's install SQLite on your computer.

## Setting Up SQLite CLI Tools for Windows

On Windows, we need to download SQLite CLI tools and add the folder for SQLite to the system path so it will be found when we enter commands at a command prompt or terminal:

1. Start your favorite browser and navigate to [https://www.sqlite.org/download.html](https://www.sqlite.org/download.html).
2. Scroll down the page to the **Precompiled Binaries for Windows** section.
3. Click **sqlite-tools-win-x64-3510200.zip** (the file will probably have a higher version number by the time you read this), as shown in *Figure 7.4*:
   ![](Images/B34553_07_04.png)
   Figure 7.4: Downloading SQLite for Windows on Intel x64
4. Extract the ZIP file into a folder named `C:\Sqlite`. Make sure that the three extracted files, including `sqlite3.exe`, are directly inside the `C:\Sqlite` folder, or the executable will not be found later when you try to use it.
5. In the Windows **Start** menu, navigate to **Settings**.
6. Search for `environment` and choose **Edit the system environment variables**. On non-English versions of Windows, please search for the equivalent word in your local language to find the setting.
7. Click the **Environment Variables** button.
8. In **System variables**, select `Path` in the list, and then click **Edit…**.
9. If `C:\Sqlite` is not already in the path, then click **New**, enter `C:\Sqlite`, and press *Enter*.
10. Click **OK**, then **OK**, then **OK** again, and then close **Settings**.
11. To confirm that the path to SQLite has been configured correctly, at any command prompt or terminal, enter the following command to start SQLite:
    ```
    sqlite3
    ```
12. Note the result, as shown in the following output:
    ```
    SQLite version 3.51.2 2026-01-09 17:27:48
    Enter ".help" for usage hints.
    Connected to a transient in-memory database.
    Use ".open FILENAME" to reopen on a persistent database.
    sqlite>
    ```
