
# Multi-stage Docker builds

The `Dockerfile` shown earlier is simple and easy to understand, but it includes tools that are only needed during installation, such as compilers. These tools increase the size of the final image and are not required when the application is running.

The current Docker image includes compilers (`gcc`, `make`), package manager cache, and build dependencies. Those are not needed at runtime and increase both the image size and potential attack surface.

A more advanced technique called a `multi-stage build` separates the build environment from the runtime environment. The first stage installs dependencies, and the second stage copies only the results into a clean image.

A multi-stage build separates:

1. **Build stage**: Install dependencies, compile anything needed
2. **Runtime stage**: Copy only what is needed to run the app

This avoids shipping unnecessary tools like compilers into your final image.

Here is a rewritten version of your `Dockerfile` using a multi-stage build:

```
# ---- Stage 1: Build dependencies ----
FROM python:3.12-slim AS builder
WORKDIR /app
RUN apt-get update \
 && apt-get install -y --no-install-recommends build-essential \
 && rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --upgrade pip \
 && pip install --prefix=/install --no-cache-dir -r requirements.txt
# ---- Stage 2: Runtime image ----
FROM python:3.12-slim
WORKDIR /app
ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1
# Copy installed packages from builder
COPY --from=builder /install /usr/local
# Copy project code
COPY . /app/
CMD ["python", "manage.py", "runserver", "0.0.0.0:8000"]
```

This produces smaller images, faster downloads, and a reduced attack surface. The final image only contains a Python runtime, your dependencies, and your app. Multi-stage builds are common in production setups, but optional for learning projects.

## Viewing logs to debug container issues

When something goes wrong in a Docker-based setup, the first place to look is the container logs.

If you ran your containers with:

```
docker compose up
```

You will already see logs in that terminal window.

However, if you run containers in the background or open a new terminal, you can view logs using:

```
docker compose logs
```

This shows the combined output of all services, including your Django app and PostgreSQL database. For example, you might see Django startup messages, database connection errors, migration warnings, and Python exceptions.

You can focus on just one container:

```
docker compose logs web
```

Or:

```
docker compose logs db
```

This is useful when you want to separate Django errors from database output.

To watch logs as they happen:

```
docker compose logs -f
```

This is like running `docker compose up`, but works even if the containers are already running in the background.

Viewing logs is important because Docker changes how you debug problems. You are no longer running everything directly on your machine. Your app runs inside containers, so errors show up there, not in your editor or terminal history.

If the app fails to start, or cannot connect to the database, the logs will usually tell you why.

For example:

- "could not connect to server" tells you that PostgreSQL is not ready
- "no such table" tells you that database migrations were not applied
- Python traceback tells you that there is a bug in your code

## Common mistakes and quick fixes

If Django starts before PostgreSQL is accepting connections, you might see connection errors on first startup. The simplest fix for a learning project is to rerun `docker compose up` or retry migrations. In more advanced setups you add a `wait-for-database` script.

## Where this fits in TallyApp's overall deployment story

This Docker setup is primarily a development environment, but it teaches patterns that carry into production: immutable builds, multi-service composition, and persistent data via volumes.

It also sets up an easy database upgrade path: you can develop locally with PostgreSQL in containers, then later deploy with PostgreSQL on a VPS or managed PostgreSQL without changing your application logic, only its configuration.

While Docker focuses on packaging applications into consistent, portable environments, it does not address how code itself is tracked, shared, and evolved over time. That is where Git comes in. If Docker ensures that software runs the same way everywhere, Git ensures that teams (including human and AI programmers) can collaborate on that software without losing track of changes or overwriting each other's work. Together, Docker and Git form a natural pairing in web development workflows, but before combining them, it is important to understand how Git manages version control so each change can be saved, reviewed, and, if necessary, undone.

# Source code version control using Git

Before you add features to TallyApp, you need protection against your own mistakes. Git gives you a complete history of your project, lets you experiment safely, and makes collaboration and deployment straightforward.

This section teaches a focused, practical subset of Git using VS Code's built-in Git integration. You will learn how to initialize a repository, make meaningful commits, create branches, connect to a remote, and recover from common mistakes.

## What Git does

Git is a distributed version control system. It records snapshots of your project over time.

A few terms matter, as summarized in *Table 11.2*:

| **Term** | **Definition** |
| --- | --- |
| Repository | A folder that Git tracks. It contains a hidden `.git` directory that stores the project history. |
| Commit | A saved snapshot of your project at a specific moment, along with a message explaining the change. |
| Working branch | The files you are currently editing. |
| Staging area | The set of changes you intend to include in the next commit. |
| Branch | A parallel line of development. You can experiment on a branch without affecting `main`. |
| Remote | A hosted copy of your repository, typically on GitHub, GitLab, or Bitbucket. |

Table 11.2: Common Git terms

Git runs locally on your machine. Services such as GitHub host a remote copy so you can back up and share your work.
