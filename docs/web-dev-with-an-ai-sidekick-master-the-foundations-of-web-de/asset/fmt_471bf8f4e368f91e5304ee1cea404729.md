
## Splitting URLs by App

As projects grow, Django encourages you to split URLs by app. Each app defines its own `urls.py`, and the project-level `urls.py` includes them by calling the `include()` function, as shown highlighted in the following code:

```python
from django.contrib import admin
from django.urls import path, include
urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include("blog.urls")),
]
```

This keeps routing modular and mirrors Django’s *project contains apps* philosophy. The project routes decide where an app lives in the URL space. The app routes decide what happens inside that space.

## Dynamic segments in URLs

URL patterns often include dynamic segments. These are defined using path converters in angle brackets like this: `<path_converter_type:parameter_name>`.

For example, to show a single blog post by its slug:

```python
path("<slug:slug>/", post_detail, name="post_detail"),
```

Here, `<slug:slug>` means *match a* `slug` *-shaped string and pass it into the view as a parameter named* `slug`. The view signature must match:

```python
def post_detail(request, slug):
    ...
```

Common path converters include:

*   `str` for any non-empty string
*   `int` for integers
*   `slug` for URL-friendly strings
*   `uuid` for universally unique identifier (UUID) values

A URL-friendly string is a piece of text that is safe to use in a web address without causing ambiguity, encoding issues, or readability problems. In practice, a URL-friendly string has a few key characteristics: it uses lowercase letters only, it contains numbers if needed, words are separated with hyphens, not spaces or underscores, and it avoids punctuation, symbols, and non-ASCII characters. For example, if the title of a web page is *Hello, Django!*, its slug might be `hello-django`, or if the title is *C# & .NET Basics*, its slug might be `c-net-basics`.

Using converters keeps URLs readable and avoids manual parsing inside views.

## Named URLs

Instead of hard-coding links like `/posts/hello-django/`, templates should use the `{% url %}` tag, passing the name of the view that should process the request and the path defined by its slug. The contents of the `<a>` element should be whatever text you want to see in the link, like the title of the post:

```html
<a href="{% url 'post_detail' slug=post.slug %}">
    {{ post.title }}
</a>
```

At this point, you do not need to understand the preceding template syntax. Template syntax is explained fully later in this chapter.

This does two important things.

1.  It decouples templates from URL structure. You can change the URL pattern later without touching every template.
2.  Django will raise an error if the URL name or arguments do not match, which catches mistakes early instead of silently producing broken links.

URL names also matter outside templates. Redirects and reverse lookups in views rely on them:

```python
from django.shortcuts import redirect
return redirect("post_detail", slug=post.slug)
```

This is why naming URLs is a good practice.

## Ordering in URL patterns

Ordering matters in URL patterns. Django stops at the first match. This means more specific patterns should come before more general ones. For example, if you had both, as in this incorrect example:

```python
path("<slug:slug>/", post_detail),
path("archive/", archive_view),
```

Then Django will treat `"archive"` as a slug and never reach the `archive/` view.

To fix this issue, `"archive/"` must appear before the slug pattern, as in this fixed example:

```python
path("archive/", archive_view),
path("<slug:slug>/", post_detail),
```

## Routing and models

URL routing does not know or care about models. It simply matches strings and then calls views. Validation, database lookups, and `404 Missing resource` handling belong in the view layer. This separation keeps routing simple and predictable.

In practice, clean URL design pays off quickly. Readable paths, named routes, and consistent structure make templates easier to write and views easier to understand.

Now we are ready to learn about models, one of the best parts of Django because once you’ve defined the classes for your models, so much more happens for you. Django can create migrations, build database tables, generate admin forms, and give you a Python API for querying data.

# Django models

In Django, a model is the single source of truth for your application’s data. You define models as Python classes, and Django uses them to do three jobs at once:

*   Describe the shape of your data
*   Generate and evolve your database schema
*   Provide a high-level API for creating, reading, updating, and deleting rows in the database

A model usually maps to a database table. Each attribute on the model maps to a column. Each instance of the model maps to a row. Django’s **object-relational mapper (ORM)** sits between your Python code and the database, translating Python operations into SQL behind the scenes.

## Creating your first app and model

Let’s create a blog app with a model to represent posts:

1.  Create an app feature named `blog`:

    ```bash
    python manage.py startapp blog
    ```

2.  Register the `blog` app in `scribble/settings.py`, as shown in *Figure 9.4* and the following code:

    ```python
    INSTALLED_APPS = [
        ...
        "blog",
    ]
    ```

![Figure 9.4: Registering the blog app in settings.py](Images/B34553_09_04.png)

**Warning!** If you miss this step, the Scribble project will not know about the `blog` app and it won’t scan the `blog` folder hierarchy to discover all its features and settings. A lot of problems are caused by forgetting to register an app after creating it.

3.  You define models in `blog/models.py`. Add the highlighted code under the comment:

    ```python
    from django.db import models
    # Create your models here.
    class Post(models.Model):
        title = models.CharField(max_length=200)
        body = models.TextField()
        created_at = models.DateTimeField(auto_now_add=True)
        updated_at = models.DateTimeField(auto_now=True)
        is_published = models.BooleanField(default=False)
        def __str__(self) -> str:
            return self.title
    ```

Note the following about the preceding code:

*   `CharField` is for short text and requires a `max_length` keyword argument or field option because the database needs a defined column size. `max_length` is known as a **keyword argument** in Python, and more specifically a **field option** in Django.
*   `TextField` is for longer free-form text.
*   `DateTimeField(auto_now_add=True)` sets the value once when the row is created.
*   `DateTimeField(auto_now=True)` updates the value every time the row is saved.
*   `BooleanField` stores `true` or `false`, with `default` used for new rows.

**Good practice**: The `__str__` method is not required, but it is worth adding early. Django uses it in places like the admin UI, and a readable string makes debugging much nicer than seeing `Post object (3)` everywhere.
