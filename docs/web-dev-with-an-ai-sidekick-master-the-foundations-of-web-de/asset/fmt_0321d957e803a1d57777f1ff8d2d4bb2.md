## Testing models, forms, and business logic

In a Django app like TallyApp, your tests should cover:

- **Model logic**: Custom methods such as `is_open()`, `can_edit(user)`, or computed properties
- **Form validation**: Ensure invalid data is rejected and correct error messages appear
- **Permission logic**: Confirm that only owners can edit or delete their surveys
- **Utility functions**: Pure Python functions for calculating statistics or transforming data

A useful rule is: *if it contains logic, test it, and test behavior, not boilerplate*. But if it is just a template rendering static content, unit tests are usually unnecessary.

## Property-based testing with Hypothesis

Most tests you have seen so far are example-based. You choose specific inputs, call a function, and assert the expected result. **Property-based testing** takes a different approach. Instead of writing many individual examples, you describe a general property that should always be true, and a tool generates a wide range of inputs automatically to try to break it.

In Python, the most popular property-based testing library is **Hypothesis**. Rather than testing only a few handpicked values, Hypothesis generates dozens or hundreds of inputs, including edge cases you might not think of, such as empty strings, extremely large numbers, unusual Unicode characters, or boundary values.

For example, suppose you have a simple utility function in TallyApp that calculates the percentage of responses:

```python
def percentage(part, total):
    if total == 0:
        return 0
    return round((part / total) * 100, 2)
```

A traditional test might look like this:

```python
def test_percentage_basic():
    assert percentage(1, 4) == 25.0
```

That is fine, but it only tests one example. With Hypothesis, you can define properties that should hold for many inputs:

```python
from hypothesis import given
from hypothesis import strategies as st

@given(
    part=st.integers(min_value=0, max_value=10_000),
    total=st.integers(min_value=0, max_value=10_000),
)
def test_percentage_is_between_0_and_100(part, total):
    result = percentage(part, total)
    assert 0 <= result <= 100
```

Now Hypothesis will generate many combinations of `part` and `total` and verify that the result always falls within a valid range. If it finds a failing case, it will shrink the input to the smallest example that still breaks the property, which makes debugging easier.

When you run this, Hypothesis will find cases where `part > total`, producing results above 100%. This is the point of property-based testing because it found a bug we didn't anticipate. Then you'd need to decide how to handle the discovered bug: should the function clamp the result to 100%, or should the property allow values above 100%? To fix the function, you could use the following code:

```python
def percentage(part, total):
    if total == 0:
        return 0
    return min(round((part / total) * 100, 2), 100.0)
```

Property-based testing is especially useful for:

- Pure functions with mathematical or logical invariants
- Data transformations
- Validation logic
- Parsers and formatters
- Anything that should behave consistently across a wide input space

It is less useful for complex integration tests that depend heavily on databases, HTTP calls, or external systems.

With property-based tests, the question changes from *What example should I test?* to *What must always be true?* For business logic in TallyApp like score calculations, survey statistics, or normalization rules, that perspective can uncover edge cases that example-based tests miss.

## Measuring coverage

Testing is also about knowing where the blind spots are. The `coverage.py` tool measures how much of your code runs during tests.

You typically:

1. Run tests with coverage enabled.
2. Generate an HTML report.
3. Inspect which lines were never executed.

High coverage does not guarantee correctness, but low coverage almost guarantees blind spots.

## A sensible testing strategy for TallyApp

For a project like TallyApp:

- Write unit tests for model methods and validation logic
- Use Django's test client for authentication and create, read, update, and delete (CRUD) flows
- Keep tests small and focused
- Avoid testing trivial getters or Django internals

Different kinds of tests exercise different parts of the system. Use the lightest tool that still gives you confidence in the behavior you care about, as shown in *Figure 12.2*:

![](Images/B34553_12_02.png)

Figure 12.2: Testing layers in TallyApp

Start with the cheapest layer that can prove the behavior. If a pure Python unit test can prove it, do not use a browser test. It will be faster, simpler to maintain, and easier to debug.

Aim for:

- Fast test runs
- Clear failures
- Confidence when refactoring

The goal is to catch most bugs with layers 1 to 3. Reserve Playwright tests in layer 4 for the flows that matter most to real users. When unit tests and server-side integration tests are strong, UI testing becomes a thin safety layer rather than your only defense. That keeps browser tests valuable without letting them dominate the suite.

Testing is where you decide what the application is allowed to do. An AI assistant can write another `assertEqual` line, but it cannot decide whether an unpublished survey should be invisible, whether a creator can edit a survey after responses exist, or whether a duplicate submission should leave the database unchanged. Those decisions belong to the developer. Once you make them explicit as tests, the code has something concrete to satisfy.

## pytest and pytest-django

Many Django projects use `pytest` instead of `unittest`-style classes. But you should verify that `pytest-django` supports your Django version before assuming that you can use it. You can check for the latest compatibility information at the following link: [https://github.com/pytest-dev/pytest-django](https://github.com/pytest-dev/pytest-django)

Why developers prefer `pytest`:

- Simpler syntax (plain functions instead of classes)
- Powerful fixture system
- Better error output
