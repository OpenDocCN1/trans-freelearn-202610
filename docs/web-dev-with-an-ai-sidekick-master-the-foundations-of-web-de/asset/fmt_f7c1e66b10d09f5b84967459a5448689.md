
```
Write a test that verifies creating a survey fails when the user is not approved. Use self.client and assert the correct redirect or error message.
```

This shifts the AI from hallucinating behavior to implementing a behavior you have already defined.

## Using AI to explain failing tests

When a test fails in CI, pasting the failure output into an AI assistant can be surprisingly effective.

Example prompt:

```
Here is the traceback from my Django test run. Explain what is happening and suggest likely causes. Do not rewrite my code, just diagnose.
```

The AI can often:

* Identify that a redirect is happening instead of a `200`.
* Notice that an object does not exist because setup data was incomplete.
* Spot a mismatch between URL names and `reverse()` usage.
* Recognize a validation error triggered by new model constraints.

This is especially helpful for beginners, who often struggle to interpret multi-layered Django tracebacks involving middleware, URL resolution, and database errors.

## Using AI to refactor brittle tests

AI is also useful for cleaning up overly verbose or fragile tests.

Suppose you show it a test like this:

* Hardcoded URL paths.
* Repeated user creation boilerplate.
* Manual login logic.
* Repeated model setup across many tests.

Example prompt when using agent mode in a code editor:

```
Refactor these Django integration tests to reduce duplication. Extract factories or helper methods. Avoid relying on hardcoded URLs.
```

The AI can:

* Replace literal paths with `reverse()`.
* Introduce a `make_user` helper.
* Use `force_login` instead of manual `POST` login in tests that do not test the login view.
* Consolidate repeated setup into `setUp` or `setUpTestData`.

AI is useful here because the task is mechanical: reduce duplication without changing behavior.

## The risks of shallow AI-generated tests

The biggest danger is not incorrect syntax. It is false confidence.

Common problems with AI-generated tests are shown in Table 12.3:

| Problem | Explanation |
| --- | --- |
| They only assert `status_code == 200`. | A page can return `200` and still be wrong. |
| They assert the presence of text that is unrelated to the business rule. | For example, asserting `Survey` appears on a page, rather than verifying that the correct survey title appears and the incorrect one does not. |
| They mirror the implementation rather than the test behavior. | If your view calls `Survey.objects.filter(is_published=True)`, an AI may generate a test that asserts the exact same query, rather than asserting that unpublished surveys are not visible. |
| They ignore negative cases. | AI tends to produce happy-path tests unless you explicitly ask for failure modes. |
| They rely on brittle details. | Hardcoded primary keys, implicit ordering, or assumptions about IDs starting at 1. |
| They overfit to the current code. | If you later refactor internal logic but preserve behavior, shallow tests may break unnecessarily because they were testing implementation details. |

## How to review AI-generated tests critically

Treat AI output as a pull request from an enthusiastic but inexperienced developer. Review it with the same skepticism.

Ask these questions:

1. What behavior does this test prove?
2. Would this test fail if the business rule were broken?
3. Is this asserting meaningful outcomes, or just that the page loads?
4. Is it testing implementation details rather than observable behavior?
5. Does it cover both success and failure paths?
6. Does it rely on fragile assumptions about IDs or ordering?
7. Is setup minimal and clear?

If the test would still pass after you deliberately break the intended behavior, it is not a good test.

A useful discipline exercise is this:

1. Accept the AI-generated test.
2. Temporarily break the feature intentionally.
3. Run the test.
4. Confirm that it fails for the right reason.

If it does not fail, the test is weak.

## When AI is most valuable in testing

AI is most helpful for:

* Generating edge-case lists
* Drafting repetitive scaffolding
* Suggesting additional assertions you may have missed
* Explaining complex tracebacks
* Refactoring test duplication

It is least reliable when:

* Interpreting ambiguous requirements
* Inferring security rules
* Guessing business logic
* Designing a test strategy from scratch without clear constraints

Tests are executable specifications. AI can help you write them faster, but it cannot decide what your system should guarantee.

AI-generated tests can look impressive, run green, and still assert nothing that matters.

Used carefully, AI helps. Used lazily, it gives you more code to review. The difference is not in the model. It is in you, the human reviewer.
