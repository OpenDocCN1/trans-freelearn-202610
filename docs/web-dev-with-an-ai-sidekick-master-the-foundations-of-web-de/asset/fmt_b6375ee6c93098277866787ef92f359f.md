## Grouping elements with `<g>`

As soon as your SVG has more than a couple of shapes, you’ll want a way to organize them. The `<g>` element groups shapes together so you can move them, style them, or hide them as a unit.

Here’s the badge icon again, but with logical grouping:

```svg
<svg viewBox="0 0 180 180" width="180" 
     xmlns="http://www.w3.org/2000/svg">
  <!-- Badge background -->
  <g class="badge-base">
    <circle cx="90" cy="90" r="70" />
    <circle cx="90" cy="90" r="52" />
  </g>
  <!-- Checkmark -->
  <g class="badge-check">
    <line x1="60" y1="95" x2="82" y2="115" />
    <line x1="82" y1="115" x2="122" y2="70" />
  </g>
</svg>
```

Notice what’s missing: color and stroke details, because those will move into CSS. SVG becomes much easier to maintain once you stop hard-coding styles into every element.

## Styling SVG with CSS

Inline SVG can be styled using regular CSS. You can place styles in a `<style>` block, a separate CSS file, or alongside your existing site styles.

Here’s how to style the grouped badge using CSS classes:

```css
<style>
  svg {
    max-width: 220px;
  }
  .badge-base circle:first-child {
    fill: #e6f4ea;
    stroke: #1e8e3e;
    stroke-width: 6;
  }
  .badge-base circle:last-child {
    fill: white;
  }
  .badge-check line {
    stroke: #1e8e3e;
    stroke-width: 10;
    stroke-linecap: round;
  }
</style>
```

This should feel familiar if you’ve already worked through the CSS chapter. The selectors work the same way. The only difference is that properties like `fill` and `stroke` apply to SVG shapes instead of text or boxes.

Moving style into CSS gives you three advantages:

* Your SVG becomes readable markup instead of a pile of attributes.
* You can change colors for dark mode, themes, or hover states.
* Designers and developers can change the drawing and its styling separately.

Try this small experiment. Add a hover effect to the badge:

```css
svg:hover .badge-base circle:first-child {
  fill: #d2eadc;
}
```

## Transforms on groups

One more reason `<g>` is useful is transforms. You can move, scale, or rotate an entire group with a single attribute, as shown highlighted in the following code:

```svg
<g class="badge-check" transform="rotate(-5 90 90)">
  <line x1="60" y1="95" x2="82" y2="115" />
  <line x1="82" y1="115" x2="122" y2="70" />
</g>
```

This rotates the checkmark slightly around the center of the SVG at (90, 90). Without grouping, you’d have to recalculate every coordinate manually, which is tedious and prone to error.

# Custom shapes using paths

So far, SVG has felt friendly. Rectangles, circles, and lines get you a long way, but they can’t describe arbitrary shapes. The moment you want icons, waves, blobs, arrows, or anything that looks *designed*, you end up using `<path>`. Paths give SVG its flexibility, but they are often the hardest part for beginners.

## The `<path>` element

A `<path>` is a sequence of drawing commands stored in a single attribute called `d`. The `d` attribute is a set of instructions for an invisible pen: move here, draw a line there, draw a curve like this, close the shape (meaning draw a line back to the starting point).

Here’s the smallest possible path that actually draws something, a horizontal line, as shown in *Figure 4.4* and the following code:

```svg
<svg viewBox="0 0 120 120" width="200" 
     xmlns="http://www.w3.org/2000/svg">
  <path
    d="M 20 60 L 100 60"
    stroke="black"
    stroke-width="6"
    fill="none"
  />
</svg>
```

![](Images/B34553_04_04.png)

*Figure 4.4: A horizontal line drawn using a path*

Read that `d` value slowly:

* `M 20 60` means *move the pen to (20, 60)*
* `L 100 60` means *draw a line to (100, 60)*

Nothing is filled because we explicitly said `fill="none"`. Without that, SVG would try to fill the shape, which makes no sense for a single line.

## Why paths look intimidating at first

Paths look intimidating because all the logic is compressed into one string. There are no named attributes like `x`, `y`, or `r`. But each command is simple on its own, and most real-world paths are built from a few command types.

The commands you’ll use most often are:

* `M` move to
* `L` line to
* `C` cubic Bézier curve
* `Q` quadratic Bézier curve
* `Z` close path

Uppercase commands use absolute coordinates. Lowercase versions (`m`, `l`, `c`, `q`) use relative coordinates. For beginners, absolute coordinates are much easier to understand, so stick to uppercase while learning.

## A closed shape with Z

Here’s a simple house-like shape drawn with straight lines, as shown in *Figure 4.5* and the following code:

```svg
<svg viewBox="0 0 120 120" width="200" xmlns="http://www.w3.org/2000/svg">
  <path
    d="
      M 20 70
      L 60 30
      L 100 70
      L 100 100
      L 20 100
      Z
    "
    fill="#cfe8ff"
    stroke="#1f5fbf"
    stroke-width="4"
  />
</svg>
```

![](Images/B34553_04_05.png)

*Figure 4.5: A house drawn with a path*

The important new command is `Z`, which closes the path by drawing a line back to the starting point. Once a path is closed, fill suddenly makes sense, because the shape encloses an area.

## Drawing curves with paths

Straight lines are fine, but curves are where paths show their strengths. SVG uses Bézier curves, which are controlled by points that *pull* the curve into shape.

**Prompt:** Please explain control points in SVG curves with code examples.

Here’s a smooth wave using a cubic Bézier curve (`C`), as shown in *Figure 4.6*:

```svg
<svg viewBox="0 0 300 120" width="300" 
     xmlns="http://www.w3.org/2000/svg">
  <path
    d="
      M 10 60
      C 60 10, 120 110, 170 60
      C 220 10, 280 110, 330 60
    "
    fill="none"
    stroke="#6a5acd"
    stroke-width="6"
  />
</svg>
```

![](Images/B34553_04_06.png)

*Figure 4.6: A curvy line drawn with a path*

Each `C` command takes six numbers (three pairs of coordinates):

* First control point (X and Y coordinates)
* Second control point (X and Y coordinates)
* End point (X and Y coordinates)

The curve starts where the previous command ended. You don’t need to understand the math to use this effectively. The useful way to think about it is that *control points pull the curve toward themselves*, as shown in *Figure 4.7*:
