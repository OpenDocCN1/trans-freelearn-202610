## Avoiding SQL injection

The safest approach is simple: use Django’s ORM:

```
# Safe
User.objects.filter(username=username)
```

Avoid constructing SQL queries manually using string concatenation. If you must use raw SQL, use parameterized queries.

Django’s documentation emphasizes that its ORM protects against SQL injection by default, but only when used properly.

## Securing authentication

Login endpoints are a favorite target for bots.

Basic protections include:

* Enforce strong passwords
* Add rate limiting to login attempts
* Consider adding a human-verification challenge after repeated failures
* Avoid exposing the Django admin at predictable URLs without additional protection

A simple rate-limiting approach can dramatically reduce brute-force attempts.

## Handling file uploads safely

If your app allows file uploads:

* Limit file size
* Validate file types
* Never execute uploaded files
* Store uploads outside your main application domain

Django recommends serving uploaded files from a separate domain or storage system to reduce risk.

## Defending against denial-of-service

For a small project, most DoS attempts are actually abusive usage patterns.

Common examples:

* Repeated login attempts
* Large file uploads
* Expensive database queries
* Aggressive crawling

Low-cost defenses include:

* Rate limiting key endpoints
* Limiting upload size
* Using caching where appropriate
* Moving static files to a CDN

Using a service like Cloudflare can provide free or low-cost protection, including basic **Distributed Denial of Service** (**DDoS**) mitigation and request filtering.

## Protecting secrets and configuration

Never store secrets in your source code repository.

Use environment variables instead:

```
import os
SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]
```

Django’s deployment guidance stresses that sensitive settings must remain confidential.

## Logging, monitoring, and backups

Security is not just about prevention. You must also detect and recover.

At a minimum:

* Enable logging for errors and suspicious activity
* Monitor failed login attempts
* Keep regular database backups
* Test restoring from backups

For example, add the following code to your `settings.py`:

```
import os
LOG_DIR = os.path.join(BASE_DIR, "logs")
os.makedirs(LOG_DIR, exist_ok=True)
LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,
    "formatters": {
        "verbose": {
            "format": "{asctime} {levelname} {name} {message}",
            "style": "{",
        },
    },
    "handlers": {
        "file": {
            "level": "WARNING",
            "class": "logging.FileHandler",
            "filename": os.path.join(LOG_DIR, "django.log"),
            "formatter": "verbose",
        },
    },
    "loggers": {
        "django": {
            "handlers": ["file"],
            "level": "WARNING",
            "propagate": True,
        },
    },
}
```

The preceding code:

* Logs warnings, errors, and exceptions
* Writes to `logs/django.log`
* Captures suspicious activity like bad requests or errors

To check the server logs, use the following Bash/shell commands:

```
sudo journalctl -u gunicorn -f
sudo tail -f /var/log/nginx/error.log
```

To log failed logins, add the following code to your login view:

```
import logging
logger = logging.getLogger(__name__)
def login_view(request):
    if request.method == "POST":
        username = request.POST.get("username")
        password = request.POST.get("password")
        user = authenticate(request, username=username, password=password)
        if user is None:
            logger.warning(f"Failed login attempt for username: {username}")
        else:
            login(request, user)
```

OWASP highlights that failures in logging and monitoring can allow attacks to go unnoticed for long periods.

## Use a ready-made package to track logins

To track failed login attempts, temporarily block brute-force attacks, and store attempts in the database, you can install a Django middleware package named Axes:

```
pip install django-axes
```

Then enable the package in `settings.py`:

```
INSTALLED_APPS += ["axes"]
MIDDLEWARE += ["axes.middleware.AxesMiddleware"]
AUTHENTICATION_BACKENDS = [
    "axes.backends.AxesBackend",
    "django.contrib.auth.backends.ModelBackend",
]
AXES_FAILURE_LIMIT = 5
AXES_COOLOFF_TIME = 1  # hours
```

This package logs to permanent tables so you must then run database migrations:

```
python manage.py migrate
```

## Summary checklist

For a beginner-friendly deployment, aim for the following:

* Disable debug mode
* Enforce HTTPS everywhere
* Use secure cookies
* Configure `ALLOWED_HOSTS`
* Keep secrets out of source control
* Use Django’s ORM and built-in protections
* Add rate limiting to login and public endpoints
* Limit and validate file uploads
* Put a CDN or proxy in front of your site
* Enable logging and maintain backups

Each of the preceding points is covered in detail in either this chapter or [*Chapter 9*](#09.xhtml#_idTextAnchor598), *Django – Web Development on the Backend*.

This does not make your application invulnerable. It makes it robust enough for production use, which is exactly what you need for a public-facing example like `TallyApp`.

# Deploying TallyApp

The first step is to pick a host server provider. This is the machine that will run your application continuously and make it accessible to users over the internet. Unlike your local development environment, this server must be reliable, reachable at all times, and capable of handling requests from unknown users and automated systems.

There are several categories of hosting to choose from, each with different trade-offs. Shared hosting is inexpensive but too restrictive for most Django applications. Platform-as-a-service options remove much of the operational burden, but they also hide how deployment actually works. At the other end of the spectrum, large cloud providers offer enormous flexibility, but can introduce unnecessary complexity for a small project. For a project like `TallyApp`, a VPS strikes the right balance. It gives you full control over a Linux machine at a low cost, while still being simple enough to understand how all the pieces fit together.

Choosing a VPS also aligns well with the architecture introduced earlier in this chapter. You will install and configure each component yourself: the web server, the application server, and the database. This might sound like extra work, but it is where much of the learning happens. Instead of relying on a black-box platform, you will see exactly how requests flow through your system and how your application behaves in a real environment.
