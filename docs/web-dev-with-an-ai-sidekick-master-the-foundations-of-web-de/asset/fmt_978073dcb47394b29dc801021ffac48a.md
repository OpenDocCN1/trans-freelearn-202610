
**Good practice**: Keep your `.dockerignore` file aligned with your `.gitignore` file, but do not assume they should be identical. Docker cares about build context and image contents, while Git cares about version control. Some files, like `Dockerfile` or `docker-compose.yml`, are tracked by Git but usually do not belong inside the final image.

## Creating a Docker Compose file

Next, we will define a `docker-compose.yml` file. While a `Dockerfile` defines how to build a single image, and a `.dockerignore` file excludes files and folders from an image, a `docker-compose.yml` file defines how to run multiple containers together.

You could run your Django container manually with `docker run`, but it would get messy fast. You would need to start PostgreSQL separately, link containers manually, pass environment variables by hand, and manage ports and volumes yourself. Docker Compose replaces all of that with one command and a single config file.

The `docker-compose.yml` file is **orchestration**. It answers:

* What containers do we need?
* How do they connect?
* What environment variables do they use?
* What ports are exposed?
* What volumes persist data?

For our TallyApp project, Docker Compose will define two services:

* `web` is the Django app container (built from the `Dockerfile`)
* `db` is a PostgreSQL container

It will also:

* Connect the two containers via a network
* Map ports (`8000`, `5432`)
* Set environment variables for the Django project
* Create a volume for database persistence

Running a single command, `docker compose up`, will start the entire system, not just one container.

In the `Chapter11\tallyapp` folder, create a `docker-compose.yml` file for Django and PostgreSQL:

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: tallyapp
      POSTGRES_USER: tallyapp
      POSTGRES_PASSWORD: tallyapp_password_change_me
    volumes:
      - tallyapp_postgres_data:/var/lib/postgresql/data
    ports:
      - "5432:5432"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U tallyapp -d tallyapp"]
      interval: 5s
      timeout: 5s
      retries: 5
  web:
    build:
      context: .
    depends_on:
      db:
        condition: service_healthy
    environment:
      # Django will read these to build DATABASES config (you wire this up in settings.py)
      DJANGO_DB_NAME: tallyapp
      DJANGO_DB_USER: tallyapp
      DJANGO_DB_PASSWORD: tallyapp_password_change_me
      DJANGO_DB_HOST: db
      DJANGO_DB_PORT: "5432"
      DJANGO_SECRET_KEY: dev-only-change-me
      DJANGO_DEBUG: "1"
    ports:
      - "8000:8000"
    volumes:
      - .:/app
volumes:
  tallyapp_postgres_data:
```

Note the following about the preceding code:

* `db` uses the official PostgreSQL image and initializes a database using environment variables documented for that image.
* `db` has a `healthcheck`, and `web` depends on `db` being `service_healthy`, not merely started.
* The `tallyapp_postgres_data` volume is what keeps database data persistent across container restarts.
* The `web` service builds from your `Dockerfile`.
* The `volumes: - .:/app` bind-mount means code changes on the host instantly appear inside the container, which is ideal for a Docker-based dev environment.
* `depends_on` starts the database container before the web container, but by itself it does not guarantee that PostgreSQL is ready to accept connections. To make startup more reliable, we defined a PostgreSQL `healthcheck` and set `depends_on` to wait for condition: `service_healthy`. Then Docker Compose waits until the database reports that it is ready before starting Django.

## Switching from SQLite to PostgreSQL

Now we can configure project files like the Python dependencies and Django project settings so that the project uses PostgreSQL instead of SQLite:

1. In the `Chapter11\tallyapp` folder, create a `requirements.txt` file to configure Django 6 to use PostgreSQL in Docker:

```
Django>=6.0,<7.0
psycopg[binary]>=3.1
```

2. In `settings.py`, you can switch database config based on environment variables. A simple pattern is:

* If `DJANGO_DB_HOST` is set, use PostgreSQL
* Otherwise, fall back to SQLite for local non-Docker runs

```python
import os
DJANGO_DB_HOST = os.environ.get("DJANGO_DB_HOST")
if DJANGO_DB_HOST:
    # PostgreSQL configuration
    DATABASES = {
        "default": {
            "ENGINE": "django.db.backends.postgresql",
            "NAME": os.environ.get("DJANGO_DB_NAME", "tallyapp"),
            "USER": os.environ.get("DJANGO_DB_USER", "tallyapp"),
            "PASSWORD": os.environ.get("DJANGO_DB_PASSWORD", ""),
            "HOST": DJANGO_DB_HOST,
            "PORT": os.environ.get("DJANGO_DB_PORT", "5432"),
            "CONN_MAX_AGE": 60,  # persistent connections (good for production)
        }
    }
else:
    # SQLite fallback (default for local development)
    DATABASES = {
        "default": {
            "ENGINE": "django.db.backends.sqlite3",
            "NAME": BASE_DIR / "db.sqlite3",
            "OPTIONS": {
                "timeout": 20,  # helps reduce "database is locked" errors
            },
        }
    }
```

## Build and run the Docker system

Now we can build the Docker image and start the containers using Docker Compose:

1. Build images:

```
docker compose build
```

2. Start containers:

```
docker compose up
```

3. At this point PostgreSQL is running in one container, and Django is running in another container, exposed on [http://localhost:8000](http://localhost:8000), as shown in *Figure 11.2*:

2. In a new terminal window, run migrations and create an admin user inside the `web` container:

```
docker compose exec web python manage.py migrate
docker compose exec web python manage.py createsuperuser
```

Docker changes where you run commands and where you look for errors. You usually do not SSH into a server. You run commands inside the container that already has your app and dependencies. You also read the container logs, because that is where the app is running.

3. Start your preferred browser and navigate to the admin site: [http://localhost:8000/admin/](http://localhost:8000/admin/)

5. Close the browser.

6. At the command prompt or terminal, stop the containers:

```
docker compose down
```

To stop containers and remove volumes (this wipes the database) use the `-v` switch: `docker compose down -v`. This reinforces why volumes matter. Without a volume, a database container is disposable, and so is its data.
