## Execution order is top-to-bottom

The first idea is that JavaScript is executed step by step, from top to bottom. When the browser encounters JavaScript, it reads each statement in order and runs it immediately unless told otherwise. That sounds obvious, but it explains a lot of beginner confusion. If you try to use something before it exists, JavaScript will complain. Order matters.

Create a second file in the same folder as the HTML file named `code-order.js`.

In `code-order.js`, add the following code:

```javascript
console.log("1) Script started.");
const statusElement = document.querySelector("#status");
statusElement.textContent = "Status: JavaScript is running.";
console.log("2) Updated the status paragraph.");
const messageElement = document.querySelector("#message");
messageElement.textContent = "Message: The script ran top-to-bottom.";
console.log("3) Updated the message paragraph.");
console.log("4) Script finished.");
```

The expression `document.querySelector("#status")` returns a reference to the element on the web page with the `id` of `status`. You will learn more about this and other ways of working with a page's DOM in a later section in this chapter. For now, this is all you need to know.

**Prompt**: How does the browser render the DOM and when does JavaScript run during page load? A common beginner mistake is trying to access DOM elements before the browser has parsed them.

Open the web page in your browser and view **Developer Tools**, as shown in *Figure 5.1*:

1. In the Chrome toolbar, click the three dots to open the main menu.
2. In the menu, click **More tools**.
3. In the submenu, click **Developer Tools** (and note the keyboard shortcut).
4. In **Developer Tools**, click the **Console** tab.

## Comments for documenting your code

Comments are notes for people reading the code, not for the browser. The JavaScript engine completely ignores them. Comments exist to explain why code is there, clarify tricky logic, and temporarily disable code while you are experimenting or debugging. Used well, comments help readers understand intent. Used badly, they add clutter or fall out of date and mislead the comment reader.

JavaScript supports two kinds of comments.

- Single-line comments start with `//`. Everything after `//` on that line is ignored. These are best for short explanations or quick notes. They are also commonly used to explain why something is done a certain way, which is often more valuable than explaining what the code does:

```javascript
// This is a single-line comment.
let counter = 0; // This comment might explain why the variable named counter exists and has been initialized to zero.
```

- Multi-line comments start with `/*` and end with `*/`. Everything inside is ignored, even if it spans multiple lines:

```javascript
/*
  This is a multi-line comment.
  It can span several lines
  and is useful for longer explanations.
*/
let total = 10;
```

Multi-line comments are often used for file-level explanations or for temporarily commenting out a block of code during testing, as shown in the following code:

```javascript
/*
function calculateTotal(price, tax) {
  return price + tax;
}
*/
```

Be careful with this technique. It is easy to forget commented-out code and leave dead logic behind.

A note about phrasing related to comments. You **comment** code by adding descriptive text above or after code statements. You **comment out** code by adding comment characters before or around statements to make them inactive. **Uncommenting** means removing the comment characters.

Comments are especially useful when the code expresses *how* something is done but not *why*. For example, the following code is obvious:

```javascript
counter = counter + 1;
```

A comment explaining *why* might actually help:

```javascript
// Increment the counter to track user clicks for analytics.
counter = counter + 1;
```

Avoid comments that simply repeat what the code already says. This adds clutter without adding understanding. Anyone who can read JavaScript already knows what the line does.

Comments are also useful when working with an AI sidekick. When you ask an AI to help with a function, a short comment describing the job often gives better results:

```javascript
// Update the UI so it reflects the current counter value.
function renderCounter() {
  counterEl.textContent = String(counter);
}
```

Finally, remember that comments do not run, cannot fix bugs, and cannot replace clear naming. If you find yourself writing long comments to explain confusing code, that is usually a sign the code itself should be simplified. Good JavaScript should be clear enough that comments mostly explain why, not what or how.
