
# Model Field Options and SQL Injection

## Common Field Options (Table 9.2)

*Table 9.2: Common field options and their descriptions*

| **Field option** | **Description** |
| --- | --- |
| `null=True` | The database column may store SQL `NULL`. |
| `blank=True` | Forms and validation allow an empty value. |
| `default=...` | Sets a default for newly created rows. |
| `unique=True` | Enforces uniqueness at the database level. |
| `choices=[(...), (...)]` | Constrains values to a fixed set, useful for status fields. |

### Warning

A common beginner pitfall is mixing up `null` and `blank`. As a rule of thumb: `blank` is about validation, especially when filling in forms, while `null` is about how the database stores the value. For text fields, Django often prefers empty strings rather than `NULL`, so you will frequently use `blank=True` without `null=True` on `CharField` and `TextField`.

## SQL Injection and How Django Prevents It

SQL injection is one of the oldest and most damaging web application vulnerabilities. It happens when user input is treated as part of a SQL command instead of as data.

You already know how SQL queries work. The problem begins when an application builds those queries using strings.

Here is a simplified example in Python using raw SQL:

```
email = request.GET.get("email")
query = f"SELECT * FROM users WHERE email = '{email}'"
cursor.execute(query)
```

This looks harmless. But it is fundamentally unsafe.

If a user supplies this value:

```
' OR 1=1 --
```

The query becomes:

```
SELECT * FROM users WHERE email = '' OR 1=1 --'
```

That condition is always `true`. The query now returns every user in the database. The database is doing exactly what you asked. The problem is that you allowed the user to change the meaning of the query.

SQL does not distinguish between code (the structure of the query) and data (the values being compared). If you build SQL using string concatenation, you blur that boundary. The database cannot tell where your query ends and user input begins.

Instead of inserting values into SQL strings, you pass them separately:

```
cursor.execute(
    "SELECT * FROM users WHERE email = %s",
    [email]
)
```

Now the SQL query structure is fixed, and the value is treated strictly as data. Even if the user enters malicious input, it cannot change the query’s meaning.

The good news is that Django’s ORM protects you automatically when used correctly.

For example:

```
User.objects.filter(email=email)
```

Django generates SQL internally and safely binds parameters. The input is never treated as executable SQL. This is one of the main reasons to use an ORM. It removes an entire class of security bugs by design.

But even in Django, SQL injection is still possible if you step outside the ORM.

For example:

```
cursor.execute(f"SELECT * FROM users WHERE email = '{email}'")
```

or:

```
User.objects.raw(
    f"SELECT * FROM users WHERE email = '{email}'"
)
```

Both reintroduce the same vulnerability. Remember: you also need to review code written by an AI. That means recognizing dangerous patterns such as raw SQL built from user input.

### Good Practice

Django ORM queries are safe by default. Raw SQL is safe only if you use parameters. String concatenation is always unsafe. If you remember nothing else, remember this: Never mix user input directly into a SQL string.

In web development, especially with AI-assisted coding, it is very easy to generate working code quickly. It is also very easy to generate insecure code quickly.

SQL injection is a good example of the difference between code that works and code that is safe. The database will happily execute whatever valid SQL it receives. It is your responsibility to make sure that SQL cannot be manipulated by users.

# Django Views and Templates

Views and templates are the point where your data becomes something a user can actually see. Models define what the data looks like, but views decide which data is used for a request, and templates decide how that data is presented as HTML.

## Views

A Django view is a Python function or class that takes an HTTP request and returns an HTTP response. Most views follow the same basic shape: fetch some data using models, then return a rendered template.

In your `blog` app, in `views.py`, import your `Post` model and add code to define a `post_list` function, as shown highlighted in the following code:

```
from django.shortcuts import render
from blog.models import Post
# Create your views here.
def post_list(request):
    posts = (
        Post.objects
        .filter(status="published")
        .order_by("-created_at")
    )
    return render(request, "blog/post_list.html", {"posts": posts})
```

The `render` helper function combines three things into a single response: the incoming request, a template name, and a context dictionary. The context dictionary is how you pass Python objects into the template.

To make this view callable from a web browser, you map it to a URL. In your `blog` app, create `urls.py`:

```
from django.urls import path
from .views import post_list
urlpatterns = [
    path("", post_list, name="post_list"),
]
```

Then include the app’s URLs in the project’s main `urls.py` by importing the `include` function and adding an entry for an empty path `""` to `urlpatterns`, as shown highlighted in the following code:

```
from django.contrib import admin
from django.urls import path, include
urlpatterns = [
    path("admin/", admin.site.urls),
    path("", include("blog.urls")),
]
```

At this point, a request to `/` will call `post_list`, fetch published posts from the database, and render a template.

## Improving Performance by Prefetching Related Data

When your template accesses related objects such as `post.author` or `post.tags`, Django may run additional database queries for each post. This can quickly become inefficient as the number of posts grows.

The `select_related()` method tells Django to fetch related objects, like `author`, in the same database query using a SQL join. The `prefetch_related()` method handles relationships like tags by running a second query and combining the results in Python.

Using these methods avoids the common N+1 query problem, where one query for a list of objects triggers many additional queries for related data.

An improved version of the `post_list(request)` method would add calls to both methods, as shown highlighted in the following code:

```
def post_list(request):
    posts = (
        Post.objects
        .filter(status="published")
        .select_related("author")
        .prefetch_related("tags")
        .order_by("-created_at")
    )
    return render(request, "blog/post_list.html", {"posts": posts})
```

Before optimizing a view, check what the template will access, how that translates into database queries, and where performance problems actually come from. An AI can generate a working `post_list()` function in seconds, but it may not reliably predict what data you will use in your template or the best way to optimize database access.

You must make judgments about behavior, not just writing code.
