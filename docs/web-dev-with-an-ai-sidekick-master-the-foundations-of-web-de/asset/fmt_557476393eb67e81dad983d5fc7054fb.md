
# Normalization

Normalization exists largely to prevent these problems. Normalization is a systematic way of structuring tables to reduce redundancy and dependency issues, typically by splitting data into related tables and linking them with keys.

You can learn more about the standard normal forms (1NF, 2NF, 3NF) and how they eliminate these anomalies at the following links: [https://www.guru99.com/database-normalization.html](https://www.guru99.com/database-normalization.html) and [https://en.wikipedia.org/wiki/Database_normalization](https://en.wikipedia.org/wiki/Database_normalization)

## Normalization: storing facts once

Normalization is the process of organizing data so that each fact is stored in exactly one place to provide a single source of truth. In practice, this usually means:

* Creating separate tables for separate concepts
* Using primary keys to identify rows
* Using foreign keys to reference related data
* Removing repeated or derived values

For example, instead of storing a person's name in every episode they appear in, you store the person once in a `person` table and reference them from an appearance or credit table. If the person's name changes, there is exactly one row to update.

Beginners often worry that splitting data into more tables makes querying harder. In reality, the opposite is true over time. Well-designed schemas lead to predictable joins and simpler logic. Poor schemas lead to string parsing, duplicated filters, and fragile assumptions.

Joins exist precisely to recombine normalized data at query time. That is the trade-off relational databases make: store data cleanly and consistently, then reconstruct the views you need using SQL.

Schema design decisions are hard to undo once data exists. Adding a new column is easy. Untangling duplicated data across millions of rows is not. That is why spending time on tables, rows, columns, and relationships early on pays off disproportionately later.

Good database schema design is about respecting what tables, rows, and columns are meant to represent, and resisting the temptation to repeat data for short-term convenience.

## Primary and foreign keys

Primary keys and foreign keys are what give a relational database its identity and structure. They answer two fundamental questions: *Who is this row?* and *How does this row relate to others?*

### Primary keys are for identity

A primary key uniquely identifies each row in a table. It is the database's notion of identity. No two rows in the same table can share the same primary key value, and a primary key cannot be `NULL` (meaning *unknown* or *not applicable*, which will be explained in more detail in a later section).

In practice, a primary key is usually a single column, often an auto-incrementing integer or a GUID. The actual value rarely matters to humans. What matters is that it is stable and unique. Titles can change, names can be corrected, and emails can be updated, but the primary key stays the same. This is why primary keys should never encode meaning or business logic.

For example, a person's name is a poor primary key. Names are not unique and they change. An internal `person_id` is a good primary key because it exists solely to identify the row.

Primary keys also serve as the target for relationships. Other tables point to them to say, *This row refers to that row*.

In SQLite, declaring a column as `INTEGER PRIMARY KEY` gives it a special role. The column becomes an alias for the internal `rowid`, and when you insert a row without providing a value, SQLite automatically assigns a unique integer. In practice, this behaves like an auto-incrementing ID, typically increasing by one each time a new row is added.

It is worth knowing that SQLite also supports an explicit `AUTOINCREMENT` keyword, but this is rarely needed. Without it, SQLite will usually pick the next highest unused value, which is fast and efficient. With `AUTOINCREMENT`, SQLite guarantees that it will never reuse a previously issued value, even if rows are deleted, but this comes with a small performance and storage cost. For most applications, `INTEGER PRIMARY KEY` on its own is the better choice.

Other database systems provide similar features, but with different syntax and behavior. In MySQL, you use the `AUTO_INCREMENT` attribute to achieve the same effect. In PostgreSQL, older code often uses `SERIAL`, while modern versions recommend `GENERATED AS IDENTITY`, which is more flexible and standards compliant. Although the goal is the same across all systems, which is to generate unique numeric identifiers automatically, the exact rules and guarantees can vary slightly, especially around gaps in sequences and reuse of deleted values.

### Foreign keys are for relationships

A `foreign key` is a column in one table that references the primary key of another table. It represents a relationship between two entities.

For example, an episode belongs to a series. The episode table might contain a `series_id` column that references the primary key of the `series` table. That `series_id` is a foreign key.

Foreign keys let the database enforce rules about relationships. With a foreign key in place, the database can prevent:

* Inserting a row that refers to a non-existent parent
* Deleting a parent row that still has dependent rows
* Creating orphaned records that no longer make sense

This enforcement is a major advantage of relational databases over ad-hoc data storage.

### One-to-many relationships

The most common relationship is one-to-many. One series has many episodes. One customer has many orders. One author has many books.

In a one-to-many relationship, the foreign key lives on the many side. Each episode row stores the `series_id` it belongs to. The `series` table does not need to know how many episodes it has. That information can always be derived by querying the `episodes` table.

Figure 7.1 shows a classic one-to-many relationship between the `people` table and the `emails` table. On the left, the `people` table stores one row per person, identified by a unique `id`. On the right, the `emails` table stores email addresses. Each email row includes a `person_id`, which links it back to the person it belongs to. The key idea is that one person can have many email addresses, but each email address belongs to only one person:

You can see this in the sample data:

* John Doe (id = 1) has two email addresses: `john_doe@gmail.com` and `jdoe@work.com`. Both rows in the `emails` table have `person_id = 1`.
* Jane Doe (id = 2) has one email: `janed@msn.com`
* Mika Jones (id = 3) also has one email: `m_jones@gmail.com`

So, the relationship works like this:

* `people.id` is the primary key
* `emails.person_id` is a foreign key
* The foreign key allows multiple rows in emails to point to the same row in people

The `1---M` notation in the diagram reinforces this: one row in people maps to many rows in emails. The duplication lives on the "many" side. The person_id value repeats in the emails table, and that repetition is what creates the relationship.
