
# TypeScript 类型系统核心概念

## Union Types

```typescript
function formatId(id: number | string): string {
  if (typeof id === "number") {
    return id.toFixed(0);
  }
  return id.toUpperCase();
}
```

Inside each branch, TypeScript understands exactly which type you are working with and allows only the appropriate operations. If you forget to handle one of the cases, the compiler can warn you.

Union types are also commonly used with literal types to describe fixed sets of values:

```typescript
type Status = "active" | "inactive" | "pending";
```

This creates a union of string literal types, which is ideal for modeling states and modes in an application.

A useful way to remember it:

- **Basic types** describe categories of values
- **Literal types** describe exact values
- **Union types** describe a controlled choice between them.

Like interfaces and other types in TypeScript, union types exist only during development. They do not affect runtime behavior, but they dramatically reduce ambiguity while you are writing and changing code.

When a value can legitimately be more than one thing, union types let you say so explicitly, without falling back to overly permissive types like `any`.

## Optional Properties

Not every object has all properties all the time. Interfaces support optional properties using `?`:

```typescript
interface User {
  name: string;
  age?: number;
}
```

Now both of these are valid:

```typescript
const a: User = { name: "Mark", age: 42 };
const b: User = { name: "Guest" };
```

When you use an optional property, TypeScript forces you to acknowledge that it might be missing:

```typescript
function describe(user: User): string {
  if (user.age !== undefined) {
    return `${user.name} is ${user.age}`;
  }
  return `${user.name} (age unknown)`;
}
```

This prevents a large class of `cannot read property of undefined` errors.

## Making Absence Explicit with `null` and `undefined`

In JavaScript, `null` and `undefined` are easy to ignore until they cause a runtime error. But in TypeScript, they are much harder to ignore because they become part of the stricter type system. This is one of the biggest practical differences between JavaScript and TypeScript.

With strict type checking enabled (which you should be using), `null` and `undefined` are not automatically allowed. You must explicitly say when a value can be missing (`undefined`).

For example:

```typescript
let name: string = "Mark";
name = undefined; // Error
```

If a value really might be missing, you must say so:

```typescript
let name: string | undefined;
```

Now TypeScript understands that `name` may or may not exist.

You already saw the `?` syntax with optional properties:

```typescript
interface User {
  name: string;
  age?: number;
}
```

Now I can explain that the `?` does not just mean optional. It really means:

```typescript
age: number | undefined
```

That is why TypeScript forces you to check:

```typescript
if (user.age !== undefined) {
  console.log(user.age);
}
```

This is TypeScript forcing you to deal with reality: the value might not be there.

The distinction between `null` vs `undefined` in TypeScript still exists:

- `undefined` usually means "not provided" or "not set"
- `null` usually means "explicitly empty"

But in practice, many teams standardize on one (often `undefined`) to reduce confusion.

If you want to allow both, you must say so:

```typescript
let value: string | null | undefined;
```

Most common JavaScript runtime errors look like this:

```
Cannot read property 'x' of undefined
```

TypeScript pushes those problems earlier. Instead of failing at runtime, you get an error while writing the code:

```
"Object is possibly undefined"
"Type 'undefined' is not assignable to type 'string'"
```

That forces you to stop assuming values exist and start handling the missing case explicitly.

> **Good practice**: If a value might be missing, say so in the type. If it must exist, do not include `undefined` or `null`. Handle missing cases explicitly instead of hoping they never happen.

## Optional Parameters versus Default Parameter Values

TypeScript supports two related but distinct ways of handling function parameters that may not always be provided: optional parameters and default parameter values. They solve similar problems, but they communicate slightly different meanings.

An optional parameter is marked with a question mark:

```typescript
function greet(name?: string): string {
  if (name) {
    return `Hello, ${name}`;
  }
  return "Hello, guest";
}
```

In the preceding code, `name` may be omitted when the function is called. From TypeScript's point of view, an optional parameter is treated as a union with `undefined`. In other words, `name` has the type `string | undefined`. That is why TypeScript forces you to check that it exists before using it as a string.

Default parameter values look similar, but behave differently:

```typescript
function greet(name: string = "guest"): string {
  return `Hello, ${name}`;
}
```

In this case, `name` is not optional from the type system's perspective. It is always a string inside the function body. If the caller omits the argument, JavaScript supplies the default value at runtime, and TypeScript reflects that behavior in its types.

This difference matters when you are writing function logic. With an optional parameter, you must handle the missing case explicitly. With a default value, TypeScript knows the parameter will never be `undefined` inside the function.

There is also a difference at the call site. Both of these calls are valid in both cases:

```typescript
greet();
greet("Mark");
```

But defaults make the meaning clearer. Optional parameters say `this value might not exist`. Default parameters say `this value always exists but may fall back to a standard value`.

> **Good practice**: Use optional parameters when the absence of a value is meaningful and must be handled explicitly. Use default parameter values when there is a sensible fallback and you want the rest of the function to work with a guaranteed, well-defined type.

## Preventing Errors Instead of Catching Them

In JavaScript, error handling often means reacting after something goes wrong using `try` and `catch`. TypeScript shifts that balance. Many errors are prevented at compile time, before the code runs at all.

Consider this JavaScript example:

```javascript
function formatName(user) {
  return user.name.toUpperCase();
}
```

If `user` is `null` or missing the `name` property, this fails at runtime.

In TypeScript, you would write:

```typescript
function formatName(user: { name: string }): string {
  return user.name.toUpperCase();
}
```

Now the problem happens earlier:

- If you pass the wrong shape, TypeScript complains immediately
- The error appears when you call the function, not deep inside it

This is the main improvement to error handling in TypeScript compared to JavaScript: you prevent the error instead of catching it later.

TypeScript encourages you to design functions that make invalid states harder to represent.

For example:

```typescript
function greet(name: string | undefined): string {
  if (!name) {
    return "Hello, guest";
  }
  return `Hello, ${name}`;
}
```

The type forces you to handle the missing case. Without TypeScript, it would be easy to forget that check.

But TypeScript does not eliminate runtime errors entirely. You still need `try` and `catch` for:

- Network requests
- File access
- JSON parsing
- Third-party libraries

Example:

```typescript
try {
  const data = JSON.parse(input);
  console.log(data);
} catch (error) {
  console.error("Invalid JSON:", error);
}
```
