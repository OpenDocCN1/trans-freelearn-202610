## Summary

In this chapter, you deployed TallyApp as a public web application instead of a local development project. You saw how a production `Django` stack separates responsibilities: `Nginx` receives public traffic and serves static files, `Gunicorn` runs `Django`, `Django` handles application behavior, and the database stores user data.

You also learned why deployment is not just copying code to a server. A real deployment needs secure settings, environment variables, `HTTPS`, firewall rules, process management, migrations, static file collection, logging, and backups. Even a small demo site needs these habits because public servers attract bots, mistakes, and unexpected traffic.

The setup in this chapter is intentionally modest. A single `VPS` with `Django`, `Gunicorn`, `Nginx`, and `SQLite` is enough for a public learning project. As the project grows, you can move to `PostgreSQL`, add `Cloudflare`, improve monitoring, and automate deployment with `CI/CD`.

Specifically, you learned the following:

- Deployment turns a local `Django` app into a continuously running public service
- A production stack separates concerns: `Nginx` (web), `Gunicorn` (app), `Django` (logic), database (data)
- `WSGI` allows `Django` to run behind different web servers without modification
- A small `VPS` provides the best balance of control, cost, and learning value for beginners
- `SQLite` is acceptable for low-traffic apps but has limits around concurrent writes
- Data must persist independently of application code and be protected with regular backups
- Safe deployments follow a repeatable process: update code, apply migrations, collect static files, restart services
- `Django` includes strong built-in protections, but only when configured correctly, and the most common risks come from misconfiguration, not sophisticated attacks
- A simple security baseline plus an edge service like `Cloudflare` is enough for most small apps
- A host like DigitalOcean provides infrastructure, but application-level protection is the developer’s responsibility
- Scaling a `Django` app usually means swapping components, not rewriting the application
