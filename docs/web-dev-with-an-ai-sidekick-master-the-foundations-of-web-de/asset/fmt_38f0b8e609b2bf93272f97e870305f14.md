|-----------------------------------|-------------------------------------|-------------------------------------------------------------------------------------------------------------------|
| Relying on queryset default ordering | "The first item in Survey.objects.all() is the newest." | Use explicit ordering in queries or in the model Meta ordering, and assert based on content rather than position. |
| Sharing module-level objects across tests | For example, you create a Survey at import time in the test module. This will run once when the test module is imported, which makes ordering and isolation unpredictable. | Always create objects inside setUp, setUpTestData, or the test method. |

Now let's look at continuous integration and automated test pipelines.

# Continuous integration and automated test pipelines

A test suite only changes your day-to-day behavior if it runs automatically, every time. That is what **continuous integration** (**CI**) does: whenever code is pushed or a pull request is opened, the CI system creates a clean environment, installs dependencies, and runs your tests. If anything fails, you find out immediately, before the change is merged or deployed.

**GitHub Actions** is the default choice for many Django projects because it is built into GitHub, supports Linux runners, and is easy to express as a YAML workflow that runs on `push` and `pull_request`.

## Discipline is the point

CI is a team rule enforced by a machine.

Disciplined CI usually means:

* Every push and pull request runs the test suite, not just when someone remembers to do it.
* The `main` branch stays green. Broken builds are treated as stop-the-line events.
* Pull requests are not merged if CI fails. This can be enforced with branch protection rules in GitHub.
* Flaky tests are fixed or removed quickly. A flaky test is worse than no test because it trains everyone to ignore failures.
* CI runs in a clean environment, so it catches *works on my machine* bugs.

## A minimal Django CI workflow with SQLite

This workflow runs on every push and pull request, sets up Python, installs dependencies, and runs Django's test runner with warnings enabled, which is useful for catching deprecations early. Django itself recommends running tests with Python warnings enabled using `python -Wa manage.py test`.

You do not need to add this workflow to TallyApp now, but this is what a minimal workflow looks like.

**Warning!** Never store secrets (API keys, passwords, secret keys) directly in your repository or in `ci.yml`. Use environment variables and GitHub Actions Secrets instead. If a repository is public, anything committed to it is visible to everyone.

Create `.github/workflows/ci.yml`:

```
name: CI
on:
  push:
    branches: [ "main" ]
  pull_request:
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        python-version: [ "3.14", "3.13", "3.12" ]
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
          cache: "pip"
      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt
      - name: Run tests
        env:
          DJANGO_SETTINGS_MODULE: tallyapp.settings
          # If you use environment variables in settings.py, set them here too.
          # DJANGO_SECRET_KEY: "ci-only-not-secret"
        run: |
          python -Wa manage.py test
```

Note the following about the preceding code:

* It runs on `push` and `pull_request`, meaning every change is tested automatically.
* It uses `actions/setup-python` to install a specific Python version consistently across runs, and can cache pip dependencies to keep CI fast.
* A small Python version matrix catches compatibility issues early, especially if your readers might use different Python versions.

This section about CI is to raise your awareness about the technique, but we won't implement it in this book because it overcomplicates the project when you're first learning.

Now let's see how AI can help you write tests.

# Asking an AI to write tests

AI tools are very good at producing plausible-looking tests very quickly. They are not good at knowing whether those tests are meaningful. Used properly, an AI assistant can help you draft and revise tests faster. Used carelessly, it will generate a large volume of shallow tests that assert almost nothing.

The difference comes down to how you prompt, how you review, and whether you treat AI as a junior engineer or as an oracle.

The best way to use AI for testing is to start with a good walking skeleton: a project that already has a working test suite, a sensible structure, and examples at the right layers of the test pyramid. For example, if your project already has a few clear unit tests, a small number of integration tests, and perhaps one end-to-end test, the AI can usually extend those patterns effectively. Without that foundation, it is much more likely to generate inconsistent, redundant, or low-value tests.

Establish the testing strategy first. Then use AI to extend it.

## Using AI to draft initial test cases

AI is most helpful when you give it:

* The model or view code.
* A clear description of expected behavior.
* Constraints and edge cases you care about.
* The testing style you want, such as Django `TestCase` or `pytest`.

Example prompt:

```
Here is my Django model for Survey. Write unit tests that verify validation rules, default values, and any constraints. Use Django TestCase and avoid relying on primary key values.
```

The output will usually:

* Create a `TestCase` subclass.
* Instantiate a model instance.
* Call `full_clean()` to test validation.
* Assert defaults and field behavior.

This gives you a first draft. You still need to ask: are these the tests I would have written? Or did the AI simply test that objects can be saved?

## Using AI to generate edge cases

AI is often better at brainstorming edge cases than at writing elegant production code. That makes it particularly useful for negative and boundary tests.

Example prompt:

```
Given this Django form for creating a survey, list edge cases I should test. Focus on boundary values, invalid combinations, and security-related inputs.
```

A good answer might suggest:

* Empty title
* Overly long title exceeding `max_length`
* Slug collision
* Invalid characters in slug
* Duplicate submission
* User not approved by admin
* Attempt to publish without required questions
* Extremely long text input
