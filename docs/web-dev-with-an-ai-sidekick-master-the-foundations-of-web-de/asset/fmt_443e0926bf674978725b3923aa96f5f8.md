## Limiting backup size

If you never delete old backups, they will eventually fill your disk. This is one of the most common failures on small servers.

To delete backups older than 7 days, you can run:

```
find /home/tallyapp/backups -type f -mtime +7 -delete
```

The preceding code works as follows:

* `-type f`: only applies to files
* `-mtime +7`: modified more than 7 days ago
* `-delete`: remove them

To automate cleanup, add a second scheduled task to `cron`:

```
30 2 * * * find /home/tallyapp/backups -type f -mtime +7 -delete
```

This runs every day at 02:30 a.m..

**Good practice**: It is best to do cleanup as a separate job because that keeps backup creation simple and fast, cleanup happens during low-traffic hours, and you avoid mixing responsibilities in one command.

## Continuous Integration (CI) and Continuous Deployment (CD)

As your project grows, manually copying files to a server and restarting services becomes tedious and error-prone. CI/CD replaces that manual process with an automated pipeline that builds, tests, and deploys your application in a consistent way.

CI focuses on validating changes. Every time you push code to your repository, an automated process runs tasks such as installing dependencies, running tests, and checking code quality. The pipeline should catch problems early, before they reach your server.

CD takes the next step. Once changes pass validation, they are automatically deployed to your server. Instead of logging into your `VPS` and running commands by hand, the pipeline performs the same steps every time in a predictable sequence.

### A typical CI/CD pipeline for a Django project

For a Django project like `TallyApp`, a typical CI/CD pipeline looks like this:

1. A developer pushes code to a `Git` repository (for example, `GitHub`).
2. A CI service (such as `GitHub Actions`) starts a workflow.
3. The workflow installs dependencies and runs tests.
4. If the checks pass, the CD stage connects to your server.
5. The server pulls the latest code.
6. Migrations are applied.
7. Static files are collected.
8. The application service (`Gunicorn`) is restarted.

This mirrors the manual deployment steps you followed earlier, but removes the risk of forgetting a step or introducing inconsistencies.

### GitHub Actions

A minimal example using `GitHub Actions` might:

* Trigger on every push to the main branch
* Run `pip install -r requirements.txt` and `python manage.py test`
* Use `SSH` to connect to your server and execute deployment commands

The benefits are immediate:

* Deployments become repeatable and reliable
* Errors are caught before they affect users
* You spend less time managing servers and more time improving your application

There are trade-offs. CI/CD adds some initial complexity, and mistakes in your pipeline can deploy broken code quickly. For that reason, many teams start with continuous integration only and add automated deployment once they are confident in their tests.

For a small project like `TallyApp`, CI/CD is not required. But even a simple pipeline gives you a taste of how software is built and maintained, and prepares you for larger projects where manual deployment is no longer practical.
