
# Spec-Driven Development with Spec Kit

## Formal or End-to-End

This is the full version, often associated with frameworks like Spec Kit. Typical characteristics:

* Multiple structured artifacts (spec, plan, tasks, validation steps)
* Traceability from requirements to implementation
* Iterative refinement of the spec itself
* Strong alignment between humans and AI over longer workflows

Use this for large features or systems, high-risk or high-complexity work, and team environments where coordination matters. The key idea is that the specification drives the entire lifecycle, not just the initial prompt.

You can learn more about Birgitta Böckeler and watch some of her conference talks at the following link: [https://gotopia.tech/experts/1305/birgitta-boeckeler](https://gotopia.tech/experts/1305/birgitta-boeckeler)

## Alternatives to Spec Kit

Structured AI development workflows are not one-size-fits-all. Heavier frameworks, such as Spec Kit, can work well when you need strong guardrails, explicit planning, and traceable handoffs across a larger or riskier project.

For smaller features or solo work, a lighter approach such as `OpenSpec` may be a better fit because it preserves the habit of writing down intent without turning the process into a document factory. The goal is to give the AI enough clear context to produce better code.

For readers exploring spec-driven AI workflows, there is a spectrum. Spec Kit is more structured and stage-oriented. OpenSpec is lighter and less stage-oriented. Beginners should be wary of any method that produces lots of planning documents without clearly improving implementation, testing, or review.

You can learn more about OpenSpec as an alternative to Spec Kit at the following link: [https://github.com/Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec)

## Spec Kit Commands

Spec Kit includes helper scripts that automate parts of this process. After initializing the project, you can run commands that guide the development process:

1. `/speckit.constitution` – define project principles
2. `/speckit.specify` – create a baseline specification
3. `/speckit.plan` – generate an implementation plan
4. `/speckit.tasks` – break the plan into tasks
5. `/speckit.implement` – execute the implementation

Additional commands help refine the specification or check consistency between artifacts.

**Warning!** GitHub's current Spec Kit README notes that most agents expose `/speckit.*` slash commands, but Codex CLI in skills mode uses `$speckit-*` instead. Skills mode is behind a feature flag, so if you didn't explicitly enable it, you're not using it. To enable skills mode, you should have started Codex like this: `codex --enable skills`. If you didn't pass that flag (or configure it in your setup), then skills are off.

These commands do not generate production code themselves. Instead, they structure the conversation with the AI so that each step builds on the previous one.

AI coding tools are good at filling gaps. That is useful when the gap is obvious, but risky when the missing detail is a product decision. If the spec does not say whether short links are public, private, expiring, or trackable, the tool may choose for you.

Spec Kit reduces this problem by making the specification explicit and structured. Because the specification, plan, and tasks all live in the repository, they can be reviewed, versioned, and improved over time.

For teams experimenting with AI-assisted development, this approach provides a useful balance: the speed of AI-generated code combined with the discipline of traditional software engineering.

## Install the Specify CLI

For this chapter, install the GitHub SpecKit `Specify CLI` with `uv`, as shown in the following command:

```
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git
```

`uv` is a fast Python package manager from Astral. We use it here because Spec Kit's installation from a Git repository works more reliably with `uv tool install`. If you prefer, you can also clone the repository and install with `pip install -e`.

If `uv` is not installed yet, install `uv` first, then run the command above. You can install `uv` from the following link: [https://docs.astral.sh/uv/getting-started/installation/](https://docs.astral.sh/uv/getting-started/installation/).

After installation, confirm that the Specify CLI and its dependencies are available:

```
specify check
```

# Adding a URL Shortener Feature to TallyApp

A useful way to learn how to do Spec-Driven Development is to add a feature to an existing system. In this section, you will add a URL shortener to TallyApp.

## Why a URL Shortener?

A URL shortener might seem unrelated to surveys. But survey creators often want to share their survey links in emails, presentations, or printed materials. A long URL such as [https://tallyapp.example.com/surveys/8e5a4c39-2f4d-4b9e-bbfa-2c10a96d21fd/take/](https://tallyapp.example.com/surveys/8e5a4c39-2f4d-4b9e-bbfa-2c10a96d21fd/take/) is inconvenient to share. A short link such as [https://tallyapp.example.com/s/abc123](https://tallyapp.example.com/s/abc123) is easier to remember and distribute.

The goal of this feature is to allow survey creators to generate a short link that redirects to their survey.

**Prompt**: Please explain how URL shorteners work internally. Describe the algorithms commonly used to generate short URL codes and compare random code generation with hash-based URL shortening.

## Writing the Feature Specification

Before writing any code, define the behavior of the feature.

A typical feature specification includes the following sections.

### Goal

Allow authenticated users to create short URLs that redirect to longer links inside TallyApp.

The most common use case will be generating short links for surveys.

### Non-Goals

To keep the feature small and focused, we explicitly exclude several capabilities:

* No analytics tracking in the first version
* No expiration dates for links
* No custom aliases (users cannot choose the short code)
* Only authenticated users can create short links

These restrictions prevent the feature from expanding into a full commercial-style service.

### User Stories

Describe the interactions from the user's perspective:

* As a logged-in user, I can create a short link for a survey URL
* As a logged-in user, I can view a list of the short links I created
* As any visitor, I can visit a short URL and be redirected to the target page

The URL shortener request flow:

1. The browser requests the short URL from your site.
2. Django matches the `/s/<code>/` pattern and calls the view `redirect_short`.
3. The view looks up the code in the `ShortLink` table.
4. Django returns an HTTP 302 redirect to the original survey URL for the browser to request.
5. Django returns a `404 Not Found` response if the code does not exist.

### Acceptance Criteria

These criteria define observable behavior:

* When a valid URL is submitted, a short code is generated
* The short code is unique
* Visiting `/s/<code>` redirects to the stored target URL
* A user can only see short links they created
