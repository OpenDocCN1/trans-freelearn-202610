
# Django Overview

Django is often described as "batteries included", and that phrase is worth unpacking. Django deliberately ships with solutions for common web development problems rather than leaving them as optional add-ons. Database migrations, authentication, form handling, security protections, and an administrative interface are all part of the core framework.

A database migration is a set of instructions that tells your database how to change its structure. Instead of directly editing the database, you write changes like adding a new column called `date_of_birth`, renaming that column, or creating a new table. Each of these changes is saved as a small file, usually in your project.

Where other web frameworks leave those features to additional layers on top of their framework, like a content management system (CMS), Django includes them.

This means Django projects tend to look similar to each other, which makes them easier to understand, maintain, and hand over to other developers.

The trade-off is that Django expects you to follow its conventions, but in return, you get routing, forms, authentication, migrations, static-file handling, and admin tools with little setup.

## Request-response lifecycle

At a high level, Django applications follow a clear request–response lifecycle:

1. A browser sends an HTTP request to your web server.
2. Django matches that request against a set of URL patterns defined by `path()` to decide which view should handle it.
3. The view runs Python code, optionally queries the database through models like `Post.objects.filter()`, and produces an HTTP response. In many cases, that response is HTML generated by rendering a template, but it could also be JavaScript Object Notation (JSON), a redirect, or an error page.
4. This response is returned to the web browser to display to the user, or to the client app that made the request if it is just data.

Keeping this flow in mind makes it much easier to understand how the different Django components cooperate.

Django is a useful test of how well you understand a web application. An AI assistant can write a `path()` call or a `Post.objects.filter()` query quickly. The part you still have to judge is where that code belongs. Should this check live in the view, the model, the form, or middleware? What should happen if the post is missing, unpublished, or requested by the wrong user?

That is why Django is worth learning as a system, not as a pile of snippets. URLs choose views. Views make decisions. Models define and protect data. Templates render HTML. Middleware handles site-wide behavior. Settings describe the environment. When those pieces are clear in your head, generated code is much easier to review, debug, and reject when it puts logic in the wrong place.

## Middleware

Before your view ever sees a request, Django runs it through a stack of middleware, which acts like a pipeline of processing steps. Each layer gets a chance to inspect or modify the request on the way in, and the response on the way out. This is how Django handles behavior that applies across the whole site without cluttering your view code.

Middleware is responsible for things that apply across your entire application, not just a single page. This includes session handling, security checks like cross-site request forgery (CSRF) protection, and user authentication. For example, when you access `request.user` in a view, that value has already been attached by Django's authentication middleware earlier in the pipeline.

This design keeps your views focused on your app's logic, while middleware handles the site-wide behavior around it. You are unlikely to write your own middleware at the start of learning Django, but understanding that it sits between the browser and your view helps explain how Django can provide so much functionality automatically, before your code even runs.

## Beginner-friendly, but not only for small projects

Although Django is approachable for beginners, it is not a toy framework. It is designed to scale from small personal projects to large, long-lived applications. Many real-world systems start as simple Django projects and grow over time without changing frameworks.

Django's emphasis on explicit structure, clear separation of responsibilities, and predictable conventions helps keep complexity under control as applications evolve.

## Django releases

Django has a very regular cadence for releases:

- Feature releases every eight months or so
- Every few releases, one is designated long-term support (LTS)
- LTS releases receive security and data-loss fixes for much longer than non-LTS releases

An LTS release is designed to be boring in the best sense. Many professional Django teams standardize on LTS releases only. If you want to target an LTS release, the latest at the time of publishing is Django 5.2, which will be supported until April 2028. Many professional Django teams standardize on LTS releases for that reason.

This book targets Django 6.0, which is a non-LTS release. It is supported until April 2027. Later versions will exist by the time you read this book, but the concepts and code shown here remain valid. For example, you should be able to target 6.1 when it releases in August 2026, or 6.2 in April 2027, which is expected to be the next LTS release and will be supported until April 2030.

You can learn more about the current supported versions of Django at the following link: [https://www.djangoproject.com/download/#supported-versions](https://www.djangoproject.com/download/#supported-versions)

## Alternatives to Django

Although I chose Django for this book, it is not the only web framework for Python.

Flask is probably the most well-known alternative. It is much lighter than Django and gives you just the basics for handling HTTP requests and routing. You add other components yourself as needed. This makes Flask more flexible, but also means you need to make more decisions. You can learn more about Flask at the following link: [https://flask.palletsprojects.com/](https://flask.palletsprojects.com/)

FastAPI is a newer framework that has become very popular for building APIs. It focuses on performance, modern Python features like type hints, and automatic documentation generation. It is widely used for backend services and AI-related applications. You can learn more about FastAPI at the following link: [https://fastapi.tiangolo.com/](https://fastapi.tiangolo.com/)

Pyramid sits somewhere in between Django and Flask. It allows you to start small and scale up in complexity, but it is less commonly used today than Flask or FastAPI. You can learn more about Pyramid at the following link: [https://docs.pylonsproject.org/projects/pyramid/](https://docs.pylonsproject.org/projects/pyramid/)

In practice, most developers choose between three main options:

- Django for full-featured web applications
- Flask for simple or flexible projects
- FastAPI for APIs and high-performance services

For this book, Django is a sensible choice. It gives new web developers a structured environment with fewer decisions to make, which aligns well with your goal of teaching concepts rather than forcing readers to assemble a stack from scratch.

## Expectations for this chapter

The focus in this chapter is on Django's core ideas: defining models, handling requests, rendering templates, and using the admin interface.

Django includes many other features, such as authentication systems and API tooling for building web services, but those build on the same foundations you will learn here.
