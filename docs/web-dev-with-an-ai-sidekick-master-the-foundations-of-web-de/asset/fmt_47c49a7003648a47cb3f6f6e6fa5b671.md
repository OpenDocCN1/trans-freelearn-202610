# Practical AI-assisted project planning

Formal spec-driven development that you will learn about in the next chapter can be useful, but for a beginner-friendly process, it is often excessive. Full spec systems involve structured requirement documents, traceability, staged refinement loops, and sometimes dedicated command sets or multi-agent AI workflows. That is valuable in large teams building regulated or mission-critical systems. It is not necessary for learning how to design and build a clean Django application.

Instead, you can use a lightweight approach. The idea is to write a short, structured project brief in Markdown, then use a carefully written one-shot prompt to guide the AI.

**Prompt**: Show me an example of a bad one-shot prompt for TallyApp and how to improve it.

For example, before building TallyApp, create a file named `project-brief.md` with clearly defined sections such as:

* Goal
* Target users
* Core features
* Non-goals
* Technical constraints
* Definition of done

This forces you to define scope before writing code. Including a *Non-goals* section prevents accidental feature creep, which is one of the most common problems in both human-led and AI-assisted development.

Once the brief is written, you can prompt your AI assistant along the following lines:

```
I am building a Django 6 project called TallyApp. The attached Markdown file describes the requirements. Please:
- Break the project into implementation phases.
- Propose Django models and relationships.
- Suggest URL patterns and app structure.
- Provide initial scaffolding for models, views, and templates.
- Restate the requirements in your own words before generating code and identify any ambiguities.
```

That final instruction is important because it forces the AI to review the requirements before coding. This reduces hallucinations and makes assumptions visible. It also models a good professional habit to clarify before you implement.

This is why the brief matters. Codex or Claude Code can create Django files in seconds, but they will still make product decisions unless you make them first. Should TallyApp allow someone to submit the same survey twice? Should a survey become locked after it is published? Should results be stored for easy reporting later, or only for simple display now? Those are not coding questions. They are design decisions. Write them down before asking the AI to build anything. The better your brief, the better the code has a chance of being.

## Review the AI’s work before running it

After receiving the output, you do not blindly paste it into your editor. You review it. Here’s a checklist:

* Review the model relationships.
* Confirm the field data types.
* Look out for unnecessary complexity.
* Run database migrations and tests.

It is particularly important to look out for security issues:

* Every form template should include `{% csrf_token %}`
* Protected views should use `@login_required` or `LoginRequiredMixin`
* Watch out for raw SQL queries that could allow SQL injection attacks so the code should use the Django object-relational mapper (ORM) exclusively
* User input should never be rendered unescaped, for example `{{ variable }}` will automatically escape the output
* Make sure that `SECRET_KEY` is not hardcoded in any committed file
* Survey submission views should validate ownership and permissions

The AI produces a draft, but you remain the software engineer who applies human judgment to the generated code.

This approach captures many of the benefits of spec-driven thinking:

* Explicit scope
* Defined constraints
* Clear success criteria
* Reduced ambiguity
* Structured planning before coding

But it avoids the overhead of formal specification frameworks.

As your skills grow and your projects become more complex, you can adopt more formal spec-driven approaches, as you will see in the next chapter. But for building TallyApp and mastering web development fundamentals, a clear project brief plus a well-crafted prompt is the right balance of structure and simplicity.
