
# Read project-brief.md and act as a senior engineer reviewing a new project before implementation

Your job is to find everything that is missing, unclear, or risky. Work in phases:

## Phase 1: Gap analysis

Identify missing or weak areas across:

- Requirements clarity and scope boundaries
- User journeys and edge cases
- Data model assumptions
- Permissions and security
- Validation and error handling
- Performance and scalability risks
- Testing strategy
- Operational concerns (deployment, configuration, secrets)

Do not suggest solutions yet. Just list gaps and ambiguities.

## Phase 2: Targeted interview

Ask me focused questions to resolve those gaps.

- Skip obvious or already well-defined areas
- Prioritize high-impact uncertainties
- Ask one topic at a time, not a long list
- Push for concrete decisions, not vague preferences

Continue until there are no meaningful unknowns left.

## Phase 3: Trade-offs and assumptions

For any remaining open decisions, propose 2–3 options with clear trade-offs.

## Phase 4: Update the brief

Produce an improved version of the file named `project-brief-ai-enhanced.md` that:

- Preserves all correct existing content
- Clarifies ambiguous sections
- Adds missing constraints and edge cases
- Makes assumptions explicit

Show the updated file in full. Do not remove sections unless clearly incorrect.

Be concise, direct, and practical. Avoid generic advice.

---

This will enhance your project brief because doing a gap analysis stops the AI from immediately asking weak questions like:

- Who are your users?

Instead, it has to think first, then ask.

This makes the AI slow down and inspect the brief before jumping into code. That is closer to how an experienced developer reviews a feature request before implementation.

If you prefer a more compact version of the prompt:

```
Read project-brief.md and review it like a senior engineer before implementation.
1. List missing or unclear areas (requirements, edge cases, data model, permissions, validation, performance, testing).
2. Interview me with focused questions to resolve the most important gaps. Ask one topic at a time.
3. For unresolved decisions, propose options with trade-offs.
4. Produce an improved version of the brief, preserving correct content and making assumptions explicit.
Skip obvious points. Be direct and practical.
```

**Prompt**: What are the risks of blindly trusting AI-generated scaffolding code?

# Guiding AI with a design.md

The project brief defines what the system should do. It only briefly defines how the system should look, feel, or behave from a user interface perspective. If you skip that step, the AI will make those decisions for you. Often, you need to be more specific, especially when creating a public website for an organization with a strong brand.

A simple way to avoid this is to create a second document alongside your project brief: `design.md`.

This file captures your design decisions in plain language so that both you and your AI assistant follow the same rules.

## Why a separate design document?

Separating design from the project brief keeps concerns clear:

- The project brief defines behavior, features, and constraints
- The design document defines layout, interaction, and visual consistency

This mirrors how real projects are often structured. Product and engineering define behavior. Design defines how that behavior is presented.

For a learning project like TallyApp, pixel-perfect design is unnecessary. Consistency is enough.

## What goes into design.md?

A useful `design.md` does not need to be long; it should answer a few practical questions:

### 1. Layout and structure

Describe the overall page structure:

- Header with navigation (**Home**, **My Surveys**, **Login/Register**)
- Main content area with a fixed-width container
- Footer (optional)

```
Pages use a simple layout: a top navigation bar, a centered content column, and minimal distractions. Avoid complex multi-column layouts.
```

### 2. Navigation and flow

Explain how users move through the app:

- Where users land after login
- How they access survey creation
- How they return to previous pages

```
After logging in, users are redirected to "My Surveys." Primary actions should be visible without scrolling.
```

### 3. Forms and interaction patterns

Define how forms behave:

- Labels above inputs
- Clear validation messages
- Submit buttons at the bottom

```
All forms use server-side validation with clear error messages shown above each field. Avoid JavaScript-heavy form logic.
```

### 4. Styling approach

Set constraints on styling:

- Use plain CSS
- Avoid heavy frameworks unless needed
- Prefer simple color palette

```
Use a minimal CSS approach. No CSS frameworks. Keep colors neutral with one accent color for actions.
```

### 5. Components and reuse

Encourage consistency:

- Buttons look the same everywhere
- Tables follow a consistent structure
- Messages use a shared style

```
Use reusable CSS classes for buttons, alerts, and tables. Do not redefine styles per page.
```

### 6. Accessibility and clarity

Even at a basic level:

- Use semantic HTML
- Ensure readable text
- Avoid hidden interactions

```
Prefer semantic HTML elements. Buttons should be <button>, not clickable <div> elements.
```

## Using a design file with AI tools

Once you have both `project-brief.md` and `design.md`, you can include both in your prompt:

```
The project-brief.md file defines functionality. The design.md file defines layout, styling, and interaction rules. Follow both.
```

This reduces a common problem where AI-generated code mixes styling approaches or creates inconsistent UI patterns.

Some tools are starting to formalize this idea. For example, Anthropic's Claude Design encourages separating design intent from implementation so the model can generate more consistent user interfaces.

Introducing Claude Design by Anthropic Labs: [https://www.anthropic.com/news/claude-design-anthropic-labs](https://www.anthropic.com/news/claude-design-anthropic-labs)

You do not need a special tool like Claude Design to apply the same idea. A simple `design.md` file achieves most of the benefit.

**Good practice**: Do not turn `design.md` into a full design system. For TallyApp, a single page of guidelines is enough. The purpose is not to design a production UI. The purpose is to stop the AI from inventing one.

The more clearly you define behavior and design upfront, the less time you spend fixing code later.
