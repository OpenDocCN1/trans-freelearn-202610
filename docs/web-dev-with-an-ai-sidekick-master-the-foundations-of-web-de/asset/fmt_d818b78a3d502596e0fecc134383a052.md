# Deployment options for a Django website

When you have been working locally, running the site just meant starting Django’s development server and opening a browser on your own machine. Deployment replaces that temporary setup with a system that keeps running, can accept requests from the public internet, and survive reboots and crashes.

In practical terms, deployment involves:

- A server that is always on and reachable from the internet
- A web server that listens on standard HTTP ports
- An application server that runs Django as a long-lived process
- A database that persists data independently of your code
- A repeatable process for updating code and applying migrations

None of this is specific to TallyApp. These are the same building blocks used by Django sites of all sizes.

When you visit a site using `https://`, TLS ensures three things: (1) Encryption: data is unreadable to anyone intercepting it. (2) Authentication: the server proves it really is who it claims to be. - `Django` processes requests and talks to the database.

Keeping these jobs separate makes later changes less painful. You can move from SQLite to PostgreSQL, or put Cloudflare in front of Nginx, without rewriting your views and models.

## Why a production Django site needs Gunicorn and Nginx

Django’s built-in development server is not designed for production use. Instead, Django applications are typically run behind a `Web Server Gateway Interface (WSGI)` server. WSGI is a specification, not a library. Gunicorn is one of the common WSGI implementations used with Django.

Gunicorn runs your Django project as a long-lived Python process. It does not listen directly on the public internet. Instead, it listens on a local socket and waits for Nginx to forward requests to it:

1. A browser sends an HTTP request.
2. Nginx receives it first.
3. That server calls your Django application using the WSGI interface.
4. Django returns a response object.
5. The server sends the HTTP response back to the browser.

WSGI exists so that Django (and other web frameworks) do not need to know or care which web server is in front of them. As long as the server speaks WSGI, Django can run behind it.

Key points about WSGI:

- It is synchronous and request–response based, meaning each request is handled in a blocking way. The server passes a request to your Django app, and that worker is tied up until the response is fully generated. If your code waits on something slow, like a database query or an API call, that worker just sits there waiting. It cannot do anything else in the meantime. Request–response based means a connection is not kept open to send multiple messages back and forth over time.
- In practice, this means WSGI works very well for traditional web pages and APIs, but it is not designed for things like real-time updates, chat systems, or live notifications where long-lived connections are needed.
- Django is a WSGI application, and Gunicorn is a WSGI server.

Gunicorn loads your Django project and calls it for each incoming request using the WSGI protocol.

### Gunicorn configuration

For TallyApp, we will intentionally keep Gunicorn’s configuration conservative. It will have a single worker process and optionally a small number of threads. It will be managed by the operating system’s service manager, so it starts automatically on boot.

This configuration works particularly well with SQLite, which prefers limited write concurrency.

### Using Nginx as a reverse proxy

A reverse proxy receives the public request and forwards it to another service behind the scenes. Nginx sits in front of Gunicorn and acts as the public-facing web server. Its responsibilities include:

- Listening on ports 80 and 443
- Serving static files such as CSS and images
- Forwarding dynamic requests to Gunicorn

Nginx handles slow clients efficiently so your Django app does not have to.

This division of labor is one of the reasons Django applications perform well even on modest hardware.

## Choosing between shared hosting, VPS, and cloud platforms

For this book, a `VPS` is the best place to start. A VPS gives you a full Linux machine with root access at a low monthly cost. You install exactly what you need and nothing more.

You should also note that other options exist:

- Shared hosting is cheaper but usually unsuitable for Django deployments
- Platform-as-a-service (PaaS) offerings handle more for you, but you learn less about the moving parts
- Large cloud providers offer enormous flexibility, but also complexity that is unnecessary at this stage

A small VPS lets you see how the pieces fit together without overwhelming you.
