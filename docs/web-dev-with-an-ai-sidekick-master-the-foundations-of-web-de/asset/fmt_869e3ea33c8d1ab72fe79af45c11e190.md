
# Django Integration Testing with Test Client

```python
from django.contrib.auth import get_user_model
from django.test import TestCase
from django.urls import reverse
from surveys.models import Survey

User = get_user_model()

class SurveyCreatePostIntegrationTests(TestCase):
    @classmethod
    def setUpTestData(cls):
        cls.user = User.objects.create_user(
            username="creator",
            email="creator@example.com",
            password="pass12345",
        )

    def test_post_creates_survey_and_redirects(self):
        self.client.force_login(self.user)
        url = reverse("surveys:create")
        response = self.client.post(
            url,
            data={
                "title": "Conference Feedback",
                "slug": "conference-feedback",
                "is_published": False,
            },
            follow=False,
        )
        self.assertEqual(response.status_code, 302)
        created = Survey.objects.get(slug="conference-feedback")
        self.assertEqual(created.title, "Conference Feedback")
        self.assertFalse(created.is_published)
        # Optionally verify where we redirect to
        expected = reverse("surveys:detail", kwargs={"slug": created.slug})
        self.assertRedirects(
            response,
            expected,
            fetch_redirect_response=False,
        )
```

If you want to validate the final page content after redirects, pass `follow=True` and assert on the final response. Django’s docs describe `follow=True` and the `redirect_chain` attribute:

```python
response = self.client.post(url, data=payload, follow=True)
self.assertEqual(response.status_code, 200)
self.assertGreaterEqual(len(response.redirect_chain), 1)
self.assertContains(response, "Conference Feedback")
```

## Practical Guidance

Keep integration tests stable:

* Prefer named URLs (`reverse()`) over hardcoded paths. It reduces brittleness during refactors.
* Use `setUpTestData` for expensive setup shared across tests; use `setUp` for per-test state you intend to mutate.
* Assert the minimum that proves the behavior. For example, assert a redirect and a database row exists, rather than asserting the entire HTML output.
* If a test fails, diagnose in this order:
    1. Did you hit the right URL name and arguments?
    2. Did you get redirected (`302`) when you expected a `200`?
    3. Did authentication state exist (`force_login` or `login`)?
    4. Did your database setup match what the view expects?

## Where Integration Tests End and End-to-End Tests Begin

The test client will never run JavaScript, it will never validate that a button is clickable in a real browser, and it will not find layout issues. That is the job of Playwright-based end-to-end tests. But for most server-side workflows in Django, integration tests give you the best feedback for the time they take.

Now let’s move on to end-to-end testing, also known as user interface testing.

# End-to-End Web User Interface Testing

Unit tests and Django’s test client give you fast feedback, but they still do not prove that TallyApp works in a real browser. Web UI tests sit at the top of the testing pyramid: you run the application, open a real browser engine, and automate the same actions a user performs like clicking links, filling forms, submitting, and verifying what appears on screen.

This section uses Playwright, a browser automation tool that is fast, reliable, and supports Chromium, Firefox, and WebKit. We’ll use it to test a small number of important end-to-end user journeys for TallyApp.

## What UI Tests Are For

UI tests are best used for critical flows that must not break:

* **Authentication flow**:
    * A logged-out user is redirected to login for protected pages
    * A user can log in and log out
* **Core product flow**:
    * A logged-in user can create a survey
    * The new survey appears in the survey list
    * A user can edit and delete their survey
* **Authorization boundaries**:
    * User A cannot edit or delete User B’s surveys (tested by attempting direct navigation)

Avoid using UI tests for everything. They are slower than unit tests and take more work to keep stable. Your goal is a small suite that proves the app works from the user’s point of view.

## Why Playwright Instead of Selenium

Historically, Selenium has been the most popular web UI testing framework. Selenium can work, but Playwright is usually a better fit for modern projects because:

* **Auto-waiting is built in**. It waits for elements to be ready, which reduces flaky tests.
* **Locators are resilient**. They re-query and track elements rather than finding once and praying.
* **Great debugging**. It can record screenshots, videos, and traces.
* **Cross-browser**. One **application programming interface** (**API**) drives Chromium, Firefox, and WebKit consistently.
* **Plays nicer with AI coding agents**. The Playwright **Model Context Protocol** (**MCP**) server (`playwright-mcp`) integrates well with GitHub Copilot.

> **Prompt**: Please compare Playwright and Selenium in terms of architecture and reliability.

## Make Your UI Easy to Test

UI tests get dramatically more reliable if you adopt two habits:

* **Prefer accessible selectors**: Playwright can locate elements by role, label, and visible text. This encourages good HTML and makes tests less brittle.
* **Use test IDs sparingly**: For a few key elements, add `data-testid="..."` attributes. This prevents styling changes from breaking tests.

Example in a Django template:

```html
<button type="submit" data-testid="save-survey">Save</button>
```

Use this sparingly. Most of the time, prefer labels and roles.

## Choosing the Playwright Style for a Django Project

Playwright supports two common approaches:

1. **Python + `pytest`**. Fits naturally in a Django/Python repo. Tests look like Python tests and can run alongside your other test tooling.
2. **TypeScript runner (Playwright Test)**. Excellent if your team is already TypeScript-heavy. Not required for TallyApp.

For this Django-first book project, Python with `pytest` is the simplest and most consistent choice.

## Installing Playwright

You need two things:

* The Python Playwright package
* The actual browser binaries Playwright uses

Typical setup commands (run in your virtual environment):

```bash
python -m pip install playwright pytest
python -m playwright install
```

Optional but recommended for better assertions and waiting helpers:

```bash
python -m pip install pytest-playwright
```

If you already use `pytest` for unit tests, this fits nicely. If not, you can still run Playwright tests separately, but `pytest` keeps things tidy.

## Organizing UI Tests in the Git Repository

A clean structure is to keep UI tests separate from Django unit tests:

* `tests/` for unit and integration tests
* `e2e/` for web user interface tests

Example:

* `e2e/test_auth_flow.py`: a test of the website’s authentication
* `e2e/test_surveys_crud.py`: a test of the database CRUD operations for surveys

This prevents confusion about which tests require a running server and a browser.

## Running Django for UI Tests

UI tests need a running server. You have two reasonable approaches:

1. **Run the Django dev server manually**. Start the server in one terminal, and then run Playwright tests in another terminal:
