## Working with pull requests and code review

So far, you have created branches and merged them locally. That works when you are working alone, but most real projects use a slightly different process.

Instead of merging directly into the main branch, developers open a pull request.

A `pull request` is a way to propose a change, review it, and discuss it before merging.

Here is the standard process used by most teams:

1. Create a feature branch:
   ```
   git checkout -b feature/home-page
   ```

2. Make changes and commit them:
   ```
   git add .
   git commit -m "Add home page view and template"
   ```

3. Push the branch to GitHub:
   ```
   git push origin feature/home-page
   ```

4. Open a pull request in GitHub:
   * Compare your branch to `main`
   * Add a description of what changed and why

5. Review the changes:
   * You (and others) can comment on specific lines
   * You can suggest improvements or fixes

6. Make updates if needed:
   ```
   git add .
   git commit -m "Fix feedback from review"
   git push
   ```

7. Once approved, merge the pull request into `main`.

A pull request is not just a button in GitHub. It serves three important purposes:

* `Review`: someone checks the code before it becomes part of the main project
* `Discussion`: design decisions can be questioned and improved
* `History`: the project records not just what changed, but why

Even if you are working alone, opening a pull request for your own work is useful. It gives you a chance to review your changes before merging. The pull request step slows you down slightly, but that is the point. It forces you to think before code becomes permanent.

This is especially important when using AI-generated code. It is easy to accept code that "looks right" but has subtle issues. A pull request creates a natural checkpoint for review. AI makes it easier to produce code quickly. Pull requests are where you apply human judgment to decide whether that code is actually good.

Many teams protect the `main` branch so it cannot be changed directly. All changes must go through a pull request. This prevents accidental mistakes and ensures every change is reviewed.

## Pulling changes and handling conflicts

If you work on multiple machines or collaborate, you will need to pull changes:

1. Click `Sync Changes` or run `Pull`.

If conflicts occur, VS Code opens a merge editor.

1. Choose one of: `Accept Current Change`, `Accept Incoming Change`, or `Accept Both Changes`.
2. Edit if necessary. What should be edited is entirely dependent on the specific conflict scenario.
3. Save, stage, and commit the resolved file.

A conflict does not mean corruption. It means Git needs help deciding between two edits.

## Undoing common mistakes

You only need three recovery tools at this stage.

* `Discard local edits`: Right-click a modified file in `Source Control` and choose `Discard Changes`.
* `Unstage a file`: Right-click a staged file and choose `Unstage Changes`.
* `Amend the last commit`: If you forgot a file:
  1. Stage the file.
  2. Open the `Source Control` menu `...`.
  3. Choose `Commit` | `Amend Commit`.

Amend rewrites the last commit. Only use it if you have not pushed yet.
