
## Arrays

Arrays are typed by describing the type of their elements followed by a pair of square brackets to indicate it is an array, like `number[]` for an array of `number` values:

```
let scores: number[] = [10, 20, 30];
let names: string[] = ["Alice", "Bob", "Charlie"];
```

This means every element in `scores` must be a `number`, and when calling the `push()` method to add a new item, it must also therefore be a `number` value rather than another type like `string`:

```
scores.push(40);    // OK
scores.push("40");  // Error
```

Arrays are everywhere in DOM and API code, so this single rule pays off quickly.

## Objects and inline types

You can describe the shape of an object directly:

```
let user: { name: string; age: number } = {
  name: "Mark",
  age: 42
};
```

This is fine for small, one-off objects, but it gets noisy and repetitive fast. That is where interfaces come in.

## Interfaces

An `interface` is a named description of an object's shape. It does not exist at runtime. It is purely for TypeScript's type system:

```
interface User {
  name: string;
  age: number;
}
```

You can now use this interface anywhere you need a `User`:

```
let user: User = {
  name: "Mark",
  age: 42
};
```

If you forget a property or add one that does not belong, TypeScript catches it:

```
let user: User = {
  name: "Mark"
  // Error: age is missing
};
```

Interfaces are great when used with function parameters:

```
function formatUser(user: User): string {
  return `${user.name} (${user.age})`;
}
```

## The type keyword

The `type` keyword creates a type alias, meaning a name for any type expression. While `interface` describes the shape of objects, `type` can name any type, including unions, intersections, and primitives:

```
type Role = "admin" | "editor" | "viewer";
type ID = number | string;
```

Most TypeScript projects follow this convention: use `interface` for object shapes and `type` for everything else.

## Structural typing vs nominal typing

TypeScript uses a structural type system. This means that compatibility between types is based on their shape, not on their name. If two values have the same structure, TypeScript considers them compatible, even if they come from different interfaces or type declarations.

For example:

```
interface User {
  name: string;
  age: number;
}
interface Person {
  name: string;
  age: number;
}
const u: User = { name: "Mark", age: 42 };
const p: Person = u; // OK
```

In the preceding code, even though `User` and `Person` are different interfaces, they describe the same shape. TypeScript allows the assignment because the required properties and their types match.

This is different from nominal typing, which is used by languages such as Java and C#. In a nominal type system, the name of the type matters. Two types with identical structure are still considered distinct unless there is an explicit relationship between them, such as inheritance or interface implementation.

Structural typing fits naturally with JavaScript, where objects are defined by the properties they have, not by explicit class declarations. It also makes TypeScript more flexible when working with plain objects, JSON data, and values returned from APIs.

However, this flexibility can sometimes be surprising. Because only the shape matters, TypeScript does not care where an object came from, only whether it has the right properties:

```
function printUser(user: User) {
  console.log(user.name);
}
printUser({ name: "Alice", age: 30 }); // OK
```

The object passed into the `printUser` function was never explicitly declared as a `User`, but it matches the required shape, so TypeScript accepts it.

The practical takeaway is that interfaces in TypeScript describe what a value must look like, not what it is called. That design choice keeps TypeScript lightweight and interoperable with JavaScript, while still providing strong guarantees about how data is used.

## Literal types

So far, we have used types like `string`, `number`, and `boolean` to describe broad categories of values. Sometimes, that is still too loose. In real applications, a variable may only be allowed to hold one of a small, fixed set of specific values. This is where literal types come in.

A literal type says not just "this is a string", but "this is this exact string".

For example:

```
let status: "active" | "inactive";
status = "active";     // OK
status = "inactive";   // OK
status = "pending";    // Error
```

Here, `status` is still a string at runtime, but at development time TypeScript enforces that it can only be one of the two allowed values. Any typo or unexpected value is caught immediately by the editor or compiler.

Literal types are especially useful when modeling states, roles, or modes. For example:

```
type Role = "admin" | "editor" | "viewer";
interface User {
  name: string;
  role: Role;
}
```

Now the `role` property can only ever be one of those three values. This removes an entire class of bugs caused by misspellings or inconsistent conventions such as `"Admin"`, `"administrator"`, or `"user"`.

Literal types also work with numbers and Booleans, though string literals are the most common in everyday code. Here's how you might limit the possible values to represent the roll of a die:

```
type DieRoll = 1 | 2 | 3 | 4 | 5 | 6;
```

A useful way to think about literal types is that they sit between free-form values and enums. They give you strong guarantees and excellent editor support without introducing extra runtime constructs. As with interfaces, literal types exist only at development time. When your code runs, they disappear, leaving plain JavaScript behind.

TypeScript has the `enum` keyword that is a construct that defines a set of named constants. However, TypeScript projects often prefer literal union types because they're simpler and don't add runtime code. You may see enums used in older codebases and frameworks like Angular.

When a value must come from a short list, use a literal union type. It catches misspellings and makes the allowed values obvious.

## Union types

Sometimes a value is not limited to a single type, but it is still limited to a known set of possibilities. A union type lets you express exactly that. It says that a value can be one of several types, but not anything else.

You define a union type using the pipe character `|`, which you can read as "or":

```
let id: number | string;
id = 42;        // OK
id = "42";      // OK
id = true;      // Error
```

In the preceding code example, `id` is allowed to be either a `number` or a `string`, but nothing else. This pattern is very common when working with APIs, user input, or database identifiers that may come in different forms.
