
# SQL 基础与数据库设计

SQL is a good place to repeat a theme from this book: typing the command is only part of the job. The harder part is deciding what the data should look like before the query exists. Which facts belong together? Which facts should never be repeated? Which values are optional? Which rules should the database enforce even if the application makes a mistake? Get those decisions wrong and every query becomes awkward. Get them right and most of the SQL becomes ordinary.

A database is the system that stores and protects your data. SQL is the language you use to ask questions of that system and to change what it contains. Learning SQL means getting used to thinking in sets and relationships, not lines of code executed one after another.

## SQL 数据类型

SQL data types define what kind of values a column can store and how the database interprets, compares, and stores those values. Choosing appropriate data types helps keep data valid and queries predictable.

Data types control:

*   Which values are allowed
*   How comparisons and sorting behave
*   How indexes work
*   How arithmetic and functions are applied

A poorly chosen data type can lead to confusing bugs, incorrect comparisons, and unnecessary complexity later.

Most relational databases group data types into a few broad categories.

### 数值类型

These store numbers and allow arithmetic. Common examples include:

*   `INTEGER` 或 `INT`：Whole numbers
*   `REAL`、`FLOAT`、`DOUBLE`：Approximate decimal numbers
*   `NUMERIC` 或 `DECIMAL`：Exact decimal numbers, often used for money

**Good practice**：Use integer types for counts, IDs, and years. Use exact decimal types for values where precision matters, such as money. Avoid floating-point types for currency.

### 文本类型

These store strings of characters. Common examples include:

*   `TEXT`：Prioritizes flexibility
*   `VARCHAR(n)`：Expresses an expectation about maximum length (`n`)
*   `CHAR(n)`：Fixed storage size (`n`)

For most application data, `TEXT` is sufficient unless you have a strong reason to enforce a length limit.

### 日期和时间类型

These store dates and timestamps. Common examples include:

*   `DATE`
*   `TIME`
*   `TIMESTAMP`

Use date and time types instead of storing dates as text. They allow correct sorting, comparison, and date-based calculations.

### 布尔类型

These store true or false values. Common examples include:

*   `BOOLEAN`
*   `INTEGER` used as `0` or `1` in some systems

Use a Boolean type when available rather than an integer. It makes the meaning clear and avoids inconsistent conventions like mixing `0`, `1`, `true`, and `false`.

### 二进制类型

These store raw binary data. Examples include:

*   `BLOB`
*   `BYTEA`

Binary types are used for files, images, or opaque data. They are rarely involved in filtering or joining and are often better stored outside the database unless transactional consistency is required.

### SQLite 与类型亲和性

SQLite is more flexible than most databases. It uses a system called **type affinity**, meaning columns have a preferred type, but the database does not strictly enforce it.

For example, a column declared as `INTEGER` can still store text. SQLite will try to convert values when possible, but it will not reject mismatched types in many cases.

This flexibility is convenient for learning and prototyping, but it means developer discipline matters more. Using appropriate types and constraints is still important, even if SQLite does not force them.

PostgreSQL and SQL Server, by contrast, enforce data types much more strictly.

Data types show what kind of data belongs in a column. They tell the database and future readers of your schema what kind of data belongs in each column. Choosing clear, appropriate types early makes queries simpler, prevents invalid data, and reduces surprises as your database grows.

## 数据库模式设计

**Database schema design** is about deciding what data you store, how you structure it, and how pieces of data relate to each other. A well-designed schema makes queries simpler, data more consistent, and applications easier to change over time. A poorly designed one leads to duplication, bugs, and increasingly complex SQL.

### 表代表一种事物

In a relational database, each table models a single concept. Examples are a user, a film, an episode, or an order. A table should answer one clear question: *What is one row in this table?* If you cannot explain that in a short sentence, the table is probably doing too much.

### 行代表该事物的一个实例

Each row is a single record. One user, one film, one episode. Rows should be independent of each other. The database does not care about row order, and your design should not rely on it. Every row must be uniquely identifiable, which is why tables have a primary key. This is usually an integer ID or GUID that never changes, even if the data in the row does.

### 列代表一个属性

Columns hold individual facts about the thing the table represents. A column should contain one value of one type. For example, a release year, an email address, or a duration in minutes. Mixing multiple facts into one column, such as storing a comma-separated list of actors in a single text field, makes querying harder and breaks the relational model.

### 数据放在哪里

Good schema design starts by separating **entities** from **attributes**.

If a value describes the thing itself, it belongs in the table for that thing. A film's title and release year belong in the `titles` table. If a value describes a relationship between two things, it usually belongs in a separate table. A character name belongs to the relationship between an actor and a film, not to the actor or the film alone.

A useful rule of thumb is this: if a value would have to be repeated for multiple rows, stop and ask whether it should be stored somewhere else and referenced instead. Repeating the same data across multiple rows or tables seems harmless at first, especially in small examples. In real systems, it causes three classic classes of bugs known as anomalies:

*   An **insertion anomaly** happens when you cannot add a piece of data without also adding unrelated data. For example, if a table mixes films and actors, you might not be able to add a new actor unless they are already linked to a film.
*   An **update anomaly** occurs when the same value is stored in multiple places and must be changed everywhere. If you update it in one row but miss another, your data becomes inconsistent.
*   A **deletion anomaly** happens when removing one piece of data accidentally deletes something else you wanted to keep. For instance, deleting the last film an actor appeared in might also remove the only record of that actor.
