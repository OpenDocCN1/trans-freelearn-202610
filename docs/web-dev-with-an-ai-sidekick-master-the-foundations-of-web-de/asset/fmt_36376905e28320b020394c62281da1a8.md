
*   **Isolated**: They do not depend on external systems such as the real database (unless intentionally testing DB behavior), network calls, current time (unless controlled), or random values.

    **Good practice**: For testing time-dependent logic, you can use `freezegun` ([https://github.com/spulec/freezegun](https://github.com/spulec/freezegun)) or `time_machine` ([https://github.com/adamchainz/time-machine](https://github.com/adamchainz/time-machine)) to freeze the clock at a specific moment. This makes tests deterministic regardless of when they run. `freezegun` is older and very popular. `time_machine` is newer, faster, and it is a good default for many current Python projects.

A test that randomly fails is often worse than no test because flaky tests erode trust. Once people stop trusting test failures, they stop reading them carefully.

# Unit testing Python and Django

Unit tests are where you check small pieces of logic before they disappear inside views, forms, and templates. At this level, you focus on small, self-contained pieces of logic such as functions, model methods, validation rules, and permission checks, and verify that they behave correctly for specific inputs.

In a Django project like TallyApp, this means testing pure Python utilities as well as model behavior, form validation, and custom business rules using Django's `TestCase` and its built-in test database. These tests should be fast, deterministic, and isolated, so you find mistakes while the code is still fresh in your head. When your unit tests are strong, they form a stable base for everything else in your test suite.

## Django's test base classes

Django provides several base test classes, each designed for a slightly different purpose. Choosing the right base class avoids slow tests and misleading tests.

**Table 12.1** is a compact summary of the most commonly used test base classes:

| Test Base Class | Transactions Rolled Back Per Test | Typical Use Case |
| --- | --- | --- |
| `SimpleTestCase` | Not applicable | Pure logic tests that do not touch the database or Django models. Useful for utility functions and simple view logic with `RequestFactory`. |
| `TestCase` | Yes (fast transactional rollback) | Most model, form, and integration tests. Default choice for Django apps. Fast and isolated. |
| `TransactionTestCase` | No (flushes DB between tests) | When you need to test real transaction behavior, such as commit/rollback effects or database constraints that require an actual commit. Slower than `TestCase`. |
| `LiveServerTestCase` | Yes | End-to-end tests that require a real HTTP server, often used with Selenium or Playwright in integration mode. Spins up a live test server. |
| `StaticLiveServerTestCase` | Yes | Same as `LiveServerTestCase`, but also serves static files during tests. Useful for full browser-based UI testing. |

Table 12.1: Most commonly used test base classes

Practical guidance:

*   Use `TestCase` by default. It is optimized for speed and isolation and covers most scenarios in a Django project like TallyApp.
*   Use `SimpleTestCase` when no database is needed. This keeps tests faster and makes intent explicit.
*   Use `TransactionTestCase` only when you truly need to test behavior that depends on committed transactions.
*   Use `LiveServerTestCase` or `StaticLiveServerTestCase` when driving a real browser for end-to-end tests.

In many Django projects, most tests will use `TestCase`, with the others reserved for specialized scenarios.

## Python unit testing basics

Python ships with a built-in testing framework called `unittest`. Django builds on top of it.

A minimal `unittest`-style test looks like this:

```
import unittest

def add(a, b):
    return a + b

class AddTests(unittest.TestCase):
    def test_adds_two_numbers(self):
        result = add(2, 3)
        self.assertEqual(result, 5)
```

You run tests with:

```
python -m unittest
```

In Django projects, you usually run:

```
python manage.py test
```

Django automatically discovers tests inside files named `tests.py` or inside `tests/` packages.

## Django's TestCase and the Test database

Django provides its own `TestCase` class, which extends `unittest.TestCase`.

Key features:

*   **Automatic test database**: Django creates a temporary test database before running tests and destroys it afterward.
*   **Transaction isolation**: Each test runs in a transaction that is rolled back, ensuring a clean state.
*   **Client for simulating HTTP requests**: Django includes a test client for making fake `GET` and `POST` requests without a real browser.

Example model test:

```
from django.test import TestCase
from .models import Survey
from django.contrib.auth.models import User

class SurveyModelTests(TestCase):
    def test_survey_string_representation(self):
        user = User.objects.create_user(
            username="mark",
            password="password123"
        )
        survey = Survey.objects.create(
            title="Favorite Sci-Fi Series",
            owner=user
        )
        self.assertEqual(str(survey), "Favorite Sci-Fi Series")
```

This test:

*   Uses the test database
*   Creates real model instances
*   Verifies model behavior
*   Leaves the database clean afterward

This is the everyday shape of many Django tests.

## Testing views with the Django test client

There are two useful ways to test Django views.

Use `RequestFactory` when you want to call a view directly in isolation. This bypasses URL routing and middleware, so it behaves more like a traditional unit test of the view function itself. If the view depends on authentication, session data, or other middleware behavior, you must provide that manually. Django's documentation describes `RequestFactory` as a way to generate a request object and test a view like any other function.

Use `self.client` when you want to test the full Django request pipeline without launching a real browser. This includes URL routing and more of the framework behavior, so these tests are broader than isolated unit tests, but they are still fast and very useful in everyday Django projects. Django describes the test client as a way to simulate a user interacting with the application at the view level.

Example using `RequestFactory`:

```
from django.test import RequestFactory, TestCase
from django.contrib.auth.models import User
from surveys.views import survey_list

class SurveyViewUnitTests(TestCase):
    def setUp(self):
        self.factory = RequestFactory()
        self.user = User.objects.create_user(
            username="alice",
            password="example123"
        )

    def test_survey_list_with_authenticated_user(self):
        request = self.factory.get("/surveys/")
        request.user = self.user
        response = survey_list(request)
        self.assertEqual(response.status_code, 200)
```
