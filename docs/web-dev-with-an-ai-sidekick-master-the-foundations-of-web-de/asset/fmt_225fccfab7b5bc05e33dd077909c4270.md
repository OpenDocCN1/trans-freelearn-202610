
# Django Templates and Views

## Template Basics

Templates live in a dedicated directory, usually `<app_name>/templates/<app_name>/`, for example `blog/templates/blog/`. The nested folder structure is deliberate. It avoids name clashes when multiple apps define templates with the same filename.

You can define the whole template in one file like `post_list.html`:

```html
<!DOCTYPE html>
<html>
<head>
    <title>Blog</title>
</head>
<body>
    <h1>Latest posts</h1>
    {% for post in posts %}
        <article>
            <h2>{{ post.title }}</h2>
            <p>{{ post.body|truncatewords:30 }}</p>
        </article>
    {% empty %}
        <p>No posts yet.</p>
    {% endfor %}
</body>
</html>
```

Django's template language is intentionally limited. You can use variable interpolation with `{{ ... }}`, simple control flow with `{% for ... %}` and `{% if ... %}`, and filters like `truncatewords`.

**Warning!** You cannot write arbitrary Python code in templates, and that is a feature. It enforces a clean separation between logic and presentation.

## Template Inheritance

Templates become more reusable when you introduce inheritance. A base template defines the shared structure (stored in `<app_name>/templates/`), and child templates override specific blocks (stored in `<app_name>/templates/<app_name>/`).

In the base template, you define replaceable blocks using the following syntax: `{% block <block_name> %}<default_block_content>{% endblock %}`. For example, to define a block named `title` with a default content of `My Site`, use `{% block title %}My Site{% endblock %}`. You can define as many replaceable blocks with unique names as you like.

Then in an inherited template, you define the contents for each named block using the following syntax: `{% block <block_name> %}<block_content>{% endblock %}`. For example, to provide the content for a block named `title` with `Blog` as its content, use `{% block title %}Blog{% endblock %}`.

In the `blog` folder, create a folder named `templates`.

In the `blog/templates` folder, create a file named `base.html`:

```html
<!DOCTYPE html>
<html>
<head>
    <title>{% block title %}My Site{% endblock %}</title>
</head>
<body>
    <header>
        <h1>My Django Site</h1>
    </header>
    <main>
        {% block content %}{% endblock %}
    </main>
</body>
</html>
```

Note that the `content` block does not provide any default content, so if a template does not supply any content, it will remain empty.

In the `blog/templates` folder, create a folder named `blog`.

In the `blog/templates/blog` folder, create a file named `post_list.html`:

```html
{% extends "base.html" %}
{% block title %}Blog{% endblock %}
{% block content %}
    <h2>Latest posts</h2>
    {% for post in posts %}
        <article>
            <h3>{{ post.title }}</h3>
            <p>{{ post.body|truncatewords:30 }}</p>
        </article>
    {% empty %}
        <p class="no-posts">No posts yet. Check back soon.</p>
    {% endfor %}
{% endblock %}
```

This pattern keeps HTML consistent across pages and reduces duplication, which matters as soon as a site grows beyond a single view.

## Returning Response Status Codes

Views are also responsible for returning responses that are not HTML. Redirects, `404` errors, JSON responses, and form submissions all live in views.

For example, a detail view for a single post might look up an object by slug and return a `404 Missing resource` status code if it does not exist:

```python
from django.shortcuts import get_object_or_404, render

def post_detail(request, slug):
    post = get_object_or_404(Post, slug=slug, status="published")
    return render(request, "blog/post_detail.html", {"post": post})
```

This illustrates an important design principle: views handle decisions and error conditions, templates assume they have valid data and focus only on rendering.

## Class-based and Function-based Views

Django also supports class-based views, which reduce repetition for common patterns like list and detail pages. They are powerful, but harder to read when you are new.

For learning purposes, function-based views as you've seen so far are often clearer because you can see the full request–response flow in one place. Once that understanding is solid, class-based views make much more sense.

In short, views decide what happens for a request, templates decide what the user sees, and models supply the data. Keeping those responsibilities separate is one of the reasons Django applications remain understandable as they grow.

# Serving Static Files

**Static files** are assets that are sent to the browser exactly as they are, without being generated dynamically. This includes CSS stylesheets, JavaScript files, images, fonts, and icons. Django treats these very differently from templates, and understanding that distinction early prevents a lot of confusion.

Templates are rendered on the server and can contain logic and placeholders. Static files are not rendered at all. Django never opens a CSS file to inspect it or modify it. It simply sends the file to the browser when asked.

## Where Static Files Are Stored

Django expects static files to live in a folder named `static`. In an app-based project, with an app name of `blog`, the usual layout would look like this:

```
blog/
  static/
    blog/
      style.css
      logo.png
```

The nested `blog` folder is deliberate. Just like templates, this avoids name collisions when multiple apps define files with the same name, such as `style.css`.

To use a static file in a template, you must first load Django's `static` template tag:

```html
{% load static %}
```

Then you can reference static files using the `{% static ... %}` helper and pass the `static`-folder relative path to the file:

```html
<link rel="stylesheet" href="{% static 'blog/style.css' %}">
<img src="{% static 'blog/logo.png' %}" alt="Logo">
```

This is important. You should never hard-code paths like `/static/blog/style.css`. Using `{% static ... %}` allows Django to change how static files are served without breaking your templates.

## Configuring the Static Files Folder

Static files are configured in `settings.py` using `STATIC_URL`:

```python
STATIC_URL = "static/"
```
