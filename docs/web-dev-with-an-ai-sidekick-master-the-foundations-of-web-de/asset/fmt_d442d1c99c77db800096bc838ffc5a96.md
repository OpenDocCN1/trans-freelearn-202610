
# Type Hints

* Provide more accurate autocomplete
* Highlight likely mistakes before you run the code
* Improve navigation and refactoring

Static type checkers can analyze your code and warn you about type mismatches that would otherwise only show up at runtime.

Type hints do not turn Python into a statically typed language. They are optional, gradual, and non-enforced by default. You can add type hints only where they help, mix typed and untyped code freely, and ignore them entirely if you choose.

This is called `gradual typing`. It lets teams add type information over time without rewriting everything.

Type hints are most valuable at boundaries:

* Function parameters and return values
* Public APIs
* Complex data structures
* Code that is reused by others

They are less useful for short-lived variables inside small functions, where the type is obvious.

Type hints are not required to learn Python. Beginners can write clean, correct code without them. However, understanding what they are and why they exist prepares readers for modern Python codebases, documentation, and frameworks like Django for web development.

# Decorators

Sooner or later, you will see Python code like this:

```
@something
def my_function():
    ...
```

That `@something` syntax is a `decorator`.

Decorators can look strange at first, but the core idea is simple: a decorator is a way to wrap one function with another function. This lets you add behavior without changing the original function body.

In other words, a decorator says, *before or after this function runs, do some extra work*.

This matters because Python treats functions as values. A function can be passed into another function, returned from a function, or replaced by another function.

Here is a very small example without using the `@` syntax yet:

```
def say_hello():
    print("Hello")
def wrapper(func):
    def inner():
        print("Before the function runs")
        func()
        print("After the function runs")
    return inner
say_hello = wrapper(say_hello)
say_hello()
```

This prints:

```
Before the function runs
Hello
After the function runs
```

What happened?

1. `wrapper` takes a function as input
2. It defines a new function called `inner`
3. `inner` runs some extra code, then calls the original function
4. `wrapper` returns the new function
5. `say_hello` is replaced with that wrapped version

That is the essence of a decorator.

## The @ Syntax

Python provides a cleaner way to write the same idea:

```
def wrapper(func):
    def inner():
        print("Before the function runs")
        func()
        print("After the function runs")
    return inner
@wrapper
def say_hello():
    print("Hello")
say_hello()
```

This does the same thing as:

```
say_hello = wrapper(say_hello)
```

The `@wrapper` line is a more readable shortcut.

## Why Decorators Exist

Decorators are useful when you want to add behavior to many functions in a consistent way. Common uses include logging, timing, access control, caching, and validation.

For example, instead of adding “print a log message” inside ten different functions, you can write one decorator and apply it to all ten. This keeps the core function focused on its real job.

Here is a simple decorator that logs when a function is called:

```
def log_call(func):
    def inner():
        print(f"Calling {func.__name__}")
        func()
    return inner
@log_call
def greet():
    print("Hi")
greet()
```

This prints:

```
Calling greet
Hi
```

The function `greet` still does its own job. The decorator adds extra behavior around it.

## Decorators and Function Parameters

One complication is that real functions often take arguments. A decorator must usually accept those too.

Here is a version that handles any positional and keyword arguments:

```
def log_call(func):
    def inner(*args, **kwargs):
        print(f"Calling {func.__name__}")
        return func(*args, **kwargs)
    return inner
@log_call
def greet(name):
    print(f"Hello, {name}")
greet("Alice")
```

You do not need to master `*args` and `**kwargs` yet. For now, know that they allow the wrapper to pass through whatever arguments the original function expects.

## Why Beginners Should Care

You do not need decorators for everyday beginner Python scripts.

But you do need to recognize them, because they appear often in real Python codebases and web frameworks. Django uses decorators for tasks such as requiring login or restricting HTTP methods. Other libraries use them for caching, validation, and configuration.

At this stage, do not rush to write decorators. Make sure you can recognize what they do.

* A decorator wraps a function
* The `@name` syntax is shorthand
* Decorators add behavior without changing the original function body

**Good practice**: When first learning Python, use decorators sparingly. Read them often, recognize what they do, and only write your own when the benefit is obvious.

If a decorator hides simple logic that would be clearer written normally, it is probably making the code worse, not better.

# Guidance for Writing Functions

At this stage, you should focus on writing clear, simple functions:

* Give them descriptive names
* Make them do one thing
* Pass data in using parameters
* Get results out using return values

Functions are the point where Python code starts to scale. Almost everything you do next, working with files, handling user input, processing data, or building web applications, will rely heavily on functions.

But before we go any deeper, let’s get into handling errors and implementing strategies to debug problems.

# Errors and Debugging Basics

Errors are a normal part of writing code. Every programmer, regardless of experience, sees error messages constantly. The difference between a beginner and an experienced developer is not how often errors happen, but how quickly they can understand and fix them. This section is about building that skill early.

When Python encounters a problem that it cannot recover from, it stops executing your program and prints an error message to the terminal. This message usually includes a `traceback`. A traceback is a report of what Python was doing when the error occurred.

Here is a simple example:

```
print(message)
```

If `message` has not been defined, Python will respond with something like the following:

```
Traceback (most recent call last):
  File "example.py", line 1, in <module>
    print(message)
NameError: name 'message' is not defined
```

The preceding output may look intimidating, but it follows a predictable structure. The most important rule is this: *read the last line first*. The final line tells you the type of error and usually explains the problem in plain language. In this case, Python is telling you that you tried to use a variable that does not exist.

The lines above the final message show where the error happened. They include the file name and line number. In small programs, this is often enough to locate and fix the issue immediately.

## Common Errors

There are a few error types that beginners encounter frequently. Learning to recognize them early will save a lot of time.

A `SyntaxError` means Python could not understand the structure of your code. This often happens because of a missing colon, unmatched parentheses, or incorrect indentation, as shown in the following code:

```
if x > 5
    print("Too big")
```
