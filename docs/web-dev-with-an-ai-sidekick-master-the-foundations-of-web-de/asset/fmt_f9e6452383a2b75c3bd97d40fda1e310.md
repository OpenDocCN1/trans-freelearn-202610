# Managing test data and fixtures

Most flaky or painful Django tests are not caused by Django. They are caused by messy test data. If the test setup is slow, confusing, or tightly coupled to unrelated details, tests become hard to write and easy to break. Good test data management keeps tests fast, readable, and independent.

The goal is simple: each test should set up only the data it needs, create it in a predictable way, and never depend on data created by some other test.

## Fixtures, factories, and why factories usually win

Django supports `fixtures`, usually JSON/YAML/XML files you load into the test database. They are tempting because you can create data once and reuse it. In practice, they often become brittle: a fixture file grows over time, contains irrelevant objects, and breaks whenever you change models. Django documents fixtures and how they are loaded via the `loaddata` management command. For example:

```
python manage.py loaddata initial_data
```

Django will look for files named `initial_data.json`, `initial_data.yaml`, or `initial_data.xml` in known fixture locations. Django searches in:

- A `fixtures/` folder inside each app
- Any directories listed in `FIXTURE_DIRS` in `settings.py`
- The current working directory

`Factories` (created in code) are usually a better default. They produce the exact objects a test needs, right where the test can see them, with sane defaults and explicit overrides. Factories also make refactors easier because model changes tend to cause clear Python errors instead of mysterious fixture load failures.

`Good practice`: Use factories for most tests. Use fixtures only for small, stable reference data (for example, a short list of countries, or a couple of static `question types`) and only if that data truly is stable.

## Django fixtures in tests

Django’s `TestCase` can load fixtures automatically by declaring a `fixtures` attribute on the test class. This is convenient, but you should keep fixture files small and focused. For example:

```python
from django.test import TestCase

class SurveyListFixtureTests(TestCase):
    fixtures = ["surveys_small.json"]

    def test_list_page_shows_published_surveys(self):
        response = self.client.get("/surveys/")
        self.assertEqual(response.status_code, 200)
```

Problems you tend to hit with fixtures:

- **Hidden coupling**: Tests depend on fixture IDs, ordering, or assumptions about what’s inside the file.
- **Hard to read**: The data is not near the assertion, so you mentally jump between files.
- **Refactor pain**: Renaming a field or changing a constraint can break fixture loading across many tests at once.
- **Slow growth**: One fixture becomes “the fixture” and accumulates unrelated objects.

If you do use fixtures, keep them small, and name them after the specific scenario they support.

## Factories in plain Django

You do not need a library to use factories. A simple approach is to write helper functions that create objects with defaults, and override with parameters. The defaults should be realistic, and they should always create valid objects.

Example helpers:

```python
from django.contrib.auth import get_user_model
from surveys.models import Survey

User = get_user_model()

def make_user(**kwargs):
    defaults = {
        "username": "user1",
        "email": "user1@example.com",
        "password": "pass12345",  # note: create_user will hash it
    }
    defaults.update(kwargs)
    return User.objects.create_user(
        username=defaults["username"],
        email=defaults["email"],
        password=defaults["password"],
    )

def make_survey(**kwargs):
    defaults = {
        "title": "Sample Survey",
        "slug": "sample-survey",
        "is_published": True,
    }
    defaults.update(kwargs)
    return Survey.objects.create(**defaults)
```

Then in a test:

```python
from django.test import TestCase
from django.urls import reverse

class SurveyListFactoryTests(TestCase):
    def test_list_shows_only_published(self):
        make_survey(title="Published A", slug="a", is_published=True)
        make_survey(title="Draft B", slug="b", is_published=False)
        response = self.client.get(reverse("surveys:list"))
        self.assertContains(response, "Published A")
        self.assertNotContains(response, "Draft B")
```

## Factories with factory_boy

If you want a more scalable factory approach, the most common Django-friendly library is `factory_boy`, which provides declarative factories and handy features like sequences and subfactories. In a book context, it’s worth mentioning as an option, even if you keep the core examples library-free.

A typical pattern with `factory_boy` is:

- Use `Sequence` for unique slugs/usernames.
- Use `SubFactory` for related models.
- Keep the default state valid and minimal.

## Database transactions and test isolation in Django

Django’s `TestCase` isolates tests using database transactions. At a high level:

- Django creates a test database (or reuses one, depending on settings) for the test run.
- Each `TestCase` runs inside a transaction and is rolled back so the next test starts clean.

This is why you can safely create objects in one test without them leaking into another.

`TransactionTestCase` is a lower-level base class that does not wrap each test in the same fast transactional approach, and is used when you need to test behavior that depends on real transaction commits. This is less common for typical web app tests, but matters if you test transaction hooks or some concurrency behavior.

Practical implications:

- Use `TestCase` for most integration and model tests.
- Use `TransactionTestCase` only when you have a specific reason.
- Keep tests deterministic. Do not depend on implicit ordering from the database unless you specify ordering.
