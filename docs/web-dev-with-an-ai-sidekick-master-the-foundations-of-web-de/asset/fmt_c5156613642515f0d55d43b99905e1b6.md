
This setup works, but it requires coordination. The server must already be running before the tests start, and if it is not, the failures can be confusing because Playwright will simply fail to connect. In automated environments such as CI, you would not rely on two manual terminals. Instead, you would start Django as part of the test run itself, either by using a test server (such as Django’s `LiveServerTestCase`) or by using a test runner that launches and tears down the server automatically. That leads us to the second option.

1. Start a test server from `pytest`. This is cleaner for CI, but a little more setup.

For this book, starting the dev server manually is often easier, and then you can implement the automated approach later. A simple improvement, even during development, is to script both steps together. For example, you can use a shell script or task runner that starts Django and then runs Playwright tests once the server is ready. This removes the need to manually coordinate two terminals:

```
# Example (Unix-like systems)
python manage.py runserver &
pytest e2e
```

This is a simple approach for learning, but in real projects, you would use a more robust process that waits for the server to be ready before running tests.

When beginners run Playwright tests without a running server, they see connection refused errors, timeouts, and `page.goto failed` messages. None of those errors clearly say: “you forgot to start Django.”

In the examples below, assume the server is running at: `http://127.0.0.1:8000`.

## A first Playwright test: Login Required Redirect

Create `e2e/test_auth_flow.py`:

```
import re
from playwright.sync_api import Page, expect
BASE_URL = "http://127.0.0.1:8000"
def test_protected_page_redirects_to_login(page: Page) -> None:
    page.goto(f"{BASE_URL}/surveys/")
    # Expect we end up on the login page (URL patterns vary by project).
    expect(page).to_have_url(re.compile(r".*/login/?(\?.*)?$"))
    # And the login form should be visible (adjust label/text to your templates).
    expect(page.get_by_label("Username")).to_be_visible()
    expect(page.get_by_label("Password")).to_be_visible()
```

Notes:

* `expect` provides automatic waiting and clearer failures than manual sleeps.
* Use labels where possible. If your form fields do not have labels, add them. It improves accessibility and testability.

## Testing a real user journey: Create a Survey

UI tests should exercise the same steps a user takes. For that, you need a known user account.

You can create test users in a few ways:

* Create a dedicated user in your dev database
* Use a setup script/fixture to create a user automatically
* Use the Django admin to create a user once

The simplest is: create a user once (for example, `mark` / `password123`) and use that in early UI tests, then later evolve into an automated setup. For learning, creating a test user manually is fine. In a real project, E2E tests should create their own data programmatically. Django’s `StaticLiveServerTestCase` provides a test server with a clean test database, or you can write a setup script that creates the required test user before each test run.

Create `e2e/test_surveys_crud.py`:

```
import os
from playwright.sync_api import Page, expect
# Read base URL from an environment variable with a default.
BASE_URL = os.environ.get("BASE_URL", "http://127.0.0.1:8000")
USERNAME = "mark"
PASSWORD = "password123"
def login(page: Page) -> None:
    page.goto(f"{BASE_URL}/login/")
    page.get_by_label("Username").fill(USERNAME)
    page.get_by_label("Password").fill(PASSWORD)
    page.get_by_role("button", name="Log in").click()
    expect(page).to_have_url(f"{BASE_URL}/surveys/")
def test_create_survey(page: Page) -> None:
    login(page)
    page.get_by_role("link", name="New survey").click()
    expect(page).to_have_url(f"{BASE_URL}/surveys/new/")
    page.get_by_label("Title").fill("Best Star Trek Captain")
    page.get_by_role("button", name="Save").click()
    # Back on list page, new survey should appear.
    expect(page).to_have_url(f"{BASE_URL}/surveys/")
    expect(page.get_by_text("Best Star Trek Captain")).to_be_visible()
```

This test proves:

* Authentication works
* Navigation works
* Forms render and submit
* Data appears in the UI

Adjust the link text, button text, and URLs to match your templates.

## Edit and delete tests

Once you have created a working test, edit and delete follow the same pattern. Keep them short:

```
def test_edit_survey_title(page: Page) -> None:
    login(page)
    page.get_by_text("Best Star Trek Captain").click()  # or click an "Edit" link
    page.get_by_label("Title").fill("Best Star Trek Series")
    page.get_by_role("button", name="Save").click()
    expect(page.get_by_text("Best Star Trek Series")).to_be_visible()
def test_delete_survey(page: Page) -> None:
    login(page)
    page.get_by_text("Best Star Trek Series").click()
    page.get_by_role("button", name="Delete").click()
    expect(page.get_by_text("Best Star Trek Series")).not_to_be_visible()
```

If your UI uses confirmation dialogs, Playwright can handle them, but a beginner-friendly approach is to implement a simple confirmation page in Django rather than a browser modal.

## Keeping UI tests reliable

Most flaky UI tests come from two causes: unstable selectors and timing assumptions.

* Use stable selectors:
    * Prefer `get_by_role`, `get_by_label`, and visible button/link names
    * Use `data-testid` only for a handful of key controls
* Never use sleeps:
    * Avoid `time.sleep(...)`
    * Use `expect(...)` which waits until the condition is `true` or times out
* Reset state. UI tests should not depend on the previous test order. If your tests create surveys, either:
    * Create unique titles per test, or
    * Clean up after the test, or
    * Reset the database between UI runs (best for CI)

## Debugging failures: headed mode, screenshots, and traces

When a UI test fails, you want evidence. Unlike unit tests, browser tests involve timing, rendering, and user interaction, so failures are not always obvious from the test output alone.

One of the most important concepts to understand is the difference between headless and headed browser modes:

* **Headless mode (default)**: The browser runs without a visible window. This is faster and is typically used in CI pipelines and automated runs.
* **Headed mode**: The browser window is shown on screen. You can watch the test interact with the page in real time, which is extremely useful when debugging.

**Good practice**: Use headless for speed and automation. Use headed when something is failing and you need to see what is happening.

Run tests in headed mode (visible browser) while developing or debugging tests:

```
pytest -s e2e --headed
```

You can also slow down interactions to make them easier to follow:

```
pytest -s e2e --headed --slowmo 200
```

The preceding code adds a delay (in milliseconds) between actions so you can visually track what the test is doing.

Even with the headed mode, you often want a record of what went wrong, especially in CI where no screen is visible. A simple pattern is to capture a screenshot when a test fails:

```
def test_something(page: Page) -> None:
    try:
        # test steps...
        pass
    except Exception:
        page.screenshot(path="e2e_failure.png", full_page=True)
        raise
```

For more complex failures, Playwright also supports tracing, which records:

* Screenshots at each step
* Document Object Model (DOM) snapshots
