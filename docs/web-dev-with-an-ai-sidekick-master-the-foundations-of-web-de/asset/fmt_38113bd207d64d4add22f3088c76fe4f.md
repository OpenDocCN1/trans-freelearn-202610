
# Spec-Driven Development

In the previous chapter, you used a large prompt and a product requirements document to generate the first working version of `TallyApp`. That approach demonstrated how AI tools can scaffold an entire project quickly. However, real software projects rarely stop after the first implementation. New features are added, behavior is refined, and edge cases are discovered as the system evolves.

For the next feature, do not start by asking the AI to “add something useful.” Start by writing down the feature. Say what it should do, who can use it, what should happen when it fails, and how you will check that it works.

This style of working is often called **Spec-Driven Development**. The specification becomes the agreed description of the feature, and the code becomes its implementation. When AI coding assistants are involved, this discipline is particularly important because they tend to fill in missing details by inventing behavior based on unvalidated assumptions. A clear specification leaves fewer gaps for the AI to fill and gives the AI less room to invent behavior you did not ask for.

In this chapter, you will apply this approach to the existing `TallyApp` Django project. Instead of generating a brand new application, you will extend the current codebase by designing and implementing a small but realistic feature.

By the end of this chapter, you will have written a structured feature specification, used an AI coding assistant to implement it inside an existing Django project, and verified that the implementation satisfies clearly defined acceptance criteria.

## Spec-Driven Development

In Spec-Driven Development, you begin with a written description of what the system should do. Instead of starting with code and hoping the design sorts itself out, write down the feature first: the problem, what is in scope, what is out of scope, and what must be true when the work is finished. Then you implement.

This idea is not new. Good engineers have always written requirements, user stories, and acceptance criteria. What is new is the presence of AI coding assistants. Tools such as `GitHub Copilot`, `OpenAI Codex`, and `Claude Code` can generate large amounts of code quickly. They can scaffold projects, refactor modules, and even propose architectural changes. That can help, but it also introduces risk. Without a clear specification, AI tools will confidently implement assumptions you did not intend. They will fill in gaps you did not know existed. They will optimize for plausibility rather than correctness. That is dangerous because plausible code is often harder to spot than obviously broken code.

Spec-Driven Development brings discipline to AI-assisted coding. The specification becomes the reference document. It defines the scope of the feature, the non-goals, the data model, the behavior of the user interface, and the error conditions. The AI is not asked to *build an app*. It is asked to satisfy explicit acceptance criteria. Each requirement must be traceable to code. Each behavior must be verifiable.

This is why the specification matters. `Codex` or `Claude Code` can write a lot of Django code, but it will not know whether a feature is finished unless you define finished. For the URL shortener, that means writing rules such as: who can create links, how codes are generated, what happens for an unknown code, and which tests must pass.

> **Prompt:** Why do AI coding assistants tend to make incorrect assumptions when specifications are incomplete? Describe the risks of vague requirements when using AI coding assistants.

Tests turn a specification from a document into something enforceable. A spec that cannot be verified is simply documentation. A spec backed by automated tests becomes enforceable. In a Python web project, this usually means mapping acceptance criteria to unit tests with `pytest` and, where appropriate, browser-level tests. The test suite becomes the referee. When AI generates code, the tests decide whether that code is acceptable. If it fails, the implementation is wrong, regardless of how polished it looks.

### What a Good Specification Contains

A useful web feature spec should be short, but not vague. For `TallyApp`, a typical feature spec might include the following sections:

#### Goal

A short paragraph describing what this feature enables. Example: *Allow authenticated users to create, edit, and delete surveys*.

#### Non-Goals

List what you are deliberately not building. Example: *No public survey sharing in this iteration*.

> **Prompt:** Please explain why “non-goals” are important in software specifications and give examples from real-world projects.

#### User Stories

Write the main interactions from the user’s perspective:

- As a logged-in user, I can create a new survey
- As a logged-in user, I can edit the title of an existing survey
- As a logged-in user, I can delete my own survey

#### Acceptance Criteria

These are precise, testable conditions. Acceptance criteria should be written so they can become tests without reinterpretation. Avoid vague statements like *the UI should be clean*. They should be observable facts:

- When a valid survey form is submitted, the survey is saved in the database
- When an invalid form is submitted, validation errors are displayed
- A user cannot edit another user’s survey
- After deletion, the survey no longer appears in the list view

> **Prompt:** Please show me some examples of poorly written acceptance criteria and how to rewrite them into clear, testable requirements.

#### Data Model Changes

Define fields, relationships, and constraints. For example:

- Survey: `id` (primary key), `owner` (foreign key to user), `title` (string, max length 200), `created_at` (timestamp). If a field has constraints, write them down. If a relationship has cascading behavior, specify it.

#### Error Handling and Edge Cases

- What happens if a user attempts to edit a survey that does not exist?
- What happens if required data is missing?
- What HTTP status codes should be returned for forbidden access?

> **Prompt:** Please give examples of edge cases developers often forget when writing specifications. Please explain how to identify hidden assumptions in a software specification.

#### Verification Commands

Write down how you will check the feature later:

- Run unit tests
- Run integration tests
- Start the development server and confirm behavior manually if needed
