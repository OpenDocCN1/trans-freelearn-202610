## 技术架构

开展与 Salesforce 协作构建应用程序的旅程，可能有点像站在大都市的十字路口。您有两个主要起点可供选择，每个起点都通向一种独特的应用程序类型。

第一条道路通向原生应用，这些应用主要在 Salesforce 生态系统内构建，并且不与外部系统集成。第二条道路通向复合应用，这些应用旨在与 Salesforce 之外的其他系统无缝集成。

这些道路的区别在于构建应用程序时所使用的 Salesforce 技术数量。然而，值得注意的是，这些路径并非严格线性。有时，合作伙伴会发现自己从原生应用转向复合应用，反之亦然，这表明这些道路可能会随着时间的推移而相交和交叉。

正如城市的建筑可以赋予其独特的风味，应用程序类型的选择对其设计有着深远的影响。每个应用程序都经过精心打造，可无缝融入客户的 Salesforce 景观，就像一座新建筑与城市天际线和谐地融合在一起。但关键部分来了。这种选择不仅仅是关于 Salesforce 生态系统内的美观或功能。对于复合应用而言，考虑与外部系统的集成至关重要，这可能需要使用上一章中未涵盖的技术和概念。

就像城市规划者在设计新城区时考虑道路连接一样，您对应用程序类型的决策会影响与外部系统的集成路径。这不仅仅是构建一个独立实体，而是构建一个更大网络中相互连接、交互的组件。因此，当您开始绘制应用程序蓝图时，请记住这一点：您所构建的应用程序类型不仅定义了其独立结构，还定义了它与 Salesforce 之外的世界互动、集成的方式，并可能引入复杂性。

## 原生应用程序

原生应用程序完全构建在 Salesforce 平台上，并充分利用 Salesforce 的基础设施管理、核心功能和创新。此类应用程序受益于市场上最强大的功能，因为它们 100% 建立在 Salesforce 平台之上。

原生应用程序的关键方面包括以下内容：

- 完全构建在 Salesforce 平台上
- 受益于 Salesforce 的基础设施管理和核心功能
- 与客户的 Salesforce 实例无缝集成
- 快速开发和创新
- 无需担心数据驻留——所有数据都托管在客户 Salesforce 实例所在的位置

## 复合应用程序

复合应用程序是 ISV 构建的最常见的应用程序类型。这些应用程序主要在平台外构建，但包含部分构建在 Salesforce 平台上的功能。通过利用 Salesforce 技术，复合应用程序可以更无缝地融入客户的 Salesforce 实例，从而提高可见性和采用率。

复合应用程序的关键方面包括以下内容：

- 应用程序的部分构建在平台外
- 部分功能构建在 Salesforce 平台上
- 与客户的 Salesforce 实例无缝集成
- 更高的可见性和更高的采用率

## 集成的扩展包

在将 Salesforce 与外部系统集成时，确保产品的核心功能不受影响至关重要。如果集成不是核心产品的主要组成部分，请考虑将其作为扩展包交付，您可能在 *第 4 章* 中回忆起这一概念。

保持集成在核心包之外的想法源于解耦的需求。这种分离确保集成模块中的任何潜在问题或更改都不会影响核心产品的性能或功能。

此外，客户通常具有多样化的集成需求。有些人可能希望与常用的外部系统连接，而其他人可能具有根据其运营量身定制的具体要求。通过采用扩展包，您可以在不使核心产品复杂化的情况下满足这些不同的需求。

本质上，虽然集成在增强产品功能方面发挥着至关重要的作用，但以模块化思维方法对待它们至关重要。扩展包提供了一种结构化解决方案，确保核心产品精简，同时提供灵活性以满足不同的集成要求。

## 远程过程调用——请求和回复

此模式涉及客户端应用程序向远程服务发出请求并等待响应。客户端在收到响应或发生超时之前处于阻塞状态。此模式通常用于客户端需要在继续之前处理响应时使用。

例如，ISV 可能会使用此模式将第三方支付处理服务集成到其 AppExchange 应用程序中。当客户付款时，应用程序向支付服务发送请求，并在继续之前等待确认响应。

## 远程过程调用——即发即弃

在此模式中，客户端应用程序向远程服务发送请求，但不等待响应。当客户端不需要

立即处理响应，或根本不处理。

例如，ISV 可以使用此模式将来自其 AppExchange 应用的使用数据发送到远程分析服务。应用程序可以在不等待分析服务响应的情况下继续运行。

## 批量数据同步

批量数据同步涉及在计划的间隔内传输大量数据。当不需要实时数据时，此模式很有用，对于大型数据集而言，其比实时传输数据更高效。

一个例子可能是 ISV 需要每晚在 AppExchange 应用程序和远程数据库之间同步数据。应用程序全天收集数据，然后在非高峰时段以单批方式全部发送到数据库。

## 远程调用

远程调用模式涉及远程服务向客户端应用程序发出请求。这与远程过程调用模式相反，在该模式中客户端向服务发出请求。

一个例子是 ISV 将其 AppExchange 应用与外部地址验证服务集成。当用户在应用程序中输入地址时，AppExchange 应用会发送请求以验证地址的准确性和格式。外部地址验证服务随后检查地址并返回验证结果，确保数据的准确性和一致性。

## 基于数据变化的 UI 更新

此模式涉及根据托管在平台外的底层数据的变化来更新应用程序的用户界面。这使应用程序能够向用户提供实时反馈。

例如，ISV 可以使用此模式在托管在其 AWS 实例中的底层数据发生变化时更新其 AppExchange 应用程序中的驾驶舱。一旦检测到更改，应用程序就会更新 Salesforce 驾驶舱以反映新数据。

## 数据虚拟化

数据虚拟化是一种数据管理方法，允许应用程序在无需了解数据的技术细节（例如其在源处的格式或物理位置）的情况下检索和操作数据。这降低了数据错误的风险以及移动可能永远不会使用的数据的工作量，并且不会试图对数据强加单一的数据模型。

例如，ISV 可能会使用数据虚拟化在其 AppExchange 应用程序中提供来自多个来源的数据的统一视图。应用程序可以像所有数据都在单个位置一样访问和操作数据，即使实际上数据分布在多个数据库中。

## 选择合适的集成模式

为您的应用程序选择合适的集成模式是一个关键决策，会显著影响其性能、用户体验和整体成功。在深入编码细节之前，请花点时间进行深思熟虑。通过自问以下问题，您可以简化开发流程，并通过确保选择最合适的设计模式来可能节省数周的努力。
请记住，少量的前期规划在创建稳健高效的集成解决方案方面可以大有裨益。

### 1. 需要什么交互级别？

考虑客户端应用程序与远程服务之间所需的交互程度。您需要立即响应，还是应用程序可以在等待响应的同时独立运行？如果实时交互至关重要，则同步模式可能最佳。另一方面，如果应用程序可以在没有即时反馈的情况下继续运行，您可以探索不会阻塞应用程序进度的异步模式。

### 2. 数据一致性有多重要？

思考在应用程序和远程服务之间保持一致数据的重要性。如果数据准确性至关重要，则促进同步通信和即时反馈的模式可能是合适的选择。然而，如果可以容忍数据中的细微差异，异步模式可能提供更多灵活性。

### 3. 真的需要实时响应吗？

考虑客户端应用程序是否必须在继续之前等待远程服务的响应。如果不是，允许非阻塞通信的模式，例如“即发即弃”，可能更有优势。这种方法可以防止应用程序工作流程和响应能力的延迟。

### 4. 数据量是多少？

评估需要传输的数据量。对于大型数据集，批量数据同步模式可能比实时传输更高效、更实用。这可以帮助您管理网络资源并保持应用程序的性能。

### 5. 谁发起请求？

检查远程服务是否需要向客户端应用程序发起请求。根据通信方向，您可能需要选择特定的调用模式，例如“远程调用”模式，以适应这些场景。

### 6. 是否需要实时 UI 更新？

思考应用程序的用户界面是否应根据外部数据变化实时更新。如果是，则“基于数据变化的 UI 更新”等模式可以帮助您提供动态且响应迅速的用户体验。

### 7. 是否涉及不同的数据源？

如果您的应用程序需要在不强加单一数据模型的情况下处理来自各种来源的数据，请考虑“数据虚拟化”模式。这种方法可以在无需大量数据转换工作的情况下统一数据。

通过花时间思考这些问题，您为集成解决方案奠定了坚实的基础。请记住，一个小时的深思熟虑的规划可以转化为开发过程中节省的数周时间，从而实现更高效、更有效、更成功的 AppExchange 应用程序。因此，在编写第一行代码之前，请参与这一关键的最优模式选择阶段。

## 外发集成的可用技术

Salesforce 提供了一系列工具和方法来促进与外部系统的外发集成。在本节中，我们将探讨 Salesforce 平台提供的最流行和最广泛使用的外发集成技术。

### 使用 Flow 的声明式

Salesforce 中的声明式外发集成主要通过使用 Flow 实现。Salesforce Flow 是一款强大的工具，允许用户无需编写代码即可自动化业务流程。在外发集成的领域中，Flow 提供两种主要方法：外发消息和外部服务。

外发消息是 Salesforce 在满足特定条件时发送给外部系统的 SOAP 消息。它们旨在通知外部系统 Salesforce 数据的变化。另一方面，外部服务为流程直接集成第三方 API 提供了一种方式，支持使用 GET、POST、PUT、PATCH 和 DELETE 等方法的 HTTP 调用。在创建外部服务包时，开发人员可以向外部服务注册包添加命名凭据组件，或者订阅者可以在其组织中建立与外部服务注册中指示的命名凭据匹配的命名凭据。

### 使用 Lightning Web Components 的编程方式

Lightning Web Components (LWC) 虽然主要设计用于在 Salesforce 平台上构建动态用户界面，但也能够执行编程外发集成。

LWC 利用现代 Fetch API 向外部服务进行调用。此 API 提供了一种灵活高效的方式来获取资源，无论是通过 HTTP 还是 HTTPS。LWC 中的 Fetch API 允许开发人员向外部服务发出异步请求。开发人员可以指定请求方法（GET、POST、PUT、DELETE）、标头和请求正文，然后在收到响应后进行处理。

在从 LWC 进行调用之前，将 API 端点的基本 URL 添加到 Salesforce 中的内容安全策略 (CSP) 受信任站点至关重要。

### 使用 Apex 的编程方式

Apex 是 Salesforce 的专有编程语言，是希望以编程方式进行外发集成的开发人员的基石。它提供了一套全面的工具和方法来促进与外部系统的通信。

HTTP 和 HTTPS 调用：Apex 提供了内置类来执行向外部服务的 HTTP 和 HTTPS 调用。这些调用允许 Salesforce 与几乎任何 Web 服务集成，无论是 RESTful 还是基于 SOAP。

HttpRequest 和 HttpResponse 类：Apex 调用的核心是 **HttpRequest** 和 **HttpResponse** 类。**HttpRequest** 类允许开发人员设置请求的各种参数，例如端点 URL、方法（GET、POST、PUT、DELETE）、标头和请求正文。一旦调用完成，外部服务的响应将被捕获在

一个 **HttpResponse** 类的实例，它提供了检索响应状态、头信息和正文的方法。

## 你应该使用哪一个？

选择 Salesforce 中出站集成的适当技术取决于几个关键因素：所采用的集成模式、外部系统的功能以及特定的安全要求。必须将即将到来的 *集成密钥管理* 部分中强调的限制与每种技术的独特要求（如对命名凭据的需求）进行对比。根据我的经验，大多数 ISV 在构建出站集成时倾向于使用 Apex。这种偏好的理由很明确：Apex 提供了无与伦比的适应性。它赋予开发人员调整集成的每个方面的自由，从微调请求头到设计定制的错误处理策略。总而言之，虽然前方有多条道路，但集成的旅程往往在 Apex 中找到最可靠的指引。

## 平台事件的挑战和限制

平台事件存在若干挑战和限制⁴。主要考虑因素是它们不提供保证交付⁵，这意味着在基础设施出现问题的情况下，事件可能会丢失，使其不适合传输不可替代的数据。此外，像 CometD 这样的传输方式存在重大限制，这可能会阻碍集成的扩展。一些用户还报告了可靠性问题，指出由于网络波动，在与外部系统集成时他们错过了大约 5% 的消息。此外，在出站集成的上下文中，外部系统必须能够订阅和处理事件。这意味着它需要实现 CometD 协议并不断监听传入事件。

考虑到这些限制，让我们通过下表比较 API 和事件：

| 准则 | API | 事件（平台事件和变更数据捕获） |
|---|---|---|
| 可靠性 | 具有错误处理的高度可靠性。 | 存在事件丢失风险；无保证交付。 |
| 可扩展性 | 更高限制，适合高容量集成。 | 对 CometD 等传输方式的限制。 |
| 灵活性 | 支持推送和拉取机制。 | 主要基于推送。 |
| 复杂性 | 简单的请求-响应方法。 | 处理遗漏事件时可能存在复杂性。 |
| 数据完整性 | 即时反馈确保数据完整性。 | 存在数据丢失或事件乱序的风险。 |

总之，虽然平台事件和变更数据捕获为 Salesforce 客户提供了独特的优势，但从 ISV 的角度来看，API 作为将 Salesforce 与外部系统集成的更可靠、可扩展且更直接的解决方案脱颖而出。

## 集成密钥管理

在创建托管包时，保护集成密钥是优先事项。不同的 Salesforce 元数据类型提供了存储和管理这些密钥的方法，包括命名凭据、外部凭据和受保护的自定义元数据类型。在本节中，我们将探讨这些选项中的每一个，并提供有关为什么受保护的自定义元数据类型是大多数托管包最安全且最合适的选择的信息。

从命名凭据开始，它们提供了一种简化的方式来管理和验证对外部系统的调用。然而，对于托管包开发人员而言，其使用存在重大注意事项。最重要的是，命名凭据可以被订阅组织中的任何代码使用。这一事实固有地增加了您打包的密钥暴露和被滥用的风险。此外，命名凭据存在实际限制，例如由于安全原因无法在元数据中包含密钥值——元数据可以以纯文本 XML 访问。此外，远程端点详细信息通常无法在打包时确定，导致复杂性增加。因此，我不建议在托管包中分发密钥时使用命名凭据。

同样，外部凭据虽然旨在安全地存储外部系统的密钥，但并非没有限制。根据 Salesforce 元数据覆盖报告，截至我撰写本书的 2023 年，其目前不支持 2GP 打包是主要问题。这种缺乏支持在考虑托管包的外部凭据时构成了相当大的限制。要获取有关 Salesforce 元数据支持的最最新信息，您可以查看官方 Salesforce 元数据覆盖报告 https://developer.salesforce.com/docs/metadata-coverage。该资源将允许您验证上述限制是否已得到缓解。

这就引出了受保护的自定义元数据类型。它们是存储 Salesforce 中密钥的高度安全选项，因为它们只能在同一命名空间内访问。这意味着它们对托管包之外的任何代码的访问或使用具有免疫力，从而增加了一层至关重要的安全保护。因此，如果您的托管包包含密钥，我建议使用受保护的自定义元数据类型。此选项还提供了存储各种配置或环境的多个密钥的灵活性。

然而，存储在订阅者之间有所不同且需要在每个组织中配置的密钥需要不同的方法。您可以提供创建命名凭据（新版或旧版）的说明，或开发自定义界面以安全地修改受保护的自定义元数据。

总之，虽然命名凭据和外部凭据各有其用例，但它们的限制通常使它们不适合在托管包中存储密钥。相反，受保护的自定义元数据类型的安全性和灵活性通常使其成为此目的的理想选择。

## 配置受保护的自定义元数据

在使用 Salesforce 或任何类似平台时，保护元数据变得至关重要，特别是如果它包含可能影响应用程序或其用户的安全性和隐私的敏感数据。

受保护的自定义元数据，顾名思义，为您的元数据提供了一层保护。一旦纳入，客户组织中的用户无法读取或修改信息。这在防止未经授权的更改或潜在数据泄露方面非常有效。

然而，可能存在这样的场景，您可能希望受信任的人员（例如客户的管理员）在不向其提供所有元数据访问权限的情况下配置某些信息。一个常见的用例是当您希望允许配置集成所需的消费者密钥和消费者密钥时。



为满足此类需求，最优解决方案是设计一个配置向导。通常，这是一个简单的 Lightning Web Components (LWC) 界面，为管理员提供更新或配置必要细节的途径，而无需访问完整的元数据。有了此界面，管理员提供必要的数据，然后您的 Apex 代码会安全地将这些信息保存到受保护的自定义元数据中。

## Security pitfalls

虽然配置向导为管理员提供了增强的灵活性，但仍需谨慎注意潜在的安全陷阱。开发人员和管理员应了解的一个关键问题是被称为“password echo”的漏洞。密码或任何敏感数据在输入后绝不应回显给用户，因为这是存储不安全的一个明显迹象。理想情况下，密码应使用涉及哈希和加盐的方法进行存储，确保即使系统本身也不知道明文版本，从而使密码回显实际上不可能。此外，包含敏感数据的字段，例如 **Consumer Key** 和 **Consumer Secret**，应保持隐藏。管理员在配置向导中首次输入时可能需要查看这些值，但在后续交互或编辑过程中不应能够访问它们。此外，务必始终警惕数据的记录位置。确保敏感细节不会意外出现在 debug logs、JavaScript logs 或其他非预期存储点中，对于维护系统的安全完整性至关重要。此类漏洞可能是导致安全审查失败的原因，我们将在下一章深入探讨这一主题。

## Utilizing Salesforce APIs for inbound integrations

你可能在想，API 到底是什么？好吧，让我们拆解一下。你可以把 Application Programming Interface（API）想象成一个勤奋而有礼的管家，总是准备好将你的消息（请求）从一个房间（一个应用程序）递送到另一个房间（服务器），取回答案再带回来给你。这一切都很有《唐顿庄园》的感觉，只是我们面对的不是 Dowager Countess，而是数据。

在 Salesforce 领域，API 就像高效的桥梁建造者，在你的 Salesforce Org 与其他功能之间构建坚固的连接，拓展你在商业生态系统中的版图。

## Types of Salesforce APIs

好吧，Salesforce 拥有一个完整的 API 自助餐——每种都有其独特的风味和用途。这简直就是一场 API 拼盘聚会！

SOAP and REST APIs：可将它们视为 Salesforce 提供的每项丰富 API 功能的基础。它们就像 API 世界中必不可少的面包和黄油。

Connect REST API：这类似于为移动应用程序提供的个人礼宾服务，擅长从推送通知到展示你的 Chatter 动态等一切事务。

Metadata API：它为你提供进入 Salesforce Org 后台的通道。它处理设置的方式就像舞台经理一样——管理自定义和构建工具，而不是舞台设备。

User Interface API：此 API 让你可以编排一场独特的舞台表演——在这种情况下，打造一个按你设想方式呈现 Salesforce 数据或元数据的用户界面。

GraphQL API：将其想象为 API 乐团的指挥，通过允许客户端请求所需内容来协调和谐的交互。GraphQL 作为单一端点，根据查询动态塑造响应，而不是多个端点返回固定的数据结构。

Bulk API：想象它是一个超级英雄助手，能够在一举之间处理庞大的数据量并以强力扫荡的方式操作记录。

Streaming API：这是你的专属新闻播报员，提供实时更新流，让你随时了解 Salesforce Org 中每一次细微变化。

Tooling API：当复杂元数据类型需要专家之手时，Tooling API 便会介入，以精湛的技巧处理它们。

Analytics REST API：最后，Analytics API 充当你的可靠间谍，深入特定数据集、筛选器和仪表板以获取宝贵的情报。

## Choosing the right Salesforce API for integration

![](img/44ed632038957e4c80220676e84c5109_264_0.png)

选择 API 有点像速配活动——你希望能迅速找到合适的匹配。你需要实时查看数据变化吗？Streaming API 听起来不错。处理海量数据？Bulk API 可能是你的英雄。如果你想把 Salesforce Apex 代码开放给世界，Apex SOAP 和 REST API 可能就会俘获你的心。

在 API 世界中，了解它们独特的个性和特征是建立成功关系的关键。明智选择，你将打造出一套推动生产力和创新同时始终将用户体验放在首位的强大工具组合。

## Developing an Apex REST endpoint

标准 API 提供了广泛的功能并满足许多常见用例。然而，有时这些标准方案无法满足 ISV 对灵活性的需求或不符合其特定要求。这就需要构建自定义 Apex REST 端点。

Apex REST 方法使开发人员能够使用 Apex 编程语言构建自定义 RESTful Web 服务。这些服务在外部调用时，填补了标准 Salesforce API 可能不足的能力鸿沟。方法提供了灵活性，使开发人员能够设计符合特定需求的 API。此外，Apex REST 方法与标准 HTTP 方法无缝集成，便于执行 CRUD 操作和各种其他操作。

要使一个 Apex 类成为外部服务的灯塔，它需要被 **global** 注解装饰。这不仅将该类公开为 RESTful Web 服务，还确保其可从 Salesforce 域外部访问。

## Best practices for designing your APIs

API 设计是一个细致的过程，遵循行业最佳实践可确保其稳健、可理解且安全：

- Consistency：命名约定以及请求和响应结构的一致性可增强可用性。
- Versioning：在初始阶段进行版本控制可促进变更管理，防止潜在中断。
- HTTP Status Codes：使用合适的 HTTP 状态码描述 API 调用的结果至关重要。
- Error Handling：清晰且有意义的错误消息有助于用户进行故障排除。
- Security：纳入强大的身份验证和授权层。在 Salesforce 上下文中，OAuth 通常是首选。此外，建立输入清理和验证以防止注入和 XSS 攻击至关重要。我们将在下一章更详细地探讨这些安全要素。
- Pagination：为数据密集型端点实现分页，将结果分割为易于消化的部分。
- Rate Limiting：执行速率限制，确保公平使用并减轻潜在滥用。
- Documentation：详细的文档，涵盖请求-响应结构、错误和示例等方面，可提升用户体验。

## Potential pitfalls

在 API 开发和部署的迷宫中导航时，某些陷阱会挑战旅程：

- Versioning Issues：明显缺少版本控制会引发重大挑战，尤其是在产品演进且 REST 端点修改不可避免时。当现有用户绑定到旧版本时，可能导致创建近乎相同的 REST 端点。一种补救措施是在 urlMapping 中嵌入版本号，例如 `@RestResource(urlMapping='/AccountsList/v1/*')`。从初始版本起就采用此模式可避免未来的复杂问题。
- Information Disclosure Vulnerability：诸如披露系统或调试数据之类的细微泄漏可为对手提供洞察，可能促进攻击策略。此类泄漏通常发生在系统或调试数据意外通过输出流或日志机制渗出时。为防范此问题，请创建自定义错误消息，细心地掩盖诸如堆栈跟踪、路径信息或任何调试数据等复杂细节。必须在所有 API 中修复此类漏洞。此漏洞可能是导致安全审查失败的原因，我们将在下一章深入探讨这一主题。

## API rate limit management – ensuring efficient usage

API 速率限制是 Salesforce 管理其资源需求的机制。它在 24 小时内设置了应用程序可进行的 API 调用次数的最大限制。此功能旨在

防止单个应用过度消耗资源，从而确保所有应用的资源分配均衡和系统性能最优。

## API 调用限制的原理与方式

Salesforce 制定了 API 调用限制，其额度根据组织类型、许可证数量以及额外购买的授权而有所不同。请注意，计入这些限制的 API 调用不仅包括你的 AppExchange 应用直接发出的调用，还包括应用内任何集成服务和自动化流程发起的调用。

## 高效使用 API 调用：一种战略方法

妥善管理 API 调用是确保你的 AppExchange 应用平稳运行而不触及速率限制的关键。你可以考虑一些策略，例如批量处理，它允许将多条记录打包成一次 API 调用。在处理海量数据时这一点尤为重要。目标是以最少的 API 调用消耗获得最大结果——这就是效率的本质。

## 预估与监控 API 使用情况

不要仅仅被动应对 API 使用情况，你需要主动预防。在托管包的设计阶段，计算包中使用的每个 API 的预期使用量。这种前瞻性思考可确保你的终端客户不会意外触及限制。应用上线后，使用 Salesforce 的“API 使用通知”以及 REST API 中的 limits 资源来密切监控你的 API 调用消耗。这些措施有助于你发现趋势并相应调整使用模式。

## 处理“请求过多”错误：救援方案

你的应用可能会超出分配的 API 调用限制，出现“请求过多”错误。这时你需要一个稳健的方案来处理速率限制错误。实施带有指数退避的重试机制是推荐的策略，以度过这一小插曲。它在尝试下一次 API 调用前为你的应用提供超时时间。

总之，熟练掌握 API 速率限制管理是精通 AppExchange 应用开发不可或缺的一部分。

## Salesforce Connect

Salesforce Connect 是一项云集成服务，允许 Salesforce 用户直接在 Salesforce 内访问和管理外部应用中的数据。它使用 OData（开放数据协议）进行数据集成，使 Salesforce 能够通过 RESTful API 与外部系统中的数据交互。

OData 是一种开放标准协议，以简单标准的方式允许创建和消费可查询且互操作的 RESTful API。它使 Salesforce 能够对外部系统提供完整的 CRUD 支持（创建、读取、更新、删除）。

## 面向 ISV 的 Salesforce Connect

对于 ISV 而言，Salesforce Connect 提供了显著优势。它作为 ISV 合作伙伴的福利免费提供，每个合作伙伴可为每个客户获得三个许可证来连接合作伙伴拥有的数据源。这意味着 ISV 可以零额外成本将自己的外部数据源集成到 Salesforce 应用中。

然而，需要注意的是该福利存在限制。免费许可证仅用于连接合作伙伴拥有的数据源，任何用于其他目的的额外 Salesforce Connect 许可证将作为附加组件额外收费。

## Salesforce Connect 如何帮助降低开发成本？

Salesforce Connect 可以通过以下几种方式帮助 ISV 降低开发成本：

- 简化集成：Salesforce Connect 简化了将外部数据源集成到 Salesforce 的流程。这可以显著减少集成所需的时间和精力，从而降低开发成本。
- 实时访问：Salesforce Connect 提供对外部数据的实时访问。这消除了数据复制的需求，而数据复制可能成本高昂且耗时。
- 易用性：Salesforce Connect 使用 OData，这是一种广泛使用且易于理解的协议。这使得开发人员更容易使用，减少学习曲线并加快开发速度。
- 降低维护成本：通过提供无缝的集成解决方案，Salesforce Connect 减少了对自定义集成解决方案的持续维护需求，从而降低长期成本。

总之，Salesforce Connect 是 ISV 的有用工具。它提供了一种简单、经济的方式将外部数据源集成到 Salesforce，增强应用的功能和多功能性。要获取 Salesforce Connect 访问权限，ISV 可以在合作伙伴社区中以 **提交帮助案例** 类型提交案例，以便将其添加到产品目录中。

## 连接的应用

![](img/44ed632038957e4c80220676e84c5109_271_0.png)

连接的应用本质上是外部应用与 Salesforce 之间的桥梁。它使用标准协议进行身份验证、授权并为外部应用提供单点登录（SSO）。与 Salesforce 集成的外部应用可在各种平台、设备或 SaaS 订阅上运行。

例如，当你登录 Salesforce 移动应用并查看来自 Salesforce 组织的 数据时，你正在使用连接的应用。Salesforce 移动应用是一个连接应用，它与你的 Salesforce 组织集成，为你提供数据访问权限。

## 了解 Salesforce 连接应用和会话 ID

在 Salesforce 的互联生态系统中，连接的应用充当关键的授权工具，允许外部系统安全地“借用”会话 ID 用于特定用途。必须认识到会话 ID 所具有的强大权限——将会话 ID 授予第三方相当于递上一把上膛的枪，提供无限制的访问权限并可能延长过期时间。

对于内部 Salesforce 开发，共享会话 ID 可能是可行的选择，但必须遵循严格的安全措施。相比之下，对于 AppExchange 开发，如果需要与外部系统共享会话 ID，连接的应用不仅是建议，而且由于 Salesforce 的安全审查要求而是强制性的。为了确保安全集成，ISV 必须使用连接的应用。

请允许我重复：如果你查阅的是面向 Salesforce 开发人员的资料，而不是专门针对 AppExchange 开发的资料，你会发现连接的应用并非总是授权所必需的。在某些情况下，尤其是在内部开发中，可以在没有连接的应用的情况下进行授权，包括以下情况：

- 一个传出消息操作，为选定用户创建会话 ID。
- 一个交互式 Visualforce 页面使用其自身的会话 ID 调用 REST API。
- 一个内部公司系统使用存储的用户名、安全令牌或密码登录 Salesforce 并获取会话 ID。

然而，这些替代方法缺乏连接的应用所提供的先进安全措施和受控访问范围，这凸显了使用连接的应用进行安全、高效和受控集成的价值。

## Salesforce 连接应用的优势

连接的应用提供多个关键优势。它们促进使用情况的跟踪和审计，从而提高透明度和控制力。授予的访问级别可以自定义，确保外部应用仅具有必要的权限。访问时长也灵活，且授予的访问权限可以轻松撤销，而无需更改你的 Salesforce 密码。

Salesforce 本身在其产品中也使用连接的应用，例如 Workbench、Salesforce Mobile 和 Environment Hub，遵循最佳实践并展示了不直接处理原始登录凭据的重要性。

## 访问令牌、刷新令牌和 Salesforce 连接应用

与会话 ID 类似，访问令牌和刷新令牌也提供重要访问权限，但它们设计时增加了额外的安全保障——它们可以被撤销并且权限可以受限，从而为数据管理增加另一层安全保障。

## 连接应用与托管包

ISV 通常会疑惑连接的应用是否需要成为包的一部分。虽然开发人员通常可以在没有安装包的情况下进行断言并获取访问令牌，但在某些情况下安装是必要的。这些情况包括管理员希望在没有用户交互的情况下预先授权连接的应用，或组织特定策略（如登录 IP 限制）需要为该应用放宽的情况。

然而，连接的应用可以在不需要托管或非托管包的情况下安装。因此，ISV 可能不希望将连接的应用包含在托管包中。这对于托管或离平台集成尤其相关。此外，将应用包含在包中可能会因需要全局唯一的客户端 ID 或消费者密钥而使包开发复杂化。

在决定是否将连接的应用纳入托管包时，有几个关键因素需要权衡。以下是主要考虑因素的分解：

- 打包类型限制：连接的应用仅限于 1GP（第一代打包）。如果你使用的是 2GP，则需要为连接的应用创建单独的包。
- 分发范围：当你打包连接的应用时，它将对所有客户可用。这意味着每个安装

您的软件包将有权访问此应用。

- 一致的身份验证：打包带来的优势之一是其统一性。通过打包您的连接应用，您可以确保在所有 Salesforce 组织中使用相同的消费者密钥和密钥。
- 双层身份验证：连接应用采用双层身份验证系统。第一组凭据位于用户级别，第二组位于消费者或应用级别。这种双重身份验证同时使用消费者密钥/密钥和用户令牌/密钥，增强了安全性。从本质上讲，它类似于拥有两套用户名/密码组合。虽然这看起来可能很复杂，但它并不会使部署过程变得复杂。此外，如果需要，可以在用户级别或应用级别撤销访问权限。
- 跨平台应用身份验证：在创建时，连接应用会被分配唯一的消费者密钥和密钥。这允许应用在 Salesforce 平台上进行身份验证，确保其合法性。
- 回调 URL 的灵活性：连接应用的一个显著优势是其支持多个回调 URL 的能力。此功能在需要指定不同环境（如生产环境和测试环境）时特别有益。通过使用多个回调 URL 打包连接应用，客户可以根据需要无缝地在生产环境和测试环境之间切换。

通过了解这些注意事项，您可以就连接应用是否适合您的托管软件包做出明智的决定。

如果您决定在软件包中包含连接应用，一种推荐的配置连接应用以实现安全集成的方法是使用 OAuth 2.0 JWT Bearer Flow。这种稳健且安全的工作流允许应用程序自行向 Salesforce 进行身份验证，而无需共享密码或安全令牌等敏感信息。

## 如何（以及为什么）您的客户可以安装您的连接应用

安装连接应用不仅仅是为了促进 Salesforce 与外部平台之间的集成。对于您的客户的系统管理员而言，这关乎获得控制权和增强安全性。通过安装和配置连接应用，管理员可以定义谁可以使用应用、从何处访问以及在什么条件下访问。这包括设置配置文件、权限集、IP 范围限制，甚至实施多因素身份验证 (MFA) 以加强安全性。

在深入安装过程之前，务必向您的客户的系统管理员介绍安装连接应用的重要性和方法论。此步骤可确保他们了解应用的重要性，并在必要时能够协助或接管安装。

在客户的 Salesforce 组织上安装连接应用有几种方法：

- 通过托管软件包：这是一种最简单的方法之一，在此，系统管理员安装一个固有包含连接应用的托管软件包。
- 直接安装 URL：在连接应用未捆绑在软件包中的情况下，可以使用专用链接直接安装。此链接应在相关文档中 readily available，例如配置指南。以下是如何获取此链接的方法：
  - 登录您设置连接应用的 Salesforce 组织。
  - 转到 **Setup**，然后选择 **Apps**，接着选择 **App Manager**。从那里找到您的连接应用。
  - 查找 **id** URL 参数（它将以 0Ci 开头）。找到后，将其复制并粘贴到以下链接中：
    https://login.salesforce.com/identity/app/AppInstallApprovalPage.apex?app_id=0CiXXXXXXXXXXXX
- 使用连接应用 OAuth 使用页面：此平台列出当前链接到您组织中用户的全部 OAuth 连接应用。如果用户正在访问某个应用但尚未安装，则该应用旁边会出现 **Install** 按钮。
  - 转到 **Setup**，然后选择 **Apps**，接着选择 **Connected Apps**，最后选择 **Connected Apps OAuth Usage**。从列表中选择您想要的应用，然后点击 **Install**。

无论您如何安装连接应用，系统管理员都可以简单地导航到 **Setup**，然后选择 **Apps**，接着选择 **Connected Apps**，最后选择 **Manage Connected Apps**。从那里，您可以调整应用的本地访问权限。

## Canvas SDK

Salesforce Canvas SDK 是一款成熟且强大的工具，旨在将外部 Web 应用与 Salesforce 无缝集成。该技术在 Salesforce 与其他平台之间建立了桥梁，提供多种有效的 UI 集成选项。虽然 canvas 应用提供了大量机会，但了解其优势、局限性和适用用例是充分发挥其潜力的关键。

## Canvas SDK 的固有挑战和优势

Canvas SDK 尽管是一款强大的工具，但面临着关于 UI 和 UX 一致性的重大挑战。由于它将外部系统的用户界面带入 Salesforce，这可能并不总是能与 Salesforce 原生的 UI 和 UX 规范无缝对齐。这种差异可能会阻碍希望在应用中实现一致用户界面体验的 ISV。因此，尽管 Canvas SDK 是一款成熟且功能强大的技术，但其在 ISV 中的采用率并未像预期那样广泛。

然而，Canvas SDK 提供了多个显著优势，在合适的条件下使其成为一个有吸引力的选择。主要优势之一是开发成本可能更低，尤其是在外部系统已有界面的情况下。与在托管软件包中构建自定义用户界面并通过 API 集成相比，这一优势可能非常显著。

此外，Canvas SDK 可以简化连接应用框架内的操作，消除了维护两个相关代码库的需求——一个用于托管软件包，另一个用于外部系统。通过减少代码库数量，开发人员可以简化工作流程并降低系统的整体复杂性。

## Aura 与 Visualforce 与 LWC

开发人员在 Salesforce 中展示 canvas 应用时主要有两个选择：Aura 组件和 Visualforce，各自具有独特的优势和局限性。Visualforce 允许导入 Canvas JavaScript SDK 来处理 Canvas 事件。另一方面，Aura 组件可以使用 `lightning:isUrlAddressable` 功能维护 Salesforce 全局导航标题。需要注意的是，截至 2023 年，**Lightning Web Components (LWC)** 不支持 Canvas，限制了在 Salesforce 生态系统中使用该技术的选项。

## Canvas 应用配置和打包困境

Canvas 应用的关键配置，例如 OAuth 启用、canvas 应用 URL、访问方法和位置，均在连接应用中管理。开发人员还可以使用 Canvas 生命周期处理程序在运行时管理 canvas 应用的额外方面。

Canvas 应用虽然提供多种优势，但由于其在保持 UI 一致性方面的局限性以及缺乏对 LWC 的支持，并不常被使用。还需要注意的是，Salesforce 倾向于劝阻 ISV 使用 Canvas，并非出于安全问题——事实上，与 IFrame 解决方案相比，Canvas 更安全——而是出于认知问题。使用 Canvas 可能会被视为缺乏与 Salesforce 集成方面的认真承诺。当 ISV 在 AppExchange 上发布面向 Salesforce 的基于 Canvas 的解决方案时，他们可能会忽视 Canvas 通常意味着两种不同的用户体验这一事实。这可能会让客户措手不及，并可能降低成功销售的机会。Canvas 可能还存在额外的技术缺陷，这可能会使合作伙伴关系和应用成功变得不太可能。

如果您正在考虑使用 canvas 应用，建议与 Salesforce 或其中一家 **Product Development Outsourcer (PDO)** 合作伙伴讨论您的用例，该合作伙伴在 *Chapter 12* 中有描述。他们的专业指导可以帮助确保您的 Salesforce 集成符合最佳实践并取得成功。

## 通过 REST API 与 Canvas SDK 集成比较

在 Salesforce 中开发轻量级应用时，选择使用 REST API 集成还是 Canvas SDK 应由多个因素指导，每个因素都对开发的便捷性、灵活性以及集成的最终成功产生影响。在下面的表格中，我们从多个角度对比 REST API 和 Canvas SDK，以帮助您做出明智的决定。

|  | REST API 集成 | Canvas 应用 |
|---|---|---|

| 因素 |  |  |
|---|---|---|
| 交互性和集成深度 | 易于实现交互功能和更深层次的集成，提供更丰富的用户体验。 | 由于 Canvas SDK 的专有性质，实现交互性和更深层次的集成可能具有挑战性。 |
| 标准合规性 | 使用得到良好支持且广为人知的互联网标准，简化开发流程。 | 依赖专有 SDK 和技术，可能无法被普遍理解，造成潜在的学习曲线和集成挑战。 |
| 后端和前端分离 | 在后端和前端之间保持清晰的分离，促进代码更清洁、更易维护。 | 通常导致后端和浏览器脚本混合，复杂化代码管理和关注点分离。 |
| **连接应用的要求** | 无需连接应用，简化设置并减少管理开销。 | 需要连接应用，这增加了打包和设置的复杂性。 |
| **对 Lightning 和 SLDS 的支持** | 完全支持 Salesforce Lightning 和 Salesforce Lightning 设计系统 (SLDS)，确保与 Salesforce 环境一致的 UI 和 UX。 | 对 Lightning 和 SLDS 的支持有限，可能导致与标准 Salesforce 环境相比 UI 和 UX 不一致。 |
| 启动和扩展 | 允许从简单应用开始，并根据需求逐步扩展功能。 | 初始设置可能复杂，通过添加功能扩展可能需要大量重构。 |

对于开发轻量级应用程序，REST API 集成似乎比 Canvas 应用提供更多优势，尤其是在标准合规性、设置简易性和对 Lightning 和 SLDS 的支持方面。

此外，REST API 对迭代开发的支持使其成为满足不断变化的应用需求的更灵活选择。
