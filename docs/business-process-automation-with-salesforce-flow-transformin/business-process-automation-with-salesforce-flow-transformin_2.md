# Part 1: Understanding Business Requirements and Automation Needs

在这一部分，你将学习并理解业务需求以及自动化这些需求的必要性，以便系统能够处理后端中重复、冗余且可自动化的任务。我们将探索并了解如何利用我们可以借助的工具，以及识别哪些任务可以被自动化。在这一部分结束时，你将能够创建一份功能设计规范，用于识别哪些任务应由终端用户执行，哪些任务可以被自动化。

我们还将解决在此阶段面临的一些关键挑战：

- 无法识别出可以被自动化的正确需求集合。
- 缺乏对业务需求的理解，因而无法为“自动化什么”和“不自动化什么”创建解决方案/设计。
- 过度自动化源于缺乏规划。
- 未能整体评估现有和计划中的自动化的影响，导致自动化逻辑随机执行。

本部分将涵盖以下章节。

- Chapter 1, Process Flows – Understanding Business Requirements
- Chapter 2, Identification of Functional Requirements for Automation
- Chapter 3, Business Process Features to Automate

无论你在项目中的角色是什么，都应始终努力理解业务需求和业务流程。结合流程图阅读需求将有助于清晰地理解需求。你必须尽一切努力理解业务需求和期望，它们如何与愿景和战略保持一致，以及这如何帮助我们实现战略终极目标。要理解业务需求，你需要了解它们是如何运作的。了解当前流程以及未来的期望状态非常重要，这样你才能找到合适的解决方案并满足业务需求。

## Tips for success

- 了解项目利益相关者、SME 和项目团队成员。你可以从组织架构图和社交资料中获取信息。
- 如果你是业务分析师，你很可能会促进并记录这些需求和流程。如果不是，请确保你在这些讨论中参与其中。
- 确保鼓励每个人贡献意见并提问。这将帮助团队中的每个人。这也包括你自己。
- 在当天结束前向所有参与者发送会议纪要。视需要跟进，直到你和利益相关者理解并同意高层级需求。
- 不要陷入设计解决方案。理解业务需求和流程。记住——你目前还不知道哪些需求在范围之内。你的目标应该是对整体情况有良好的理解，而不是提供选项或解决方案。
- 以设计思维的心态开展项目。在可行性和可行性之前先关注人们及其需求，以最大化可用性和用户体验。
- 积极倾听，鼓励并让参与者自由协作，记笔记、管理冲突并保持会议按计划进行。

## Developing an FSD outlining tasks to be automated

在本节中，我们将简要查看一份 FSD 并决定规范的哪些步骤可以被自动化。提前在 FSD 中识别这些内容不仅有助于技术团队构建功能和自动化，还能为业务用户设定期望。与所有关键利益相关者共同讨论这一点将有助于形成对需求及其执行方式的集体理解。有时，我们认为需要自动化的内容可能不会得到业务利益相关者的认可。提前知道这一点是好的，资源可以更好地用于其他需求。

如何创建 FSD 超出了本书的范围。在本节中，我们将快速浏览典型的 CRM 功能设计文档中重要的字段。

接下来列出了典型的 FSD 字段。请注意下表中 *Can be automated?* 和 *Estimated effort* 列。这将帮助我们识别功能步骤是否需要自动化，无论是现在还是将来。无论你使用的是 Agile 还是瀑布项目方法，我们都需要功能规范和任何需求的可视化流程图。如果计划自动化步骤，这一点更为重要。如果你无法将其可视化，就不应该自动化它。在没有共同利益相关者理解的情况下自动化步骤会导致更多的挫败感和困惑。你应该能够以多种方式记录任何需求——功能规范、用例或流程图。不管我们如何描述需求，它们都应向所有项目利益相关者传达相同的含义：

| FSD: Excel document with the following columns |  |
|---|---|
| Business requirements document (BRD) ID (unique ID) | `<Function Name>-<NN>` – for example, `Account-01`. |
| Purpose | The business objective of a requirement. |
| BRD summary | A requirement summary in simple business language. |





| 字段 | 描述 |
| --- | --- |
| FSD ID | 你可以使用任何唯一标识符；最佳实践是将FS、BRD ID和NN连接起来，因为一个BRD可以对应多个FSD行项目——例如：FS- Account-01.01、FS- Account-01, 02……、FS- Account-01.10。 |
| FSD 摘要 | 以更技术性的术语对需求进行总结，以便技术团队准确理解业务需求中的步骤。 |
| FSD 详情 | 包含技术团队能够理解的细粒度细节。流程图将帮助你更准确地捕获这些细节。 |
| 正常流程 | 这是最乐观的流程。这是用户在未遇到任何问题时为达成目标所执行的操作——即顺利路径（happy path）。 |
| 备选流程 | 如果用户遇到问题，则提供步骤让他们走不同的流程。 |
| 异常流程 | 在发生错误时，这将是系统的响应。 |
| 业务规则 | 捕获与需求相关的业务规则。例如，没有KYC ID，账户记录不能从潜在客户（Prospect）转换为客户（Customer）。 |
| 用户操作 | 用户在系统中执行的步骤——例如，登录Salesforce、访问账户选项卡、点击创建新记录、填写所有必填字段，并成功保存记录。 |
| 系统响应 | 系统显示人类可理解的成功、错误或信息消息。 |
| 复杂度（高/中/低） | 高、中或低。 |
| 是否可自动化？ | 是/否。 |
| 预估工作量 | 捕获有自动化和无自动化两种情况下的估算。这将让我们了解是否应该对该功能规格说明中的此步骤进行自动化。 |
| 项目阶段 | 如Release -1、Release -2、Release -3等阶段。 |
| 记录日期 | 需求被添加到矩阵中的日期。 |
| 范围内/范围外 | 你的优先级列表通常由已批准的在范围内（in-scope）项目组成；在某些情况下，由于技术限制或资源约束，你可以将一些需求推迟到未来版本中。在这里，你可以将被推迟的需求标记为范围外（out of scope）。 |
| 备注 | 添加任何有助于澄清需求的评论或细节。 |

这是功能文档中关键部分的全面列表。根据需要，添加其他你认为对实施有价值的相关部分。与BRD一样，你需要与技术和测试负责人及SME（主题专家）一起审查，获得所有人的同意和批准，然后锁定此文档。你应该将此文档分享给业务SME和利益相关者，以便他们审查并提供意见。不过，他们的批准可能是可选的。这个基线版本将作为你路线图上后续版本的起始文档。

# 场景——自动化的依据

在本节中，我们将探讨一个真实场景，从定义高层次需求开始，然后更细致地深入低层次需求。借助流程图，我们将讨论计划自动化步骤背后的依据。

## 高层次需求：

用户将能够请求并获取账户及相关记录（如联系人、机会和案例）的访问权限。不属于特定业务组的用户需要获得合规部门的批准，才能被授予账户及相关记录的访问权限。

## 低层次功能需求：

1. 销售分析师请求访问Salesforce数据。
2. 销售经理/销售运营将能够将用户添加到账户团队。
3. 如果用户不属于同一组，合规部门需要批准用户访问。例如：Zone 1的销售用户可以获准访问Zone 1用户拥有的任何记录，而如果Zone 2用户需要访问Zone 1用户的数据，则需要合规部门的批准。
4. 合规部门审查请求，并可以批准或拒绝该案例。

让我们逐一检查每个步骤，看看哪些可以自动化，以及这样做是否有意义：

1. 销售分析师能否通过创建案例直接从系统请求访问权限？
2. 如果请求符合准则（即用户属于同一销售组），销售经理/运营批准案例后，我们能否自动创建账户团队，还是他们需要手动创建账户团队？自动化是有意义的，但我们有时间和资源吗？我们的实例中有多少用户？如果用户量不大，自动化还有意义吗？
3. 是否需要案例管理？还是我们在系统外获得批准？
4. 如果数据量和频率都很低，我们是否需要构建审批流程？我们有供合规用户使用的系统许可证吗？假设你有良好的用户基础和中到高的数据量，启用案例管理和自动创建账户团队是有意义的。原因如下：我们需要方便获取的案例用于审计，并通过自动创建账户团队来帮助合规用户。
5. 我们是否根据系统内的操作自动发送电子邮件通知，还是在系统外完成？用户是否需要活跃在系统中才能收到通知？自动化电子邮件通知听起来是个理所当然的选择，但如果用户无法访问系统，而你又需要用户的响应（如批准/拒绝），该怎么办？

> **注意**
> 如果同一组用户需要类似的数据访问权限，账户所有者将能够从其用户记录中将该用户添加到账户团队和销售团队。这是一个一次性过程，我们可以将该团队默认应用到所有账户团队和机会团队。如果是不同的用户集，则需要在账户/机会记录级别添加团队成员。

现在我们已经更详细地确定了需求，并且能够评估自动化流程中全部或部分步骤是否具有价值，下一个非常重要的步骤是与所有关键利益相关者和项目团队进行沟通，就整体需求以及计划自动化的潜在任务达成共识和协议。让我们在下一节中了解这一点。

# 获得所有利益相关者的共识和协议

在上一节中，我们有机会识别所有需求步骤——最重要的是那些可能通过流程图实现自动化的步骤。我怎么强调这些流程图的重要性都不为过。如果你的团队无法绘制业务流程并直观地解释它，那意味着你并未完全理解自己的业务流程，这将导致需求收集不完整以及对业务需求的理解不足。如果出现这种情况，请暂停一下，确保需求已被获取、记录并获得所有项目利益相关者的同意。在研讨会期间，利用白板或翻页挂图，在业务利益相关者、SME和项目团队成员的帮助下制定流程图。

以下是与关键利益相关者达成一致的一些注意事项：

- **做一个积极的倾听者**：能够理解工作背后的含义和用户的意图。
- 在上下文中理解用户需求，并保持技术中立。
- 避免利益相关者告诉你该做什么（解决方案），而不是他们需要什么。
- 尽可能采用增量方法，以促进创新和更好的解决方案。
- 记笔记……大量地记。标记你获取信息的来源。之后如果需要澄清，这有助于你轻松识别来源。
- 尽可能使用可视化工具，使所有人达成共同理解。
- **沟通**：向所有利益相关者发送会议纪要（包括可视化内容），并征求反馈。

你可以让优先级会议更有意义、更有效，如下所示：

- 应传达参与规则
- 应妥善规划和传达优先级会议
- 应传达明确的议程和目标
- 应制定冲突解决的基本规则




- 对团队计划使用的工具和技术进行培训并概述
- 确定因素优先级排序的标准及其权重
- 布置一个设施齐全的会议室，配有大型整墙白板、挂图和投影仪，以展示之前创建的流程图、概念流程图等

> **注意**
>
> 项目团队不会定义和创建业务流程图。我们 IT 团队不会告诉业务用户如何经营业务。我们会帮助开发业务流程图，并与关键利益相关方和主题专家一起微调。不过，项目团队应讨论如何改进业务流程的最佳实践和建议。最终，研讨会中的业务用户应同意或否决，他们对业务流程的最终形态拥有最终决定权。业务流程图是业务流程的反映，在每次发布期间会多次迭代改进。我们会在每次发布时对业务流程图拍下快照，以便将其作为该次发布的基线。

# 关于需求优先级排序的实用技巧

让我们看一些可能有助于优先级排序活动的要点。它们非常实用和重要，可以为你节省大量痛苦和时间。在项目实施过程中，你会发现以下一些实用技巧：

- 确保项目中的每个团队成员和所有利益相关方都理解流程的流转。
- 在最初发布版本中不要试图将所有内容自动化。专注于核心功能，这些功能会为系统增加更多功能，即使它们需要用户执行更多步骤。
- 了解用户对你计划自动化的步骤的使用情况和反馈。这些步骤自动化真的有意义吗？业务用户希望自动化，还是满足于现状？
- 避免自动化边界情况。如果该功能很少使用或只有少数用户使用，你真的想自动化这些步骤吗？为了降低这些情况的风险，你可以向销售运营/计划团队发送一封简单的电子邮件通知，以核实这些边界情况。
- 当你有多版本发布项目时，为自动化制定路线图。这将有助于在自动化与增加新特性/功能之间进行权衡协商。
- 通过渐进式优先级排序和保持透明来管理预期。让你所有的利益相关方和项目团队成员都能访问你的**业务需求文档（BRD）**或产品待办列表。

现在我们已经了解了 Flow 的基本构建块，下一节让我们学习 Salesforce 中可触发业务步骤、从而实现业务流程自动化的各种流程。
