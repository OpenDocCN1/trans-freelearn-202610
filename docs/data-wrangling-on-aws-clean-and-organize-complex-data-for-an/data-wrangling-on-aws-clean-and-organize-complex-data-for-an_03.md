# 开始数据整理

在本書的引言部分，我们列出了组织如何使用数据为客户创造价值的用例。除此之外，组织还会收集大量其他数据，以便了解客户的财务状况，这有助于他们与利益相关者分享，包括用于安全、系统健康检查的日志数据，以及用于客户 360 等用例的客户数据。

我们讨论了所有这些用例，以及如何从不同的数据源收集数据来解决它们。然而，从收集数据到解决这些业务用例，一个非常重要的步骤是清理数据。这就是数据整理发挥作用的地方。

在本章中，我们将学习数据整理的基礎并涵盖以下主题：

- 介绍数据整理
- 数据整理涉及的步骤
- 数据整理的最佳实践
- **亚马逊网络服务 (AWS)** 中用于执行数据整理的可用选项

## 介绍数据整理

为了使组织能够以数据驱动的方式为客户创造价值或做出更明智的业务决策，他们需要从不同的数据源收集大量数据，例如点击流、日志数据、交易系统和平文件，并将它们存储在不同的数据存储中，例如数据湖、数据库和数据仓库作为 **原始数据**。一旦数据存储在不同的数据存储中，就需要对其进行清理、转换、组织并从不同的数据源进行连接，以为下游应用程序提供更有意义的信息，例如机器学习模型提供产品推荐或查找交通状况。或者，它可以被业务或数据分析使用，以提取有意义的业务信息：

数据整理带来诸多优势：

- **增强数据质量：** 数据整理有助于提高数据的整体质量。它涉及识别和处理缺失值、异常值、不一致和错误。通过解决这些问题，数据整理可确保用于分析的数据准确可靠，从而产生更稳健、更值得信赖的结果。

- **提高数据一致性：** 原始数据通常来自各种来源或以不同格式存在，导致命名约定、测量单位或数据结构不一致。数据整理允许您标准化并协调数据，确保数据集中的一致性。一致的数据使信息更容易集成和比较，促进有效的分析和解释。

- **提高数据完整性：** 不完整的数据在分析和建模过程中会带来挑战。数据整理方法允许您通过应用诸如插补等技术来处理缺失数据，其中缺失值基于现有信息进行估计或填充。通过适当处理缺失数据，数据整理有助于确保数据集更完整，减少潜在偏差并提高分析的准确性。

- **促进数据集成：** 组织的数据通常分散在多个系统和来源中，使集成成为一项复杂任务。数据整理有助于合并和集成来自各种来源的数据，使分析人员能够使用统一的数据集。这种集成提供了数据的整体视图，使全面分析和洞察成为可能，而这些在处理碎片化数据时可能无法实现。

- **简化数据转换：** 数据整理提供工具和技术将原始数据转换为适合分析的格式。这种转换包括数据规范化、聚合、过滤和重新格式化等任务。通过简化这些流程，数据整理简化了数据准备阶段，为分析人员节省时间和精力，使他们能够更专注于实际分析和结果解释。

- **实现有效的特征工程：** 特征工程涉及创建新的派生变量或转换现有变量以提高机器学习模型的性能。数据整理为特征工程奠定了基础，通过以允许有意义转换的方式准备数据。通过执行诸如缩放、对类别变量进行编码或创建交互项等任务，数据整理有助于导出信息丰富的特征，增强模型的预测能力。

- **支持数据探索和可视化：** 数据整理通常涉及探索性数据分析 (EDA)，分析人员在正式建模之前获得数据见解并了解数据模式。通过清理和准备数据，数据整理能够进行有效的数据探索，帮助分析人员发现关系、识别趋势并使用图表、图形或其他视觉表示来可视化数据。这些探索步骤对于形成假设、做出数据驱动的决策和有效传达见解至关重要。





现在我们已经了解了数据整理（data wrangling）的优势，让我们来了解数据整理过程中涉及的步骤。

## 数据整理涉及的步骤

与原油类似，原始数据必须经过多个数据整理步骤才能变得有意义。在本节中，我们将学习数据整理涉及的六步流程：

- 1. 数据发现
- 2. 数据结构化
- 3. 数据清洗
- 4. 数据丰富
- 5. 数据验证
- 6. 数据发布

在开始之前，重要的是要理解这些活动可能不需要按顺序执行，或者在某些情况下，你可能会跳过其中任何一步。

另外，请记住这些步骤是迭代的，并且因不同角色而异，例如数据分析师、数据科学家和数据工程师。

举例来说，数据工程师的数据发现可能与数据分析师或数据科学家对数据发现的理解不同：

![](img/e28602b44ec813a47df57c96b204412c_25_0.png)

让我们开始详细学习这些步骤。

数据整理过程的第一步是数据发现。这是数据整理中最重要的步骤之一。在数据发现中，我们熟悉我们拥有的原始数据的种类，我们希望用该数据解决什么用例，原始数据之间存在什么关系，数据格式会是什么样的，例如 CSV 或 Parquet，存储、转换和查询此数据的可用工具有哪些，以及我们希望如何组织此数据，例如按文件夹结构、文件大小、分区等，以便于访问。

让我们通过一个例子来理解这一点。

在这个例子中，我们将尝试了解数据发现如何根据角色而变化。假设我们有两位同事，James 和 Jean。James 是数据工程师，而 Jean 是数据分析师，他们都在一家汽车销售公司工作。

Jean 是组织的新人，她需要分析南加州的汽车销售数据。她已联系 James，请他从生产系统中的销售表中提供数据。

以下是 Jane（数据分析师）的数据发现过程：

- 1. Jane 必须确定她需要生成销售报告的数据（例如，销售交易数据、车辆详细信息数据、客户数据等）。
- 2. Jane 必须找到销售数据存储的位置（数据库、文件共享、CRM 等）。
- 3. Jane 必须确定她需要多少数据（过去 12 个月、过去一个月等）。
- 4. Jane 必须确定她将使用什么工具（Amazon QuickSight、Power BI 等）。
- 5. Jane 必须确定她需要数据以何种格式，以便与她拥有的工具兼容。
- 6. Jane 必须确定她希望将此数据存储在哪里——在数据湖（Amazon S3）、她的桌面、文件共享、沙箱环境等。

以下是 James（数据工程师）的数据发现过程：

- 1. 哪个系统请求数据？例如，Amazon RDS、Salesforce CRM、生产 SFTP 位置等。
- 2. 数据将如何提取？例如，使用 Amazon DMS 或 AWS Glue 等服务或编写脚本。
- 3. 时间表会是什么样？每天、每周或每月？
- 4. 文件格式会是什么样？例如，CSV、Parquet、orc 等。
- 5. 数据将如何存储在提供的存储中？

## 数据结构化

为了支持现有和未来的业务用例更好地为客户服务，组织必须从不同的数据源以不同的形式收集前所未有的大量数据。在现代数据架构中，大多数情况下数据存储在数据湖中，因为数据湖允许你存储各种各样的数据文件，无论是结构化数据、非结构化数据、图像、音频、视频或其他，其原始形式形状和大小各不相同。当数据处于原始形式时，它缺乏明确的结构，这是将其存储在数据库或数据仓库中或用于构建分析和机器学习模型所必需的。在这一点上，它尚未针对成本和性能进行优化。

此外，当你处理流数据（如点击流和日志分析）时，并非所有数据字段（列）都用于分析。

在数据整理的这个阶段，我们通过执行分区和转换文件类型（例如，将 CSV 转换为 Parquet）来尝试优化原始数据集以获得成本和性能优势。

再次，让我们考虑我们的朋友 James 和 Jean 来理解这一点。

对于 Jean，数据分析师而言，数据结构化意味着她希望直接查询或将数据存储在 BI 工具的内存存储中，在 Amazon QuickSight 的情况下称为 SPICE 层，可提供更快的数据访问。

对于 James，数据工程师而言，当他从生产系统提取数据并希望将其存储在 Amazon S3 等数据湖中时，他必须考虑文件格式会是什么样。他可以按地理区域（如县、州或地区）或按日期进行分区——例如，year=YYYY、month=MM 和 day=DD。

## 数据清洗

数据整理过程的下一步是数据清洗。前两个步骤让我们了解数据看起来如何以及如何存储。在数据清洗步骤中，我们开始处理原始数据，使其变得有意义，以便我们可以定义未来的用例。

在数据清洗步骤中，我们通过以下方式使数据变得有意义：

- 删除不需要的列、重复值并填充空值列以提高数据的就绪度
- 执行数据验证，例如识别必填列（如名字、姓氏、SSN、电话号码等）的缺失值
- 验证或修复数据类型以更好地优化存储和性能
- 识别并修复异常值
- 删除垃圾数据或不需要的值，例如特殊字符

James 和 Jane 都可以执行类似的数据清洗任务；然而，其规模可能不同。对于 James，这些任务必须针对整个数据集执行。对于 Jane，她可能只需要对来自南加州的数据执行，并且粒度也可能不同。对于 James，也许仅限于南加州、北加州等地区，而对于 Jean，可能是城市级别甚至邮政编码级别。

## 数据丰富

直到数据清洗步骤，我们主要是在单个数据源上工作，并使其对未来使用变得有意义。然而，在现实世界中，大多数情况下，数据是分散的并存储在多个不同的数据存储中，为了支持构建个性化或推荐解决方案或构建客户 360 或日志取证等用例，我们需要将来自不同数据存储的数据连接起来。

例如，要构建客户 360 解决方案，你需要来自 **客户关系管理（CRM）** 系统、点击流日志、关系数据库等的数据。

因此，在数据丰富步骤中，我们构建流程，将原始数据与从不同来源获得的相关数据进行增强。

## 数据验证

计算机科学中有一个非常有趣的术语，称为 **垃圾进，垃圾出（GIGO）**。GIGO 的概念是，有缺陷或有问题的（垃圾）输入数据会产生有缺陷的输出。

换句话说，输出的质量取决于输入的质量。因此，如果我们提供不良数据作为输入，我们将得到不准确的结果。

在数据验证步骤中，我们通过执行各种数据质量检查来解决这个问题：

- 业务验证数据准确性
- 验证数据安全
- 验证整个数据集中的结果一致性
- 通过验证以下数据质量检查来验证数据质量：
  - 记录数
  - 重复值
  - 缺失值
  - 异常值
  - 不同的值
  - 唯一值
  - 相关性




数据清洗和数据验证之间有很多重叠之处，是的，这两个过程之间有很多相似之处。然而，数据验证是在结果数据集上进行的，而数据清洗主要是在原始数据集上进行的。

## 数据发布

完成所有数据整理步骤后，数据就可以用于分析，从而解决业务问题。

因此，最后一步是以所需的访问权限和许可将数据发布给最终用户。

在这一步中，我们主要关注数据如何暴露给最终用户，以及最终数据存储在何处——即关系数据库、数据仓库、数据湖中的精选区或用户区，或通过**安全文件传输协议（SFTP）**。

数据存储的选择取决于最终用户希望通过哪种工具访问数据。例如，如果最终用户希望通过 Amazon QuickSight、Power BI、Informatica 等 BI 工具访问数据，那么关系型数据存储将是理想的选择。如果是数据科学家访问，理想情况下应存储在对象存储中。

我们将在本书后面了解可用于存储原始数据和整理后数据的不同类型的数据存储。

在本节中，我们通过朋友 James 和 Jean 了解了数据整理过程的各个步骤，以及这些步骤如何可能或可能不会因角色而异。现在，让我们了解数据整理的最佳实践。

# 数据整理的最佳实践

执行数据整理有很多方法和工具，具体取决于数据整理的方式和人员。例如，如果你正在处理实时用例，如提供产品推荐或欺诈检测，那么与构建**商业智能（BI）**仪表板以显示销售数据相比，你选择的数据整理工具和流程会有很大不同。

无论你要解决哪种类型的用例，每种情况都可以应用一些标准的最佳实践，这些实践将帮助数据整理者更轻松地完成工作。

## 识别业务用例

建议在编写任何代码之前，先决定要使用哪种服务或工具进行数据整理。识别业务用例非常重要，因为这将为数据整理过程奠定基础，并使识别你打算使用的服务变得更加容易。例如，如果你有一个业务用例，比如为小型组织分析 HR 数据，只需要对一个包含 10,000 条记录的小型数据集进行几列拼接、删除几列、删除重复项、删除 NULL 值等操作，并且只有少数用户会访问整理后的数据，那么你不需要投入大量资金去购买市场上花哨的数据整理工具——只需使用 Excel 工作表即可完成工作。

然而，当你有一个业务用例，例如处理从不同合作伙伴处接收的索赔数据，需要处理 JSON 等半结构化文件或 XML 等非结构化数据集，仅提取少量文件数据（如索赔 ID 和客户信息），并且需要执行复杂的数据整理过程（如连接、使用正则表达式查找模式等），那么你应该考虑编写脚本或订阅任何企业级工具来完成工作。

## 识别数据源并获取正确的数据

在识别业务用例之后，重要的是确定需要哪些数据源来解决它。识别数据源将帮助你选择需要哪些服务来获取数据、获取频率以及最终存储方式。例如，如果你要构建信用卡欺诈检测解决方案，就需要实时获取信用卡交易数据；甚至数据清洗和处理也应在实时进行。机器学习推理也需要在实时数据上运行。

类似地，如果你正在构建销售仪表板，可能需要从 Salesforce 等 CRM 系统或 Oracle、Microsoft SQL Server 等事务性数据存储中获取数据。

在识别了正确的数据源之后，重要的是从这些数据源中引入正确的数据，因为这将帮助你解决业务用例并使数据整理过程变得简单。

## 识别你的受众

在执行数据整理时，一个重要方面是识别你的受众。了解受众将帮助你确定他们希望消费哪种类型的数据。例如，与数据科学团队或业务高管相比，营销团队可能有不同的数据整理需求。

这也会让你了解你打算在哪里展示数据——例如，数据科学家团队可能需要 Amazon S3 等对象存储中的数据，业务分析师可能需要 CSV 等平面文件中的数据，BI 开发人员可能需要事务性数据存储中的数据，而业务用户可能需要应用程序中的数据。

至此，我们已经介绍了数据整理的最佳实践。接下来，我们将探讨 AWS 中可用于执行数据整理的不同选项。

# AWS 上可用于数据整理的选项

根据客户需求、数据源和团队专业技能，AWS 提供了多种数据整理选项。在本节中，我们将介绍 AWS 可用的最常见选项。

## AWS Glue DataBrew

AWS Glue DataBrew 于 2020 年发布，是一种可视化数据准备工具，可让你轻松清洗和规范化数据，以便为分析和机器学习做好准备。该服务提供的可视化 UI 使没有编码或脚本经验的数据分析师也能完成数据整理的各个方面。它附带了一组丰富的常见预构建数据转换操作，可以简化这些数据整理活动。与任何软件即服务（SaaS）(https://en.wikipedia.org/wiki/Software_as_a_service) 类似，客户无需预置任何服务器即可开始使用 Web UI，并且只需为使用的资源付费。

## SageMaker Data Wrangler

与 AWS Glue DataBrew 类似，AWS 还提供了 SageMaker Data Wrangler，这是一种基于 Web UI 的数据整理服务，更面向数据科学家。如果主要用例是构建机器学习管道，则应优先选择 SageMaker Data Wrangler。它直接与 SageMaker Studio 集成，使用 SageMaker Data Wrangler 准备的数据可以输入数据管道，以构建、训练和部署机器学习模型。它带有预配置的数据转换，可使用均值或中位数填补缺失数据、独热编码，以及为机器学习准备数据所需的时间序列专用转换器。

## AWS SDK for pandas

对于拥有具备编码和脚本经验的数据集成团队的客户来说，AWS SDK for pandas (https://github.com/aws/aws-sdk-pandas) 是一个很好的选择。它构建在其他开源项目之上，提供了抽象函数来执行典型的数据整理任务，例如从各种数据库、数据仓库和 Amazon S3 等对象数据存储加载/卸载数据。AWS SDK for pandas 简化了与常见 AWS 服务的集成，如 Athena、Glue、Redshift、Timestream、OpenSearch、Neptune、DynamoDB 和 S3。它还支持 MySQL 和 SQL Server 等常见数据库。
