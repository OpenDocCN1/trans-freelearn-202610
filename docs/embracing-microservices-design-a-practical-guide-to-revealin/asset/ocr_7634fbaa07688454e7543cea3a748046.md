As a rule of thumb, a new version of the event should be convertible from the old version; otherwise, it's a new event. It's a good practice to specify the event version as part of the event structure. This is because it gives you the flexibility to publish multiple versions of an event to allow different consumers to process it. Another approach is to go with no event versioning and keep the events backward compatible by ensuring that you don't delete or change fields in the event structure. New fields are treated as nullable values so that the old version of the events can be replayed later. The following diagram depicts how event versioning works in an event-driven architecture:

The idea is to allow different parts of the system to evolve independently, where events aid in enabling communication, where each consumer processes relevant events.
