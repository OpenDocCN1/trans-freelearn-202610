## 总结

在本章中，我们简要介绍了 Kubernetes 的起源、它对你有用的原因、它的主要功能以及它的架构。

一旦你决定将代码迁移到更现代的云原生方法，或者开始使用容器，你很可能将不得不与 Kubernetes 这类容器管理系统打交道。本章让你对它们的工作原理以及可以在何处使用它们有了很好的了解。

Kubernetes 是 CNCF 下载量最大的产品。到底什么是云原生，将在下一章中讨论。

但这还不是全部。如今，我们许多人将云用作备份。在手机上存储照片时，不仅存储在设备本身，还会在某种云存储中保留一份副本以妥善保管，这非常普遍。苹果的 iCloud 就是一个很好的例子，但还有其他的云存储提供商，如 Google Cloud 和 Dropbox。

如今，有许多云提供商，其中以 **亚马逊网络服务（AWS）**、Microsoft Azure 和 Google Cloud 为主。也许在西方国家不太为人所知，阿里云是全球第四大云提供商，其在云市场的份额距离 Google Cloud 并不遥远。因此，我们可以有把握地说，如今云无处不在。

*云原生*意味着我们正在使应用程序适应云所提供的新可能性。不过，我们需要记住，云是由一组不同的架构约束所驱动的。在接下来的章节中，我们将以简单的方式解释这些约束。

## 云原生原则

我相信你在拿起这本书之前，一定已经多次听到过*云原生*这个词。也许正是听到这些词，才让你选择阅读这本书。现在让我们仔细审视云原生的原则。

云原生由四个不同的特性驱动，如下所示：

- 微服务
- 容器和编排
- DevOps
- **持续集成和持续交付（CI/CD）**

我们将在本章中更详细地讨论这些特性，但你必须意识到，我们在这里只能触及皮毛。每一个特性本身都值得写一本书，事实上，你可以在 Packt Publishing 找到关于这些主题的书籍。

## 微服务

虽然在云端运行微服务并非强制要求，但大多数云原生应用实际上都是微服务。我们在本书中已经多次遇到*微服务*这个术语，但让我们先看看它的定义。

微服务是一种架构风格，它将应用程序构建为一系列服务，这些服务具有以下特点：

- 可独立部署
- 松耦合
- 围绕业务能力组织
- 由专门的团队拥有

独立可部署性至关重要。你应该能够将新的或更新的服务部署到生产环境，而无需担心会破坏其他服务，或需要记住重新部署这些其他服务。本章的*介绍 12-factor 应用*一节将对此进行更详细的描述。

软件开发中的松耦合总是一个好主意，在微服务中更是如此。它允许服务随着时间的推移而变化，而这些变化不会影响其他服务。为了实现松耦合，需要考虑很多事情，但最重要的是：为你的每个服务使用独立的数据库模式，通过 API 进行通信（记住亚马逊的 Jeff Bezos 对此的引用：“*所有服务接口，无一例外，必须从一开始就设计为可外部化*”），以及在服务之间提供异步通信。

这些服务应该围绕业务领域组织，这一点不言而喻：它们存在的唯一理由是在某种程度上支持使用它们的公司的业务流程。

最后，它们应该由一个小团队拥有。原因是这些服务仅服务于完整业务流程的一小部分。因此，所需的领域逻辑量也是有限的。将此与传统应用程序开发进行比较，在传统开发中，每个开发人员都可能需要处理整个应用程序。这将需要对完整业务领域的了解。

使用微服务，新成员加入你的团队会变得更加容易和快速。此外，对你的微服务进行更改也可以更快地实施，因为每个开发人员都知道所有细节以及这些更改将产生的影响。

## 容器和编排

在关于 Docker（*第 6 章*）和 Kubernetes（*第 7 章*）的章节中，我们已经解释了使用这些技术的优势。事实上，你可能会说，容器化正是使云原生运动成为可能的原因。

在不可修改的容器中创建制品（即应用程序二进制文件），并通过流水线的不同阶段（开发、预发布、生产）进行推送，这具有巨大的优势。

在由几十个、几百个甚至几千个容器组成的系统中，某种容器编排工具是必需的。这也意味着你的部分运维工作将被自动化，从而减轻运维部门的琐碎工作，使他们能够专注于手头更重要、更有趣的任务。

## DevOps

**DevOps** 是将**开发**和**运维**结合成一个无缝团队。在传统的应用程序开发中，开发部门会创建或更新应用程序。该应用程序将进行单元测试并通过验收测试。一旦验收测试完成，应用程序将被移交给运维部门。

运维部门将执行所需操作，将应用程序带入生产环境，例如运行数据库脚本或创建新的应用程序绑定。

一旦在生产环境中运行，如果发现任何错误，分析和可能修复这些错误的过程也将是运维部门的责任。

简而言之，两个团队在高度分离的孤岛中工作。

你可能会看到这非常低效。开发人员凭借他们对应用程序内部机制的所有了解，实际上可能更适合帮助分析错误。

将两个部门合并为一个似乎是合乎逻辑的举措，团队中的每个人都负责应用程序的完整生命周期，从开发到在生产环境中运行。这种共同的责任将不可避免地创造更强的“拥有服务”的意识，并在应用更改时导致更仔细的考虑。

DevOps 的关键点之一是，任何可以自动化的事情都应该自动化，或者正如这句格言所说：“自动化一切！”

## CI/CD

CI/CD 是一个流程，其中对代码库的更改会自动集成到该代码库中，并部署到生产环境。

CI 的工作原理如下：

1. 开发人员在一个所谓的特性分支上工作，以对系统进行更改。特性分支本质上是原始软件（位于主分支上）的一份副本。

2. 当他们完成该任务的工作后，他们将在本地运行单元测试。一旦这些测试全部为“绿色”（green），意味着全部成功通过，他们就会将代码推送到 **版本控制系统（VCS）**（如 Git）。

3. 自动化服务器现在将开始构建已更改的软件。构建过程完成后，将针对构建运行自动化测试。这些测试将不仅包括单元测试，还包括集成测试。

4. 如果所有这些测试也都成功，开发人员在特性分支上所做的代码更改将被集成到主分支中。
