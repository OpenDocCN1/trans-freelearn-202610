该流程有几个优点。其中之一是，位于功能分支上的新开发软件在早期阶段就会被测试，以确保其与主分支中的原始软件兼容。任何差异都会被及早发现，这意味着修复它们所需的时间不应太长，并且风险也不会太大。

此外，新更改将在早期阶段提供给其他开发人员，这意味着他们在将其合并到自己的更改中时遇到的问题会更少。CD 在 CI 的基础上扩展。这是一个流程，在 CI 中成功构建后，软件将被自动部署到暂存环境甚至生产环境。

现代 CI/CD 流水线已将此流程完全自动化，有些甚至自动化到无需人工干预即可将软件更改引入生产环境。

这是通过高度自动化所有测试工作来实现的。这些测试必须具有如此详尽的性质，以至于应用程序可以以很高的确定性部署到生产环境，并且可以按照规范运行并且不太可能包含错误。

从以上内容可以看出，整个 CI/CD 流程是高度自动化的。市面上存在众多 CI 和 CI/CD 服务器。

请注意，CI/CD 也可用于云原生开发之外。事实上，如今在常规软件开发中使用 CI 服务器已非常普遍。最主要缺少的是 CD 部分，因为它需要高度自动化的测试。除了这一点外，通常公司尚未准备好接受软件自动发布到生产环境。

这可能是组织流程的结果（在政府组织中，通常仍然要求某个**质量保证 (QA)** 部门给出最终的“通过”）。在其他情况下，公司可能对即时将软件投入生产存在心理上的“阻碍”：他们仍希望在发布到生产环境之前由人工眼睛和大脑检查更改。

## 介绍 12-Factor 应用

*The 12-factor app* 是对云原生应用程序应如何最好构建的描述。最初由 Heroku 的团队提出，此后已成为云原生应用程序或**软件即服务 (SaaS)** 的事实标准。

这些规则最重要的方面之一是它们可以应用于任何编程语言。在以下各节中，我们将逐一介绍这 12 个要素，并强调它们的重要性：

- Code base
- Dependencies

### Dependencies

部署在应用服务器上的应用程序依赖于服务器提供的一组共享库。每个应用程序都可以使用这些库，而无需自行提供。

虽然这似乎有利，但它也违反了我们在此提出的第二个要素：应用程序应明确指定并使用库的特定版本。因此，云原生应用程序绝不应依赖共享库，而应始终随其所需的所有依赖项一起打包。

在 Java 中，我们可以使用 Maven 和 Gradle 等工具中的项目配置文件来明确声明我们的依赖项及其版本。

### Config

*Store config in the environment.*

*要素 3 规定应用程序应仅使用环境变量进行配置。此配置数据可以是数据库的 URL 和凭据，或在访问另一个微服务时使用的密钥。*

这些值在开发、暂存和生产环境中很可能有所不同。通过将这些值设置为环境变量，应用程序可以在启动时检索并使用它们。

应用程序本身在从暂存环境移动到生产环境时保持不变，只有环境变量的值会不同，反映该环境配置值。

Docker、Podman 和 Kubernetes 等容器和编排工具为使用环境变量提供了非常好的支持。

需要注意的是，环境变量并非用于配置应用程序逻辑，例如无效密码允许的重试次数。此类应用程序特定配置应存储在某种属性文件或数据库表中。

### Backing services

*Treat backing services as attached resources.*

应将支持服务视为有界资源。首先，什么是支持服务？**支持服务**是应用程序正常运行所依赖的任何外部服务。想想数据库、消息系统和外部服务，但也包括磁盘存储。这一点乍一看可能很奇怪，但请记住我们是在容器中运行。容器本质上是短暂的。这意味着它们寿命短暂，一旦容器死亡，存储在该容器内的任何内容都将永远消失。

在此上下文中有界资源意味着您的应用程序可以声明对特定支持服务的需求，但实际绑定到该服务的则是云运行时。

*要素 3 规定配置应外部化，这包括您将绑定的实际支持服务。这具有一个主要优势，即在运行时，您实际上可以更改此绑定。因此，如果某个支持服务出现故障，应用程序可以通过将其绑定到另一个资源而继续运行——例如，用新的数据库服务器替换出现故障的数据库服务器。*

### Build, release, run

*Strictly separate build and run stages.*

我们已在本章前面讨论过自动化构建流程的必要性。最好使用构建服务器创建应用程序的不可变实例并将其打包到容器中。

发布此工件意味着为其分配某种唯一 ID。这可以是某种版本号。例如，容器允许您为其添加标签。其中一个标签可以是该版本号。这将使其与其他容器唯一区分开来。

工件随后将在开发、暂存、生产等不同阶段之间移动，而不会被修改。

在每个环境中应用的不同环境变量将相应地更改其配置。工件本身在任何时候都不会被更改。这将保证如果它在一个阶段工作正常，那么在另一个阶段也很可能正常工作。

### Processes

*Execute the app as one or more stateless processes.*

进程应作为无状态进程运行并应用**无共享 (SN)** 原则。这是一个分布式架构原则，规定节点之间不共享任何信息。这可确保您不会在系统中创建任何**单点故障 (SPOF)**。

实际上，这意味着如果您的应用程序缓存数据，它应使用缓存服务器作为支持服务来执行此操作，而不是自行缓存数据。缓存需要时间填充，最好在相似节点之间共享。

传统上，Web 服务器有一个称为**粘性会话**的概念。这会将来自用户的请求绑定到特定服务器，因为该服务器出于速度原因在内存中保留有关客户端会话的某些信息。

粘性会话违反了 SN 原则，因此应避免。同样，通过存储在本地磁盘上的数据在进程之间共享信息在所有非常简单的情况下也应避免。将文件或图像上传进行处理就是此类情况的一个例子。

从此开始，将应用程序带入运行状态以及在运行时监控应用程序则由他们负责。

该要素表明 DevOps 对于运行您的云原生应用程序至关重要。开发和运维应共同负责部署和应用程序的运行时检查。这不仅会带来更快的交付，还会增加团队成员对应用程序的责任感。

### Resources

开发人员机器可能与实际生产环境看起来非常不同，不仅因为操作系统，还因为外部资源的不同。在本地，开发人员可能会使用不同的数据库引擎，具有不同的消息服务器等等。他们可能会使用不同的**数据库管理系统 (DBMS)**，也许在本地机器上运行免费版本，而在生产环境中运行付费版本。

如果开发中使用资源与实际生产环境中的资源不同，则不兼容性可能会开始出现。因此，很明显，开发和生产环境应保持相似。

### Logs

*Treat logs as event streams.*

日志可能来自多个来源，而不仅仅是您的应用程序。它们通常是所有正在运行的进程和支持服务的输出按时间顺序排列的流。

您的应用程序永远不必担心路由日志或存储位置。相反，您的应用程序只需将其日志输出流式传输到 stdout。

在开发期间，开发人员可以轻松地在其控制台中查看日志流。

在暂存和生产期间，每个进程流将被执行环境捕获并路由到一个或多个最终目的地。这些最终目的地通常是日志收集器，它们会以某种形式或结构存储信息，使数据易于在 Splunk 或 Kibana 等专用日志工具中检索和查看。

### Admin processes

*Run admin/management tasks as one-off processes.*

管理任务可以是多种事物，例如——例如——数据库维护任务、需要定期运行的某些清理过程，或通常的 cron 作业。
