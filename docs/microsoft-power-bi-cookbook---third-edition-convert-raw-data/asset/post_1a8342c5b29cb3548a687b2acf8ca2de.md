## How it works

When first connecting to a Power BI semantic model (*steps 2 and 3*), the semantic model is connected in Live mode. Live mode connections to Power BI semantic models allow reports to be created using an existing semantic model and were originally the only connection method available for Power BI semantic models.

Microsoft subsequently released **DirectQuery for Power BI datasets and Analysis Services models**. *Steps 4, 5, and 6* convert the connection from a Live connection to a DirectQuery connection using this feature. *Steps 7 through 10* add an import mode table to the data model, making the semantic model a composite or “mixed-mode” model.

The differences between the various tables within the semantic model are evident in the Model view, as shown in Figure 10.2:

![](img/5e366dc9e90fe4b1ca9dd97c82976bbd_438_0.png)

Figure 10.2: Different storage modes in the composite model

In the Model view, DirectQuery tables are displayed with a blue bar while import tables have no such bar. In Figure 10.2, the Sales Plan table is selected, and in the Properties pane under the Advanced settings, Storage mode is set to Import. Selecting the DirectQuery tables would display a Storage mode value of DirectQuery.

There are actually three storage modes within Power BI: Import, DirectQuery, and Dual. Import tables are cached into memory and queries against the semantic model for such tables are fulfilled via this cache. DirectQuery tables are not cached and queries against the semantic model using these tables can only be fulfilled by querying the source. Dual mode tables can operate as cached or not cached, depending on the query.

It is important to remember that after setting a table to Import mode, it is subsequently impossible to then convert that table to DirectQuery or Dual storage modes.

Automatic aggregations use machine learning technology to automatically optimize DirectQuery models such that queries against the semantic model can be fulfilled from cached aggregations instead of accessing the source data systems, thus improving performance.

## Improving DAX Measure Performance

Just as specific columns and relationships can be optimized for performance per the prior recipe, frequently used DAX measures can also be targeted for performance improvements. Existing DAX measures may contain inefficient data access methods that generate additional, unnecessary queries or that largely execute in a single CPU thread. Revising measures to better leverage the multi-threaded storage engine and to avoid or reduce unnecessary queries and iterations can deliver significant performance improvements without invasive, structural modifications to the model.

In this recipe, DAX queries executed by Power BI visuals are captured and analyzed using the Performance analyzer feature of Power BI Desktop. These queries are then further analyzed within DAX Studio.

### Getting ready

To prepare for this recipe, follow these steps:

+   1. Download and install DAX Studio: https://daxstudio.org/downloads/.
+   2. Download and open the file Improving DAX Measure Performance Start.pbix from this book's GitHub repository (see the Technical Requirements section).
+   3. Create the following four measures in the Calculations table:

```
Internet Sales = SUM('Internet Sales'[SalesAmount])

Internet Sales (TOTALYTD) = TOTALYTD([Internet Sales], 'Dates'[Date])

Internet Sales (CALCULATE YTD) =
    CALCULATE(
        [Internet Sales],
        'Dates'[CalendarYear] = MAX('Dates'[CalendarYear]) &&
        'Dates'[Date] <= MAX('Dates'[Date])
    )

Internet Sales (NC YTD) =
    VAR __Date = MAX('Dates'[Date])
    VAR __Year = YEAR(__Date)
    VAR __Table =
        SUMMARIZE(
            ALL('Internet Sales'),
            'Internet Sales'[OrderDate],
            "__Year", YEAR([OrderDate]),
            "__Sales", [Internet Sales])
    VAR __Result = SUMX(FILTER(__Table, [__Year] = __Year && [OrderDate] <= __Date), [__Sales])
    RETURN
        __Result
```

3. Choose the TI results in the Performance analyzer pane and select Copy query:

```
// DAX Query
DEFINE
    VAR __DS0Core =
        SUMMARIZECOLUMNS(
            ROLLUPADDSUBTOTAL('Dates'[Date], "IsGrandTotalRowTotal"),
            "Internet_Sales__TOTALYTD_", 'Calculations'[Internet Sales (TOTALYTD)]
        )
    VAR __DS0PrimaryWindowed =
        TOPN(502, __DS0Core, [IsGrandTotalRowTotal], 0, 'Dates'[Date], 1)
EVALUATE
    __DS0PrimaryWindowed
ORDER BY
    [IsGrandTotalRowTotal] DESC, 'Dates'[Date]
```

4. In DAX Studio, enable the Server Timings, Query Plan, and Clear on Run options in the top toolbar.

5. With the DAX Studio trace running, click on Run or press the F5 key and note the performance in the Server Timings window.

![](img/5e366dc9e90fe4b1ca9dd97c82976bbd_443_0.png)

Figure 10.6: DAX Studio server timings for the time intelligence measure

While DAX traditionalists have lauded DAX’s CALCULATE function as well as time intelligence functions for years, more modern approaches such as using a No CALCULATE approach (so dubbed by Brian Julius) can significantly improve DAX query performance. With its focus on the use of VAR statements, simple FILTER functions, the SUMMARIZE function, and X aggregators (SUMX, AVERAGEX, etc.), the No CALCULATE approach also tends to be easier to debug and learn for newer users of DAX given the nuances and complexities of the CALCULATE function and the black-box nature of DAX’s time intelligence functions.

## There’s more…

Another example of where a DAX measure can be optimized is in this example where a measure must be filtered by complex conditions, such as a range of dates. Perform the same analysis as in this recipe but with the following three measures:

```
Last 7 Days 1 =
    VAR __Date = MAX('Dates'[Date])
    VAR __MinDate = __Date - 6
    VAR __Table = FILTER(ALL('Internet Sales'), [OrderDate] >= __MinDate && [OrderDate] <= __Date)
    VAR __Result = SUMX(__Table, [Internet Sales])
RETURN
    __Result

Last 7 Days 2 =
    VAR __Date = MAX('Dates'[Date])
    VAR __MinDate = __Date - 6
    VAR __Table1 = FILTER(ALL('Internet Sales'), [OrderDate] <= __Date)
    VAR __Table2 = FILTER(__Table1, [OrderDate] >= __MinDate )
    VAR __Result = SUMX(__Table2, [Internet Sales])
RETURN
    __Result

Last 7 Days 3 =
    VAR __Date = MAX('Dates'[Date])
    VAR __MinDate = __Date - 6
    VAR __Table1 = SUMMARIZE(ALL('Internet Sales'), [OrderDate], "Sales", [Internet Sales])
    VAR __Table2 = FILTER(__Table1, [OrderDate] <= __Date)
    VAR __Table3 = FILTER(__Table2, [OrderDate] >= __MinDate )
    VAR __Result = SUMX(__Table3, [Sales])
RETURN
    __Result
```
