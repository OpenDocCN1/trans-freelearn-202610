
Growth or variance measures (step 4) that calculate the difference between the current time period value of a measure and a prior time period such as Year-over-Year (YOY) growth can be created with new measures that subtract the previous time period measure from the current period measure. Additional growth or variance measures expressed in percentages can use the DIVIDE function to compute this difference as a percentage of the previous time period value.

Prior period date columns allow the prior time period measures to apply simple filter expressions relative to the active date filter context down to the individual date granularity. In the absence of these columns and for period- or month-level date tables, measure filter conditions can be written as follows:

```
Prior Year (PY) = 'Dates'[Year Month Number] = MAX('Dates'[Year Month Number])
- 12

Prior Month (PM) = 'Dates'[Year Month Number] = MAX('Dates'[Year Month Number])
- 1
```

For the dynamic prior period measure, Internet Sales (Prior Period) in step 5, the DAX variable (Periods) computes the number of periods in the current filter context, such as 12 if a year is the subtotal, 3 if it is a quarter, or 1 for an individual period. Test conditions with HASONEVALUE check whether a single date or week is selected, and return the corresponding previous day or week, respectively. The remaining date granularities (Year, Quarter, Period) are accounted for by the Periods variable; this value is subtracted from both the MIN and the MAX of the period number of the given context. This example underscores the importance of using sequential date intelligence columns for accessing specific time frames across granularities to apply custom filter conditions.

## There’s more…

DAX includes a full set of time intelligence functions, such as DATESYTD and SAMEPERIODLASTYEAR, which, given a standard (Gregorian) calendar, can compute the same values as the expressions in this recipe. Although these functions generally improve readability relative to the examples in this recipe, the use (and knowledge) of core DAX functions, such as FILTER, MAX, and MIN, is necessary when working with non-standard calendars—such as fiscal calendars and more complex scenarios. Considering that the vast majority of DAX time intelligence functions are simply syntax sugar for the FILTER function and the simplifying assumptions regarding calendar dates, it is unwise to rely on DAX time intelligence functions to be of any meaningful use in many real-world scenarios.

It is often surprising for many individuals new to business intelligence how differently organizations measure and conceptualize time; this can be particularly true regarding weeks. Here again, the DAX time intelligence functions are useless, as there are no included week functions. When dealing with weeks, different organizations start weeks on different days within a week. Thus, when assigning week numbers at either a yearly or monthly grain, it is important to bear this in mind.

Furthermore, organizations will also treat partial weeks differently as well. For example, in the final Dates table, there is a single entry with a Year Week Number of 54. This is because the year 2010 ends with a partial 53rd week. A single day of this week, Saturday, January 1, 2011, falls outside of 2010. Organizations will treat these partial weeks differently, either including that single day as part of the week starting in 2010, as its own week, or as part of the first full week of 2011.

Finally, there are alternative approaches to traditional DAX programming that eschew the use of the CALCULATE function. This approach is called the No CALCULATE approach and, perhaps unintuitively, can produce the same results as using CALCULATE but in many cases actually performs better. For the two measures used in the matrix visual, the No CALCULATE versions are the following:

```
Internet Sales (YTD) NC =
    VAR __Year = MAX('Dates'[Year])
    VAR __Date = MAX('Dates'[Date])
    VAR __Table =
        SUMMARIZE(
            ALL('FactInternetSales'),
            'FactInternetSales'[OrderDate],
            "__Year", YEAR([OrderDate]),
            "__Sales", [Internet Sales]
        )
    VAR __Result = SUMX(FILTER(__Table, [__Year] = __Year && [OrderDate] <= __Date), [__Sales])
    RETURN
        __Result

Internet Sales (PYTD) NC =
    VAR __Year = MAX('Dates'[Year]) - 1
    VAR __Date = MAX('Dates'[Date])
    VAR __Table =
        SUMMARIZE(
            ALL('FactInternetSales'),
            'FactInternetSales'[OrderDate],
            "__Year", YEAR([OrderDate]),
            "__Sales", [Internet Sales]
        )
    VAR __Result = SUMX(FILTER(__Table, [__Year] = __Year && [OrderDate] <= __Date), [__Sales])
    RETURN
        __Result
```

While it is more verbose, many find this approach easier to conceptualize, understand, and debug given its top-down coding style and the ability to return intermediate variables for troubleshooting purposes. This is especially powerful when using the TOCSV function to return intermediate tables.

Create a new matrix using the Year column and these two No CALCULATE measures. The results are the same, but opening the Performance analyzer pane demonstrates that the DAX queries performed for the No CALCULATE versions perform faster with respect to the DAX queries performed.
