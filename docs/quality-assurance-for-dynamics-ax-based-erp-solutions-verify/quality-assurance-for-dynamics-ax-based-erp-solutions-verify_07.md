## 8 缺陷管理系统

任何定制而非从零开始开发的软件系统都需要全面的测试，这超出了需求验证的范围，因为许多错误是由于定制而出现的。这需要对“缺陷”进行特殊定义，因为缺陷可能超出需求范围。以下情况可被视为缺陷：

- 系统执行了需求和设计文档未提及的功能。
- 系统未执行需求和设计文档中提及的功能。
- 系统执行了某个功能，而需求文档中对此功能没有任何信息。根据所有相关利益相关者的协议，这可能被视为缺陷或增强。
- 系统未执行某个功能，而需求文档中对此功能没有任何信息。根据所有相关利益相关者的协议，这可能被视为缺陷或增强。

核心 Dynamics AX 产品或本地化中发现的所有问题应逐案处理。除了上述方面之外，业务应用程序需要获得可信性。为了实现这一特性，安全问题必须系统化处理。所有安全问题应按照本章规定的方法进行分类和处理。

为处理安全缺陷，缺陷跟踪工具应具备接受和处理此类问题的额外信息的功能。

### 缺陷分类

从缺陷管理的角度来看，缺陷可分为两类，即安全相关缺陷和非安全相关缺陷。安全相关缺陷需要为每个安全缺陷附加一些额外信息。在 Dynamics AX 中，缺陷分类（即无论发现错误的类型如何）基于以下因素：

- Bug priority
- Category
- Issue status
- Requirement Ref.
- STRIDE
- Severity
- Discoverability
- Mitigation
- Vulnerability
- Resources

缺陷管理工具应具备接受所有安全相关缺陷信息的功能。工具应确保当缺陷被记录为安全相关问题时，用户输入所有必需信息。工具还应能够根据上述所有维度生成报告。

### Bug Priority

错误优先级分类表示整体重要性并决定错误修复的顺序。为了确保优先修复的错误得到应有的优先级，为每个错误分配正确的优先级是必要的。以下是在 Dynamics AX 的 IBI 规范中推荐的优先级级别。

- **紧急 (0)**：在做任何其他事情之前修复。
- **高 (1)**：立即修复；这应是优先级 0 之后的最高重要问题。
- **普通 (2)**：尽快修复；具体时间取决于客户或测试的变通成本。
- **低 (3)**：如果有时间则修复，很好有。

### Severity

严重性应根据问题从技术角度的影响进行分配。以下是在 Dynamics AX 的 IBI 规范中推荐的严重性级别：

- **严重性 1（必须修复）**：这些是与系统崩溃或信息丢失相关的修复。此类别的几个示例包括应用程序崩溃、产品不稳定、主要测试阻塞、高安全风险、构建损坏或构建验证测试失败、应用程序安全故障和可信计算故障、数据丢失、损坏或误表示、内存泄漏等。
- **严重性 2**：当主要部分或整个功能不可用，或功能的小部分不可用但变通方法非常复杂时分配此严重性。这也可能是一个严重性级别，其中错误会显著影响客户或测试。几个示例是：
  - 电话号码字段（必须填写）只能容纳 5 个字符，而客户所在地的实际电话号码为 7 位数字。
  - 缺少加密信用卡号码等敏感信息的加密功能。
- **严重性 3**：当存在次要功能问题且有变通方法时应分配此严重性级别。客户或测试不应因错误而受到显著影响。
  - 某个字段接受 ISD 代码超过两位字符，但客户所在国家的 ISD 代码为一位数字。变通方法可能是输入 00X 而不是 X。
- **严重性 4**：非常次要的问题，如拼写错误（不提供错误信息）、制表符顺序不正确等。

有些人对严重性和优先级感到困惑，常常认为高优先级的错误也是高严重性的，这是不正确的。例如：

- 新添加的功能缺少帮助文件：
  - High Priority (a user cannot use the functionality as the help file is the only way to know about the new feature).
  - Low severity (it is not information loss or functionality missing; from a technical perspective it is not so damaging).
- Interest calculation is wrong in the year 2100 due to incorrect leap year calculation at the end of a century:
  - Low priority (Customer is not affected today).
  - High severity (the calendar algorithm may need a change).



## 安全漏洞分类

安全漏洞按照 STRIDE 进行分类，因此正确对漏洞进行分类至关重要：

- **欺骗：** 如果用户冒充另一个实体或个人。欺骗的其他术语有冒名、伪装或身份盗用。
- **篡改：** 如果通过诸如 SQL 注入等技术对数据进行未经授权的修改。其其他术语可能是（数据）完整性。
- **否认：** 如果用户否认已执行某个操作，且没有足够的证据证明相反的情况。
- **信息泄露：** 如果信息被未经授权的人员访问。
- **拒绝服务：** 如果人们滥用功能，意图制造压力状况，从而使其他真实用户无法舒适地使用系统。
- **权限提升：** 如果用户获得超出其应有权限的更多权限。
- **攻击面减小：** 如果对权限最低的用户（如匿名用户）的代码访问被减少。

缺陷管理工具必须提供一个额外的选项 '不是安全漏洞' 来声明某个问题不是安全相关问题。

## 安全漏洞的根本原因分析

必须对所有安全漏洞进行根本原因分析。根据其来源，安全漏洞可归类为以下一种类型：

- 不是安全漏洞。
- **缓冲区溢出或欠溢：** 当变量的大小不足以容纳给定值时发生，内存缓冲区会被额外数据覆盖。缓冲区溢出是最常见且危害最大的安全风险之一。在设计或编码时，确保声明的变量具有足够的尺寸或精度来处理最大或最小可能值。缓冲区溢出的几种类型有堆溢出、基于栈的缓冲区溢出、V-表和函数指针覆盖以及异常处理程序覆盖。缓冲区溢出可能导致访问违规、不稳定以及用于恶意目的的代码注入。
- 算术错误：当变量的限制（任一上限或下限范围边界）被超过时发生。例如，整数溢出。算术错误可分为两种——溢出和欠溢。溢出发生在要存储的值超过变量存储容量的上限时，欠溢发生在要存储的值小于变量的下限时。算术错误可能导致更严重的错误，如缓冲区溢出或缓冲区欠溢。
- SQL/脚本注入：这是在用户输入中添加 SQL 语句的过程，可能用于绕过授权、调用内置存储过程并探测数据库。当使用用户输入动态构建 SQL 语句时可能发生 SQL 注入攻击；黑客可以在用户输入中添加 SQL 语句的一部分，从而使生成的 SQL 语句执行恶意操作。
- 跨站脚本：此攻击发生在用户输入未经有效性检查直接输出时。例如，如果在讨论论坛中输入了恶意 JavaScript，则每当用户打开该论坛时，此恶意 JavaScript 代码就会在客户端机器上执行。另一个例子可能是使用电子邮件中的表单标签窃取客户端 cookie。
- 加密弱点：当使用弱算法或密钥未安全存储时发生。有时这是由于人为工程因素造成的。
- 弱认证：认证机制应足够强，用户不应通过任何手段（如 SQL 注入、规范化等）绕过它。
- 弱授权或不当的访问控制列表：应为每项资产精确设置授权级别；应正确设置。
- 秘密隐藏无效：这发生在向用户提供某些秘密信息时。几个例子是错误消息、异常处理等。
- 无限资源消耗（DoS）：当向未经授权的用户提供过多服务时发生。例如，在从数据库检索任何数据之前，应尽早检查（而不是仅在向用户显示信息前检查）用户是否被授权访问该信息。DoS 攻击可分为四种类型：CPU 饥饿、内存饥饿、资源饥饿和网络饥饿。当用户输入被信任超过所需程度、在检查授权之前执行昂贵操作，或安全设计中未涉及适当安全时，应考虑此威胁。
- 不正确/无路径名：文件或路径名可以以多种方式编码，因此不正确的路径名可能导致规范化错误。应避免包含空格或特殊字符（如 &、? 或 +）的路径名。
- 规范化错误：当安全决策基于文件名且在解析文件名、URL 或设备名时发生解析错误时出现。这可能导致对被访问资源应用不正确的权限。
- 其他等，如意外泄露（例如由于不适当或缺少错误消息或不良安全实践导致用户操作错误）、目录遍历，以及未处理的异常或异常处理不当，从而导致用户获取有价值的信息。

## 使用 DREAD 模型进行重要性识别

为了对每个安全问题采取适当措施，需要识别其重要性。DREAD 是计算安全漏洞重要性的有用工具。DREAD 代表：

- 损害潜力：对系统的损害程度会如何？
- 可再现性：是否容易一再产生相同的攻击？
- 可利用性：实施攻击需要多少努力或实验？
- 受影响用户：有多少百分比的人会受到此威胁影响？
- 可发现性：此攻击是否可以被轻易发现？

为 DREAD 的五个组成部分中的每一个分配 1 到 10 的值，然后为每个安全威胁计算评级总和。此总和值表示安全威胁的重要性级别。

根据 DREAD 中的总和值，可对每个威胁采取以下措施：

- 不采取行动：如果 DREAD 值为非常低。
- 告知客户所有信息：如果 DREAD 值为非常低。
- 禁用或移除功能：如果 DREAD 值为中等到高，且修复成本相对于投资回报率来说非常高。
- 修复它：如果 DREAD 值为中等到高，且修复并不复杂。

缺陷管理工具应能够接受上述其中一个值作为关闭解决方案。

## 缺陷管理工具

缺陷管理工具必须支持分类并为分类提供适当的级别。除此之外，根据 IBI 规范对 Dynamics AX 的规定，缺陷管理工具还有一些额外的要求。

- 缺陷管理系统必须具备注册、跟踪和报告以下内容的 capability：
  - 缺陷
  - 问题
  - 设计变更请求
- 缺陷管理工具必须接受或为每个缺陷生成以下信息：
  - 唯一编号（自动生成）
  - 缺陷描述
  - 缺陷优先级（上面提到的四个级别）
  - 缺陷严重性（上面提到的四个级别）
  - 评论记录，以显示缺陷在其生命周期内是如何处理的
  - 关闭评论
- 缺陷管理工具应根据上述提到的不同分类标准以及状态生成报告。
- 缺陷管理工具必须为所有开放缺陷生成报告（即状态为进行中、正在调查、需要更多信息、等待客户澄清、已延期等）。这有助于在任何时间点生成所有已知缺陷的报告。
- 缺陷管理工具必须接受安全相关缺陷的额外信息。
- 缺陷管理工具在发现安全相关问题后必须采取行动：
  - 必须修复：诸如写访问违规、栈溢出异常等问题
  - 必须调查：大内存分配、整数溢出、自定义异常、可能导致可利用崩溃的其他系统级异常



- 缺陷管理工具必须能够记录 bug 的原因，并且选项必须包括以下内容：
  - 不是安全漏洞
  - 缓冲区溢出或下溢
  - 算术错误（例如，整数溢出）
  - SQL/脚本注入
  - 目录遍历
  - 竞态条件
  - 跨站脚本
  - 加密弱点
  - 弱认证
  - 弱授权或不当的访问控制列表
  - 无效的密钥隐藏
  - 无限资源消耗（DoS）
  - 不正确/无错误消息
  - 不正确/无路径名
  - 规范化
  - 其他
- 缺陷管理工具应能够接受以下其中一个值作为解决方式：
  - 不采取行动
  - 将所有内容告知客户
  - 禁用或移除该功能
  - 修复它

## 缺陷生命周期

缺陷生命周期应基于项目的定制需求以及项目中使用的通信方法。关闭类别应具有充足的选项，以便可以轻松记录关闭 bug 的原因。可能的已关闭类别可能包括以下内容：

- 不是问题
- 无法重现
- 需求已更改
- 与此代码段无关
- 已验证
- 重复
- 不可重现
- 按设计
- 已推迟
- 已撤回
- 无需操作

如此广泛的已关闭类别列表将有助于识别已关闭问题如何达到关闭阶段。
