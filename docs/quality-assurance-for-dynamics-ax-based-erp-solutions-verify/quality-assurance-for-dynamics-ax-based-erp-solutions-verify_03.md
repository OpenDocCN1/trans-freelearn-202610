## 2 Quality in Dynamics AX-Based ERP Solutions

在上一章中，我们讨论了从业务或用户角度使 ERP 系统理想的关键特征。我们还了解了为什么 Dynamics AX 可被视为理想的 ERP 解决方案。在本章中，我们将从技术角度讨论各种关键特征，并学习如何保持这些特征。学习本章后，以下主题将变得清晰：

- 什么是质量？
- 为什么需要关注质量？
- 我们如何实现这一质量？

### Quality Definition for Dynamics AX

为保持 Dynamics AX 的关键特性，需要考虑一些规范。这些规范最初由微软作为“Industry Builder Initiatives”发布。尽管它们已详细讨论，但可能存在一些差异，因为我结合了自己在经济成本下提高质量的经验。

### Coding

定制编写的代码应符合规定的编码标准。编码标准基于以下因素制定：

- 后续定制的便捷性
- 集成
- 性能
- 国际化/本地化
- 可扩展性
- 可理解性（包括代码布局和注释）
- 易用性
- Dynamics AX 之道
- 可信赖性

这些编码标准分为以下两类：

- 语法级最佳实践（静态代码分析）
- 设计模式级最佳实践

大量语法级最佳实践的检查可以通过 Dynamics AX 的内置工具——Dynamics AX 最佳实践检查工具来执行。该工具可用于：

- 编译时
- 提交时
- 随时通过在 AOT 中右键单击对象并检查最佳实践

随时可以通过右键单击节点并选择 **Add-Ins | Best Practices | Check Best Practices.** 来检查应用程序对象树（AOT）中一个或多个节点的最佳实践。

要在编译时配置最佳实践检查，用户需要执行以下操作：

1. 选择 **Tools | Options**。
2. 单击 **Compiler** 按钮。
3. 将 **Diagnostics level** 选择为 **level 4**。

最佳实践检查工具显示三种类型的最佳实践偏差，即 Error、Warning 和 Information。我们可以选择要显示的偏差严重程度级别。以下是可选择的不同的警告级别：

- **Errors only**: 如果 Dynamics AX 仅显示严重程度为 Error 的偏差。
- **Errors and Warnings**: 如果 Dynamics AX 应显示严重程度为 Error 和 Warning 的偏差。系统不会显示严重程度为 'Information' 的偏差。
- **All**: 当所有最佳实践偏差都需向用户显示时。

与警告级别相关的设置只会隐藏不相关的错误，但不会停止对最佳实践偏差的检查。警告级别可在 **Tools | Options | Best Practices** 中通过从警告级别列表中选择适当的警告级别进行设置。

定义了三种不同的严重程度级别如下：

- **Information:** 可能值得了解的事情（在最佳实践工具输出中以蓝色显示）。
- **Warnings:** 强烈建议修复的事情（在最佳实践工具输出中以黄色显示）。建议至少消除该类别中 95% 的偏差，并且对无法修复的部分需要提供适当的理由并记录。
- **Errors:** 必须修复的事情（在最佳实践工具输出中以红色显示）。

如果双击偏差消息，它将打开代码编辑器并聚焦于该偏差消息。

### Testing and Quality Assurance Standards

必须利用与开发 Dynamics AX 时相同的质量标准，即微软标准，来保持核心 Dynamics AX 的质量，从而在 Dynamics AX 定制中保持其质量。缺陷必须得到适当的分类和管理。应强调以下几点：

- 定义缺陷严重程度和优先级的依据必须与微软标准相同。
- 缺陷管理系统应具有微软定义的特点，包括但不限于以下内容：
  - 每个错误都应有一个唯一的编号（ID）与之关联。
  - 它应允许根据严重程度和优先级对错误进行分类。
  - 它应允许插入注释或至少是关闭注释。
  - 它应允许为安全相关错误提供附加信息（对于安全错误而言这是强制性的）。
- 所有已知问题必须记录在案，以描述可能的影响/故障以及可能的变通方法以最大程度地减少已知问题的影响。

我们将在第 8 章《缺陷管理系统》中讨论这些标准。

### User Friendliness

行业事实标准是帮助应可在用户当前屏幕下通用访问，即帮助系统在 HR 模块和 CRM 模块中不应不同。这将确保用户在无需花费太多精力查找帮助本身的情况下获得帮助。为了与 Microsoft Dynamics AX 用户帮助指南保持一致，我们需要遵守以下规定：

- 帮助文档应为 `.chm` 文件格式。
- 帮助必须可通过按 `F1` 功能键访问。
- 帮助必须描述“如何”，而不仅仅是“什么”或“为什么”。
- 帮助样式应符合 Microsoft Dynamics AX 帮助样式/标准。
- 用户界面应符合 Microsoft Dynamics AX 用户界面指南和 Microsoft Windows 用户界面指南。
- 高水平的一致性，例如：
  - 同一实体不应使用不同的标签，例如 Bill of material 和 BOM 或 Inquiry 和 enquiry。
  - 按钮应按确定的顺序出现。

Dynamics AX 用户界面指南将在第 4 章《最佳实践 – GUI》中详细讨论。

### Report Standards

在定制期间使用 Dynamics AX 中遵循的通用标准是可取的。标准报表应使用 Dynamics AX 提供的报表向导开发。

如果需要创建新型标准报表，应在所有此类报表中使用内置通用模板以保持一致性。使用标准模板还将提高可维护性。

应按照 Dynamics AX 应用程序中 SQL 报表实现的指南所述使用 SQL 报表。这些指南在 Microsoft Dynamics AX 中提供。

### Performance Optimization

编码和实现应进行性能优化。以下考虑因素可确保定制不会导致性能下降：

- 遵循性能优化/三层架构的最佳实践。
- 正确选择 run-on 属性，该属性决定代码应在哪个层运行。合适的选择将最大程度地减少不同层之间的调用，从而提高性能。
- 正确使用缓存不仅可以减少网络/带宽资源，还可以使 AOS/数据库服务器的负载最小化。
- 在代码中使用客户端/服务器中立函数。

如果遵循上述考虑因素，将确保定制后没有显著的性能下降，这是 IBI 规范的要求之一。

### Trustworthy Computing

如果不为用户提供可信赖的计算体验，任何 ERP 系统实施都无法成功。可通过以下特性实现可信赖的计算体验：

- **Security**: 如今计算机网络不仅局限于一个组织。网络可能暴露于互联网或广域网等，这增加了安全攻击的风险。业务系统应能够保护系统并维护数据的保密性、完整性和可用性。
- **Privacy**: 如今业务成功在于信息、其保密性、流动性和可用性。业务系统不仅应具有适当的访问控制机制，还应确保恶意用户无法通过设计、开发或部署中的安全漏洞访问机密信息。
- **Reliability**: ERP 系统实施不仅仅是另一种工具。它是一种文化变革。在新的文化中，业务成功高度依赖于 ERP 系统的可靠性，这意味着在每种情况下 ERP 系统都应按预期执行。系统呈现的信息应准确、精确且格式符合要求。客户应体验到一致且无故障的计算体验，无需使用其他手段来处理/了解信息。



可信性不能像一次事件那样实现。它需要受过教育的人力资源持续工作，并高度关注与可信性相关的质量，即安全性、隐私性、可靠性等。最后但同样重要的是，客户也应了解如何以最安全的方式使用系统，即应提供实施指南，其中描述了安全加固。

推荐的做法是对所有相关人员进行安全、安全设计和安全编码等方面的教育。这将有助于他们分析安全问题。所有安全问题必须归类为以下类别之一：伪造、篡改、否认、信息泄露、拒绝服务、权限提升和攻击面减少。适当的分类将有助于更好地理解安全问题，并能有效进行根本原因分析。有效的根本原因分析将有助于采取纠正和预防措施。

我们将在第 5 章 *最佳实践 – 可信计算* 中更详细地讨论可信计算。

### 全球化

Microsoft Dynamics AX 是一个真正全球化的 ERP 解决方案，因为它支持全球不同地理位置的三十多种语言和货币的输入和输出显示。为了保持 ERP 解决方案的全球化特性，应具备以下特征：

- 更改日期格式等不应需要定制，因此：
  - 应使用内置数据类型，或 **EDT（扩展数据类型）** 应从内置数据类型扩展用于时间和日期。
- 代码应与语言元素分离，以便翻译时无需定制：
  - 语言元素（例如帮助文本、显示标签、错误消息等）应使用标签文件系统实现。
  - 标签长度在不同语言中可能有所不同，因此标签/UI 控件的宽度必须能够根据不同语言的要求进行调整。Microsoft Dynamics 具有一个非常好的功能，如果遵循最佳实践（例如控件上的标签未设置为固定宽度），UI 元素的宽度将根据语言需求自动更改。
- 在世界不同地区，数字格式的约定各不相同，例如小数分隔符、千位分隔符等。Microsoft Dynamics AX 提供了根据偏好约定调整数字格式的灵活性。需要遵循一些关于千位分隔符、小数分隔符等的最佳实践，即这些应设置为自动。
- 在当今企业中，国家已不再是边界，因此 ERP 系统必须允许使用多种货币及其转换。Microsoft Dynamics AX 方便用户使用不同货币。

我们将在第 3 章中更详细地讨论这些最佳实践。

### 本地化

本地化是将全球化应用程序适配到特定文化或区域的过程。ERP 系统应实现本地化，这意味着：

- 语言元素应与代码分离，以便代码可在本地语言中使用而无需重新定制。
- GUI 应根据标签或 Windows 控件数量的变化进行调整，以防止布局损坏。
- 为特定文化或区域调整图形。

Dynamics AX 是一个真正可本地化的 ERP 解决方案。Dynamics AX 中的标签文件系统允许将以下项目与代码分离：

- 显示标签
- F1 帮助文件
- 错误消息

Dynamics AX 最佳实践工具是一个非常有用的工具，用于查找代码中是否嵌入了任何语言元素，即上述任何语言元素均未使用标签文件。

Dynamics AX 具有 IntelliMorph 技术，可使其调整或重新排列用户界面元素，例如文本框、复选框等。这些对齐或调整大小的需求来自以下原因：

- 显示标签在不同语言中的大小不同。
- UI 元素数量可能根据本地需求而变化，因此可能需要删除某些 UI 元素或容纳更多 UI 控件。

最佳实践是使用不包含任何语言元素或特定文化信息的图形。需要注意的是，是否符合此最佳实践无法使用最佳实践工具进行验证。

### 平台兼容性

在定制过程中，我们需要特别注意使其平台兼容：

- 不应使用与 Dynamics AX 不兼容的任何技术。
- 不应使用在该操作系统中为保留关键字的任何名称，例如组件名称、注册表项名称等。
- 在设计企业门户时应考虑浏览器兼容性。

### 设置/安装

任何软件安装或卸载过程中的错误不仅可能导致正在安装或卸载的应用程序出现故障，还可能导致共享某些组件的其他应用程序出现故障，例如 DLL/Active X 组件、配置设置、注册表值等。以下示例可能是安装或卸载过程中出现的一些可能问题：

- 对共享组件的引用计数和版本检查管理不当可能导致在其他应用程序仍在使用共享组件时将其删除。另一个错误可能是应用程序安装未导致共享组件更新，这将导致已安装应用程序出现故障。
- 如果需要取消安装过程或由于某种原因安装未完成，设置中缺少回滚功能可能会带来很多困难。一个这样的例子可能是系统/设置包中没有依赖项。
- 不适当的卸载可能会损坏在 Dynamics AX 的多个不同层中定制的共享 AOT 元素。不当卸载的另一个例子是未手动删除标签和帮助文件。如果未手动删除标签和帮助文件，它们仍将被 Dynamics AX 使用，这意味着它们将抑制本不应再被抑制的标签。

为了最大程度地减少不良安装或卸载的影响，设置过程应具有以下特征：

- 应用程序的安装程序必须与核心 Dynamics AX 产品兼容。
- 设置程序必须在注册表数据库中记录所有 DLL 和 Active X 组件，因为注册表是 Windows 操作系统中用户、应用程序和计算机特定信息的中央配置数据库。
- 设置必须更新 AOT 中的 ApplicationVersion 类以添加应用程序的版本/构建号。
- 正在安装的应用程序的设置程序必须在设置早期阶段检查所需的 Dynamics AX 模块是否可用。如果所需的 Dynamics AX 模块不可用，设置程序应显示依赖项列表并优雅地失败，即适当地逆转设置过程。如果未自动化，则必须提供正确的手动检查程序。设置不应强制从 Internet 下载。
- Dynamics AX 具有内置系统，可通过检查配置键来选择或取消选择特定功能。配置键可在以下位置查看：**主菜单 | 管理 | 设置 | 系统 | 配置**。正在安装的应用程序必须使用此机制来打开和关闭功能。此类功能的一个例子是国家/地区特定功能。应用程序不得覆盖核心 Dynamics AX 产品中可用的配置键，但可以扩展新的配置键或核心产品中可用的任何配置键。如果无法扩展，必须创建新的配置键。
- Dynamics AX 是一个完全可定制的 ERP 解决方案，其中定制可以在多个层或同一层的多个位置进行。在卸载 Dynamics AX 应用程序时，卸载过程不应删除任何其他定制，这些定制可能位于不同的层或与正在卸载的应用程序所在的同一层中。

### 备份/恢复

客户应能够备份和恢复应用程序以及相关数据。由于在基于 Dynamics AX（即基于 X++）的应用程序中，新字段和表将与其他数据同样对待，因此基于核心 Dynamics AX 的流程会将这些实体视为与其他数据相同，它们将与核心 Dynamics AX 备份流程一起备份。



如果安装的应用程序具有独立的数据库，则必须在文档中提供数据备份和数据恢复流程。

### 可扩展性和定制

Dynamics AX 具有内置的 AOT 文档系统，其中提到了成功定制应用程序的注意事项。在 AOT 文档中，每个 AOT 元素（如表、窗体等）都对应一个节点。如果对现有元素进行定制，则必须更新相应的节点；但如果创建了新的 AOT 元素，则应在 AOT 文档中新增一个节点。

### 升级和维护

应用程序可以通过多种方式连接到 Dynamics AX，例如 COM 连接器、BizTalk 等。必须了解所有集成点，以便客户可以使用这些集成点从外部访问 Dynamics AX。需要以下信息，但也鼓励提供其他必要信息。

### 集成点的文档

Dynamics AX 集成点应至少涵盖以下信息；不过，强烈鼓励提供更多信息。

- 修改的核心 Dynamics AX 对象（根据需要重复此部分多次）
  - 修改的对象（表/窗体/报表/类）
  - 与核心对象一起添加或修改的组件列表
  - 新增的限制或依赖项（保存/删除验证、对可查看数据的限制等）
  - 与此对象的集成点列表
- 新增的与核心 Dynamics AX 接口的 Dynamics AX 对象
  - 添加的对象（表/窗体/报表/类）
  - 导航到新对象的方法（如果是窗体或 Web 资源）
  - 新对象使用的核心 Dynamics AX 资源列表
  - 使用的表
  - 引用的类
  - 从新对象到核心 Dynamics AX 的集成点
  - 使用的集成方法
  - 集成类型（只读、读写等）
- 新增的与核心 Dynamics AX 接口的外部对象
  - 添加的对象
  - 导航到新对象的方法（如果是窗体或 Web 资源）
  - 新对象使用的核心 Dynamics AX 资源列表
  - 使用的表
  - 引用的类
  - 从新对象到核心 Dynamics AX 的集成点
  - 使用的集成方法
  - 集成类型（只读、读写等）

### 数据库升级脚本

由于 Dynamics AX 需要数据升级脚本来处理数据升级，每当进行任何更改（如发布新版本、服务包或热修复）时，如果数据模型结构需要更改，则应提供升级脚本。

### DLL 和 ActiveX 控件的文件版本控制

所有可执行文件（例如 DLL 和 ActiveX 控件文件）都应具有关联的版本元数据。这将有助于升级以及服务包或热修复的应用程序。任何升级、服务包或热修复的安装程序都会检查这些文件的所需版本是否已到位。只有在找到所需的一切后，它才会继续安装。如果未关联版本元数据，则可能出现安装故障的情况。元数据必须包含供应商公司信息，以便如果该文件出现任何类型的损坏，客户可以识别公司名称并联系以进行回归。

### 所有修改对象的描述

Dynamics AX 可以生成所有修改对象的列表。应为版本中修改的所有对象提供详细描述。描述必须包括更改如何影响应用程序。

需要注意的是，详细描述仅适用于修改的对象，而不适用于新对象或在先前版本中已定制的未更改对象。

### 删除非功能代码

应从代码库中删除任何非功能代码，因为非功能代码在理解代码以进行进一步定制或支持时可能会带来困难。

我们研究了如何在 Dynamics AX 中定义质量以及为什么应保持这种质量。本章将成为理解 IBI 规范的基础。

## 3 最佳实践—技术

## 最佳实践—技术

完成本章后，您将了解各种编码和设计最佳实践背后的基础知识。在本章中，我们将讨论一些最重要的最佳实践。

第 1 章中讨论的理想 ERP 系统的大多数质量都是通过符合本章中讨论的技术最佳实践来实现的。Dynamics AX 最佳实践可以分为三个类别，即应用程序设计标准、共享标准和 AOT 对象标准。

## 应用程序设计标准

Dynamics AX 设计标准包括以下考虑因素：

- 代码放置
- 性能优化
- 在表中使用字段组
- 自动属性设置

## 代码放置

代码放置很重要，因为它会影响以下方面：

- 性能
- 定制
- 可重用性
- 可维护性（升级、可扩展性等）

一般指导原则是，代码应放置在尽量减少对其他层的各种调用、操作在成本最低的层执行，并且无需在多个地方编写相同代码的方式（例如，如果业务逻辑写入窗体，则也需要在 Web 客户端的企业门户中编写）。因此，我们不仅应考虑三层架构中的放置层，还应考虑代码片段的最佳 AOT（应用程序对象树）元素类型。设计完成后，我们需要考虑类中的方法和对象类型等。

## 三层架构考虑

该架构中的三个层专用于以下三种类型的工作：

- **Client**—表示层—窗体存储在此处。将客户端特定的类和方法放置在此处。
- **Object server**—业务应用程序逻辑层—应在此处、靠近数据库运行面向事务的数据库更新作业。
- **Database server**—数据库层—通过使用聚合函数、连接和其他数据库管理系统的计算功能来利用数据库服务器的强大功能。

Dynamics AX 为每个 AOT 元素都有一个属性 RunOn，表示应在哪一层执行，即 Client、AOS 或 Database server。此 RunOn 属性可能具有三个值之一，即 Client、Called from 和 Server。

Client: 对象将驻留在客户端。

Called from: 对象将驻留在使用 'new' 构造函数创建对象的层。

Server: 对象将驻留在服务器上。

现在我们将讨论如何确定 RunOn 属性值。

## 类

类的 RunOn 属性值将决定从该类创建的对象的所在位置。

- 如果父类具有除 Called from 之外的 RunOn 属性，则类的 RunOn 属性值将与父类相同，即如果父类的值为 Client 或 Server，则不能更改类的 RunOn 属性。
- 如果父类的 RunOn 属性值为 `Called from`，则可以将其更改为 `Client` 或 `Server`，如果未更改，则将保留继承的值，即 `Called from`。
- RunOn 属性的 `Called from` 值意味着对象将驻留在创建它的代码（通过调用 new 构造函数）运行的层。

## 方法

现在我们将讨论各种类型方法的执行位置。

- 类静态方法和表方法（数据库方法除外）可以具有其默认行为。
- 可以通过在方法声明中添加 `Client` 或 `Server` 修饰符关键字将方法的执行位置更改为 `Server` 或 `Client`，如下所示：
  - `server static boolean mymethod()`：使服务器成为执行位置。
  - `client static boolean mymethod()`：使客户端成为执行位置。
  - `client server static boolean mymethod()`：使 called from 成为执行位置。

下表总结了各种类型方法的执行位置：

| AOT 元素 | 默认行为 | 可以更改 |
|---|---|---|
| 类静态方法 | 默认情况下在与关联类相同的地点运行，即如果关联类的 RunOn 属性值为 `server`，则类静态方法也将在服务器上执行。 | 是 |
| 类实例方法 | 在类的对象所在位置运行。类对象按类 RunOn 属性所述驻留。 | 否 |
| 表静态方法 | 表静态方法具有 RunOn 属性为 `Called from`，因此默认情况下它们在被调用的位置运行。 | 是 |
| 表实例方法 | 表实例方法具有 RunOn 属性为 `Called from`，因此默认情况下它们在被调用的位置运行。标准方法 Insert/doInsert、Update/doUpdate 和 Delete/doDelete 在数据源所在位置的 `Server` 上运行。 | 否 |



## GUI 对象和报表

GUI 对象始终驻留在 `client` 上。GUI 对象包括 FormRun、FormDataSource、所有 FormControls、DialogBox 和 OperationProgress 对象。

报表始终驻留在 `calledFrom` 上，这意味着对象将在创建它的代码（通过调用 new 构造函数）运行的层上驻留。

## 临时表

临时表在数据首次插入的层上实例化并驻留，声明位置无关紧要。由于临时表的位置对性能至关重要，临时表应驻留在使用的层上。如果表在多个层中使用，则应驻留在执行插入和更新次数最多的层上。

## 查询

QueryRun 的 RunOn 属性的默认值是 `calledFrom`。QueryRun 应始终从最初运行它的同一层提供。

如果要用新的 QueryRun 替换旧的 QueryRun，则应在旧 QueryRun 执行的同一层上创建。

## AOT 元素类型考虑

决定代码容器类型时必须遵循以下准则：

| AOT 元素 | 考虑因素 |
|---|---|
| Class | 当满足以下任一条件时在类中编写代码：
• 代码与多个表相关。
• 代码与任何表都不相关。

当满足以下条件时创建类实例方法：
• 在类的实例变量上工作。
• 重写可能很有用。

当满足以下条件时创建类静态方法：
• 不需要访问类实例方法。
• 不需要重写。
• 方法的功能与其定义的类相关。
• 方法需要在与方法层不同的层上执行。 |
| Table | 当满足以下条件时在表方法中编写代码：
- 它严格与表相关。
当满足以下条件时创建表实例方法：
- 它应该一次处理一条记录。
当满足以下条件时创建表静态方法：
- 它应该一次处理零条、一些或所有记录。 |
| Global class | 当满足以下条件时在全局类中编写代码：
- 代码不能更合逻辑地放置在另一个类（或表）中。
- 代码是通用目的、工具扩展和应用程序中立的。 |
| Forms and reports | 只要可能就应避免在表单或报表上编码，即除调用处理复杂布局和业务逻辑的类和表方法外。
如果表方法中放置了编辑和显示方法，则必须避免使用它们。
如果代码无法放置在其他任何位置，即表示层最合适，则应遵守以下准则：
- 将代码放置在数据源或数据源字段级别，而不是控件级别。
- 通过使用菜单项从表单上的按钮调用类。例如，而不是在表单或报表上编写代码，可以在类中编写代码并从菜单项调用该类。 |
| Maps | 当需要对少量连接字段进行分组时在映射中编写代码。 |
| Views | 不要在视图中放置太多代码。 |

## 性能优化

性能优化准则可分为以下三类：

- 数据库设计
- AOS 性能优化
- 通用编程

## 数据库设计

数据库设计原则基于以下考虑：

- 通过缓存最小化数据库调用
- 最小化数据库事务
- 明智的索引设计
- 以最佳方式使用 select 语句
- 在尽可能短的时间内执行事务

## 缓存

只要不是绝对必要就应避免数据库访问，因为从内存中检索数据库记录要便宜得多且更快。将数据库记录记录在内存中称为缓存。服务器上可能的缓存类型如下：

- 记录缓存
- 整个表缓存
- 结果集缓存

## 记录缓存

记录缓存是一种性能增强技术，其中一个或一组记录是从内存而不是数据库中检索的。相对于从数据库检索，从内存中检索记录可显著改善数据访问。只有满足以下条件时才能启用记录缓存：

- 表中的 CacheLookup 属性应通过选择 notITTS、Found 或 FoundAndEmpty 值启用。
- 表具有唯一索引；使用主索引或第一个唯一索引。基于 RecId（称为 RecId 索引）的索引不符合缓存索引条件。

如果满足以下条件，则检索到的记录可以放入缓存：

- 表已缓存，即满足上述条件。
- 用于读取记录的 select 语句在缓存键上使用相等运算符 (==)。
- 检索记录中的所有字段。

当满足以下条件时，会查找记录：

- 表已缓存。
- 用于读取记录的 `select` 语句在缓存键上使用相等运算符 (==)。
- `select` 语句位于 TTS 内或外，但表的缓存属性值不是 NotITTS 且 `select` 不是 `forupdate`。

下表总结了不同类型的缓存机制：

| CacheLookup 属性 | 说明 |
|---|---|
| None | 不会缓存数据或从缓存中检索数据。
CacheLookup 属性此值用于以下情况：
- 表经常更新，例如事务表。
- 非常关键地读取最新数据。 |
| NotITTS | 所有检索到至少一个结果的 `select` 查询将被缓存。 |
| Found | - 对于此类型的缓存，所有基于缓存键的成功 `select` 查询都会被缓存。
- 如果记录存在于其中，则所有 `select` 查询都将从缓存返回。
- TTS 中的 `select forupdate` 将始终从数据库读取并替换缓存中的记录。
- CacheLookup 属性此值通常用于静态表，如 ZipCodes，其中记录通常存在。 |
| FoundAndEmpty | - 所有基于缓存键的 `select` 查询都会被缓存，即使那些不返回数据的 `select` 查询也会被缓存。
- 如果记录存在或被标记为不存在，则所有缓存键选择将从缓存返回，如果既未标记为不存在也未检索到任何结果，则会检查数据库并相应地更新缓存。
- TTS 中的 `select forupdate` 将始终从数据库读取并替换缓存中的记录。
- CacheLookup 属性此值通常用于注册不存在的键也很重要的表，例如折扣表。 |
| EntireTable | - 以临时表的形式创建表的副本。
- 对表的所有选择都将在副本上执行。
- 包含该表的连接仅在参与连接的所有表都是 EntireTable 缓存时才对副本执行。否则将执行数据库连接。
- 更改数据（插入、更新和删除）的操作将同时对数据库和副本执行。
- reread 方法将从数据库检索数据并同时更新副本数据。
- Microsoft Dynamics AX Object Server  thin 客户端将把 EntireTable 缓存表视为 FoundAndEmpty 缓存，并因此在访问表时在本地构建 recordCache。
- CacheLookup 属性此值通常用于不打算经常修改的表。 |

## 结果集缓存

RecordViewCache 对于缓存非静态表或包含太多记录以至于其他缓存方法不切实际的表很有用。

这种类型的缓存可通过 RecordViewCache 类获得。RecordViewCache 使用带有定义结果集的 where 子句的 X++ select 实例化。从技术上讲，RecordViewCache 可以使用 X++ select 实例化，但它会在内存中创建表的副本，这可能是内存的低效使用。

以下规则适用于实例化 X++ select：

- 它可能不是连接。
- 它必须是 noFetch。
- 表不能是临时的。
- 运行 Dynamics AX Object Server thin 客户端时，实例化必须在服务器上进行。




结果集缓存的局限性如下：

-   RecordViewCache 在 Dynamics AX 客户端之间不共享。
-   RecordViewCache 对象超出作用域或被销毁时，RecordViewCache 立即被停用。

在某些情况下，结果集缓存可能很危险，因此仅建议谨慎使用。以下关于结果集缓存的事实有助于决定是否使用结果集缓存。

-   数据库会与 RecordViewCache 同时更新。
-   在实例化时未符合结果集的行，其键的更新不会导致该行被包含在缓存中。
-   插入操作始终包含在该表的 RecordViewCaches 中。这无疑是一个优势；然而，在向表插入大量行同时该表上存在 RecordViewCache 时应谨慎，因为这会延长缓存更新时间。
-   `delete` 会将该行从该表上的 RecordViewCaches 中移除，但不会从表中移除
-   `Delete_from` 会使该表上的 RecordViewCaches 无效。

如上所述，RecordViewCache 可能不同步，因此我们可能需要再次重新同步它。X++ 有一个方法 `reread`，它从数据库检索数据并更新缓存副本。

## 索引

索引设计对于数据库性能优化而言非常重要。一般来说，索引存储在与数据表不同的文件或表中。因此，搜索是通过一小部分列（仅索引列）进行的，然后数据库使用索引最终从表本身检索数据。目标如下。

主键或索引通常用于唯一标识一条记录。主键和外键的最初意图是表示和强制相关表之间的引用完整性。现在主键被用作表的最重要的索引，并且不一定在其他表中具有引用的外键。主键通常附加到表本身的数据空间，但并非总是如此。这取决于数据库产品。

非主键索引是从一个或多个表列构造的索引。非主键索引可能包含也可能不包含主键索引列。非主键索引的目的是提高数据库访问性能。这些索引将在数据库内创建为单独的文件。因此，在搜索这些索引时，只会将少量列加载到内存中进行搜索。这些索引具有指向表数据空间的虚拟内存地址，从而允许索引空间与表空间之间快速访问。

请注意，索引所需的内存或缓存空间远小于数据表，因为索引表的行长度更小。其原因在于，与数据表相比，索引的列数更少。因此，在内存/缓存与磁盘之间进行页面交换时，由于索引比数据表小，一次可将更多页面加载到内存中，从而索引可以比数据表空间快得多地遍历。不同数据库的处理方式不同。

有不同类型的索引可用。

索引可以是唯一的或非唯一的。唯一索引通常用作主键（并非总是如此），而非唯一索引包含重复项，通常用于数据库访问。

聚簇索引通常是哈希或 B 树算法的数据表空间形式。聚簇索引将表的实际数据表行聚类或分组，其中实际数据行驻留在索引的叶页面中。

非聚簇索引将索引的叶页面设置为指向包含表中行的數據页面的指针。

任何类型的索引都可以按升序或降序排列。升序索引是常见做法。

现在很明显，索引并不会使每个数据库操作都变快；由于除了表之外还需要更新索引文件，读写以外的操作甚至会因索引而变慢。

## 要索引的内容

为了在避免或最小化索引缺点的前提下发挥索引的最大益处，应仔细决定索引什么或不索引什么。以下是经验法则：

在频繁执行查询的地方使用索引：

-   列用于连接。
-   列用于 where 子句或 group by。
-   列用于 order by 子句。
-   当被分组的值范围相对于所选表中的行数较小时，通过索引可以增强 group by 子句。

索引会降低插入和更新的性能，有时甚至大幅下降。以下是一些此类情况：

-   行数较少的表
-   静态表
-   值范围很广的列
-   频繁更改且数据访问量低的表
-   列未在数据访问查询 `select` 语句中使用
-   没有固定宽度或数值数据列可供索引的表，或未对该列进行索引

## 索引类型

有几种类型的索引，每种都有其自身的优点和缺点。聚簇索引是在表本身中创建的索引，而不是在单独的索引文件中，因此使用这种类型的索引，整个表会按索引列排序。这是聚簇索引与非聚簇索引之间的主要区别。在非聚簇索引中，索引是在一个或多个列上创建的，然后列值被引用到表中的记录。因此，在非聚簇索引中主要进行两个操作，即在索引中定位键，然后在表中定位引用的记录，而聚簇索引则不同，可以直接搜索记录。由于这一事实，聚簇索引比非聚簇索引是更好的选择，因此如果只需要一个索引，建议使用聚簇索引，或者最频繁使用的列或主键应为聚簇索引。

聚簇索引也有一些缺点。当更新操作更改索引列的值时，本质上需要两个操作，即从先前位置删除，然后根据更新后的值在下一个位置插入。

复合索引是对两个或多个列的索引，可以是聚簇的也可以是非聚簇的。通常不建议使用复合索引，除以下情况外：

-   覆盖查询：覆盖查询中的所有列，以便数据库无需在数据库中搜索引用，只需扫描列即可达到目的。
-   满足特定的（复杂）搜索条件，例如主键本身就是两个或多个列的组合。

## 索引的一些提示：

| Category | Tips |
|---|---|
| 表列选择 | -   应选择易于索引的列。
-   数值比字符串更容易索引，因此对整数值的索引要快得多。
-   如果需要在字符串字段上创建索引，则应为定宽，而非 `varchar` 等。
-   切勿基于日期创建索引。
-   Dynamics AX 为大多数表自动生成 `RecID`。如果没有其他列符合条件，对该列进行索引是明智的。 |
| 需包含在索引中的编号列（用于构成复合键） | -   尽量减少复合键的使用。如果没有其他单个列符合条件，RecId 可以是索引的良好选择。
-   索引中的列数应尽可能少，以便搜索条件尽可能简单。
-   复合键建议最多包含三列。 |
| 索引数量 | -   表上的索引数量没有上限。然而，建议将索引限制在 `select` 查询的 `where` 子句中频繁使用的列上。
-   索引过多会减慢整体操作，因为一次插入或更新操作会导致多次插入或更新操作，因为除了表之外，每个索引文件都需要进行插入或更新。 |
| 索引列大小 | 索引所基于的列或列组合称为键。键的大小应尽可能小，以发挥索引在性能优化方面的优势。键大小可以通过以下方式减小：
-   在索引中使用最少的列数
-   使用用作索引键的列的最小数据大小
-   使用数值键代替其他数据类型，如 varchar、字符串等。 |
| 不同的索引键 | 应选择索引键，使键的重复值最少。最佳情况是键是唯一的。 |




## Select Statements

以下是关于使用 `select` 语句的最佳实践：

- 使用 `joins` 代替多个嵌套的 `while` selects。
- 在适用时使用字段列表。
- 在适用时使用 `select` 或聚合函数。
- 使用 `delete_from`（而不是 `while`、`select`、... `delete()`）。
- 在可能的情况下从缓存中选择。

## Transactions

关于数据库事务的最佳实践的关键原则是，数据库事务的数量应最小化，并且所需的事务应在最短时间内执行并且必须避免死锁。因此可以得出以下最佳实践：

- 在事务内部绝不要等待用户交互。
- 如果必须执行多个操作才能使数据恢复到一致状态，请在一个事务中执行所有操作。
- 使事务尽可能短小，以避免死锁和大的回滚日志。
- 避免死锁或长时间锁定。始终明确地按特定顺序（最好是键的顺序）在表中选择要更新的记录，在整个应用程序中每次都如此。从不同表中选择要更新的记录时，在整个应用程序中每次都按相同顺序进行。
- 如果记录未被更改，则不要写入或更新。
- 为避免对常用记录进行长时间锁定，进一步建议以下最佳实践：
  - 使用 **乐观并发控制 (OCC)**。
  - 对代表应用程序瓶颈的中央、常用（已更新）记录进行更新锁定。
  - 尽量避免在事务内部更新常用记录。
  - 设计结构以便可以使用插入代替更新。插入不会锁定对象。
  - 将用于更新的 `select` 语句尽可能靠近 `ttsCommit` 语句，以减少记录被锁定的时间。

## Use Joins in Forms

`join` 在表单中的使用与使用包含 `select` 查询的显示方法相比可以提供明显的优势。一次调用即可获取所有记录，用于显示大约二十行网格的表单。使用 `join` 的另一个优点是，对连接字段进行排序、过滤和查找非常容易。

## AOS Performance Optimization

AOS 优化背后的关键原则是最大限度地减少客户端和服务器之间的调用次数。每次调用传输的数据量是次要的，调用次数更为重要。一些最佳实践如下：

- 实现选择折扣。
- 使用容器减少客户端或服务器调用。

## Achieve Select Discount

每当需要从位于另一层的数据源执行 select 语句时，返回的记录具有一定的最小大小，这意味着可以在一次调用中获取多条记录，因此对于给定数量的记录，需要的往返 AOS 调用更少。这种现象被称为 'Select Discount'。

如果只需要获取一条记录，则记录数可以最小化为仅第一条记录。

## Using Field Groups in Tables

字段组是 Dynamics AX 设计中的一个重要功能，不仅用于在添加、删除或修改表的任何字段时将表单和报表与相关表同步，还用于缓存和性能优化等许多其他目的。以下是使用字段组在表中的一些优点：

- IntelliMorph 可以在对字段组进行任何更改时自动更新所有相关表单和报表的布局。
- 升级具有与标准表相同字段组的新表单和报表很容易，即标准字段组中的自定义对象在升级版本中也会得到更新。
- 可以使用字段序列来确定表单和报表中字段的序列，因此可以确保与表相关的所有表单和报表中字段的顺序相同。
- 表和表单上相同的字段组有助于 AOS 优化。

## Maintaining Auto Property Settings

在 Dynamics AX 中，许多属性的值应设置为 Auto，这可以使应用程序对象根据内核对各种事物（如区域设置等）的解释自动适应任何更改。Auto 属性设置的一些优点如下：

- 根据客户端的区域设置自动选择日期和时间格式
- 自动选择货币代码
- 根据登录用户的可用权限控制表单或报表布局

## Shared Standards

一些 Dynamics AX 自定义最佳实践适用于任何 AOT 元素。这些标准包括 X++ 标准、命名约定、标签标准和帮助文本指南。

## X++ Standards

本节讨论与 X++ 语言相关的一些最佳实践。遵循此标准可带来执行时间改善、升级和进一步自定义的便利性、面向对象概念的高效使用、代码可读性更好等。一些一般原则如下：

- 变量、常量或参数声明应尽可能局部化，以高效利用内存资源。
- 应在开始时检查错误条件，以便对操作和操作回滚所做的工作最少。这也有助于阻止拒绝服务攻击。拒绝服务攻击是试图通过太多垃圾请求使系统超负荷，从而使授权用户无法获得服务。
- 作为值提供的参数不得被修改或操作，否则可能增加在其他地方使用错误值几率。
- 代码应以干净的方式编写，这意味着应从代码中删除未使用的变量、方法和类。
- 应尽可能使用现有的 MorphX 函数或功能（除非其他最佳实践阻止你这样做），而不是创建新功能，因为这样可以使升级更容易。
- 用户不应遇到运行时错误。所有可能的情况都应预见并相应处理。如果运行时出现某些不可预测的情况，应在 Infolog 中显示错误，并附带帮助用户避免该情况以及可采取什么措施防止它的消息。

### Best Practices – Technical

- `this` 变量的值不应被更改。
- 应最大化可重用性。例如，而不是在不同地方重复代码行，可以编写一个单一方法，以便对该方法的更改可以在使用该方法的所有地方得到体现。
- 应该只有一个成功的返回点（switch 语句除外），以便可以确保对象删除等操作。
- 方法应执行单一明确定义的任务，并根据所执行任务命名。

## Text Constant Standards

Dynamics AX 中使用的所有文本都应放在标签文件中，无论其用途如何，例如用户界面或错误或成功消息。文本常量的使用可分为两大类，即用户界面文本和系统导向文本。

用户界面中使用的文本应遵循以下最佳实践：

- 修改应用程序中扩展数据类型或基础枚举的属性值。
- 切勿创建重复的标签文件，即相同的文本（同一种语言）但不同的标签文件。
- 在自定义文本时可以创建新的标签文件，但始终建议重用标准标签。然而，这可能带来一个缺点——每当升级发生时，对 SYS 层标签文件所做的所有更改都会丢失。因此，是否自定义现有标签文件或创建新标签文件的决定应谨慎做出。
- 用户界面文本（标签文件）应使用双引号。

系统导向的文本常量必须使用单引号。

## Exception Handling

异常处理的原则用途包括释放系统资源（例如通过对象删除释放内存、关闭数据库连接等）以及在 Infolog 中提供建设性信息，以便用户可以防止此类错误情况。以下是与异常处理相关的一些推荐最佳实践：

- 应始终在可能导致死锁的数据库事务周围创建 `try` 或 `catch` 死锁或 `retry` 循环。
- 在 `retry` 子句中，瞬态变量的值应恢复为 `try` 之前的值。



## Branching

一些关于 `if-else` 语句和 `switch` 语句的推荐最佳实践如下：

- 始终使用正向逻辑，例如写 `if (true)` 而不是 `if (! false)`。
- 优先使用 `switch` 语句而不是多个 `if-else` 语句。
- 除非有意使用 fall through 机制，否则应始终以 `break` 或 `return` 或 `throw` 语句结束一个 case。当使用 fall through 机制时，应给出类似 `//fall through` 的注释，以便每个读者都能清楚明白。

## Code Layout

为了提高代码的可读性，代码应以适当的布局编写。代码布局的一些主要最佳实践如下：

- 在发布代码前移除注释掉的代码。
- 遵循缩进规则。
- 遵循命名类、方法、表等的大小写规则。

## Methods

以下是方法的一些最佳实践：

- 方法应小而逻辑清晰，以便于轻松重写或覆盖。
- 方法应执行单一明确定义的任务，并且从其名称即可清楚任务内容。
- 对于静态类方法和表方法，应以最小化对其他层调用的方式使用限定 `client`、`server` 或 `client server`。更多细节请参阅《开发者指南》中的 *Best Practices for Designing* 部分。
- 为确保可信度，应分配适当的访问级别（public、private 或 protected）。
- 方法应根据 Dynamics AX 命名约定命名；保留关键字如 *is*、*check*、*validate*、*set*、*get* 和 *find* 应按照 Dynamics AX 使用这些标准方法或函数的方式使用。所有使用此类关键字的方法不得产生副作用，例如 validate、check、get 或 is 方法中不得进行赋值。
- 参数名称必须以下划线 (`_`) 字符开头，同时遵循其他通用命名约定。

## Handling Dates

日期因日期呈现格式的差异以及时区差异导致的值差异而成为错误来源。处理日期的几个最佳实践如下：

- 日期字段必须仅存储或显示在日期字段中，因为 **IntelliMorph** 具有在日期格式属性选择为 **Auto** 且以日期控件呈现时以适合用户格式显示日期值的能力。
- 系统日期不应被视为可靠信息，但在某些情况下（如用户输入信息的验证），系统日期应使用 `SystemDateGet()` 函数读取，而不是 `today()` 函数。
- 应避免日期转换，因为它会丢失日期属性，因此有时转换可能导致错误信息。对于所有与用户界面相关的情况，应使用 strFmt 或 date2Str，并将所有格式化相关参数的值设为 **-1**。这将允许用户以区域设置中指定的格式使用此信息。还应注意，存储转换后日期信息的字符串变量应足够长。

## Label Standards

强烈建议使用标签定义任何用户界面文本。这将在翻译过程中确保许多优势。以下是一些标签文件标准，以确保标签文件系统的真正优势：

- 标签文件的位置应尽可能通用，即扩展数据类型（EDT）。在某些情况下，仅因标签文本不同而无法使用现有 EDT。在这种情况下，应通过扩展现有 EDT 创建新的 EDT。在这种情况下，也可能有其他替代方案（例如在字段处更改标签），但经验法则是将标签用于最通用位置。
- 标签文件不应重复，即不应为同一文本存在两个标签文件。

## AOT Object Standards

AOT 对象标准特定于某个 AOT 元素。我们可以大致将 AOT 元素分类如下：

- Data Dictionary
  - Extended data type
  - Base Enum
  - Tables
  - Feature keys
  - Table collection
- Classes
- Forms
- Reports
- Jobs
- Menu items

## Data Dictionary

这是一组 AOT 对象，包括上一节提到的项目。表的最佳实践可进一步细分为字段、字段组、索引、表关系、删除操作和方法方面的最佳实践。

## Extended Data Type

EDT 在 GUI 元素中发挥重要作用，因为它是 GUI 元素的基本实体。以下是与扩展数据类型相关的一些基本最佳实践。

- 所有日期和日期格式相关属性都应设置为 Auto。
- 帮助文本不应与标签属性相同。帮助文本应更具描述性，并能够解释原因和/或方法。
- EDT 名称必须是真实世界的名称，如果仅属于一个模块，则应以模块为前缀。

## Base Enum

以下是与基础枚举相关的一些基本最佳实践：

- 枚举名称应表示可能的几个值或值的类型。例如 DiscountType、OpenClose 等。
- 显示长度属性应设置为 auto，以便在每种语言中都能显示完整名称。
- 帮助和标签属性必须具有值。帮助和标签属性不应具有相同的值。

## Tables

表的许多最佳实践属于性能优化、数据库设计标准等范围，因此这些标准已在其他地方讨论。一些未讨论的标准在此讨论。

- 表名可能包含以下有价值的信息：
  - **Prefix**：模块名称，例如 Cust 代表应付账款，Sales 代表应收账款
  - **Infix**：内容的逻辑描述
  - **Post fix**：数据类型，例如 Trans（交易）、Jour（日记账）、Line（包含表头表中特定记录详细信息的表）、Table（主要主表）、Group、Parameters、Setup 或表所属的模块名称
- Label 是强制属性，表必须仅使用 Label ID 进行标记。Label ID 的文本值在所有受支持语言中必须唯一。
- 如果表属于 Parameter、Group、Main 或 WorksheetHeader 四种类型之一，则必须具有关联的表单来维护表记录。该表单应具有与其显示菜单项（用于启动该表单）相同且与表名相似的名称。formRef 是表用于关联表单名称的属性。
- 应提及标题字段 1 和标题字段 2：
  - **TitleField1**：表中记录的键字段。如果键是用户的信息，则应为描述性标题。
  - **TitleField2**：表中记录的描述。

## Fields

字段的大多数属性都继承自扩展数据类型；然而，对于此类属性，使用部分或全部继承值并非强制。以下是一些指导原则：

- Name：应与对应的 EDT 名称相似，但如果单独命名，则应合乎逻辑。用作键的字段应以 ID 为后缀，例如 CustId、ItemId 等。
- HelpText：这是一个强制属性，并继承自对应的 EDT。由于帮助文本需要根据同一 EDT 的不同用途进行自定义，帮助文本可在任何字段中修改，但以下为指导原则：
  - 帮助文本属性不应与标签属性相同。
  - 标签也是一个强制属性，继承自 EDT。如果在此处设置值，则应与 EDT 上的值不同。
  - 每个主键或关键强制属性之一的字段必须设置为 Yes。
  - 在考虑 memo 或容器类型字段之前，应记住它们会增加应用程序和数据库获取的时间，它们会抑制数组获取，并且此类字段不能在 where 表达式中使用。

## Field Group

字段组是在用户界面中显示的字段组。Dynamics AX 有一些标准组（例如 Identification、Administration、Address、Dimension、Setup、Misc 等），同时也可以创建其他组。逻辑上属于一起的字段可以放在一个字段组中，而 Misc 字段组可用于对不适合任何其他字段组的字段进行分组。维度字段组必须具有单一类型的 Dimension 字段。字段组应在数据库和表单或报表中具有相同类型的分组，以提高缓存性能。

## Delete Actions

数据库完整性是关系数据库管理系统（RDBMS）的主要原则之一。删除操作应在两个表之间的每个关系上使用。以下是删除操作的关键最佳实践

- 在两个表之间的每个关系上使用删除操作。
- 使用表删除操作，而不是编写代码来指定删除是受限还是级联。



Dynamics AX 有三种类型的删除操作；选择其中一种完全取决于自定义需求。

## 表方法

Dynamics AX 中的表具有多个属性，例如 delete、validateDelete 等，因此 Dynamics AX 建议您不要编写方法或 X++ 代码来实现仅通过设置属性值即可完成的功能。

Dynamics AX 建议对无法通过表属性设置满足的自定义需求使用内置表方法。其中一些表方法是必须实现的，例如 find 和 exists 方法。

## 类

类的一个特点是它们可能同时具有后端（数据库）和前端（GUI）。前端界面应易于使用，同时尽可能安全。类的实现细节应始终对用户隐藏，因此建议使用私有或受保护的方法。后端方法高度安全、标准化且可靠，因此在规定的设计模式中建议使用私有或受保护的方法。设计模式取决于类的类型。类可以分为以下类别：

- 真实对象
- 操作类
- 支持类

以下是在声明方面常见的一些最佳实践：

- 对象成员变量只能用于保存对象的状态，即在实例方法调用之间和之外应保持其值的变量。
- 必须尽量减少全局变量的使用。
- 必须清理未使用的变量；可使用 Add-Ins | Best Practices | Check Variables 处的工具来了解未使用的变量。
- 在一个类（或子类）中的多个方法中使用的常量应在类声明期间声明。

类有一套丰富的最佳实践，微软发布的《Microsoft Dynamics AX 开发最佳实践》是一本很好的读物。

## 表单

在任何三层架构系统中，表单都位于表示层。它们大多数与外观或布局相关，我们将在第 4 章 *最佳实践 – GUI* 中讨论。表单的其他一些最佳实践围绕以下特征展开：

- 最大化使用 IntelliMorph
- 不强制日期或时间格式
- 不强制布局，例如标签的固定宽度、GUI 控件的位置控制等。
- 对 GUI 文本使用标签文件
- 表单具有最少的编码

### 避免在表单上编码

三层架构的基本概念是表单应仅用于表示层，因此不应在表单上存在其他代码，例如业务逻辑。放置在表单上的代码也会降低其可重用性和进一步定制的便利性；例如，如果您想开发企业门户，表单上编写的代码将需要在类或表方法等中重写，这会使实现变得复杂。另一个例子可能是当您想“COM 启用”您的业务逻辑时；与业务逻辑相关的表单代码会让您的生活几乎不可能。

在表单上编写的任何代码（除表示逻辑外）都会对性能造成限制，因为不同层之间的调用会增加，从而降低性能，因此应尽可能避免在表单上编写代码。在无法避免在表单上编写代码的情况下，应使用下表中总结的指南来编写表单上的代码。

| 编写代码的位置 | 指南 |
|---|---|
| 表单级别 | 当代码与整个表单相关时 |
|  | 当代码与多个数据源相关时 |
|  | 编辑器或显示方法（仅与任何数据源无关的那些） |
| 数据源 | 与数据源相关的编辑或显示方法 |
|  | 仅与数据源相关的代码，无法有效放置在表方法中 |
| 控件 | 当它严格与控件相关时 |

### 最大化使用 IntelliMorph

由于用户的区域设置或首选格式，表单可能以不同的语言和/或不同的日期、时间或货币格式呈现。Dynamics AX 最佳实践建议将以下显示属性的值设为 **Auto**：

- 日期
- 货币
- 时间
- 语言
- 数字格式（如小数运算符、分隔符等）
- 标签大小
- 表单大小

经验法则是将各种属性保持为 **Auto** 或默认值，这将有助于 IntelliMorph 最大化发挥作用。有关最佳实践的更多详细信息，建议读者阅读《最佳实践开发者指南》。

## 报表

报表的一个特殊事实是它们是输出媒体，其中纸张大小、用户关于区域设置或语言的配置、字体大小等外部环境很重要。

Dynamics AX 建议使用“Auto Design”来开发报表，因为这类报表可以根据外部环境变量更改布局。另一种在 Dynamics AX 中开发报表的方式是“Generated Design”；这种设计类型仅在需要严格的报表布局时才推荐。一些此类示例可能是监管报表、财务报表等。
