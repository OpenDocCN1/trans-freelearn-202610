
## Summary

本章我们研究了由 ERP 包解决的业务挑战。为应对这些挑战，ERP 包需要具备以下关键特性：

- 竞争力强且经济的所有权成本
- 对业务流程适应性的灵活性
- 可扩展性
- 易用性

### Quality Definition for Dynamics AX

为保持 Dynamics AX 的关键特性，需要考虑一些规范。这些规范最初由微软作为“Industry Builder Initiatives”发布。尽管它们已详细讨论，但可能存在一些差异，因为我结合了自己在经济成本下提高质量的经验。

### Coding

定制编写的代码应符合规定的编码标准。编码标准基于以下因素制定：

- 后续定制的便捷性
- 集成
- 性能
- 国际化/本地化
- 可扩展性
- 可理解性（包括代码布局和注释）
- 易用性
- Dynamics AX 之道
- 可信赖性

这些编码标准分为以下两类：

- 语法级最佳实践（静态代码分析）
- 设计模式级最佳实践

大量语法级最佳实践的检查可以通过 Dynamics AX 的内置工具——Dynamics AX 最佳实践检查工具来执行。该工具可用于：

- 编译时
- 提交时
- 随时通过在 AOT 中右键单击对象并检查最佳实践

随时可以通过右键单击节点并选择 **Add-Ins | Best Practices | Check Best Practices.** 来检查应用程序对象树（AOT）中一个或多个节点的最佳实践。

要在编译时配置最佳实践检查，用户需要执行以下操作：

1. 选择 **Tools | Options**。
2. 单击 **Compiler** 按钮。
3. 将 **Diagnostics level** 选择为 **level 4**。

最佳实践检查工具显示三种类型的最佳实践偏差，即 Error、Warning 和 Information。我们可以选择要显示的偏差严重程度级别。以下是可选择的不同的警告级别：

- **Errors only**: 如果 Dynamics AX 仅显示严重程度为 Error 的偏差。
- **Errors and Warnings**: 如果 Dynamics AX 应显示严重程度为 Error 和 Warning 的偏差。系统不会显示严重程度为 'Information' 的偏差。
- **All**: 当所有最佳实践偏差都需向用户显示时。

与警告级别相关的设置只会隐藏不相关的错误，但不会停止对最佳实践偏差的检查。警告级别可在 **Tools | Options | Best Practices** 中通过从警告级别列表中选择适当的警告级别进行设置。

定义了三种不同的严重程度级别如下：

- **Information:** 可能值得了解的事情（在最佳实践工具输出中以蓝色显示）。
- **Warnings:** 强烈建议修复的事情（在最佳实践工具输出中以黄色显示）。建议至少消除该类别中 95% 的偏差，并且对无法修复的部分需要提供适当的理由并记录。
- **Errors:** 必须修复的事情（在最佳实践工具输出中以红色显示）。

如果双击偏差消息，它将打开代码编辑器并聚焦于该偏差消息。

### Testing and Quality Assurance Standards

必须利用与开发 Dynamics AX 时相同的质量标准，即微软标准，来保持核心 Dynamics AX 的质量，从而在 Dynamics AX 定制中保持其质量。缺陷必须得到适当的分类和管理。应强调以下几点：

- 定义缺陷严重程度和优先级的依据必须与微软标准相同。
- 缺陷管理系统应具有微软定义的特点，包括但不限于以下内容：
  - 每个错误都应有一个唯一的编号（ID）与之关联。
  - 它应允许根据严重程度和优先级对错误进行分类。
  - 它应允许插入注释或至少是关闭注释。
  - 它应允许为安全相关错误提供附加信息（对于安全错误而言这是强制性的）。
- 所有已知问题必须记录在案，以描述可能的影响/故障以及可能的变通方法以最大程度地减少已知问题的影响。

我们将在第 8 章《缺陷管理系统》中讨论这些标准。

### User Friendliness

行业事实标准是帮助应可在用户当前屏幕下通用访问，即帮助系统在 HR 模块和 CRM 模块中不应不同。这将确保用户在无需花费太多精力查找帮助本身的情况下获得帮助。为了与 Microsoft Dynamics AX 用户帮助指南保持一致，我们需要遵守以下规定：

- 帮助文档应为 `.chm` 文件格式。
- 帮助必须可通过按 `F1` 功能键访问。
- 帮助必须描述“如何”，而不仅仅是“什么”或“为什么”。
- 帮助样式应符合 Microsoft Dynamics AX 帮助样式/标准。
- 用户界面应符合 Microsoft Dynamics AX 用户界面指南和 Microsoft Windows 用户界面指南。
- 高水平的一致性，例如：
  - 同一实体不应使用不同的标签，例如 Bill of material 和 BOM 或 Inquiry 和 enquiry。
  - 按钮应按确定的顺序出现。

Dynamics AX 用户界面指南将在第 4 章《最佳实践 – GUI》中详细讨论。

### Report Standards

在定制期间使用 Dynamics AX 中遵循的通用标准是可取的。标准报表应使用 Dynamics AX 提供的报表向导开发。

如果需要创建新型标准报表，应在所有此类报表中使用内置通用模板以保持一致性。使用标准模板还将提高可维护性。

应按照 Dynamics AX 应用程序中 SQL 报表实现的指南所述使用 SQL 报表。这些指南在 Microsoft Dynamics AX 中提供。

### Performance Optimization

编码和实现应进行性能优化。以下考虑因素可确保定制不会导致性能下降：

- 遵循性能优化/三层架构的最佳实践。
- 正确选择 run-on 属性，该属性决定代码应在哪个层运行。合适的选择将最大程度地减少不同层之间的调用，从而提高性能。
- 正确使用缓存不仅可以减少网络/带宽资源，还可以使 AOS/数据库服务器的负载最小化。
- 在代码中使用客户端/服务器中立函数。

如果遵循上述考虑因素，将确保定制后没有显著的性能下降，这是 IBI 规范的要求之一。

### Trustworthy Computing

如果不为用户提供可信赖的计算体验，任何 ERP 系统实施都无法成功。可通过以下特性实现可信赖的计算体验：

- **Security**: 如今计算机网络不仅局限于一个组织。网络可能暴露于互联网或广域网等，这增加了安全攻击的风险。业务系统应能够保护系统并维护数据的保密性、完整性和可用性。
- **Privacy**: 如今业务成功在于信息、其保密性、流动性和可用性。业务系统不仅应具有适当的访问控制机制，还应确保恶意用户无法通过设计、开发或部署中的安全漏洞访问机密信息。
- **Reliability**: ERP 系统实施不仅仅是另一种工具。它是一种文化变革。在新的文化中，业务成功高度依赖于 ERP 系统的可靠性，这意味着在每种情况下 ERP 系统都应按预期执行。系统呈现的信息应准确、精确且格式符合要求。客户应体验到一致且无故障的计算体验，无需使用其他手段来处理/了解信息。
