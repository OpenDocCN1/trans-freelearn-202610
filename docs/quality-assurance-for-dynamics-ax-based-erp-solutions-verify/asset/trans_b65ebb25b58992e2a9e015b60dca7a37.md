
结果集缓存的局限性如下：

-   RecordViewCache 在 Dynamics AX 客户端之间不共享。
-   RecordViewCache 对象超出作用域或被销毁时，RecordViewCache 立即被停用。

在某些情况下，结果集缓存可能很危险，因此仅建议谨慎使用。以下关于结果集缓存的事实有助于决定是否使用结果集缓存。

-   数据库会与 RecordViewCache 同时更新。
-   在实例化时未符合结果集的行，其键的更新不会导致该行被包含在缓存中。
-   插入操作始终包含在该表的 RecordViewCaches 中。这无疑是一个优势；然而，在向表插入大量行同时该表上存在 RecordViewCache 时应谨慎，因为这会延长缓存更新时间。
-   `delete` 会将该行从该表上的 RecordViewCaches 中移除，但不会从表中移除
-   `Delete_from` 会使该表上的 RecordViewCaches 无效。

如上所述，RecordViewCache 可能不同步，因此我们可能需要再次重新同步它。X++ 有一个方法 `reread`，它从数据库检索数据并更新缓存副本。

## 索引

索引设计对于数据库性能优化而言非常重要。一般来说，索引存储在与数据表不同的文件或表中。因此，搜索是通过一小部分列（仅索引列）进行的，然后数据库使用索引最终从表本身检索数据。目标如下。

主键或索引通常用于唯一标识一条记录。主键和外键的最初意图是表示和强制相关表之间的引用完整性。现在主键被用作表的最重要的索引，并且不一定在其他表中具有引用的外键。主键通常附加到表本身的数据空间，但并非总是如此。这取决于数据库产品。

非主键索引是从一个或多个表列构造的索引。非主键索引可能包含也可能不包含主键索引列。非主键索引的目的是提高数据库访问性能。这些索引将在数据库内创建为单独的文件。因此，在搜索这些索引时，只会将少量列加载到内存中进行搜索。这些索引具有指向表数据空间的虚拟内存地址，从而允许索引空间与表空间之间快速访问。

请注意，索引所需的内存或缓存空间远小于数据表，因为索引表的行长度更小。其原因在于，与数据表相比，索引的列数更少。因此，在内存/缓存与磁盘之间进行页面交换时，由于索引比数据表小，一次可将更多页面加载到内存中，从而索引可以比数据表空间快得多地遍历。不同数据库的处理方式不同。

有不同类型的索引可用。

索引可以是唯一的或非唯一的。唯一索引通常用作主键（并非总是如此），而非唯一索引包含重复项，通常用于数据库访问。

聚簇索引通常是哈希或 B 树算法的数据表空间形式。聚簇索引将表的实际数据表行聚类或分组，其中实际数据行驻留在索引的叶页面中。

非聚簇索引将索引的叶页面设置为指向包含表中行的數據页面的指针。

任何类型的索引都可以按升序或降序排列。升序索引是常见做法。

现在很明显，索引并不会使每个数据库操作都变快；由于除了表之外还需要更新索引文件，读写以外的操作甚至会因索引而变慢。

## 要索引的内容

为了在避免或最小化索引缺点的前提下发挥索引的最大益处，应仔细决定索引什么或不索引什么。以下是经验法则：

在频繁执行查询的地方使用索引：

-   列用于连接。
-   列用于 where 子句或 group by。
-   列用于 order by 子句。
-   当被分组的值范围相对于所选表中的行数较小时，通过索引可以增强 group by 子句。

索引会降低插入和更新的性能，有时甚至大幅下降。以下是一些此类情况：

-   行数较少的表
-   静态表
-   值范围很广的列
-   频繁更改且数据访问量低的表
-   列未在数据访问查询 `select` 语句中使用
-   没有固定宽度或数值数据列可供索引的表，或未对该列进行索引

## 索引类型

有几种类型的索引，每种都有其自身的优点和缺点。聚簇索引是在表本身中创建的索引，而不是在单独的索引文件中，因此使用这种类型的索引，整个表会按索引列排序。这是聚簇索引与非聚簇索引之间的主要区别。在非聚簇索引中，索引是在一个或多个列上创建的，然后列值被引用到表中的记录。因此，在非聚簇索引中主要进行两个操作，即在索引中定位键，然后在表中定位引用的记录，而聚簇索引则不同，可以直接搜索记录。由于这一事实，聚簇索引比非聚簇索引是更好的选择，因此如果只需要一个索引，建议使用聚簇索引，或者最频繁使用的列或主键应为聚簇索引。

聚簇索引也有一些缺点。当更新操作更改索引列的值时，本质上需要两个操作，即从先前位置删除，然后根据更新后的值在下一个位置插入。

复合索引是对两个或多个列的索引，可以是聚簇的也可以是非聚簇的。通常不建议使用复合索引，除以下情况外：

-   覆盖查询：覆盖查询中的所有列，以便数据库无需在数据库中搜索引用，只需扫描列即可达到目的。
-   满足特定的（复杂）搜索条件，例如主键本身就是两个或多个列的组合。

## 索引的一些提示：

| Category | Tips |
|---|---|
| 表列选择 | -   应选择易于索引的列。
-   数值比字符串更容易索引，因此对整数值的索引要快得多。
-   如果需要在字符串字段上创建索引，则应为定宽，而非 `varchar` 等。
-   切勿基于日期创建索引。
-   Dynamics AX 为大多数表自动生成 `RecID`。如果没有其他列符合条件，对该列进行索引是明智的。 |
| 需包含在索引中的编号列（用于构成复合键） | -   尽量减少复合键的使用。如果没有其他单个列符合条件，RecId 可以是索引的良好选择。
-   索引中的列数应尽可能少，以便搜索条件尽可能简单。
-   复合键建议最多包含三列。 |
| 索引数量 | -   表上的索引数量没有上限。然而，建议将索引限制在 `select` 查询的 `where` 子句中频繁使用的列上。
-   索引过多会减慢整体操作，因为一次插入或更新操作会导致多次插入或更新操作，因为除了表之外，每个索引文件都需要进行插入或更新。 |
| 索引列大小 | 索引所基于的列或列组合称为键。键的大小应尽可能小，以发挥索引在性能优化方面的优势。键大小可以通过以下方式减小：
-   在索引中使用最少的列数
-   使用用作索引键的列的最小数据大小
-   使用数值键代替其他数据类型，如 varchar、字符串等。 |
| 不同的索引键 | 应选择索引键，使键的重复值最少。最佳情况是键是唯一的。 |
