
Dynamics AX 有三种类型的删除操作；选择其中一种完全取决于自定义需求。

## 表方法

Dynamics AX 中的表具有多个属性，例如 delete、validateDelete 等，因此 Dynamics AX 建议您不要编写方法或 X++ 代码来实现仅通过设置属性值即可完成的功能。

Dynamics AX 建议对无法通过表属性设置满足的自定义需求使用内置表方法。其中一些表方法是必须实现的，例如 find 和 exists 方法。

## 类

类的一个特点是它们可能同时具有后端（数据库）和前端（GUI）。前端界面应易于使用，同时尽可能安全。类的实现细节应始终对用户隐藏，因此建议使用私有或受保护的方法。后端方法高度安全、标准化且可靠，因此在规定的设计模式中建议使用私有或受保护的方法。设计模式取决于类的类型。类可以分为以下类别：

- 真实对象
- 操作类
- 支持类

以下是在声明方面常见的一些最佳实践：

- 对象成员变量只能用于保存对象的状态，即在实例方法调用之间和之外应保持其值的变量。
- 必须尽量减少全局变量的使用。
- 必须清理未使用的变量；可使用 Add-Ins | Best Practices | Check Variables 处的工具来了解未使用的变量。
- 在一个类（或子类）中的多个方法中使用的常量应在类声明期间声明。

类有一套丰富的最佳实践，微软发布的《Microsoft Dynamics AX 开发最佳实践》是一本很好的读物。

## 表单

在任何三层架构系统中，表单都位于表示层。它们大多数与外观或布局相关，我们将在第 4 章 *最佳实践 – GUI* 中讨论。表单的其他一些最佳实践围绕以下特征展开：

- 最大化使用 IntelliMorph
- 不强制日期或时间格式
- 不强制布局，例如标签的固定宽度、GUI 控件的位置控制等。
- 对 GUI 文本使用标签文件
- 表单具有最少的编码

### 避免在表单上编码

三层架构的基本概念是表单应仅用于表示层，因此不应在表单上存在其他代码，例如业务逻辑。放置在表单上的代码也会降低其可重用性和进一步定制的便利性；例如，如果您想开发企业门户，表单上编写的代码将需要在类或表方法等中重写，这会使实现变得复杂。另一个例子可能是当您想“COM 启用”您的业务逻辑时；与业务逻辑相关的表单代码会让您的生活几乎不可能。

在表单上编写的任何代码（除表示逻辑外）都会对性能造成限制，因为不同层之间的调用会增加，从而降低性能，因此应尽可能避免在表单上编写代码。在无法避免在表单上编写代码的情况下，应使用下表中总结的指南来编写表单上的代码。

| 编写代码的位置 | 指南 |
|---|---|
| 表单级别 | 当代码与整个表单相关时 |
|  | 当代码与多个数据源相关时 |
|  | 编辑器或显示方法（仅与任何数据源无关的那些） |
| 数据源 | 与数据源相关的编辑或显示方法 |
|  | 仅与数据源相关的代码，无法有效放置在表方法中 |
| 控件 | 当它严格与控件相关时 |

### 最大化使用 IntelliMorph

由于用户的区域设置或首选格式，表单可能以不同的语言和/或不同的日期、时间或货币格式呈现。Dynamics AX 最佳实践建议将以下显示属性的值设为 **Auto**：

- 日期
- 货币
- 时间
- 语言
- 数字格式（如小数运算符、分隔符等）
- 标签大小
- 表单大小

经验法则是将各种属性保持为 **Auto** 或默认值，这将有助于 IntelliMorph 最大化发挥作用。有关最佳实践的更多详细信息，建议读者阅读《最佳实践开发者指南》。

## 报表

报表的一个特殊事实是它们是输出媒体，其中纸张大小、用户关于区域设置或语言的配置、字体大小等外部环境很重要。

Dynamics AX 建议使用“Auto Design”来开发报表，因为这类报表可以根据外部环境变量更改布局。另一种在 Dynamics AX 中开发报表的方式是“Generated Design”；这种设计类型仅在需要严格的报表布局时才推荐。一些此类示例可能是监管报表、财务报表等。

## 摘要

在本章中，我们讨论了通过采用最佳实践可以提高质量的各个领域。我们还讨论了各种最佳实践、最佳实践背后的理论以及如何采用这些最佳实践，即提供实用技巧。

## 4 最佳实践—GUI

用户界面在 ERP 系统的可用性中发挥着至关重要的作用，并影响用户的工作效率。Dynamics AX 的用户界面标准主要基于以下标准：

- Dynamics AX 用户帮助最佳实践
- Windows 用户体验指南

Dynamics AX 用户界面标准的目标是确保与核心 Dynamics AX 应用程序的一致性，并最大限度地减少对 Dynamics AX 默认设置的覆盖。

我们将讨论如何实现上述目标以及需要遵守的最佳实践。阅读本章后，以下主题将变得清晰：

- 各种 GUI 最佳实践
- 对 GUI 最佳实践偏离的文档记录

### 窗口和屏幕布局

该标准的目标是在 Dynamics AX 和其他 Windows 应用程序之间提供通用性。实现这一目标可确保轻松管理 Dynamics AX 应用程序的不同窗口；因为用户在使用其他 Microsoft 应用程序（如 MS Office、Outlook 和 Internet Explorer 等）时通常了解 Microsoft 对窗口的标准。

| 序号 | 检查点 | 预期结果 |
|---|---|---|
| 1.1 | 是否有任何窗口可以通过除调整大小按钮以外的任何方式调整大小？ | 否 |
| 1.2 | 是否有任何表单在网格调整大小时会被调整大小？ | 否 |
| 1.3 | 是否有任何窗口在用户从表格视图更改为树视图或反之时会被调整大小？ | 否 |
| 2 | 是否有任何窗口无法适应 1024*768 像素的 SVGA 显示？ | 否 |
| 3 | 是否有任何窗口在默认大小时需要水平滚动？ | 否 |
| 4 | 是否有任何窗口正好打开在已打开窗口的顶部？（如果提供充分理由，测试人员可以忽略此标准。） | 否 |
| 5 | 是否有任何窗口无法调整大小？ | 否 |

### 导航窗格要求

导航窗格的 GUI 标准是为了确保导航窗格的使用方式与其他 Microsoft 应用程序（如 Outlook 等）相同。

| 序号 | 检查点 | 预期结果 |
|---|---|---|
| 1 | 导航窗格必须以应用程序窗口的特定百分比显示。如果用户调整窗口大小，导航窗格必须自动调整大小以保持百分比恒定。是否遵循此标准？ | 是 |
| 2 | 导航窗格必须具有以下两个部分：
- 收藏夹
- 主菜单
是否遵循此标准？ | 是 |
