
# 使用 Gulp 和 Mocha 进行测试

## 单元测试

```
"use strict";

var gulp = require("gulp"),
    notify = require("gulp-notify"),
    config = require("../config"),
    paths = require("../utils/paths"),
    mocha = require("gulp-mocha");

function test() {
    return gulp.src(paths.makeFullPath(config.test.code), 
                    {read: false})
               .pipe(mocha({reporter: "spec"}))
               .once("error", notify.onError(
               "TEST: <%= error.message %>\n <%= error.stack %>"))
               .once("error", function () {
                   process.exit(1);
               })
               .once("end", function () {
                   process.exit();
               });
}

module.exports = {
    task: test
}
```

这应该相当简单；大部分是错误处理和通知。事实上，`process.exit` 方法是为了确保测试能干净地退出。否则，这等同于执行 `mocha . --reporter=spec`。因为我们在 `gulpfile.js` 顶部引入了 `Babel`，所以所有测试都会自动被 `Babel` 转译。

## UI 自动化测试

我们的自动化测试并不更复杂。唯一的额外代码在于处理环境变量：

```
"use strict";

var gulp = require("gulp"),
    gutil = require("gulp-util"),
    notify = require("gulp-notify"),
    config = require("../config"),
    settings = require("../settings"),
    paths = require("../utils/paths"),
    mocha = require("gulp-mocha");

function testUI() {
    var iosUDID = gutil.env.udid;
    var profile = gutil.env.profile;
    var server = gutil.env.server || "local";

    process.env["UIA_PROFILE"] = profile;
    process.env["UIA_SERVER"] = server;
    if (settings.VERBOSE) {
        process.env["UIA_LOGGING"] = "enabled";
    }
    if (iosUDID) {
        process.env["UIA_UDID"] = iosUDID;
    }

    return gulp.src(paths.makeFullPath(config.test.ui), 
                    {read: false})
               .pipe(mocha({reporter: "spec"}))
               .on("error", notify.onError(
                   "TEST-UI: <%= error.message %>"))
               .once("error", function () {
                   process.exit(1);
               })
               .once("end", function () {
                   process.exit();
               });
}

module.exports = {
    deps: ["build"],
    task: testUI,
}
```

除了处理环境变量的部分外，唯一的其他变化是使用 `config.test.ui` 作为指示测试存储位置的配置设置。

### 注意

另请注意，`test-ui` 依赖于 `build` 步骤。我们将其设为依赖，因为测试需要构建好的应用包。如果你想，可以移除该依赖；但你需要记住每次更改时手动重新构建应用。

或者，你可以创建一个设置，允许你在需要时跳过构建步骤（当你只是修改测试代码时这可能很有用）。请查看本书的代码包以获取示例。注意，实际的更改是在 `gulp/tasks/cordova-build.js` 中，而不是 `test-ui.js`。

## 运行测试

现在，要运行代码测试，你只需执行以下命令：

```
gulp test
```

要运行自动化测试，命令会稍微复杂一些，但也不算太复杂：

```
gulp test-ui --target=device|emulator --profile=appium-profile --udid=ios-udid --verbose=yes|no --server=local|sauce
```

你的目标应与用于测试的配置文件相匹配。如果你在模拟器上测试，请为目标指定 `emulator`。如果你在真机上测试，请指定 `device`。`udid` 开关仅在测试物理 iOS 设备时才需要。日志由 `verbose` 控制；如果省略，则不记录日志。`server` 也是可选的；如果省略，将默认为 `local`。

没有理由不将这些命令串联起来，让一个 `Gulp` 命令启动所有测试，但我们将其留作练习供你完成。

# IndexedDB 概览

## 存储选项

`Cordova` 应用可以使用多种不同类型的持久化存储。你使用哪种存储机制主要取决于应用的存储需求。此外，你的应用不限于单一类型的存储。将用户偏好存储在 `localStorage` 中，而将较大文件使用 `File API` 存储，这可能最合理。另一方面，`localStorage` 和 `File API` 都没有提供存储、检索和搜索结构化数据的简单机制。当然你可以将它们用于这些目的，但你必须自己完成大部分艰苦工作。

两种存储机制来拯救我们，使我们不必重复造轮子。较旧（现已弃用）的标准 `Web SQL Database` 使用关系数据模型，这类似于 `Oracle`、`PostgreSQL`、`Microsoft SQL` 等数据库。一种名为 `IndexedDB`（Indexed Database 的缩写）的较新标准使用键-对象存储。这对 `JavaScript` 特别有用，因为我们最常处理对象。因此，持久化这些对象变得非常简单。

`IndexedDB` 和 `Web SQL Database` 都不特定于 `Cordova`；你也可以在桌面浏览器中使用它们。这是一个很好的特性，因为你可以在桌面浏览器上测试应用的存储，从而实现更快的迭代和更容易的调试。如果你为桌面编写过网站应用，也可能重用你的存储代码（以及可能的许多其他代码）。不过有个坑（总是有的！）：`IndexedDB` 的支持情况参差不齐；要在不遇到许多痛苦问题的情况下使用它，你可能需要使用 polyfill 或其他封装器。值得庆幸的是，有几个优秀的可用方案。

## 浏览器支持

在继续之前，讨论 `IndexedDB` 的支持情况很重要。因为它比 `Web SQL Database` 规范更新，所以支持较少。在某些支持它的平台上，它也可能极其受限和/或充满 bug。

### 注意

有关最新的浏览器支持，请参阅 [http://caniuse.com/#feat=indexeddb](http://caniuse.com/#feat=indexeddb)。

截至撰写时，`IndexedDB` 具有以下移动浏览器支持：

*   **iOS**：iOS 7.x 不支持；iOS 8.x 和 iOS 9.x 行为极其 buggy
*   **Android**：4.4 以下版本不支持；Android 4.4 及更高版本完全支持
