# 自定义、社区与合作

在本结束章节中，我们希望收尾一些未竟之事，并指引您在 CiviCRM 实施方面的前进方向。我们将了解以下内容：

### 未来版本和项目路线图

当我们开始撰写本书时，CiviCRM 的当前稳定版本是 3.1.4，3.2 alpha 刚刚发布给社区。此后，v3.2 stable 已发布并经过多次修订，3.3 现在是稳定版本。到本书制作完成时，v3.4 将接近 alpha 发布。毋庸置疑，CiviCRM 的开发周期通常遵循开源的格言“尽早发布，经常发布”。

本书基于 v3.2 系列。有时，我们在新 v3.3 功能影响或扩展现有 v3.2 工具集的地方提供了注释。然而，在大多数情况下，我们专注于 v3.2 版本中存在的功能。

## 新功能

如果您是 CiviCRM 的新手，并且接触到的版本比 v3.2 更新，本书对您仍有价值，因为绝大部分功能是相同的。以下代表了 v3.3 中我们未在本书记载的关键新功能：

- CiviCampaign 作为一个新组件以某种 beta 版本引入。该功能面向倡导组织和政治活动，提供外展、请愿和调查工具。
- **Advanced Search** 现在可用于检索相关记录，而不仅仅是联系人记录。回想一下我们在回顾搜索工具时区分了检索记录的不同“透镜”。**Basic Search** 和 **Advanced Search** 检索联系人（无重复），而组件搜索检索相关记录（例如捐款）。在 v3.3 中，**Advanced Search** 现在可用于检索这些相关记录。例如，您可以指定跨捐款、会员和活动的搜索标准，并检索捐款记录。
- 去重/合并引擎已大幅重写以提高性能。在以前的版本中，如果在大型数据库上运行，此工具可能需要大量时间或超时。现在它对大型数据集的扩展性非常好。
- CiviMail 也获得了可扩展性改进，现在支持多线程发送。虽然取决于 SMTP 服务的能力，但这可以显著提高大型邮件的吞吐量。还创建了多个新报告，以提供跨多个邮件搜索的工具。
- 已添加多个 CiviCase 和 CiviGrant 的新报告，扩展了可以从这些组件中检索的数据类型。
- CiviEvent 价格集现在支持字段选项的最大值。这主要用于限制报名参加分会场的参会人数。许多会议都有并发的分会场，参会人数上限基于房间大小。每个会话组将是一个价格集字段，每个并发会话是一个选项值，以单选按钮显示，并附带相关价格（如适用）和最大参会人数。
- 您还记得本书前面讨论过的共享家庭地址给个人的能力吗？在 v3.3 中，此结构扩展到任何联系人类型。例如，个人可以将工作地址设置为共享其雇主的地址。




- CiviCRM目前的一个弱点是变更跟踪机制有限。虽然v3.2及更早版本能很好地跟踪最近一次修改是由谁在何时完成的，但关于修改性质的信息却很少。V3.3首次引入了全面审计跟踪机制，数据库中任意一项修改都会被记录并可访问。用于审查、交互和从这些变更中恢复的工具起初有限。然而，原始数据将保留在那里，保护你免受意外删除的影响。未来，我们可能会看到质量保证和审核功能，使主管能够监控和批准自助服务和一线工作人员的更改。
- 从开发者角度进一步讨论，v3.3 包含了升级版的 jQuery 和 jQuery UI，以及一套用于安装 CiviCRM 扩展的新机制，这些扩展可用于报表、自定义搜索、支付处理器和其他工具。CiviCRM社区正在迅速扩大，带来了许多新的参与者，他们参与开发和扩展该软件，以满足其组织的需求。该扩展框架为针对特定需求打包和传播工具提供了更大的灵活性。它使社区能够开发和维护专用功能，而无需将其包含在核心下载中。

与每次发布一样，整个软件中都有大量细微改进，旨在提高性能、创建更高效的工作流程并扩展功能。

## 定制与扩展

在本书开头，我们将CiviCRM的开源许可作为该软件的主要卖点之一进行了介绍。开源意味着源代码随时可用，并且可以在不违反许可的情况下进行修改或添加。简而言之，这意味着你可以打开引擎盖，随心所欲地修补。

当然，“修补”并不是真正让你受益的地方。真正受益的是能够真正定制、扩展、添加、重构，或做任何你需要做的事，以确保该软件适合你所在组织的需求。然后，你可以与社区分享，这样你就能从他们改进、编写文档、支持和扩展该软件的努力中受益。这就是开源的真实价值。与专有的闭源软件不同，你并不完全依赖软件所有者的路线图计划（祈祷他们会构建你所期望的功能），也不需要通过他们的技术支持团队来实现软件修改。开源意味着你可以自己修改代码，或者聘请开发人员来帮助你实现需求。

虽然深入探讨CiviCRM定制超出了本书的范围，但我们希望为你提供一些最佳实践和总体方向，以便你能有效开展自己的定制工作。

## 为定制而生

首先要认识到，CiviCRM 生来就是为定制而构建的。如果你与核心团队交流，他们会告诉你，他们构建该软件的明确目的就是使其尽可能易于扩展。他们不希望代码束缚你，而是希望帮助你快速高效地实现定制需求。这通过几种方式实现。

## 钩子与覆盖

软件支持定制的第一种方式是通过代码管理辅助。钩子提供了将代码注入现有流程的工具，是定制的干净（且通常最易升级）方法。

如果你熟悉 Drupal 的钩子结构，你会发现 CiviCRM 的结构也遵循类似模式。当特定事件发生时，你可以将自己的代码插入执行流程，而无需修改任何人的代码。在 Drupal 中，你通过模块实现钩子；在 Joomla! 中，钩子通过一个单一的钩子文件来处理，该文件可以存放在 PHP 覆盖目录中（如后续部分所述）。无论哪种方式，钩子实现都包括调用钩子函数、限制其范围（如适用），以及根据需要修改或添加代码行为。例如，你可以使用 buildForm 钩子来修改网站上显示的配置文件表单的默认值。

有关可用钩子列表及具体实现指导，请访问 `http://wiki.civicrm.org/confluence/display/CRM+DOC/CiviCRM+hook+specification.`

钩子很干净，通常更受青睐，因为你通常只处理和影响与你特定需求相关的代码。在前面的修改默认表单值的示例中，钩子允许你锁定特定表单，只修改所需字段，不触及或影响表单类中的任何其他字段或流程。你的定制“足迹”保持在最小。

然而，有时你可能会有更重要的定制，无法用钩子完成，或者当前没有可用的钩子。在这种情况下，CiviCRM 允许你为 PHP 和模板（`.tpl`）文件定义覆盖目录。覆盖 `.tpl` 文件来修改页面布局，往往比修改决定显示内容的 PHP 代码更容易。

覆盖目录，顾名思义，是一个与核心代码不同的位置，你可以在其中放置修改后的文件，这些文件将“覆盖”核心文件。在使用覆盖目录之前，必须在全局设置中定义它们。访问 **管理 | 配置 | 全局设置 | 目录** 来设置这些位置，并注意帮助文本中的推荐设置（取决于你的 CMS）。配置完成后，你需要将原始核心文件的修改副本放在覆盖目录内相应的文件夹路径中。

例如，假设你在 Drupal 安装中用于 CiviCRM 的 PHP 覆盖目录是 `/var/www/domain.com/public_html/sites/domain.com/files/civicrm/custom_php/`。要覆盖用于创建新个案的表单文件，你需要将修改后的文件放在 `/var/www/domain.com/public_html/sites/domain.com/files/civicrm/custom_php/CRM/Case/Form/Case.php`。

在 Joomla! 中，放置覆盖文件的标准位置将是你的媒体目录。例如：`/var/www/domain.com/public_html/media/civicrm/custom_php/CRM/Case/Form/Case.php`。

> 特定配置文件、贡献页和事件的文件可以与其他配置文件、贡献页和事件的文件分开覆盖。可插入一个额外的目录层级，包含要覆盖的配置文件、贡献页或事件的 ID。例如，`/var/www/domain.com/public_html/sites/domain.com/files/civicrm/custom_tpl/CRM/Contribute/Form/Contribution/11/Main.tpl` 将覆盖 ID 为 11 的贡献页。

使用覆盖文件时，有几点重要事项需要注意：

- PHP 覆盖文件夹必须从 CRM 目录构建，如前面示例所示。模板覆盖将从 `/templates/CRM/` 目录构建。换句话说，这些结构是从 `civicrm/` 包子文件夹（在您的核心文件中）构建的。
- 覆盖文件本身应该是原始文件的修改版本。即使您只修改了文件的一小部分，整个文件也会替换相应的核心文件，因此必须包含所有必要的代码。这是钩子（hook）与覆盖文件之间的关键区别——钩子可以在代码行级别进行修改，而覆盖文件则是在文件级别进行修改。
- 请务必使用正确版本的核心文件，并保持核心文件和覆盖文件同步更新。例如，如果您的站点运行的是 v3.2.4，请不要使用 v3.2.5 的核心文件作为覆盖定制的基础。较新的修订版可能包含会破坏您站点功能的额外更改。当将站点升级到较新的版本或修订版时，您应该计划仔细比较覆盖文件中的代码，并使用新的核心版本重新实现您的修改。

这两种定制方法都有助于您遵循开发中的一个重要原则：不要改动核心文件。只要有可能，您就应该避免修改核心代码文件。否则，您将无法顺利升级代码库，并且容易忽视（甚至丢失）重要的修改。

## API

如果您的定制是在 CiviCRM 环境内进行的，您可以轻松访问并使用整个代码中的类和方法。但是，如果您在该环境之外扩展 CiviCRM（例如 Joomla! 扩展或 Drupal 模块），您可能需要使用 CiviCRM 的公共 API。

您可以在线查看 API 列表：`http://wiki.civicrm.org/confluence/display/CRMDO/CiviCRM+Public+APIs`，或通过（相对较新的）API 文档 `http://api.civicrm.org` 查看。

API 可以通过您站点中的 PHP 代码、CiviCRM 的 REST 接口、JavaScript 或 AJAX、Smarty 模板、Drupal 中的 Drush 模块，甚至通过创建其他语言（如 Perl）的标准包装器来调用。根据您的访问方式，您需要相应地调整带有相关参数的函数调用。有关通过这些不同方法实现 API 的更多详细信息，请访问上面提供的 API 链接。

## 社区与合作

核心团队和许多活跃的开发者也经常在 IRC 频道上交流，那里是提问并获取专业答案的好地方。与任何实时聊天室一样，IRC 频道在全天不同时段会有不同的活跃用户数量，以及他们是否有空帮助您解决问题。因此，如果对话看起来很冷清，不要放弃——稍后再来，看看是否有人在。

您可能还想熟悉公共问题跟踪器（http://issues.civicrm.org）。开发团队使用它，并向社区开放，用于跟踪 bug 和功能请求。

如果您遇到看起来像是软件 bug 的问题，请不要立即创建新问题单。它可能只是您的 CiviCRM 实现所特有的问题，也可能是已经被报告甚至已在较新版本中修复的 bug。一个很好的起点是在 http://forum.civicrm.org 上搜索相关帖子。如果找不到任何内容，请尝试在 http://demo.civicrm.org 的演示站点上运行的最新稳定版 CiviCRM 上重现该错误。然后将您的问题发布到相应的论坛，附上收到的错误消息文本、发生问题时您在做什么，以及您是否可以在演示站点上重现该问题。几小时或一天内，您可能会得到有用的回复。可能是建议的修复方法或变通方案、wiki 相关页面的链接，或者要求您在 bug 跟踪器上创建新问题。

如果您能够解决发布到论坛上的问题，最好在话题中更新最终有效的解决方案，以帮助其他可能遇到同样问题的人，并向帮助您的人提供反馈。请记住，他们也是人。许多在论坛上提供帮助的人并没有因为在那里花费时间而获得报酬。一句“谢谢”和尊重的语气对获得帮助大有帮助，而粗暴、自以为是的语气更可能遭到冷遇。

如果您花了一些时间弄清楚了如何做某件未被记录的事情，那么最好在 wiki 上写下您的做法。这不仅会帮助您在六个月后再次需要时记住如何做，也会帮助其他人。其中一些人甚至可能为您的修改提供额外的改进。

论坛不仅仅是用来询问潜在 bug 的。它们也是询问如何做事的好地方。请尽量具体地描述您的请求，说明您已经尝试过哪些方法，并谈谈您正在考虑用什么可能的方法来满足需求。

一种日益流行的学习和分享 CiviCRM 经验的方式是本地聚会。这些相对非正式的活动通常包括演示某地区的人们如何使用 CiviCRM，可能还有一些技术讨论，以及聊天和提问的机会。到目前为止，世界各地的城市都举办过聚会，包括柏林、波士顿、布里斯托尔、布鲁塞尔、布法罗、芝加哥、达拉斯、沃斯堡、德累斯顿、都柏林、日内瓦、伦敦、蒙特利尔、孟买、纽约、旧金山、西雅图、台北、多伦多、华沙和华盛顿。请查看 http://civicrm.org，看看附近是否有聚会，如果没有，可以考虑发起一个。

核心团队和越来越多的其他提供商还举办用户、管理员和开发人员培训活动。还有过几次代码冲刺（code sprint），第一次 CiviCon 于 2010 年在旧金山举行，第二次于 2011 年 3 月在芝加哥举行。面对面的交流为在线社区空间中的分享和社交提供了宝贵的人际维度。最有价值的互动和学习通常发生在走廊里和举杯交谈中。

由于这对您和社区都有好处，我们强烈鼓励您以任何您觉得舒服的方式参与。可能是在 wiki 上查找建议、在论坛上发帖提问、参加聚会，甚至参加培训营。许多人发现他们投入的时间和精力是值得的。

您可能还会发现，在某个时刻，您希望看到 CiviCRM 添加某个功能或进行一些调整。http://civicrm.org/contribute 列出了当前的 Make It Happen 倡议，社区成员可以通过捐款来资助改进和新功能的开发。有能力的人还可以为新倡议提供 50% 的种子资金，以帮助其启动。
