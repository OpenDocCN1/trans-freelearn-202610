## 分析工程：数据工程的新核心

在本章中，我们将理解数据的完整生命周期——从数据在运营过程中产生，到最终被业务用户消费。在这一过程中，我们将分析从原始数据到信息这一数据转化各阶段最重要的细节。

这将帮助我们理解，为什么分析工程——即我们使用 dbt 工作时所聚焦的数据旅程环节——除了仍是数据全生命周期中最富创造力和趣味性的部分之外，已经成为数据工程项目中的关键组成部分。

分析工程将来自公司各个异构数据源的原始数据转化为信息，这些信息可直接用于分析师和业务人员使用的工具，帮助他们获得洞察并支持数据驱动的决策。

随后，我们将讨论现代数据栈以及数据团队如何更好地协作，定义现代分析工程学科和数据团队中的角色，并特别关注分析工程师这一角色。

在本章结尾，我们还将探讨软件工程的最佳实践，这些实践可以帮助使用 dbt 在现代数据栈上工作的数据团队编写更好的代码、更加从容、不再疲于应对突发问题，并向利益相关方提供更好的数据。

- 数据生命周期及其演进
- 理解现代数据栈

## 数据创建

通常，我们可以确定数据创建的三种主要数据源类型：

- 运营系统，包括**企业资源计划（ERP）**软件以及各类业务系统，更不用说 Excel 文件，它们仍然是许多业务流程的基石。最有价值且易于使用的数据通常产生于运营系统，运营人员开展日常运营并生成与公司运营保持一致的数据。

- 生产系统，包括监控生产现场的 IoT 系统。

  这些系统可以产生大量非常底层的数据，通常使用专门的或行业特定的格式，使得这类数据与公司的业务思维相去甚远，且不太容易使用。

- 在线系统，包括营销和网站，可能产生大量数据。这些系统可以产生高层次的、易于使用的数据，例如在线销售和支付，以及大量关于用户行为的低层次数据，这些数据需要复杂的分析工具。这是机器学习的应用领域之一，用于理解和预测用户行为。

理解我们使用的数据源至关重要，因为数据的速度和结构化程度是决定如何移动和管理数据的关键因素。

你可以理解，处理高容量、半结构化的 Web 数据、来自**变更数据捕获（CDC）**的结构化 ERP 数据以及不稳定的 IoT 数据是非常不同的。

在本书的第二和第三部分，我们将看到管理不同类型数据的模式。

## 数据移动与存储

如果我们所使用的源系统不提供所需的分析工具，或者我们需要将这些系统的数据与其他系统的数据集成，我们面临的第一个障碍是如何将数据从这些源系统移动到可以进行分析的地方。

如果你的源系统足够标准、足够通用，以至于受到一个或多个数据提取工具（如 Fivetran、Stitch 或 Supermetrics）的支持，那么你可能会很省心，只需配置工具即可让数据流动起来。

在那些你不够幸运，没有现成工具可以快速可靠地为你移动数据的情况下，你需要设计自己的数据移动方案，并考虑以下方面：

- 如何从源系统提取数据
- 如何将数据从源移动到存储位置
- 长期在哪里以及如何存储提取的数据

在这三个主要操作中，有很多细微之处需要考虑，我们将在接下来的章节中讨论。

### 从源系统提取

最理想的情况是，源系统被设计为提供数据甚至其状态的外部可观测性，而无需处理系统内部。这意味着系统将其变更发布在一个易于读取的地方（通常是队列）。在这种情况下，我们不会有丢失任何变更的风险，也不必急于获取数据，因为所有数据都在那里供我们读取，并且会保留一段时间。

如果我们能够接入**数据库（DB）**的日志系统，我们也能达到同样的效果，因为数据库本身会将所有正在执行的变更写入其中。

如果源系统在设计时就考虑到了数据导出，那么从源系统提取数据可能很简单；但如果源系统是一个复杂的应用程序，没有构建外部接口，而且可能文档也很少，那么提取数据可能会很困难。

在所有这类情况下，即使我们可以完美地复制数据库表，表本身的设计或应用程序逻辑可能很适合外部可观测性，因为如果不按照应用程序自身的规则进行解释，数据本身可能处于不一致状态。

一个例子是，当系统删除已完成或不再有效的内容时，例如删除已取消的发票，但保留连接发票和订单的多对多表中的条目。

这是一个简单的案例，一旦你弄明白了；但其他案例更为微妙，所需的业务逻辑可能很难仅从数据中反向推导出来。

另一个常见例子是后续变更覆盖了自身，例如文档的不同状态。如果我们获取表的变更（快照）不够频繁，就会错过中间步骤。这可能不是问题，但应该被知晓，因为数据平台将无法提供所有的历史变更，也无法解释在现实世界中观察到的所有行为。

在下面的列表中，我们描述了最常见的提取类型：

- **基于事件的可观测性**：这是指系统本身发布被认为对外部应用有用、需要其知晓的变更。如果设计得当，我们可以保证不会丢失（重要的）中间步骤，并且不存在逻辑不一致。一个特殊情况是，事件不仅仅是数据变更事件，而是*业务事件*，即具有业务意义、定义明确的事件，例如创建订单或接受付款。事件的语义与业务流程相关联，这为事件数据提供了额外的上下文，其信息通常还可以用于最初设计事件时未考虑到的额外用例。

- **变更数据捕获**：这是指我们可以连接到数据库日志或源系统的其他事件流。虽然我们可以确保不会丢失任何中间变更，但仍然可能存在逻辑问题，因为表可能不是为外部系统访问而设计的。这是一个非常常见的用例，能够提供良好且可审计的数据，但我们必须警惕不一致的数据。

- **应用程序编程接口（API）**：另一个非常常见的用例是系统提供 API，我们可以用来从系统读取数据。如今，这些 API 往往是 REST API，以 JSON 格式提供数据；而在过去，大多数 API 以 XML 格式提供数据。

  在这种情况下，很大程度上取决于 API 设计的质量。最常见的问题源于 JSON 和 XML 可以表示嵌套结构，且关系在嵌套中一目了然，而 SQL 表只能表示扁平结构。要在 SQL 中表示嵌套结构之间的关系，我们需要至少两个表和一些键。如果我们希望能够随时间管理这种关系，我们需要 JSON 或 XML 中两种结构的键；否则，我们就无法确定组成关系的每个表中的哪些结构应该添加、更新甚至删除。

- **数据库快照**：这是另一种非常常见的方法，即在特定时间（无论是定期还是按需）从源系统导出数据，可能包含所有数据（全量数据导出），也可能只包含最新数据（自某个已知时间以来创建或更改的数据）。“快照”这个名称提醒我们，数据是特定时间点的“原样”数据。




使用快照时，我们可能会遇到两类问题：我们无法观察到两次快照之间发生并被覆盖的中间变化；虽然我们拥有特定时间点的各个表，但可能会出现逻辑不一致。

如果导出的是全量数据，我们可以追踪删除操作；但如果只导出变更数据，则无法做到这一点。

## 提取数据的临时存储

在上一节中，我们看到从源系统检索/提取数据的方法有很多种。其中一些方法可以直接将数据传输到数据平台的永久存储中，但在许多情况下，提取的数据会在中间存储中保存一段时间。

这样做可能是为了在多次尝试移动数据时保持数据可用，也可能是因为在系统间移动数据的工具与提取数据的工具不同。

以下列表简要讨论了提取后数据最常见的存储方式：

- **直接在数据平台中**：将数据直接存储在目标系统中，无论是直接存储在表中，还是存储在数据湖的文件中，都是最简单、最干净的方式，因为执行提取的工具同时也在系统之间移动数据。

- **文件**：这是最常用也最古老的数据移动方式。包括数据库在内的许多系统都有将数据导出为文件的方式，通常是 CSV 文件，也有 XML 或 JSON 文件。

    当从 API 读取数据的工具不负责将数据传输到目标系统时，这也是一种常见的中间格式。在本地系统环境中，由不同系统分别执行提取和传输是很常见的，但如今这种情况已越来越少，在云应用中更是罕见。

- **队列系统**：当源系统被设计为提供外部可观测性，并自行发送有关其状态或事件的消息时，将数据存储在 Kafka 等队列系统中非常常见。队列用于存储传输中数据的另一个常见场景是物联网或实时场景，队列中存储的数据可被多个系统访问，而数据平台只是这些数据的目的地之一。

## 源系统与数据平台之间的数据移动

在考察数据的实际移动时，我们需要关注两个维度：移动是如何编码的，以及数据在传输过程中发生了什么。

以下是数据移动编码的常见方式：

- **数据移动/加载工具**：随着许多应用程序和服务迁往云端以及在线营销的兴起，能够直接从 API 提取数据的工具大量涌现，这些 API 由众多云应用和数据库提供，用于将数据移动到 Snowflake 或 BigQuery 等云数据平台。

    Fivetran、Supermetrics 和 Funnel 等工具从诞生之初就面向营销部门，而 Stitch Data 等其他工具则从 IT 部门/ETL 的角度来处理数据移动问题。它们最终都提供了易于配置的接口，可从数百种常见云服务中检索数据，非技术用户无需学习 API，也几乎不需要配置访问参数之外的内容即可轻松下载数据。

- **ETL 或数据科学工具：** 使用 Matillion、Talend 或 Informatica 等 ETL 专用工具，或 Alteryx、Dataiku 等数据科学工具，是利用现有工具移动数据的有效方式，因为这些工具为处理文件和表中的数据提供了广泛的可能性。使用这些工具时，需要有人编写代码，或使用可视化界面绘制转换逻辑，然后由工具生成/执行。

- **直接编码：** 当有强大的 IT 部门且没有适合该目的的既定工具时，使用 Python 或 Java 等通用编程语言直接编码是一种可能的选择。在本地环境中仍常见的一种方法是使用 Shell 或 Perl 等脚本，配合 FTP 或临时构建的可执行文件等常见的 Unix 风格工具。

我们将上述工具类别列为处理数据移动的现代方式，但归根结底，你可以选择任何能够满足需求、且无需人工干预即可无误移动数据的方式。

数据移动的第二个维度涉及数据在移动过程中的变化。可选方式如下：

- **数据在移动过程中被转换：** 这就是所谓的“老派”方式，称为 **ETL**，代表 **提取、转换和加载**。在数据从源系统移动到目标系统的过程中进行转换，在数据量有限、数据库面向行、速度慢、部署在本地且内存和存储受限的情况下，是合理的做法。

    如今，若考虑逻辑转换，这种方式已不那么常见，但在处理提供 XML 或专有数据格式、甚至是复杂 JSON 格式（不适合轻松导入目标平台）的旧系统时，进行格式转换并不少见。

- **数据在移动过程中保持不变：** 这是云时代数据仓库的现代方式，称为 **ELT**，代表 **提取、加载和转换**。

    这种逻辑转变远不止是交换操作顺序，因为新范式是将数据原样加载到数据平台上，然后再进行转换，充分利用现代极为强大的数据库，这些数据库能够提供海量内存、几乎无限的存储和线性可扩展的性能。

在使用 dbt 时，你将在数据迁移后开始处理数据。你可以使用移动数据的工具来开始数据转换，但我们的建议是尽可能保持数据不变，并尽可能接近其在源系统中的状态。

虽然进行任何必要的格式转换是可以的，但我们建议不要在数据移动过程中应用任何业务逻辑。这将尽可能保留原始数据，使其接近操作型系统的记录方式，不受会随时间变化的业务规则的篡改。

尽可能少地改变既简单又快捷，它将为你提供几乎未经修改的数据，这些数据适合对源系统进行良好的审计，并且可以被信任来讲述真实情况，而不是当时业务规则所解读的情况。

保持事实不变，并在后续过程中构建解读。

## 数据平台中的初始存储与永久存储

从源系统提取数据后，你需要将其移动到某个位置，以便以简单有序的方式供数据平台访问，这意味着人们可以轻松找到所需的数据，并且能够获取其有权访问的数据。

当我们讨论刚提取完的数据移动时，这些仍然是相当原始的数据，因此这里所说的“人员”指的是数据架构师、数据科学家和分析工程师，他们将以更持久的方式存储这些数据，并将其转化为信息。

好消息是，从技术层面看，虽然名称众多，但初始和永久存储基本上只有两种选择，而且它们通常简单、便宜，并且彼此相差不大。

在技术层面，永久存储的两种选择是文件或数据库表。

以下是对这两种选择的简要讨论：

- *文件* 是半结构化数据（如 JSON 或 XML，其模式内嵌在数据中且不固定）或非结构化数据（图像、视频、音频、文本文档或几乎没有模式的日志）的首选。

    这类数据也可以存储在数据库中，但可能与数据库结构不太匹配，并且使用 SQL 和典型数据库代码对其进行处理的能力有限，因此最好将其保存在文件中，这样既能保持数据完整，也符合处理此类数据的工具和库的预期格式。

    这种方法通常被称为数据湖，最初之所以这样命名，是为了描述其缺乏固定、标准化结构却能容纳海量数据的特点。尽管缺乏固定、标准化结构的情况依然如此，但如今云数据库能够以相当的价格存储同样数量的数据，因为归根结底，这些数据与你的文件存储在同一个云存储中。

    现代云数据库还允许我们使用 SQL 很好地管理半结构化数据，从而在使用 dbt 处理此类数据时更加得心应手。



- 本书将采用的方式是尽可能以源系统中的原始形式存储数据，保留数据和关系，并明确标识业务键（也称为自然键），这些键将在后续层中用于驱动系统间的集成。
- **存储精炼数据：** 在Kimball架构中，其理念是将传入数据转换为事实表和一致性维度，对传入数据应用必要的业务规则，使其符合某种约定的方式来表示所需信息。虽然将事实表和维度作为数据平台的最终层来支撑报表几乎已成为常态，但我们并不建议像Kimball架构所倡导的那样将事实表和维度作为主要数据存储，因为那些结构中的数据可能已经远离原始数据，经过多次复杂业务规则的应用而发生了改变。需要重申的是，在业务规则出错或变更时，追溯到原始数据可能非常困难，甚至不可能。

我们对此的建议是尽可能“原样”移动和保存原始数据，仅执行非常重要的任务：通过清晰命名和测试主键、业务键及其变化方式，来正确识别概念及其身份，因为这是正确存储历史数据的三个关键方面。

事实上，如果你希望能够识别并存储某个概念的变化，你需要知道该概念的实例是什么，以及如何区分该概念的两个实例是同一概念实体的两个版本，还是两个独立的实体。

例如，能够识别“Person”表中的两行是关于两个不同的人，还是同一个人的两个版本（即同一个人经历某些变化后的状态），这一点至关重要。

## 数据转换

一旦你将原始数据从源系统移动到数据平台，并以保留所有所需历史数据的方式存储，这些数据很可能还远未达到可用于报表的正确格式。

正如我们在上一节中所见，你很可能先将数据以某种初始位置和格式落到平台上，再以另一种位置和格式永久存储，最后生产出业务用户通过BI工具使用的内容。

这使我们能够为你的数据识别出以下三个主要层次：

- **原始数据：** 这是最初加载到数据平台上的数据，即其在源系统中的状态，或由迁移工具传输过来的状态。
- **历史数据：** 这是你决定以何种方式、在何处保留数据的完整历史。尚未应用任何业务规则。它仍然与源系统中的形式非常相似。
- **精炼数据：** 这是为报表或其他用例（如机器学习或人工智能）准备好的数据。这是你通过应用所有必需的通用业务规则和特定于用例的业务规则所生成的数据。

dbt的核心功能是帮助你管理这些层次之间的数据转换。以下是对这两个步骤的描述：

- **存储转换：** 将落地数据准备好以进行持久化历史存储。

  这些转换具有一定的技术复杂性，但它们相当常见且重复性高，以至于大部分过程都可以自动化。我们将看到如何使用dbt及其宏来实现这一点。

  在此步骤中，列名应改为使用业务名称以创建通用词汇表，但应用于数据的转换应仅是技术性的，不应改变数据本身，而只改变其格式、添加处理过程中可用的元数据以及添加计算字段。

  示例包括从文本中解析日期和数字、计算哈希键和哈希DIFF字段，以及用于将传入数据存储到历史中的实际代码。可以执行诸如移除填充零和空格等操作，但在这一层，原始源数据应被保留，并在每次数据变更时存储到历史中。

- **主数据和业务规则转换：** 从持久化历史中获取数据，并使其为报表做好准备。

  这是我们应用大部分数据转换的地方，从主数据映射到各种各样的业务规则。

  这是数据工程师工作中的“创造性”部分，最佳实践、指导原则和经验可以帮助你找到好的解决方案并避免死胡同，但你个人的见解至关重要。

  毕竟，业务规则的发现和应用是构建数据平台中最复杂的事情，而且仍然是专家级专业人士能够带来巨大价值的领域。

在本节中，我们开始展示我们认为最适合dbt和Snowflake等现代工具的思维方式，并且根据我们的经验，这种方式能为构建云数据平台的公司带来最大的价值。

我们将多次涉及的一个关键概念是，必须放弃一些更传统的数据仓库方法，转而采用更简单的方法，这些方法如今凭借云平台强大的功能和低廉的成本而变得可行。

一个例子是使用基于序列构建的代理键。当数据库处理数字键的能力远强于文本键，且无法并行工作时，代理键是不错的选择。如今，基于键类型的差异几乎不存在，云数据库可以利用并行性让你的查询快得难以置信，因此使用自然业务键或通过哈希构建的代理键（它们能很好地与并行性配合）要好得多，并且要不惜一切代价避免使用序列，因为序列会扼杀键生成和查找过程中的所有并行性。

另一个例子是增量加载；要做到正确，它们比提供所需转换的简单查询复杂得多。差异在于增量加载依赖于当前执行之前发生的状态和历史（包括失败）。如果出现问题，你必须修复数据，否则你的数据将不一致，因为它将构建在未修复的数据之上。

当你必须购买数据库服务器时，你往往最终会选择能满足需求的最小、最慢的服务器，因此小且慢的数据库加上缺乏并行性，自然无法一次性处理你的所有数据。那时，我们被迫将增量加载作为性能工具，一次处理更少的数据，这使得转换更复杂但更快。

如今，借助提供极其强大配置的云平台，我们能够避免将增量加载作为性能工具，并且可以构建更简单的转换，这些转换构建更快、更容易理解、错误更少，并且维护工作量大大减少。想想看，你不需要处理之前任何一次运行中发生了什么，只需关心你的代码做了什么。

## 业务报表

构建数据平台的主要目的是提供可用于支撑报表的精炼数据，而报表反过来又能驱动良好的决策。

如今，我们有两个主要用例：经典业务报表（通过对源数据应用业务规则得出）和高级分析（包括机器学习和人工智能生成的报表洞察）。

在两种情况下，我们可能都需要按照Kimball维度模型向最终用户提供数据，这意味着使用事实表和维度。虽然我们不建议将这些产物作为永久存储，但它们是提供报表数据的标准方式。

最常见的交付方式是为每个报表域（如营销或采购）构建一个数据集市，有时还按国家或地区划分。数据集市是提供所需事实表和维度的表和视图的集合。

为了提高一致性并避免返工，我们建议你实现一个通用的精炼层，以表的形式存储应用主数据和通用业务规则的结果，同时将各个数据集市实现为从精炼层读取数据并最终添加该报表域特有业务规则的视图集合。




机器学习和人工智能流程可以使用完整历史或精炼数据作为输入数据，并生成更精炼的数据，这样就能自然地将其添加到所需的数据集市中。

## 反馈回源系统

数据流中最后一个可能的步骤，是关于数据平台中生成的数据以及在其他系统中使用这些数据的需求。

一个常见用例是将数据平台中计算出的某些数据带回到某个运营系统。这在营销和 CRM 领域非常常见，数据平台可用于计算客户细分以及各种度量指标，然后需要将这些指标反馈回营销工具和 CRM 平台。

另一个日益常见的用例是，某些机器学习流程正在为运营系统构建有价值的数据，例如销售预测或预测性维护数据。

在所有这些情况下，我们可以采用与之前将数据从源系统移动到数据平台时相似的思路来处理该主题，但一个很大的区别是：许多系统提供了某种导出的方式，却几乎没有提供任何导入数据的方式。

即使目标应用程序确实有加载数据的 API，数据加载器也很少具备同样广泛的回载数据能力。

不要绝望，因为有一些工具专注于“反向 ETL”流程，即把数据从数据仓库移回业务工具/运营系统，例如 Census（可在 `https://www.getcensus.com/` 获取）。

数据平台中生成数据的另一种情况是：使用 BI 工具的人员可以在 BI 工具的报表中编辑数据，并以某种方式将其发送回数据平台本身。这通常被称为 BI 工具中的写回功能。

一些示例用例包括：人们可以使用 BI 工具输入缺失信息或在特定报表中提供更新值，例如管理库存水平或更新预测。

在这种情况下，更好的做法是将从 BI 工具写回的新数据视为数据平台的新输入，并将其作为转换链的一部分进行集成，而不是直接修改为报表提供支持的数据集市。这同样符合让数据变更可见的精神，并且无需处理先前的状态即可从头重现最终结果。

现在我们已经探索了数据生命周期及其演变，接下来将继续学习现代数据栈，它使数据工程变得更加顺畅。

## 理解现代数据栈

当我们谈论数据工程时，我们涵盖了端到端覆盖数据生命周期的所有技能、工具和实践，如上一节所述，从数据提取到用户数据消费，最终还包括数据写回。

这是一套庞大的能力和工具，从安全到脚本和编程，从基础设施运维到数据可视化。

除了非常简单的情况外，单个人能够对所有涉及领域有透彻理解和良好技能来完全覆盖这一切，是相当罕见的，更不用说还有时间去开发和维护了。

### 传统数据栈

传统数据栈通常由数据工程师构建，他们开发临时的 ETL 流程，从源系统提取数据，并在本地转换，然后以精炼形式加载到用于支撑报表的传统数据库中。这被称为 ETL 管道。

该过程包括创建一些临时集成来从源系统提取数据，确定要提取的内容，并设计提取逻辑。通常，它还包含所需的数据转换（包括汇总），最后才将“已消化”的数据加载到用于报表的普通数据库中。

使用 MySQL 或 SQL Server 这类事务型数据库进行报表会带来巨大问题，需要各种技巧才能实现报表功能。主要问题在于，这些数据库针对与表中的整行数据进行交互的大量小型操作进行了优化。它们是面向行的。

事实上，分析工作恰恰相反：它需要对大量数据执行少量查询，而且通常只使用少数几列，而不是所有列。为了解决分析工作负载的需求，列式数据库应运而生，但在 2000 年代的头十年，它们并未被广泛了解，而且与“常规”面向行的 OLTP 数据库相比，它们仍然相当昂贵。

使用传统 OLTP 数据库时，最容易出现问题的折衷之一是在将数据加载到报表数据库之前应用业务规则和数据汇总。这造成了一种局面：源数据或业务规则的任何变化都会影响整个数据历史。这反过来又要求修复转换逻辑以及现有数据，以符合新逻辑。如你所见，这是双倍的工作，而且也很可怕，因为你必须修改历史数据的唯一副本。

另一个问题是，工具的大小和功能都受到限制，编写集成并保持其运行的时间也同样有限，因此通常只加载真正需要的数据，而且往往只保留有限的时间段。

数据分析师会从数据库获取已加载的数据，为最终用户构建报表和仪表板，并偶尔对数据的某些方面进行深入分析。

即使在这些深入分析中，他们也只能使用已有的数据：如果某些内容被过度汇总，他们除了请求重新加载之外别无他法；如果某些有用数据不可用，他们也只能再次请求数据工程师通过创建另一个 ETL 管道来添加数据。

难怪最终用户常常需要等待新数据被添加，或者只能从可用数据中获得部分答案。

数据工程师和分析师之间的工作分工，也使得数据分析师更难以充分理解数据及其局限性，也让数据工程师更难理解他们交付的数据的使用情况与质量。

通常，几乎没有测试或数据质量检查，导致数据团队在数据生命周期的两端持续“救火”：源系统中不断变化/缺失的数据，以及报表中过时/错误的数据。

另一点是，鉴于维持 ETL 管道运行的技术难度以及数据工程师与业务问题之间的距离，通常更多的精力花在了让数据流动上——这是一个传统且客观、无人能质疑的指标——而不是理解数据和确保其质量上。

### 现代数据栈

快进到 2010 年代中期，我们发现自己的处境好多了：

- 云上的分析型数据仓库，例如 BigQuery、Redshift 和 Snowflake，越来越普遍，并且对大多数数据团队来说已成为可负担的选择
- Stitch 和 Fivetran 等数据移动/集成工具，可以非常轻松地将数据从传统数据库和常见业务平台移动到云数据仓库
- 现代 BI 工具开始提供改进的自助式报表能力，供高级用户使用

云数据仓库的出现是一个转折点，它提供了海量的存储和处理能力，而无需预先购买容量。

在用户侧，这使公司能够将大量数据加载到这些云**数据仓库（DW）**中，并以更快、更便宜的方式处理数据，成本仅为本地系统的一小部分。

在商业侧，这促进了数据移动工具的创建和兴起，使得从最常用的系统（如传统 DBMS 以及运营和 SaaS 软件）快速、轻松地将数据加载到这些标准云 DW 之一成为可能。

采用这种现代数据栈，可以轻松地将来自源系统的原始数据加载到云 DW 中，从而减少了数据工程领域最复杂、最耗时的工作需求。




拥有一种只需在短时间内设置好就能将数据送到你的数据仓库（DW）的工具，使得一个人就能负责源系统的数据生命周期的全部或大部分工作，前提是这些源系统可以用数据移动工具来管理。它也解决了学习并跟上这些丰富但经常变化的 API 的需求，因为这现在已成为数据移动工具开发团队的问题。

如今，你只有在没有工具可以自动化数据移动时，才会作为最后的手段创建临时管道。

原始数据易于获取，促进了下一个问题的产生：我们如何改进转换阶段并使其有效？*这正是 dbt 被创建来帮助解决的问题。*

我们将在下一节中对此提供更多细节。

数据栈中的另一个巨大变化是，将尽可能少的逻辑放入报表工具中并保留在 DW 中，以便你只需编写和管理一次，它就可以为每份报表和每种其他用途提供服务。这之所以成为可能，是因为随着运行 ETL 管道所需的编程和基础设施减少，负责转换的工程师拥有更好的 SQL 和仓库技能，而现代工具如 dbt 使直接在转换中编写和测试业务逻辑变得更容易。

现在我们已经描述了传统和现代的数据栈，让我们深入探讨 dbt 的核心：作为一个敏捷团队，将原始数据转换成语义信息。这就是分析工程的核心，我们将在下一部分讨论。

## 定义分析工程

我们在上一节中看到，随着现代数据栈的出现，数据移动变得更容易，因此重点已转向管理原始数据并将其转换成语业用户在报表中使用的精炼数据。仍然存在大量需要临时集成和 ETL 管道的案例，但这不再是数据团队的主要关注点，就像过去一样。

另一个哥白尼式的革命是，新的数据栈使数据专业人员能够作为团队工作，而不是延续在传统数据栈中常见的孤立工作。重点现在是应用软件工程的最佳实践，使数据转换开发像构建软件一样可靠。你可能听说过 DevOps 和 DataOps。

随着重点的转移，术语 **分析工程** 出现了，用以标识从访问原始数据到将精炼数据提供给 BI 报表工具的数据生命周期中的核心部分。这并非巧合，因为这也是云 DW 平台和 dbt 所覆盖的数据生命周期部分。

以新的眼光审视数据生命周期，我们可以将其分为以下几个部分：

- **数据集成：** 通过尽可能使用现成的工具将所有数据收集到一个地方，即云数据平台，并在需要时求助于临时数据管道。
- **分析工程：** 将原始数据转换为精炼的、可用的、可信赖的数据。这就是你使用 dbt 所做的工作，使用你偏好的数据平台，在我们的案例中是 Snowflake。
- **数据分析：** 使用精炼数据构建报表、仪表板、机器学习模型等。这是在你的 BI 工具中完成的工作，以使数据对业务用户可访问。

这三个阶段与我们在上一节中看到的并没有太大不同。不同之处在于，在现代数据栈中，我们现在有了与现代工具相一致的清晰边界，这对从事其中的专业角色产生了影响。

## 现代数据栈中的角色

将数据生命周期划分为这三个步骤后，这些是在使用 dbt 和云 DW 的现代数据团队中所属的专业角色：

- **数据工程师：** 拥有脚本/编码和基础设施知识的“传统”数据工程师仍然非常有价值，尤其是当并非所有数据源都能被现代数据加载工具覆盖时。即使在这种情况下，复杂的日程安排、安全性和许多其他主题可能仍需要数据工程师的专业知识和专注。
- **分析工程师：** 一个新角色，牢牢围绕了解并将原始数据转换为有用信息。他们不太关心数据移动管道的开发，而是专注于使数据可用、可使用且可信赖。
- **数据分析师：** 这是传统数据分析师的改进版本，因为现在他们可以理解甚至帮助构建数据模型，并且能够调查更广泛的数据集的能力前所未有。

虽然清楚地区分这三个角色是有意义的，但重要的是要注意它们有很大重叠，核心能力围绕 SQL 和数据素养。

现代数据栈甚至使得拥有一个人的数据团队成为可能，如果你可以在无需编写和照看一个或多个数据管道的情况下移动数据，并且你的业务逻辑不是 constantly 变化的，因此现有的数据模型和报表不需要频繁更改。

## 分析工程师

我们看到分析工程师有点像数据工程师，在收集和理解原始数据方面，又有点像数据分析师，在了解如何创建能够实现良好分析的数据集方面。但该角色的核心是使用允许软件工程师生产和维护可靠软件的最佳实践来转换数据为信息。

从旧栈到新栈的主要变化是，能够并且需要从个人工作转向团队合作，以使用为传统软件工程创建的心态和强大工具来用于数据工程。

构建数据平台的方法变得更类似于构建软件，认识到即使在数据世界中，你也可以构建模块化模型，并且可以通过使用通用、可重用的模型来组合复杂的数据集，就像在构建软件时重用软件组件和库一样。

分析工程师组织数据转换及其依赖关系，就像软件工程师设计应用程序一样，使用可重用模式，并应用关注点分离，以最大限度地减少因多种不同原因而更改模型的需求。

分析工程师的工作不仅仅是编写执行从原始数据到信息的所需转换的 SQL，还要应用或发现模式来分解、结构化和以有意义且可重复的方式组织转换，使用清晰的命名，以便团队中的每个人都知道这些转换的每个步骤可以预期什么。

在下一节中，我们将讨论可以从传统软件工程中采用的最佳实践，以改进数据项目。

## DataOps – 数据的软件工程最佳实践

事实是，许多数据团队曾经、现在仍然不是由具有软件工程背景的人组成，因此他们错过了采用属于 DevOps 的现代软件工程技术。

名副其实，DevOps 运动为软件开发领域带来了巨大改进，帮助团队变得更具生产力并对工作更满意。

简而言之，DevOps 的核心思想是为团队提供所需工具，以及对整个开发周期的权限和责任：从软件编码到质量保证（QA），到发布然后运行生产操作。

实现这一目标的基石是使用自动化来避免手动执行重复性任务，例如发布和测试，强调自动化测试，依赖主动自动化监控，最重要的是，团队对代码的共同所有权。

这些思想通过四眼原则得到体现，要求每段代码至少被两个人看到并批准（通过结对、拉取请求或代码审查），以及童子军规则，该规则促使你在触碰一段代码时确保它比你触碰它之前处于更好的状态，无论是谁编写的，从而随着时间的推移改进工作。





另一个重要概念是主动管理技术债务。虽然代码库的某些部分即使未达到标准也可以发布，这很正常，但必须出于真实的权宜原因，并且团队必须在权宜原因过去后偿还这笔债务，修复质量较低的代码。

在以下小节中，我们讨论一些软件工程最佳实践，它们可以帮助数据团队以更令人满意的方式工作。

请注意，这些实践与 dbt-labs 创始人 Tristan Handy 在开始开发 dbt 时发表的一篇开创性文章中提出的观点非常一致。你可以在以下网址阅读 Tristan 的 2016 年文章：https://blog.getdbt.com/building-a-mature-analytics-workflow/。

## 版本控制

拥有一个中央仓库，将所有代码存储并组织好供所有人访问，并清楚了解版本的更迭，这已经比许多将 SQL 文件保存到共享磁盘、通过文件名或文件夹名来维护版本的情况改进良多。

创建分支以独立工作，然后合并更改的能力，不仅可以实现功能的并行开发，还提供了一种安全的方式来尝试更改。

无论如何，采用代码版本控制不仅本身有用，也是实现许多积极流程的必要步骤。

版本控制系统（如 Git）成为集成中心，可以触发协作和自动化流程，例如以下这些：

- **拉取请求：** 这一强大功能允许团队查看开发人员提出的更改并发表评论，要求澄清并提出改进建议，同时跟上最新的更改。
- **自动化：** 当新代码被检入时，可以触发多种自动化，从分析新代码的代码质量工具，到自动化测试，再到持续集成和持续部署。
- **授权：** 尤其是在非常官僚或高度监管的环境中，版本控制系统可以作为审批的记录工具，使这一必要步骤变得简单。

## 质量保证

DataOps 的三大基石——所有权、自由和责任——在很大程度上依赖于团队拥有一个可靠的质量保证流程。

确保生产环境中的代码按预期工作、传入的数据符合预期的最佳方式，是每次发布新代码或加载新数据时都执行自动化测试。

现代数据栈允许你构建可复用的模型，因此你可以只编写一次客户模型，也许可以通过组合代表线上客户、门店客户和批发客户的底层模型来实现。所有这些模型都是有用的精炼模型，可以在多种场景中复用。

这里的关键是，技术和业务必须保持一致，以定义相关的业务概念，然后技术帮助实现这些概念，减少代码重复并促进稳定接口的使用。

我们将在 *设计可维护性* 一节中进一步探讨如何编写模块化代码。

## 开发环境

为了让开发团队能够快速迭代代码并开发和测试新功能，每个开发人员都必须拥有自己的环境，可以在其中工作，无需等待或与他人同步，也无需担心破坏任何东西。

能够在你准备好时自由运行代码，运行能在几秒或几分钟内给出可信答案的测试，或者能够在同样短的时间内销毁并重建你的环境，这些都是现代数据栈提供的基本能力。这些能力使开发人员能够专注于编写良好、干净的业务代码，而不是支持或附带任务，更不用说只是等待了。

相反，当开发人员必须在生产环境中尝试代码时，他们无法承受犯错的代价，因为失败会引发重大问题。结果是害怕更改任何代码，发布需要很长时间，因为每一个小更改都必须经过深思熟虑并权衡后果。

即使只有一个共享的开发环境，或者只有少数几个创建缓慢或昂贵、因此必须共享并精心维护的环境……结果也是相似的：害怕更改，以及由于浪费时间等待环境或因为开发环境不能反映真实环境而导致结果误导，从而失去动力。

毕竟，这应该并不令人意外，因为大多数人不喜欢排队等待，更不愿意在悬在高空的缆索上行走，无论有没有安全网。

个人开发环境是快速开发和测试新功能的关键推动因素。如果每个开发人员都要等半天才能尝试自己的代码，你怎么能每天发布甚至一天发布多次？

持续集成是提高开发流程速度和信任度的下一步，确保所有已开发的独立功能能够良好协同工作。它提供了另一个更强的信心水平，强化了所有发布的代码都经过团队审查和讨论的意识。

持续部署提供了最后一步，允许将在集成环境中测试过的代码发布到生产环境。这可以自动完成，也可以在手动提升代码后完成。

## 设计可维护性

我们把最重要的最佳实践留到了最后：在开发时着眼未来，即考虑演进和维护。

数据平台是生命周期最长的企业应用程序之一，因此当你编写一个数据平台时，可以确信它将长期使用。这意味着随着时间的推移，数据源和业务规则会发生很多变化，甚至更多的问题会围绕数据平台中管理的数据而产生。

这反过来又意味着很多人，包括未来几个月和几年的你自己，肯定会回来重新阅读那些代码。这就构成了为人类编写可理解代码的理由。

仅仅编写能运行的代码是不够的，就像把控制器半隐藏在一个难以触及的地方不是好的设计一样。设计你的代码，让下一个接触它的人会因为你把控制器放在易于看到和触及的地方而感谢你。

编写可维护的代码意味着编写容易被同事理解和更改的代码。通过将逻辑步骤分解为单独的**通用表表达式（CTE）**来避免冗长复杂的查询，以便为每一步提供适当的命名，并创建干净、可读的代码。保持模型在 100 行以内，连接数控制在两到三个，除非模型的唯一目的是连接多张表。

在这方面，Bob Martin 的经典著作 *《代码整洁之道》* 以及 Martin Fowler 关于架构、重构和敏捷的文章将是很好的指南；即使代码示例和主要讨论可能涉及 Java 和应用软件，这些思想也适用于每个编程环境。

性能和正确性是架构良好且表达清晰的代码的结果；它们绝不是编写晦涩代码或过于复杂逻辑的借口。

记住，代码越少，其中的错误就越少。

我们可能使用 SQL 或某种基于 Python 的脚本来表达逻辑，这一事实并不意味着我们应该满足于不够好的代码，而应该追求良好、可读的代码和清晰表达的业务逻辑。毕竟，如果代码易于理解，那么人类也容易验证其逻辑，并自动测试其行为是否符合预期；但如果代码晦涩或业务逻辑不清晰，情况就并非如此。

编写可维护代码的另一个关键部分是确保你的代码不必每隔一天就更改一次，并且当你需要更改时，它很容易更改。为此，我们可以借助整个软件工程知识体系，特别关注面向对象编程中的 SOLID 原则。以下是一些易于在数据项目中应用的原则：

- **SRP**：**单一职责原则** 指出，一个模型应该只有一个、且仅有一个更改的理由。在实践中，这意味着一个模型应该专注于做一件事，希望把它做好，并明确说明它做什么。这与那些一次性完成所有事情、甚至尽可能做更多事情的巨型查询正好相反。





- **OCP:** **开放/封闭原则** 指出模型应对扩展开放，对（接口）修改封闭。这意味着我们用作系统与模型之间连接点的模型，其所暴露的接口应保持稳定，同时也应易于扩展。在数据世界中，这很容易通过选择良好、经过业务验证且经得起时间考验的名称，并使用视图作为接触点来隔离消费者与底层存储精炼数据的表可能发生的变更来实现。
- **ISP:** **接口隔离原则** 指出客户端不应依赖于其未使用的接口。听起来很 trivial，但我们都见过拥有超过 100 列的客户维度。同样，在数据世界中，通过使用一个视图来提供对底层精炼数据的访问，仅暴露所需信息，而非“仅仅因为可用”而暴露所有内容，就很容易遵守这一原则。这样，我们就限制了未来变更导致某些字段不可用或语义改变时的“爆炸半径”。
- **LSP:** **最小惊讶原则** 指出模型应做其名称和在项目中的位置所暗示的明显事情。你应该能够正确猜测它所做的事情，并且在阅读其代码时不应感到惊讶。没有这一原则，你就无法信任任何代码片段而不必每次都重新阅读，使工作变得痛苦。

一个例子是，你不会期望数据仓库中的视图从原始数据源读取，也不会期望一个应用了主数据映射的模型同时计算一些无关的指标。

在讨论这些原则时，我们已经尝试将措辞和示例适配到数据世界，因此你可能会发现它们与应用软件开发的等效定义略有不同。

除了这些总体原则之外，还有其他软件工程原则，如抽象、封装和继承，虽然不能直接映射到数据/SQL 世界，但可以提供良好的灵感，例如使用视图来定义抽象（想想像基础客户或产品维度这样的通用接口，可以存在于许多不需要所有细节的通用数据仓库中）或封装（通过使用合适的名称暴露大表中列的子集）。

最后，项目的可理解性和可维护性很大程度上取决于非常简单的操作，例如采用简单、商定的约定，使每个人都能轻松弄清模型的位置或模型的作用，正如 LSP 所建议的那样。

可维护性的另一个重要主题是文档。请注意，过于详细且手动创建的文档往往会迅速过时，从而变得毫无价值甚至具有误导性。

在这里，我们想强调的事实是，大多数文档应是生成的，特别是对于经常变化的技术细节，如模型及其连接。

如果稳定的部分，如高层架构和模型或字段的描述，或报告或仪表板的总体描述，由人类创建是完全可以的。
