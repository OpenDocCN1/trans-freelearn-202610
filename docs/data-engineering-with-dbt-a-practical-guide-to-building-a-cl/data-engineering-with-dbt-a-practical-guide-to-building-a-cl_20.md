## 历史模式

在之前的章节中，我们已经了解了如何定义合适的 HKEY 和 HDIFF 字段，如何使用 `save_history` 宏来存储我们随时间看到的实体的版本，以及如何使用 `current_from_history` 宏从历史表中读取每个实体的当前版本。

我们还了解了如何将 `HDIFF` 字段用作版本标识符，在事实表中使用，当我们不仅关心当前版本，还希望使用具有所有历史版本的维度，即 SCD2 维度时。

在讨论如何从投资组合的定期活跃投资组合提取中计算我们的投资组合中的未平仓头寸时，我们引入了源数据中删除的问题，并创建了解决方案来检测删除以识别已关闭头寸。

`save_history` 宏的加载模式的一个重要警告是，它一次只能处理每个键的一个版本。通过在 STG 模型中使用 QUALIFY 子句并仅放行输入中最新的版本，可以轻松实现这一点。

这种解决方案编码简单、非常健壮且易于测试，但当我们需要保留更改的可靠审计时就无法使用，因为 QUALIFY 子句可能会删除一些中间版本。

在本章中，我们将讨论并提供可用的代码，以扩展历史表的使用，涵盖那些你想要跟踪源中删除的情况或需要保留收到的更改的完整审计的用例。

我们还将为你提供处理 **个人身份信息 (PII)** 并在保存历史表时遵循 **GDPR 合规** 的解决方案。

为了回顾，让我们看一下我们将涵盖的用例列表：

- 在识别完整导出中的删除的同时存储历史。
- 在接收显式删除的同时存储历史。在这里，我们将区分你接收到带有删除标志的完整记录还是仅删除实体的键。
- 在保留输入中的多个版本的同时存储历史（完整审计）。
- 在你有 PII 且需要 GDPR 合规时存储历史。

通过查看这一组宏，我们已经涵盖了你将面临的大多数实际用例，并为你提供了将这些宏适配到其他用例的能力，在这些用例中，所提出的解决方案不能直接应用。

### 存储历史并删除 – 完整加载

我们已经在示例项目中以某种方式介绍的常见情况是，当你没有提供关于删除的信息时识别删除。

### 存储历史并删除 – 删除列表

在上一节中，我们看到如果你有完整导出，你可以在没有进一步外部帮助的情况下识别已删除的行。它运行良好，但对于大表来说可能相当慢，因为你需要对两个相同大小的表进行两次连接。

为了避免庞大且昂贵的导出以及更大的连接，公司通常会配置其系统以提供有关哪些列已被删除的信息，即使这不是系统的原始功能。

你可以配置许多数据库以跟踪表中的更改（新行、更新和删除），并以某种方式使它们可用。

在其他情况下，当变更数据捕获功能不可用（或对组织来说成本太高）时，可以使用现有的数据库功能，例如触发器，来捕获表中的变更事件。

#### 删除时附带完整负载

我们讨论的第一个案例是，你接收到表的所有正常列以及负载的完整负载，外加另一个包含行状态（已删除 VS 活跃）或产生该行的操作（创建、更新或删除）的列。

在这种情况下，你可以将状态/操作列视为一个正常的负载列，并使用正常的 save_history 宏加载表，将该列作为表 HDIFF 列的一部分。

在这种情况下，我们建议在 STG 模型中添加一个布尔 DELETED 列，该列封装了识别行是否已被删除的具体规则。这有助于将有关导出和加载的硬规则封装在存储层中。

以这种方式处理删除检测是好的，因为我们回到了只有一个内容真实来源的正常情况。

一个特殊情况是，当你有一个初始或周期性的对账完整导出而没有这个额外的状态/操作列，以及更频繁的增量加载而具有此列时。

这里的“技巧”是认为完整导出为你在某个时间点存在的行提供了数据，并且你可以在 STG 模型中创建额外的列，同时将这些行指定为活跃或具有操作代码，该代码也可以有自己的值。

在下一节中，我们进入了同一个表的多个真实来源的领域，因此我们需要建立一个可靠的时间线，并在 STG 模型中最终设定一些优先级规则，以便为每个实体发送正确的行到 HIST 表。

#### 删除时仅有已删除键

当我们没有已删除行的完整负载而只有它们的键时，我们发现自己处于接近从完整导出删除的情况，但我们知道哪些行已被删除，而无需在输入中拥有完整导出，也无需执行昂贵的连接操作。

我们的解决方案将按通常方式加载来自输入的实体，同时我们使用历史和删除列表生成记录删除的行。

该宏具有以下清晰但非幂等的行为：

- 当实体在 `HIST` 表中被标记为已删除时，如果它存在于输入中，它将被再次添加。

- 当实体在 `HIST` 表中未被标记为已删除时，如果它存在于 `DEL` 输入中，它将被标记为已删除。

- 这两个输出的组合结果是，如果一个键同时存在于输入和删除列表中，结果将取决于其在 `HIST` 中的状态和版本：如果该键已被删除，它将被取消删除，而如果未被删除，结果将取决于版本是否相等。

作为示例，要消除这种情况，你可以通过在为历史表提供数据的 STG 模型中加入以下逻辑之一来优先考虑其中一个输入：

- 要优先考虑输入，必须从删除列表中移除出现在输入中的键

- 要优先考虑删除列表，必须从输入中移除出现在删除列表中的键

## 在输入中存储历史的多版本

到目前为止，我们每次只向历史中添加一个版本——来自输入的“最新”版本——因此很自然地，它要么与历史中已有的版本相同，要么是更新的版本。

在本节中，我们将介绍一种模式，你可以用它在一次加载轮次中加载多个版本，从而能够以任意速度加载数据并保持准确的审计，以存储在输入中可以观察到的所有版本。

我们在此提出的模式使用历史中的当前版本作为基线，将历史中的当前版本与每个实例的输入中的第一个最旧版本进行比较，然后按输入中的顺序比较其余输入。

这需要满足一些易于实现但很重要的条件：

- 版本的顺序必须稳定。你需要提供一个排序表达式，以确保版本按正确的顺序进行评估。

    最常见的情况是具有某个生效或最后修改时间戳来提供版本顺序，但任何能产生排序且没有多个行具有相同排名的排序方式都有效，包括按摄取文件名和行号排序。

    毕竟，如果你无法为收到的版本建立顺序，又如何知道哪个是当前/最新的？这可能是你遗漏了某些东西的信号。

- 为了拥有精简且有序的版本序列，输入只能包含与历史中的当前版本对齐或更新的版本。

    如果你的输入包含早于历史中当前版本的版本，历史将包含按正确顺序排列的完整版本序列，但历史中当前版本之前的版本将被再次插入，而没有任何必要，生成除加载时间戳外都是重复的行。

    自然的解决方案是使用高水位列，根据历史表的内容过滤来自 STG 模型的传入数据。

    这种模式非常适合摄取增量加载，但也可以很好地与完整导出一起使用，只要你可以使用业务信息的一部分作为高水位，例如最后修改或生效时间戳，而不是某些加载元数据，例如摄取时间戳。

    在此模式中，高水位在表级别实现，作为给定列的最大值。这是常见情况并提供良好性能，但该模式可以修改为按键级别。

- 另一个重要考虑因素是延迟到达。

    数据是根据到达时间线添加到历史表的，因此输入数据被认为是在同一时间或在上一次加载之后到达。

    每个键的版本将根据提供的排序表达式与“前一个”版本进行比较。第一个输入与历史中的当前版本进行比较；其他输入与输入中的前一个进行比较。

    在许多情况下，可以通过架构 HDIFF 列、排序表达式和加载时间线来存储延迟到达的数据，同时接受某些数据可能被存储两次，但你可以正确地从历史表中读取数据。

    如果你有多个时间线，并且对于你的用例，仅基于一个时间线与历史表中最当前记录进行比较是不够的，那么这种模式不适合你。

到目前为止，我们一直摄取来自输入的最新版本。现在，如果我们可以识别这个起点，我们就可以一次性保存所有在上次摄取后到达的新信息。通常，这就是通过最后更新列完成的。

在我们进入代码之前，我们可以说摄取机制与保存历史的其他宏非常相似。不同之处在于能够为单个加载时间戳存储一个实例的多个版本，反过来，能够在存在多个具有相同加载时间戳的版本的情况下，从历史中获取单个最当前实例。

正如我们之前提到的，要实现这一点，我们需要一个排序表达式来将一个实例的多个版本排序。

为了实现这种模式，我们将实现两个宏：一个是 current_from_history 的扩展，用于从最后加载时间的多行中选择最后一行；另一个是 save_history 的扩展，根据版本的顺序应用正确的比较。

这里，我们使用的是 `current_from_history_with_multiple_versions` 宏，其名称已暗示，它是一个专门用于在历史表可以为单个加载时间戳存储多个版本时读取最新版本的宏。在这种情况下，我们还需要 `sort_expr`，一个 SQL 表达式，用于对在同一时间输入/加载时呈现的版本进行排序。

对于此宏，我们需要检索最新版本的 HKEY 和 HDIFF 两列，因此必须在 `selection_expr` 参数中构建此 SQL 表达式。

下面的 `load_from_input` CTE 在选择要保存的行方面具有与我们在其他 `save_history` 宏中相同的功能：

```
load_from_input as (
  SELECT
    i.*
    , LAG(i.{{diff_column}})
      OVER(PARTITION BY i.{{key_column}}
      ORDER BY {{sort_expr}}) as PREV_HDIFF
    , CASE
        WHEN PREV_HDIFF is null
        THEN COALESCE(i.{{diff_column}} != h.{{diff_column}}, true)
        ELSE (i.{{diff_column}} != PREV_HDIFF)
      END as TO_BE_STORED
  FROM {{input_rel}} as i
  LEFT OUTER JOIN current_from_history as h
    ON h.{{key_column}} = i.{{key_column}}
  WHERE {{input_filter_expr}}
```

我们以通常的查询结束，该查询在所有情况下都能产生所需的结果：

```
SELECT * EXCLUDE(PREV_HDIFF, TO_BE_STORED)
FROM load_from_input
WHERE TO_BE_STORED
ORDER BY {{key_column}}, {{sort_expr}}
{%- endmacro %}
```

这里，与其他保存历史宏相比，我们有几个不同之处。

第一个是我们对 `TO_BE_STORED` 列进行了显式过滤。我们本可以在两种情况下使用 `QUALIFY` 谓词，但我们认为在这里使用单个谓词更具可读性。

第二个是我们从最终的 `SELECT` 投影中移除了用于确定要存储行的临时 `PREV_HDIFF` 和 `TO_BE_STORED` 列。

第三个是我们最后添加了 `ORDER BY`，以便于从历史表中读取数据时检索。

现在我们知道了如何在历史表中存储多个版本，让我们来看看 `current_from_history_with_multiple_versions` 宏，该宏用于检索最后一个版本。

在宏声明之后，我们创建一个新变量，通过添加行号和计数窗口函数来扩展提供的 `SELECT` 投影表达式。这些用于通过加载时间戳确定最新版本：

```

    {{selection_expr}}
    , row_number() OVER( PARTITION BY
        {{key_column}}, {{load_ts_column}}
        ORDER BY {{sort_expr}}) as rn
```

使用这种方法，当 PII 信息从源系统中消失时，它会自然地从您的数据平台中清除。在落地表中，PII 仅保留您在删除导入数据之前决定的保留期，对于包含 PII 数据的表，您可以使其尽可能短；在数据平台中，它仅存储在每天重新创建的表中。

另一个优点是，通过在各处使用相同的代理，您仍然可以连接、计数和分析每个参与者的活动，即使您已“忘记”其 PII。
