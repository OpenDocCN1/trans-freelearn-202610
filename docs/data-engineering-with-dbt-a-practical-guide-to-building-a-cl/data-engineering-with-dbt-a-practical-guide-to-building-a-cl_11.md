## 确保数据可靠性

在上一章中，我们学习了如何确保代码行为一致，以及如何在代码中使用宏和外部库。

在本章中，你将学习如何通过添加测试来验证你的预期并检查转换结果，从而确保数据的可靠性。

最后，你将了解哪些测试在每个层中最有意义，我们将向示例项目中添加许多测试和宏。

本章涵盖以下主题：

- 通过测试提供可靠性
- 在正确的位置测试正确的内容

## 通过测试提供可靠性

如果你只从本节带走一样东西，那就是：“测试将成为让你安睡的超能力。”

测试确保事情按你期望的方式发展，并在情况并非如此时提醒你。

它们是你的军队，保护你的工作和时间免受数据源损坏和不可避免的代码错误（你自己的和同事的）的邪恶影响。

这就是真正的力量。

缺乏测试，再加上不严谨的开发（因为编写SQL查询的人往往缺乏软件工程背景），使得“救火”成为太多数据团队中最常见的活动；而更改数据管道中某些被大量使用的部分（比如客户或订单）的想法，可能会让整个团队紧张不已。你是否经历过？

我们希望你能摆脱这些噩梦。在前面的章节中，我们提供了关于如何组织代码并使其易于阅读和维护的合理指南。在本节中，我们将向你展示如何在部署的转换关键节点设置守卫，以检查一切是否按预期进行。

我们在*第5章*中介绍了dbt开箱即用的通用测试，并向你展示了如何在YAML文件中使用它们；在本章中，我们将更详细地讨论所有类型的测试及其用法。

## 测试类型

每个测试都检查对dbt资源的某个预期是否得到满足。

在dbt中，测试以SQL查询的形式实现，你也可以将它们编写为SQL查询，但大多数时候，你只需在YAML文件中以声明方式将它们应用于dbt资源（模型、源、快照或种子）或其某个列。

dbt测试运行一条SELECT语句，返回不满足你所测试预期的行，因此空结果集表示测试通过，而返回的每一行都表示测试失败。这些失败的行可以自动保存以供你检查。

例如，not-null测试的查询看起来像`SELECT column FROM model WHERE column is null`。你可以看到，如果存在column为null的行，那么这些行会被返回；如果没有null值的行，则查询没有结果行。

在dbt中，你可以用两种方式表达测试：

- 通过编写一个普通的SQL查询来测试你的假设。这被称为**单一测试**，因为它用于单个场景。你通常只会使用少量此类测试来覆盖现有通用测试未覆盖的罕见情况。
- 通过编写或使用参数化SQL查询并传递所需参数；这被称为**通用测试**，因为原则上你可以用它来测试任何dbt资源。这类测试将成为你的家常便饭，而且你将从包中获得大多数测试，因为通常你会反复测试与其他人在其他项目中测试的相同类型的假设。

在讨论要编写哪种测试之前，让我们先看看编写测试的两种方式。

## 单一测试

这是最简单的测试形式，其测试能力仅受限于你用SQL表达待测试假设的能力。

鉴于我们最终会在大多数dbt资源上测试相似的假设，而且通用测试一旦写好就非常简单易用，那么通用测试成为最常见的测试类型也就不足为奇了。

在大多数情况下，你只需以纯声明方式使用通用测试，将想要应用于资源的通用测试作为列表元素添加到YAML文件中dbt资源的`tests`属性下，就像我们在*第5章*中所做的那样。

## 开箱即用的通用测试

你可能还记得*第5章*，dbt自带以下四种通用测试：

- `not_null`：测试表中某列永不为null。
- `unique`：测试某列中的值是唯一的。
- `relationships`：测试两个表之间的参照完整性，即一个表中的每个外键值都存在于指定表的指定列中。换句话说，你测试被测试表中没有*孤儿记录*。
- `accepted_values`：测试列中的值是否属于列出的值之一。

使用这些基础测试，你已经可以强化项目，并覆盖构建管道时所做的基本假设，例如主键和业务键唯一且不为null，外键没有孤儿记录，以及类别具有预期集合中的值。

dbt提供的通用测试覆盖了最常见的测试需求，并且可以进一步配置以针对特定情况定制——例如，要求`email`这样的列唯一，但仅针对活跃用户；或者认为单个姓名为空的客户不足以阻塞ELT，只应发出警告，而超过10个错误则可能有必要停止管道。

## 应用通用测试

你将使用YAML文件将通用测试应用于模型，就像本书前面我们对源所做的操作一样。

例如，下面是`refined.yml`文件，它对refined层中的`REF_POSITION_ABC_BANK`模型提供了描述和测试：

```yaml
version: 2
models:
  - name: REF_POSITION_ABC_BANK
    description: The positions we have in the ABC Bank portfolio.
    columns:
      - name: UNREALIZED_PROFIT
        description: The unrealized profit on the position.
        tests:
          - not_null
      - name: UNREALIZED_PROFIT_PCT
        description: The unrealized profit % on the position.
        tests:
          - not_null
```

上面的代码片段演示了not_null测试在两个不同列上的基本用法。稍后，你将看到如何添加额外配置以更好地定制测试行为，例如让测试返回警告、仅在超过某个阈值时出错，或在特定条件下应用测试。

dbt提供的默认测试在列级别应用，但测试也可以应用于资源级别，无需嵌套在列下。

以下语法用于将`has_default_record`测试应用于`REF_SECURITY_INFO_ABC_BANK`表：

```yaml
version: 2
models:
  - name: REF_SECURITY_INFO_ABC_BANK
    tests:
      - has_default_record
```

这对于应用于表而非特定列的测试很常见，例如假设的`table_is_not_empty`测试。

## 来自包的通用测试

你可以用开源或私有包提供的许多其他通用测试来补充开箱即用的通用测试，从而用他人甚至你自己编写的通用测试扩展项目。

事实上，在之前关于包的部分，我们提到了两个提供大量测试的包——`dbt_utils`和`dbt_expectations`。

`dbt_utils`包提供了丰富的通用测试选择，补充了dbt Core开箱即用的四个测试，使你能够覆盖常规测试需求，从而很少需要自己编写通用测试，你可能只是为了可读性或配置方便而使用它。

请查看我们在上一节中描述的测试，以及dbt Hub上`dbt_utils`页面中的其余测试：https://hub.getdbt.com/dbt-labs/dbt_utils/。

`dbt_expectations`包极大地扩展了可用的通用测试，并允许你使用与Python的Great Expectations测试套件相同的测试风格向项目添加测试。

为了让您了解可用测试的扩展范围，以下是`dbt_expectations`包0.8.0版本的测试类别列表：表形态、缺失值、唯一值和类型、集合和范围、字符串匹配、聚合函数，以及多列和分布函数。




您可以在 dbt Hub 的 `https://hub.getdbt.com/calogica/dbt_expectations/` 上查看这些定义。每个测试都附有用法示例，您还可以查看测试的源代码。

## 定义通用测试

要定义通用测试，或者覆盖现有的开箱即用测试，您可以编写一个测试 Jinja 块，在 SQL 文件中包含测试的 SQL。

测试块与宏非常相似，因为通用测试曾经是名称以 `test_` 开头的宏，而且它们的工作方式与宏基本相同——定义一个接受参数并以测试结果形式评估其结果的函数。

通用测试的 SQL 必须编写为返回测试失败的行，使用我们在单一测试中看到的相同逻辑。如果您测试一个等于 42 的列，那么您的 SQL 应选择所有列值不为 42 的行。

通用测试使用 YAML 文件应用，并且必须始终至少定义两个参数：`model` 和 `column_name`，这两个参数会自动用于向每次测试调用传递资源引用，以及传递测试在 YAML 文件中应用的列名称。

您可以在测试定义中添加其他参数，带或不带默认值，就像处理宏一样。然后您可以在 YAML 文件中为这些额外参数传递值，稍后我们开发第一个通用测试时会看到。

从 dbt 1.0.0 版本开始，您可以将通用测试放在两个位置：

- 在 `macro` 文件夹中，您还可以在其中定义宏。这是最初将通用测试定义为宏的遗留方式，当您想在通用测试中使用其他临时宏来定义复杂逻辑时，它会变得很方便。
- 在 `tests/generic` 文件夹中，与单一测试相邻。这个特殊文件夹是在 dbt 1.0.0 中引入的，允许您将所有测试放在同一文件夹下，通用测试放在 generic 文件夹中，而单一测试则按您认为合适的方式组织。

我们建议您选择这两个位置之一来组织您的通用测试。

我们将使用 macro 文件夹下的 tests 子文件夹，以便在需要时可以在测试旁边定义宏，而 tests 文件夹仅用于单一测试。

## 通用测试模式

为通用测试编写的 SQL 使用 `model` 和 `column_name` 参数来测试您已为其配置测试的资源和列，但您的测试可以使用更多参数。

```
SELECT * FROM validation_errors
{%- endtest %}
```

在 no_hash_collisions 通用测试的测试块声明中，我们声明了三个参数，将 hashed_fields 添加到了必需的 model 和 column_name 参数之外。

我们将 model_data CTE 重命名为 all_tuples，以强调我们获取的是由哈希字段和用于构建哈希的所有字段组成的所有不同元组。

然后我们选择了存在多个字段元组的所有哈希，因为这将是一种冲突情况——由两个不同的值集生成相同的哈希。

- 3. 创建一个 snapshots.yml YAML 文件来描述和测试快照：

```
version: 2
snapshots:
  - name: SNSH_ABC_BANK_POSITION
    columns:
      - name: POSITION_HKEY
        tests:
          - no_hash_collisions:
              hashed_fields: ACCOUNT_CODE, SECURITY_CODE
```

model 和 column_name 参数由 dbt 自动管理，因此我们无需将它们传递给测试，但我们需要为通用测试中没有默认值的任何其他参数提供值，例如 hashed_fields。我们省略了描述，但描述应该是存在的。

您将参数值作为所声明测试的属性来提供。实际上，这意味着您在测试名称后添加一个冒号（:），然后在下一行，相对于测试名称缩进，写入参数名称、冒号（:）和参数值，就像我们在前一个示例中为 hashed_fields 参数所做的那样。

参数值可以是 Jinja 表达式，但此时应适当加上引号。

- 4. 在快照上运行测试，看看您闪亮的新测试的实际效果：

```
dbt test -s SNSH_ABC_BANK_POSITION
```

通过在测试 Jinja 块中编写一些 SQL，并使用一些关于必需参数名称的约定，我们轻松定义了一个通用测试。

让我们看看如何添加一个支持使用此测试的宏，以便我们可以使用与定义哈希相同的代码来用于测试，而不必提供相同的字段列表，但无需加引号。

如果您查看 STG 模型，您会看到为了构建哈希键和哈希差异，我们将字段名称列表传递给 dbt_utils.surrogate_key 宏。通过使用 join 筛选器，很容易生成以逗号分隔的名称列表，所以让我们来做吧：

- 1. 将用于生成字段列表的宏添加到 no_hash_collisions 文件中：

```
{% macro as_sql_list(hashed_fields_list) -%}
{{ hashed_fields_list|join(', ') }}
{%- endmacro %}
```

这个宏很简单；它使用 Jinja 的 join 筛选器将字段名按逗号连接起来，但通过快速复用我们用来定义哈希字段的同一列表，它使操作变得简单，使测试编写更快捷并减少错误。

- 2. 在 snapshots.yml 文件中为 POSITION_HDIFF 字段添加 no_hash_collisions 测试，该测试使用一长串字段：

```
- name: POSITION_HDIFF
  tests:
    - no_hash_collisions:
        hashed_fields: "{{ as_sql_list(
          ['ACCOUNT_CODE', 'SECURITY_CODE',
           'SECURITY_NAME', 'EXCHANGE_CODE',
           'REPORT_DATE', 'QUANTITY', 'COST_BASE',
           'POSITION_VALUE', 'CURRENCY_CODE'
          ] ) }}"
```

您可以看到，在参数定义中，我们通过传递字符串列表，在花括号内调用宏来生成包含所需内容的字符串。如果宏在 YAML 文件中正确用引号括起来，它会工作得很好。在这种情况下，我们使用双引号，因为我们想对字符串列表使用单引号。

通过这个简单示例，我们向您展示了一些重要过程——定义带有额外参数的通用测试、传递额外参数、添加宏以简化通用测试的使用，以及最终在 YAML 文件内调用宏来提供值。

## 配置测试

与大多数 dbt 资源一样，对于测试，除了传递参数外，还有一些配置可用于控制测试行为。

您可以在不同的层级上配置测试，最通用的配置优先级最低，最专业的配置优先级最高：

- 在全局配置文件 dbt_project.yml 中，您可以使用 tests: 属性配置所有测试，如下例所示：

```
tests:
  portfolio_tracking:
```

前面的代码展示了如何将配置作为属性应用于 YAML 文件中的通用测试，但它们也可以通过 `config()` 块或通常在主配置文件中应用于任何测试。

以下是对它们的简要描述：

- where: 这会将测试限制为满足以字符串形式传入的 where 子句的行。这通常用于将测试限制为活动行（某些列不为空）或某个时间范围内的数据。
- severity: 这将在测试失败时将严重级别设置为 error 或 warn。默认值为 error。
- error_if 和 warn_if: 这些配置一个 SQL 条件，该条件可以与失败次数进行比较以微调严重级别，允许您应用阈值来产生错误或警告。两个配置的默认值都是 != 0。
- fail_calc: 这配置应用于测试查询以报告错误的聚合函数。默认值为 count(*)，即测试失败的行数。
- limit: 这配置测试返回失败行的最大数量。通常不设置，仅在将错误存储到大表中时有用。
- store_failures: 这是一个用于启用或禁用存储测试失败行的配置。默认值为 false，表示不存储失败行。

这些配置会从 severity 和 error_if 条件开始检查，以评估是否必须引发错误；如果未触发错误，则检查 warn_if 条件。

例如，您可以使用 sum(n_records) 查看具有重复项的总行数，或使用 max(n_records) 查看找到的最大重复数。您需要充分了解测试 SQL 代码，才能应用正确的聚合表达式。

当配置为存储测试失败时，dbt 会将测试查询的结果（即失败行）保存到 schema 中与测试同名的表中，并带有默认的 dbt_test__audit 后缀。这使您可以轻松分析失败行。

除了这里提到的测试特定配置外，还可以将其他通用配置应用于测试，例如 enabled、tags 和 meta，以及 database、schema 和表别名，以配置失败存储的位置。

## 在正确的位置测试正确的内容

在前面的章节中，我们看到了在 dbt 中添加测试是多么容易；大多数时候，您只需在 YAML 文件的表或列下添加一个 tests: 属性，并包含几个测试名称。

添加测试如此简单，以至于很容易过度，开始测试所有内容和所有地方，但请克制不要这样做，并记住测试也是代码，因此它们也会带来相应的错误（错误地应用或配置来自库的通用测试，以及编码

我们自己单元测试中的错误）、维护（误报、没有业务价值、可以忽略的错误，以及不断的测试重构），以及后果（因为持续的测试失败疲劳而忽略重要测试）。

测试的执行也需要时间和金钱，所以等待无用的测试完成完全是浪费金钱，也浪费开发者在自己的开发环境中运行测试时的时间。这也不是特别有趣，所以找到一个好的平衡点会很棒。

真正的问题于是变成了：*我们测试什么？*以及*我们在哪里进行测试才能让我们的时间和金钱获得最大的价值？*

让我们先从 dbt 测试一个意想不到的特殊用例开始——数据探索。

在源数据上编写 dbt 测试非常简单快捷，以至于它常常是熟悉一些你还不够了解的新数据的最佳方式。在这种情况下，你可以使用 dbt 测试来探索你的预期并更好地理解数据。

一个常见的场景是尝试不同的潜在主键和业务键，以验证它们是否唯一，以及它们的列是否始终非空。其他常见场景包括：验证从事实表到维度表的关系没有孤儿数据（或者维度表是完整的）、验证类别和度量是否存在及其比例。

当然，进行此类探索的理想方式之一是使用 `dbt_profiler` 包，但如果你没有安装它，使用测试是一种快速且常见的方式，用于检查你最初的预期，并与团队其他成员分享你的发现。

## 我们测试什么？

一旦这阵为了更好地理解数据而进行的初步测试热潮过去，我们就必须专注于在我们的项目中保留真正重要的测试。下一节将讨论这个问题。

我们必须始终从驱动价值的事物开始，进而思考哪些问题会最大程度地损害价值，或足以造成影响。

让我们来看看模型中能发现的主要数据类别：

- **主键（PK）**和**业务键（BK）**：正确的 PK/BK 对于识别实体和存储其变更历史至关重要。它们使我们能够连接事实表和维度表，而 BK 则是跨不同系统识别同一实体的关键。

    虽然不可变事实在缺少 PK/BK 时可能没问题，但对于我们可能要在平台上使用的所有其他实体来说，键是必不可少的：可变事实、维度、参考表、映射表和配置。

- **外键（FK）**：FK 是关系系统的核心要素，因为它们通过指向另一张表中补全信息的 PK/BK 来存储表与实体之间的关系。在多对多关系的情况下，每一侧的 FK 存储在定义该关系的映射表中，而不是直接存储在表内。

    FK 最常见的场景是事实表拥有与维度表建立关系的 FK。在这种情况下，如果关系是强制的，我们需要确保事实表中的 FK 没有 NULL 值。无论如何，我们还希望事实表中的每个 FK 都能在维度表中找到对应的 PK。

    同样非常常见且重要的是，正确表示维度之间的关系以创建层级结构，比如城市位于国家内、国家位于地区内、地区位于大洲内；以及表示业务流程的事实之间的关系，例如与销售订单行关联的发票行或退货行。

    贯穿正确识别 PK 和 FK 的一个核心主题是正确理解关系的多重性。

- **业务规则（BR）**：业务规则形式多样，是为我们的数据平台带来大部分价值的“调味料”。要完整列出 BR 类型是不可能的，因为它们可以从计算到实体连接方式再到数据格式化方式，包罗万象。

    无论它们是哪种类型，如果我们想正确表达业务，就必须把它们做对。

- **度量**：度量是可用于计算的数值型数据。有些度量极其重要，因为计算需要用到它们，缺少它们会使数据几乎毫无用处，比如没有销售金额的销售订单。

- **类别**：类别是非纯描述性的文本数据，例如名称或任意自由文本，但它们用于分组或以某种方式组织数据，比如产品类型、客户所在行业，或者用户用来切片报表的任何值，但它不是一个完整的维度。

- **描述性数据**：其他几乎所有数据都可以归入描述性数据类别，其中包含名称、自由文本，以及一般意义上所有不属于其他类别类型的文本数据。

观察这些数据类别，很明显，其中一些如果弄错了会引发许多问题，而另一些可能只算是小小的麻烦：

- PK 和 BK 至关重要，我们必须尽一切可能把它们做对；否则，我们将无法正确地连接数据或存储变更历史，并且很可能会产生重复数据。

    简而言之，如果 PK/BK 出错，我们的数据模型就绝无可能正常工作；因此，我们必须测试我们选作 PK/BK 的键是否是一个好键。

- 同样重要程度的是，正确理解由 FK 所标识的关系的多重性（包括可选或强制状态）。我们必须测试我们使用的强制关系的 FK 是否存在（非空）；否则，我们的数据模型将无法按预期工作。

- 谈到 BR 时，测试我们是否拥有计算它们所需的全部要素也非常重要，如果可能的话，还要测试我们的计算是否正确。最后这一点需要业务用户提供带有预期结果的可用于测试的用例。

- 对于度量、类别或描述性数据等优先级较低的数据类别，其重要性应逐案评估。

销售负责人、销售团队或客户名称在某些情境下可能是次要的，而在其他情境下则可能是关键的。

在考虑为这些数据类别添加测试时，你需要权衡利弊。

现在我们对测试什么有了清晰的认识，接下来让我们分析在哪里进行测试最好。

## 在哪里测试什么？

关于在哪里进行测试，总的想法很简单：我们越早发现问题越好，所以只要测试可行，我们就应该尽快进行测试。

你还希望测试你要交付的内容，以确保尽管你做了所有中间转换，结果仍然符合你预期的数据模型。

黄金法则是：

- 在源数据上或尽可能早地测试你对输入的预期

- 在交付输出时测试你对输出的预期

- 在 ELT 管道的中间转换中，测试那些可能引发大量问题、或者你并不完全信任其总能按计划工作的关键内容，例如 BR 或复杂的连接

在接下来的章节中，让我们讨论我们数据平台每一层的典型测试。

## 源数据测试（输入层）

这是数据的入口点，你尚未触碰过这些数据，因此你只能测试那些不需要对传入数据做任何更改的假设。

在这里，你有一些最重要的测试：

- 测试 PK 和 BK 非空且唯一。这是最高优先级，确保你正确理解并存储实体。

如果你的源数据具有完整历史，甚至只是包含多个版本的部分历史，你必须将唯一性测试移到另一层，通常是 STG 层（你可以在该层进行过滤，只保留要存储的最新版本）。




你可以通过测试 PK 以及更新时间戳的唯一性，但这更多是为了探索你的输入数据模型，而不是为了确保数据质量的一致性。

请记住，对于一个不可变事实来说，没有 PK/BK 也是可以的。

- 测试 FK，以检查强制的一对多关系是否不为空。这是高优先级，确保 FK 存在且符合预期。关系是强制性的，意味着它必须始终存在；因此，FK 必须不为空。

- 测试关系，以检查它们是否没有孤立的 FK。这是低优先级。知道关系是完整的很好，但你只能使用输入数据提供的东西。

  知道事实中存在孤儿（维度或查找表对于事实的一个或多个 FK 没有 PK）可能是给运营人员的一个良好输入，让他们知道问题所在，特别是如果他们可以添加缺失的主键，并且否则确保你自己管理孤儿，但它不会提供结构信息，你必须接受你所拥有的数据。

- 我们依赖的类别和度量是中到低优先级，这意味着你必须确保拥有重要的数据片段，但并非所有内容都是必要的。

  例如，如果你没有销售额，就很难报告销售情况；如果某些客户没有国家代码，就很难按国家拆分数据。你必须根据最终可用的替代方案以及测试失败时可以采取的行动来决定其重要性。

- 测试源数据的新鲜度。这是高优先级。你必须确保数据与预期一样新鲜。

  利用 dbt 的功能，为每个源表输入期望的新鲜度阈值并自动运行测试，从而生成易于阅读的报告。

## 存储层上的测试 – STG 和 HIST 模型

在这里，我们以我们想要存储的基本可用格式过滤和转换数据，并且我们可以测试所有我们感兴趣的内容，但无法直接在源数据上测试。

这是数据质量最重要的层，因为在这里我们将数据放入其可被使用且存储其历史的正确形状。你必须确保你所存储的内容：

- 测试 PK 和 BK（在源上无法测试）是否不为空且唯一。这是最高优先级。你需要确保键是有效的键，因为你将依赖它们。

  在大多数现实案例中，即使你的源包含多个版本，在每次运行中仅将最新版本添加到历史中也是可以的，在 STG 模型中过滤数据以存储在 HIST 模型中的版本。

  在此阶段，你必须测试 STG 模型输出的 PK/BK 是否唯一，并且在 HIST 模型中，PK/BK 与 LOAD_TS 的组合也唯一，因为我们希望在每次运行中存储一次变更。

- 测试 HKEY 和 HDIFF 是否没有哈希冲突（在 HIST 模型中）。

  这是低优先级。冲突风险很小，特别是如果你没有数十亿行。

  哈希冲突风险随着表中哈希数量的增加而增加；因此，有意义在 HIST 模型中检查哈希，因为它包含一个实体的所有哈希。风险始终非常小，一次冲突最终只会影响一行数据，但不测试它是不负责任的。

  当表有数十亿行时，测试开始更有用但也更慢，因此可能有意义以更低的频率运行哈希冲突测试。

- 创建所有你在源层本应执行但因需要数据转换而不可行的测试。

  某些输入数据在按预期工作之前需要清理或转换的情况很常见。常见示例是日期和时间戳从文本解析而来（你希望确保可以从其文本格式解析它们，然后再测试它们所期望的内容），或文本字段通过删除多余空格或无意义的零进行规范化，或更改为大写或小写。

## 精炼层上的测试

这是依赖于存储数据正确性的业务规则层。

在此层，我们应假设来自存储层的数据是可靠的，我们只需在可能通过转换引入错误的地方进行测试：

- 测试计算值的 BR 结果。这是高优先级。我们必须确保我们有结果并且它是正确的。

  最低期望是你检查计算值是否产生结果而不是空值（除非该值是可选的），并且如果有控制数据，则测试结果是否正确。BR 的正确性通常使用针对知名测试用例的单项测试进行验证。

- 在执行 BR 的有风险或复杂的连接后测试 PK/FK。

  这是最高优先级。确保数据符合 BR 的数据模型。

  另一大类 BR 是丰富，其中你连接表以引入度量或描述值。我们在上一要点中处理了值的获取及其在计算中的使用。

  请注意，获得结果表的正确基数极其重要，你应测试实现 BR 的连接链不会产生重复或遗漏数据。

## 投递层上的测试

投递层使数据可供我们的消费者、我们的“客户”使用。

我们需要测试我们交付的内容是否符合我们的数据模型和行业标准：

- **测试维度是否格式良好：** 测试 PK 或 BK 是否唯一且不为空，并且只有一个且仅有一个默认记录。
- **测试事实是否格式良好：** 测试 PK（如果存在）是否唯一且不为空，事实到维度的 FK 不为空（具有业务值或如果关系是可选的则为默认值），并且没有孤儿（事实的 FK 存在于维度的 PK 中，最终作为默认记录）。
- **测试事实和维度中的值：** 测试强制类别和度量不为空，并且类别具有预期值集合中的值。
- **测试众所周知的预期输出是否正确生成：** 使用一组众所周知的案例，检查计算值是否与预期值匹配。这可以通过单项测试轻松实现。
- **运行统计、定量测试以确保数据流动且在合理范围内：** 我们知道一定数量的事件或值应该流动。测试我们在特定时间范围内事件数量或度量值的范围内，最终基于过去的数据，同时考虑季节性。例如，我们每周/每月应有合理数量的订单，订单总额应在合理范围内。

这类测试补充了源新鲜度测试，增加了对数据数量的控制并确保其值合理。

## 测试我们的模型以确保良好质量

回顾我们的项目，我们在为 ABC_BANK_POSITION 源添加测试方面做得相当好，因为我们正在检查我们关心的列是否不为空。

我们投入的精力较少来为其他层添加测试，因为我们专注于构建模型本身；在这一节中，我们将遍历示例的各层并添加一些重要测试，以确保我们的应用程序按预期工作。

### 测试复合键的唯一性

在 ABC_BANK_POSITION 源中，我们正在检查 SYMBOL 列是否唯一。然而，这真的正确吗？

嗯，如果我们只考虑一个人的单个投资组合，则是的，但如果我们考虑一个人可能在同一家银行拥有多个账户，那么我们可能应该承认这太严格了。

当我们查看 STG 层时，我们可以看到 POSITION_HKEY 由两个字段 ACCOUNT_CODE 和 SECURITY_CODE 定义，所以我们有一个复合键，这是常见情况。

由于这也看起来更符合现实要求，让我们看看如何在源上测试此复合键。

建议的解决方案是使用分隔符创建它们的连接列（以避免‘ab’||‘c’等于‘a’||‘bc’并且也等于 ‘’||‘abc’ 或 ‘abc’||‘’），并对其进行测试，但我们无法更改源，因此此解决方案不可行。

我们可以将测试移至下一层，在那里我们已经将 POSITION_HKEY 列定义为这些列的组合，外加哈希。这可行，但如果我们可以在源上测试，那更好，这样我们就知道问题不在我们的代码中，而在我们的假设与传入数据不一致。

为了将测试保留在源层，我们有两个替代方案——在源 YAML 文件中创建列的匿名连接，或使用 dbt_utils 包中的 unique_combination_of_columns 测试。

第一个方法很直接但可能存在性能问题，而第二个是应用于表的测试，并且是高效的解决方案。

让我们看看这两种方法，然后你可以决定你更喜欢哪一种。打开 source_abc_bank 文件并为 ABC_BANK_POSITION 表添加以下代码：

```
- name: ABC_BANK_POSITION
  tests:
    - dbt_utils.unique_combination_of_columns:
        combination_of_columns:
          - ACCOUNTID
          - SYMBOL
  columns:
    - name: CONCAT_WS('-', ACCOUNTID, SYMBOL)
      tests:
        - not_null
        - unique
    - name: SYMBOL
      tests:
        - not_null
```


在前面的代码中，我们完成了以下操作：

- 在表名和 `unique_combination_of_columns` 测试下添加了 `test:` 属性，并将我们想要的两列（ACCOUNTID 和 SYMBOL）作为 YAML 列表传入。

- 添加了一个伪列，用有效的 SQL 表达式代替列名。

这种方式始终有效，通过使用 `CONCAT_WS` 函数，你可以使用分隔符连接任意数量的列。如你所见，它的优点是快速且易于阅读，并将测试放在与其他列测试相同的位置。只需注意，这种连接并非严格必要，而且在处理大表时可能会增加大量开销。表级测试只是对要测试的列做一个 `group` by，这是最低要求且速度很快。它还将测试直接放在表下，使其更加醒目，避免将主键测试与其他列的测试混在一起。

- 从 SYMBOL 列移除了 `unique` 测试。

总而言之，我们可以说，在处理小表时使用 `CONCAT_WS` 函数没有问题，而在处理大表（1 亿行以上）时，则应使用 `dbt_utils` 包中的测试。只有当我们需要编辑或提取相关列，或对源进行过滤时，才应考虑将这类重要测试移到下一层。

## 测试 CSV 种子数据

我们的第二个输入是一个作为 `seed` 加载的 CSV 文件。

在这种情况下，我们可以在三个位置进行测试：

- **在 CSV 种子上：** 如果测试的需求或重要性与被测试源是 CSV 文件有关，我们会把测试放在这里。例如，解析日期或数字，或者在我们的场景中，正确应用 post-hook 查询。

- **在种子源表上：** 如果测试的重要性与输入类型无关，我们会把测试放在这里。换句话说，它与数据的语义有关。

- 和往常一样，我们可以将测试传递到 STG 模型中，但如果可能的话，我们更倾向于尽早测试。

为了展示这两种方式，让我们在种子上为 `LOAD_TS` 列添加一个 `not null` 测试，并在我们定义为读取 CSV 的源上添加我们认为合适的其他测试。

让我们从种子开始：

1. 在 `seeds` 文件夹下创建一个 `seeds.yml` 文件

2. 添加以下代码：

```
version: 2
seeds:
tests:
  - not_null
  - not_empty
```

在前面的代码中，我们完成了以下操作：

- 测试了 SECURITY_CODE 列是唯一且非空的，隐式地将其定义为业务键
- 测试了 SECURITY_NAME 列非空且非空字符串；我们以后会经常使用证券名称，不能接受它为空

我们把这个留作练习：如果你认为有必要，可以为 ABC_Bank_SECURITY_INFO 表的其他列添加更多的 not_null 和/或 not_empty 测试。

## 添加测试以避免回归

看看我们的 STG 层，剩下的测试不多了，因为我们已经设法在源和种子上完成了重要测试（唯一性和必填的非空字段）。

只有一个字段需要转换，那就是报告日期，它之前以两位数字存储在 CSV 文件中，并被加载为 1 世纪的日期。

我们决定保持加载不变（得到一个日期），然后在 STG 模型中通过创建宏来“修复”该日期。我们也可以更改加载方式，从 CSV 中加载字符串，并在 STG 模型中将其正确解析为两位数的年份。

两种方法都可行，而且我们无法排除日后有人不喜欢我们的解决方案，从而修改加载或找到其他方式，包括从不同的源获取数据。现在，为了提高加载质量并增强信任，我们可以设置一个测试，避免回退到我们已经解决过的问题。

让我们添加一个测试来检查 REPORT_DATE 列属于 21 世纪：

1. 在 models/staging 文件夹中创建一个 staging.yml 文件。
2. 向文件中添加以下代码：

```
version: 2
models:
  - name: STG_ABC_BANK_POSITION
    tests:
      - dbt_utils.expression_is_true:
          expression: " YEAR(REPORT_DATE) >= 2000 "
```

我们将使用 `dbt_utils` 包中的 expression_is_true 测试来表达表级条件：REPORT_DATE 列的年大于 2000，或者任何对你合适的值（如果你的数据更旧，也许是 1970 或 1900）。

这是对宏进行单元测试的一种非常简单有效的方法，但这只是其中一种方式，根据要执行的测试，可以使用这种模式的许多变体。

你可以通过多种方式提供输入数据，像我们这样使用简单的 SELECT 和 UNION ALL；但如果你打算提供更多数据，你可能会想改用 SELECT FROM VALUES SQL 子句，甚至将数据放在一个正式的表中，既可以是 CSV 种子加载，也可以作为提供给您的源并在测试中访问。

在某些情况下，只需验证结果满足某个规则即可，而不必为每个输入值表达预期结果，因此你可能不需要预期的数据，因为它将被按给定规则进行的计算所取代。

在其他情况下，预期数据可能不绑定到单个行，而是会有一个预期的结果集。在这种情况下，你会得到两个表，一个用于输入数据，一个用于预期数据，你可以使用 MINUS（等同于 EXCEPT）集合运算符：

```
SELECT results
MINUS
SELECT expectations
UNION
SELECT expectations
MINUS
SELECT results
```

前面查询的第一部分验证 results 中的所有行都是预期表中的预期行，而第二部分验证预期表中只有预期行出现在 results 中。这两部分合起来验证结果与预期产生相同的行。

在介绍通用测试时，我们已经在 HIST 模型上应用了 no_hash_collisions 测试，因此不需要再对它们进行更多测试。

## 避免事实表中的孤儿键

转到 refined 层，我们已经有了几个测试来确保我们计算的值（业务规则）不为空。

我们的两个 REF 模型也非常简单，不做任何连接，因此剩下的唯一有意义的测试是：确保 position 事实表与 security 维度表之间的关系是正确构建的，且事实表中没有孤儿记录。

让我们使用 dbt 提供的 relationship 测试来确保这一点：

1. 打开 refined 文件夹中的 refined.yml 文件。
2. 添加以下代码：

```
- name: REF_POSITION_ABC_BANK
  columns:
    ...
    - name: SECURITY_CODE
      description: The code of the security in the position.
      tests:
        - relationships:
            to: ref('REF_ABC_BANK_SECURITY_INFO')
            field: SECURITY_CODE
```

我们已经为事实表的 SECURITY_CODE 列添加了一个 relationships 测试。

该测试声明事实表中的这一列是与 security 维度表关系的的外键，其中 SECURITY_CODE 字段是主键。

测试通过，所以我们可以继续前进，并因知道我们没有孤儿记录而感到安心，即使我们知道自己迟早会遇到一些孤儿记录，届时需要管理它们。我们会在讨论重构模型时处理这个问题。

测试我们期望的模型之间的关系是否按预期工作，对于保证我们的数据模型持续适用极其重要。

另外需要注意的是，通常我们在 refined 层有一个关系型数据模型（在 REF 模型之间），它试图广泛表示现实世界和我们领域内的流程，但我们为创建的每个数据集市都有一个 Kimball（或星型模式）模型。它们相关但不相等。我们应该在哪里测试这些关系？

黄金法则是：尽快测试！因此，我们应该在 REF 层测试属于 REF 层数据模型的关系，然后在数据集市层测试仅为该数据集市创建的关系。

## 测试交付层

看看我们交付层的模型，可以看到它们都是非常简单的 `SELECT * FROM aRefModel` 类型，因此我们只需确保主键有效，并且维度表有一个默认键。

让我们从主键开始：

1. 在数据集市文件夹中创建 _portfolio.yml 文件。

2. 向文件中添加以下代码：

```
version: 2
models:
  - name: FACT_POSITION
```




```
tests:
  - dbt_utils.unique_combination_of_columns:
      combination_of_columns:
        - ACCOUNT_CODE
        - SECURITY_CODE
  - name: DIM_SECURITY
    columns:
      - name: SECURITY_CODE
        tests:
          - not_null
          - unique
```

在上面这段代码中，我们测试了两个模型的主键。我们提醒你，使用 `unique_combination_of_columns` 宏测试的两列并不会检查它们是否为空，因此你应该添加必需的列级测试。

为了能够测试维度具有默认记录且只有一个默认记录键，我们需要创建相关的通用测试，那么让我们开始吧。

3. 在 `macros/tests` 文件夹中创建一个 `has_default_key.sql` 文件，并添加以下代码：

```
{% test has_default_key ( model, column_name
, default_key_value = '-1'
, record_source_field_name = 'RECORD_SOURCE'
, default_key_record_source = 'System.DefaultKey'
) -%}
{{ config(severity = 'error') }}
WITH
default_key_rows as (
    SELECT distinct {{column_name}},
        {{record_source_field_name}}
    FROM {{ model }}
    WHERE {{column_name}} = '{{default_key_value}}'
    and {{record_source_field_name}} = '{{default_key_record_source}}'
),
validation_errors as (
    SELECT '{{default_key_value}}' as {{column_name}},
'{{default_key_record_source}}' as {{record_source_field_name}}
    EXCEPT
    SELECT {{column_name}}, {{record_source_field_name}}
    FROM default_key_rows
)
SELECT * FROM validation_errors
{%- endtest %}
```

此测试验证存在一行具有正确的值和记录来源。

4. 在 `macros/tests` 文件夹中创建一个 `warn_on_multiple_default_key.sql` 文件，并添加以下代码：

```
{% test warn_on_multiple_default_key ( model, column_name
, default_key_value = '-1'
, record_source_field_name = 'RECORD_SOURCE'
, default_key_record_source = 'System.DefaultKey'
) -%}
{{ config(severity = 'warn') }}
WITH
validation_errors as (
    SELECT distinct {{column_name}},
        {{record_source_field_name}}
    FROM {{ model }}
    WHERE {{column_name}} != '{{default_key_value}}'
    and {{record_source_field_name}} = '{{default_key_record_source}}'
)
SELECT * FROM validation_errors
{%- endtest %}
```

此测试在存在具有默认记录记录来源的行、但其键不是默认记录预期键时，会引发警告。如果你想要区分事实表中没有外键的不同原因，这可能是一个有效的情况，例如：数据缺失（-1）、未来/尚无数据（-2）、错误/不正确的值（-3）以及有意留空/不适用（-4）。如果是这种情况，我们建议一旦你确认多个键是有意为之，就移除该测试。

5. 让我们通过编辑 `_portfolio.yml` 文件来应用这两个测试。

在维度的主键（`SECURITY_CODE`）下添加这两个测试：

```
- name: DIM_SECURITY
  columns:
    - name: SECURITY_CODE
      tests:
        - not_null
        - unique
        - has_default_key
        - warn_on_multiple_default_key
```

现在我们已经定义了两个测试，`has_default_key` 和 `warn_on_multiple_default_key`，你可以看到测试每个维度是多么容易。

我们已经遍历了示例项目的各层，并添加了我们认为有用的测试，最终创建了所需的通用测试宏。
