

你可以通过测试 PK 以及更新时间戳的唯一性，但这更多是为了探索你的输入数据模型，而不是为了确保数据质量的一致性。

请记住，对于一个不可变事实来说，没有 PK/BK 也是可以的。

- 测试 FK，以检查强制的一对多关系是否不为空。这是高优先级，确保 FK 存在且符合预期。关系是强制性的，意味着它必须始终存在；因此，FK 必须不为空。

- 测试关系，以检查它们是否没有孤立的 FK。这是低优先级。知道关系是完整的很好，但你只能使用输入数据提供的东西。

  知道事实中存在孤儿（维度或查找表对于事实的一个或多个 FK 没有 PK）可能是给运营人员的一个良好输入，让他们知道问题所在，特别是如果他们可以添加缺失的主键，并且否则确保你自己管理孤儿，但它不会提供结构信息，你必须接受你所拥有的数据。

- 我们依赖的类别和度量是中到低优先级，这意味着你必须确保拥有重要的数据片段，但并非所有内容都是必要的。

  例如，如果你没有销售额，就很难报告销售情况；如果某些客户没有国家代码，就很难按国家拆分数据。你必须根据最终可用的替代方案以及测试失败时可以采取的行动来决定其重要性。

- 测试源数据的新鲜度。这是高优先级。你必须确保数据与预期一样新鲜。

  利用 dbt 的功能，为每个源表输入期望的新鲜度阈值并自动运行测试，从而生成易于阅读的报告。

## 存储层上的测试 – STG 和 HIST 模型

在这里，我们以我们想要存储的基本可用格式过滤和转换数据，并且我们可以测试所有我们感兴趣的内容，但无法直接在源数据上测试。

这是数据质量最重要的层，因为在这里我们将数据放入其可被使用且存储其历史的正确形状。你必须确保你所存储的内容：

- 测试 PK 和 BK（在源上无法测试）是否不为空且唯一。这是最高优先级。你需要确保键是有效的键，因为你将依赖它们。

  在大多数现实案例中，即使你的源包含多个版本，在每次运行中仅将最新版本添加到历史中也是可以的，在 STG 模型中过滤数据以存储在 HIST 模型中的版本。

  在此阶段，你必须测试 STG 模型输出的 PK/BK 是否唯一，并且在 HIST 模型中，PK/BK 与 LOAD_TS 的组合也唯一，因为我们希望在每次运行中存储一次变更。

- 测试 HKEY 和 HDIFF 是否没有哈希冲突（在 HIST 模型中）。

  这是低优先级。冲突风险很小，特别是如果你没有数十亿行。

  哈希冲突风险随着表中哈希数量的增加而增加；因此，有意义在 HIST 模型中检查哈希，因为它包含一个实体的所有哈希。风险始终非常小，一次冲突最终只会影响一行数据，但不测试它是不负责任的。

  当表有数十亿行时，测试开始更有用但也更慢，因此可能有意义以更低的频率运行哈希冲突测试。

- 创建所有你在源层本应执行但因需要数据转换而不可行的测试。

  某些输入数据在按预期工作之前需要清理或转换的情况很常见。常见示例是日期和时间戳从文本解析而来（你希望确保可以从其文本格式解析它们，然后再测试它们所期望的内容），或文本字段通过删除多余空格或无意义的零进行规范化，或更改为大写或小写。

## 精炼层上的测试

这是依赖于存储数据正确性的业务规则层。

在此层，我们应假设来自存储层的数据是可靠的，我们只需在可能通过转换引入错误的地方进行测试：

- 测试计算值的 BR 结果。这是高优先级。我们必须确保我们有结果并且它是正确的。

  最低期望是你检查计算值是否产生结果而不是空值（除非该值是可选的），并且如果有控制数据，则测试结果是否正确。BR 的正确性通常使用针对知名测试用例的单项测试进行验证。

- 在执行 BR 的有风险或复杂的连接后测试 PK/FK。

  这是最高优先级。确保数据符合 BR 的数据模型。

  另一大类 BR 是丰富，其中你连接表以引入度量或描述值。我们在上一要点中处理了值的获取及其在计算中的使用。

  请注意，获得结果表的正确基数极其重要，你应测试实现 BR 的连接链不会产生重复或遗漏数据。

## 投递层上的测试

投递层使数据可供我们的消费者、我们的“客户”使用。

我们需要测试我们交付的内容是否符合我们的数据模型和行业标准：

- **测试维度是否格式良好：** 测试 PK 或 BK 是否唯一且不为空，并且只有一个且仅有一个默认记录。
- **测试事实是否格式良好：** 测试 PK（如果存在）是否唯一且不为空，事实到维度的 FK 不为空（具有业务值或如果关系是可选的则为默认值），并且没有孤儿（事实的 FK 存在于维度的 PK 中，最终作为默认记录）。
- **测试事实和维度中的值：** 测试强制类别和度量不为空，并且类别具有预期值集合中的值。
- **测试众所周知的预期输出是否正确生成：** 使用一组众所周知的案例，检查计算值是否与预期值匹配。这可以通过单项测试轻松实现。
- **运行统计、定量测试以确保数据流动且在合理范围内：** 我们知道一定数量的事件或值应该流动。测试我们在特定时间范围内事件数量或度量值的范围内，最终基于过去的数据，同时考虑季节性。例如，我们每周/每月应有合理数量的订单，订单总额应在合理范围内。

这类测试补充了源新鲜度测试，增加了对数据数量的控制并确保其值合理。

## 测试我们的模型以确保良好质量

回顾我们的项目，我们在为 ABC_BANK_POSITION 源添加测试方面做得相当好，因为我们正在检查我们关心的列是否不为空。

我们投入的精力较少来为其他层添加测试，因为我们专注于构建模型本身；在这一节中，我们将遍历示例的各层并添加一些重要测试，以确保我们的应用程序按预期工作。

### 测试复合键的唯一性

在 ABC_BANK_POSITION 源中，我们正在检查 SYMBOL 列是否唯一。然而，这真的正确吗？

嗯，如果我们只考虑一个人的单个投资组合，则是的，但如果我们考虑一个人可能在同一家银行拥有多个账户，那么我们可能应该承认这太严格了。

当我们查看 STG 层时，我们可以看到 POSITION_HKEY 由两个字段 ACCOUNT_CODE 和 SECURITY_CODE 定义，所以我们有一个复合键，这是常见情况。

由于这也看起来更符合现实要求，让我们看看如何在源上测试此复合键。

建议的解决方案是使用分隔符创建它们的连接列（以避免‘ab’||‘c’等于‘a’||‘bc’并且也等于 ‘’||‘abc’ 或 ‘abc’||‘’），并对其进行测试，但我们无法更改源，因此此解决方案不可行。

我们可以将测试移至下一层，在那里我们已经将 POSITION_HKEY 列定义为这些列的组合，外加哈希。这可行，但如果我们可以在源上测试，那更好，这样我们就知道问题不在我们的代码中，而在我们的假设与传入数据不一致。

为了将测试保留在源层，我们有两个替代方案——在源 YAML 文件中创建列的匿名连接，或使用 dbt_utils 包中的 unique_combination_of_columns 测试。

第一个方法很直接但可能存在性能问题，而第二个是应用于表的测试，并且是高效的解决方案。

让我们看看这两种方法，然后你可以决定你更喜欢哪一种。打开 source_abc_bank 文件并为 ABC_BANK_POSITION 表添加以下代码：

```
- name: ABC_BANK_POSITION
  tests:
    - dbt_utils.unique_combination_of_columns:
        combination_of_columns:
          - ACCOUNTID
          - SYMBOL
  columns:
    - name: CONCAT_WS('-', ACCOUNTID, SYMBOL)
      tests:
        - not_null
        - unique
    - name: SYMBOL
      tests:
        - not_null
```
