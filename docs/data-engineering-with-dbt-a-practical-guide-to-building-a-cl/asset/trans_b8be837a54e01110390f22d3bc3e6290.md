
5. **数据写回**：最终，业务用户可以在报表工具中与数据交互，生成反馈回数据平台的数据。业务用户的输入以及机器学习洞察可以产生数据，这些数据甚至可以被发送回源系统。

这个流程非常通用，几乎可以应用于所有用例，主要的巨大差异在于各步骤的执行方式以及每一步的结果。

> **关于数据网格的说明**
>
> *步骤 2 和步骤 3*在数据网格的情况下会有所不同，因为不存在中央平台，这些步骤以去中心化的方式执行，并增加了一些机制，允许业务的其他部分访问和使用在其他地方产生的精炼数据。本质上，步骤是相同的，但范围不同，因为我们并不是要构建一个完整的数据平台，也不是所有数据都会以原始源数据的形式出现。在数据网格中，每个部门在设置其本地数据平台时，会用来自其他部门数据平台的更精炼的数据源替换相同的源系统。

在接下来的章节中，我们将更详细地分析这些步骤。

## 数据创建

通常，我们可以确定数据创建的三种主要数据源类型：

- 运营系统，包括**企业资源计划（ERP）**软件以及各类业务系统，更不用说 Excel 文件，它们仍然是许多业务流程的基石。最有价值且易于使用的数据通常产生于运营系统，运营人员开展日常运营并生成与公司运营保持一致的数据。

- 生产系统，包括监控生产现场的 IoT 系统。

  这些系统可以产生大量非常底层的数据，通常使用专门的或行业特定的格式，使得这类数据与公司的业务思维相去甚远，且不太容易使用。

- 在线系统，包括营销和网站，可能产生大量数据。这些系统可以产生高层次的、易于使用的数据，例如在线销售和支付，以及大量关于用户行为的低层次数据，这些数据需要复杂的分析工具。这是机器学习的应用领域之一，用于理解和预测用户行为。

理解我们使用的数据源至关重要，因为数据的速度和结构化程度是决定如何移动和管理数据的关键因素。

你可以理解，处理高容量、半结构化的 Web 数据、来自**变更数据捕获（CDC）**的结构化 ERP 数据以及不稳定的 IoT 数据是非常不同的。

在本书的第二和第三部分，我们将看到管理不同类型数据的模式。

## 数据移动与存储

如果我们所使用的源系统不提供所需的分析工具，或者我们需要将这些系统的数据与其他系统的数据集成，我们面临的第一个障碍是如何将数据从这些源系统移动到可以进行分析的地方。

如果你的源系统足够标准、足够通用，以至于受到一个或多个数据提取工具（如 Fivetran、Stitch 或 Supermetrics）的支持，那么你可能会很省心，只需配置工具即可让数据流动起来。

在那些你不够幸运，没有现成工具可以快速可靠地为你移动数据的情况下，你需要设计自己的数据移动方案，并考虑以下方面：

- 如何从源系统提取数据
- 如何将数据从源移动到存储位置
- 长期在哪里以及如何存储提取的数据

在这三个主要操作中，有很多细微之处需要考虑，我们将在接下来的章节中讨论。

### *从源系统提取*

最理想的情况是，源系统被设计为提供数据甚至其状态的外部可观测性，而无需处理系统内部。这意味着系统将其变更发布在一个易于读取的地方（通常是队列）。在这种情况下，我们不会有丢失任何变更的风险，也不必急于获取数据，因为所有数据都在那里供我们读取，并且会保留一段时间。

如果我们能够接入**数据库（DB）**的日志系统，我们也能达到同样的效果，因为数据库本身会将所有正在执行的变更写入其中。

如果源系统在设计时就考虑到了数据导出，那么从源系统提取数据可能很简单；但如果源系统是一个复杂的应用程序，没有构建外部接口，而且可能文档也很少，那么提取数据可能会很困难。

在所有这类情况下，即使我们可以完美地复制数据库表，表本身的设计或应用程序逻辑可能很适合外部可观测性，因为如果不按照应用程序自身的规则进行解释，数据本身可能处于不一致状态。

一个例子是，当系统删除已完成或不再有效的内容时，例如删除已取消的发票，但保留连接发票和订单的多对多表中的条目。

这是一个简单的案例，一旦你弄明白了；但其他案例更为微妙，所需的业务逻辑可能很难仅从数据中反向推导出来。

另一个常见例子是后续变更覆盖了自身，例如文档的不同状态。如果我们获取表的变更（快照）不够频繁，就会错过中间步骤。这可能不是问题，但应该被知晓，因为数据平台将无法提供所有的历史变更，也无法解释在现实世界中观察到的所有行为。

在下面的列表中，我们描述了最常见的提取类型：

- **基于事件的可观测性**：这是指系统本身发布被认为对外部应用有用、需要其知晓的变更。如果设计得当，我们可以保证不会丢失（重要的）中间步骤，并且不存在逻辑不一致。一个特殊情况是，事件不仅仅是数据变更事件，而是*业务事件*，即具有业务意义、定义明确的事件，例如创建订单或接受付款。事件的语义与业务流程相关联，这为事件数据提供了额外的上下文，其信息通常还可以用于最初设计事件时未考虑到的额外用例。

- **变更数据捕获**：这是指我们可以连接到数据库日志或源系统的其他事件流。虽然我们可以确保不会丢失任何中间变更，但仍然可能存在逻辑问题，因为表可能不是为外部系统访问而设计的。这是一个非常常见的用例，能够提供良好且可审计的数据，但我们必须警惕不一致的数据。

- **应用程序编程接口（API）**：另一个非常常见的用例是系统提供 API，我们可以用来从系统读取数据。如今，这些 API 往往是 REST API，以 JSON 格式提供数据；而在过去，大多数 API 以 XML 格式提供数据。

  在这种情况下，很大程度上取决于 API 设计的质量。最常见的问题源于 JSON 和 XML 可以表示嵌套结构，且关系在嵌套中一目了然，而 SQL 表只能表示扁平结构。要在 SQL 中表示嵌套结构之间的关系，我们需要至少两个表和一些键。如果我们希望能够随时间管理这种关系，我们需要 JSON 或 XML 中两种结构的键；否则，我们就无法确定组成关系的每个表中的哪些结构应该添加、更新甚至删除。

- **数据库快照**：这是另一种非常常见的方法，即在特定时间（无论是定期还是按需）从源系统导出数据，可能包含所有数据（全量数据导出），也可能只包含最新数据（自某个已知时间以来创建或更改的数据）。“快照”这个名称提醒我们，数据是特定时间点的“原样”数据。
