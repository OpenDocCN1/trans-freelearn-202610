
```
tests:
  - dbt_utils.unique_combination_of_columns:
      combination_of_columns:
        - ACCOUNT_CODE
        - SECURITY_CODE
  - name: DIM_SECURITY
    columns:
      - name: SECURITY_CODE
        tests:
          - not_null
          - unique
```

在上面这段代码中，我们测试了两个模型的主键。我们提醒你，使用 `unique_combination_of_columns` 宏测试的两列并不会检查它们是否为空，因此你应该添加必需的列级测试。

为了能够测试维度具有默认记录且只有一个默认记录键，我们需要创建相关的通用测试，那么让我们开始吧。

3. 在 `macros/tests` 文件夹中创建一个 `has_default_key.sql` 文件，并添加以下代码：

```
{% test has_default_key ( model, column_name
, default_key_value = '-1'
, record_source_field_name = 'RECORD_SOURCE'
, default_key_record_source = 'System.DefaultKey'
) -%}
{{ config(severity = 'error') }}
WITH
default_key_rows as (
    SELECT distinct {{column_name}},
        {{record_source_field_name}}
    FROM {{ model }}
    WHERE {{column_name}} = '{{default_key_value}}'
    and {{record_source_field_name}} = '{{default_key_record_source}}'
),
validation_errors as (
    SELECT '{{default_key_value}}' as {{column_name}},
'{{default_key_record_source}}' as {{record_source_field_name}}
    EXCEPT
    SELECT {{column_name}}, {{record_source_field_name}}
    FROM default_key_rows
)
SELECT * FROM validation_errors
{%- endtest %}
```

此测试验证存在一行具有正确的值和记录来源。

4. 在 `macros/tests` 文件夹中创建一个 `warn_on_multiple_default_key.sql` 文件，并添加以下代码：

```
{% test warn_on_multiple_default_key ( model, column_name
, default_key_value = '-1'
, record_source_field_name = 'RECORD_SOURCE'
, default_key_record_source = 'System.DefaultKey'
) -%}
{{ config(severity = 'warn') }}
WITH
validation_errors as (
    SELECT distinct {{column_name}},
        {{record_source_field_name}}
    FROM {{ model }}
    WHERE {{column_name}} != '{{default_key_value}}'
    and {{record_source_field_name}} = '{{default_key_record_source}}'
)
SELECT * FROM validation_errors
{%- endtest %}
```

此测试在存在具有默认记录记录来源的行、但其键不是默认记录预期键时，会引发警告。如果你想要区分事实表中没有外键的不同原因，这可能是一个有效的情况，例如：数据缺失（-1）、未来/尚无数据（-2）、错误/不正确的值（-3）以及有意留空/不适用（-4）。如果是这种情况，我们建议一旦你确认多个键是有意为之，就移除该测试。

5. 让我们通过编辑 `_portfolio.yml` 文件来应用这两个测试。

在维度的主键（`SECURITY_CODE`）下添加这两个测试：

```
- name: DIM_SECURITY
  columns:
    - name: SECURITY_CODE
      tests:
        - not_null
        - unique
        - has_default_key
        - warn_on_multiple_default_key
```

现在我们已经定义了两个测试，`has_default_key` 和 `warn_on_multiple_default_key`，你可以看到测试每个维度是多么容易。

我们已经遍历了示例项目的各层，并添加了我们认为有用的测试，最终创建了所需的通用测试宏。

### 敏捷开发与协作

在本章中，我们将涉及开发周期中可能最重要的部分，即对项目成功和交付时间贡献最大的部分——让你的团队富有生产力，并渴望通过互相帮助作为团队在项目上工作。

凭借二十多年在不同国家、公司、行业和职能领域工作的经验，我可以说开发人员热爱他们的工作，他们讨厌无所事事，甚至更讨厌愚蠢、毫无意义的事情。

你可以放心，只要你的开发人员清楚要构建什么，并有足够小的增量目标去实现，他们就会构建你的项目，因为这正是带给他们满足感的东西。

事情并不是这样运作的。构建软件和创建数据平台在很大程度上是以有组织的方式编写新代码。这是一个创造性过程，不同的能力、经验和观点都很重要。它更接近于在已知行业中发明新产品的过程。

在构建数据平台的过程中，公司和需求可能会发生变化；数据平台基础的数据和流程会随世界不断变化，并非一成不变。在写下第一行代码之后，甚至在首次发布之前，为跟上不断变化的需求而进行演进就是开发的一部分。

我建议你还阅读敏捷宣言背后的12条原则，可在 https://agilemanifesto.org/principles.html 获取。

它们提供了关于敏捷工作的宝贵且常青的洞见，这些原则中的大多数已成为敏捷团队的基石，例如其中一条说：“可工作的软件是衡量进度的首要标准”。可工作的软件正是你想要的；其他一切只有在多大程度上让你更接近拥有（并保持）可工作的软件时才有用。

### 将敏捷应用于数据工程

审视敏捷宣言的四条声明，关键信息是人员、结果和遵循现实世界的关注比计划和文件更重要。这并不意味着其他要素本身不好，只是它们不是最重要的，它们的重要性在于对其他要素的贡献。

以下是一些适用于数据工程领域的总体考虑：

- 敏捷不是即兴发挥。拥有计划很重要，同时要理解任何计划都不是一成不变的，它会不断变化。计划的意义在于跟踪我们所处的位置、当前期望目标以及我们在领域周边积累的知识。快速失败对于尽早了解此路不通很重要。
- 与了解领域（即业务）的人以及了解技术的人合作选定方向。持续交付并验证中间结果，在每一步只需进行小幅方向调整。你走得越远，方向变化越小，目标越清晰。当遇到失败时，尽快将所学纳入计划，并按需调整方向。
- 前一点的一个重要推论是，在推进过程中不断完善你的目标细节。这是一个迭代过程。你从一个明确的范围和一个总体目标开始，可能对可用数据知之甚少。通过努力并交付初步成果，你最终会明确你想要什么和不想要什么。你也会更好地理解数据中有哪些内容，哪些没有。不断与业务方讨论他们想要什么，并相应调整他们的期望/你的项目。保持信息流通和想法灵活。
