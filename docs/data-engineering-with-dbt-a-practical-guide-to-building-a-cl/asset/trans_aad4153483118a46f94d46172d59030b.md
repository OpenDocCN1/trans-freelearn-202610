

照常，我们从增量物化（materialization）的代码开始。

我们做的第一件事，与保存历史的其他宏一样，是为每个实例检索我们已存储的最后一个版本：

```
WITH
{% if is_incremental() %}
current_from_history as (
  {{current_from_history_with_multiple_versions(
    history_rel = history_rel,
    key_column = key_column,
    sort_expr = sort_expr,
    selection_expr = key_column ~ ', ' ~ diff_column,
    load_ts_column = load_ts_column,
    history_filter_expr = history_filter_expr
  )}}
),
```

这里，我们使用的是 `current_from_history_with_multiple_versions` 宏，其名称已暗示，它是一个专门用于在历史表可以为单个加载时间戳存储多个版本时读取最新版本的宏。在这种情况下，我们还需要 `sort_expr`，一个 SQL 表达式，用于对在同一时间输入/加载时呈现的版本进行排序。

对于此宏，我们需要检索最新版本的 HKEY 和 HDIFF 两列，因此必须在 `selection_expr` 参数中构建此 SQL 表达式。

下面的 `load_from_input` CTE 在选择要保存的行方面具有与我们在其他 `save_history` 宏中相同的功能：

```
load_from_input as (
  SELECT
    i.*
    , LAG(i.{{diff_column}})
      OVER(PARTITION BY i.{{key_column}}
      ORDER BY {{sort_expr}}) as PREV_HDIFF
    , CASE
        WHEN PREV_HDIFF is null
        THEN COALESCE(i.{{diff_column}} != h.{{diff_column}}, true)
        ELSE (i.{{diff_column}} != PREV_HDIFF)
      END as TO_BE_STORED
  FROM {{input_rel}} as i
  LEFT OUTER JOIN current_from_history as h
    ON h.{{key_column}} = i.{{key_column}}
  WHERE {{input_filter_expr}}
```

我们以通常的查询结束，该查询在所有情况下都能产生所需的结果：

```
SELECT * EXCLUDE(PREV_HDIFF, TO_BE_STORED)
FROM load_from_input
WHERE TO_BE_STORED
ORDER BY {{key_column}}, {{sort_expr}}
{%- endmacro %}
```

这里，与其他保存历史宏相比，我们有几个不同之处。

第一个是我们对 `TO_BE_STORED` 列进行了显式过滤。我们本可以在两种情况下使用 `QUALIFY` 谓词，但我们认为在这里使用单个谓词更具可读性。

第二个是我们从最终的 `SELECT` 投影中移除了用于确定要存储行的临时 `PREV_HDIFF` 和 `TO_BE_STORED` 列。

第三个是我们最后添加了 `ORDER BY`，以便于从历史表中读取数据时检索。

现在我们知道了如何在历史表中存储多个版本，让我们来看看 `current_from_history_with_multiple_versions` 宏，该宏用于检索最后一个版本。

宏声明与 `current_from_history` 宏的声明类似，只是增加了 `sort_expr` 参数，用于提供版本的顺序，以及 `qualify_function` 参数的默认值，该参数用于过滤结果：

```
{% macro current_from_history_with_multiple_versions(
    history_rel,
    key_column,
    sort_expr,
    selection_expr = '*',
    load_ts_column = 'LOAD_TS_UTC',
    history_filter_expr = 'true',
    qualify_function = '(rn = cnt) and rank'
) %}
```

在宏声明之后，我们创建一个新变量，通过添加行号和计数窗口函数来扩展提供的 `SELECT` 投影表达式。这些用于通过加载时间戳确定最新版本：

```
{%- set multiple_versions_selection_expression %}
    {{selection_expr}}
    , row_number() OVER( PARTITION BY
        {{key_column}}, {{load_ts_column}}
        ORDER BY {{sort_expr}}) as rn
```

使用这种方法，当 PII 信息从源系统中消失时，它会自然地从您的数据平台中清除。在落地表中，PII 仅保留您在删除导入数据之前决定的保留期，对于包含 PII 数据的表，您可以使其尽可能短；在数据平台中，它仅存储在每天重新创建的表中。

另一个优点是，通过在各处使用相同的代理，您仍然可以连接、计数和分析每个参与者的活动，即使您已“忘记”其 PII。

## 使用增量导出处理 PII

如果我们要处理的 PII 是增量导出的一部分，则解决方案需要更多逻辑，因为我们无法将 PII 存储委托给外部源。这是因为导出仅包含已更改的行，而大多数行很长时间都不会更改。

在这种情况下，实现与之前的步骤 2 不同，因为我们需要在永久表中存储 PII。为了能够在时机到来时删除 PII，我们需要收到一个信号。

信号可以有两种类型：

- 我们收到信息表明某个 PII 不再使用。这可能是因为包含 PII 的行已被删除，或者 PII 本身已更改，从而创建了实体的新版本。如果该版本是旧 PII 的唯一出现，我们需要删除/匿名化它。
- 我们收到信息表明某个 PII 需要被匿名化/删除。

在任何这些情况下，我们都可以使用信号将 MAP 表中 PII 的值替换为其代理，使两个列相同。这将确保在交付层，连接将自动输出代理值。

第一个用例更复杂，因为我们需要制定业务规则来决定何时需要匿名化 PII。

考虑在一个发票中，您有销售人员或操作员姓名的情况。仅仅因为您删除了该发票并不意味着您需要在所有发票中匿名化该值。

同样，当我们收到 PII 的新版本时，我们称之为 PII₂，我们需要决定对之前的版本 PII₁ 做什么，并且通常，正确的操作是什么都不做。

在这种情况下，如果在一张发票中操作员姓名的值被更改，这并不意味着之前操作员姓名的所有版本都必须被匿名化。

针对这种情况的一种解决方案是比较 MAP 表中的代理列表与来自 HIST 表的当前版本的列表。

仅出现在 MAP 表中而未出现在列表中的所有代理都应被匿名化，因为它们不再使用，要么是因为它们已更改，要么是因为使用它的记录已被删除。

```
, current_from_history as (
  {{ current_from_history(
    history_rel = ref('HIST_XXX_Vn'),
    key_column = 'XXX_HKEY'
  ) }}
)
, all_current as (
  SELECT * FROM current_from_history
  UNION ALL
  SELECT * FROM current_from_old_histories
)
{{ current_from_history(
  history_rel ='all_current',
  key_column = 'XXX_HKEY'
) }}
```

前面的代码获取所有先前历史表中的当前实体——即静态表——因为这些历史表不会更改。然后，活动历史中的当前实体将它们放在一起，并从联合数据中取出最新实体。

作为替代方案，根据表中更改的数量，您可以将所有先前历史表中的当前实体添加到活动历史中，并从联合中取出当前实体。实际上，这意味着用包含 `select * from {{ ref('HIST_XXX_Vn') }}` 查询以获取活动历史中所有内容的 CTE 命名为 `active_history` 来替换伪代码中的 `current_from_history`。

此示例也向您展示了，我们所看到的宏通常可以应用于类似的情况，即使它们与我们引入它们的用例不完全相同。

通过理解它们的作用，您可以在新上下文中应用它们，或派生出一个新宏来执行您经常需要的操作。
