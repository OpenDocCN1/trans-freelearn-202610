## 定义通用测试

要定义通用测试，或者覆盖现有的开箱即用测试，您可以编写一个测试 Jinja 块，在 SQL 文件中包含测试的 SQL。

测试块与宏非常相似，因为通用测试曾经是名称以 `test_` 开头的宏，而且它们的工作方式与宏基本相同——定义一个接受参数并以测试结果形式评估其结果的函数。

通用测试的 SQL 必须编写为返回测试失败的行，使用我们在单一测试中看到的相同逻辑。如果您测试一个等于 42 的列，那么您的 SQL 应选择所有列值不为 42 的行。

通用测试使用 YAML 文件应用，并且必须始终至少定义两个参数：`model` 和 `column_name`，这两个参数会自动用于向每次测试调用传递资源引用，以及传递测试在 YAML 文件中应用的列名称。

您可以在测试定义中添加其他参数，带或不带默认值，就像处理宏一样。然后您可以在 YAML 文件中为这些额外参数传递值，稍后我们开发第一个通用测试时会看到。

从 dbt 1.0.0 版本开始，您可以将通用测试放在两个位置：

- 在 `macro` 文件夹中，您还可以在其中定义宏。这是最初将通用测试定义为宏的遗留方式，当您想在通用测试中使用其他临时宏来定义复杂逻辑时，它会变得很方便。
- 在 `tests/generic` 文件夹中，与单一测试相邻。这个特殊文件夹是在 dbt 1.0.0 中引入的，允许您将所有测试放在同一文件夹下，通用测试放在 generic 文件夹中，而单一测试则按您认为合适的方式组织。

我们建议您选择这两个位置之一来组织您的通用测试。

我们将使用 macro 文件夹下的 tests 子文件夹，以便在需要时可以在测试旁边定义宏，而 tests 文件夹仅用于单一测试。

## 通用测试模式

为通用测试编写的 SQL 使用 `model` 和 `column_name` 参数来测试您已为其配置测试的资源和列，但您的测试可以使用更多参数。

```
SELECT * FROM validation_errors
{%- endtest %}
```

在 no_hash_collisions 通用测试的测试块声明中，我们声明了三个参数，将 hashed_fields 添加到了必需的 model 和 column_name 参数之外。

我们将 model_data CTE 重命名为 all_tuples，以强调我们获取的是由哈希字段和用于构建哈希的所有字段组成的所有不同元组。

然后我们选择了存在多个字段元组的所有哈希，因为这将是一种冲突情况——由两个不同的值集生成相同的哈希。

- 3. 创建一个 snapshots.yml YAML 文件来描述和测试快照：

```
version: 2
snapshots:
  - name: SNSH_ABC_BANK_POSITION
    columns:
      - name: POSITION_HKEY
        tests:
          - no_hash_collisions:
              hashed_fields: ACCOUNT_CODE, SECURITY_CODE
```

model 和 column_name 参数由 dbt 自动管理，因此我们无需将它们传递给测试，但我们需要为通用测试中没有默认值的任何其他参数提供值，例如 hashed_fields。我们省略了描述，但描述应该是存在的。

您将参数值作为所声明测试的属性来提供。实际上，这意味着您在测试名称后添加一个冒号（:），然后在下一行，相对于测试名称缩进，写入参数名称、冒号（:）和参数值，就像我们在前一个示例中为 hashed_fields 参数所做的那样。

参数值可以是 Jinja 表达式，但此时应适当加上引号。

- 4. 在快照上运行测试，看看您闪亮的新测试的实际效果：

```
dbt test -s SNSH_ABC_BANK_POSITION
```

通过在测试 Jinja 块中编写一些 SQL，并使用一些关于必需参数名称的约定，我们轻松定义了一个通用测试。

让我们看看如何添加一个支持使用此测试的宏，以便我们可以使用与定义哈希相同的代码来用于测试，而不必提供相同的字段列表，但无需加引号。

如果您查看 STG 模型，您会看到为了构建哈希键和哈希差异，我们将字段名称列表传递给 dbt_utils.surrogate_key 宏。通过使用 join 筛选器，很容易生成以逗号分隔的名称列表，所以让我们来做吧：

- 1. 将用于生成字段列表的宏添加到 no_hash_collisions 文件中：

```
{% macro as_sql_list(hashed_fields_list) -%}
{{ hashed_fields_list|join(', ') }}
{%- endmacro %}
```

这个宏很简单；它使用 Jinja 的 join 筛选器将字段名按逗号连接起来，但通过快速复用我们用来定义哈希字段的同一列表，它使操作变得简单，使测试编写更快捷并减少错误。

- 2. 在 snapshots.yml 文件中为 POSITION_HDIFF 字段添加 no_hash_collisions 测试，该测试使用一长串字段：

```
- name: POSITION_HDIFF
  tests:
    - no_hash_collisions:
        hashed_fields: "{{ as_sql_list(
          ['ACCOUNT_CODE', 'SECURITY_CODE',
           'SECURITY_NAME', 'EXCHANGE_CODE',
           'REPORT_DATE', 'QUANTITY', 'COST_BASE',
           'POSITION_VALUE', 'CURRENCY_CODE'
          ] ) }}"
```

您可以看到，在参数定义中，我们通过传递字符串列表，在花括号内调用宏来生成包含所需内容的字符串。如果宏在 YAML 文件中正确用引号括起来，它会工作得很好。在这种情况下，我们使用双引号，因为我们想对字符串列表使用单引号。

通过这个简单示例，我们向您展示了一些重要过程——定义带有额外参数的通用测试、传递额外参数、添加宏以简化通用测试的使用，以及最终在 YAML 文件内调用宏来提供值。

## 配置测试

与大多数 dbt 资源一样，对于测试，除了传递参数外，还有一些配置可用于控制测试行为。

您可以在不同的层级上配置测试，最通用的配置优先级最低，最专业的配置优先级最高：

- 在全局配置文件 dbt_project.yml 中，您可以使用 tests: 属性配置所有测试，如下例所示：

```
tests:
  portfolio_tracking:
```

前面的代码展示了如何将配置作为属性应用于 YAML 文件中的通用测试，但它们也可以通过 `config()` 块或通常在主配置文件中应用于任何测试。

以下是对它们的简要描述：

- where: 这会将测试限制为满足以字符串形式传入的 where 子句的行。这通常用于将测试限制为活动行（某些列不为空）或某个时间范围内的数据。
- severity: 这将在测试失败时将严重级别设置为 error 或 warn。默认值为 error。
- error_if 和 warn_if: 这些配置一个 SQL 条件，该条件可以与失败次数进行比较以微调严重级别，允许您应用阈值来产生错误或警告。两个配置的默认值都是 != 0。
- fail_calc: 这配置应用于测试查询以报告错误的聚合函数。默认值为 count(*)，即测试失败的行数。
- limit: 这配置测试返回失败行的最大数量。通常不设置，仅在将错误存储到大表中时有用。
- store_failures: 这是一个用于启用或禁用存储测试失败行的配置。默认值为 false，表示不存储失败行。

这些配置会从 severity 和 error_if 条件开始检查，以评估是否必须引发错误；如果未触发错误，则检查 warn_if 条件。

例如，您可以使用 sum(n_records) 查看具有重复项的总行数，或使用 max(n_records) 查看找到的最大重复数。您需要充分了解测试 SQL 代码，才能应用正确的聚合表达式。

当配置为存储测试失败时，dbt 会将测试查询的结果（即失败行）保存到 schema 中与测试同名的表中，并带有默认的 dbt_test__audit 后缀。这使您可以轻松分析失败行。

除了这里提到的测试特定配置外，还可以将其他通用配置应用于测试，例如 enabled、tags 和 meta，以及 database、schema 和表别名，以配置失败存储的位置。
