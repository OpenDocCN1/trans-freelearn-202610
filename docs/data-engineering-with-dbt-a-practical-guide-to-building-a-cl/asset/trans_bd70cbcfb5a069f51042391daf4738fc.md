## 通过测试提供可靠性

如果你只从本节带走一样东西，那就是：“测试将成为让你安睡的超能力。”

测试确保事情按你期望的方式发展，并在情况并非如此时提醒你。

它们是你的军队，保护你的工作和时间免受数据源损坏和不可避免的代码错误（你自己的和同事的）的邪恶影响。

这就是真正的力量。

缺乏测试，再加上不严谨的开发（因为编写SQL查询的人往往缺乏软件工程背景），使得“救火”成为太多数据团队中最常见的活动；而更改数据管道中某些被大量使用的部分（比如客户或订单）的想法，可能会让整个团队紧张不已。你是否经历过？

我们希望你能摆脱这些噩梦。在前面的章节中，我们提供了关于如何组织代码并使其易于阅读和维护的合理指南。在本节中，我们将向你展示如何在部署的转换关键节点设置守卫，以检查一切是否按预期进行。

我们在*第5章*中介绍了dbt开箱即用的通用测试，并向你展示了如何在YAML文件中使用它们；在本章中，我们将更详细地讨论所有类型的测试及其用法。

## 测试类型

每个测试都检查对dbt资源的某个预期是否得到满足。

在dbt中，测试以SQL查询的形式实现，你也可以将它们编写为SQL查询，但大多数时候，你只需在YAML文件中以声明方式将它们应用于dbt资源（模型、源、快照或种子）或其某个列。

dbt测试运行一条SELECT语句，返回不满足你所测试预期的行，因此空结果集表示测试通过，而返回的每一行都表示测试失败。这些失败的行可以自动保存以供你检查。

例如，not-null测试的查询看起来像`SELECT column FROM model WHERE column is null`。你可以看到，如果存在column为null的行，那么这些行会被返回；如果没有null值的行，则查询没有结果行。

在dbt中，你可以用两种方式表达测试：

- 通过编写一个普通的SQL查询来测试你的假设。这被称为**单一测试**，因为它用于单个场景。你通常只会使用少量此类测试来覆盖现有通用测试未覆盖的罕见情况。
- 通过编写或使用参数化SQL查询并传递所需参数；这被称为**通用测试**，因为原则上你可以用它来测试任何dbt资源。这类测试将成为你的家常便饭，而且你将从包中获得大多数测试，因为通常你会反复测试与其他人在其他项目中测试的相同类型的假设。

在讨论要编写哪种测试之前，让我们先看看编写测试的两种方式。

## 单一测试

这是最简单的测试形式，其测试能力仅受限于你用SQL表达待测试假设的能力。

鉴于我们最终会在大多数dbt资源上测试相似的假设，而且通用测试一旦写好就非常简单易用，那么通用测试成为最常见的测试类型也就不足为奇了。

在大多数情况下，你只需以纯声明方式使用通用测试，将想要应用于资源的通用测试作为列表元素添加到YAML文件中dbt资源的`tests`属性下，就像我们在*第5章*中所做的那样。

## 开箱即用的通用测试

你可能还记得*第5章*，dbt自带以下四种通用测试：

- `not_null`：测试表中某列永不为null。
- `unique`：测试某列中的值是唯一的。
- `relationships`：测试两个表之间的参照完整性，即一个表中的每个外键值都存在于指定表的指定列中。换句话说，你测试被测试表中没有*孤儿记录*。
- `accepted_values`：测试列中的值是否属于列出的值之一。

使用这些基础测试，你已经可以强化项目，并覆盖构建管道时所做的基本假设，例如主键和业务键唯一且不为null，外键没有孤儿记录，以及类别具有预期集合中的值。

dbt提供的通用测试覆盖了最常见的测试需求，并且可以进一步配置以针对特定情况定制——例如，要求`email`这样的列唯一，但仅针对活跃用户；或者认为单个姓名为空的客户不足以阻塞ELT，只应发出警告，而超过10个错误则可能有必要停止管道。

## 应用通用测试

你将使用YAML文件将通用测试应用于模型，就像本书前面我们对源所做的操作一样。

例如，下面是`refined.yml`文件，它对refined层中的`REF_POSITION_ABC_BANK`模型提供了描述和测试：

```yaml
version: 2
models:
  - name: REF_POSITION_ABC_BANK
    description: The positions we have in the ABC Bank portfolio.
    columns:
      - name: UNREALIZED_PROFIT
        description: The unrealized profit on the position.
        tests:
          - not_null
      - name: UNREALIZED_PROFIT_PCT
        description: The unrealized profit % on the position.
        tests:
          - not_null
```

上面的代码片段演示了not_null测试在两个不同列上的基本用法。稍后，你将看到如何添加额外配置以更好地定制测试行为，例如让测试返回警告、仅在超过某个阈值时出错，或在特定条件下应用测试。

dbt提供的默认测试在列级别应用，但测试也可以应用于资源级别，无需嵌套在列下。

以下语法用于将`has_default_record`测试应用于`REF_SECURITY_INFO_ABC_BANK`表：

```yaml
version: 2
models:
  - name: REF_SECURITY_INFO_ABC_BANK
    tests:
      - has_default_record
```

这对于应用于表而非特定列的测试很常见，例如假设的`table_is_not_empty`测试。

## 来自包的通用测试

你可以用开源或私有包提供的许多其他通用测试来补充开箱即用的通用测试，从而用他人甚至你自己编写的通用测试扩展项目。

事实上，在之前关于包的部分，我们提到了两个提供大量测试的包——`dbt_utils`和`dbt_expectations`。

`dbt_utils`包提供了丰富的通用测试选择，补充了dbt Core开箱即用的四个测试，使你能够覆盖常规测试需求，从而很少需要自己编写通用测试，你可能只是为了可读性或配置方便而使用它。

请查看我们在上一节中描述的测试，以及dbt Hub上`dbt_utils`页面中的其余测试：https://hub.getdbt.com/dbt-labs/dbt_utils/。

`dbt_expectations`包极大地扩展了可用的通用测试，并允许你使用与Python的Great Expectations测试套件相同的测试风格向项目添加测试。

为了让您了解可用测试的扩展范围，以下是`dbt_expectations`包0.8.0版本的测试类别列表：表形态、缺失值、唯一值和类型、集合和范围、字符串匹配、聚合函数，以及多列和分布函数。
