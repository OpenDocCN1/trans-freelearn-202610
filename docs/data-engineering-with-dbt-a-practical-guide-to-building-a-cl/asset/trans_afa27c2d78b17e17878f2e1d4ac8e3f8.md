
机器学习和人工智能流程可以使用完整历史或精炼数据作为输入数据，并生成更精炼的数据，这样就能自然地将其添加到所需的数据集市中。

## 反馈回源系统

数据流中最后一个可能的步骤，是关于数据平台中生成的数据以及在其他系统中使用这些数据的需求。

一个常见用例是将数据平台中计算出的某些数据带回到某个运营系统。这在营销和 CRM 领域非常常见，数据平台可用于计算客户细分以及各种度量指标，然后需要将这些指标反馈回营销工具和 CRM 平台。

另一个日益常见的用例是，某些机器学习流程正在为运营系统构建有价值的数据，例如销售预测或预测性维护数据。

在所有这些情况下，我们可以采用与之前将数据从源系统移动到数据平台时相似的思路来处理该主题，但一个很大的区别是：许多系统提供了某种导出的方式，却几乎没有提供任何导入数据的方式。

即使目标应用程序确实有加载数据的 API，数据加载器也很少具备同样广泛的回载数据能力。

不要绝望，因为有一些工具专注于“反向 ETL”流程，即把数据从数据仓库移回业务工具/运营系统，例如 Census（可在 `https://www.getcensus.com/` 获取）。

数据平台中生成数据的另一种情况是：使用 BI 工具的人员可以在 BI 工具的报表中编辑数据，并以某种方式将其发送回数据平台本身。这通常被称为 BI 工具中的写回功能。

一些示例用例包括：人们可以使用 BI 工具输入缺失信息或在特定报表中提供更新值，例如管理库存水平或更新预测。

在这种情况下，更好的做法是将从 BI 工具写回的新数据视为数据平台的新输入，并将其作为转换链的一部分进行集成，而不是直接修改为报表提供支持的数据集市。这同样符合让数据变更可见的精神，并且无需处理先前的状态即可从头重现最终结果。

现在我们已经探索了数据生命周期及其演变，接下来将继续学习现代数据栈，它使数据工程变得更加顺畅。

## 理解现代数据栈

当我们谈论数据工程时，我们涵盖了端到端覆盖数据生命周期的所有技能、工具和实践，如上一节所述，从数据提取到用户数据消费，最终还包括数据写回。

这是一套庞大的能力和工具，从安全到脚本和编程，从基础设施运维到数据可视化。

除了非常简单的情况外，单个人能够对所有涉及领域有透彻理解和良好技能来完全覆盖这一切，是相当罕见的，更不用说还有时间去开发和维护了。

### 传统数据栈

传统数据栈通常由数据工程师构建，他们开发临时的 ETL 流程，从源系统提取数据，并在本地转换，然后以精炼形式加载到用于支撑报表的传统数据库中。这被称为 ETL 管道。

该过程包括创建一些临时集成来从源系统提取数据，确定要提取的内容，并设计提取逻辑。通常，它还包含所需的数据转换（包括汇总），最后才将“已消化”的数据加载到用于报表的普通数据库中。

使用 MySQL 或 SQL Server 这类事务型数据库进行报表会带来巨大问题，需要各种技巧才能实现报表功能。主要问题在于，这些数据库针对与表中的整行数据进行交互的大量小型操作进行了优化。它们是面向行的。

事实上，分析工作恰恰相反：它需要对大量数据执行少量查询，而且通常只使用少数几列，而不是所有列。为了解决分析工作负载的需求，列式数据库应运而生，但在 2000 年代的头十年，它们并未被广泛了解，而且与“常规”面向行的 OLTP 数据库相比，它们仍然相当昂贵。

使用传统 OLTP 数据库时，最容易出现问题的折衷之一是在将数据加载到报表数据库之前应用业务规则和数据汇总。这造成了一种局面：源数据或业务规则的任何变化都会影响整个数据历史。这反过来又要求修复转换逻辑以及现有数据，以符合新逻辑。如你所见，这是双倍的工作，而且也很可怕，因为你必须修改历史数据的唯一副本。

另一个问题是，工具的大小和功能都受到限制，编写集成并保持其运行的时间也同样有限，因此通常只加载真正需要的数据，而且往往只保留有限的时间段。

数据分析师会从数据库获取已加载的数据，为最终用户构建报表和仪表板，并偶尔对数据的某些方面进行深入分析。

即使在这些深入分析中，他们也只能使用已有的数据：如果某些内容被过度汇总，他们除了请求重新加载之外别无他法；如果某些有用数据不可用，他们也只能再次请求数据工程师通过创建另一个 ETL 管道来添加数据。

难怪最终用户常常需要等待新数据被添加，或者只能从可用数据中获得部分答案。

数据工程师和分析师之间的工作分工，也使得数据分析师更难以充分理解数据及其局限性，也让数据工程师更难理解他们交付的数据的使用情况与质量。

通常，几乎没有测试或数据质量检查，导致数据团队在数据生命周期的两端持续“救火”：源系统中不断变化/缺失的数据，以及报表中过时/错误的数据。

另一点是，鉴于维持 ETL 管道运行的技术难度以及数据工程师与业务问题之间的距离，通常更多的精力花在了让数据流动上——这是一个传统且客观、无人能质疑的指标——而不是理解数据和确保其质量上。

### 现代数据栈

快进到 2010 年代中期，我们发现自己的处境好多了：

- 云上的分析型数据仓库，例如 BigQuery、Redshift 和 Snowflake，越来越普遍，并且对大多数数据团队来说已成为可负担的选择
- Stitch 和 Fivetran 等数据移动/集成工具，可以非常轻松地将数据从传统数据库和常见业务平台移动到云数据仓库
- 现代 BI 工具开始提供改进的自助式报表能力，供高级用户使用

云数据仓库的出现是一个转折点，它提供了海量的存储和处理能力，而无需预先购买容量。

在用户侧，这使公司能够将大量数据加载到这些云**数据仓库（DW）**中，并以更快、更便宜的方式处理数据，成本仅为本地系统的一小部分。

在商业侧，这促进了数据移动工具的创建和兴起，使得从最常用的系统（如传统 DBMS 以及运营和 SaaS 软件）快速、轻松地将数据加载到这些标准云 DW 之一成为可能。

采用这种现代数据栈，可以轻松地将来自源系统的原始数据加载到云 DW 中，从而减少了数据工程领域最复杂、最耗时的工作需求。
