

拥有一种只需在短时间内设置好就能将数据送到你的数据仓库（DW）的工具，使得一个人就能负责源系统的数据生命周期的全部或大部分工作，前提是这些源系统可以用数据移动工具来管理。它也解决了学习并跟上这些丰富但经常变化的 API 的需求，因为这现在已成为数据移动工具开发团队的问题。

如今，你只有在没有工具可以自动化数据移动时，才会作为最后的手段创建临时管道。

原始数据易于获取，促进了下一个问题的产生：我们如何改进转换阶段并使其有效？*这正是 dbt 被创建来帮助解决的问题。*

我们将在下一节中对此提供更多细节。

数据栈中的另一个巨大变化是，将尽可能少的逻辑放入报表工具中并保留在 DW 中，以便你只需编写和管理一次，它就可以为每份报表和每种其他用途提供服务。这之所以成为可能，是因为随着运行 ETL 管道所需的编程和基础设施减少，负责转换的工程师拥有更好的 SQL 和仓库技能，而现代工具如 dbt 使直接在转换中编写和测试业务逻辑变得更容易。

现在我们已经描述了传统和现代的数据栈，让我们深入探讨 dbt 的核心：作为一个敏捷团队，将原始数据转换成语义信息。这就是分析工程的核心，我们将在下一部分讨论。

## 定义分析工程

我们在上一节中看到，随着现代数据栈的出现，数据移动变得更容易，因此重点已转向管理原始数据并将其转换成语业用户在报表中使用的精炼数据。仍然存在大量需要临时集成和 ETL 管道的案例，但这不再是数据团队的主要关注点，就像过去一样。

另一个哥白尼式的革命是，新的数据栈使数据专业人员能够作为团队工作，而不是延续在传统数据栈中常见的孤立工作。重点现在是应用软件工程的最佳实践，使数据转换开发像构建软件一样可靠。你可能听说过 DevOps 和 DataOps。

随着重点的转移，术语 **分析工程** 出现了，用以标识从访问原始数据到将精炼数据提供给 BI 报表工具的数据生命周期中的核心部分。这并非巧合，因为这也是云 DW 平台和 dbt 所覆盖的数据生命周期部分。

以新的眼光审视数据生命周期，我们可以将其分为以下几个部分：

- **数据集成：** 通过尽可能使用现成的工具将所有数据收集到一个地方，即云数据平台，并在需要时求助于临时数据管道。
- **分析工程：** 将原始数据转换为精炼的、可用的、可信赖的数据。这就是你使用 dbt 所做的工作，使用你偏好的数据平台，在我们的案例中是 Snowflake。
- **数据分析：** 使用精炼数据构建报表、仪表板、机器学习模型等。这是在你的 BI 工具中完成的工作，以使数据对业务用户可访问。

这三个阶段与我们在上一节中看到的并没有太大不同。不同之处在于，在现代数据栈中，我们现在有了与现代工具相一致的清晰边界，这对从事其中的专业角色产生了影响。

## 现代数据栈中的角色

将数据生命周期划分为这三个步骤后，这些是在使用 dbt 和云 DW 的现代数据团队中所属的专业角色：

- **数据工程师：** 拥有脚本/编码和基础设施知识的“传统”数据工程师仍然非常有价值，尤其是当并非所有数据源都能被现代数据加载工具覆盖时。即使在这种情况下，复杂的日程安排、安全性和许多其他主题可能仍需要数据工程师的专业知识和专注。
- **分析工程师：** 一个新角色，牢牢围绕了解并将原始数据转换为有用信息。他们不太关心数据移动管道的开发，而是专注于使数据可用、可使用且可信赖。
- **数据分析师：** 这是传统数据分析师的改进版本，因为现在他们可以理解甚至帮助构建数据模型，并且能够调查更广泛的数据集的能力前所未有。

虽然清楚地区分这三个角色是有意义的，但重要的是要注意它们有很大重叠，核心能力围绕 SQL 和数据素养。

现代数据栈甚至使得拥有一个人的数据团队成为可能，如果你可以在无需编写和照看一个或多个数据管道的情况下移动数据，并且你的业务逻辑不是 constantly 变化的，因此现有的数据模型和报表不需要频繁更改。

## 分析工程师

我们看到分析工程师有点像数据工程师，在收集和理解原始数据方面，又有点像数据分析师，在了解如何创建能够实现良好分析的数据集方面。但该角色的核心是使用允许软件工程师生产和维护可靠软件的最佳实践来转换数据为信息。

从旧栈到新栈的主要变化是，能够并且需要从个人工作转向团队合作，以使用为传统软件工程创建的心态和强大工具来用于数据工程。

构建数据平台的方法变得更类似于构建软件，认识到即使在数据世界中，你也可以构建模块化模型，并且可以通过使用通用、可重用的模型来组合复杂的数据集，就像在构建软件时重用软件组件和库一样。

分析工程师组织数据转换及其依赖关系，就像软件工程师设计应用程序一样，使用可重用模式，并应用关注点分离，以最大限度地减少因多种不同原因而更改模型的需求。

分析工程师的工作不仅仅是编写执行从原始数据到信息的所需转换的 SQL，还要应用或发现模式来分解、结构化和以有意义且可重复的方式组织转换，使用清晰的命名，以便团队中的每个人都知道这些转换的每个步骤可以预期什么。

在下一节中，我们将讨论可以从传统软件工程中采用的最佳实践，以改进数据项目。

## DataOps – 数据的软件工程最佳实践

事实是，许多数据团队曾经、现在仍然不是由具有软件工程背景的人组成，因此他们错过了采用属于 DevOps 的现代软件工程技术。

名副其实，DevOps 运动为软件开发领域带来了巨大改进，帮助团队变得更具生产力并对工作更满意。

简而言之，DevOps 的核心思想是为团队提供所需工具，以及对整个开发周期的权限和责任：从软件编码到质量保证（QA），到发布然后运行生产操作。

实现这一目标的基石是使用自动化来避免手动执行重复性任务，例如发布和测试，强调自动化测试，依赖主动自动化监控，最重要的是，团队对代码的共同所有权。

这些思想通过四眼原则得到体现，要求每段代码至少被两个人看到并批准（通过结对、拉取请求或代码审查），以及童子军规则，该规则促使你在触碰一段代码时确保它比你触碰它之前处于更好的状态，无论是谁编写的，从而随着时间的推移改进工作。
