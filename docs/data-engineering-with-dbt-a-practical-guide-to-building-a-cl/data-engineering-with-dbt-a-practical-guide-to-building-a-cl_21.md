## 使用增量导出处理 PII

如果我们要处理的 PII 是增量导出的一部分，则解决方案需要更多逻辑，因为我们无法将 PII 存储委托给外部源。这是因为导出仅包含已更改的行，而大多数行很长时间都不会更改。

在这种情况下，实现与之前的步骤 2 不同，因为我们需要在永久表中存储 PII。为了能够在时机到来时删除 PII，我们需要收到一个信号。

信号可以有两种类型：

- 我们收到信息表明某个 PII 不再使用。这可能是因为包含 PII 的行已被删除，或者 PII 本身已更改，从而创建了实体的新版本。如果该版本是旧 PII 的唯一出现，我们需要删除/匿名化它。
- 我们收到信息表明某个 PII 需要被匿名化/删除。

在任何这些情况下，我们都可以使用信号将 MAP 表中 PII 的值替换为其代理，使两个列相同。这将确保在交付层，连接将自动输出代理值。

第一个用例更复杂，因为我们需要制定业务规则来决定何时需要匿名化 PII。

考虑在一个发票中，您有销售人员或操作员姓名的情况。仅仅因为您删除了该发票并不意味着您需要在所有发票中匿名化该值。

同样，当我们收到 PII 的新版本时，我们称之为 PII₂，我们需要决定对之前的版本 PII₁ 做什么，并且通常，正确的操作是什么都不做。

在这种情况下，如果在一张发票中操作员姓名的值被更改，这并不意味着之前操作员姓名的所有版本都必须被匿名化。

针对这种情况的一种解决方案是比较 MAP 表中的代理列表与来自 HIST 表的当前版本的列表。

仅出现在 MAP 表中而未出现在列表中的所有代理都应被匿名化，因为它们不再使用，要么是因为它们已更改，要么是因为使用它的记录已被删除。

```
, current_from_history as (
  {{ current_from_history(
    history_rel = ref('HIST_XXX_Vn'),
    key_column = 'XXX_HKEY'
  ) }}
)
, all_current as (
  SELECT * FROM current_from_history
  UNION ALL
  SELECT * FROM current_from_old_histories
)
{{ current_from_history(
  history_rel ='all_current',
  key_column = 'XXX_HKEY'
) }}
```

前面的代码获取所有先前历史表中的当前实体——即静态表——因为这些历史表不会更改。然后，活动历史中的当前实体将它们放在一起，并从联合数据中取出最新实体。

作为替代方案，根据表中更改的数量，您可以将所有先前历史表中的当前实体添加到活动历史中，并从联合中取出当前实体。实际上，这意味着用包含 `select * from {{ ref('HIST_XXX_Vn') }}` 查询以获取活动历史中所有内容的 CTE 命名为 `active_history` 来替换伪代码中的 `current_from_history`。

此示例也向您展示了，我们所看到的宏通常可以应用于类似的情况，即使它们与我们引入它们的用例不完全相同。

通过理解它们的作用，您可以在新上下文中应用它们，或派生出一个新宏来执行您经常需要的操作。
