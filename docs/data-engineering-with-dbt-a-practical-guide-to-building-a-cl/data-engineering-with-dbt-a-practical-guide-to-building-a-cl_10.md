## 在数据中实现一致性

在之前的章节中，我们了解了如何使用基本的 dbt 功能来构建一个端到端的数据平台，将源数据转换为可用的信息。

在本章和下一章中，你将学习如何为你的转换添加一致性和可靠性。这是 dbt 独有的两项关键优势，它通过将函数和测试作为开发过程中的一等公民，使这两点变得如此简单。

在本章中，你将学习如何超越基本的 SQL，将脚本能力引入你的代码，编写你的第一个宏，并学习如何在项目中使用外部库。

在本章中，你将了解以下主题：

- 通过复用代码保持一致性——宏
- 站在巨人的肩膀上——dbt 包

### 通过复用代码保持一致性——宏

在前面的章节中，我们使用 dbt 将简单的基于 SQL 的转换串联起来，为报表生成精炼的信息。这很好，并且提供了一种使用 SQL 代码的良好方式，但与之前可用的工具相比，它算不上一个重大的改进。

dbt 在数据转换方面区别于其他工具的一个主要不同点在于，它能够轻松定义宏。宏与编程语言中的函数非常相似，允许我们复用逻辑和 SQL 代码片段，以生成最终要在数据库中执行的 SQL 代码。

另一个巨大的不同点是，在编写代码时轻松地集成测试，并让测试与代码一起运行以保持数据质量，这一点我们将在下一章中看到。

你使用一种名为 Jinja 的脚本语言来编写 dbt 宏，Jinja 基于 Python，并且被许多其他基于 Python 的项目使用。

使用宏，你可以应用 DRY 和 KISS 软件工程原则，减少代码重复，并将复杂任务简单化，使诸如模式之类的通用解决方案得以广泛采用，因为复杂性可以对大多数编码者隐藏。

### 重复是数据项目的固有特性

在构建数据平台时，你反复做同样的事情是很正常的，有时甚至数百次。这通常由两个主要原因驱动——应用列特定的转换，以及应用通用使用模式。

第一种情况，重复的字段转换，源于你处理的数据是由某些软件生成的，而这些数据总是带有该软件的特定怪癖。

每次从系统读取数据时，你都需要处理它的怪癖，例如转换特定的日期格式，或者用 null 代替空字符串，或者去掉短数字前面的填充零。

无论需要什么样的处理，它很可能被应用很多次——可能非常多次——因为数据源中有许多字段需要处理。

第二种常见的重复来自反复应用相同的逻辑，也就是一种模式。它可能是如何存储历史数据，如何使用映射表进行主数据映射，或者你在代码中一遍又一遍地做的任何其他简单或复杂的行为。

在这两种情况下，使用复制粘贴的诱惑都很大，因为所需的代码几乎总是相同的，唯一的改变通常只是一个字段名或其他参数。

在我们的代码中已经有一个这样的例子。

看看我们两个 REF 模型中的 `current_from_snapshot` 通用表表达式（CTE）——我们有两个“相似”的模型，是通过复制粘贴完成的。这很糟糕！

### 为什么复制粘贴会毁掉未来的你

我们现在有两个 REF 模型，并且有“相同代码”的两个副本，它们在我们读取的快照名称上有所不同，而且是否排除某些技术字段也不同。

你已经可以看到，如果我们有 100 个源表，我们就需要 100 个快照，并且需要 100 次相同的代码来从中提取当前数据。

将代码复制粘贴 100 次似乎是一种不错的收益，因为你无需想太多就能获得所需的数据，但如果你想做任何更改呢？

使用复制粘贴，你必须去修改代码重复自身的 100 个地方。这太糟糕了！你在项目开始时节省了一点精力，结果却在后来被坑了。

那么，让我们的代码由函数（即宏）来生成呢？

那样的话，你只需要更改宏一次，所有 100 处使用都会立即更新。

这节省了大量时间。

项目中唯一不变的是变化和 bug。Bug 比业务变更需要更多的修改。每当你把某些内容写了几次，就开始思考如果你需要更改它，你会受到什么影响。

第二个考虑因素（在许多情况下更重要）是，当你更改生成代码的函数时，你可以 100% 确定所有实例都已更新，无需到处寻找它们。

如果你需要在一个中型项目中找到某个模式或特定格式的所有出现位置，而这样的模式或格式你只应用过 20 或 30 次，那我祝你好运。除了耗费时间外，结果的不确定性和不完整更改的后果会让你的开发人员对提议的更改感到害怕。这不是一个令人愉快的情况，尽管不幸的是这相当常见。

不一致地应用模式和公式，是导致数据平台 bug 的最常见原因之一，这些数据平台是使用鼓励复制粘贴而不是让函数创建几乎像复制粘贴一样简单的工具构建的。

dbt 中的宏为你提供了彻底解决这个问题的利器，让你对重复感到舒适，而不是被它们吓到。

### 如何编写宏

编写宏非常简单，只需在宏文件夹中的 SQL 文件内的宏声明中编写 SQL 即可，看起来如下所示：

```
{% macro this_with_filter(arg1, arg2='XXXX') %}
  SELECT * FROM {{this}}
  {% if arg1 %}
```

```
SELECT
    * EXCLUDE (DBT_SCD_ID, DBT_VALID_FROM, DBT_VALID_TO)
    RENAME (DBT_UPDATED_AT as SNSH_LOAD_TS_UTC )
FROM {{ snsh_ref }}
WHERE DBT_VALID_TO is null
{% endmacro %}
```

3. 编辑 REF_POSITION_ABC_BANK.sql 文件中的 CTE，用我们在上一步创建的宏调用来替换当前 SQL：

```
WITH
current_from_snapshot as (
    {{ current_from_snapshot(
        snsh_ref = ref('SNSH_ABC_BANK_POSITION')
    ) }}
)
SELECT
    *
    , POSITION_VALUE - COST_BASE as UNREALIZED_PROFIT
    , ROUND(UNREALIZED_PROFIT / COST_BASE, 5)*100
        as UNREALIZED_PROFIT_PCT
FROM current_from_snapshot
```

请注意，你可以决定是保留参数名并为其赋值，还是在调用宏时按正确顺序直接传入值，就像在 Python 中调用函数一样。保留参数名使调用更易于阅读，并且在参数不多且并非所有参数都像这里那样直接时会有很大帮助。

下面的调用不带参数名也同样有效：

```
{{ current_from_snapshot(ref('SNSH_ABC_BANK_POSITION')) }}
```

保存文件后，宏会取代 CTE 的位置，你可以通过点击 </> Compile 按钮来查看宏编译后的结果。你会在名为 Compiled Code 的选项卡下找到编译后的代码。点击 Preview 按钮来运行查询。

4. 同样地，按照步骤 3，编辑 REF_ABC_BANK_SECURITY_INFO.sql 文件中的 CTE，用宏调用来替换当前 SQL：

```
WITH
current_from_snapshot as (
    {{ current_from_snapshot(
        snsh_ref=ref('SNSH_ABC_BANK_SECURITY_INFO')
    ) }}
)
SELECT *
FROM current_from_snapshot
```



注意，在前面的代码中，正如它在之前的表述中一样，你可以只保留 CTE 的内容并删除其余代码，以保留你在以下代码块中看到的内容。我们更喜欢保留这种带有 CTE 的较长格式，因为它使得在保持结构在各模型中非常清晰和一致的同时，更容易添加逻辑：

```
{{ current_from_snapshot(
    snsh_ref = ref('SNSH_ABC_BANK_SECURITY_INFO')
) }}
```

作为良好的实践，在编辑模型后，运行预览以检查其是否正常工作。

5. 现在我们已经创建了宏，将其放置在我们的代码中，并检查我们的模型仍然正常工作，你可以使用以下命令部署更新后的代码：

```
dbt build
```

如果你回顾一下你编写的宏，你会看到，使用一个仅有一个参数且没有逻辑的非常简单的宏，我们已经极大地改善了项目的质量和可维护性。

我们宏中唯一的 Jinja 编码部分是 {{ snsh_ref }} 表达式，它将打印出由 snsh_ref 变量引用的对象对应的值。

在这种特定情况下，你可以看到，在我们使用宏的每个模型中，我们都通过对 ref() 函数的调用来初始化变量：

```
{{ current_from_snapshot(snsh_ref = ref('SNSH_ABC_BANK_POSITION')) }}
```

如果你在 dbt 参考文档的 dbt Jinja 函数页面中查找 ref() 函数，你会发现它返回一个 Relation 对象，“它具有与 {{ this }} 变量相同的 table、schema 和 name 属性”。

{{ this }} 变量表示指向正在编译的模型的 Relation 对象，在增量模型或钩子中引用模型本身时尤其有用。

还需要注意的是，当在表达式中调用时，例如 {{ snsh_ref }}，Relation 对象将返回它所引用的数据库对象的完全限定名称的字符串，通常是视图或表。

## 为我们的宏添加条件行为

你可能已经注意到，自从使用宏以来，我们的 REF 模型获得了一个名为 SNSH_LOAD_TS_UTC 的新字段。这是因为宏排除了快照中的大多数技术字段，并将 DBT_UPDATED_AT 重命名为 SNSH_LOAD_TS_UTC。

我们的 REF 模型已经从 STG 模型获得了 LOAD_TS_UTC 字段，因此我们可能会认为同时拥有这两个时间戳是多余的，我们希望使宏更灵活，提供选择是否想要该额外字段的能力。

在本节中，我们添加了一个宏来实现一种模式，并使模型开发者能够轻松使用其逻辑——在我们的例子中，如何从快照中获取当前数据。模型开发者现在只需要知道他们想要从哪个快照读取数据，以及最终是否还想要 SNSH_LOAD_TS_UTC 列。

我相信你能理解，能够以如此简单的形式生成实现项目特定工作方式的宏，并让模型开发者直接使用它，而不是每次都开发或复制代码，其威力有多大。

## 修复从 CSV 文件加载的数据

查看我们为 ABC BANK 的头寸加载的数据，你可能会注意到日期有点偏差，因为它们指的是第一个世纪而不是 21 世纪。

该死！我们受到了一个非常常见问题的侵害——在导出、导入和跨系统移动数据时，数据格式往往会以某种方式不完美，最终的数据与开始时的数据会不同。

在我们的例子中，从 Excel 导出到 CSV 文件产生了年份只有两位数字的日期。在这里，我复制了文件中的一行，你可以看到日期表示为 4 / 9 / 21。Snowflake 能够将其解释为美国格式的日期，并生成日期 0021-04-09，即公元 21 年 4 月 9 日：

```
ABC000123, STAR, ISTAR INC, NYSE, 4/9/21, 150, 2444, 2725.5, USD
```

现在我们对这个问题有了更深的了解，我们在任何项目中通常有两种前进方式：

- 在源头修复问题并重新加载数据。

这是更好的选择，因为数据在所有步骤中都是正确的，你的项目不需要有修复问题的代码，而代码越少，错误越少，维护也越少。不幸的是，在许多情况下，我们无法控制源头或无法要求其修复，或者我们需要保留收集的历史记录，因此修复源头只会修复一半的问题。

- 至少暂时忍受它，然后再修复它。

即使它不如前者好，这通常是我们唯一的选择。

即使我们能够要求修复数据，修复的时间表和我们工作预期的发布时间可能不匹配，或者我们可能不想依赖外部操作，因此我们仍然需要修复数据，即使只是暂时。

如果你愿意，你可以去修复 CSV，重新导入它，并运行所有内容，以便快照中的最新版本是正确的。

我们将采用修复路径，因为这是你经常必须采取的路径，因为你无法在源头影响问题。

我们的源是一个包含数据已在 date 数据类型中的表的表，因此我们无法修复 CSV 的解析；我们的修复将涉及将日期从公元 1 世纪带到 21 世纪。

由于我们将 CSV 作为 seed 导入，我们也可以强制该列为文本数据类型，然后从文本解析为日期并提供正确的格式。这可以以与此处所示类似的方式实现为宏。你可以将其作为练习。

我们本可以直接在 STG 模型中编写 SQL，但为了使其可重用，我们将创建一个带有 SQL 和参数的宏，并向你展示如何在 STG 模型中使用它。

让我们开始：

1. 在 macros 文件夹中创建 `to_21st_century_date.sql` 文件，代码如下：

```sql
{% macro to_21st_century_date(date_column_name) -%}
    CASE
        WHEN {{ date_column_name }} >= '0100-01-01'::date
        THEN {{ date_column_name }}
        ELSE DATEADD(year, 2000, {{ date_column_name }})
    END
{%- endmacro %}
```

在前面的代码中，我们创建了 `to_21st_century_date` 宏，它有一个单一的 `date_column_name` 参数。代码是纯 SQL，只是将列名替换为将保存列名的参数。

请注意，宏将在 dbt 中运行以创建要发送到数据库的 SQL；因此，我们传入的参数值只是列名的字符串，而不是列值。

2. 打开 `STG_ABC_BANK_POSITION.sql` 文件并编辑 `src_data` CTE，将 `REPORT_DATE` 列的行编辑为如下所示：

```sql
src_data as (
    SELECT
        ACCOUNTID   as ACCOUNT_CODE    -- TEXT
      , SYMBOL      as SECURITY_CODE   -- TEXT
      , DESCRIPTION as SECURITY_NAME   -- TEXT
      , EXCHANGE    as EXCHANGE_CODE   -- TEXT
      , {{to_21st_century_date('REPORT_DATE')}}
            as REPORT_DATE            -- DATE
      , QUANTITY    as QUANTITY        -- NUMBER
      , COST_BASE   as COST_BASE       -- NUMBER
      , POSITION_VALUE as POSITION_VALUE
      , CURRENCY as CURRENCY_CODE      -- TEXT
      , 'SOURCE_DATA.ABC_BANK_POSITION' as RECORD_SOURCE
    FROM {{ source('abc_bank', 'ABC_BANK_POSITION') }}
),
```

你可以看到，唯一的变化是将 REPORT_DATE 列名替换为 {{to_21st_century_date('REPORT_DATE')}} 宏调用，将列名作为字符串传递（用单引号或双引号括起来）。

运行 dbt 模型时，宏将被运行并替换为执行结果的代码。你可以通过单击 </> Compile 按钮查看结果。你可以通过单击 Preview 按钮预览结果并检查日期是否已在 21 世纪。

3. 使用以下命令运行模型及其下游模型：

```
dbt build -s STG_ABC_BANK_POSITION+
```

4. 运行完成后，验证你现在是否在快照中为已修复的行获得了新条目，而旧行已关闭，并在 DBT_VALID_TO 列中带有我们运行的时间戳。

你也可以验证 REF 模型现在是否正在提供当前值，即带有 21 世纪日期的值。

在本节中，我们创建了一个宏，它隐藏了一段更长的 SQL 代码，并使其在简单名称下可用，易于应用于不同的列。

虽然为仅使用一次而创建宏是没有意义的，就像我们的例子一样，在现实项目中，如果你需要应用修复或转换，通常需要多次应用它，因此创建宏可能是一个不错的解决方案。

在全面用宏替换 SQL 之前，请记住，代码的可读性是我们最重要的目标之一，引入过多的宏，尤其是如果你找不到合适的名称，可能会使你的代码难以理解。

## Jinja 分隔符

在处理 Jinja 时，首先要理解也是最重要的一点是，如何从输出上下文（代码原样输出）切换到 Jinja 上下文（逻辑控制流程和输出），以及如何从 Jinja 生成输出，使其成为发送到数据库的代码的一部分。

在 dbt 模型中编写的文本被视为要发送到数据库的 SQL 代码，除非你使用此处描述的分隔符进入 Jinja 上下文：

- `{% ... %}` 用于开始和结束 Jinja 语句。

语句是你在 Jinja 中用来控制执行流程的控制结构。例如 if 条件语句、for 循环、宏定义、set 赋值和过滤器。

- `{{ ... }}` 用于包围 Jinja 表达式，表示将结果打印出来。

Jinja 表达式与 Python 表达式非常相似，包括多种类型的字面量、数学运算、比较和逻辑运算，以及其他一些运算符，包括调用 Python 方法的能力。

- `{# ... #}` 用于包围 Jinja 注释，可用于将某些 Jinja 代码从求值/输出中排除。

- 需要注意的是，一旦进入 Jinja 上下文，你就不再需要分隔符，可以直接使用表达式而无需额外的大括号。

在接下来的章节中，我们将更详细地描述一些最常用的元素。

## Jinja 表达式

与 Python 一样，表达式允许你使用字面量、变量、函数和运算符来计算值。然后你可以使用表达式的结果，将结果存储在变量中，作为函数的输入，或者直接打印出来。

在这里，我们可以看到不同类别的一些示例：

- Jinja 字面量示例：

```text
'Hello World' or "Hello World"   -- String literals
42 or 42.24 or 42E3               -- Numeric literals
true / false                       -- Boolean literal
['list', 'of', 'objects']          -- List literal
('tuple', 'of', 'values')          -- Tuple literal
{'dict': 'of', 'key': 'and', 'value': 'pairs'}
        -- Dictionary literal
```

你可以用双花括号将它们包围起来打印出来，例如 `{{ 'Hello World' }}` 或 `{{ 42.24 }}`，这将会打印出这些值。

- **使用数学运算符的示例：**

```text
{{ 1 + 1 }} or {{3-1}} or {{7 // 3}}  -- all print 2
{{ 1 / 2 }}                         -- prints out 0.5
{{ 3*2 }} or {{ 20 % 7 }}            -- all print out 6
{{ 2**3 }}                            -- prints out 8
```

数学运算符是通常的四种算术运算符（+、-、* 和 /），它们执行浮点运算，此外还有 // 整数除法、% 取模或余数，以及 ** 幂运算符。

- **使用比较运算符的示例：**

```text
{{ 42 == 42 }} or {{ 42 != 24 }}       -- both return true
{{ 42 > 24 }} or {{ 42 >= 24 }}          -- both return true
{{ 24 < 42 }} or {{ 24 <= 42 }}          -- both return true
```

如前面的示例所示，我们有常用的比较运算符：`==`——等于，`!=`——不等于，`>`——大于，`>=`——大于或等于，`<`——小于，`<=`——小于或等于。

- **使用逻辑运算符的示例：**

```text
{{ true and true }} or {{ not false }} -- will return true
{{ false or (42 > 24) }}              -- will return true
```

你可以使用逻辑运算符（and、or、not 以及 () 分组）来组合布尔表达式，并控制 if 语句或任何其他需要使用布尔值的地方。

- **使用其他运算符的示例：** `in` 运算符执行包含性测试，如果被测试的元素包含在 `in` 运算符之后的序列或映射中，则返回 true：

```text
{{ 1 in [1, 2, 3] }} or {{ 'bc' in ['bc', 'a'] }} -- in operator
```

`is` 运算符使用一种 Jinja 测试对变量或表达式执行测试。你编写表达式，然后是 `is` 运算符，接着是测试名称，最终可以在测试名称后面带上测试的其他参数：

```text
{{ (expr) is integer }}                 -- is operator
```

`~` 运算符将操作数转换为字符串并连接它们：

```text
{{ 1 ~ " string" ~ '!' }}             -- ~ operator
```

`()` 运算符允许我们调用可调用对象并传递最终参数：

```text
{{ "Welcome {}".format(name) }}        -- () operator
```

`|` 运算符，称为管道符或竖线，用于应用过滤器。过滤器会修改其应用到的值。过滤器可以链式使用，并依次应用，第一个过滤器的输出由第二个过滤器修改，依此类推：

```text
{{ "to uppercase"|upper }}          -- | operator (pipe)
```

`.` 或 `[]` 运算符允许访问存储在你应用运算符的变量中的对象的属性，其语法类似于 Java 或 Python：

```text
{{ obj.attr }} or {{ obj[attr] }}      -- . / [] operator
```

组合不同类型的表达式，你可以生成复杂的表达式，从而像在 Python 中一样表达几乎任何计算或测试。

## If 语句（if... then... 和 else）

if 语句，也称为条件语句，其工作方式与 Python 中相同，允许你根据一个或多个测试来决定在哪个分支中继续执行。

主要区别在于表示法略有不同，它以 `{% if value_to_test %}` 块开始，并始终以 `{% endif %}` 块结束。

在最简单的版本中，如果测试值为真，if 语句将继续流程，如以下示例所示：

```text
{% if value_to_test %}
some output
{% endif %}
```

如果你愿意，也可以将前面的示例全部写在一行：

```text
{% if value_to_test %}some output{% endif %}
```

如果测试为真，则 if 语句内的代码将被执行——在这种情况下，返回文本。你可以在 if 语句内放置其他语句和表达式。

if 语句的一般形式如下：

```text
{% if test1 %}
    Test 1 is true. Do something ...
{% elif test2 %}
    Test 2 is true, but not test 1. Do second thing...
{% else %}
    Both test1 and test2 did not return true. Do something else...
{% endif %}
```

查看前面的示例，你会发现你可以根据需要链式使用任意数量的 elif 块，并且可以使用 else 块来捕获未满足前述任一测试的所有情况。

## for 循环语句

for 循环是另一种主要的控制结构，与 if-else 语句一起，并且与 Python 的 for 循环非常接近。主要区别在于你不能在 Jinja for 循环中 break 或 continue，但可以应用过滤器和测试。

你可以使用 for 循环遍历序列，如以下示例所示：

```text
{% for item in sequence %}
  {{item}} {% if not loop.last %},{% endif %}
{% endfor %}
```

在这里，我们举例说明了 loop 特殊变量的 last 属性的用法。

示例中的 sequence 变量可以是任何类型内容的列表，通常是列名或值的列表。另一个常见用例是使用 range 函数生成数字列表——例如，要生成从 1 到 10 的列表，可以使用 range(1, 11) 表达式。

你也可以使用 for 语句遍历字典的内容：

```text
{% for key, value in a_dict | dictsort %}
{{ key }}, {{ value }} is the same as {{ key ~ ', ' ~ value}}
{% endfor %}
```

在前面的示例中，我们还应用了 dictsort 过滤器，以便在遍历之前对字典进行排序。

## set 语句

在 Jinja 中，你使用 set 语句来执行变量赋值。

赋值有两种格式；第一种是内联赋值，类似于 Python 中的赋值，如下面的示例所示：

```text
{% set var = "some value" %}
{% set a_mixed_list = ['one', 2, three] %}
{% set var1, var2 = my_function() %}
```

如你所见，你可以在同一次赋值中同时给多个变量赋值，就像在 Python 中一样。

请注意，for 循环引入了不同的作用域（而 if 条件语句则不会）；结果是，在 for 循环外部，你看不到在循环内部进行的赋值的效果，即使该变量是在 for 循环外部声明/初始化的。为此，你应该使用命名空间或其他不同的结构。





第二类赋值是块赋值，你只需在 set 语句中声明变量名，然后该变量就会被赋值为 set 块内代码解析后的结果：

```
{% set date_filter %}
  DATE between {{ start_date }} and {{ end_date }}
{% endset %}
```

这种第二类赋值对于赋值较长的文本非常方便，尤其是当你希望它们格式正确时，因为该块会保留正确的换行符。

当我们想在文本中加入变量时，我们倾向于使用这种赋值方式，因为在块内，你可以正常输入文本，并使用常见的双花括号表达式格式输出变量或计算结果。

这是一种简单易读的方式，可以将 SQL 查询的文本或要在宏中传递的过滤器赋值给变量。

## run_query() 函数

dbt 提供的 run_query() Jinja 函数允许我们向执行调用所在环境配置的数据库执行一段 SQL。

在开始编写更复杂的函数——这些函数的行为取决于数据库的内容，或者当你希望执行超出正常的 dbt 运行周期的 SQL 命令时——你才需要使用此函数。

以下来自 dbt 函数参考的示例代码为我们提供了两个有用的信息来讨论：

```
{% set results = run_query('select 42 as the_answer') %}
{% do run_query('DROP TABLE IF EXISTS PUBLIC.MY_USELESS_TABLE') %}
```

- 第一行表明，如果你想将结果存储在变量中，可以使用赋值来执行函数并在变量中获取结果。
- 第二行表明，作为替代方案，你可以使用带有 `do` 标签的表达式语句来执行表达式，而不打印任何结果。

  如果你不想存储结果，这对于执行具有副作用的表达式或函数非常有用；示例包括更改列表或运行一些 DDL 或 DML SQL 代码。

通常，我们只会在想要执行某些操作（即非 SELECT 查询）并且不想使用查询结果时使用 run_query 函数，因为结果是 Agate 表——这是一个不太容易操作的复杂对象。

当你想要在宏中使用查询结果时，我们建议使用 dbt_utils 库中的 get_query_results_as_dict() 宏，我们将在下一节中介绍。该宏将返回一个易于使用的 Python 字典。

当我们希望以自动化方式运行 DDL 或 DML 命令时，我们会将 `run_query` 函数与 `run-operation` dbt 命令结合使用，例如当我们想要定义外部表、创建落地表，或使用 `COPY INTO` 命令直接从文件摄取数据时。

## `return()` 函数

我们只在更高级的宏中使用 `return()` 函数，这些宏不直接产生最终输出，而是返回一个数据结构以供进一步使用，通常是列表或字典，如下面的示例宏所示：

```jinja
{%- macro get_user_dictionary() -%}
{% set users_dict_yaml -%}
developers:
  - MY_SF_USER
  - ANOTHER_SF_USER
readers:
  - PBI_USER
{%- endset %}
{% do return(fromyaml(users_dict_yaml)) %}
{%- endmacro %}
```

上面的宏允许你使用 YAML 格式创建和维护字典，方法是将其写在赋值给 `users_dict_yaml` 变量的块内。

然后，该变量被传递给 dbt 的 `fromyaml` 函数，该函数解析文本并构建相应的数据结构。存在一个类似的函数 `fromjson` 用于解析 JSON 格式。

最后，`return()` 函数将数据结构返回给调用者。

这里，我们看到了一个返回手动维护配置的示例；return() 函数的另一个常见用途是返回你通过 `run_query()` 函数（或库提供的其他更可用的变体）加载的数据。

到目前为止，我们一直在从头编写模型和宏——也就是说，除了基本的 dbt 功能外，不借助任何帮助地编写所有代码。在下一节中，我们将看到我们可以从 dbt 库（称为包）获得很多帮助，我们可以将它们导入到我们的项目中。

## 站在巨人的肩膀上 – dbt 包

我们一直在仅使用基本 dbt 功能编写模型和宏。在本节中，我们将了解一些现有的库（在 dbt 中称为包），以及如何导入它们以提高生产力。

仅使用 dbt 或 Java 或 Python 标准功能，你就可以构建所需的一切。凡事自己做并不构成绝对的限制，但在所有语言中，库的可用性——这些库是经过良好测试的代码集合，用于处理频繁或复杂的任务，你可以轻松下载并使用它们来完成复杂任务——极大地提升了程序员的生产力和解决更复杂问题的能力。

使用库，你可以专注于问题的核心，并依靠许多其他聪明人的知识和经验来降低项目的复杂性，节省大量时间。

你可以重用由在团队不擅长的领域的专家编写的代码，使用你自己可能无法创造的经过验证的解决方案，或者使用快速且标准的解决方案来实现日常需求，使用经过验证的方案而不是重新发明轮子。

### 创建 dbt 包

也许你想知道如何创建 dbt 包。

你可能会惊讶地听到你已经做到了！

一个 **dbt 包**只是一个普通的 dbt 项目，与其他项目一样，通常存储在 git 仓库中。

是什么让 dbt 项目成为包？实际上并没有特别的原因——只是被另一个包导入这一事实。*包*这个名字指的是被导入的项目将一些功能打包在一起，供其他项目重用。

一个包可以包含 dbt 项目包含的所有内容——模型、宏、源、测试等——这些将成为导入项目的一部分，因此你可以像往常一样引用这些元素。

因此，你可以使用 `ref()` 函数引用导入的模型，并通过其名称调用宏，调用时以导入的包名作为前缀以避免名称冲突。

当你导入一个包时，所有 dbt 命令都将同时作用于你的代码和你导入的代码。例如，当你运行 `dbt run` 命令时，导入包中的最终模型也会被运行。

你通常可以找到或创建包来解决常见问题，例如：

- 转换来自标准接口（如 SaaS 和常见产品）的数据
- 用于执行常见任务或与特定领域相关的任务的宏库
- 管理或审计特定工具

### 导入 dbt 包

- 使用本地文件夹，语法如下：

  ```yaml
  packages:
    - local: /your/local/folder  # a local path
  ```

  这是一种特殊的导入包的方式，对于你正在开发的包非常有用，因为只要你保存包的文件，更改就会立即生效，无需在每次更改时运行 `dbt deps`。

  此功能仅在 dbt Core 中可用，而不可在 dbt Cloud 中使用，因为你无法访问 dbt Cloud 项目的本地文件系统。

- 从 Git 私有仓库导入：语法略有不同，具体取决于你使用的 Git 服务提供商，因为你需要使用正确的 HTTP URL 格式来提供访问令牌，以及（如需要）用户名，具体取决于服务提供商的要求：

  ```yaml
  packages:
    # github format
    - git: "https://<application token>@github.com/..."
    - git: "https://<user_name>:<personal token>@github.com/..."
    # Azure format
    - git: "https://<personal access token>@dev.azure.com/..."

    # BitBucket format
    - git: "https://<user>:<personal token>@bitbucketserver.com/..."
    # GitLab format
    - git: "https://<user>:<personal token>@gitlab.xxx.com/..."
  ```

  正如你在前面的示例中所看到的，你可以在 @ 符号之前提供访问信息，然后是通常的完整仓库 URL。

  提供访问信息的格式主要有两种——一种只包含访问令牌，另一种包含用户名和访问令牌，用冒号分隔。

  为了避免将机密明文放入你的仓库，你不应直接在 YML 文件中编写用户名和令牌。相反，你应该使用环境变量来存储实际值，并在 YML 文件中使用 `env_var` 函数。

  参考前面的示例，你可以进行以下替换：

  将 `<user_name>` 替换为 `{{ env_var('DBT_ENV_SECRET_GIT_USERNAME') }}`。

  将 `<token>` 替换为 `{{ env_var('DBT_ENV_SECRET_GIT_CREDENTIAL') }}`。

  请记住，在 dbt Cloud 中，环境变量有严格的名称，必须以 `DBT_` 或 `DBT_ENV_SECRET_` 开头。两者之间的区别在于 dbt Cloud 是否能够将其打印的值从日志中移除，并且不在 UI 中显示或打印出这些机密值。

现在我们已经了解了如何导入包，让我们讨论何时使用每种方法。





## 使用 dbt 包的导入方法

看到这四种导入包的方式，你可能已经猜到了它们的常见用例，但让我们简要讨论一下：

- 从 dbt Hub 导入包是从常用的开源包中导入通用包的首选方法。这绝对是你项目中最常使用（甚至可能是唯一）的导入包的方法，至少对于引入第三方构建的功能而言是如此。
- 从 git 公共仓库导入是将不太知名或小众的包引入的便捷方式，这些包由作者向社区提供，无需费心在 dbt Hub 上注册。如果你可以接受将代码公开，也可以将它用于自己的库。
- 本地导入是一种专门的功能，主要由包开发者使用。其主要优势是任何更改都会立即生效，无需调用 dbt deps 命令来刷新包。
- 从私有仓库导入使你能够拥有私有包，从而构建自己的 dbt 宏和模型库，并在所有项目中复用，而无需公开代码。
- 从私有仓库导入还可用于构建嵌套的项目架构，其中多个项目共用的部分（例如来自同一数据源的摄取和/或初始转换）被提取到一个公共包中，并包含在需要相同数据的所有项目中。
- 私有导入的另一个用途是将较大的项目拆分为多个子项目，但这样做风险在于最终全局项目的复杂度增加，以及在小项目中工作的收益减少。当某些数据或代码不能与某些第三方共享时，可能需要这种用途；这些第三方可以转而处理整个项目中不那么敏感的部分。

这可以通过两种方式实现；第一种是导入公共包的代码，重复处理过程，并为每个项目生成一份独立的数据副本，而无需管理多份代码副本，同时提供连续的沿袭图。这种做法的缺点是处理过程和数据的重复。

第二种方式是让一个项目执行公共导入/处理，且只运行一次、只针对数据的一份副本，然后创建第二个“仅接口”项目，将第一个项目的结果定义为源。这个第二个项目可以被所有需要读取转换后数据的其他项目导入。这种设置的缺点是沿袭被分散在公共项目和被导入的项目之间。

我们讨论了一些导入 dbt 包的常见方式，以及一些更高级的可能性；这些高级可能性很可能在你项目变得相当大（数百个模型）并且积累了丰富经验之前，都不需要考虑。

大多数时候你都会从 dbt Hub 导入常规包，这是完全正常的；尽管如此，我们认为了解一些高级可能性以备将来使用仍然是有益的。

## 使用包构建内部共享库

如果你的公司有多个 dbt 项目，那么很有可能你在所有这些项目中都应用了相同的最佳实践和模式。因此，有相当多的宏和工具模型在这些项目中的全部或许多项目里被使用，且几乎没有改动。

共享宏的示例可能包括摄取数据（使用宏，我们将在后续章节中看到）、你持续使用的通用测试（例如针对哈希冲突的测试），或者你经常需要应用的格式转换（例如去除字符串中的填充零或为字符串添加填充零）。

共享模型的示例可以包括监控本地部署中的性能和资源或 SaaS 平台中的消耗，提供安全相关的报告（如用户和角色访问），或提供活动审计（如某个用户运行的查询或访问某些信息的用户）。

在这些情况下，复制粘贴和复用模型或宏的诱惑很大，但如果你回到本章开头重新阅读“为什么复制粘贴会毁掉未来的你”一节，你会被提醒：在项目内部这样做不是一个好主意，而且你可以猜到，跨项目这样做同样如此。

解决方案是将公共宏和模型重构为一个独立的 dbt 项目，作为你共享库的第一个版本。然后，你将根据项目中出现的需求来演化它，例如当我们需要额外功能时扩展了我们的 current_from_snapshot 宏。

设计一个库并不是简单的事情，因为你需要平衡你想给用户的灵活性与使用的简单性。以下指导原则将帮助你入门：

- 优先选择小而专注的包，而不是包罗万象的包。导入三个或五个不同的包很容易，但你无法只导入一个包的一半。
- 特别是当包含会在每次运行项目时物化的模型时，宁可拆成多个高内聚的小包，这样你的用户可以在不携带任何额外负担的情况下选择他们想要的功能。
- 提供一种简单的方式来配置模型，使用 dbt 变量或环境变量，并记录如何完成配置。
- 当你制作的包只包含宏或测试时，可以倾向于制作更少但更大的包，因为未使用的宏和测试只是放在那里，不会打扰任何人。一个很好的例子是 dbt_utils 包，它提供了一组相当不同的宏，其共同点是通用性。

  库越大，按领域和功能组织宏就越重要。要提供它们的使用示例，清楚地说明你期望参数具有什么数据类型以及你期望处理的数据结构，并说明是否有任何特殊要求，例如键字段是列列表中的第一个。

- 与软件工程中一贯的原则一样，避免库之间的循环引用，因此在构建库时要考虑它们的抽象层级，并最终拆分库，将许多库使用的对象与使用其他库的对象分开。

现在，通过使用宏、通用测试和包，你知道了如何避免项目内部和跨项目的重复。在下一节中，我们将浏览一些有用的包，它们为你提供了大量新功能。

## 浏览 dbt 值得关注的包

你现在知道如何导入包来为你的项目添加功能，也知道有一个 dbt Hub 存储库，其中包含最常用的开源包，你可以轻松地将它们添加到项目中。

你可以通过 `https://hub.getdbt.com/` URL 访问 dbt Hub 存储库。

在接下来的几节中，我们将介绍一些你可以在 dbt Hub 中找到的值得关注的包。

### dbt_utils 包

这无疑是使用最普遍、最常用的 dbt 包，因为它提供了各种各样的常见功能，从更通用的测试到不同领域的宏，例如从数据库加载数据、扩展 SQL、提供统一的跨数据库功能，以及更具体需求，例如从 URL 中提取参数或 Jinja 辅助函数。

以下是一些通用测试和宏的列表，我们会发现它们对此包尤其有用：

- `expression_is_true`：这是一个模型级测试，用于断言你提供的 SQL 谓词（一个求值为真或假的表达式）对表中的所有记录均为真。这个宏允许你测试几乎任何可以用 SQL 谓词表达的内容，但如果你一直以相同方式使用它，我们建议你定义一个具有适当名称的自己的通用测试。
- `not_empty_string`：这是一个列级测试，用于验证某一列在修剪该列内容后，不存在空字符串（`''`）。

与 `not_null` 测试结合使用，你可以验证文本列确实包含真实的文本值，既没有 null，也没有 `''`。

```yaml
- name: column_name
  tests:
```





- `not_null`
- `dbt_utils.not_empty_string`
- **mutually_exclusive_ranges**: 该模型级宏测试按列分区时行是否创建正确的日期范围，让你验证范围不重叠、有或没有间隙，以及范围大小大于零。
- **get_column_values**: 该宏将模型中特定列的值加载为 Python 列表，而无需处理 Agate 表。
- **get_query_results_as_dict**: 该宏将 SQL 查询的结果加载为 Python 字典，这样你就无需处理 Agate 表。
- **date_spine**: 该宏生成 SQL 代码以在区间内生成连续的日期序列，根据所需的粒度（天、月等）。
- **union_relations**: 该宏允许你联合两个或多个关系（表或视图），对具有相同名称的字段进行对齐并为缺失的字段添加 null 列，从而简化对相似但列不完全相同且顺序不同的表的 UNION 操作。
- **star**: 该宏的基本行为是生成关系中列的逗号分隔列表，最终可带别名，并能够排除某些列。这可以用在通常的 SELECT * 代码的位置，以更好地控制你想要选择的列，即使在数据库不支持 SELECT * EXCLUDE (...) 构造的情况下也是如此。
  更高级的用法允许你为列名添加前缀或后缀。
- **generate_surrogate_key**: 该宏提供了一种跨数据库的方式来计算列列表的哈希值。这可以用作代理键或用于任何其他哈希的常见用途。
  我们将在宏中经常使用它来存储表的历史记录。

我们刚刚提供了一个非常简短的 dbt_utils 包中可用有用宏的列表，我们强烈建议你去 https://hub.getdbt.com/dbt-labs/dbt_utils/ 看一看。

## Codegen package

该包同样来自 dbt-labs，提供了许多有用的宏来生成常用代码片段的初始版本，以便你可以最大程度地减少输入数据库中已有的信息，尤其是名称的需要。

使用这些宏，你可以生成模式中表的源定义，将其复制粘贴到源 YAML 文件中，或者你可以生成一个骨架暂存模型或用于记录和测试一组模型的 YAML 代码。

预览以下代码将生成用于导入所选数据库中模式的关联的源文件的 YAML：

```
{{ codegen.generate_source('<schema>',database_name = '<database>') }}
```

你也可以使用 run-operation 命令运行宏，如下所示：

```
dbt run-operation generate_source --args '{"schema_name": "<schema>", "database_name": "<database>", "table_names":["table_1", "table_2"]}'
```

以下代码可用于生成描述和测试模型的 YAML：

```
{{ codegen.generate_model_yaml(model_name='<model>') }}
```

我们强烈建议使用这些宏或自行构建，以最大程度地减少无用的输入，减少输入列和关系名称时的错误，并专注于你需要添加以将数据转换为信息的逻辑。

在第 6 章中，我们提供了可运行的 SQL 查询示例，以同样的效果从数据库已有的源表元数据信息中生成模型所需的代码。

## Adding the dbt-utils package to our project

我们看到 dbt-utils 包具有许多有用的功能，所以让我们将其添加到我们的项目中，然后使用它来重构我们的代码以生成更好的代理键，取代我们迄今为止使用的简单字段拼接。

另外，预览此模型以确保一切按预期工作。

我们不必部署 STG 模型，因为它们是临时性的，所以让我们更新收集 STG 模型输出数据的快照。

我们没有更改 STG 模型的模式，所以我们可以直接运行快照，其效果是所有旧行都被带有新哈希码的行替换。

这无论如何也没什么意义，因为我们将用两个不同的键在表中表示同一个实体。继续使用旧历史的解决方案是重命名当前表或快照，以便只有一个使用当前键的活动快照表。然后，你以正确的方式在 REF 模型中引用这两个表。

就我们而言，由于快照不包含任何珍贵的历史，我们将直接删除快照表，这样运行快照将创建新表，其键基于哈希码。

让我们这样做：

1. 让我们删除旧的快照表：

```
DROP TABLE
  PORTFOLIO_TRACKING.SNAPSHOTS.SNSH_ABC_BANK_POSITION;
DROP TABLE
  PORTFOLIO_TRACKING.SNAPSHOTS.SNSH_ABC_BANK_SECURITY_INFO;
```

2. 运行快照以创建新表：

```
dbt snapshot
```
