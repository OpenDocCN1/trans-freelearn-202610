
## 云安全 – 可防止风险的措施示例

云安全，正如预期所言，涉及旨在实现多项目标的一系列策略。这包括对网络进行归档和防护以抵御网络攻击、恢复任何丢失或被盗的数据，以及总体上减少受损系统或个人数据泄露的影响。

过于频繁地，迁移到云端是在未先评估要迁移哪些数据和流程、也未为特定情况定义合适的网络安全措施的情况下进行的。

因此，一切必须从对数据迄今为止是如何得到保护的、所使用的基础设施以及需要干预的薄弱环节的认知开始。因此，对当前情况进行快照，以评估哪种云服务提供足够的安全级别并规划适当的迁移策略。

根据具体情况和需求，公司可以实施不同的工具来实现稳固的云安全。以下是一些示例：

- 一个 **身份和访问管理 (IAM)** 系统，用于身份和访问管理
- 微分段，通过该方式云的实现被划分为不同的段，直至单个工作负载的级别，最小化可能攻击者的损害
- 新一代防火墙——与传统防火墙相比，它们增加了高级功能，例如应用感知过滤器、深度包检测和入侵防御系统
- 加密，以便数据只能使用特定密钥解密
- 威胁情报、监控和预防，或旨在分析流量以识别、阻止或至少减轻恶意软件攻击的功能

## 云计算的七大痛点

安全是所有公司的议题，无论它们是否在云端运营。你将面临诸如拒绝服务、恶意软件、SQL 注入、数据泄露和数据丢失等威胁——所有这些都可能严重影响你公司的声誉和财务状况。

迁移到云端引入了一组新的风险，并改变了其他风险的性质。这并不意味着云计算不安全。事实上，许多云服务提供商提供你原本无法获得的非常先进的安全技术和资源。

它仅仅意味着你必须意识到不断变化的风险，以便进行管理。因此，让我们审视云计算的特定安全漏洞。

### 可见性降低

大多数企业将通过众多设备、部门和地理位置访问各种云服务。在没有适当工具的情况下，这种云计算安排中的复杂程度可能会导致你失去对基础设施访问的认知。

如果没有适当的程序，就可能无法追踪谁在使用你的云服务，包括他们访问、发布和下载的信息。

只要记住，云中的资产可能不可见。而如果不可见，就无法得到保护，从而增加数据丢失和数据泄露的可能性。

当然，适用于本地的相同或类似控制措施也适用于云。

### 合规违规

随着监管监督的扩大，你必须遵守各种严格的合规标准。如果不谨慎，迁移到云端可能会使你面临合规问题。

其中许多要求要求你的组织了解数据的所在位置、谁有权访问它、如何处理以及如何保护它。其他要求可能规定你的云服务提供商需要具备某些合规认证。

不经意地将数据转移到云端或迁移到错误的提供商可能会使你的公司处于不合规状态，带来严重的法律和财务后果（我们已在第 4 章《数据处理》中谈到过数据传输和 Schrems II 判决）。

### 缺乏云安全策略和架构

你可以轻松避免这种云安全风险，但许多人并未做到。在急于将系统和数据迁移到云端时，许多公司在用于防御基础设施的安全机制和计划到位之前就开始运营。

确保在将系统和数据部署到云端之前创建云特定安全策略和架构。

### 内部威胁

你最信任的员工、承包商和业务合作伙伴可能构成最大的安全威胁。这些内部风险即使没有恶意也可能对你的组织造成伤害。事实上，大多数内部事件都是由于培训不足或粗心大意造成的。

尽管你现在会遇到这种困难，但转向云端会改变风险。当你将数据管理转移给云服务提供商时，你会产生由该公司员工构成的新一层内部威胁。

### 合同违规

你拥有的任何合同关系都会对共享数据的用途、存储和允许访问范围施加限制。未经授权将受限数据无意转移到云提供商可能构成合同违规并导致法律诉讼。

务必阅读云提供商的条款和条件。即使你有权限将数据转移到云端，多个服务提供商保留共享上传到其基础设施的任何数据的权利。你可能因无知而意外违反保密协议。

### 未受保护的用户界面（API）

在云基础设施上运行系统时，你可以通过 API 实现控制。包含在你的网络或移动应用中的任何 API 都可以被内部和外部访问。

外部 API 可能会对云造成安全风险。任何未受保护的外部 API 都会为窃贼提供未经授权的访问权限以窃取数据和修改服务。

Facebook–剑桥分析丑闻是未安全外部 API 的最著名实例。剑桥分析通过 Facebook 未受保护的外部 API 获得了对 Facebook 用户数据的广泛访问。

### 云服务配置错误

另一个可能的云安全问题是云服务配置错误。随着服务范围和复杂性的扩大，这是一个日益增长的问题。云服务的配置错误可能导致数据暴露给公众、被篡改甚至被删除。

常见原因包括对极其敏感的数据保留默认的安全和访问控制设置。其他原因包括访问管理不匹配，导致未经授权的用户获得访问权限，以及非预期的数据访问，即个人信息的访问未获授权而被遗留开放。

### 云与 GDPR 问题

尽管 GDPR 采用基于风险的数据保护方法，但它并未直接提及云。然而，该法规是技术中立的，即无论使用何种方法处理个人数据均适用。云的碎片化处理环境，其中此类标准可能并不总是适用，使得实施 GDPR 变得困难。以下各节详细分解了这些挑战。

## 云特有的安全问题

**欧洲数据保护监督员 (EDPS)** 和 **欧洲联盟网络和信息安全局 (ENISA)** 表示，与云基础设施的不同服务和部署模型相关的特定功能和流程，与“传统”本地数据中心相比意味着特定的风险。

**NIST** 定义了三种服务模型（SaaS、PaaS 和 IaaS）和四种部署模型：公共、私有、社区和混合（前三种模型的组合）云环境。每种都代表不同的外包模式，具有不同的安全和隐私风险。

其中一些安全任务（例如监控、修补和事件响应）被外包。根据云服务类型，部分任务仍由客户负责，而其他任务仍由提供商负责。责任划分有时会成为问题的重大来源，因为它通常基于假设且记录不完善，导致重叠和空白。例如，在 IaaS/PaaS 中，客户在其云服务之上运行自己的代码，并且通常仍对该（应用）软件负责。而在 SaaS 中，应用软件通常由提供商控制。

因此，客户对安全责任感到困惑并不罕见——即哪些安全任务外包给提供商，哪些安全任务仍由其自身负责。

如果没有适当的程序，就可能无法追踪谁在使用你的云服务，包括他们访问、发布和下载的信息。

只要记住，云中的资产可能不可见。而如果不可见，就无法得到保护，从而增加数据丢失和数据泄露的可能性。

当然，适用于本地的相同或类似控制措施也适用于云。

### 合规违规

随着监管监督的扩大，你必须遵守各种严格的合规标准。如果不谨慎，迁移到云端可能会使你面临合规问题。

其中许多要求要求你的组织了解数据的所在位置、谁有权访问它、如何处理以及如何保护它。其他要求可能规定你的云服务提供商需要具备某些合规认证。

不经意地将数据转移到云端或迁移到错误的提供商可能会使你的公司处于不合规状态，带来严重的法律和财务后果（我们已在第 4 章《数据处理》中谈到过数据传输和 Schrems II 判决）。

### 缺乏云安全策略和架构

你可以轻松避免这种云安全风险，但许多人并未做到。在急于将系统和数据迁移到云端时，许多公司在用于防御基础设施的安全机制和计划到位之前就开始运营。

确保在将系统和数据部署到云端之前创建云特定安全策略和架构。

### 内部威胁

你最信任的员工、承包商和业务合作伙伴可能构成最大的安全威胁。这些内部风险即使没有恶意也可能对你的组织造成伤害。事实上，大多数内部事件都是由于培训不足或粗心大意造成的。

尽管你现在会遇到这种困难，但转向云端会改变风险。当你将数据管理转移给云服务提供商时，你会产生由该公司员工构成的新一层内部威胁。

### 合同违规

你拥有的任何合同关系都会对共享数据的用途、存储和允许访问范围施加限制。未经授权将受限数据无意转移到云提供商可能构成合同违规并导致法律诉讼。

务必阅读云提供商的条款和条件。即使你有权限将数据转移到云端，多个服务提供商保留共享上传到其基础设施的任何数据的权利。你可能因无知而意外违反保密协议。

### 未受保护的用户界面 (API)

在云基础设施上运行系统时，你可以通过 API 实现控制。包含在你的网络或移动应用中的任何 API 都可以被内部和外部访问。

外部 API 可能会对云造成安全风险。任何未受保护的外部 API 都会为窃贼提供未经授权的访问权限以窃取数据和修改服务。

Facebook–剑桥分析丑闻是未安全外部 API 的最著名实例。剑桥分析通过 Facebook 未受保护的外部 API 获得了对 Facebook 用户数据的广泛访问。

### 云服务配置错误

另一个可能的云安全问题是云服务配置错误。随着服务范围和复杂性的扩大，这是一个日益增长的问题。云服务的配置错误可能导致数据暴露给公众、被篡改甚至被删除。

常见原因包括对极其敏感的数据保留默认的安全和访问控制设置。其他原因包括访问管理不匹配，导致未经授权的用户获得访问权限，以及非预期的数据访问，即个人信息未获授权而被遗留可访问。

### 云与 GDPR 问题

尽管 GDPR 采用基于风险的数据保护方法，但它并未直接提及云。然而，该法规是技术中立的，即无论使用何种方法处理个人数据均适用。云的碎片化处理环境，其中此类标准可能并不总是适用，使得实施 GDPR 变得困难。以下各节详细分解了这些挑战。

## 云特有的安全问题

**欧洲数据保护监督员 (EDPS)** 和 **欧洲联盟网络和信息安全局 (ENISA)** 表示，与云基础设施的不同服务和部署模型相关的特定功能和流程，与“传统”本地数据中心相比意味着特定的风险。

**NIST** 定义了三种服务模型（SaaS、PaaS 和 IaaS）和四种部署模型：公共、私有、社区和混合（前三种模型的组合）云环境。每种都代表不同的外包模式，具有不同的安全和隐私风险。

其中一些安全任务（例如监控、修补和事件响应）被外包。根据云服务类型，部分任务仍由客户负责，而其他任务仍由提供商负责。责任划分有时会成为问题的重大来源，因为它通常基于假设且记录不完善，导致重叠和空白。例如，在 IaaS/PaaS 中，客户在其云服务之上运行自己的代码，并且通常仍对该（应用）软件负责。而在 SaaS 中，应用软件通常由提供商控制。

因此，客户对安全责任感到困惑并不罕见——即哪些安全任务外包给提供商，哪些安全任务仍由其自身负责。

## GDPR 对云行业有何影响？

在该规则颁布近 5 年后，企业仍难以遵守 GDPR 监管标准。此外，由于企业快速使用云服务，组织和云服务提供商都必须修改其业务模式。为了遵守法规，他们必须显著改变业务实践。GDPR 在第 4 章第 24–43 条中为数据控制者和处理者制定了具体要求。该法规概述了处理个人数据时必须遵循的义务、规范和指南。让我们更深入地研究该部分列出的规范，以便更好地理解 GDPR 对作为云服务提供商的数据控制者和处理者的影响。
