## 17 DevOps 最佳实践

我们已经读完了本书的最后一章，最后，在读完所有内容后，你可能会问自己：_有哪些最佳实践可以有效地实施开发运维（DevOps）文化？_

本章是对我们已经见过的 DevOps 良好实践的一个很好的概述，它将使你能够练习本书中看到的所有元素。

我们将讨论自动化、工具选择、**基础设施即代码（IaC）**、应用程序架构和基础设施设计方面的最佳实践。我们还将讨论在项目管理中应用的良好实践，以便于实施 DevOps 文化和实践。然后，我们将回顾 **持续集成/持续部署（CI/CD）** 管道、测试自动化以及将安全性集成到 DevOps 流程中的最佳实践。

最后，我们将以 DevOps 文化中监控的一些最佳实践结束本章。

### 自动化一切

当你想要在公司内实施 DevOps 实践时，重要的是要记住 DevOps 文化的目的：它能更快、以更短的周期交付应用程序的新版本。

为此，要应用的第一个良好实践是自动化所有部署、测试和保护应用程序及其基础设施的任务。确实，当任务手动执行时，其执行存在较高的出错风险。这些任务手动执行的事实会增加应用程序的部署周期。

此外，一旦这些任务在脚本中自动化，它们就可以轻松集成并在 CI/CD 管道中执行。自动化的另一个优势是，开发人员和运维团队可以花更多时间，并将工作重点放在其业务功能上。

在项目开发初期开始交付流程的自动化也很重要；这使我们能够更快、更早地提供反馈。

最后，自动化使得通过在每个操作上放置痕迹来改进部署监控成为可能，并允许你在出现问题时非常快速地进行备份和恢复。

因此，自动化部署将减少部署周期，团队现在可以负担得起以较小的迭代进行工作。因此，**上市时间（TTM）**将得到改善，并带来更高质量应用程序的额外好处。

- 自动化一切
- 选择合适的工具
- 将所有配置写成代码
- 设计系统架构
- 构建良好的 CI/CD 管道
- 集成测试
- 通过**开发安全运维（DevSecOps）**将安全性前移
- 监控你的系统
- 演进项目管理

然而，自动化和编排需要工具来实施，工具的选择是在实施 DevOps 文化时需要考虑的重要元素。

### 选择合适的工具

当一家公司想要应用 DevOps 文化时，面临的挑战之一是工具的选择。

确实，许多工具要么是付费的，要么是免费开源的，它们允许你对应用程序的源代码进行版本控制、处理自动化、实施 CI/CD 管道，以及测试和监控应用程序。

除了这些工具，脚本语言也被加入，例如 PowerShell、Bash 和 Python，它们也是 DevOps 工具套件的一部分，用于集成。

所以，我经常被问到的一个问题是：_我如何为我的公司和业务选择有用的合适的 DevOps 工具？_

事实上，为了回答这个问题，我们必须记住 Donovan Brown 提供的 DevOps 文化定义，该定义在 _第 1 章，DevOps 文化和基础设施即代码实践_ 中提到过，并在此复述：

> _"DevOps 文化是人员、流程和产品的结合，以便向最终用户持续交付价值。"_

这个定义的重要点是，DevOps 文化是 Dev、Ops、流程以及工具的_结合_。也就是说，使用的工具必须由 Dev 和 Ops 共享和使用，并应集成到同一流程中。换句话说，工具的选择取决于团队和公司模式。

还必须考虑财务体系，选择开源工具，这些工具通常是免费的；在公司 DevOps 转型的初期，使用它们更容易。付费工具并非如此，它们功能和支持当然更丰富，但需要大量投资。

关于脚本语言，我认为语言的选择应根据团队的知识来决定。例如，接受过 Linux 系统培训的 Ops 团队，使用 Bash 制作自动化脚本会比使用 PowerShell 更好。

在本书中，我们向你介绍了几种工具，其中一些是开源且免费的——例如 Terraform、Packer、Vault 和 Ansible——另一些是付费的——例如 Azure DevOps（超过五个用户）或 LaunchDarkly——这将帮助你选择最适合你的工具。

在对实施 DevOps 实践中的工具选择进行反思后，我们将探讨另一个良好实践，即将一切编码化。

### 将所有配置写成代码

在本书中，特别是在关于 IaC 的前三章中，我们已经看到，将所需的基础设施配置写成代码可以为团队和公司的生产力带来许多优势。

因此，将所有与基础设施配置相关的内容写成代码是一个非常好的实践。我们已经在 Terraform、Ansible 和 Packer 中实践过这一点，但还有许多其他工具可能更适合你的需求和组织。在这些工具中，我们不仅谈论主要编辑器，还谈论 **JavaScript 对象表示法（JSON）** 文件、Bash、PowerShell 和 Python 脚本，我们将应用这些脚本到此配置中。关键是拥有一个易于人类阅读的代码中的基础设施描述，以及适合你的工具，如前一节所讨论的。

此外，这种实践还在其他领域不断发展，如我们在 _第 14 章，DevOps 流程中的安全与 DevSecOps_ 中所见，使用 InSpec，它允许我们在代码中描述基础设施的合规性规则。

我们还在本书的几个章节中看到了这种 IaC 实践，即所谓的 **管道即代码（PaC）**，使用 GitLab CI、Travis CI、GitHub Actions，以及 Azure Pipelines，后者也允许 **YAML 不是标记语言（YAML）** 管道模式（此模式在本书中未讨论）。

将任何配置写成代码是 DevOps 文化中从项目一开始就要考虑的关键实践，适用于运维和开发团队。对于开发人员，还有关于设计应用程序和基础设施架构的良好实践，我们将在下一节讨论。

### 设计系统架构

几年前，同一应用程序的所有服务都在同一个应用程序块中_编码_。这种架构设计是合理的，因为应用程序是按照瀑布模型管理的（https://activecollab.com/blog/project-management/waterfall-project-management-methodology），因此应用程序的新版本会在非常长的周期内部署。自那时起，软件工程实践发生了许多变化，从采用敏捷方法和 DevOps 文化开始，然后随着云的到来而继续。

这种演进带来了许多改进，不仅在应用程序方面，也在其基础设施方面。

然而，为了利用有效的 DevOps 文化在云中部署应用程序，在设计软件架构和基础设施架构时都有需要考虑的良好实践。

首先，云架构师必须与开发人员（或解决方案架构师）密切合作，以确保所开发的应用程序与架构的不同组件保持一致，并且架构也考虑到应用程序的不同约束。

除了这种协作，安全团队还必须提供将由开发人员和云架构师实施的规范。

为了能够更频繁地部署应用程序的新版本，而不必影响其所有功能，一个良好的实践是首先将应用程序的不同领域分离到独立的代码中，然后在后期分离到不同的部门。这样，分离的代码将更加易于维护和扩展，并且可以更快地部署，而无需重新部署所有内容。

> **注意**
> 将代码分离到多个服务的方法属于称为**微服务**的架构模式；要了解更多信息，请阅读以下综合文章：https://microservices.io/patterns/microservices.html。

然而，一旦解耦，仍然需要控制依赖关系，以便实施一个考虑应用程序所有依赖关系的 CI/CD 管道。





### 构建良好的 CI/CD 流水线

在本书中，我们专门用整个章节（第 7 章，持续集成与持续交付）来介绍如何使用 GitLab CI、Jenkins 和 Azure Pipelines 等不同工具构建 CI/CD 流水线，其中已提及构建 CI/CD 流水线的先决条件。

我们还在第 16 章（开源项目的 DevOps）中讨论了 CI/CD 流程，并举例介绍了面向开源项目的 CI 流水线，例如 Travis CI 和 GitHub Actions。

构建良好的 CI/CD 流水线确实是 DevOps 文化中的关键实践，配合正确的工具选择，可实现更快速的部署和更高质量的应用程序。

CI/CD 流水线的最佳实践之一是在项目启动阶段就尽早构建它们。这一点对于 CI 流水线尤其重要，它能够在编写第一行代码时就验证代码（至少是编译步骤）。随后，一旦首个环境被配置好，应立即创建部署流水线，以便在该环境中部署和测试应用程序。CI/CD 流水线流程的其余任务，例如单元测试执行，可随项目进展逐步开展。

此外，优化 CI/CD 流水线流程也很重要，即构建运行速度快的流水线。这些流水线可为团队成员（尤其是 CI 流水线）提供快速反馈，并避免阻塞其他可能正在排队的流水线的执行队列。

因此，如果某些流水线运行时间过长（例如集成测试，可能会很耗时），则将其执行安排在活动较少的时段（例如夜间）可能是个好主意。

最后，保护 CI/CD 流水线中嵌入的敏感数据也很重要。因此，如果在流水线中使用配置管理工具，请勿将密码、连接字符串和令牌等信息暴露给所有用户。

为保护这些数据，请使用集中式密钥管理工具，例如我们在第 14 章（DevOps 流程中的安全性与 DevSecOps）中介绍的 Vault；如果你拥有 Azure 订阅，也可以使用 Azure Key Vault（AKV）。

以上是 CI/CD 流水线实施的一些最佳实践；我们在本书的不同章节以及其他专门介绍 DevOps 文化的书籍中，还提及了其他可供研究的 CI/CD 流水线良好实践。

作为对 CI/CD 流水线良好实践的延续，让我们来回顾一下将测试集成到 DevOps 流程中的良好实践。

### 集成测试

在当今世界，测试是 DevOps 流程的重要组成部分，也是开发实践的重要组成部分。确实，即使拥有能够自动化所有交付阶段的最佳 DevOps 流水线，如果没有集成测试，其效率也将几乎丧失。就我而言，我认为 DevOps 流程的最低要求是至少集成应用程序的单元测试执行。此外，这些单元测试应从应用程序的第一行代码开始编写，采用测试驱动开发（TDD）（https://hackernoon.com/introduction-to-test-driven-development-tdd-61a13bc92d92）和行为驱动开发（BDD）等测试实践，这样就可以将这些测试的自动执行集成到 CI 流水线中。

但是，集成其他类型的测试（例如功能测试或集成测试）也很重要，这些测试可以让应用程序与其生态系统中的其他组件一起，从头到尾进行功能测试。

当然，执行这些测试可能需要时间；在这种情况下，可以将其执行安排在夜间。但这些集成测试将保证应用程序在交付的所有阶段（从部署到生产）都能平稳运行。

然而，在 CI 流水线中禁用测试执行（以防测试执行失败）往往是一种非常糟糕的实践。这通常是为了避免阻塞完整的 CI 流程，从而更快地交付到生产环境。但请记住，单元测试检测到的错误（包括那些本应被已禁用的测试检测到的错误），最终都会在生产阶段被发现，而修复失败代码所花费的时间，将比在 CI 期间启用测试时更长。

我们还在本书中了解了其他类型的测试，例如代码分析测试或安全测试，这些测试不容忽视。越早将它们集成到 CI/CD 流水线中，就能为代码维护和应用程序安全性增加更多价值。

总结来说，你不应忽视在应用程序中实施测试以及将其集成到 CI/CD 流水线中，因为它们保证了应用程序的质量。

在介绍完测试集成的良好实践后，我建议你了解一下在 CI/CD 流程中集成安全性的良好实践。

### 通过 DevSecOps 将安全性前移

正如我们在第 14 章（DevOps 流程中的安全性与 DevSecOps）中讨论的那样，安全性和合规性分析必须成为 DevOps 流程的一部分。然而，在公司中，开发团队往往缺乏对安全规则的认识，这就是为什么安全性在 DevOps 流程中被实施得太晚。

为了将安全性集成到流程中，有必要提高开发人员对应用程序代码安全性方面的认识，同时也要提高对 CI/CD 流水线配置保护的认识。

此外，还需要消除 DevOps 与安全性之间的壁垒，更频繁地将安全团队纳入将 Dev 和 Ops 团队聚集在一起的各种会议中，从而确保开发人员、运维团队以及安全团队之间更好的一致性。关于工具选择，不要使用过多不同的工具，因为目标是这些工具也能被开发人员使用，并集成到 CI/CD 流水线中。因此，有必要选择少数几个自动化、无需深厚安全知识且能提供报告以便更好分析的工具。

最后，如果你不知道从哪里开始分析应用程序的安全性，可以使用社区认可的简单安全规则，例如我们在第 13 章（安全性和性能测试）中介绍的 Open Web Application Security Project（OWASP）十大规则（`https://www.owasp.org/index.php/Category:OWASP_Top_Ten_Project`）。你可以使用 Zed Attack Proxy（ZAP）工具，它使用这 10 条规则，来对 Web 应用程序进行安全测试。

这些是将安全性集成到 DevOps 文化中以实现 DevSecOps 文化的一些良好实践。我们现在将查看一些监控方面的良好实践。

### 监控你的系统

DevOps 文化成功的主要要素之一，是实施能够持续监控系统和应用程序状态的工具。监控必须在系统的所有级别实施，并让所有团队参与，目标是为最终用户提供具有真正附加价值的应用程序。

确实，首先可以监控的组件是应用程序本身，通过尽早实施日志记录或跟踪系统来收集应用程序使用情况的信息。然后，我们将测量和监控基础设施的状态，例如虚拟机（VM）的随机存取存储器（RAM）和中央处理器（CPU）级别，或网络带宽。最后，必须监控的最后一个元素是 DevOps 流程的状态。因此，拥有 CI/CD 流水线执行的指标非常重要，例如流水线执行时间的信息，或执行成功或失败的流水线数量。有了这些数据，例如，我们可以确定应用程序的部署速度。

有许多监控工具，例如 Prometheus、Grafana、New Relic、Nagios 等，以及集成到各种云提供商的工具，例如 Azure Application Insights 或 Azure Monitor Logs。

关于监控的良好实践，我认为重要的是针对对你来说必要且易于分析的关键绩效指标（KPI）。拥有一个捕获大量数据或编写大量日志的应用程序是没有用的，因为分析这些信息太耗时。此外，关于捕获数据的数量，我们需要注意确保其保留期。数据的保留时间必须经过评估，并应咨询不同团队。保留时间过长可能导致 VM 容量饱和或云托管组件的高成本，而保留时间过短，日志历史会更短，因此你可能会丢失对任何问题的追踪。





最后，在选择工具时，必须确保它能保护所有被捕获的数据，工具呈现的仪表板所有团队成员都能充分理解，并且它已集成到 DevOps 流程中。

我们已经解释过，监控是一种必须融入 DevOps 文化的实践，需要考虑一些良好实践要点，这些要点可以改善开发与运维之间的沟通，并提升最终用户的产品质量。

在回顾了 DevOps 最佳实践（包括自动化、CI/CD 流水线和监控）之后，我们将概述项目管理和团队组织方面的 DevOps 实践。

### 演进项目管理

我们之前讨论过一些可应用于项目的良好 DevOps 实践，但所有这些只有在项目管理方式和团队组织方式发生改变后，才能得以实施和实现。

以下是一些可以促进企业内项目管理中 DevOps 文化实施的良好实践。

首先，应该牢记，DevOps 文化只有在实施开发和交付实践（这些实践将允许以短部署周期交付应用程序）时才有意义。因此，为了适用，项目也必须以短周期进行管理。为了实现这一点，近年来已被证明是有效的、最适合应用 DevOps 文化的项目管理方法之一是敏捷方法，它使用冲刺（2 到 3 周的短周期）以及增量式、迭代式部署和开发人员之间的强强协作。

DevOps 文化只是通过促进多个领域（开发/运维/安全/测试人员）之间的协作来扩展敏捷方法论。

> **注意**
> 要了解有关敏捷方法及其不同框架（例如 Scrum 和极限编程 (XP)）的更多信息，我推荐 `http://agilemethodology.org/`，该网站提供了大量文档。

此外，为了更好地应用 DevOps 实施，重要的是改变你的组织，不再按专业领域组建团队，例如拥有一个开发人员团队、另一个运维团队和一个测试人员团队。这种组织模式的问题是团队被隔离，导致沟通不畅（我们在第一章“DevOps 文化和基础设施即代码实践”中看到的混乱之墙）。这意味着不同的团队有不同的目标，这会阻碍 DevOps 文化良好实践的应用。

一种允许更好沟通的模式是功能团队组织，由多学科项目团队组成，这些团队由来自所有领域的人员组成。在一个团队中，我们有开发人员、运维人员和测试人员，所有这些人都以相同的目标工作。

如果你想了解更多关于 Microsoft 的 DevOps 转型信息，我建议你观看 Donovan Brown 在 https://www.agilealliance.org/resources/sessions/microsoft-devops-transformation-donovan-brown/ 上的演示，该演示解释了 Microsoft 如何改变其组织以适应 DevOps 文化，以便在考虑用户需求的同时持续改进其产品。

我们刚刚看到，要在企业中实施 DevOps 文化，需要进行组织变革，包括敏捷项目管理和多学科团队的组成。

### 总结

在本最终章节中，我们看到，在项目中实施 DevOps 文化需要使用关于所有手动任务自动化、正确选择工具、非单体项目架构以及监控实施的最佳实践。

在大规模上，对于团队和整个公司的组织，我们看到敏捷方法以及多学科团队对 DevOps 文化的实施有很大贡献。

为了结束本书，我对所有正在采用 DevOps 实践的读者的建议是：在小型项目上实施和监控它们，并从使用对你最熟悉且最易访问的工具开始。然后，一旦你的 DevOps 流程正常运行，就可以将其扩展到更大的项目。

### 第 1 章：DevOps 文化和基础设施即代码实践

- 1. DevOps 是由 *Development* 和 *Operations* 两个词组合而成的缩写。
- 2. DevOps 是一个代表文化的术语。
- 3. DevOps 文化的三个轴心是协作、流程和工具。
- 4. 持续集成的目标是快速获得团队成员存档代码质量的反馈。
- 5. 持续交付和持续部署之间的区别在于，持续交付的生产部署触发是手动进行的，而持续部署则是自动进行的。
- 6. 基础设施即代码是指编写构成基础设施的资源代码。

### 第 2 章：使用 Terraform 配置云基础设施

- 1. Terraform 使用的语言是 HashiCorp 配置语言 (HCL)。

- 6. Terraform 的三个主要命令是 `terraform init`、`terraform plan` 和 `terraform apply`。

### 第 3 章：使用 Ansible 配置 IaaS 基础设施
