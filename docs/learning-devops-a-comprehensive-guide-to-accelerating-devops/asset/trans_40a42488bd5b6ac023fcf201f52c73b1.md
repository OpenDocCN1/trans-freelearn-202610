

## 构建良好的 CI/CD 流水线

在本书中，我们专门用整个章节（第 7 章，持续集成与持续交付）来介绍如何使用 GitLab CI、Jenkins 和 Azure Pipelines 等不同工具构建 CI/CD 流水线，其中已提及构建 CI/CD 流水线的先决条件。

我们还在第 16 章（开源项目的 DevOps）中讨论了 CI/CD 流程，并举例介绍了面向开源项目的 CI 流水线，例如 Travis CI 和 GitHub Actions。

构建良好的 CI/CD 流水线确实是 DevOps 文化中的关键实践，配合正确的工具选择，可实现更快速的部署和更高质量的应用程序。

CI/CD 流水线的最佳实践之一是在项目启动阶段就尽早构建它们。这一点对于 CI 流水线尤其重要，它能够在编写第一行代码时就验证代码（至少是编译步骤）。随后，一旦首个环境被配置好，应立即创建部署流水线，以便在该环境中部署和测试应用程序。CI/CD 流水线流程的其余任务，例如单元测试执行，可随项目进展逐步开展。

此外，优化 CI/CD 流水线流程也很重要，即构建运行速度快的流水线。这些流水线可为团队成员（尤其是 CI 流水线）提供快速反馈，并避免阻塞其他可能正在排队的流水线的执行队列。

因此，如果某些流水线运行时间过长（例如集成测试，可能会很耗时），则将其执行安排在活动较少的时段（例如夜间）可能是个好主意。

最后，保护 CI/CD 流水线中嵌入的敏感数据也很重要。因此，如果在流水线中使用配置管理工具，请勿将密码、连接字符串和令牌等信息暴露给所有用户。

为保护这些数据，请使用集中式密钥管理工具，例如我们在第 14 章（DevOps 流程中的安全性与 DevSecOps）中介绍的 Vault；如果你拥有 Azure 订阅，也可以使用 Azure Key Vault（AKV）。

以上是 CI/CD 流水线实施的一些最佳实践；我们在本书的不同章节以及其他专门介绍 DevOps 文化的书籍中，还提及了其他可供研究的 CI/CD 流水线良好实践。

作为对 CI/CD 流水线良好实践的延续，让我们来回顾一下将测试集成到 DevOps 流程中的良好实践。

## 集成测试

在当今世界，测试是 DevOps 流程的重要组成部分，也是开发实践的重要组成部分。确实，即使拥有能够自动化所有交付阶段的最佳 DevOps 流水线，如果没有集成测试，其效率也将几乎丧失。就我而言，我认为 DevOps 流程的最低要求是至少集成应用程序的单元测试执行。此外，这些单元测试应从应用程序的第一行代码开始编写，采用测试驱动开发（TDD）（https://hackernoon.com/introduction-to-test-driven-development-tdd-61a13bc92d92）和行为驱动开发（BDD）等测试实践，这样就可以将这些测试的自动执行集成到 CI 流水线中。

但是，集成其他类型的测试（例如功能测试或集成测试）也很重要，这些测试可以让应用程序与其生态系统中的其他组件一起，从头到尾进行功能测试。

当然，执行这些测试可能需要时间；在这种情况下，可以将其执行安排在夜间。但这些集成测试将保证应用程序在交付的所有阶段（从部署到生产）都能平稳运行。

然而，在 CI 流水线中禁用测试执行（以防测试执行失败）往往是一种非常糟糕的实践。这通常是为了避免阻塞完整的 CI 流程，从而更快地交付到生产环境。但请记住，单元测试检测到的错误（包括那些本应被已禁用的测试检测到的错误），最终都会在生产阶段被发现，而修复失败代码所花费的时间，将比在 CI 期间启用测试时更长。

我们还在本书中了解了其他类型的测试，例如代码分析测试或安全测试，这些测试不容忽视。越早将它们集成到 CI/CD 流水线中，就能为代码维护和应用程序安全性增加更多价值。

总结来说，你不应忽视在应用程序中实施测试以及将其集成到 CI/CD 流水线中，因为它们保证了应用程序的质量。

在介绍完测试集成的良好实践后，我建议你了解一下在 CI/CD 流程中集成安全性的良好实践。

## 通过 DevSecOps 将安全性前移

正如我们在第 14 章（DevOps 流程中的安全性与 DevSecOps）中讨论的那样，安全性和合规性分析必须成为 DevOps 流程的一部分。然而，在公司中，开发团队往往缺乏对安全规则的认识，这就是为什么安全性在 DevOps 流程中被实施得太晚。

为了将安全性集成到流程中，有必要提高开发人员对应用程序代码安全性方面的认识，同时也要提高对 CI/CD 流水线配置保护的认识。

此外，还需要消除 DevOps 与安全性之间的壁垒，更频繁地将安全团队纳入将 Dev 和 Ops 团队聚集在一起的各种会议中，从而确保开发人员、运维团队以及安全团队之间更好的一致性。关于工具选择，不要使用过多不同的工具，因为目标是这些工具也能被开发人员使用，并集成到 CI/CD 流水线中。因此，有必要选择少数几个自动化、无需深厚安全知识且能提供报告以便更好分析的工具。

最后，如果你不知道从哪里开始分析应用程序的安全性，可以使用社区认可的简单安全规则，例如我们在第 13 章（安全性和性能测试）中介绍的 Open Web Application Security Project（OWASP）十大规则（`https://www.owasp.org/index.php/Category:OWASP_Top_Ten_Project`）。你可以使用 Zed Attack Proxy（ZAP）工具，它使用这 10 条规则，来对 Web 应用程序进行安全测试。

这些是将安全性集成到 DevOps 文化中以实现 DevSecOps 文化的一些良好实践。我们现在将查看一些监控方面的良好实践。

## 监控你的系统

DevOps 文化成功的主要要素之一，是实施能够持续监控系统和应用程序状态的工具。监控必须在系统的所有级别实施，并让所有团队参与，目标是为最终用户提供具有真正附加价值的应用程序。

确实，首先可以监控的组件是应用程序本身，通过尽早实施日志记录或跟踪系统来收集应用程序使用情况的信息。然后，我们将测量和监控基础设施的状态，例如虚拟机（VM）的随机存取存储器（RAM）和中央处理器（CPU）级别，或网络带宽。最后，必须监控的最后一个元素是 DevOps 流程的状态。因此，拥有 CI/CD 流水线执行的指标非常重要，例如流水线执行时间的信息，或执行成功或失败的流水线数量。有了这些数据，例如，我们可以确定应用程序的部署速度。

有许多监控工具，例如 Prometheus、Grafana、New Relic、Nagios 等，以及集成到各种云提供商的工具，例如 Azure Application Insights 或 Azure Monitor Logs。

关于监控的良好实践，我认为重要的是针对对你来说必要且易于分析的关键绩效指标（KPI）。拥有一个捕获大量数据或编写大量日志的应用程序是没有用的，因为分析这些信息太耗时。此外，关于捕获数据的数量，我们需要注意确保其保留期。数据的保留时间必须经过评估，并应咨询不同团队。保留时间过长可能导致 VM 容量饱和或云托管组件的高成本，而保留时间过短，日志历史会更短，因此你可能会丢失对任何问题的追踪。
